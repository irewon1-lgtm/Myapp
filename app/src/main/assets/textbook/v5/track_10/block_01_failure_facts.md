## CHAPTER 01 · LESSON 01 · 버그의 증상과 원인을 분리한다

**LESSON ID:** `T10-B01-L01`

### 먼저 쉬운 말로 이해하기

프로그램이 “안 된다”는 말에는 정보가 거의 없다. 버튼을 눌렀는데 화면이 멈췄다는 것은 **증상**이고, 이벤트 함수가 호출되지 않았는지, 호출됐지만 예외가 났는지, 서버 응답이 늦는지는 아직 **원인 후보**다. 처음 배우는 사람이 가장 먼저 바꿔야 할 습관은 증상을 본 순간 원인을 단정하지 않는 것이다.

### 안에서는 실제로 무엇이 일어나는가

디버깅은 관찰 가능한 현상을 더 작은 단계로 쪼개는 작업이다. 입력이 들어왔는지, 분기 조건을 통과했는지, 함수가 반환됐는지, 외부 시스템이 응답했는지를 순서대로 확인하면 원인 공간이 줄어든다. 같은 증상도 서로 다른 원인으로 생길 수 있으므로 `symptom → evidence → hypothesis → experiment` 순서를 유지한다.

### 아주 쉬운 예

두 숫자를 나누는 함수가 특정 입력에서 실패한다고 하자. “나눗셈 함수가 고장 났다”라고 단정하지 말고 어떤 입력에서 어떤 결과가 나왔는지 먼저 적는다.

```python
def divide(a, b):
    return a / b

print(divide(10, 2))
print(divide(10, 0))
```

### 한 줄씩 읽기

- `divide(10, 2)`는 정상 사례를 하나 만든다.
- `divide(10, 0)`은 같은 함수에 실패 입력을 넣어 증상을 재현한다.
- 두 호출이 같은 함수라는 사실 때문에 “함수 전체가 항상 고장”이라는 가설은 바로 약해진다.

### 직접 실행

1. 파일을 `symptom.py`로 저장하고 `python symptom.py`를 실행한다.
2. 첫 출력 `5.0` 뒤에 어떤 예외 이름과 어느 줄 번호가 나오는지 기록한다.
3. 코드를 고치기 전에 실패 입력 `b=0`이 실제로 들어갔다는 사실만 적는다.


### 일부를 바꿔서 다시 확인하기

두 번째 호출의 `0`을 `1`로 바꾼다. 실패가 사라지면 “0이라는 입력과 관련 있다”는 증거는 늘지만, 이것만으로 올바른 해결책이 무엇인지는 아직 결정되지 않는다. 0을 금지할지, 별도 값을 반환할지, 사용자 입력을 앞에서 막을지는 요구사항에 따라 달라진다.

### 작은 문제

어떤 앱이 저장 버튼을 누르면 꺼진다. 개발자가 “DB 버그다”라고 말했다. 지금 확보된 사실은 무엇이고, 아직 가설인 것은 무엇인가?

### 왜 맞고 왜 틀리는가

확실한 사실은 “특정 동작 뒤 앱이 종료되었다” 정도다. DB가 원인이라는 말은 로그·stack trace·재현 실험으로 확인하기 전에는 가설이다. DB 호출 전에 이미 null 오류가 났을 수도 있고, 응답 parsing에서 예외가 났을 수도 있다.

### 자주 만나는 실패와 확인 순서

- 증상을 원인 이름으로 바꿔 부르면 조사 범위가 잘못 고정된다.
- 첫 수정 뒤 증상이 사라져도 우연·캐시·다른 상태 변화인지 확인하지 않으면 오판할 수 있다.

### 이번 LESSON에서 구분할 것

- **암기 최소선:** 증상은 관찰된 현상, 원인은 그 현상을 만든 실제 메커니즘이다.
- **직접 코딩·실행해서 익힐 것:** 실패를 일부러 재현하고 입력·출력·예외 위치를 기록한다.
- **AI에게 맡겨도 되는 것:** 가능한 원인 목록 생성, 로그 해석 보조, 재현용 테스트 초안 작성.
- **사람이 최종 확인할 것:** 어떤 가설이 실제 증거로 지지되는지와 수정이 요구사항에 맞는지 확인한다.

### 근거 연결

## CHAPTER 02 · LESSON 02 · 기대값과 실제값을 한 문장으로 쓴다

**LESSON ID:** `T10-B01-L02`

### 먼저 쉬운 말로 이해하기

버그 보고에는 “이상하다”보다 **기대값과 실제값의 차이**가 필요하다. 기대값은 내가 바라는 값이 아니라 요구사항·계약·테스트에서 정한 값이어야 한다. 실제값은 방금 실행해서 관찰한 값이다.

### 안에서는 실제로 무엇이 일어나는가

비교가 가능해야 실패를 자동으로 검출할 수 있다. `expected == actual` 같은 단순 비교부터 HTTP status, DB row, 파일 hash, UI 상태까지 같은 원리가 적용된다. 기대값이 불명확하면 테스트도 불명확하고, 버그 수정이 끝났는지도 판정할 수 없다.

### 아주 쉬운 예

배송비 규칙이 “5만원 이상 무료”라면 경계값 50,000원이 핵심이다.

```python
def shipping_fee(total):
    if total > 50000:
        return 0
    return 3000

expected = 0
actual = shipping_fee(50000)
print("expected:", expected)
print("actual:", actual)
```

### 한 줄씩 읽기

- 조건이 `>`이므로 정확히 50,000원은 참이 아니다.
- `expected = 0`은 요구사항을 코드 밖에서 명시한다.
- `actual`은 함수를 실제 실행한 결과라서 둘을 직접 비교할 수 있다.

### 직접 실행

1. `python expected_actual.py`를 실행한다.
2. `expected`와 `actual`이 다르게 출력되는지 확인한다.
3. 조건을 고치기 전 요구사항 문장 “5만원 이상”과 코드의 `>`를 나란히 둔다.


### 일부를 바꿔서 다시 확인하기

`>`를 `>=`로 바꾼 뒤 49,999원, 50,000원, 50,001원 세 입력을 실행한다. 한 사례만 맞추는 수정이 아니라 경계 주변에서 규칙이 유지되는지 확인한다.

### 작은 문제

실패한 테스트가 하나 있다. 기대값을 실제값과 같게 바꾸면 테스트가 통과한다. 이것을 버그 수정이라고 불러도 되는가?

### 왜 맞고 왜 틀리는가

아니다. 요구사항이 그대로인데 기대값만 실제 구현에 맞춰 바꾸면 테스트가 실패를 숨길 수 있다. 요구사항이 바뀐 경우에만 기대값 변경이 정당화된다. 구현 수정과 사양 변경을 구분해야 한다.

### 자주 만나는 실패와 확인 순서

- 요구사항 출처 없이 기대값을 만들면 테스트가 개인 취향 검사가 된다.
- 경계값을 빼고 평균적인 값만 검사하면 `>`/`>=` 같은 결함을 놓치기 쉽다.

### 이번 LESSON에서 구분할 것

- **암기 최소선:** 버그 보고는 “조건·기대·실제”를 포함해야 한다.
- **직접 코딩·실행해서 익힐 것:** 경계값을 직접 실행하고 기대/실제 차이를 숫자로 확인한다.
- **AI에게 맡겨도 되는 것:** 테스트 데이터 생성과 경계 후보 제안.
- **사람이 최종 확인할 것:** 기대값의 근거가 실제 요구사항인지, 테스트를 통과시키려고 바꾼 것인지 판단한다.

## CHAPTER 03 · LESSON 03 · 재현 절차를 다른 사람이 따라 할 수 있게 만든다

**LESSON ID:** `T10-B01-L03`

### 먼저 쉬운 말로 이해하기

내 컴퓨터에서 한 번 실패한 것과 **재현 가능한 버그**는 다르다. 재현 절차는 시작 상태, 입력, 행동 순서, 관찰 결과를 적어 다른 사람이나 미래의 내가 같은 실패를 다시 만들 수 있게 한다.

### 안에서는 실제로 무엇이 일어나는가

재현 절차가 고정되면 수정 전후를 같은 조건에서 비교할 수 있다. 반대로 절차가 매번 달라지면 수정 효과와 환경 차이를 구분하기 어렵다. 자동 테스트는 결국 재현 절차를 기계가 반복할 수 있는 형태로 옮긴 것이라고 볼 수 있다.

### 아주 쉬운 예

장바구니 합계가 가끔 틀리다면 상품 이름만 적는 대신 정확한 시작 상태와 순서를 기록한다.

```python
def total(cart):
    return sum(item["price"] * item["qty"] for item in cart)

cart = [
    {"price": 1200, "qty": 2},
    {"price": 500, "qty": 3},
]
print(total(cart))
```

### 한 줄씩 읽기

- `cart` 값 자체가 재현에 필요한 입력이다.
- 수량과 가격을 코드에 고정했기 때문에 같은 실행은 같은 계산 조건을 가진다.
- 출력만 복사하지 말고 어떤 입력으로 그 출력이 나왔는지 함께 남긴다.

### 직접 실행

1. 코드를 실행해 현재 합계를 기록한다.
2. 두 번째 수량을 `3`에서 `-1`로 바꿔 비정상 입력을 만든다.
3. 실패 보고에 “초기 cart 값 → total 호출 → 실제 결과”를 적는다.


### 일부를 바꿔서 다시 확인하기

재현 절차에서 필요 없는 단계를 하나씩 제거한다. 로그인, 화면 이동, 여러 데이터 생성 중 어느 단계가 없어도 같은 실패가 나면 그 단계는 최소 재현에서는 제외할 수 있다.

### 작은 문제

“어제 오후에 앱을 쓰다가 한 번 튕겼다”는 보고만 있다. 첫 번째로 추가해야 할 정보는 무엇인가?

### 왜 맞고 왜 틀리는가

정확한 행동 순서와 시작 상태, 입력, 버전/환경, 관찰된 오류를 모아야 한다. 원인 추측보다 먼저 같은 현상을 다시 만드는 조건을 찾는 것이 우선이다.

### 자주 만나는 실패와 확인 순서

- 재현 전에 코드를 여러 군데 바꾸면 어떤 변경이 증상을 바꿨는지 알기 어렵다.
- 재현 단계에 계정 비밀번호나 실제 고객 개인정보를 그대로 복사하면 보안 사고가 될 수 있다.

### 이번 LESSON에서 구분할 것

- **암기 최소선:** 재현 절차는 시작 상태·행동·입력·기대·실제를 포함한다.
- **직접 코딩·실행해서 익힐 것:** 다른 사람이 그대로 따라 할 수 있는 최소 절차를 직접 작성한다.
- **AI에게 맡겨도 되는 것:** 긴 로그에서 행동 순서 후보 정리, 자동 재현 스크립트 초안.
- **사람이 최종 확인할 것:** 민감정보를 제거하고도 실패가 재현되는지, 절차가 실제로 반복 가능한지 확인한다.

## CHAPTER 04 · LESSON 04 · 환경을 고정해 “내 컴퓨터에서는 된다”를 해체한다

**LESSON ID:** `T10-B01-L04`

### 먼저 쉬운 말로 이해하기

같은 소스 코드라도 Python 버전, 운영체제, dependency 버전, locale, timezone, 환경변수, 파일 권한이 다르면 결과가 달라질 수 있다. “내 컴퓨터에서는 된다”는 말은 해결이 아니라 **환경 차이를 조사하라는 신호**다.

### 안에서는 실제로 무엇이 일어나는가

프로그램의 실제 동작은 소스 코드만으로 결정되지 않는다. 실행기와 라이브러리, 설정, 외부 서비스가 함께 입력이 된다. 따라서 재현 기록에는 코드 commit뿐 아니라 실행 환경의 중요한 식별자도 필요하다.

### 아주 쉬운 예

날짜 parsing은 locale이나 timezone에서 차이가 잘 드러나는 예다. 여기서는 간단히 Python과 플랫폼 정보를 함께 출력한다.

```python
import platform, sys, os

print("python", sys.version.split()[0])
print("os", platform.system(), platform.release())
print("mode", os.getenv("APP_MODE", "unset"))
```

### 한 줄씩 읽기

- `sys.version`은 실행기 버전을 보여 준다.
- `platform` 값은 OS 차이를 확인하는 단서다.
- 환경변수는 코드 파일 밖에서 동작을 바꿀 수 있으므로 버그 보고에 중요할 수 있다.

### 직접 실행

1. 스크립트를 실행해 세 줄을 저장한다.
2. `APP_MODE=test python env_info.py`처럼 환경변수를 바꿔 다시 실행한다.
3. 두 실행에서 코드가 같아도 환경 입력이 다르다는 점을 확인한다.


### 일부를 바꿔서 다시 확인하기

프로젝트의 dependency 목록과 lockfile이 있다면 버전도 함께 기록한다. 단, 비밀키가 들어간 `.env` 파일 전체를 버그 보고에 붙이지 않는다.

### 작은 문제

개발 PC에서는 성공하지만 CI에서만 실패한다. “CI가 이상하다”라고 결론내리기 전에 비교할 항목 세 가지를 말해 보라.

### 왜 맞고 왜 틀리는가

런타임 버전, dependency/lockfile 상태, 환경변수·권한·경로·timezone 같은 실행 환경을 우선 비교한다. 그다음 실행 명령과 입력 데이터를 확인한다.

### 자주 만나는 실패와 확인 순서

- 환경변수를 모두 출력하다 secret을 로그로 유출하는 실수가 흔하다.
- lockfile 없이 “최신 버전”을 다시 설치하면 어제와 오늘의 실험 조건이 달라질 수 있다.

### 이번 LESSON에서 구분할 것

- **암기 최소선:** 코드 commit과 실행 환경은 함께 재현 조건을 만든다.
- **직접 코딩·실행해서 익힐 것:** 런타임·OS·환경변수 차이를 직접 바꿔 결과를 비교한다.
- **AI에게 맡겨도 되는 것:** 환경 진단 명령 생성과 차이 목록 요약.
- **사람이 최종 확인할 것:** secret 노출 없이 필요한 환경만 기록했는지와 두 환경이 정말 동등한지 판단한다.

### 근거 연결

`NIST-SSDF-12` · `SLSA-12`

## CHAPTER 05 · LESSON 05 · FACT와 HYPOTHESIS를 따로 적는다

**LESSON ID:** `T10-B01-L05`

### 먼저 쉬운 말로 이해하기

디버깅 노트에서 가장 강력한 구분 중 하나가 `FACT`와 `HYPOTHESIS`다. FACT는 실행·로그·측정으로 확인한 사실이고 HYPOTHESIS는 그 사실을 설명하려는 가설이다. 둘을 같은 문장으로 섞으면 추측이 사실처럼 굳어진다.

### 안에서는 실제로 무엇이 일어나는가

가설은 틀려도 된다. 중요한 것은 반증 가능한 형태로 만드는 것이다. “서버가 이상하다”는 가설은 너무 넓지만 “요청이 handler에 도달하기 전에 인증 middleware가 401을 반환한다”는 가설은 로그 지점 두 곳으로 검사할 수 있다.

### 아주 쉬운 예

간단한 분기 코드에서 가설을 하나 세우고 출력으로 검증한다.

```python
def label(age):
    print("FACT: age=", age)
    if age >= 19:
        print("FACT: adult branch")
        return "adult"
    print("FACT: minor branch")
    return "minor"

print(label(18))
```

### 한 줄씩 읽기

- 입력값 출력은 관찰된 사실을 남긴다.
- 어느 branch를 탔는지 출력하면 control flow에 관한 사실이 생긴다.
- “조건식이 잘못됐다”는 말은 코드를 읽은 뒤 세우는 가설이며 실행 결과와 구분한다.

### 직접 실행

1. 실행하고 FACT 줄만 복사한다.
2. 가설을 “18이 adult branch로 들어간다”라고 세운다.
3. 실행 증거가 그 가설을 지지하는지 반박하는지 표시한다.


### 일부를 바꿔서 다시 확인하기

조건을 `> 19`로 일부러 바꾼 뒤 19를 넣어 같은 실험을 반복한다. 이전 가설과 새 증거가 어떻게 달라지는지 노트에 적는다.

### 작은 문제

로그에 `timeout`이라는 단어가 보였다. “DB가 느리다”를 FACT라고 적어도 되는가?

### 왜 맞고 왜 틀리는가

아니다. timeout 발생은 FACT가 될 수 있지만 어느 구간이 느렸는지는 추가 측정이 필요하다. DB, DNS, network, lock 대기 등 여러 가설이 가능하다.

### 자주 만나는 실패와 확인 순서

- 가설을 뒷받침하는 증거만 모으면 confirmation bias가 생긴다.
- FACT라고 적었지만 사실은 다른 사람이 추측한 내용을 옮겨 적는 경우가 있다.

### 이번 LESSON에서 구분할 것

- **암기 최소선:** FACT는 관찰·측정, HYPOTHESIS는 설명 후보다.
- **직접 코딩·실행해서 익힐 것:** 가설 하나를 세우고 그것을 반박할 수도 있는 실험을 만든다.
- **AI에게 맡겨도 되는 것:** 가설 후보 확장과 로그 분류.
- **사람이 최종 확인할 것:** 어떤 문장이 실제 증거인지, 가설이 반증 가능하게 쓰였는지 확인한다.

## CHAPTER 06 · LESSON 06 · 한 번에 한 가설만 검증한다

**LESSON ID:** `T10-B01-L06`

### 먼저 쉬운 말로 이해하기

버그가 나면 여러 줄을 한꺼번에 고치고 싶은 유혹이 크다. 하지만 동시에 세 가지를 바꾸고 성공하면 어떤 변경이 원인이었는지 모른다. **한 가설–한 실험**은 변화량을 작게 만들어 배운 정보를 선명하게 한다.

### 안에서는 실제로 무엇이 일어나는가

통제된 실험은 가능한 한 한 변수만 바꾸고 나머지를 유지한다. 소프트웨어에서는 완벽한 통제가 어려워도 commit, 입력, 환경, 실행 명령을 고정하고 특정 조건만 바꾸면 인과 추론이 훨씬 좋아진다.

### 아주 쉬운 예

문자열 공백 문제가 의심되면 대소문자 처리와 DB 조회까지 같이 바꾸지 말고 먼저 실제 문자열 표현을 확인한다.

```python
name = " alice "
print(repr(name))
print(name == "alice")
print(name.strip() == "alice")
```

### 한 줄씩 읽기

- `repr`은 눈에 잘 안 보이는 앞뒤 공백까지 드러낸다.
- 두 번째 비교는 원래 상태를 검사한다.
- 세 번째 비교만 공백 제거 가설을 시험한다.

### 직접 실행

1. 원본 그대로 실행한다.
2. `name`만 `"alice"`로 바꿔 다시 실행한다.
3. 두 실행에서 달라진 변수가 무엇인지 한 줄로 기록한다.


### 일부를 바꿔서 다시 확인하기

이번에는 `strip()`과 `lower()`를 동시에 넣지 말고 각각 따로 실험한다. 어떤 정규화가 필요한지는 실제 입력 사례와 요구사항으로 결정한다.

### 작은 문제

세 개 파일을 동시에 수정한 뒤 버그가 사라졌다. 왜 이것이 디버깅 관점에서 약한 증거인가?

### 왜 맞고 왜 틀리는가

세 변경 중 어느 것이 필요했는지, 둘 이상의 조합이 필요했는지, 우연히 상태가 바뀐 것인지 분리할 수 없기 때문이다. 작은 독립 실험이나 commit으로 효과를 나눠 확인해야 한다.

### 자주 만나는 실패와 확인 순서

- 대규모 자동 포맷과 기능 수정이 섞이면 diff가 커져 원인 추적이 어려워진다.
- 캐시 삭제까지 동시에 해버리면 코드 수정 효과와 상태 초기화 효과를 구분 못 한다.

### 이번 LESSON에서 구분할 것

- **암기 최소선:** 가설 하나에는 가능한 한 한 가지 판별 실험을 붙인다.
- **직접 코딩·실행해서 익힐 것:** 입력 또는 조건 하나만 바꿔 결과 차이를 비교한다.
- **AI에게 맡겨도 되는 것:** 실험 후보와 최소 diff 제안.
- **사람이 최종 확인할 것:** 실험이 정말 한 가설을 분리하는지, 다른 변수가 함께 변하지 않았는지 확인한다.

## CHAPTER 07 · LESSON 07 · PASS라는 말의 범위를 증거에 맞춘다

**LESSON ID:** `T10-B01-L07`

### 먼저 쉬운 말로 이해하기

`PASS`는 “대충 괜찮아 보인다”의 동의어가 아니다. 어떤 조건을 실제로 실행했고 어떤 결과를 확인했는지 붙어 있어야 한다. 정적 검사를 통과했다고 Android 실기기 실행까지 통과한 것은 아니다.

### 안에서는 실제로 무엇이 일어나는가

검증은 층이 있다. 예를 들어 JSON parsing 성공, unit test 성공, full build 성공, 설치 성공, 실제 기기 동작 성공은 서로 다른 실패 유형을 검출한다. 한 층의 성공을 더 넓은 층으로 확장해서 보고하면 위험하다.

### 아주 쉬운 예

작은 함수 검증에서도 동일한 원칙을 적용할 수 있다.

```python
def add(a, b):
    return a + b

cases = [(1, 2, 3), (-1, 1, 0), (0, 0, 0)]
for a, b, expected in cases:
    actual = add(a, b)
    print(a, b, actual, actual == expected)
```

### 한 줄씩 읽기

- 각 case는 검증 범위를 하나씩 구체화한다.
- `True` 세 번은 이 세 입력에 대한 증거다.
- 아직 큰 정수·float·잘못된 타입·성능·통합 동작은 검증하지 않았다.

### 직접 실행

1. 스크립트를 실제 실행한다.
2. 세 case가 모두 True인지 출력으로 확인한다.
3. 검증 보고에 “3개 입력 case 실행”이라고 범위를 명시한다.


### 일부를 바꿔서 다시 확인하기

문자열 `"1"`과 숫자 `2`를 넣는 case를 추가한다. 예외가 나면 기존 PASS가 거짓이 되는 것이 아니라 **기존 세 정상 입력 범위에서는 통과했지만 타입 경계는 미검증/실패**였다는 뜻이다.

### 작은 문제

`python -m compileall`이 성공했다. “앱 전체 PASS”라고 써도 되는가?

### 왜 맞고 왜 틀리는가

안 된다. 문법/컴파일 계층의 일부 검증일 뿐, 테스트·빌드·설치·런타임·UI·네트워크 동작은 별도다. PASS 이름에 검증 범위를 붙여야 한다.

### 자주 만나는 실패와 확인 순서

- 실행하지 않은 test file이 존재한다는 이유로 테스트 PASS라고 보고하는 오류.
- mock 기반 unit test만 성공했는데 실제 API 연결 성공으로 확대 해석하는 오류.

### 이번 LESSON에서 구분할 것

- **암기 최소선:** PASS는 실행된 검증의 범위와 증거를 함께 가져야 한다.
- **직접 코딩·실행해서 익힐 것:** 작은 검증을 직접 실행하고 어떤 실패 유형까지 잡는지 적는다.
- **AI에게 맡겨도 되는 것:** 검증 명령 생성과 결과 요약.
- **사람이 최종 확인할 것:** 실제 실행 여부, exit code/보고서, 검증하지 않은 범위를 명확히 구분한다.
