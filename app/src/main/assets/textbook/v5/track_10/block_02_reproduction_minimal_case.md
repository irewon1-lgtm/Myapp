## CHAPTER 01 · LESSON 01 · 같은 입력에서 같은 실패가 나는지 확인한다

**LESSON ID:** `T10-B02-L01`

### 먼저 쉬운 말로 이해하기

재현은 “한 번 더 실행해 봤더니 또 안 됐다”보다 엄격하다. 같은 입력·상태·환경에서 반복했을 때 같은 종류의 실패가 나타나는지 확인해야 원인 실험의 기준점이 생긴다.

### 안에서는 실제로 무엇이 일어나는가

비결정성은 시간, 난수, 스레드 순서, 네트워크 응답, 외부 데이터처럼 프로그램 밖의 값이 매 실행마다 달라질 때 생긴다. 먼저 어떤 값이 변할 수 있는지 목록화하면 flaky bug와 진짜 코드 결함을 구분하기 쉬워진다.

### 아주 쉬운 예

난수 seed를 고정하면 같은 난수열을 다시 만들 수 있다.

```python
import random

random.seed(42)
values = [random.randint(1, 10) for _ in range(5)]
print(values)
```

### 한 줄씩 읽기

- `seed(42)`는 난수 생성기의 시작 상태를 고정한다.
- 같은 Python 구현과 조건에서 같은 난수열을 재현하는 데 도움이 된다.
- 실제 보안용 난수까지 고정하라는 뜻이 아니라 테스트 입력 통제 예다.

### 직접 실행

1. 스크립트를 두 번 실행하고 출력이 같은지 비교한다.
2. `42`를 `99`로 바꾸고 출력이 달라지는지 본다.
3. seed 값도 재현 기록에 포함한다.


### 일부를 바꿔서 다시 확인하기

seed 줄을 제거하고 여러 번 실행해 본다. 실패가 특정 난수 입력에서만 난다면 그 입력 자체를 저장해 더 작은 deterministic test로 옮긴다.

### 작은 문제

100번 중 한 번 실패하는 테스트를 한 번 재실행해서 통과했다. 버그가 사라졌다고 결론내릴 수 있는가?

### 왜 맞고 왜 틀리는가

아니다. 비결정적 조건이 이번 실행에 나타나지 않았을 수 있다. 실패 시 seed·입력·시간·순서 정보를 보존하고 반복 실행으로 실패 빈도와 조건을 조사해야 한다.

### 자주 만나는 실패와 확인 순서

- 재현 불가를 “문제 없음”으로 바꾸면 간헐 오류가 묻힌다.
- 운영에서 얻은 random seed나 입력을 저장하면서 개인정보를 함께 보존하지 않도록 주의한다.

### 이번 LESSON에서 구분할 것

- **암기 최소선:** 재현에는 변하는 입력을 식별하고 가능한 것은 고정하는 과정이 필요하다.
- **직접 코딩·실행해서 익힐 것:** seed를 바꿔 deterministic/non-deterministic 차이를 직접 본다.
- **AI에게 맡겨도 되는 것:** 반복 실행 스크립트와 실패 입력 수집 자동화.
- **사람이 최종 확인할 것:** 재현 데이터가 충분하고 민감정보는 제거됐는지 확인한다.

### 근거 연결

`PYTEST` · `HYPOTHESIS`

## CHAPTER 02 · LESSON 02 · 최소 재현 사례로 잡음을 줄인다

**LESSON ID:** `T10-B02-L02`

### 먼저 쉬운 말로 이해하기

원래 앱 전체에서만 버그를 보면 원인 후보가 너무 많다. **최소 재현 사례**는 실패를 유지하면서 필요 없는 화면, DB, 네트워크, 데이터 양을 걷어낸 작은 프로그램이나 테스트다.

### 안에서는 실제로 무엇이 일어나는가

구성요소를 제거할 때마다 실패가 유지되는지 확인한다. 어떤 요소를 제거했더니 실패가 사라지면 그 요소 또는 그와의 상호작용이 원인 범위에 들어온다. 이것은 단순 축약이 아니라 진단 실험이다.

### 아주 쉬운 예

긴 데이터 처리에서 실제로 문제를 만드는 한 행만 남기는 과정을 생각해 본다.

```python
rows = [
    {"name": "kim", "age": 20},
    {"name": "lee", "age": None},
]

for row in rows:
    print(row["name"], row["age"] + 1)
```

### 한 줄씩 읽기

- 첫 행은 정상이라 오류 원인이 아닐 가능성이 높다.
- 두 번째 행의 `None + 1`이 type error를 만든다.
- 두 번째 행만 남겨도 같은 오류가 나면 재현 입력을 축소한 것이다.

### 직접 실행

1. 전체 두 행으로 실패를 확인한다.
2. 정상 행을 제거하고 실패 행만 남겨 다시 실행한다.
3. 같은 예외 위치와 종류인지 비교한다.


### 일부를 바꿔서 다시 확인하기

`name` 필드까지 삭제해도 실패하는지 시험한다. 실패에 필요 없는 데이터 필드는 제거할 수 있다. 단, 실제 bug가 field 조합에 의존하면 너무 많이 줄여 다른 현상으로 바뀔 수 있으므로 매 단계 확인한다.

### 작은 문제

최소 재현에서 DB를 제거했더니 버그가 사라졌다. “DB가 무조건 원인”이라고 결론내려도 되는가?

### 왜 맞고 왜 틀리는가

아니다. DB 자체, 반환 데이터 모양, latency, transaction 상태 등 DB 경계와 관련된 여러 원인이 남아 있다. “DB 경계를 제거하면 현상이 사라진다”가 현재 증거다.

### 자주 만나는 실패와 확인 순서

- 축소 과정에서 실패 종류가 바뀌었는데 같은 bug라고 착각할 수 있다.
- 민감한 운영 데이터를 그대로 최소 사례에 복사하지 말고 구조를 보존한 합성 데이터로 바꾼다.

### 이번 LESSON에서 구분할 것

- **암기 최소선:** 최소 재현은 실패를 유지하면서 불필요한 요소를 제거한다.
- **직접 코딩·실행해서 익힐 것:** 데이터·기능을 하나씩 제거하며 같은 실패인지 확인한다.
- **AI에게 맡겨도 되는 것:** 큰 bug report에서 최소 코드 초안 생성.
- **사람이 최종 확인할 것:** 축소된 사례가 원래 실패와 같은 현상인지 확인한다.

### 근거 연결

`NIST-SSDF-12` · `PYTEST`

## CHAPTER 03 · LESSON 03 · 입력과 프로그램 상태를 따로 기록한다

**LESSON ID:** `T10-B02-L03`

### 먼저 쉬운 말로 이해하기

같은 버튼을 눌러도 로그인 여부, 캐시 내용, 이전 화면, DB row처럼 **상태**가 다르면 결과가 달라진다. 입력은 지금 들어오는 값이고 상태는 실행 전부터 시스템 안에 남아 있던 값이다.

### 안에서는 실제로 무엇이 일어나는가

stateful bug는 초기 상태를 재현하지 않으면 잡기 어렵다. 테스트에서는 setup 단계에서 상태를 명시적으로 만들고, teardown에서 다음 테스트에 영향을 주는 잔여물을 제거한다.

### 아주 쉬운 예

잔액이 이전 거래에 따라 달라지는 작은 예를 사용한다.

```python
balance = 1000

def withdraw(amount):
    global balance
    balance -= amount
    return balance

print(withdraw(300))
print(withdraw(300))
```

### 한 줄씩 읽기

- 두 호출의 입력 `300`은 같지만 시작 balance가 다르다.
- global state가 첫 호출에서 700으로 바뀐다.
- 두 번째 결과가 다른 것은 함수 입력 외에 상태가 숨어 있기 때문이다.

### 직접 실행

1. 스크립트를 실행해 700, 400 흐름을 확인한다.
2. 두 번째 호출 전에 `balance = 1000`을 넣어 상태를 초기화한다.
3. 같은 입력에서 결과가 달라지는 이유를 상태 변화로 설명한다.


### 일부를 바꿔서 다시 확인하기

global 대신 balance를 인자로 받고 새 balance를 반환하는 순수 함수 버전을 만들어 본다. 테스트가 왜 쉬워지는지 비교한다.

### 작은 문제

같은 API 요청인데 첫 번째는 성공, 두 번째는 실패한다. 입력 JSON이 같으니 코드가 랜덤하다고 볼 수 있는가?

### 왜 맞고 왜 틀리는가

그렇지 않다. 첫 요청이 DB 상태를 바꿨거나 token/counter/cache가 변했을 수 있다. 요청 전후 상태를 확인해야 한다.

### 자주 만나는 실패와 확인 순서

- 테스트끼리 DB 데이터를 공유하면 실행 순서에 따라 결과가 달라질 수 있다.
- cleanup 실패가 다음 테스트의 시작 상태를 오염시킬 수 있다.

### 이번 LESSON에서 구분할 것

- **암기 최소선:** 현재 입력과 이전부터 존재한 상태는 별개다.
- **직접 코딩·실행해서 익힐 것:** setup/reset을 넣어 상태 의존성을 직접 확인한다.
- **AI에게 맡겨도 되는 것:** fixture 생성과 teardown 코드 초안.
- **사람이 최종 확인할 것:** 실제 테스트 간 격리가 되는지와 운영 상태를 파괴하지 않는지 확인한다.

### 근거 연결

`PYTEST` · `GOOGLE-SRE`

## CHAPTER 04 · LESSON 04 · 시간과 timezone을 통제한다

**LESSON ID:** `T10-B02-L04`

### 먼저 쉬운 말로 이해하기

“자정에만 실패”, “한국에서는 되는데 UTC 서버에서 실패” 같은 버그는 시간이 숨은 입력이라는 뜻이다. `now()`를 함수 안에서 바로 읽으면 테스트 순간에 따라 결과가 변할 수 있다.

### 안에서는 실제로 무엇이 일어나는가

시간 의존 코드는 clock을 주입하거나 기준 시각을 인자로 받아 deterministic하게 만들 수 있다. timezone-aware datetime과 naive datetime을 섞지 않는 것도 중요하다.

### 아주 쉬운 예

만료 여부를 현재 시각 인자로 받는 함수로 만든다.

```python
from datetime import datetime, timezone

def expired(expires_at, now):
    return now >= expires_at

expires = datetime(2026, 9, 18, 0, 0, tzinfo=timezone.utc)
print(expired(expires, datetime(2026, 9, 17, 23, 59, tzinfo=timezone.utc)))
print(expired(expires, datetime(2026, 9, 18, 0, 0, tzinfo=timezone.utc)))
```

### 한 줄씩 읽기

- `now`를 외부에서 넣으므로 테스트 시각을 정확히 고정할 수 있다.
- 경계 직전과 정확한 만료 시각을 따로 검사한다.
- `tzinfo=timezone.utc`로 기준 timezone을 명시한다.

### 직접 실행

1. 두 case를 실행해 False/True 경계를 확인한다.
2. 만료 시각을 한 시간 바꿔 결과를 비교한다.
3. timezone 정보를 제거했을 때 비교가 어떻게 달라질 수 있는지 조사한다.


### 일부를 바꿔서 다시 확인하기

실제 앱에서는 production clock wrapper를 만들어 현재 시각을 제공하고, test에서는 fake clock을 넣는 구조를 그려 본다.

### 작은 문제

“오늘 날짜” 테스트가 개발 PC에서는 성공하고 자정 무렵 CI에서 실패한다. 무엇을 의심해야 하는가?

### 왜 맞고 왜 틀리는가

테스트가 시스템 현재 시각과 timezone을 암묵적으로 읽는지 확인한다. 경계 시각을 고정한 테스트로 바꾸고 환경 timezone 차이도 기록해야 한다.

### 자주 만나는 실패와 확인 순서

- 날짜 문자열만 저장하고 timezone 의미를 잃으면 서로 다른 순간을 같은 값처럼 처리할 수 있다.
- sleep으로 시간을 맞추는 테스트는 느리고 flaky해지기 쉽다.

### 이번 LESSON에서 구분할 것

- **암기 최소선:** 시간도 입력이고 timezone은 그 시간을 해석하는 규칙이다.
- **직접 코딩·실행해서 익힐 것:** 경계 시각을 직접 주입해 전후 결과를 확인한다.
- **AI에게 맡겨도 되는 것:** fake clock 코드와 경계 case 생성.
- **사람이 최종 확인할 것:** 실제 제품의 시간 기준과 저장/표시 timezone 계약을 결정한다.

### 근거 연결

`PYTEST` · `GOOGLE-SRE`

## CHAPTER 05 · LESSON 05 · 파일·네트워크·DB 같은 외부 경계를 분리한다

**LESSON ID:** `T10-B02-L05`

### 먼저 쉬운 말로 이해하기

함수가 계산도 하고 파일도 읽고 HTTP 요청도 보내면 실패 원인이 뒤엉킨다. 외부 경계를 작은 함수나 interface로 감싸면 “계산이 틀렸는지”와 “외부 시스템이 실패했는지”를 따로 검사할 수 있다.

### 안에서는 실제로 무엇이 일어나는가

dependency boundary를 만들면 test double을 넣을 수 있고, timeout·404·잘못된 JSON 같은 실패를 의도적으로 재현할 수 있다. 운영 코드는 진짜 client를 넣고 테스트는 통제된 fake를 넣는다.

### 아주 쉬운 예

환율을 가져오는 함수를 직접 호출하지 않고 함수 인자로 받는다.

```python
def price_in_krw(usd, get_rate):
    rate = get_rate()
    return usd * rate

def fake_rate():
    return 1350

print(price_in_krw(10, fake_rate))
```

### 한 줄씩 읽기

- `price_in_krw`는 환율 출처를 알 필요가 없다.
- `get_rate` 경계만 바꾸면 계산과 network를 분리할 수 있다.
- fake는 1350을 항상 반환하므로 계산 테스트가 안정적이다.

### 직접 실행

1. 실행해 13500을 확인한다.
2. fake_rate가 예외를 던지게 바꿔 외부 실패 경로를 관찰한다.
3. 실제 HTTP client를 연결하지 않고도 error handling을 설계한다.


### 일부를 바꿔서 다시 확인하기

fake가 0, 음수, 매우 큰 값을 반환하게 해 validation 위치를 결정해 본다. 계산 함수가 검증할지 client adapter가 보장할지 계약을 명시한다.

### 작은 문제

fake API 테스트는 모두 통과했는데 production에서 실제 API schema가 바뀌어 실패했다. fake test가 쓸모없었던 것인가?

### 왜 맞고 왜 틀리는가

아니다. 내부 계산을 검증하는 범위에서는 유효하다. 다만 실제 경계 계약을 검증하는 integration/contract test가 부족했던 것이다. 테스트 범위를 확장해야 한다.

### 자주 만나는 실패와 확인 순서

- mock이 실제 API와 너무 달라지면 거짓 안정감을 준다.

## CHAPTER 06 · LESSON 06 · 기기·권한·네트워크 조건을 재현 정보에 넣는다

**LESSON ID:** `T10-B02-L06`

### 먼저 쉬운 말로 이해하기

모바일 앱은 같은 코드라도 Android 버전, 화면 크기, permission 상태, Wi‑Fi/셀룰러, offline 여부에 따라 다르게 행동한다. 이런 조건은 “주변 정보”가 아니라 재현 입력의 일부다.

### 안에서는 실제로 무엇이 일어나는가

특히 permission과 lifecycle은 상태 전이가 있다. 처음 거부, 다시 요청, “다시 묻지 않음”, 앱 background/foreground 전환 등 경로에 따라 결과가 달라진다. bug report는 단말 모델명만 적는 것으로 충분하지 않다.

### 아주 쉬운 예

Python으로 network 여부를 진짜 모바일처럼 재현할 수는 없으므로 상태 machine 형태로 조건을 명시해 본다.

```python
def can_upload(has_network, has_permission):
    if not has_permission:
        return "permission_required"
    if not has_network:
        return "offline"
    return "upload"

print(can_upload(False, True))
```

### 한 줄씩 읽기

- permission 확인을 network보다 먼저 하도록 정책을 정했다.
- 두 boolean은 기기 상태를 작은 입력으로 모델링한다.
- 실제 Android에서는 이 값을 플랫폼 API에서 읽지만 의사결정 규칙은 별도 테스트할 수 있다.

### 직접 실행

1. 세 가능한 결과가 나오도록 입력 조합을 실행한다.
2. 조건 순서를 바꾸면 두 조건이 모두 false일 때 결과가 어떻게 달라지는지 본다.
3. 실제 앱 bug report에는 기기/OS/permission/network/lifecycle 상태를 함께 적는다.


### 일부를 바꿔서 다시 확인하기

`has_network`를 단순 boolean이 아니라 `offline`, `wifi`, `cellular`, `captive_portal`로 확장해 어떤 상태가 제품 요구에 필요한지 설계한다.

### 작은 문제

“Galaxy에서 안 됨”이라는 보고는 왜 재현 정보로 부족한가?

### 왜 맞고 왜 틀리는가

OS 버전, 앱 버전, permission 상태, network, 정확한 행동 순서, 계정/데이터 상태 등 결과를 바꿀 수 있는 조건이 빠져 있기 때문이다.

### 자주 만나는 실패와 확인 순서

- 기기 로그를 공유할 때 계정 식별자·token·위치 같은 개인정보가 포함될 수 있다.
- 실제 네트워크 장애를 테스트한다고 production endpoint를 무작정 끊지 않는다.

### 이번 LESSON에서 구분할 것

- **암기 최소선:** 기기·권한·network·lifecycle도 실행 조건이다.
- **직접 코딩·실행해서 익힐 것:** 상태 조합을 명시하고 어떤 결과가 기대되는지 표로 만든다.
- **AI에게 맡겨도 되는 것:** device matrix와 테스트 case 초안.
- **사람이 최종 확인할 것:** 실제 위험 없이 조건을 만들었는지, 민감정보가 제거됐는지 확인한다.

### 근거 연결

## CHAPTER 07 · LESSON 07 · 운영 재현 데이터는 개인정보를 지키며 수집한다

**LESSON ID:** `T10-B02-L07`

### 먼저 쉬운 말로 이해하기

운영에서만 나는 버그는 실제 입력이 필요할 수 있지만, 사용자의 token·전화번호·주소·건강정보 같은 데이터를 통째로 복사하면 안 된다. **재현 가능성**과 **데이터 최소화**를 함께 만족해야 한다.

### 안에서는 실제로 무엇이 일어나는가

좋은 재현 데이터는 실패를 만드는 구조적 특성만 보존한다. 예를 들어 “이름이 200자”, “emoji 포함”, “null field”는 보존하면서 실제 이름은 가짜 값으로 바꿀 수 있다. 로그는 allowlist 방식으로 필요한 field만 남기는 편이 안전하다.

### 아주 쉬운 예

민감 필드를 마스킹하는 아주 작은 예를 본다.

```python
event = {"user_id": "u-123", "phone": "010-1234-5678", "error": "timeout"}

safe = {
    "user_id_hash": hash(event["user_id"]),
    "error": event["error"],
}
print(safe)
```

### 한 줄씩 읽기

- 예시는 원문 phone을 출력하지 않는다.
- 실무에서는 Python의 내장 `hash`를 영구 익명화 식별자로 쓰면 안 된다. 실행마다 달라질 수 있고 보안 목적 hash가 아니다.
- 핵심은 필요한 진단 field와 민감 field를 구분하는 것이다.

### 직접 실행

1. 예제를 실행해 phone이 출력되지 않는지 확인한다.
2. `safe`에 불필요한 원본 field가 들어가지 않았는지 검사한다.
3. 실제 프로젝트에서는 승인된 hashing/redaction 정책을 사용한다.


### 일부를 바꿔서 다시 확인하기

error message 자체에 token이 섞일 수 있는 사례를 만들어 “field 삭제만으로 충분하지 않다”는 점을 확인한다. logger formatter 단계에서 secret pattern redaction이 필요한 이유를 적는다.

### 작은 문제

재현을 빨리 하려고 production DB row를 개인 노트북으로 복사하는 것은 왜 위험한가?

### 왜 맞고 왜 틀리는가

접근통제·보존정책·개인정보 최소화 원칙을 벗어날 수 있고, 노트북 분실이나 로그 업로드로 2차 노출이 생긴다. 승인된 안전한 데이터 처리 절차와 비식별/합성 데이터를 우선해야 한다.

### 자주 만나는 실패와 확인 순서

- redaction 전 원본 로그가 이미 외부 서비스로 전송되는 구조를 놓칠 수 있다.
- hash 처리만 했다고 모든 데이터가 익명화되는 것은 아니다. 조합으로 재식별될 수 있다.

### 이번 LESSON에서 구분할 것

- **암기 최소선:** 운영 재현은 필요한 데이터만 최소 수집하고 민감값을 제거한다.
- **직접 코딩·실행해서 익힐 것:** 합성 데이터로 구조를 보존하면서 같은 실패가 나는지 확인한다.
- **AI에게 맡겨도 되는 것:** redaction rule 초안과 합성 fixture 생성.
- **사람이 최종 확인할 것:** 데이터 사용 권한·보존·재식별 위험과 실제 재현 동등성을 확인한다.
