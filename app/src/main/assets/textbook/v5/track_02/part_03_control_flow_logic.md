# PART 03 · 조건·반복·논리 — 제어 흐름을 증명 가능한 상태 변화로 읽기

조건문과 반복문은 문법 몇 개를 외우는 영역이 아니다. 프로그램이 어떤 입력에서 어느 경로를 선택하고, 반복할 때 어떤 상태를 유지하며, 언제 반드시 종료하는지를 정의하는 장치다. `if`, `for`, `while`을 정확히 사용하려면 boolean 논리, 경계 조건, loop invariant, 종료 조건, iteration protocol을 함께 이해해야 한다.

---

## CHAPTER 01 · 조건식은 자연어 정책을 boolean 구조로 번역한다

“회원이면서 본인 소유 문서이거나 관리자면 수정 가능하다”라는 문장은 연산 우선순위를 어떻게 묶느냐에 따라 의미가 달라진다. 프로그램에서 권한 규칙을 한 줄의 긴 조건식으로 옮기면 사람의 자연어 해석과 실제 boolean 평가가 어긋날 수 있다. 먼저 의미 단위에 이름을 붙이고 그 조합을 확인하는 편이 안전하다.

```python
is_owner_member = user.is_member and document.owner_id == user.id
can_edit = is_owner_member or user.is_admin
```

이 구조에서는 “관리자는 소유자가 아니어도 되는가”, “회원이 아닌 관리자는 허용되는가” 같은 질문이 드러난다. 복잡한 정책은 truth table로 가능한 조합을 펼치면 괄호 하나의 차이가 어떤 사용자 집합을 허용하는지 볼 수 있다. 특히 권한과 금액 규칙처럼 실패 비용이 큰 조건은 정상 사례 몇 개보다 모든 boolean 조합을 확인하는 편이 강하다.

조건식 안에 함수 호출과 상태 변경을 섞으면 판단과 효과가 결합된다. `if is_valid(x) and save(x):` 같은 코드는 첫 조건 결과에 따라 `save` 호출 자체가 생략될 수 있다. 저장이 정책 판단의 일부인지, 판단 후 수행해야 하는 효과인지 분리해야 한다. 조건식은 가능한 한 “현재 사실을 판정”하고, 상태 변경은 분기 본문에서 명시적으로 수행하는 구조가 추론하기 쉽다.

정책을 boolean으로 옮기는 과정은 단순 문법 변환이 아니다. 허용 규칙과 거부 규칙의 우선순위, 누락된 상태, 기본값을 결정하는 설계 작업이다. 자연어 요구를 곧바로 코드 한 줄로 압축하기보다 predicate 이름과 조합을 먼저 모델링하면 의미 오류를 줄일 수 있다.

## CHAPTER 02 · short-circuit는 결과뿐 아니라 실행 여부를 바꾼다

Python의 `and`와 `or`는 왼쪽에서 오른쪽으로 평가하면서 결과가 이미 결정되면 나머지 피연산자를 평가하지 않는다. 이를 short-circuit evaluation이라고 한다. 따라서 `obj is not None and obj.value > 0`은 첫 조건이 거짓일 때 오른쪽 접근을 생략해 안전하게 동작할 수 있다.

하지만 오른쪽 표현식에 side effect가 있다면 short-circuit는 프로그램의 상태 변화 자체를 조건부로 만든다. `ready() or initialize()`에서 `ready()`가 truthy를 반환하면 `initialize()`는 호출되지 않는다. 이런 코드는 짧지만 호출 여부가 연산자 semantics에 숨어 있어 디버깅이 어려워질 수 있다. 판단과 효과를 분리하면 실행 경로가 더 명시적이다.

또한 `and`와 `or`는 항상 `True`나 `False`만 반환하는 연산자로 생각하면 틀릴 수 있다. Python에서는 operand 자체가 결과가 될 수 있다. `name or "anonymous"`는 `name`이 falsy면 문자열 기본값을 돌려준다. 편리한 패턴이지만 빈 문자열과 값 부재를 같은 상태로 취급해도 되는지 먼저 확인해야 한다.

조건식을 추적할 때는 각 operand의 truth value, 실제 반환 객체, 평가 여부를 따로 본다. 특히 함수 호출이 포함되어 있다면 “최종 boolean 결과”만 확인하지 말고 어떤 호출이 실행되었는지 trace해야 한다. short-circuit는 최적화 기술이 아니라 언어의 제어 흐름 semantics다.

## CHAPTER 03 · truthiness는 여러 도메인 상태를 하나의 판단으로 압축한다

Python은 `if expression:`에서 객체의 truth value를 사용한다. `None`, `False`, 숫자 0, 빈 문자열과 빈 collection 등이 falsy로 평가될 수 있다. 이 기능은 collection이 비었는지 확인하는 데 편리하지만, 서로 다른 업무 상태까지 동일하게 취급할 위험이 있다.

예를 들어 할인율 0은 “할인이 없음”이라는 유효한 값일 수 있고 `None`은 “할인율을 계산하지 못함”을 뜻할 수 있다. `if not discount:`로 둘을 묶으면 계산 실패와 정상 0%를 구분하지 못한다. 수량 0, 빈 검색어, 빈 결과 목록, 누락값도 도메인에 따라 전혀 다른 의미를 가진다.

조건을 작성할 때는 의도가 존재성 검사인지, 값 비교인지, 비어 있음 검사인지 선택한다. `value is None`, `len(items) == 0`, `amount == 0`, `if items:`는 겉보기에는 비슷해도 계약이 다르다. 의도가 선명한 표현을 사용하면 나중에 타입이 바뀌거나 새로운 유효값이 추가될 때 예기치 않은 분기가 줄어든다.

사용자 정의 객체는 truth value 동작을 정의할 수도 있으므로 `if obj:`가 객체 존재 여부만 뜻한다고 가정하지 않는다. 라이브러리 객체가 특별한 truth semantics를 갖는 경우도 있다. 조건식이 무엇을 묻는지 코드 리뷰에서 자연어 한 문장으로 설명할 수 있어야 한다.

## CHAPTER 04 · 조건 분기는 가능한 상태 공간을 나눈다

`if/elif/else`는 위에서부터 조건을 검사하며 먼저 참이 된 한 경로를 선택한다. 따라서 조건의 순서는 단순한 배치가 아니라 정책 우선순위다. 넓은 조건을 먼저 두면 뒤의 더 구체적인 조건은 도달할 수 없게 된다.

```python
if score >= 60:
    grade = "pass"
elif score >= 90:
    grade = "excellent"
```

이 코드에서 95점도 첫 분기에서 이미 `pass`가 되어 두 번째 분기는 실행되지 않는다. 의도한 정책이 `excellent`를 우선한다면 더 좁고 높은 조건을 먼저 두거나 범위를 명시해야 한다. branch ordering 오류는 문법적으로 완벽한 코드에서도 발생한다.

분기가 많아질수록 각 경로가 어떤 상태 집합을 담당하는지 겹침과 누락을 확인한다. 나이 구간, 세율, 배송비, 점수 등급처럼 연속 범위를 나누는 정책은 경계값을 표로 만들면 좋다. `18`, `19`, `20`처럼 임계값 직전·정확히 임계값·직후를 테스트하면 `<`와 `<=` 혼동을 빠르게 찾을 수 있다.

모든 가능한 입력에 결과가 있어야 하는 함수라면 마지막 `else` 또는 명시적 실패가 필요할 수 있다. 반대로 예상하지 못한 상태에 조용한 기본값을 주면 새로운 상태가 추가됐을 때 오류를 숨길 수 있다. 분기 구조는 현재 상태 공간을 얼마나 완전하게 모델링했는지 보여 주는 설계 문서이기도 하다.

## CHAPTER 05 · 반복문은 초기 상태·불변식·진전·종료로 설명한다

반복문을 단순히 “여러 번 실행하는 문법”으로 보면 경계 오류와 무한 루프의 원인을 체계적으로 찾기 어렵다. loop를 네 요소로 나누면 정확성을 설명할 수 있다. 반복 시작 전의 초기 상태, 매 반복 전후에 참이어야 하는 invariant, 종료 쪽으로 움직이게 하는 progress measure, 종료 후 보장되는 조건이다.

배열에서 최댓값을 찾는 반복을 생각해 보자. 첫 원소를 `best`로 두고 왼쪽에서 오른쪽으로 순회한다면 i번째 단계가 끝난 뒤 `best`는 지금까지 본 구간의 최댓값이라는 invariant를 세울 수 있다. 다음 원소와 비교해 더 크면 `best`를 바꾸어도 이 invariant가 유지된다. 마지막 원소까지 처리하면 전체 구간의 최댓값이라는 결론이 나온다.

이 관점은 결과 예제 몇 개보다 강하다. 특정 입력에서 맞았다는 사실이 아니라 모든 반복 단계가 어떤 성질을 보존하는지를 설명하기 때문이다. 정렬, 누적 합, 탐색, parser, pagination처럼 상태를 조금씩 갱신하는 코드에서 invariant는 디버깅 기준점이 된다.

실제 코드 작성 전에도 “반복 한 번이 어떤 상태를 바꾸는가”, “바뀌지 않아야 하는 값은 무엇인가”, “종료 후 무엇이 참이어야 하는가”를 적을 수 있다. 이 설명이 어렵다면 loop가 너무 많은 책임을 한 번에 수행하고 있을 가능성도 있다.

## CHAPTER 06 · 종료를 보장하려면 매 반복에서 줄어드는 양을 찾는다

`while` loop는 조건이 언젠가 거짓이 된다는 보장이 있어야 한다. 이를 분석할 때 남은 작업 수, 탐색 구간 길이, 처리하지 않은 입력 길이처럼 매 반복마다 한 방향으로 줄어드는 measure를 찾는다. 이 값이 아래로 제한되어 있고 실제로 감소한다면 종료를 설명하기 쉬워진다.

binary search에서 `[low, high)` 범위를 사용한다고 하자. 반복 조건은 `low < high`이고 매 반복에서 `low = mid + 1` 또는 `high = mid`로 구간을 줄인다. 핵심은 계산식이 아니라 `high - low`가 반드시 감소한다는 사실이다. `low = mid`처럼 잘못 갱신하면 어떤 경우에는 구간 길이가 줄지 않아 무한 반복이 생길 수 있다.

외부 이벤트를 기다리는 loop는 수학적으로 항상 종료하지 않을 수도 있다. 서버 event loop나 메시지 consumer는 의도적으로 오래 살아 있다. 이런 경우에는 개별 작업의 종료, cancellation, timeout, shutdown protocol을 별도로 모델링한다. “프로세스가 계속 돈다”와 “한 요청 처리 loop가 끝나지 않는다”는 다른 문제다.

retry loop도 종료 정책이 필요하다. 실패할 때까지 무한 재시도하면 외부 장애 상황에서 부하를 더 키울 수 있다. 최대 횟수, deadline, backoff, 취소 신호를 계약에 넣으면 반복이 운영 문제로 확장되는 것을 막을 수 있다.

## CHAPTER 07 · off-by-one 오류는 구간 표현이 섞일 때 생긴다

반복 범위를 다룰 때 시작점을 포함하는지, 끝점을 포함하는지 규칙을 섞으면 첫 항목 누락, 마지막 항목 중복, 범위 초과 접근이 발생한다. Python의 `range(start, stop)`와 slicing은 일반적으로 시작을 포함하고 stop을 제외하는 반열린 구간 `[start, stop)`과 잘 맞는다.

반열린 구간은 길이가 `stop - start`로 바로 계산되고 빈 구간을 `start == stop`으로 표현할 수 있다는 장점이 있다. 인접 구간 `[a, b)`와 `[b, c)`는 겹치거나 틈이 생기지 않는다. 이런 성질 때문에 반복, slicing, parser offset에서 일관된 convention으로 사용하기 좋다.

경계 코드는 빈 입력, 원소 하나, 첫 원소, 마지막 원소, 전체 범위, 부분 범위를 손으로 추적한다. `range(n)`은 `0`부터 `n-1`까지이고, `items[:n]`도 최대 n개 항목을 가져온다. “n번째”라는 자연어 표현은 1-based인지 0-based인지 모호하므로 코드 계약에서는 index와 count를 구분한다.

외부 API가 inclusive end를 사용하고 내부가 exclusive end를 사용한다면 변환 지점을 하나로 모은다. 여러 함수가 각자 `+1`, `-1`을 하면 변환 책임이 흩어져 경계 오류가 커진다. 구간 모델을 명시하는 것만으로도 반복문 버그 상당수를 구조적으로 줄일 수 있다.

## CHAPTER 08 · `for`는 숫자 반복문이 아니라 iterable protocol 소비자다

Python의 `for`는 전통적인 C 계열의 index 증가 문법과 다르게 iterable에서 값을 하나씩 받는 구조다. 리스트, tuple, 문자열, dict view, 파일 객체, generator가 모두 `for`와 함께 동작할 수 있는 이유는 iteration protocol을 제공하기 때문이다. 반복 방법과 데이터 저장 형태가 분리되어 있다.

개념적으로 `iter(obj)`가 iterator를 만들고 `next(iterator)`가 다음 값을 요청한다. 더 이상 값이 없으면 iteration 종료를 알리는 protocol이 작동한다. `for` 문은 이 과정을 감싸므로 사용자는 index 관리 없이 값을 순회할 수 있다. 이 모델을 알면 generator와 lazy pipeline을 이해하기 쉬워진다.

index가 실제로 필요한 경우 `enumerate()`를 사용하는 편이 수동 counter 관리보다 의도를 잘 드러낸다. 두 sequence를 병렬로 순회할 때는 `zip()`이 유용하지만 길이가 다를 때 어떤 요소가 버려지는지 또는 엄격히 검사할지 계약을 확인해야 한다. iteration helper도 데이터 손실 의미와 연결된다.

iteration 중 원본 collection을 구조적으로 변경하면 예상하기 어려운 결과가 생길 수 있다. 삭제 대상만 새 collection으로 만들거나 순회 대상 snapshot과 변경 대상을 분리하는 방법이 더 명확할 수 있다. 반복문은 값을 읽는 흐름과 상태를 바꾸는 흐름이 겹치는 지점이므로 aliasing을 함께 고려해야 한다.

## CHAPTER 09 · comprehension은 표현식이지만 복잡한 상태 머신으로 만들지 않는다

list/set/dict comprehension은 mapping과 filtering을 간결하게 표현할 수 있다. `squares = [x*x for x in values if x >= 0]`처럼 입력 sequence에서 조건을 만족하는 값을 변환해 새 collection을 만드는 경우 데이터 흐름이 한눈에 보인다. 하지만 중첩 loop, 여러 조건, side effect가 들어가면 짧은 줄이 오히려 읽기 어려운 프로그램이 된다.

comprehension은 새 collection을 만드는 표현식이라는 성격을 살릴 때 강하다. 파일 쓰기, 전역 상태 변경, 로그 출력 같은 side effect를 comprehension 안에 넣으면 결과값과 실행 효과가 섞인다. 값 생성이 목적이 아니라 효과 반복이 목적이라면 명시적인 `for` loop가 더 적합하다.

중첩 comprehension에서는 반복 순서가 바깥에서 안쪽으로 어떻게 전개되는지 실제 loop 형태로 풀어 설명할 수 있어야 한다. 이해가 어렵다면 먼저 명시적인 loop로 작성해 의미를 검증한 뒤 필요할 때 단순화한다. 코드 길이 감소가 인지 복잡도 감소와 항상 같지는 않다.

대용량 입력에서 list comprehension은 결과 전체를 메모리에 만든다. 값이 한 번씩만 필요하다면 generator expression이 메모리 특성상 유리할 수 있지만, lazy evaluation 때문에 오류 시점과 소비 횟수 semantics가 달라진다. 구문 선택은 가독성뿐 아니라 평가 시점과 메모리 계약을 함께 결정한다.

## CHAPTER 10 · 중첩 제어 흐름은 guard clause와 작은 predicate로 평탄화한다

조건문 안에 조건문, 그 안에 loop, 그 안에 예외 처리가 계속 중첩되면 현재 코드가 어떤 전제 아래 실행되는지 추적하기 어렵다. 중첩 깊이는 단순 스타일 문제가 아니라 동시에 머리에 유지해야 하는 상태 수를 늘린다. 실패 조건을 앞에서 종료시키는 guard clause와 의미 있는 predicate 추출은 제어 흐름을 평탄하게 만드는 도구다.

```python
def ship(order):
    if order is None:
        raise ValueError("order required")
    if not order.is_paid:
        return ShipResult.not_paid()
    if order.is_cancelled:
        return ShipResult.cancelled()
    return perform_shipping(order)
```

각 guard는 이후 코드가 가정할 수 있는 상태를 하나씩 좁힌다. 마지막 줄에 도달했다면 `order`가 존재하고 결제되었으며 취소되지 않았다는 전제가 생긴다. 반대로 모든 분기를 하나의 거대한 boolean 식으로 압축하면 실패 이유를 구분하기 어렵고, 중첩 `if`로만 표현하면 happy path가 깊숙이 밀릴 수 있다.

predicate를 함수로 추출할 때 이름만 바꾸고 여전히 여러 부작용을 숨기면 의미가 좋아지지 않는다. `can_ship(order)`가 순수하게 정책을 판단한다면 테스트하기 쉽지만, 그 안에서 DB를 갱신하거나 메시지를 보내면 이름과 동작이 어긋난다. 제어 흐름을 정리하는 목적은 줄 수를 줄이는 것이 아니라 **경로마다 필요한 전제와 효과를 선명하게 만드는 것**이다.

코드 리뷰에서는 가능한 경로 수를 세어 본다. 조건이 여러 개 독립적으로 조합되면 테스트해야 할 상태 공간이 빠르게 증가한다. 이를 작은 함수, 상태 머신, lookup table, polymorphism 등으로 나눌 수 있는지 판단하는 것이 다음 설계 단계다.
