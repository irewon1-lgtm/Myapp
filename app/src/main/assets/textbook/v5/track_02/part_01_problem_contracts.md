# PART 01 · 문제 분해와 실행 계약 — 요구사항을 상태·불변식·절차로 바꾸기

프로그램은 사람이 원하는 결과를 컴퓨터가 수행할 수 있는 상태 변화와 판단 순서로 변환한 것이다. 문법을 아는 것만으로는 충분하지 않다. 입력이 무엇인지, 어떤 상태를 허용하는지, 성공과 실패를 어떻게 구분하는지, 중간 계산이 어떤 불변조건을 지켜야 하는지를 먼저 정해야 코드가 커져도 의미가 흔들리지 않는다. 문제 분해는 일을 잘게 나누는 기술이 아니라 **모호한 요구를 검증 가능한 계약으로 바꾸는 기술**이다.

---

## CHAPTER 01 · 요구사항을 `입력 → 상태 변화 → 출력`으로 다시 쓴다

### 시작 전 용어집

#### 1. 요구사항

- **뜻:** “주문 금액을 계산한다”라는 문장은 사람에게는 충분해 보이지만 컴퓨터가 실행하기에는 정보가 부족하다.
- **왜 중요한가:** 어떤 값을 입력받는지, 값의 단위는 무엇인지, 할인은 언제 적용하는지, 수량이 0이거나 음수면 어떻게 할지, 계산 결과를 정수로 저장할지 소수로 저장할지 정해져 있지 않다.
- **예시:** 입력: unit_price, quantity, customer_tier / 검증: price >= …

#### 2. 입력

- **뜻:** 첫 번째 분해는 입력과 출력의 모양을 고정하는 데서 시작한다.
- **왜 중요한가:** 입력에는 이름만이 아니라 타입, 단위, 허용 범위, 누락 가능성, 신뢰 수준이 붙는다.
- **예시:** 입력: unit_price, quantity, customer_tier / 검증: price >= …

#### 3. 상태 변화

- **뜻:** 실행 가능한 문제 정의는 목표 문장보다 더 많은 경계를 포함한다.
- **왜 중요한가:** 출력에는 정상 결과뿐 아니라 실패가 어떻게 표현되는지도 들어간다.
- **예시:** 입력: unit_price, quantity, customer_tier / 검증: price >= …

#### 4. 출력

- **뜻:** 그 사이의 처리는 단순 계산식이 아니라 입력 검증, 상태 조회, 규칙 적용, 결과 생성의 순서다.
- **왜 중요한가:** 이렇게 쓰면 문법을 선택하기 전에도 테스트할 수 있는 질문이 생긴다.
- **예시:** 입력: unit_price, quantity, customer_tier / 검증: price >= …

```text
입력: unit_price, quantity, customer_tier
검증: price >= 0, quantity > 0, tier가 허용 집합에 속함
처리: subtotal 계산 → 할인 규칙 적용 → 반올림
출력: payable_amount 또는 명시적 오류
```

 `quantity=0`은 허용되는가, 할인 후 금액이 음수가 될 수 있는가, 고객 등급을 찾지 못하면 기본 등급을 적용할지 실패할지 같은 질문이다. 좋은 분해는 코드 줄 수를 줄이는 것이 아니라 **결정해야 할 의미를 표면으로 끌어낸다.**

## CHAPTER 02 · 자연어의 모호함을 데이터 계약으로 제거한다

### 시작 전 용어집

#### 1. 데이터 계약

- **뜻:** 데이터 계약은 이런 표현을 비교 가능한 값과 규칙으로 바꾼다.
- **왜 중요한가:** 예를 들어 “최근 30일 주문”은 기준 시각과 시간대를 정해야 한다.
- **예시:** shape: 어떤 필드가 존재하는가 / representation: 값은 어떤 …

#### 2. 요구사항

- **뜻:** 자연어 요구사항은 문맥을 공유하는 사람끼리 대화할 때는 효율적이지만 프로그램의 경계에서는 위험하다.
- **왜 중요한가:** “최근 주문”, “유효한 사용자”, “금액이 크다”, “빠르게 처리한다” 같은 표현은 구현자가 임의로 해석할 여지가 있다.
- **예시:** shape: 어떤 필드가 존재하는가 / representation: 값은 어떤 …

#### 3. 경계

- **뜻:** 서버의 현재 시각인지 사용자의 지역 시각인지, 정확히 30×24시간인지 달력 날짜 30개인지에 따라 결과가 달라진다.
- **왜 중요한가:** “금액”도 통화, 최소 단위, 반올림 방식이 빠지면 서로 다른 서비스가 같은 숫자를 다르게 해석할 수 있다.
- **예시:** shape: 어떤 필드가 존재하는가 / representation: 값은 어떤 …

#### 4. 타입

- **뜻:** 가능한 규칙은 타입, 생성 함수, validation, 테스트에 반복 가능한 형태로 남긴다.
- **왜 중요한가:** 반대로 모든 규칙을 한 곳에 몰아넣으면 변경 이유가 섞이므로 표현 수준의 검증과 업무 수준의 검증을 구분한다.
- **예시:** shape: 어떤 필드가 존재하는가 / representation: 값은 어떤 …

`1000`이라는 값은 원화 1000원, 달러 센트 1000, 포인트 1000 중 무엇인지 스스로 말해 주지 않는다.

계약을 만들 때는 다음 속성을 분리한다.

```text
shape: 어떤 필드가 존재하는가
representation: 값은 어떤 타입과 단위인가
range: 허용 범위는 어디까지인가
presence: 누락과 null은 어떤 의미인가
invariant: 여러 필드가 함께 만족해야 하는 규칙은 무엇인가
failure: 계약 위반을 어떻게 전달하는가
```

계약은 문서에만 적으면 쉽게 코드와 어긋난다.   이메일 문자열이 비어 있지 않은가와 해당 이메일이 이미 가입되어 있는가는 서로 다른 층의 판단이다.

## CHAPTER 03 · 분해의 단위는 “한 문장”이 아니라 변경 이유다

### 시작 전 용어집

#### 1. 함수

- **뜻:** 기능을 작은 함수로 많이 나눈다고 자동으로 좋은 구조가 되지는 않는다.
- **왜 중요한가:** `get_value()`, `check_value()`, `do_value()`처럼 의미가 약한 조각을 늘리면 호출 순서만 길어지고 규칙은 더 찾기 어려워진다.
- **예시:** 주문 처리라면 가격 계산, 재고 예약, 결제 승인, …

#### 2. value

- **뜻:** 분해 단위는 **하나의 독립된 책임과 변경 이유를 가지는가**로 판단하는 편이 강하다.
- **왜 중요한가:** 주문 처리라면 가격 계산, 재고 예약, 결제 승인, 영수증 생성은 서로 다른 외부 상태와 실패 조건을 가진다.
- **예시:** 가격 규칙이 바뀌어도 재고 예약 프로토콜은 바뀌지 않을 …

#### 3. 상태

- **뜻:** 호출 관계를 그릴 때 “무엇을 호출하는가”만 표시하지 말고 **어떤 상태를 읽고 쓰며 실패 시 누가 복구 책임을 지는가**를 함께 기록한다.
- **왜 중요한가:** 계산처럼 외부 상태가 없는 조각은 값만 주고 결과를 확인할 수 있고, 네트워크나 파일을 다루는 조각은 경계에서 대체 가능하게 만들 수 있다.
- **예시:** 가격 규칙이 바뀌어도 재고 예약 프로토콜은 바뀌지 않을 …

#### 4. 실패

- **뜻:** 분해한 조각 사이에는 입력과 출력뿐 아니라 부작용, 실패, 순서 의존성이 존재한다.
- **왜 중요한가:** `reserve_stock()`이 성공한 뒤 `charge_card()`가 실패했다면 예약을 되돌릴지 유지할지 결정해야 한다.
- **예시:** 가격 규칙이 바뀌어도 재고 예약 프로토콜은 바뀌지 않을 …

가격 규칙이 바뀌어도 재고 예약 프로토콜은 바뀌지 않을 수 있고, 결제사가 바뀌어도 할인 계산은 유지될 수 있다. 이런 경계가 함수·모듈 경계 후보다. 반대로 단순히 한 식을 세 함수로 쪼개는 것은 인지적 경계가 아니라 기계적인 분할일 수 있다.

  

좋은 경계는 테스트 단위도 만든다.  문제 분해는 곧 의존성 분해이며, 이 선택이 이후 디버깅 난이도와 변경 비용을 좌우한다.

## CHAPTER 04 · 상태는 “현재 값”과 “허용되는 전이”의 조합이다

### 시작 전 용어집

#### 1. 상태

- **뜻:** 주문의 `status`를 문자열 하나로 저장하는 것만으로는 상태 모델이 완성되지 않는다.
- **왜 중요한가:** 어떤 상태에서 어떤 상태로 이동할 수 있는지, 이동에 필요한 조건은 무엇인지, 전이가 실패하면 이전 상태가 유지되는지를 정의해야 한다.
- **예시:** CREATED --pay--> PAID / CREATED --cancel--> CANCELLED

#### 2. 조건

- **뜻:** 상태 전이는 단지 `status = new_status` 대입이 아니라 **이전 상태, 입력 이벤트, 허용 조건, 결과 상태를 묶은 함수**로 보는 편이 정확하다.
- **왜 중요한가:** 동시 실행이 있는 환경에서는 두 요청이 같은 이전 상태를 읽고 서로 다른 전이를 시도할 수 있다.
- **예시:** CREATED --pay--> PAID / CREATED --cancel--> CANCELLED

#### 3. 실패

- **뜻:** 프로그램이 복잡해지는 가장 큰 이유 중 하나는 값이 시간에 따라 바뀌기 때문이다.
- **왜 중요한가:** 이 모델에서 `CANCELLED → SHIPPED`는 단순히 코드에 없는 경로가 아니라 금지된 전이다.
- **예시:** CREATED --pay--> PAID / CREATED --cancel--> CANCELLED

#### 4. API

- **뜻:** API나 내부 함수가 직접 호출될 수 있으므로 실제 상태를 변경하는 경계에서도 전이 규칙을 검사해야 한다.
- **왜 중요한가:** 상태 머신을 한 곳의 진실로 만들지 않으면 화면, 서버, 데이터베이스가 서로 다른 규칙을 갖게 된다.
- **예시:** CREATED --pay--> PAID / CREATED --cancel--> CANCELLED

```text
CREATED --pay--> PAID
CREATED --cancel--> CANCELLED
PAID --ship--> SHIPPED
SHIPPED --deliver--> DELIVERED
```

 UI가 버튼을 숨기는 것만으로는 충분하지 않다.  

상태를 모델링할 때는 이벤트와 상태를 구분한다. `PAYMENT_SUCCEEDED`는 발생한 사건이고 `PAID`는 그 사건을 반영한 현재 상태다. 사건을 처리했는지 여부가 중요하다면 동일 이벤트가 두 번 들어왔을 때 결과가 중복되지 않도록 idempotency 규칙도 필요하다. 

 따라서 상태 모델은 논리 규칙뿐 아니라 저장 시점의 원자성, 버전 검사, 트랜잭션 경계까지 연결된다. 작은 프로그램에서도 상태 전이를 명시하는 습관은 나중에 데이터베이스와 네트워크를 다룰 때 그대로 확장된다.

## CHAPTER 05 · precondition과 postcondition은 함수의 의미를 고정한다

### 시작 전 용어집

#### 1. precondition

- **뜻:** precondition은 호출자가 만족시켜야 할 조건이고, postcondition은 함수가 정상적으로 끝났을 때 보장하는 조건이다.
- **왜 중요한가:** 둘 사이에 함수 내부가 항상 지켜야 하는 invariant가 있다.
- **예시:** precondition / - amount > 0

#### 2. postcondition

- **뜻:** 함수 이름은 의도를 전달하지만 허용 입력과 보장 결과를 완전히 표현하지 못한다.
- **왜 중요한가:** 이 세 가지를 구분하면 구현 세부사항과 외부 계약을 분리할 수 있다.
- **예시:** precondition / - amount > 0

#### 3. 함수

- **뜻:** 계약은 모든 함수에 거대한 문서를 붙이라는 뜻이 아니다.
- **왜 중요한가:** 내부의 단순 변환 함수는 타입과 이름만으로 충분할 수 있다.
- **예시:** precondition / - amount > 0

#### 4. 입력

- **뜻:** 반면 외부 입력을 받거나 상태를 바꾸거나 돈·권한·데이터 손실에 영향을 주는 경계는 계약을 명시할 가치가 크다.
- **왜 중요한가:** 계약의 상세도는 실패 비용에 비례해 높이는 편이 합리적이다.
- **예시:** precondition / - amount > 0

예를 들어 계좌 이체 함수의 계약을 생각해 보자.

```text
precondition
- amount > 0
- from_account와 to_account가 존재
- from_account.balance >= amount

postcondition on success
- 두 계좌 총액의 합은 변하지 않음
- 보내는 계좌는 amount만큼 감소
- 받는 계좌는 amount만큼 증가

failure
- 계약 위반이면 어느 잔액도 부분 변경되지 않음
```

이 계약은 어떤 Python 문법으로 구현할지보다 강한 정보를 준다. 테스트는 경계값과 실패 원자성을 직접 확인할 수 있고, 구현을 데이터베이스 트랜잭션으로 바꾸더라도 외부 의미는 유지할 수 있다. 반대로 “이체한다”라는 설명만 있으면 한 계좌에서 차감한 뒤 오류가 났을 때 어떤 상태가 정답인지 판단하기 어렵다.

## CHAPTER 06 · 예제보다 반례가 계약의 빈틈을 더 빨리 찾는다

### 시작 전 용어집

#### 1. 반례

- **뜻:** 따라서 요구사항을 코드로 옮길 때는 성공 예제와 함께 **규칙을 깨뜨릴 수 있는 반례 후보**를 만든다.
- **왜 중요한가:** 수량 할인 규칙이 `10개 이상이면 10% 할인`이라면 `9`, `10`, `11`을 확인한다.
- **예시:** member owner admin | allow / F F …

#### 2. 계약

- **뜻:** 외부 계약만 보고 “이 값 조합에서 어떤 결과가 나와야 하는가”를 정할 수 있어야 한다.
- **왜 중요한가:** 구현을 보고 테스트 입력을 고르면 이미 작성된 코드의 사고방식을 그대로 따라가 누락을 재현할 위험이 있다.
- **예시:** member owner admin | allow / F F …

#### 3. 입력

- **뜻:** 정상 입력 하나가 원하는 결과를 낸다는 사실은 규칙이 완성되었다는 증거가 아니다.
- **왜 중요한가:** 많은 버그는 경계, 누락, 중복, 순서 변경, 예상하지 못한 조합에서 나타난다.
- **예시:** member owner admin | allow / F F …

#### 4. 경계

- **뜻:** 반례 설계에서는 단일 필드의 경계뿐 아니라 필드 간 모순을 본다.
- **왜 중요한가:** `start_time > end_time`, `discount > subtotal`, `status=DELIVERED인데 delivered_at=null` 같은 조합은 각각의 필드 타입만 검사해서는 잡히지 않는다.
- **예시:** member owner admin | allow / F F …

날짜 범위가 `[start, end)`라면 `start` 직전, 정확히 `start`, `end` 직전, 정확히 `end`를 확인한다. 사용자 권한이 `admin OR (member AND owner)`라면 boolean 조합을 표로 펼쳐 우선순위 오해를 제거한다. 이 방식은 테스트 기술인 동시에 문제 정의 기술이다.

```text
member owner admin | allow
F      F     F     | F
T      F     F     | F
T      T     F     | T
F      F     T     | T
```

  이런 규칙은 객체 전체의 invariant다.

좋은 반례는 구현을 알 필요가 없다.   요구사항 단계에서 반례를 만들면 설계와 검증이 같은 계약을 공유하게 된다.

## CHAPTER 07 · 의사코드는 제어 흐름과 데이터 흐름을 동시에 보여 준다

### 시작 전 용어집

#### 1. 의사코드

- **뜻:** 의사코드는 특정 언어의 문법을 흉내 내는 것이 아니라 실행 순서를 검토하기 위한 중간 표현이다.
- **왜 중요한가:** 좋은 의사코드는 입력이 어떤 이름으로 저장되고, 어떤 조건에서 경로가 갈리며, 반복이 무엇을 갱신하고, 실패 시 어디서 종료되는지 드러낸다.
- **예시:** function checkout(cart, customer): / require cart is not …

#### 2. 입력

- **뜻:** 자연어 문장만 나열하면 데이터 의존성이 숨고, 실제 코드부터 쓰면 문법 세부사항에 사고가 묻힐 수 있다.
- **왜 중요한가:** 이 표현에서 `subtotal`, `discount`, `payable`은 단순 변수명이 아니라 데이터 흐름의 단계다.
- **예시:** function checkout(cart, customer): / require cart is not …

#### 3. 조건

- **뜻:** 루프가 있다면 초기 상태, 반복 조건, 한 번의 반복이 바꾸는 값, 종료 후 보장 상태를 적는다.
- **왜 중요한가:** 이렇게 하면 실제 언어에서 `for`를 쓸지 `while`을 쓸지는 뒤의 결정이 되고, 무한 반복이나 경계 누락을 코드 작성 전에 발견할 수 있다.
- **예시:** function checkout(cart, customer): / require cart is not …

#### 4. 반복

- **뜻:** 각 값이 이전 값에서 어떻게 만들어지는지 추적할 수 있고, `discount_policy`라는 별도 책임도 보인다.
- **왜 중요한가:** 이후 Python으로 옮길 때는 이 구조를 보존하면서 구체적인 타입과 예외, 함수 호출 문법을 선택한다.
- **예시:** function checkout(cart, customer): / require cart is not …

```text
function checkout(cart, customer):
    require cart is not empty
    subtotal = sum(valid line totals)
    discount = discount_policy(customer, subtotal)
    payable = round_money(subtotal - discount)
    if payable < 0:
        fail INVALID_TOTAL
    return payable
```

  

의사코드에 구현 세부사항을 너무 많이 넣으면 중간 표현의 장점이 사라진다. 반대로 “적절히 계산한다”처럼 핵심 결정을 숨기면 검토할 것이 없다. 판단 기준은 **다른 사람이 같은 의사코드를 보고 중요한 분기와 상태 변화를 동일하게 구현할 수 있는가**다.

## CHAPTER 08 · 실패도 출력의 한 종류로 모델링한다

### 시작 전 용어집

#### 1. 실패

- **뜻:** 실패를 “정상 결과가 안 나온 상태”로만 취급하면 호출자는 왜 실패했는지, 재시도해도 되는지, 부분 변경이 남았는지 알 수 없다.
- **왜 중요한가:** 실행 계약에는 성공 경로와 같은 수준으로 실패 의미가 포함되어야 한다.
- **예시:** Python에서는 이후 예외를 사용해 이런 실패 경계를 표현할 …

#### 2. 출력

- **뜻:** 입력 오류, 현재 상태 충돌, 외부 서비스 장애, 프로그램 불변식 위반은 서로 다른 대응을 요구한다.
- **왜 중요한가:** 입력 오류는 같은 입력으로 재시도해도 성공하지 않을 가능성이 높다.
- **예시:** Python에서는 이후 예외를 사용해 이런 실패 경계를 표현할 …

#### 3. 상태

- **뜻:** 내부 불변식 위반은 사용자에게 다른 값을 입력하라고 요구할 문제가 아니라 코드 또는 저장 상태의 결함일 수 있다.
- **왜 중요한가:** 모든 실패를 `False`나 빈 문자열로 축약하면 이 정보가 사라진다.
- **예시:** Python에서는 이후 예외를 사용해 이런 실패 경계를 표현할 …

#### 4. 계약

- **뜻:** 실패 계약에는 최소한 원인 범주, 호출자에게 공개할 정보, 상태 변경 여부, 재시도 가능성, 로깅에 남길 식별자가 필요할 수 있다.
- **왜 중요한가:** Python에서는 이후 예외를 사용해 이런 실패 경계를 표현할 수 있지만, 먼저 의미를 설계해야 한다.
- **예시:** 예외 타입만 많이 만든다고 실패 모델이 선명해지는 것은 …

네트워크 timeout은 잠시 후 재시도로 성공할 수 있지만, 이미 원격 작업이 완료되었는지 모르는 불확실성이 생길 수 있다.  

  예외 타입만 많이 만든다고 실패 모델이 선명해지는 것은 아니다.

실패 시 상태가 어떻게 남는지도 중요하다. 파일을 절반만 쓴 뒤 오류가 날 수 있는지, 결제 승인 후 주문 저장이 실패할 수 있는지, 메모리 안의 캐시만 갱신되고 영구 저장은 실패할 수 있는지를 따진다. 오류 처리는 마지막에 붙이는 `try/except`가 아니라 **상태 변화 설계의 일부**다.

## CHAPTER 09 · 순수 계산과 부작용의 경계를 분리한다

### 시작 전 용어집

#### 1. 부작용

- **뜻:** 실제 프로그램에는 부작용이 필요하지만 부작용의 위치를 좁히는 것이 핵심이다.
- **왜 중요한가:** 예를 들어 주문 생성 기능을 `현재 시각 읽기 → 사용자 조회 → 가격 계산 → DB 저장 → 메시지 발송`으로 한 함수에 묶으면 가격 계산 테스트에도 데이터베이스와 시계가 필요해질 수 있다.
- **예시:** 실제 프로그램에는 부작용이 필요하지만 부작용의 위치를 좁히는 것이 …

#### 2. 경계

- **뜻:** 계산 함수에 `items`, `price_policy`, `now` 같은 필요한 값을 명시적으로 전달하고, 저장과 발송을 바깥 경계에서 수행하면 계산 규칙을 독립적으로 검증할 수 있다.
- **왜 중요한가:** DB 저장은 성공했는데 메시지 발송이 실패했을 때 주문을 취소할지, 메시지만 재시도할지 정책을 결정할 수 있어야 한다.
- **예시:** 계산 함수에 `items`, `price_policy`, `now` 같은 필요한 값을 …

#### 3. 입력

- **뜻:** 같은 입력에서 같은 결과를 계산하고 외부 상태를 바꾸지 않는 함수는 추론하기 쉽다.
- **왜 중요한가:** 할인액 계산, 문자열 정규화, 좌표 변환처럼 입력을 결과로 바꾸는 로직은 가능한 한 파일, 네트워크, 현재 시각, 전역 변수와 분리할수록 테스트와 재사용이 단순해진다.
- **예시:** 같은 입력에서 같은 결과를 계산하고 외부 상태를 바꾸지 …

#### 4. 상태

- **뜻:** 필요한 상태를 명시적으로 전달하거나 좁은 객체 경계 안에 두면 데이터 흐름이 보인다.
- **왜 중요한가:** 이는 함수형 스타일을 강제하는 규칙이 아니라 복잡도를 제어하는 설계 원리다.
- **예시:** 필요한 상태를 명시적으로 전달하거나 좁은 객체 경계 안에 …

부작용 경계는 실패 처리와도 연결된다.  두 작업이 한 함수 안에 섞여 있으면 어느 단계까지 성공했는지 추적하기 어렵다. 부작용을 없애는 것이 아니라 **관찰 가능하고 복구 가능한 단위로 격리**한다.

전역 상태도 같은 문제를 만든다. 함수가 매개변수에 없는 값을 몰래 읽거나 바꾸면 호출만 보고 의존성을 알 수 없다.

- **왜 중요한가:** 한 줄씩 처리할 수 있는 문제라면 iterator나 stream 형태가 더 적합할 수 있다.

  작은 연습에서도 입력 크기를 10배, 100배 늘려 보는 습관은 코드의 구조적 비용을 드러낸다.

- **예시:** 예를 들어 “VIP 고객은 배송비 무료”라는 규칙이 있다면 …

- **왜 중요한가:** 예를 들어 “VIP 고객은 배송비 무료”라는 규칙이 있다면 UI에서만 `if tier == 'VIP'`를 쓰고 서버에서는 다른 조건을 사용하지 않도록 하나의 정책으로 모은다.

#### 4. 조건

- **뜻:** 긴 자연어 지시보다 입력/출력, 불변식, 금지 조건, 반례, 기존 인터페이스를 함께 주면 생성 코드의 자유도가 줄고 검증 기준이 선명해진다.
- **왜 중요한가:** 사람이 직접 쓰든 AI가 쓰든 계약은 결과를 평가하는 기준점이다.

추적 가능성은 과도한 문서화와 다르다.   변경 이력에서 “무엇을 바꿨는가”뿐 아니라 “어떤 계약 때문에 바꿨는가”가 드러나면 회귀 버그를 줄이는 데 도움이 된다.

AI에게 구현을 맡길 때도 같은 원리가 적용된다.

## CHAPTER 12 · 하나의 기능을 계약에서 코드 직전까지 내린다

### 시작 전 용어집

#### 1. 계약

- **뜻:** 예제로 “장바구니의 결제 가능 금액을 계산한다”는 기능을 모델링해 보자.
- **왜 중요한가:** 각 품목은 `unit_price >= 0`, `quantity > 0`을 만족하고 통화는 하나로 통일되어야 한다.
- **예시:** validate_lines(lines) / subtotal = sum_line_totals(lines)

#### 2. 조건

- **뜻:** 쿠폰은 만료되지 않았고 주문 조건을 만족할 때만 적용한다.
- **왜 중요한가:** 최종 금액은 음수가 될 수 없으며, 오류가 있으면 부분 결과 대신 명시적으로 실패한다.
- **예시:** validate_lines(lines) / subtotal = sum_line_totals(lines)

#### 3. 오류

- **뜻:** 코드 작성 전에 이 정도가 명확하다면 문법 오류는 고치기 쉬운 표면 문제가 되고, 더 비싼 의미 오류를 크게 줄일 수 있다.
- **왜 중요한가:** 품목 검증은 개별 입력의 형식을 다루고, subtotal 계산은 유효한 품목의 금액을 합산한다.
- **예시:** validate_lines(lines) / subtotal = sum_line_totals(lines)

#### 4. 실패

- **뜻:** 그리고 실패 중 어느 단계까지 상태가 변경되는지 확인한다.
- **왜 중요한가:** 쿠폰 정책은 고객·쿠폰·subtotal을 보고 할인액을 반환한다.
- **예시:** validate_lines(lines) / subtotal = sum_line_totals(lines)

먼저 외부 계약을 정한다.   

그 다음 책임을 나눈다.   금액 정규화는 통화의 최소 단위와 반올림 정책을 적용한다. 각 조각은 독립적으로 테스트할 수 있고, 조합 함수가 호출 순서를 책임진다.

```text
validate_lines(lines)
subtotal = sum_line_totals(lines)
discount = coupon_policy(customer, coupon, subtotal)
payable = normalize_money(subtotal - discount)
require payable >= 0
return payable
```

이 구조에서 구현 언어를 Python에서 다른 언어로 바꿔도 문제 모델은 유지된다. Python을 사용하면 각 단계는 함수, 값, 조건, 예외, collection으로 표현된다. 이후 배우는 문법은 이 사고 구조를 실행 가능한 형태로 옮기기 위한 도구다.

마지막 검토에서는 정상 예제뿐 아니라 빈 장바구니, 수량 0, 매우 큰 수량, 만료 쿠폰, 할인액이 subtotal보다 큰 경우, 서로 다른 통화가 섞인 경우를 본다.
