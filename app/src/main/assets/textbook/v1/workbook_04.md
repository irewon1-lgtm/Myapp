# 4장 실전 훈련편 — 성능 측정·병목·메모리·캐시

이 훈련편은 CPU/RAM 정의를 반복하지 않는다. 실제 성능 문제를 **측정 → 병목 후보 → 비교 실험 → 개선 검증** 순서로 다룬다.

---

## 훈련 A. 총 시간에서 가장 큰 구간 찾기

측정값:

```text
화면 이벤트 처리 20ms
DB 조회 80ms
JSON 파싱 30ms
이미지 로딩 650ms
UI 렌더링 70ms
```

총합과 가장 큰 비중을 계산한다.

가장 먼저 최적화 후보로 볼 곳은 이미지 로딩이다.

### 변형

이미지 로딩을 650ms → 300ms로 줄였다.

전체 예상 시간은 얼마나 줄어드는가?

성능 개선은 한 함수의 “몇 % 빨라짐”보다 사용자 전체 흐름이 얼마나 빨라졌는지 함께 본다.

---

## 훈련 B. baseline 없는 성능 주장의 문제

주장:

> 코드를 리팩터링했더니 훨씬 빨라졌습니다.

증거:

```text
수정 전 측정 없음
수정 후 800ms
```

판정: 개선을 증명할 수 없다.

필요한 최소 정보:

```text
같은 기기
같은 데이터
같은 네트워크 조건
수정 전 반복 측정
수정 후 반복 측정
```

---

## 훈련 C. 평균만 보면 숨는 느린 케이스

응답시간 10회:

```text
100, 105, 98, 102, 97, 101, 99, 103, 100, 3000 ms
```

평균을 계산하면 한 번의 3초 지연이 섞인다.

질문:

- 평균만 보고 “대부분 빠르다”라고 해도 되는가?
- 최댓값/p95/p99 같은 지표가 왜 필요한가?

정확한 통계 구현이 목표가 아니라 **사용자 일부가 겪는 긴 지연을 평균이 숨길 수 있다**는 점을 확인한다.

---

## 훈련 D. CPU 병목과 I/O 병목 구분

상황 1:

```text
CPU 95%
디스크 I/O 낮음
네트워크 대기 없음
함수 실행 중 계속 연산
```

CPU 계산 후보가 강하다.

상황 2:

```text
CPU 10%
네트워크 응답 4초 대기
```

CPU 최적화는 우선순위가 낮다.

상황 3:

```text
CPU 15%
DB query 3초
```

DB/I/O 쪽을 본다.

## 훈련 E. N+1 조회 감지

목록 100개를 불러온 뒤 각 항목마다 DB 조회를 한 번씩 추가로 실행한다고 하자.

```text
목록 조회 1회
세부 조회 100회
총 101회
```

항목 수가 늘면 조회 횟수도 선형으로 늘어난다.

로그에서 다음 패턴을 찾는다.

```text
SELECT item list
SELECT detail id=1
SELECT detail id=2
...
SELECT detail id=100
```

가능한 개선 후보:

- JOIN/일괄 조회
- 필요한 데이터 미리 포함
- 캐시

실제 정답은 데이터 구조와 DB 특성에 따라 다르다. 우선 **반복 I/O가 병목인지 측정**한다.

---

## 훈련 F. 이미지 메모리 계산

해상도:

```text
4000 × 3000 픽셀
```

픽셀당 4바이트라고 단순 가정하면 메모리 크기는:

```text
4000 × 3000 × 4 = 48,000,000 bytes
```

약 48MB 수준이다.

이런 이미지를 20장 동시에 메모리에 원본 크기로 올리면 큰 부담이 된다.

질문:

- 파일 크기가 5MB라고 디코딩 후 RAM도 5MB인가?
- 썸네일에는 원본 해상도가 필요한가?

파일 압축 크기와 디코딩 메모리 크기가 다를 수 있다.

---

## 훈련 G. 메모리 누수 패턴 찾기

측정:

```text
앱 시작 200MB
화면 A 진입/나오기 1회 230MB
2회 260MB
3회 290MB
4회 320MB
```

화면을 떠날 때 메모리가 충분히 내려가지 않고 반복할수록 계속 증가한다.

가설:

- 화면 객체 참조 유지
- listener 해제 안 됨
- 큰 bitmap cache 무제한 증가
- coroutine/task가 화면을 붙잡음

증거를 더 모으기 전 “메모리 누수 확정”이라고 단정하지 않는다.

---

## 훈련 H. 캐시 hit/miss 측정

가상의 이미지 캐시 로그:

```text
100 requests
70 cache hit
30 cache miss
```

hit rate는 70%다.

하지만 다음 질문이 더 중요하다.

- miss 30개가 매우 큰 파일인가?
- 오래된 캐시를 잘못 반환하고 있지는 않은가?
- cache key가 정확한가?
- cache가 메모리를 너무 많이 쓰는가?

높은 hit rate 자체가 올바른 캐시라는 뜻은 아니다.

---

## 훈련 I. 잘못된 cache key

이미지 URL:

```text
/avatar/user123?size=small
/avatar/user123?size=large
```

cache key를 `/avatar/user123`만 쓰면 작은 이미지와 큰 이미지가 충돌할 수 있다.

캐시 키는 **결과를 결정하는 입력**을 충분히 포함해야 한다.

주식 데이터라면:

```text
symbol + metric + asOfDate + currency + adjusted/unadjusted
```

같은 기준이 필요할 수 있다.

---

## 훈련 J. 캐시 무효화 설계

다음 데이터를 캐시한다고 하자.

```text
회사 이름: 거의 안 바뀜
실시간 주가: 자주 바뀜
분기 재무: 분기마다 바뀜
사용자 프로필 사진: 사용자가 변경할 때 바뀜
```

모든 데이터에 같은 24시간 TTL을 적용하는 것이 적절한가?

아니다. 데이터 신선도 요구가 다르다.

각 항목에 어떤 무효화 정책이 합리적인지 적어본다.

---

## 훈련 K. UI 렌더링 과다 감지

사용자가 검색어 한 글자를 입력할 때마다 전체 화면의 수천 개 항목이 다시 계산된다고 하자.

증거:

```text
keystroke 1회
recomposition/render count 2000+
CPU spike 80%
```

가능한 해결 방향:

- 필요한 state만 구독
- 계산 결과 memoization
- 리스트 virtualization
- 검색 debounce

도구 이름보다 **불필요한 작업량을 줄이는 것**이 핵심이다.

## 훈련 L. 성능 개선이 정확성을 깨뜨림

개선 전:

```text
매 요청마다 최신 가격 조회
느리지만 정확
```

개선 후:

```text
가격을 하루 종일 캐시
매우 빠름
하지만 장중 가격이 오래됨
```

성능은 좋아졌지만 제품 요구사항은 깨졌다.

성능 최적화의 완료조건에는 **정확성/신선도 회귀시험**도 들어가야 한다.

## AI 답 검증 1

AI 답:

> CPU 사용률이 30%이므로 성능 문제는 CPU와 무관합니다.

판정: 근거 부족.

전체 평균 CPU 30%라도 특정 스레드/코어가 병목일 수 있고, 짧은 spike가 있을 수 있다. 다른 지표와 함께 본다.

---

## AI 답 검증 2

AI 답:

> RAM이 12GB이므로 메모리 누수는 발생할 수 없습니다.

판정: 틀림.

누수는 총 RAM 용량과 별개로 시간이 지나면서 불필요한 참조가 누적되는 문제다.

## 디버깅 미션 1 — 리스트 느림

실험 결과:

```text
이미지 숨김 → 부드러움
이미지 표시 → 끊김
네트워크 off + 캐시 이미지 → 여전히 끊김
CPU spike 높음
```

가능성이 높은 후보를 좁힌다.

- 네트워크 자체보다는 이미지 디코딩/렌더링 비용이 강한 후보

다음 실험을 설계한다.

```text
썸네일 해상도 축소
이미지 개수 제한
디코딩 위치/시간 측정
```

# 4장 훈련 완료 기준

- 전체 시간을 단계별로 분해하고 병목을 찾는다.
- baseline 없는 성능 개선 주장을 승인하지 않는다.
- 평균만으로 tail latency를 숨기지 않는다.
- CPU 병목과 I/O 대기를 구분한다.
- 이미지 파일 크기와 디코딩 RAM 크기를 구분한다.
- 반복 사용 시 메모리 증가 패턴을 분석한다.
- cache hit rate와 데이터 신선도를 함께 본다.
- 성능 개선 후 정확성/기능 회귀를 확인한다.
