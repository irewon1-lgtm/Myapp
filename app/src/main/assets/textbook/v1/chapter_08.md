## V1-C08. 인터넷이 연결되는 순서 — IP·DNS·포트·HTTP를 처음부터

**이 장의 대상:** 인터넷은 매일 쓰지만 `IP`, `DNS`, `포트`, `HTTP`, `TLS`, `socket`이 무슨 뜻인지 모르는 사람.

**이 장의 목표:** “인터넷이 안 된다”는 말을 하나의 문제로 보지 않고 **이름 찾기 → 대상 찾기 → 연결하기 → 안전한 통신 준비 → 요청 보내기 → 응답 받기** 순서로 나눌 수 있게 된다.

---

### 1. 인터넷은 무엇일까?

인터넷은 여러 컴퓨터와 네트워크가 서로 데이터를 주고받을 수 있게 연결된 거대한 구조다.

내 스마트폰이 주식 서버에서 가격을 받는 것도 인터넷 통신이다.

```text
내 스마트폰
↓
Wi-Fi 또는 이동통신
↓
여러 네트워크 장비
↓
인터넷
↓
서비스 서버
```

사용자는 버튼 한 번만 누르지만 내부에서는 여러 단계가 이어진다.

---

### 2. Wi-Fi가 연결됐다는 것과 인터넷이 된다는 것은 다르다

휴대폰 상단에 Wi-Fi 아이콘이 보인다고 무조건 인터넷이 되는 것은 아니다.

```text
휴대폰 ↔ 공유기 연결 성공
```

과:

```text
공유기 ↔ 인터넷 연결 성공
```

은 다른 단계다.

공유기에는 연결됐지만 외부 인터넷이 끊길 수 있다.

따라서 “Wi-Fi 아이콘 있음 = 서버까지 모두 정상”이라고 생각하면 안 된다.

---

### 3. 네트워크는 여러 층으로 본다

인터넷 문제를 아주 단순화하면 다음 질문으로 나눌 수 있다.

```text
1. 기기가 네트워크에 연결됐나?
2. 목적지 이름을 찾을 수 있나?
3. 목적지까지 연결할 수 있나?
4. 안전한 연결이 성립했나?
5. HTTP 요청을 보낼 수 있나?
6. 서버가 정상 응답했나?
7. 앱이 응답을 이해했나?
```

이 순서는 앞으로 네트워크 디버깅의 지도다.

---

### 4. IP 주소는 무엇일까?

네트워크에서 기기나 목적지를 구분하기 위해 주소가 필요하다.

대표적인 주소 체계가 **IP 주소(IP address)**다.

예시:

```text
192.168.0.10
```

또는 IPv6에서는 훨씬 다른 모양의 주소를 볼 수 있다.

처음에는:

> **IP 주소 = 네트워크에서 목적지를 찾기 위해 사용하는 숫자 주소 체계**

라고 생각하면 된다.

---

### 5. 도메인은 무엇일까?

사람은 숫자 IP를 외우기 어렵다.

그래서:

```text
example.com
openai.com
```

같은 이름을 사용한다.

이런 이름을 **도메인(domain)**이라고 부른다.

> **도메인 = 사람이 기억하기 쉬운 인터넷 이름**

웹사이트 주소에서 서비스가 누구 것인지 판단할 때도 도메인이 중요하다.

---

### 6. DNS는 무엇일까?

도메인 이름을 실제 네트워크 주소와 연결해야 한다.

이 역할을 하는 대표 시스템이 **DNS**다.

처음에는 이렇게 기억하자.

> **DNS = 도메인 이름을 IP 주소로 찾아주는 인터넷 전화번호부 같은 시스템**

예:

```text
api.example.com
↓ DNS 조회
203.0.113.10
```

실제 DNS 구조는 훨씬 복잡하지만 첫 단계에서는 충분하다.

---

### 7. DNS가 실패하면 어떻게 보일까?

앱이 `api.example.com`에 접속하려는데 이름을 IP로 찾지 못하면 연결 단계로 가지 못할 수 있다.

오류 메시지 예:

```text
Unknown host
Name resolution failed
DNS lookup failed
```

이 경우 서버 앱 코드보다 먼저 DNS와 네트워크 이름 해석을 본다.

---

### 8. DNS가 됐다고 서버까지 연결된 것은 아니다

DNS가 IP를 잘 찾아줬다고 하자.

```text
api.example.com → 203.0.113.10
```

이제 실제로 그 서버의 특정 서비스에 연결해야 한다.

서버가 꺼져 있거나 방화벽이 막았거나 서비스가 해당 포트에서 듣고 있지 않으면 연결 실패할 수 있다.

즉:

```text
DNS 성공 ≠ 연결 성공
```

이다.

---

### 9. 포트는 무엇일까?

한 컴퓨터 안에서도 여러 네트워크 프로그램이 동시에 실행될 수 있다.

어느 프로그램과 통신할지 구분하기 위해 **포트(port)** 번호를 사용한다.

쉬운 비유:

```text
IP 주소 = 건물 주소
포트    = 건물 안의 호실 번호
```

완벽한 비유는 아니지만 초보자에게 도움이 된다.

예:

```text
443
80
5432
```

같은 숫자를 볼 수 있다.

> **포트 = 한 네트워크 주소 안에서 어떤 서비스와 통신할지 구분하는 번호**

---

### 10. 443과 80은 왜 자주 보일까?

웹 통신에서 흔히:

```text
80  → HTTP
443 → HTTPS
```

를 기본 포트로 사용한다.

하지만 서비스가 다른 포트를 사용할 수도 있다.

숫자를 외우는 것보다 **주소와 포트가 함께 목적지를 구체화한다**는 개념을 이해한다.

---

### 11. 소켓은 무엇일까?

네트워크 통신 프로그램이 실제 연결을 다룰 때 **소켓(socket)**이라는 개념을 사용한다.

처음에는 이렇게 이해한다.

> **소켓 = 프로그램이 네트워크로 데이터를 주고받기 위해 사용하는 통신 끝점**

앱 개발자가 항상 낮은 수준의 소켓을 직접 다루는 것은 아니다.

HTTP 라이브러리가 대신 처리해줄 수 있다.

---

### 12. TCP는 무엇일까?

인터넷 통신에는 여러 전송 방식이 있다.

대표적인 하나가 **TCP**다.

TCP는 데이터를 순서대로 안정적으로 전달하기 위해 연결과 재전송 같은 기능을 제공한다.

첫 단계에서는:

> **TCP = 데이터가 순서대로 안정적으로 전달되도록 돕는 대표 전송 방식**

이라고 이해한다.

HTTP/1.1, HTTP/2 같은 웹 통신은 전통적으로 TCP 위에서 많이 동작한다.

---

### 13. UDP는 무엇일까?

또 다른 대표 방식이 **UDP**다.

TCP보다 연결 관리가 단순하고 지연을 줄이기 유리한 상황이 있지만, 기본적으로 데이터 전달 보장을 앱이 더 고려해야 한다.

> **UDP = 빠르고 단순한 전달에 유리하지만 기본 보장 방식이 TCP와 다른 전송 방식**

지금은 어느 것이 더 좋다고 외우지 않는다.

작업 목적에 따라 다르다.

---

### 14. 연결되었다는 것은 무엇일까?

앱이 서버에 요청하기 전에 네트워크 연결 단계가 필요할 수 있다.

TCP에서는 대표적으로 연결을 성립하는 절차가 있다.

세부 패킷 이름을 외우기보다:

```text
서버가 해당 주소와 포트에서 연결을 받을 준비가 됐는가?
내 기기에서 거기까지 통신 가능한가?
```

를 확인한다.

---

### 15. 타임아웃은 무엇일까?

서버 응답을 끝없이 기다릴 수는 없다.

일정 시간이 지나면 실패로 처리할 수 있다.

이를 **타임아웃(timeout)**이라고 부른다.

> **timeout = 정해진 시간 안에 필요한 결과가 오지 않아 기다리기를 중단하는 것**

타임아웃이 발생했다고 반드시 서버가 죽었다는 뜻은 아니다.

```text
네트워크 느림
서버 과부하
방화벽
DNS 지연
잘못된 주소
```

등 여러 원인이 있다.

---

### 16. TLS는 무엇일까?

인터넷으로 중요한 데이터를 보낼 때 중간에서 내용을 쉽게 훔쳐보거나 바꾸지 못하도록 보호해야 한다.

웹에서 이 보안을 제공하는 대표 기술이 **TLS**다.

HTTPS의 `S`가 안전한 통신과 관련되어 있다.

> **TLS = 네트워크 통신을 암호화하고 상대 서버를 확인하는 데 사용하는 보안 기술**

세부 암호 알고리즘은 보안 권에서 배운다.

---

### 17. HTTPS는 무엇일까?

**HTTPS**는 HTTP 통신을 TLS로 보호하는 방식이라고 이해하면 된다.

```text
HTTP + TLS → HTTPS
```

쉽게 말하면 웹 요청과 응답을 보호된 연결 위에서 주고받는다.

주소창에:

```text
https://example.com
```

처럼 보일 수 있다.

---

### 18. 인증서라는 말

TLS 연결에서는 서버가 누구인지 확인하기 위해 **인증서(certificate)**를 사용한다.

> **인증서 = 서버의 신원을 확인하는 데 쓰이는 디지털 증명서**

인증서가 만료되었거나 도메인과 맞지 않으면 안전한 연결이 실패할 수 있다.

초보자는 “HTTPS 오류 = 인터넷 전체 장애”라고 생각하지 않는다.

---

### 19. HTTP는 무엇일까?

이제 연결 위에서 실제 요청과 응답을 주고받는다.

웹과 API에서 가장 자주 만나는 규칙이 **HTTP**다.

> **HTTP = 클라이언트와 서버가 요청과 응답을 주고받는 대표적인 웹 통신 규칙**

예:

```text
클라이언트: 이 종목 데이터를 주세요
서버: 여기 있습니다
```

---

### 20. URL은 무엇일까?

웹이나 API의 위치를 표현하는 주소를 **URL**이라고 부른다.

예:

```text
https://api.example.com/stocks/AAPL
```

부분을 나누면:

```text
https              → 통신 방식
api.example.com    → 도메인
/stocks/AAPL       → 서버 안에서 요청할 경로
```

필요하다면 포트가 포함될 수도 있다.

---

### 21. HTTP 메서드는 무엇일까?

HTTP 요청에는 “무슨 행동을 원하는가”를 나타내는 **메서드(method)**가 있다.

대표적으로:

```text
GET    → 데이터 읽기
POST   → 새 작업/데이터 생성 요청에 자주 사용
PUT    → 전체 수정에 자주 사용
PATCH  → 일부 수정에 자주 사용
DELETE → 삭제 요청
```

정확한 의미는 API 설계에 따라 달라질 수 있다.

초보자는 먼저 `GET`이 읽기 요청에 많이 쓰인다는 것부터 익힌다.

---

### 22. HTTP 상태코드는 무엇일까?

서버는 응답과 함께 처리 결과를 숫자로 알려줄 수 있다.

이를 **상태코드(status code)**라고 부른다.

대표적인 예:

```text
200 → 성공
400 → 요청이 잘못된 경우
401 → 인증이 필요한 경우
403 → 권한이 없는 경우
404 → 대상을 찾지 못함
500 → 서버 내부 오류
```

숫자를 전부 외우지 않는다.

먼저 큰 범주를 이해한다.

```text
2xx → 성공 계열
4xx → 요청/인증/권한 등 클라이언트 쪽 문제 계열
5xx → 서버 처리 문제 계열
```

---

### 23. 401과 403의 차이 맛보기

둘 다 접근 문제처럼 보인다.

아주 단순화하면:

```text
401 → 신원을 확인하지 못했거나 인증이 필요함
403 → 누군지는 알지만 이 행동 권한이 없음
```

실제 API마다 세부 정책은 다를 수 있다.

오류 번호만 보고 추측하지 말고 서버 문서를 확인한다.

---

### 24. 헤더는 무엇일까?

HTTP 요청과 응답에는 본문 외에 추가 정보를 담는 **헤더(header)**가 있다.

예:

```text
Content-Type
Authorization
User-Agent
```

> **HTTP header = 요청이나 응답에 붙이는 추가 정보**

예를 들어 JSON을 보낸다는 사실을 `Content-Type`으로 알려줄 수 있다.

---

### 25. 본문은 무엇일까?

요청이나 응답에 실제 데이터가 들어갈 수 있다.

이를 **본문(body)**이라고 부른다.

예:

```json
{
  "name": "AAPL",
  "price": 200
}
```

HTTP 메시지는 대략:

```text
요청 줄/상태
헤더
본문
```

같이 생각할 수 있다.

---

### 26. 쿼리 파라미터는 무엇일까?

URL 뒤에 추가 조건을 붙일 수 있다.

예:

```text
/stocks?market=NASDAQ&limit=20
```

이런 값을 **쿼리 파라미터(query parameter)**라고 부른다.

> **query parameter = 요청 주소에 붙여 보내는 추가 조건 값**

검색, 필터, 페이지 번호 등에 자주 사용한다.

---

### 27. API 요청 전체 그림

이제 Chapter 1에서 배운 API를 실제 네트워크 단계와 연결할 수 있다.

```text
1. 사용자가 검색어 입력
2. 앱이 API URL 결정
3. DNS로 서버 주소 찾기
4. 서버 포트에 연결
5. TLS 보안 연결 준비
6. HTTP GET 요청 전송
7. 서버 처리
8. HTTP 응답 수신
9. JSON 파싱
10. 앱 상태 변경
11. 화면 표시
```

이 흐름을 알면 “API가 안 된다”를 훨씬 잘게 나눌 수 있다.

---

### 28. 브라우저와 네이티브 앱의 차이

브라우저는 HTML, CSS, JavaScript를 해석해 웹페이지를 보여준다.

네이티브 앱은 Android 앱 코드가 직접 실행된다.

둘 다 같은 서버 API를 사용할 수 있지만 실행 환경과 보안 규칙이 다를 수 있다.

```text
브라우저 웹
네이티브 Android 앱
```

화면이 비슷하다고 구조가 같은 것은 아니다.

---

### 29. WebView는 무엇일까?

Android 앱 안에 웹페이지를 보여주는 브라우저 같은 영역을 넣을 수 있다.

이를 **WebView**라고 부른다.

> **WebView = 앱 내부에서 웹 콘텐츠를 표시하는 브라우저 엔진 영역**

웹을 감싼 앱과 완전 네이티브 앱은 업데이트 방식, 파일 접근, 로그인 상태 등이 다를 수 있다.

---

### 30. 웹에서는 되는데 앱에서는 안 될 때

가능한 차이:

```text
앱의 API 주소가 다름
인증 토큰이 다름
앱 버전이 오래됨
WebView/네이티브 네트워크 설정 차이
인증서 정책 차이
캐시 차이
```

“서버는 같은데 왜?”라고 생각하기 전에 실제 요청을 비교한다.

---

### 31. 같은 URL인데 결과가 다를 수 있는 이유

HTTP 요청은 URL만으로 구성되지 않는다.

```text
메서드
헤더
쿠키
인증 토큰
본문
```

도 결과에 영향을 준다.

브라우저는 로그인 쿠키가 있지만 앱에는 없을 수 있다.

따라서 URL만 비교하고 “완전히 같은 요청”이라고 말하면 안 된다.

---

### 32. curl이란 무엇일까?

터미널에서 HTTP 요청을 직접 보내는 대표 도구 중 하나가 **curl**이다.

예:

```text
curl https://example.com
```

지금은 옵션을 외우지 않는다.

> **curl = HTTP 요청을 직접 재현하고 확인하는 데 자주 쓰는 명령줄 도구**

앱 문제를 UI와 분리해서 API만 시험할 때 유용하다.

---

### 33. 연결 테스트와 기능 테스트를 구분하기

서버 포트에 연결된다고 API 기능까지 정상인 것은 아니다.

```text
연결 성공
↓
HTTP 요청 성공
↓
인증 성공
↓
업무 로직 성공
↓
정상 데이터 반환
```

각 단계가 별도다.

---

### 34. 타임아웃과 재시도

네트워크는 일시적으로 실패할 수 있다.

앱은 일부 오류에서 다시 시도할 수 있다.

이를 **재시도(retry)**라고 한다.

하지만 무한 재시도는 서버를 더 힘들게 만들 수 있다.

그래서 횟수를 제한하고 기다리는 시간을 늘리는 **백오프(backoff)**를 사용할 수 있다.

> **retry = 다시 시도**
>
> **backoff = 반복 실패 시 재시도 간격을 늘리는 전략**

---

### 35. 실제 예제 — Unknown host

오류:

```text
UnknownHostException
```

가능한 첫 확인:

```text
도메인 철자
DNS 조회
기기 인터넷 연결
VPN/사설 DNS
도메인 자체 상태
```

UI 코드를 수정할 이유는 아직 없다.

---

### 36. 실제 예제 — Connection refused

DNS는 성공했지만 연결이 거부된다.

가능한 후보:

```text
서버 서비스가 안 떠 있음
잘못된 포트
방화벽
서버가 다른 주소에서만 수신
```

DNS와 연결 단계를 분리한다.

---

### 37. 실제 예제 — TLS 인증서 오류

연결 과정에서 인증서 오류가 발생한다.

가능한 후보:

```text
인증서 만료
도메인 불일치
기기 시간 오류
신뢰 체인 문제
```

“인터넷 안 됨”이 아니라 **보안 연결 단계 실패**로 좁힌다.

---

### 38. 실제 예제 — HTTP 401

서버까지 연결됐고 HTTP 응답도 받았다.

상태가 401이다.

이 사실만으로 네트워크 자체는 상당 부분 통과했다는 것을 알 수 있다.

이제 인증 토큰, 로그인 상태, 헤더 등을 본다.

```text
DNS? 통과
연결? 통과
TLS? 통과
HTTP? 응답 받음
인증? 실패 가능
```

계층을 나누면 진단이 빨라진다.

---

### 39. 실제 예제 — HTTP 500

서버가 500을 반환했다.

일반적으로 서버 내부 처리 문제가 있다는 신호다.

앱은:

```text
오류 메시지 표시
필요하면 제한된 재시도
로그 기록
사용자 데이터 보존
```

등을 해야 할 수 있다.

500인데 응답을 정상 데이터라고 가정하고 DB에 저장하면 안 된다.

---

### 40. 실제 예제 — 응답 200인데 데이터가 이상함

200은 요청 처리가 HTTP 수준에서 성공했음을 뜻할 뿐, 비즈니스 데이터가 반드시 원하는 값이라는 보장은 아니다.

예:

```json
{
  "price": null
}
```

HTTP 200이지만 price가 없을 수 있다.

따라서:

```text
status code 검사
↓
JSON 형식 검사
↓
필수 필드 검사
↓
타입 검사
```

가 필요하다.

---

### 41. 네트워크 디버깅 순서

문제가 생기면 다음 순서를 사용할 수 있다.

```text
1. 기기 네트워크
2. 도메인/DNS
3. IP/포트 연결
4. TLS
5. HTTP 상태코드
6. 인증/헤더
7. 응답 본문
8. JSON 파싱
9. 앱 상태
10. UI
```

모든 문제에 기계적으로 적용하는 것은 아니지만 좋은 기본 지도다.

### 44. 용어사전

| 쉬운 말 | 영어 | 뜻 |
|---|---|---|
| IP 주소 | IP address | 네트워크 목적지를 구분하는 주소 체계 |
| 도메인 | domain | 사람이 기억하기 쉬운 인터넷 이름 |
| DNS | DNS | 도메인을 IP 주소로 찾는 시스템 |
| 포트 | port | 한 주소 안에서 서비스를 구분하는 번호 |
| 소켓 | socket | 프로그램의 네트워크 통신 끝점 |
| TCP | TCP | 안정적인 연결 중심의 대표 전송 방식 |
| UDP | UDP | 단순하고 빠른 전달에 유리한 대표 전송 방식 |
| 타임아웃 | timeout | 정해진 시간 안에 결과가 없어 중단하는 것 |
| TLS | TLS | 통신 암호화와 서버 확인에 쓰는 보안 기술 |
| HTTPS | HTTPS | TLS로 보호되는 HTTP |
| 인증서 | certificate | 서버 신원을 확인하는 디지털 증명서 |
| HTTP | HTTP | 웹 요청/응답을 주고받는 규칙 |
| URL | URL | 인터넷 자원의 주소 |
| 메서드 | method | HTTP 요청 행동 종류 |

| 재시도 | retry | 실패한 작업을 다시 시도함 |

### 46. 종합 미션

상황:

> 앱에서만 로그인 실패. 브라우저에서는 정상. 앱 로그에는 `HTTP 401`이 찍힌다.

좋은 진단 순서:

1. 앱이 실제 어느 URL로 요청하는지 확인
2. 브라우저와 앱의 인증 방식 비교
3. 앱 Authorization 헤더 존재 여부 확인
4. 토큰 만료 여부 확인
5. 서버가 받은 요청 로그와 비교
6. 토큰 갱신 흐름 확인

DNS부터 무작정 바꾸거나 앱을 재설치하지 않는다.

### 47. 한 장 요약

1. 인터넷 연결은 여러 단계로 나뉜다.
2. IP는 네트워크 주소 체계다.
3. 도메인은 사람이 읽기 쉬운 이름이다.
4. DNS는 도메인을 IP로 찾는다.
5. 포트는 한 주소 안에서 서비스를 구분한다.
6. TCP와 UDP는 서로 다른 전송 방식이다.
7. TLS는 안전한 통신을 만든다.
8. HTTPS는 TLS로 보호된 HTTP다.
9. HTTP는 요청과 응답 규칙이다.
10. 상태코드는 처리 결과를 알려준다.
11. 200이어도 데이터 내용 검증은 필요하다.
12. 웹과 네이티브 앱은 같은 서버를 써도 요청 조건이 다를 수 있다.
13. 네트워크 오류는 DNS→연결→TLS→HTTP→데이터 순서로 좁힌다.

다음 장에서는 이 네트워크와 파일 개념이 **Android 앱의 권한, 저장, 백그라운드, 동기화, 알림**에서 어떻게 실제로 적용되는지 배운다.
