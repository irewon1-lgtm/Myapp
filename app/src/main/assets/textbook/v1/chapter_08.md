# TRACK 08 · 인터넷이 연결되는 순서

이번 TRACK의 목표는 `인터넷 된다/안 된다`를 하나의 검은 상자로 보지 않는 것이다.

인터넷 통신을 아주 처음부터 층층이 쌓는다.

특히 `MIME`, `Content-Type`, `Accept`, `multipart/form-data`, `boundary`를 처음 보는 사람도 이해하도록 **파일 종류를 알려줘야 하는 이유부터** 시작한다.

---

## BLOCK 01 · 인터넷이 뭔데

### LESSON 01 · 컴퓨터끼리 정보를 주고받기

휴대폰 혼자 가지고 있는 사진을 보는 데는 인터넷이 꼭 필요하지 않을 수 있다.

하지만 다른 곳의 컴퓨터가 가지고 있는 정보를 받아오려면 컴퓨터끼리 연결되어 정보를 주고받아야 한다.

**네트워크(network)**는 여러 컴퓨터나 장치가 서로 정보를 주고받을 수 있도록 연결된 구조를 말한다.

한 줄 뜻:

> 네트워크 = 여러 장치가 서로 데이터를 주고받을 수 있게 연결된 구조

### LESSON 02 · 인터넷

세상에는 수많은 네트워크가 있다.

이런 네트워크들이 공통된 통신 규칙을 사용해 전 세계적으로 연결된 거대한 네트워크를 **인터넷(Internet)**이라고 부른다.

아주 쉽게:

> 인터넷 = 전 세계의 많은 네트워크와 컴퓨터를 서로 연결하는 거대한 연결망

인터넷과 웹은 같은 말이 아니다. 웹은 인터넷을 이용하는 여러 서비스 가운데 하나다.

---

## BLOCK 02 · Wi-Fi와 인터넷은 같은 말이 아니다

### LESSON 01 · Wi-Fi

**Wi-Fi**는 기기가 무선으로 가까운 네트워크에 연결되는 대표적인 방법이다.

휴대폰 화면에 Wi-Fi 표시가 있다고 해서 반드시 외부 인터넷까지 정상이라는 뜻은 아니다.

### LESSON 02 · 왜 Wi-Fi 표시는 있는데 인터넷이 안 될까

휴대폰이 공유기까지는 연결되어 있지만 공유기 바깥쪽 인터넷 연결에 문제가 있을 수 있다.

```text
휴대폰
↓ Wi-Fi 연결 성공
공유기
↓ 외부 인터넷 연결 실패
인터넷 서비스
```

따라서:

```text
Wi-Fi 연결됨 = 인터넷 전체가 정상
```

이라는 공식은 틀릴 수 있다.

---

## BLOCK 03 · 데이터를 보내는 쪽과 받는 쪽

### LESSON 01 · 클라이언트

사용자가 웹사이트를 열 때 브라우저는 다른 컴퓨터에 정보를 요청할 수 있다.

요청을 보내고 서비스를 사용하는 쪽을 **클라이언트(client)**라고 부른다.

한 줄 뜻:

> 클라이언트 = 다른 프로그램이나 시스템에 기능 또는 데이터를 요청하는 쪽

### LESSON 02 · 서버

요청을 받아 필요한 일을 처리하고 결과를 돌려주는 쪽을 **서버(server)**라고 부른다.

한 줄 뜻:

> 서버 = 요청을 받아 처리하고 결과를 제공하는 쪽

`서버`가 항상 거대한 컴퓨터 한 대만 뜻하는 것은 아니다. 실제 개발에서는 서버 역할을 수행하는 프로그램과 시스템 전체를 가리키기도 한다.

---

## BLOCK 04 · 주소가 왜 필요한가

### LESSON 01 · 누구에게 보낼지 알아야 한다

편지를 보내려면 받을 사람의 주소가 필요하다.

인터넷에서도 데이터를 어떤 장치나 서비스 쪽으로 보낼지 찾기 위한 주소 체계가 필요하다.

이제 IP 주소라는 말을 배울 준비가 되었다.

---

## BLOCK 05 · IP 주소

### LESSON 01 · 네트워크에서 장치를 찾는 주소

**IP 주소(IP address)**는 인터넷 프로토콜을 사용하는 네트워크에서 장치를 식별하고 통신할 위치를 찾는 데 쓰이는 주소다.

처음에는 이렇게 이해하면 된다.

> IP 주소 = 네트워크에서 데이터를 어느 장치 쪽으로 보낼지 찾는 데 쓰는 숫자 주소

예시 형태:

```text
192.0.2.10
```

이 숫자는 설명용 예다.

### LESSON 02 · IP 주소는 항상 영원히 고정인가

아니다.

환경에 따라 IP 주소가 바뀔 수 있다. 하나의 서비스가 여러 IP 주소를 사용할 수도 있다.

그래서 사람이 웹사이트를 사용할 때 매번 숫자 IP를 외우게 하는 것은 불편하다.

다음 BLOCK에서 `도메인`을 배운다.

---

## BLOCK 06 · 도메인 이름

### LESSON 01 · 사람이 기억하기 쉬운 이름

`example.com`처럼 사람이 읽고 기억하기 쉬운 인터넷 이름을 **도메인 이름(domain name)**이라고 부른다.

아주 쉽게:

> 도메인 = 숫자 IP 주소만 외우지 않아도 서비스를 찾을 수 있게 사용하는 이름 체계

### LESSON 02 · 도메인 이름만 있다고 바로 통신되는 것은 아니다

컴퓨터는 실제 통신을 위해 도메인 이름이 어떤 IP 주소와 연결되는지 알아야 할 수 있다.

`example.com`을 입력했을 때 `어느 IP로 가야 하지?`를 알아내는 과정이 필요하다.

그 역할에서 중요한 것이 DNS다.

---

## BLOCK 07 · DNS

### LESSON 01 · 이름을 주소로 찾기

**DNS(Domain Name System)**는 도메인 이름과 관련된 정보를 찾아주는 분산된 이름 시스템이다.

초보 단계에서는 이렇게 기억한다.

> DNS = example.com 같은 이름을 실제 통신에 필요한 IP 주소 정보와 연결해 찾는 시스템

전화번호부 비유를 사용할 수 있다.

```text
사람 이름 → 전화번호
도메인 이름 → IP 주소 정보
```

완전히 같은 시스템이라는 뜻은 아니고 처음 구조를 잡기 위한 비유다.

### LESSON 02 · DNS 문제가 생기면

인터넷 연결 자체는 살아 있는데 도메인 이름을 IP로 찾지 못하면 특정 사이트에 접속하지 못할 수 있다.

따라서 `인터넷 안 됨`이라는 증상을 더 잘게 나눌 수 있다.

```text
네트워크 연결 문제?
DNS 이름 찾기 문제?
그 다음 연결 문제?
```

---

## BLOCK 08 · 포트라는 것은 왜 필요한가

### LESSON 01 · 한 컴퓨터에서 여러 서비스가 일한다

한 컴퓨터가 웹 서비스도 하고 다른 네트워크 서비스도 할 수 있다.

IP 주소만으로 컴퓨터까지 도착했어도 **그 컴퓨터 안의 어떤 네트워크 서비스를 원하는지** 구분해야 한다.

이 구분에 사용하는 번호가 **포트(port)**다.

한 줄 뜻:

> 포트 = 한 장치 안에서 어떤 네트워크 서비스와 통신할지 구분하는 번호

### LESSON 02 · 집 주소와 방 번호 비유

처음에는 다음처럼 비유할 수 있다.

```text
IP 주소 = 건물 주소
포트 = 그 건물 안에서 찾아갈 서비스 번호
```

실제 네트워크 구조와 건물이 완전히 같은 것은 아니다. 역할을 구분하기 위한 비유다.

---

## BLOCK 09 · 프로토콜이란 무엇인가

### LESSON 01 · 통신에도 약속이 필요하다

두 사람이 서로 다른 규칙으로 말을 하면 대화하기 어렵다.

컴퓨터끼리 데이터를 주고받을 때도 형식과 순서에 대한 약속이 필요하다.

이런 통신 규칙을 **프로토콜(protocol)**이라고 부른다.

한 줄 뜻:

> 프로토콜 = 컴퓨터끼리 통신할 때 따르는 약속과 규칙

### LESSON 02 · 하나의 통신에 여러 프로토콜이 함께 쓰일 수 있다

웹사이트를 열 때도 여러 단계의 규칙이 함께 사용된다.

예를 들어 IP, TCP, TLS, HTTP 같은 이름을 만나게 된다.

지금 한꺼번에 설명하지 않는다.

다음 BLOCK부터 하나씩 배운다.

---

## BLOCK 10 · TCP를 아주 쉽게

### LESSON 01 · 데이터를 믿을 수 있게 이어 주는 연결 방식

인터넷에서는 데이터가 작은 단위로 나뉘어 이동할 수 있다.

웹 통신에서 많이 사용하는 **TCP**는 두 프로그램 사이에 연결을 만들고 데이터가 순서대로 안정적으로 전달되도록 돕는 전송 방식이다.

처음 한 줄:

> TCP = 두 프로그램 사이에 연결을 만들고 데이터를 빠뜨리지 않고 순서대로 전달하도록 확인하는 전송 규칙

### LESSON 02 · TCP와 HTTP는 같은 말이 아니다

TCP는 데이터를 전달하는 연결 쪽의 규칙이다.

HTTP는 그 위에서 웹 요청과 응답을 어떻게 주고받을지 정하는 규칙이다.

```text
TCP = 데이터를 전달할 연결의 규칙
HTTP = 웹 요청과 응답의 규칙
```

아직 HTTP는 뒤에서 배운다.

---

## BLOCK 11 · UDP라는 다른 방식

### LESSON 01 · 모든 통신이 TCP만 쓰는 것은 아니다

**UDP**라는 다른 전송 방식도 있다.

UDP는 TCP처럼 연결을 만들어 모든 데이터의 도착과 순서를 확인하는 방식과 다르게 더 단순한 형태로 데이터그램을 보낸다.

초보 단계에서는:

```text
TCP = 전달 확인과 순서를 중요하게 다루는 연결형 방식
UDP = 그런 확인을 덜 하고 더 단순하게 보내는 방식
```

정도로 차이를 잡는다.

### LESSON 02 · 어느 것이 무조건 더 좋은가

아니다.

통신 목적에 따라 필요한 성질이 다르다.

웹페이지의 일반 HTTP 통신에서는 TCP 기반이 널리 쓰여 왔고, 최신 HTTP/3은 QUIC이라는 다른 전송 기술을 사용한다.

지금은 `인터넷 통신에는 층과 여러 선택지가 있다`는 사실만 기억한다.

---

## BLOCK 12 · 연결에 성공한다는 뜻

### LESSON 01 · 서버까지 갈 수 있어야 한다

도메인을 IP로 찾았다고 끝이 아니다.

그 IP의 특정 포트에서 원하는 서비스가 실제로 연결을 받아야 한다.

서비스가 꺼져 있거나 방화벽이 막고 있거나 잘못된 포트를 사용하면 연결이 실패할 수 있다.

`방화벽(firewall)`은 네트워크 통신을 허용하거나 차단하는 규칙을 적용하는 보안 장치 또는 기능이다. 자세한 내용은 보안 과정에서 배운다.

---

## BLOCK 13 · 암호화된 통신이 왜 필요한가

### LESSON 01 · 중간에서 내용을 읽으면 안 되는 정보

로그인 비밀번호나 결제 정보가 인터넷을 지나간다고 하자.

통신 내용을 누구나 쉽게 읽을 수 있으면 위험하다.

그래서 통신 내용을 보호하는 기술이 필요하다.

### LESSON 02 · TLS

웹에서 안전한 통신을 만들 때 **TLS**라는 보안 프로토콜을 사용한다.

초보 단계의 한 줄 뜻:

> TLS = 인터넷 통신 내용을 암호화하고 상대를 확인하는 데 쓰이는 보안 통신 규칙

세부적인 인증서, 공개키, 개인키는 보안 TRACK에서 제대로 배운다.

---

## BLOCK 14 · HTTP란 무엇인가

### LESSON 01 · 웹에서 요청과 응답을 주고받는 약속

**HTTP(Hypertext Transfer Protocol)**는 웹에서 클라이언트와 서버가 요청과 응답을 주고받는 규칙이다.

한 줄 뜻:

> HTTP = 웹에서 무엇을 요청하고 어떤 결과를 돌려줄지 주고받는 통신 규칙

### LESSON 02 · HTTPS

HTTP 통신을 TLS로 보호해서 사용하는 것을 보통 **HTTPS**라고 부른다.

아주 쉽게:

```text
HTTP = 웹 요청/응답 규칙
HTTPS = HTTP 통신을 TLS로 보호해서 사용
```

`S`를 단순히 `안전 보장 100%`라고 생각하면 안 된다. HTTPS는 통신 경로 보호에 매우 중요하지만 사이트 내용 자체가 모두 선하다는 보증은 아니다.

---

## BLOCK 15 · URL은 무엇인가

### LESSON 01 · 웹 자원의 위치를 표현하는 주소

브라우저 주소창에 이런 모양을 본다.

```text
https://example.com/products/10
```

이런 주소를 **URL(Uniform Resource Locator)**이라고 부른다.

초보 단계에서는:

> URL = 인터넷에서 원하는 자원의 위치를 나타내는 주소

라고 기억한다.

### LESSON 02 · URL을 부분으로 나누기

```text
https://example.com/products/10
```

대략 다음처럼 볼 수 있다.

```text
https       → 어떤 통신 방식을 사용할지
example.com → 어느 서비스 이름인지
/products/10 → 그 서비스 안에서 원하는 경로
```

URL에는 포트, 질의 문자열 등 더 많은 요소가 들어갈 수 있다. 하나씩 뒤에서 배운다.

---

## BLOCK 16 · 요청이란 무엇인가

### LESSON 01 · 서버에게 보내는 메시지

클라이언트가 서버에게 `이 정보를 주세요` 또는 `이 데이터를 처리해 주세요`라고 보내는 메시지를 **요청(request)**이라고 부른다.

한 줄 뜻:

> HTTP 요청 = 클라이언트가 서버에게 무엇을 해 달라고 보내는 메시지

예:

```text
상품 10번 정보를 주세요.
```

### LESSON 02 · 요청에는 여러 정보가 들어갈 수 있다

요청은 단순한 한 문장만 있는 것이 아니다.

어떤 동작을 원하는지, 주소는 무엇인지, 추가 정보는 무엇인지, 보내는 데이터가 있는지 등을 포함할 수 있다.

이 요소를 곧 하나씩 나눈다.

---

## BLOCK 17 · 응답이란 무엇인가

### LESSON 01 · 서버가 돌려주는 결과

서버가 요청을 처리한 뒤 클라이언트에게 돌려주는 메시지를 **응답(response)**이라고 부른다.

한 줄 뜻:

> HTTP 응답 = 서버가 요청을 처리한 결과로 클라이언트에게 보내는 메시지

응답에는 성공했는지 알려주는 숫자 코드, 추가 정보, 실제 데이터 등이 들어갈 수 있다.

---

## BLOCK 18 · HTTP 메서드

### LESSON 01 · 무엇을 하려는 요청인지 표현하기

HTTP 요청에는 서버 자원에 어떤 종류의 동작을 원하는지 나타내는 **메서드(method)**가 있다.

처음 자주 보는 것은:

```text
GET
POST
PUT
DELETE
```

하지만 단어만 외우지 않는다.

### LESSON 02 · GET

`GET`은 보통 자원이나 데이터를 조회해 달라는 의미로 사용한다.

```text
GET /products/10
```

사람말:

```text
상품 10번 정보를 주세요.
```

### LESSON 03 · POST

`POST`는 서버에 데이터를 보내 새 작업이나 자원 생성을 요청하는 상황에서 많이 사용한다.

정확한 의미와 설계는 API 규칙에 따라 달라질 수 있다.

### LESSON 04 · PUT과 DELETE

`PUT`은 자원의 전체 교체나 갱신 의미로 사용되는 경우가 많다.

`DELETE`는 자원 삭제를 요청하는 데 사용한다.

메서드 이름만으로 서버가 반드시 안전하고 올바르게 구현되었다고 보장되는 것은 아니다.

---

## BLOCK 19 · 상태 코드

### LESSON 01 · 서버가 처리 결과를 숫자로 알려준다

HTTP 응답에는 요청 처리 결과를 나타내는 **상태 코드(status code)**가 있다.

예:

```text
200
404
500
```

### LESSON 02 · 숫자 하나를 외우기보다 범주 이해하기

아주 크게:

```text
2xx → 요청을 성공적으로 처리한 범주
4xx → 클라이언트 요청 쪽 문제를 나타내는 범주
5xx → 서버가 요청을 처리하는 중 문제가 생긴 범주
```

세부 코드는 각각 의미가 다르다.

예를 들어 `404`는 요청한 자원을 찾지 못했다는 뜻으로 자주 본다.

## BLOCK 20 · 헤더와 본문을 구분하기

### LESSON 01 · 내용만 보내면 정보가 부족할 수 있다

택배 상자를 보낼 때 상자 안의 물건 외에도 받는 주소, 취급 정보 등이 필요하다.

HTTP 메시지도 실제 데이터 외에 메시지를 이해하는 데 필요한 추가 정보를 함께 보낼 수 있다.

### LESSON 02 · 헤더

HTTP 요청이나 응답의 추가 정보를 담는 부분을 **헤더(header)**라고 부른다.

한 줄 뜻:

> HTTP header = 요청이나 응답의 성격과 처리 방법에 관한 추가 정보

### LESSON 03 · 바디

요청이나 응답에서 실제로 보내는 주요 데이터가 들어가는 부분을 **바디(body)**라고 부른다.

한 줄 뜻:

> HTTP body = 요청이나 응답에 실어 보내는 실제 내용 데이터 부분

모든 요청과 응답에 반드시 body가 있어야 하는 것은 아니다.

---

## BLOCK 21 · 데이터 종류를 왜 알려줘야 할까

### LESSON 01 · 서버가 바이트를 받았다

서버가 어떤 데이터 덩어리를 받았다.

이것이 글인지, PNG 사진인지, JSON 데이터인지 알아야 올바르게 처리하기 쉽다.

사람은 사진을 눈으로 보고 `사진이네`라고 판단할 수 있지만, 프로그램끼리 데이터를 주고받을 때는 **어떤 종류의 데이터라고 약속했는지** 알려주는 정보가 중요하다.

### LESSON 02 · 종류표가 필요하다

택배 상자에 `깨지기 쉬움`, `냉장` 같은 표시를 붙이는 것처럼, 인터넷으로 보내는 데이터에도 `이 데이터는 이런 종류입니다`라고 알려주는 표준 표시가 있다.

이제 MIME type이라는 이름을 배울 준비가 되었다.

---

## BLOCK 22 · MIME type은 무엇인가

### LESSON 01 · 아주 쉬운 정의

**MIME type**은 인터넷에서 데이터의 종류와 형식을 나타내기 위해 사용하는 표준 이름이다.

한 줄 뜻:

> MIME type = 지금 보내거나 받는 데이터가 어떤 종류인지 알려주는 종류표

처음에는 이것만 정확히 이해한다.

### LESSON 02 · 예시를 하나씩 읽기

```text
text/html
```

`text`는 글자 계열 데이터라는 큰 종류를 나타내고 `html`은 HTML 형식임을 나타낸다.

즉:

```text
text/html = HTML 문서 데이터
```

다음:

```text
image/png
```

`image`는 이미지 계열이고 `png`는 PNG 형식이다.

```text
image/png = PNG 이미지 데이터
```

### LESSON 03 · application/json

```text
application/json
```

이 MIME type은 JSON 형식의 데이터를 나타낼 때 사용한다.

`application`은 다양한 응용 프로그램용 데이터 종류에 사용되는 큰 분류 이름 중 하나다.

여기서 JSON 자체는 다음 BLOCK에서 먼저 배운다.

---

## BLOCK 23 · JSON이란 무엇인가

### LESSON 01 · 프로그램끼리 데이터를 표현하는 간단한 형식

**JSON**은 이름과 값, 목록 등을 일정한 글자 규칙으로 표현하는 데이터 형식이다.

예:

```json
{
  "name": "민수",
  "age": 10
}
```

사람말:

```text
name이라는 항목의 값은 민수
age라는 항목의 값은 10
```

### LESSON 02 · JSON과 서버는 같은 말이 아니다

JSON은 데이터를 표현하는 형식이다.

서버는 요청을 받아 처리하는 쪽이다.

```text
JSON = 데이터 표현 방식
서버 = 요청을 처리하고 응답하는 역할
```

JSON이 서버도 아니고 데이터베이스도 아니다.

---

## BLOCK 24 · Content-Type은 무엇인가

### LESSON 01 · 이제 헤더와 MIME을 연결한다

앞에서 두 가지를 배웠다.

```text
HTTP header = 메시지에 대한 추가 정보
MIME type = 데이터 종류를 나타내는 종류표
```

이제 둘을 연결한다.

**Content-Type**은 HTTP 헤더 가운데 하나로, 메시지 body에 담긴 데이터가 어떤 종류인지 알려준다.

한 줄 뜻:

> Content-Type = 이 HTTP 메시지의 실제 내용이 어떤 MIME type인지 알려주는 헤더

### LESSON 02 · application/json 읽기

```http
Content-Type: application/json
```

사람말:

```text
이 메시지의 body에는 JSON 형식 데이터가 들어 있습니다.
```

이제 이 한 줄이 더 이상 외계어가 아니다.

### LESSON 03 · image/png 읽기

```http
Content-Type: image/png
```

사람말:

```text
이 메시지의 body는 PNG 이미지입니다.
```

---

## BLOCK 25 · Content-Type이 틀리면 왜 문제인가

### LESSON 01 · JSON인데 사진이라고 적어 보냈다면

body에는 JSON 데이터가 들어 있는데 헤더에는:

```http
Content-Type: image/png
```

라고 적혀 있다고 하자.

받는 프로그램은 `PNG 이미지라고 했는데 실제 데이터가 이상하다`고 판단하거나 잘못 처리할 수 있다.

따라서 **데이터 자체와 데이터 종류 표시가 맞아야 한다.**

### LESSON 02 · 보안에서도 중요한 이유

파일 업로드나 웹 응답에서는 Content-Type만 무조건 믿어도 안 되고 파일의 실제 내용도 확인해야 하는 경우가 있다.

왜냐하면 사용자가 헤더 값을 거짓으로 보낼 수도 있기 때문이다.

보안 TRACK에서 이 문제를 더 깊게 다룬다.

---

## BLOCK 26 · Accept는 무엇인가

### LESSON 01 · 나는 이런 종류를 받을 수 있어요

클라이언트가 서버에게 `나는 이런 형태의 응답을 원하거나 처리할 수 있습니다`라고 알릴 수 있다.

이때 사용하는 HTTP 헤더가 **Accept**다.

한 줄 뜻:

> Accept = 클라이언트가 어떤 MIME type의 응답을 받고 싶은지 또는 처리할 수 있는지 알려주는 헤더

### LESSON 02 · Content-Type과 Accept 구분

둘을 비교한다.

```text
Content-Type
= 지금 실제로 보내는 내용은 무슨 종류인가?

Accept
= 나는 어떤 종류의 응답을 받을 수 있거나 원하는가?
```

예:

```http
Accept: application/json
```

사람말:

```text
가능하면 JSON 형식 응답을 주세요.
```

---

## BLOCK 27 · 파일 업로드는 어떻게 보내나

### LESSON 01 · 글자와 파일을 함께 보내고 싶다

프로필 등록 화면을 생각하자.

사용자가 다음을 함께 보낸다.

```text
이름: 민수
소개: 안녕하세요
프로필사진: photo.png
```

글자 값과 파일 데이터를 하나의 요청에 함께 담을 방법이 필요하다.

### LESSON 02 · 여러 부분으로 나누어 보내기

HTTP에서는 body를 여러 부분으로 나누어 각 부분에 이름과 데이터를 담는 형식을 사용할 수 있다.

그중 HTML 폼의 파일 업로드에서 많이 보는 MIME type이:

```text
multipart/form-data
```

다.

아직 이름을 외우지 않는다. 단어를 쪼개 보자.

```text
multi = 여러
part = 부분
form-data = 폼에서 보내는 데이터
```

즉 여러 부분으로 나눈 폼 데이터를 보내는 형식이라는 감각을 먼저 잡는다.

---

## BLOCK 28 · multipart/form-data

### LESSON 01 · 여러 조각을 담는 방식

**multipart/form-data**는 하나의 HTTP body 안에 여러 데이터 조각을 나누어 담을 수 있는 MIME type이다.

파일 업로드와 폼 입력을 함께 보낼 때 자주 사용한다.

각 조각에는 `이 조각의 이름`, `파일 이름`, `데이터 종류` 같은 정보가 붙을 수 있다.

### LESSON 02 · 그런데 조각과 조각을 어떻게 구분하지

body 안에 여러 조각이 연달아 들어 있으면 어디서 하나가 끝나고 다음이 시작되는지 구분해야 한다.

그래서 각 조각 사이에 **경계 표시**를 둔다.

그 경계 표시를 다음 BLOCK에서 `boundary`라고 부른다.

---

## BLOCK 29 · boundary는 무엇인가

### LESSON 01 · 조각 사이의 울타리

**boundary**는 multipart 데이터에서 각 부분을 구분하기 위해 사용하는 경계 문자열이다.

한 줄 뜻:

> boundary = multipart body 안에서 한 데이터 부분과 다음 부분을 나누는 경계 표시

예를 들어 설명을 위해 경계를 이렇게 정했다고 하자.

```text
----MY-BOUNDARY
```

body 안에서 이 문자열을 이용해 부분의 시작과 끝을 구분할 수 있다.

### LESSON 02 · Content-Type에 boundary 정보가 붙을 수 있다

예:

```http
Content-Type: multipart/form-data; boundary=----MY-BOUNDARY
```

이제 이 한 줄을 사람말로 바꿀 수 있다.

```text
이 요청 body는 여러 조각으로 나눈 form-data입니다.
각 조각은 ----MY-BOUNDARY라는 경계 표시로 구분합니다.
```

### LESSON 03 · boundary를 직접 억지로 만들 때 생길 수 있는 문제

웹 브라우저의 FormData 같은 기능을 사용할 때는 실행 환경이 적절한 boundary를 만들어 Content-Type을 설정하는 경우가 많다.

개발자가 Content-Type만 수동으로 잘못 덮어쓰고 실제 body의 boundary와 맞추지 않으면 서버가 부분을 제대로 나누지 못할 수 있다.

따라서 도구가 자동으로 처리하는 영역인지 먼저 확인해야 한다.

---

## BLOCK 30 · API란 무엇인가

### LESSON 01 · 프로그램끼리 기능을 사용하기 위한 약속

**API(Application Programming Interface)**는 프로그램이 다른 프로그램이나 시스템의 기능과 데이터를 정해진 방법으로 사용할 수 있게 만든 접점과 규칙이다.

초보용 한 줄:

> API = 프로그램끼리 기능이나 데이터를 주고받기 위해 정해 둔 사용 방법

### LESSON 02 · HTTP API

웹에서는 HTTP를 이용한 API를 매우 많이 사용한다.

예를 들어:

```text
GET /products/10
```

이라는 규칙이 `상품 10번 정보를 가져오는 API`로 정의될 수 있다.

API와 HTTP는 같은 말이 아니다.

```text
HTTP = 웹 통신 규칙
API = 어떤 기능을 어떻게 사용할지 정한 접점과 사용 규칙
```

## BLOCK 31 · 쿠키란 무엇인가

### LESSON 01 · 브라우저가 작은 정보를 보관했다가 다시 보내기

웹사이트는 사용자를 계속 구분하거나 설정을 기억할 필요가 있을 수 있다.

브라우저가 사이트와 관련된 작은 정보를 저장했다가 조건에 맞는 요청에 다시 보내는 기능이 **쿠키(cookie)**다.

한 줄 뜻:

> 쿠키 = 브라우저가 웹사이트와 관련된 작은 값을 저장하고 해당 사이트 요청에 함께 보낼 수 있는 기능

쿠키에는 보안 설정과 전송 조건이 있다. 자세한 내용은 인증·보안에서 배운다.

---

## BLOCK 32 · 세션이란 무엇인가

### LESSON 01 · 서버 쪽에서 사용자 상태를 관리하기

로그인한 사용자의 상태를 서버에서 관리하는 방법 중 하나가 **세션(session)**이다.

서버는 사용자별 상태를 저장하고, 브라우저가 보내는 식별 정보와 연결할 수 있다.

초보용 한 줄:

> 세션 = 서버가 일정 기간 동안 특정 사용자와 관련된 상태를 이어서 관리하는 방식

쿠키와 세션은 같은 말이 아니다.

쿠키는 브라우저 쪽 저장·전송 기능이고, 세션은 서버가 상태를 관리하는 방식으로 많이 쓰인다.

---

## BLOCK 33 · 토큰이란 무엇인가

### LESSON 01 · 권한이나 신원을 증명하는 값

웹과 앱에서는 사용자가 로그인했다는 사실이나 어떤 권한을 가지고 있다는 사실을 증명하기 위해 **토큰(token)**이라는 값을 사용할 수 있다.

한 줄 뜻:

> 토큰 = 시스템이 사용자의 인증이나 권한을 확인하는 데 사용할 수 있는 증표 역할의 값

토큰에는 여러 종류가 있고 보안 설계도 다양하다.

`토큰 = 항상 JWT`는 아니다. JWT는 토큰을 표현하는 한 방식이다.

## BLOCK 34 · CORS를 배우기 전에 출처

### LESSON 01 · 웹페이지가 어디에서 왔는지 구분하기

브라우저는 웹 보안을 위해 `이 페이지가 어느 출처에서 왔는가`를 중요하게 본다.

웹에서 **출처(origin)**는 보통 다음 세 요소의 조합으로 구분한다.

```text
통신 방식(scheme)
호스트(host)
포트(port)
```

예:

```text
https://example.com:443
```

### LESSON 02 · 다른 출처로 요청할 때 제한

브라우저는 악성 웹페이지가 사용자의 다른 사이트 정보에 마음대로 접근하지 못하도록 출처가 다른 요청을 제한한다.

서버가 어떤 다른 출처의 접근을 허용할지 알려주는 규칙이 필요할 수 있다.

그것이 CORS다.

---

## BLOCK 35 · CORS

### LESSON 01 · 브라우저의 교차 출처 요청 허용 규칙

**CORS(Cross-Origin Resource Sharing)**는 서버가 브라우저에게 `어떤 다른 출처에서 온 요청을 허용할 것인지` 알려주는 HTTP 헤더 기반 규칙이다.

한 줄 뜻:

> CORS = 브라우저에서 다른 출처의 웹 자원에 접근할 때 서버가 허용 범위를 알려주는 규칙

### LESSON 02 · CORS는 서버가 죽었다는 뜻이 아니다

CORS 오류가 보인다고 서버 자체가 반드시 꺼져 있는 것은 아니다.

서버는 응답했지만 브라우저가 보안 규칙 때문에 JavaScript에 그 응답 접근을 허용하지 않을 수 있다.

따라서:

```text
네트워크 연결 실패
```

와

```text
브라우저 CORS 정책에 의해 접근 차단
```

을 구분해야 한다.

## BLOCK 37 · MIME과 파일 업로드 진단

### LESSON 01 · 업로드가 실패할 때

파일 업로드가 실패했다고 하자.

무조건 `서버 버그`라고 하지 않는다.

확인할 항목:

```text
요청 메서드는 맞는가?
요청 URL은 맞는가?
Content-Type은 무엇인가?
multipart/form-data가 필요한가?
boundary가 body와 맞는가?
각 부분의 이름이 서버가 기대하는 이름인가?
파일 자체 형식은 맞는가?
서버가 허용하는 크기인가?
응답 상태 코드는 무엇인가?
```

### LESSON 02 · Content-Type만 믿지 않기

사용자가 악의적으로:

```http
Content-Type: image/png
```

라고 적어 놓고 실제로는 다른 데이터를 보낼 수도 있다.

그래서 중요한 서버는 업로드 파일의 실제 형식을 추가로 검증해야 한다.

MIME 표시는 중요한 힌트지만 **그 자체가 진실을 보증하는 보안 도장**은 아니다.

## BLOCK 39 · TRACK 08 종합 훈련

### LESSON 01 · MIME을 어린 동생에게 설명하기

금지 답변:

```text
MIME은 Multipurpose Internet Mail Extensions입니다.
```

이건 이름을 풀어 쓴 것이지 역할 설명이 아니다.

좋은 설명:

```text
인터넷으로 어떤 데이터를 보낼 때
이게 사진인지 글인지 JSON인지 프로그램이 알아야 해서
데이터 종류를 알려주는 표준 이름을 붙일 수 있는데 그게 MIME type이야.
```

### LESSON 02 · Content-Type과 Accept 구분

다음 두 문장을 완성한다.

```text
Content-Type은 지금 ______ 데이터가 어떤 종류인지 알려준다.
Accept는 내가 ______ 응답 종류를 알려준다.
```

의미상 답:

```text
보내는 실제 내용
받고 싶은/처리 가능한
```

### LESSON 03 · multipart와 boundary 설명

친구에게 설명한다.

```text
multipart/form-data는 한 상자 안에 이름, 설명, 파일처럼 여러 조각을 넣는 방식이고,
boundary는 그 조각들이 어디서 나뉘는지 표시하는 경계선이다.
```

이 비유를 이해한 뒤 실제 HTTP 문장을 읽는다.

```http
Content-Type: multipart/form-data; boundary=----ABC
```

사람말로 완전히 번역한다.

### TRACK 끝 미니 프로젝트 · HTTP 요청 해부하기

다음 가상의 요청을 한 줄도 빼지 않고 사람말로 해석한다.

```http
POST /profile HTTP/1.1
Host: example.com
Accept: application/json
Content-Type: multipart/form-data; boundary=----ABC

------ABC
Content-Disposition: form-data; name="nickname"

minsu
------ABC
Content-Disposition: form-data; name="photo"; filename="me.png"
Content-Type: image/png

[PNG 파일 데이터]
------ABC--
```

아직 `Content-Disposition`은 깊게 배우지 않았다. 모르는 말은 모른다고 표시한다.

하지만 최소한 다음은 설명할 수 있어야 한다.

```text
POST 요청이다.
/profile이라는 경로로 보낸다.
JSON 응답을 받고 싶다고 알린다.
요청 body는 여러 부분으로 나눈 form-data다.
각 부분은 ----ABC 경계로 나뉜다.
nickname이라는 글자 값과 photo라는 파일을 보낸다.
photo 파일의 종류는 image/png라고 표시되어 있다.
```

**모르는 한 단어 때문에 전체를 포기하지 않고, 아는 부분과 모르는 부분을 정확히 나누는 것**이 이번 TRACK의 마지막 목표다.
