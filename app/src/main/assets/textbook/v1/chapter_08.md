## V1-C08. 인터넷이 연결되는 순서 — DNS·포트·TLS·HTTP

**목표:** “인터넷이 안 된다”를 하나의 문제로 보지 않고 **이름 찾기 → 연결 → 암호화 → HTTP 요청 → 응답 데이터** 단계로 나눠 진단할 수 있게 된다.

---

### 1. Wi-Fi 연결과 인터넷 연결은 같은 말이 아니다

휴대폰이 Wi-Fi 공유기에 연결되어 있어도 인터넷이 반드시 되는 것은 아니다.

```text
휴대폰 ↔ 공유기     정상
공유기 ↔ 인터넷     실패 가능
인터넷 ↔ 대상 서버 실패 가능
```

그래서 Wi-Fi 아이콘이 보인다는 사실만으로 서버 통신까지 정상이라고 결론내릴 수 없다.

---

### 2. 도메인과 IP — 이름과 실제 네트워크 주소

사람은 `example.com` 같은 이름을 기억하기 쉽다. 네트워크 통신에서는 실제 연결 대상의 IP 주소가 필요하다.

```text
사람이 보는 이름: api.example.com
네트워크 주소:    203.0.113.10 같은 IP
```

도메인 이름을 IP 주소로 찾아주는 시스템이 **DNS(Domain Name System)**다.

```text
api.example.com
↓ DNS 조회
203.0.113.10
```

DNS 조회가 실패하면 서버 프로그램이 정상이어도 연결을 시작하지 못할 수 있다.

대표 증상:

```text
unknown host
name resolution failed
DNS timeout
```

---

### 3. 포트 — 같은 컴퓨터 안의 어느 서비스인가

한 컴퓨터가 웹 서버, DB, SSH 등 여러 서비스를 동시에 실행할 수 있다.

**포트(port)**는 어느 서비스와 통신할지 구분하는 번호라고 생각하면 된다.

```text
IP 주소 = 건물 주소
port    = 건물 안의 특정 창구 번호
```

이 비유는 포트에만 유용하다. 실제 네트워크가 정말 건물 구조인 것은 아니다.

HTTPS는 흔히 443 포트를 사용하지만 항상 고정된 법칙은 아니다.

```text
https://api.example.com:443
```

호스트는 맞는데 포트가 틀리면 연결이 실패할 수 있다.

---

### 4. TCP와 UDP — 전송 방식의 성질

네트워크 데이터 전송에서 자주 듣는 두 방식이 TCP와 UDP다.

초급 단계에서 패킷 헤더를 외울 필요는 없다.

핵심 차이만 본다.

```text
TCP = 연결을 만들고 순서·전달을 신뢰성 있게 다루는 데 초점
UDP = 연결 절차가 가볍고 빠르지만 전달 보장을 직접 제공하지 않음
```

웹의 HTTP/HTTPS는 일반적으로 TCP 또는 QUIC 같은 전송 계층 위에서 동작한다. 여기서 중요한 것은 **HTTP가 네트워크 전체를 혼자 담당하는 것이 아니라 여러 층 위에서 동작한다**는 점이다.

---

### 5. TLS와 HTTPS — 연결이 됐다고 안전한 것은 아니다

`https://`에서 S는 TLS를 이용한 암호화 연결을 의미한다.

TLS는 서버 인증과 암호화된 통신을 제공한다.

대략적인 흐름:

```text
TCP/전송 연결
↓
TLS 협상과 인증서 확인
↓
암호화된 통신 준비
↓
HTTP 요청/응답
```

TLS 단계가 실패하면 DNS와 TCP 연결이 정상이어도 HTTPS 요청은 실패한다.

대표 후보:

- 인증서 만료
- 호스트 이름 불일치
- 기기 시간이 크게 틀림
- 지원하지 않는 TLS 설정

“서버에 ping이 된다”와 “HTTPS 요청이 정상”은 다른 증거다.

---

### 6. HTTP — 실제 요청과 응답 규칙

웹과 API에서 널리 쓰이는 요청/응답 프로토콜이 **HTTP**다.

요청에는 대략 이런 정보가 있다.

```text
메서드
URL
헤더
필요하면 body
```

예:

```text
GET /stocks/AAPL
Host: api.example.com
Authorization: Bearer ***
```

서버는 상태코드와 데이터로 응답한다.

```text
200 OK
Content-Type: application/json

{"symbol":"AAPL","price":200}
```

---

### 7. 상태코드는 원인을 좁히는 강한 단서다

대표 범주:

```text
2xx = 요청 처리 성공 계열
4xx = 요청/인증/권한 등 클라이언트 쪽 문제 계열
5xx = 서버 처리 실패 계열
```

자주 보는 예:

```text
200 OK           = 요청 성공
400 Bad Request  = 요청 형식/값 문제 가능
401 Unauthorized = 인증 필요/실패 가능
403 Forbidden    = 인증됐지만 권한 없음 가능
404 Not Found    = 대상 경로/리소스 없음 가능
429 Too Many Requests = 요청 제한 초과 가능
500 Internal Server Error = 서버 내부 실패
503 Service Unavailable = 일시적 서버 사용 불가 가능
```

상태코드는 원인을 100% 확정하는 답은 아니지만 매우 강한 방향 정보다.

---

### 8. timeout은 “인터넷 없음”과 같은 말이 아니다

**timeout**은 정해진 시간 안에 기대한 결과가 오지 않았다는 뜻이다.

가능한 원인:

- DNS가 느림
- 연결이 늦음
- 서버 처리 지연
- 네트워크 손실
- 클라이언트 timeout 값이 너무 짧음

그래서 timeout만 보고 “서버 다운”이라고 단정할 수 없다.

단계별 시간을 기록하면 좋다.

```text
DNS 30ms
connect 50ms
TLS 80ms
server response 4800ms
```

이 경우 서버 처리/응답 지연 쪽이 강한 후보다.

---

### 9. retry와 backoff — 실패했다고 즉시 무한 재시도하면 안 된다

일시적인 네트워크 실패에서는 재시도가 도움이 될 수 있다.

하지만 다음처럼 하면 위험하다.

```text
실패 → 즉시 재시도 → 실패 → 즉시 재시도 → 무한 반복
```

서버 장애 때 요청 폭주를 더 키울 수 있다.

재시도 간격을 점점 늘리는 전략을 **backoff**라고 한다.

예:

```text
1초 후 재시도
2초 후 재시도
4초 후 재시도
종료
```

또한 결제·저장 같은 작업은 재시도로 중복 실행될 수 있으므로 멱등성까지 함께 생각해야 한다.

---

### 10. 실제 연결 순서를 한 번에 본다

사용자가 앱에서 `AAPL`을 검색한다.

```text
1. URL/host 결정
2. DNS로 IP 찾기
3. 대상 port로 연결
4. TLS 연결 수립(HTTPS라면)
5. HTTP 요청 전송
6. 서버 처리
7. HTTP 응답 수신
8. body(JSON 등) 파싱
9. 앱 상태 갱신
10. UI 표시
```

어느 단계든 실패할 수 있다.

그래서 “API가 안 된다”는 말도 더 구체적으로 바꿔야 한다.

```text
DNS 실패인가?
connect 실패인가?
TLS 실패인가?
HTTP 401인가?
HTTP 500인가?
200인데 body가 이상한가?
JSON은 정상인데 앱 표시가 틀린가?
```

---

### 11. 실제 사례 — 웹사이트는 되는데 앱만 안 됨

가능한 이유:

- 앱이 다른 API 주소 사용
- 앱의 인증 토큰 만료
- 앱에 인증서/네트워크 설정 문제
- WebView와 native network stack 차이
- 앱 캐시/프록시 설정 차이

웹이 된다는 사실은 “인터넷 전체 장애” 가능성을 낮추지만 앱 API까지 정상이라는 증거는 아니다.

---

### 12. 실제 사례 — 401과 403을 같은 문제로 고침

401:

```text
토큰 없음/만료/잘못된 인증
```

403:

```text
인증은 됐지만 해당 리소스 권한 없음
```

실제 서비스 구현에 따라 세부 의미는 다를 수 있지만, 둘을 모두 “로그인 문제”로 뭉개면 진단이 늦어진다.

---

### 13. 실제 사례 — 429가 났는데 서버를 계속 두드림

429는 rate limit과 관련된 경우가 많다.

잘못된 행동:

```text
429 → 즉시 100번 재시도
```

확인:

```text
Retry-After 헤더가 있는가?
문서에 제한 정책이 있는가?
요청을 중복으로 보내고 있지 않은가?
캐시할 수 있는 요청인가?
```

---

### 14. 네트워크 진단 체크리스트

| 단계 | 확인 |
|---|---|
| 기기 연결 | Wi-Fi/모바일 데이터가 실제 인터넷 연결인가 |
| DNS | host가 IP로 해석되는가 |
| connect | host:port 연결이 되는가 |
| TLS | 인증서/암호화 연결이 성공하는가 |
| HTTP | 상태코드는 무엇인가 |
| body | 응답 데이터는 기대 형식인가 |
| parse | 앱이 body를 읽는가 |
| state/UI | 읽은 값이 화면까지 반영되는가 |

## 장 끝 미니 프로젝트 — 한 API 요청 추적

브라우저 개발자도구, 앱 로그, API 도구 등 가능한 환경에서 요청 하나를 골라 아래를 기록한다.

| 항목 | 기록 |
|---|---|
| URL/host | |
| scheme | http/https |
| port | |
| method | |
| status code | |
| content type | |
| response 시간 | |
| body 형식 | |
| 인증 필요 여부 | |
| 실패 시 어느 단계인지 | |

실제 secret은 기록하지 않는다.

---

## 핵심 용어

| 용어 | 뜻 |
|---|---|
| IP | 네트워크에서 장치를 식별하는 주소 |
| domain/host | 사람이 읽기 쉬운 네트워크 이름 |
| DNS | 도메인 이름을 IP 등 네트워크 정보로 해석하는 시스템 |
| port | 한 호스트 안의 서비스 연결 지점 번호 |
| TCP/UDP | 대표적인 전송 방식 |
| TLS | 인증과 암호화 통신을 위한 프로토콜 |
| HTTP | 웹/API의 대표 요청·응답 프로토콜 |
| status code | HTTP 처리 결과를 나타내는 숫자 |
| timeout | 제한 시간 안에 작업이 완료되지 않은 상태 |
| retry | 실패 후 다시 시도 |
| backoff | 재시도 간격을 늘리는 전략 |
| rate limit | 일정 시간 동안 허용되는 요청량 제한 |

---

## 이 장을 끝내고 할 수 있어야 하는 것

1. Wi-Fi 연결과 인터넷/서버 연결을 구분한다.
2. DNS·port·TLS·HTTP의 순서를 설명한다.
3. 401/403/404/429/5xx를 같은 오류로 보지 않는다.
4. timeout이 어느 단계에서 발생했는지 측정할 수 있다.
5. retry가 중복/폭주를 만들 수 있음을 이해한다.
6. 웹은 되는데 앱만 안 되는 상황을 별도 경로로 진단한다.
7. API 실패를 네트워크 전체 장애로 단정하지 않는다.
