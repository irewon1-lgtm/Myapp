# TRACK 07 · 로그를 읽고 원인을 찾는 법

프로그램이 문제가 생겼을 때 가장 먼저 보게 되는 것 중 하나가 **로그(log)**다.

하지만 로그를 `빨간 글씨가 많은 화면`이라고 생각하면 원인을 찾기 어렵다.

이번 TRACK에서는 **시간 → 사건 → 출처 → 오류 경로 → 요청 연결 → 민감정보 보호** 순으로 읽는다.

---

## BLOCK 01 · 로그란 무엇인가

### LESSON 01 · 프로그램이 남기는 사건 기록

프로그램은 실행 중 일어난 일을 글이나 구조화된 데이터로 기록할 수 있다.

이 기록을 **로그(log)**라고 부른다.

한 줄 뜻:

> 로그 = 프로그램에서 어떤 일이 언제 일어났는지 남긴 기록

예:

```text
09:00:01 앱 시작
09:00:02 사용자 정보 요청 시작
09:00:03 사용자 정보 요청 성공
```

### LESSON 02 · 로그가 정답 그 자체는 아니다

로그는 프로그램이 기록하도록 만들어 둔 내용만 보여 준다.

중요한 일이 로그에 빠져 있을 수도 있고, 메시지가 부정확할 수도 있다.

따라서 로그는 중요한 **증거**이지만 항상 완전한 진실 전체라고 생각하면 안 된다.

---

## BLOCK 02 · 시간부터 본다

### LESSON 01 · timestamp

로그에는 사건이 발생한 시간을 기록하는 경우가 많다.

이 시간을 **타임스탬프(timestamp)**라고 부른다.

예:

```text
2026-09-16 09:00:01.235
```

한 줄 뜻:

> timestamp = 사건이 발생한 시각을 기록한 값

### LESSON 02 · 밀리초

`.235`처럼 초보다 더 작은 시간 단위가 붙을 수 있다.

1초는 1000밀리초(ms)다.

비동기 오류나 성능 문제에서는 몇십 밀리초 차이도 순서를 판단하는 데 중요할 수 있다.

---

## BLOCK 03 · 시간대

### LESSON 01 · 같은 순간도 시계 표시는 다를 수 있다

서울과 뉴욕의 시계는 같은 순간에도 다른 시간을 가리킨다.

지역별 시간 기준을 **시간대(time zone)**라고 부른다.

로그를 여러 서버에서 모을 때 시간대가 다르면 순서를 잘못 판단할 수 있다.

### LESSON 02 · UTC

전 세계 시스템이 공통 기준으로 많이 사용하는 시간이 **UTC**다.

서버 로그를 UTC로 저장하고 화면에서 지역 시간대로 바꾸어 보여 주는 방식도 많이 쓴다.

중요한 것은 로그의 시간대가 무엇인지 확인하는 것이다.

---

## BLOCK 04 · 로그 레벨

### LESSON 01 · 기록의 중요도를 구분하기

모든 로그가 같은 중요도를 가지는 것은 아니다.

흔히 다음과 같은 **로그 레벨(log level)**을 사용한다.

```text
DEBUG
INFO
WARN
ERROR
```

프로그램과 라이브러리에 따라 이름과 의미가 조금 다를 수 있다.

### LESSON 02 · DEBUG

개발자가 자세한 내부 상태를 볼 수 있도록 남기는 기록이다.

운영 환경에서는 양이 너무 많거나 민감정보 위험 때문에 꺼 두기도 한다.

### LESSON 03 · INFO

정상적인 주요 사건을 기록한다.

```text
서비스 시작
로그인 성공
배치 작업 완료
```

### LESSON 04 · WARN

당장은 계속 동작할 수 있지만 주의가 필요한 상황을 나타낸다.

### LESSON 05 · ERROR

요청이나 작업이 실패한 상황을 기록한다.

중요: `ERROR`가 여러 개 있어도 가장 마지막 ERROR가 최초 원인이라는 보장은 없다.

## BLOCK 05 · 로그 한 줄 해부하기

### LESSON 01 · 구성요소 찾기

예:

```text
2026-09-16T00:00:03Z ERROR PaymentService request=abc123 card charge failed timeout=5000ms
```

부분으로 나눈다.

```text
시간: 2026-09-16T00:00:03Z
레벨: ERROR
출처: PaymentService
요청 ID: abc123
메시지: card charge failed
추가 값: timeout=5000ms
```

한 줄을 한 덩어리로 읽지 않는다.

## BLOCK 06 · 로그 출처

### LESSON 01 · 어느 코드가 남겼는가

큰 시스템에는 여러 프로그램과 기능이 있다.

로그에는 어느 **모듈(module)**이나 **서비스(service)**가 기록했는지 이름을 남길 수 있다.

`module`은 프로그램을 역할별로 나눈 코드 묶음이고, `service`는 특정 기능을 제공하는 프로그램 단위를 뜻할 때 많이 쓴다.

### LESSON 02 · 같은 오류 문장도 출처가 다르면 의미가 다르다

```text
timeout
```

이라는 단어가 있어도:

```text
DB timeout
HTTP client timeout
file lock timeout
```

은 서로 다른 문제다.

출처를 함께 본다.

## BLOCK 07 · 구조화된 로그

### LESSON 01 · 글 한 줄보다 필드로 나누기

사람에게 읽기 좋은 문장만 남기면 컴퓨터가 검색하기 어려울 수 있다.

그래서 로그를 이름-값 구조로 기록할 수 있다.

예:

```json
{
  "time": "2026-09-16T00:00:03Z",
  "level": "ERROR",
  "requestId": "abc123",
  "event": "payment_failed",
  "timeoutMs": 5000
}
```

이런 방식을 **구조화된 로그(structured logging)**라고 부른다.

### LESSON 02 · 장점

```text
ERROR만 검색
requestId=abc123만 검색
timeoutMs가 큰 기록 찾기
```

같은 분석이 쉬워진다.

---

## BLOCK 08 · 예외란 무엇인가

### LESSON 01 · 실행 중 문제가 발생했음을 나타내는 객체

많은 프로그래밍 언어는 실행 중 비정상 상황이 생기면 **예외(exception)**라는 구조를 사용한다.

예:

```text
파일이 없음
숫자 변환 실패
네트워크 연결 실패
```

한 줄 뜻:

> exception = 프로그램 실행 중 정상 흐름을 계속하기 어려운 문제가 발생했음을 나타내는 구조

### LESSON 02 · 모든 예외가 앱 전체 종료는 아니다

프로그램이 예외를 잡아서 처리할 수 있다.

예:

```text
파일 없음
→ 기본 설정 파일 생성
→ 계속 실행
```

예외가 기록되었다고 앱이 반드시 완전히 죽은 것은 아니다.

---

## BLOCK 09 · stack trace를 배우기 전에 함수 호출

### LESSON 01 · 함수가 다른 함수를 부른다

```text
main
↓
loadUser
↓
readFile
```

처럼 함수가 다른 함수를 호출할 수 있다.

가장 안쪽 `readFile`에서 오류가 났다면 `어떤 경로로 여기까지 왔는지` 알고 싶다.

### LESSON 02 · stack trace

오류가 발생했을 때 호출된 함수들의 경로를 보여 주는 기록을 **stack trace(스택 트레이스)**라고 부른다.

한 줄 뜻:

> stack trace = 오류가 발생한 위치까지 어떤 함수들이 호출되었는지 보여 주는 경로 기록

---

## BLOCK 10 · stack trace 읽기

### LESSON 01 · 가장 위/아래를 무조건 원인이라고 하지 않기

언어와 도구마다 stack trace 표시 순서가 다를 수 있다.

예:

```text
FileNotFoundError: config.txt
  at readConfig(...)
  at startApp(...)
  at main(...)
```

먼저 예외 종류와 메시지를 읽는다.

그 다음 내 코드 파일과 줄 번호가 어디 있는지 찾는다.

### LESSON 02 · 라이브러리 내부 줄만 보일 때

오류가 외부 라이브러리 안에서 발생했어도 내가 잘못된 값을 넘긴 것이 원인일 수 있다.

그래서 stack trace에서 `내 코드가 라이브러리를 호출한 첫 지점`을 찾는 것도 중요하다.

## BLOCK 11 · root cause

### LESSON 01 · 마지막 증상과 최초 원인을 구분하기

예:

```text
DB 연결 실패
↓
사용자 조회 실패
↓
로그인 실패
↓
홈 화면 로딩 실패
```

화면에서는 `홈 화면 로딩 실패`만 보이지만 가장 처음 문제는 DB 연결일 수 있다.

문제를 일으킨 가장 근본적인 원인을 **root cause(근본 원인)**라고 부른다.

### LESSON 02 · 연쇄 오류

하나의 원인 때문에 뒤에서 여러 오류가 연달아 생길 수 있다.

이를 **연쇄 오류(cascading failure)**라고 표현할 수 있다.

로그에서 오류 개수가 많다고 원인이 여러 개라는 뜻은 아니다.

---

## BLOCK 12 · 최초 실패 지점 찾기

### LESSON 01 · 아래에서 위로만 읽지 않기

로그 마지막에:

```text
screen render failed
```

가 있어도 그 위 몇 초 전에:

```text
API request timeout
```

이 있었을 수 있다.

### LESSON 02 · 시간순으로 사건표 만들기

```text
10:00:00 로그인 버튼 클릭
10:00:00 API 요청 시작
10:00:05 timeout
10:00:05 user=null
10:00:05 screen render failed
```

이 표를 만들면 첫 비정상 사건이 timeout이라는 것을 쉽게 볼 수 있다.

## BLOCK 13 · request ID

### LESSON 01 · 동시에 요청이 여러 개면 로그가 섞인다

서버에 사용자 A, B, C의 요청이 동시에 들어오면 로그가 한 파일에 섞일 수 있다.

```text
A 시작
B 시작
A DB 조회
C 시작
B 완료
```

어느 로그가 같은 요청인지 구분하기 어렵다.

### LESSON 02 · 요청마다 이름표 붙이기

각 요청에 고유한 식별값을 붙일 수 있다.

이것을 **request ID**라고 부른다.

예:

```text
requestId=abc123
```

같은 ID를 가진 로그만 모으면 요청 하나의 흐름을 추적하기 쉬워진다.

---

## BLOCK 14 · correlation ID

### LESSON 01 · 여러 서비스를 지나도 같은 큰 작업으로 묶기

한 사용자 요청이:

```text
웹 서버
→ 결제 서버
→ 주문 서버
→ 알림 서버
```

를 지나갈 수 있다.

여러 시스템의 로그를 같은 작업으로 연결하기 위해 **correlation ID**를 사용할 수 있다.

한 줄 뜻:

> correlation ID = 여러 서비스에 걸친 관련 작업의 로그를 하나로 연결하기 위한 공통 식별값

### LESSON 02 · request ID와 correlation ID

시스템 설계에 따라 둘을 같은 값으로 쓰기도 하고 다른 의미로 나누기도 한다.

따라서 이름만 보고 절대 규칙이라고 생각하지 말고 프로젝트의 로깅 정책을 확인한다.

---

## BLOCK 15 · trace와 span

### LESSON 01 · 분산 추적

여러 서비스를 지나는 요청의 전체 흐름을 추적하는 것을 **분산 추적(distributed tracing)**이라고 부른다.

전체 요청 흐름 하나를 **trace**라고 부르는 시스템이 많다.

### LESSON 02 · span

trace 안에서 개별 작업 구간을 **span**이라고 부른다.

예:

```text
Trace: 주문 생성
  Span 1: 사용자 확인
  Span 2: 결제
  Span 3: DB 저장
  Span 4: 알림 발송
```

각 span의 시작·종료 시간을 보면 어느 구간이 느린지 알 수 있다.

---

## BLOCK 16 · 로그와 메트릭

### LESSON 01 · 로그는 개별 사건 기록

```text
request abc123 timeout
```

처럼 구체적인 사건을 보여 준다.

### LESSON 02 · 메트릭

시간에 따라 수치로 측정한 값을 **메트릭(metric)**이라고 부른다.

예:

```text
초당 요청 수
평균 응답 시간
오류 비율
CPU 사용률
```

### LESSON 03 · 둘을 같이 본다

메트릭에서 `오류율이 1% → 30%`로 급증한 시각을 찾고, 그 시간의 로그를 조사할 수 있다.

---

## BLOCK 17 · 로그와 트레이스

### LESSON 01 · 서로 역할이 다르다

```text
로그 = 구체적인 사건과 메시지
메트릭 = 전체 상태의 수치 변화
트레이스 = 요청 하나가 시스템을 지나간 경로와 시간
```

세 가지를 합쳐 시스템을 관찰하는 접근을 **옵저버빌리티(observability)**라고 부른다.

### LESSON 02 · observability

한 줄 뜻:

> observability = 로그·메트릭·트레이스 같은 외부 증거를 이용해 시스템 내부 상태를 이해할 수 있게 만드는 능력

단순히 로그를 많이 남긴다고 자동으로 좋은 관측성이 생기는 것은 아니다.

---

## BLOCK 18 · 로그에 무엇을 남길까

### LESSON 01 · 좋은 로그에 필요한 것

상황에 따라 다음 필드가 유용할 수 있다.

```text
시간
로그 레벨
서비스 이름
이벤트 이름
요청 ID
사용자 식별값(안전하게 처리)
처리 시간
오류 종류
```

### LESSON 02 · 지나치게 많은 로그도 문제

모든 변수와 모든 줄을 무작정 기록하면:

```text
저장비용 증가
검색 어려움
성능 저하
민감정보 노출 위험
```

이 생길 수 있다.

목적 있는 로그가 중요하다.

---

## BLOCK 19 · 민감정보

### LESSON 01 · 로그에 남기면 안 되는 값

다음 값은 로그에 그대로 기록하면 매우 위험할 수 있다.

```text
비밀번호
인증 토큰
API secret
카드번호 전체
주민등록번호
개인키
```

이런 정보를 **민감정보(sensitive information)**라고 부를 수 있다.

### LESSON 02 · 디버깅하려고 비밀번호를 출력하면 안 된다

문제 해결을 위해 `현재 token=...` 같은 로그를 넣었다가 운영 로그에 실제 토큰이 남을 수 있다.

로그는 여러 사람이 접근하거나 장기간 보관될 수 있다.

---

## BLOCK 20 · 마스킹과 레댁션

### LESSON 01 · 필요한 부분만 가리기

민감한 값 전체를 남기지 않고 일부만 보이게 가리는 것을 **마스킹(masking)**이라고 부른다.

예:

```text
카드: **** **** **** 1234
```

### LESSON 02 · 완전히 제거하기

민감정보를 로그에서 제거하거나 숨기는 것을 **레댁션(redaction)**이라고 부른다.

```text
token=[REDACTED]
```

정책에 따라 저장 전 단계에서 제거하는 것이 중요하다.

---

## BLOCK 21 · 로그 샘플링

### LESSON 01 · 모든 요청을 다 기록하기 어려울 때

초당 수백만 요청이 오는 서비스에서 모든 상세 로그를 영원히 저장하기는 어렵다.

일부 요청만 선택해서 상세하게 기록하는 방식을 **샘플링(sampling)**이라고 부른다.

### LESSON 02 · 샘플링의 위험

샘플링 비율이 낮으면 드문 오류를 놓칠 수 있다.

그래서 일반 정상 요청과 오류 요청에 다른 샘플링 정책을 사용할 수 있다.

---

## BLOCK 22 · 로그 보존 기간

### LESSON 01 · 로그를 언제까지 보관할까

로그를 영원히 저장하면 비용과 개인정보 위험이 커진다.

어떤 로그를 얼마나 오래 보관할지 정하는 정책을 **보존 정책(retention policy)**이라고 부른다.

### LESSON 02 · 목적에 따라 다르다

```text
실시간 장애 분석용
보안 감사용
법적 보존용
개발 디버깅용
```

목적에 따라 보존 기간과 접근 권한이 달라질 수 있다.

---

## BLOCK 23 · 로그 회전

### LESSON 01 · 파일 하나가 끝없이 커지면

로그를 파일에 계속 쓰면 파일이 너무 커질 수 있다.

일정 크기나 날짜를 기준으로 새 파일로 바꾸는 것을 **로그 회전(log rotation)**이라고 부른다.

예:

```text
app.log
app.log.1
app.log.2
```

### LESSON 02 · 오래된 로그 정리

회전된 오래된 로그를 압축하거나 삭제하는 정책을 함께 사용한다.

---

## BLOCK 24 · 에러 메시지의 원문을 보존하기

### LESSON 01 · 요약하면서 중요한 정보가 사라질 수 있다

AI나 사람이:

```text
네트워크 문제 같습니다.
```

라고 요약해도 실제 오류 원문은:

```text
TLS certificate expired
```

였을 수 있다.

원문을 보존해야 다시 검증할 수 있다.

### LESSON 02 · 증거와 해석 분리

좋은 장애 기록:

```text
증거: 10:03:11 TLS certificate expired
해석: 인증서 만료가 연결 실패 원인일 가능성이 높음
```

증거와 해석을 같은 문장으로 섞지 않는다.

---

## BLOCK 25 · 재현 로그 만들기

### LESSON 01 · 같은 행동을 했을 때 같은 문제가 생기나

버그를 재현할 때:

```text
시작 시각
사용한 입력
누른 버튼
요청 ID
결과
오류 로그
```

를 기록한다.

### LESSON 02 · 수정 전후 비교

수정 전:

```text
10회 중 8회 실패
평균 5.2초
```

수정 후:

```text
10회 중 0회 실패
평균 1.1초
```

처럼 같은 조건으로 비교한다.

---

## BLOCK 26 · 로그 검색

### LESSON 01 · 키워드만 찾지 않기

`ERROR`만 검색하면 수천 줄이 나올 수 있다.

다음처럼 조건을 좁힌다.

```text
시간 범위
서비스 이름
request ID
사용자 ID
오류 종류
```

### LESSON 02 · 앞뒤 문맥 보기

오류 한 줄만 보지 말고 그 전후 몇 초의 사건을 본다.

`요청 시작 → DB 호출 → timeout → 재시도 → 최종 실패` 흐름이 보일 수 있다.

---

## BLOCK 27 · 로그에서 거짓 인과관계 피하기

### LESSON 01 · 먼저 발생했다고 원인은 아니다

A 로그가 B 로그보다 먼저 나왔다고 A가 반드시 B의 원인은 아니다.

```text
09:00 광고 로딩
09:01 결제 실패
```

시간 순서만으로 광고 로딩이 결제 실패의 원인이라고 말할 수 없다.

### LESSON 02 · 인과관계에는 추가 증거가 필요하다

같은 요청 ID, 함수 호출 경로, 재현 실험, 변경 전후 비교 등을 이용해 연결을 확인한다.

---

## BLOCK 28 · TRACK 07 핵심 용어 사전

| 용어 | 아주 쉬운 뜻 |
|---|---|
| 로그 | 프로그램에서 일어난 일을 남긴 기록 |
| timestamp | 사건이 발생한 시각 |
| time zone | 지역별 시간 기준 |
| log level | 기록의 중요도나 성격을 구분하는 단계 |
| structured log | 이름-값 필드로 나눈 구조화된 로그 |
| exception | 정상 실행 흐름을 방해하는 문제를 나타내는 구조 |
| stack trace | 오류 위치까지 호출된 함수 경로 |
| root cause | 문제를 일으킨 근본 원인 |
| cascading failure | 하나의 실패가 뒤의 여러 실패로 이어지는 현상 |
| request ID | 요청 하나를 구분하는 식별값 |
| correlation ID | 여러 서비스의 관련 작업 로그를 연결하는 식별값 |
| trace | 요청 하나가 시스템 전체를 지나간 추적 기록 |
| span | trace 안의 개별 작업 구간 |
| metric | 시간에 따라 측정한 수치 데이터 |
| observability | 외부 증거로 시스템 내부 상태를 이해할 수 있게 하는 능력 |
| masking | 민감한 값 일부를 가리는 것 |
| redaction | 민감정보를 로그에서 제거하거나 숨기는 것 |
| sampling | 전체 중 일부를 선택해 기록하는 것 |
| retention | 로그를 얼마나 오래 보관할지 정한 정책 |
| log rotation | 로그 파일을 크기나 날짜 기준으로 나누는 것 |

---

## BLOCK 29 · TRACK 07 종합 훈련

### LESSON 01 · 시간축 만들기

다음 로그를 시간순으로 다시 배열한다.

```text
10:00:05 ERROR screen load failed request=A
10:00:00 INFO request started request=A
10:00:04 ERROR db timeout request=A
10:00:01 INFO db query started request=A
```

정렬 후 최초 비정상 사건을 찾는다.

### LESSON 02 · stack trace 읽기

다음 구조를 사람말로 설명한다.

```text
NullPointerException
at renderProfile(Profile.kt:88)
at loadProfile(Profile.kt:42)
at onClick(Home.kt:20)
```

```text
사용자가 버튼을 눌러 onClick이 실행됨
→ loadProfile 호출
→ renderProfile 호출
→ renderProfile 88번 줄 근처에서 null 관련 오류
```

### LESSON 03 · 민감정보 제거

나쁜 로그:

```text
login failed email=a@example.com password=MyRealPassword token=abcdef...
```

좋은 방향:

```text
login failed userId=hashed-or-internal-id token=[REDACTED]
```

실제 정책은 서비스 보안 기준에 맞춘다.

---

## BLOCK 30 · TRACK 07 완료 기준

다음을 할 수 있어야 한다.

- 로그가 무엇이고 무엇이 아닌지 설명한다.
- 타임스탬프와 시간대를 확인한다.
- DEBUG/INFO/WARN/ERROR를 구분한다.
- 구조화된 로그의 장점을 설명한다.
- exception과 stack trace를 읽는 기본 순서를 안다.
- 마지막 오류와 root cause를 구분한다.
- request ID로 같은 요청의 로그를 모을 수 있다.
- correlation ID와 분산 trace가 왜 필요한지 설명한다.
- 로그, metric, trace의 역할을 구분한다.
- 민감정보를 로그에 남기면 안 되는 이유를 설명한다.
- 증거와 해석을 분리해서 장애 노트를 작성할 수 있다.
- 같은 조건의 수정 전후 로그를 비교할 수 있다.

### TRACK 끝 미니 프로젝트 · 장애 타임라인 보고서

가상의 서비스 로그 30줄을 만들거나 실제 개발 로그를 준비한다.

다음 표를 작성한다.

```text
시간 | request ID | 서비스 | 사건 | 정상/비정상 | 근거
```

그 다음:

```text
최초 비정상 사건
뒤따른 연쇄 오류
root cause 후보
추가로 필요한 증거
재현 방법
수정 후 확인할 로그
```

를 적는다.

**로그를 많이 읽는 것보다 시간축과 원인 구조를 정확히 만드는 것**이 이 TRACK의 목표다.
