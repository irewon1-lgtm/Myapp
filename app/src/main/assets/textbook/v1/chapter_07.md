## V1-C07. 로그를 읽는 법 — “무슨 일이 있었는지” 시간순으로 복원하기

**이 장의 대상:** 오류 메시지를 보면 겁부터 나고, 긴 로그에서 무엇을 먼저 봐야 하는지 모르는 사람.

**이 장의 목표:** 로그를 전부 외우는 것이 아니라 **시간, 심각도, 어느 부분에서 나온 기록인지, 최초 실패가 무엇인지**를 순서대로 찾아낼 수 있게 된다.

---

### 1. 로그는 무엇일까?

프로그램이 실행되는 동안 중요한 사건을 글자로 기록할 수 있다.

이 기록을 **로그(log)**라고 부른다.

> **로그 = 프로그램에서 어떤 일이 언제 일어났는지 남긴 기록**

예:

```text
10:00:01 앱 시작
10:00:02 사용자 로그인
10:00:03 서버 요청 시작
10:00:04 서버 응답 200
10:00:05 화면 표시 완료
```

이런 기록이 있으면 문제가 생겼을 때 과정을 되짚어볼 수 있다.

---

### 2. 로그는 왜 필요한가?

사용자가 말한다.

> “앱이 갑자기 안 됐어요.”

이 말만으로는 원인을 알기 어렵다.

로그가 있다면:

```text
언제 실패했는지
무슨 작업 중이었는지
어떤 오류가 먼저 나왔는지
재시도가 있었는지
다른 기능은 정상인지
```

를 확인할 수 있다.

로그는 프로그램의 **사건 기록장**이다.

---

### 3. 로그 한 줄을 읽는 법

다음 로그를 보자.

```text
2026-09-15 10:00:02 ERROR Network request timeout
```

처음 보면 영어가 많지만 네 부분으로 나눌 수 있다.

```text
2026-09-15 10:00:02 → 언제
ERROR               → 심각도
Network             → 어느 부분
request timeout     → 무슨 일이 있었는지
```

한 줄 전체를 외우지 말고 **칸으로 나눠 읽는다.**

---

### 4. 타임스탬프는 무엇일까?

로그에 붙는 날짜와 시각을 **타임스탬프(timestamp)**라고 부른다.

> **timestamp = 사건이 발생한 시간을 나타내는 기록**

예:

```text
2026-09-15 10:00:02
```

문제를 재현한 정확한 시각을 알고 있으면 그 근처 로그만 찾아볼 수 있다.

그래서 버그 보고에 “오전쯤”보다 “10:03:14경”처럼 구체적인 시간이 유리하다.

---

### 5. 로그 레벨은 무엇일까?

로그는 중요도에 따라 분류될 수 있다.

대표적인 이름을 예로 보면:

```text
DEBUG
INFO
WARN
ERROR
```

정확한 의미는 프로젝트마다 조금 다를 수 있다.

초보자에게는 이렇게 이해하면 된다.

```text
DEBUG → 개발자가 자세히 보기 위한 정보
INFO  → 정상 진행 정보
WARN  → 이상할 수 있어 주의가 필요한 상태
ERROR → 실제 실패나 중요한 오류
```

> **log level = 로그의 중요도나 목적을 표시하는 분류**

---

### 6. ERROR만 보면 충분할까?

아니다.

에러 직전에 어떤 일이 있었는지가 중요하다.

예:

```text
10:00:01 INFO token expired
10:00:02 INFO refresh token start
10:00:03 ERROR refresh failed
10:00:04 ERROR API request unauthorized
```

마지막 `unauthorized`만 보면 API 권한 문제처럼 보인다.

하지만 더 앞에 **토큰 만료와 갱신 실패**가 있다.

최초 실패가 어디인지 찾는 것이 중요하다.

---

### 7. 최초 실패와 후속 오류

하나의 문제가 여러 오류를 만들 수 있다.

예:

```text
DB 연결 실패
↓
데이터 읽기 실패
↓
화면 데이터 없음
↓
후속 처리에서 null 오류
```

마지막 null 오류만 고치면 근본 원인이 남아 있을 수 있다.

> **최초 실패 = 연쇄 오류가 시작된 가장 앞쪽 문제**

로그는 뒤에서 위로만 읽지 말고 시간순으로 본다.

---

### 8. 컴포넌트는 무엇일까?

큰 앱은 여러 부분으로 나뉜다.

예:

```text
AUTH
NETWORK
DATABASE
UI
SYNC
```

로그에 어느 부분에서 나온 기록인지 표시할 수 있다.

이를 **컴포넌트(component)**라고 부를 수 있다.

> **component = 시스템 안의 기능 단위나 부분**

같은 시간대라도 어느 부분의 로그인지 구분하면 원인을 좁히기 쉽다.

---

### 9. 로그 메시지는 사실과 해석을 나눈다

좋은 로그는 실제로 관찰한 사실을 기록한다.

나쁜 예:

```text
ERROR probably server broken
```

이건 추측이 섞여 있다.

더 나은 예:

```text
ERROR request failed status=503 endpoint=/stocks
```

이 로그는 실제 상태코드와 대상 주소를 기록한다.

> **로그에는 가능한 한 관찰된 사실을 남긴다.**

---

### 10. 요청 하나를 여러 로그에서 연결하기

동시에 여러 요청이 실행되면 로그가 섞일 수 있다.

예:

```text
req-A start
req-B start
req-B response
req-A response
```

어떤 로그가 같은 요청인지 표시하기 위해 **요청 ID(request id)**나 **상관관계 ID(correlation id)**를 사용할 수 있다.

> **correlation id = 여러 로그가 같은 작업에서 나온 것인지 연결하는 식별자**

---

### 11. correlation id가 왜 유용할까?

동시에 사용자 100명이 요청한다고 하자.

시간만 보고는 로그가 뒤섞인다.

```text
10:00:01 request start user A
10:00:01 request start user B
10:00:01 response user B
10:00:02 response user A
```

각 요청에 ID가 있으면:

```text
[abc123] request start
[xyz789] request start
[xyz789] response
[abc123] response
```

처럼 같은 흐름을 묶을 수 있다.

---

### 12. 스택 트레이스는 무엇일까?

프로그램이 오류로 실패하면 어떤 함수들을 거쳐 그 위치에 왔는지 긴 기록이 나올 수 있다.

이를 **스택 트레이스(stack trace)**라고 부른다.

처음 보면 매우 무섭다.

예:

```text
Exception ...
 at loadData(...)
 at showScreen(...)
 at main(...)
```

지금은 모든 줄을 이해할 필요 없다.

> **stack trace = 오류가 발생하기까지 어떤 함수 호출 경로를 지나왔는지 보여주는 기록**

---

### 13. 스택 트레이스에서 처음 볼 곳

언어와 도구마다 다르지만 초보자는 보통 다음을 먼저 본다.

1. 오류 종류
2. 오류 메시지
3. 내 프로젝트 파일이 처음 나타나는 줄
4. 발생한 파일과 줄 번호

외부 라이브러리 내부 줄을 처음부터 전부 읽으려고 하지 않는다.

---

### 14. 오류 메시지에서 파일과 줄 번호 찾기

예:

```text
NameError: name 'price' is not defined
  File "main.py", line 12
```

중요한 정보:

```text
오류 종류: NameError
문제 내용: price가 정의되지 않음
파일: main.py
줄: 12
```

이 네 가지를 먼저 뽑아낸다.

---

### 15. 로그를 많이 남기면 무조건 좋은가?

아니다.

너무 많은 로그는 중요한 신호를 묻어버릴 수 있다.

또 개인정보나 비밀값이 노출될 수 있다.

좋은 로그는:

```text
필요한 정보만
재현에 도움이 되게
비밀값은 숨기고
시간과 대상이 명확하게
```

남긴다.

---

### 16. 절대로 로그에 그대로 남기면 안 되는 것

예:

```text
비밀번호
API secret
access token
주민등록번호
민감한 개인정보
전체 카드번호
```

디버깅 편의를 위해 이런 값을 출력하면 보안 사고가 될 수 있다.

필요하다면 일부만 가린다.

```text
token=abcd...wxyz
```

하지만 마스킹 규칙도 안전하게 설계해야 한다.

---

### 17. 마스킹이란 무엇일까?

민감정보 일부를 가리는 것을 **마스킹(masking)**이라고 부른다.

예:

```text
010-****-1234
user***@example.com
```

로그 분석에 필요한 최소 정보만 남기면서 노출을 줄일 수 있다.

---

### 18. 재현 시각을 기록하는 습관

버그를 다시 발생시켰다면 바로 시각을 기록한다.

예:

```text
2026-09-15 11:42:18 검색 버튼 누름
11:42:20 오류 화면
```

그러면 로그에서 이 구간을 집중해서 찾으면 된다.

“어제 한 번 그랬어요”보다 훨씬 강한 증거다.

---

### 19. 재현 절차와 로그를 함께 본다

예:

```text
1. 앱 실행
2. 검색 화면 이동
3. 검색어 빈칸 유지
4. 검색 버튼 누름
5. 앱 종료
```

로그:

```text
12:00:01 SearchScreen opened
12:00:03 search clicked query=""
12:00:03 ERROR validation missing
12:00:03 CRASH NullPointerException
```

재현 단계와 로그가 연결되면 문제 원인을 찾기 쉬워진다.

---

### 20. 시간순으로 정렬한다

여러 서버나 기기의 로그를 모으면 순서가 뒤섞일 수 있다.

우선 시간순으로 정렬한다.

다만 서버마다 시간대(timezone)가 다를 수 있다.

예:

```text
한국시간 10:00
UTC 01:00
```

둘이 같은 순간일 수 있다.

시간대를 확인하지 않으면 순서를 잘못 해석할 수 있다.

---

### 21. 시간대는 무엇일까?

세계 지역마다 표준 시각이 다르다.

로그에:

```text
+09:00
Z
UTC
```

같은 표시가 보일 수 있다.

지금은 세부 변환식을 외우지 않는다.

> **로그 비교 전에 같은 시간 기준인지 확인한다.**

이것이 핵심이다.

---

### 22. 로그가 없는 것도 정보다

버튼을 눌렀는데 예상한 로그가 아예 나오지 않는다면:

```text
버튼 이벤트가 실행되지 않았거나
코드가 해당 지점까지 도달하지 않았거나
로그 수집 자체가 꺼져 있을 수 있다.
```

“로그가 없다”도 진단 단서가 된다.

---

### 23. 로그 앞뒤 문맥을 본다

에러 줄 하나만 복사하지 말고 앞뒤 몇 줄을 함께 본다.

예:

```text
INFO request start
INFO dns resolved
WARN slow connection
ERROR timeout
INFO retry scheduled
```

이 흐름은 단순히 `timeout` 한 줄보다 훨씬 많은 정보를 준다.

---

### 24. 반복되는 패턴을 찾는다

매일 09:00에만 오류가 나는지, 특정 계정에서만 나는지, 3회 재시도 후 실패하는지 패턴을 찾는다.

```text
같은 시각
같은 사용자
같은 API
같은 기기
같은 앱 버전
```

반복 조건은 원인 범위를 줄여준다.

---

### 25. 로그와 메트릭의 차이

**로그(log)**는 개별 사건 기록에 가깝다.

**메트릭(metric)**은 숫자 상태를 시간에 따라 측정한 값이다.

예:

```text
로그: 10:00:03 request timeout
메트릭: 최근 5분 요청 실패율 12%
```

둘을 함께 보면 “한 건의 오류”인지 “전체 장애”인지 판단하기 쉽다.

---

### 26. 트레이스라는 말

한 요청이 여러 서비스와 단계를 지나갈 때 전체 경로를 추적하는 것을 **트레이싱(tracing)**이라고 부른다.

예:

```text
앱
→ API gateway
→ 서비스 A
→ DB
→ 서비스 B
→ 응답
```

V1에서는 개념만 알고 넘어간다.

> **trace = 하나의 요청이 지나간 경로를 이어서 보는 것**

---

### 27. 실제 예제 — 로그인 실패

로그:

```text
09:00:00 login start
09:00:01 token expired
09:00:01 refresh start
09:00:02 refresh 401
09:00:02 login failed
```

마지막 `login failed`만 보면 원인을 모른다.

앞에서 `refresh 401`이 나타났다.

더 앞에는 `token expired`가 있다.

원인 후보를:

```text
토큰 만료 자체는 정상 상황
갱신 요청이 401로 실패한 이유 확인
```

으로 좁힐 수 있다.

---

### 28. 실제 예제 — 알림이 특정 폰만 안 옴

비교 로그:

```text
엄마 기기: token registered → send 200 → displayed
배우자 기기: token missing → send skipped
```

이 경우 서버 전체 장애보다 기기 토큰 등록 문제를 우선 볼 수 있다.

정상 기기와 실패 기기의 로그를 나란히 비교하는 것이 매우 강력하다.

---

### 29. 실제 예제 — API는 성공인데 화면이 비어 있음

로그:

```text
10:00:01 GET /stocks 200
10:00:01 parsed items=20
10:00:02 saved rows=20
10:00:02 UI state items=0
```

여기서는 서버보다 **저장된 데이터가 UI 상태로 전달되는 구간**을 우선 확인할 수 있다.

“화면이 비어 있다 → API 장애”라고 단정하면 안 된다.

---

### 30. 실제 예제 — 마지막 오류가 진짜 원인이 아님

```text
11:00:01 disk full
11:00:02 save failed
11:00:03 cache missing
11:00:04 UI empty
```

사용자는 UI empty만 본다.

하지만 최초 비정상 사건은 `disk full`이다.

근본 원인은 저장공간 부족일 수 있다.

---

### 31. 로그를 표로 정리하기

긴 로그에서 필요한 부분만 뽑아 표를 만든다.

| 시간 | 부분 | 사건 | 판정 |
|---|---|---|---|
| 10:00:01 | UI | 검색 클릭 | 정상 |
| 10:00:02 | Network | 요청 시작 | 정상 |
| 10:00:05 | Network | timeout | 첫 실패 |
| 10:00:05 | UI | 오류 표시 | 후속 결과 |

이 표만으로도 원인 흐름이 눈에 보인다.

---

### 32. 로그를 읽을 때 5단계

```text
1. 재현한 정확한 시각 찾기
2. ERROR/WARN 주변 확인
3. 첫 비정상 사건 찾기
4. 같은 요청 ID 로그 묶기
5. 앞뒤 단계와 비교
```

처음부터 모든 줄을 읽지 않는다.

---

### 33. 로그를 쓸 때 5가지 질문

개발자가 로그를 추가한다면:

1. 언제 발생했나?
2. 어느 기능에서 발생했나?
3. 어떤 입력 또는 ID인가?
4. 결과가 성공/실패 중 무엇인가?
5. 비밀정보를 노출하지 않았나?

를 본다.

---

### 34. 간단한 Python 로그 맛보기

```python
print("INFO app started")
print("INFO request started")
print("ERROR timeout")
```

실제 프로젝트에서는 전문 logging 도구를 사용하지만, 기본 아이디어는 “사건을 기록한다”는 것이다.

---

### 35. 더 나은 로그 형태 맛보기

```python
request_id = "abc123"
print(request_id, "request start")
print(request_id, "response 200")
```

같은 ID를 붙이면 두 줄이 같은 요청이라는 것을 알 수 있다.

### 36. 초보자가 자주 하는 오해

#### 오해 1. 마지막 ERROR가 항상 원인이다

후속 오류일 수 있다.

#### 오해 2. ERROR만 보면 된다

직전 INFO/WARN이 중요할 수 있다.

#### 오해 3. 로그가 많을수록 무조건 좋다

#### 오해 4. 비밀번호를 로그에 찍으면 디버깅이 쉬우니 괜찮다

절대 아니다.

#### 오해 5. 서버와 폰 로그의 시간이 같아 보이면 같은 시간대다

timezone을 확인해야 한다.

### 37. 용어사전

| 쉬운 말 | 영어 | 뜻 |
|---|---|---|
| 로그 | log | 프로그램 사건 기록 |
| 타임스탬프 | timestamp | 사건 발생 시각 |
| 로그 레벨 | log level | 로그 중요도/목적 분류 |

### 39. 종합 미션

다음 로그에서 최초 실패 후보를 찾는다.

```text
14:00:01 INFO sync start
14:00:02 INFO auth token check
14:00:02 WARN token expired
14:00:03 INFO token refresh
14:00:04 ERROR refresh status=401
14:00:04 ERROR sync unauthorized
14:00:05 WARN retry scheduled
14:00:10 ERROR retry unauthorized
```

좋은 답:

> 토큰 만료 자체는 예상 가능한 상태일 수 있다. 실제 첫 실패는 갱신 요청이 401로 실패한 지점이며, 이후 unauthorized와 retry 실패는 그 결과일 가능성이 있다.

이렇게 **관찰과 추론을 구분해서** 말한다.

### 40. 한 장 요약

1. 로그는 프로그램 사건 기록이다.
2. 오류를 재현한 정확한 시각을 먼저 기록한다.
3. 로그 한 줄은 시간·레벨·컴포넌트·메시지로 나눠 읽는다.
4. 마지막 오류보다 최초 실패를 찾는다.
5. 같은 요청의 로그는 ID로 연결할 수 있다.
6. stack trace는 오류까지의 호출 경로를 보여준다.
7. 로그에는 비밀값을 그대로 남기지 않는다.
8. 정상 기기와 실패 기기를 비교하면 범위가 빠르게 줄어든다.
9. 시간대가 다르면 로그 순서를 잘못 해석할 수 있다.
10. 로그는 추측이 아니라 실제 관찰 사실을 남기는 것이 좋다.
11. 로그·메트릭·트레이스를 함께 사용하면 장애를 더 잘 이해할 수 있다.

다음 장에서는 로그에서 자주 만나는 `DNS`, `port`, `HTTP`, `server` 같은 네트워크 용어를 **인터넷이 연결되는 실제 순서대로** 처음부터 배운다.
