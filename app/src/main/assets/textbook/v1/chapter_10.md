## V1-C10. 느림·멈춤·오류를 찾는 법 — 재현에서 회귀시험까지

**목표:** 오류를 보면 바로 고치는 사람이 아니라, **재현 가능한 증상 → 증거 → 가설 → 최소 수정 → 재검증** 순서로 문제를 해결하는 사람이 되는 것이다.

---

### 1. 좋은 디버깅은 “해결책 찾기”보다 “문제 정의”가 먼저다

나쁜 문제 정의:

```text
앱이 이상함
데이터가 가끔 틀림
알림이 안 옴
```

좋은 문제 정의:

```text
Galaxy A에서 Wi-Fi 사용 시
09:00 예약 알림이 3회 중 3회 오지 않음.
수동 테스트 알림은 정상 수신.
```

좋은 문제 정의에는 가능하면 이런 정보가 있다.

```text
기기/환경
정확한 행동
입력
기대 결과
실제 결과
발생 빈도
시각
```

원인을 문제 정의에 섞지 않는다.

```text
"FCM 버그 때문에 알림이 안 옴"  ← 이미 결론을 넣음
```

먼저 증상만 정확하게 쓴다.

---

### 2. 재현 — 같은 조건에서 다시 일어나게 만든다

버그가 재현되면 비교 실험을 할 수 있다.

예:

```text
1. 앱 실행
2. 검색창 비움
3. 검색 버튼 탭
4. 앱 crash
```

이 절차가 5번 모두 같은 결과를 내면 좋은 재현 절차다.

재현이 불안정하면 조건을 더 기록한다.

```text
Wi-Fi에서만?
로그인 계정에 따라?
앱 업데이트 직후만?
특정 데이터에서만?
첫 실행만?
```

“가끔”이라는 표현을 **빈도와 조건**으로 바꾸는 것이 디버깅의 시작이다.

---

### 3. 관찰과 추론을 분리한다

관찰:

```text
API response status=200
```

추론:

```text
서버 데이터가 완전히 정상이다
```

200은 요청이 성공적으로 처리됐다는 강한 단서지만 body 내용·타입·의미까지 자동으로 보장하지는 않는다.

관찰:

```text
push provider accepted message
```

추론:

```text
기기 화면에 알림이 표시됐다
```

둘도 다르다.

디버깅 보고서에서는 **실제로 본 사실**과 **그 사실에서 추정한 결론**을 분리한다.

---

### 4. 가설은 하나가 아니라 경쟁시키는 편이 좋다

예: 화면에 가격이 안 보인다.

가능한 가설:

```text
H1 API 응답에 price가 없음
H2 parser가 price 타입을 잘못 읽음
H3 상태 갱신이 안 됨
H4 UI가 오래된 상태를 보고 있음
```

한 가설에 바로 집착하지 않는다.

각 가설에 “맞다면 어떤 증거가 보여야 하는가?”를 붙인다.

```text
H1 맞다면 → API 원문에 price 없음
H2 맞다면 → 원문에는 price 있지만 parse 결과 없음/오류
H3 맞다면 → parse 결과는 정상, state 로그는 옛 값
H4 맞다면 → state는 새 값, 화면만 옛 값
```

이렇게 하면 다음에 볼 증거가 명확해진다.

---

### 5. 격리 — 전체를 고치지 말고 경계를 찾는다

긴 시스템을 단계로 나눈다.

```text
사용자 입력
→ UI event
→ state
→ API request
→ network
→ server
→ response
→ parser
→ DB/state
→ formatter
→ UI
```

중간 지점의 증거를 확인해 앞/뒤 후보를 줄인다.

예:

```text
API 원문 price=200
parser price=200
state price=200
UI price=180
```

서버·네트워크·파서는 우선 후보에서 내려갈 수 있다.

이런 방식이 **범위 좁히기/isolation**이다.

---

### 6. 가장 싼 실험부터 한다

비용과 위험이 낮은 실험부터 한다.

알림이 안 온다고 하자.

비싼/파괴적 실험:

```text
앱 삭제
DB 초기화
서버 전체 재배포
```

싼 실험:

```text
permission 비교
channel 비교
device token 비교
provider response 확인
```

작은 확인으로 후보를 제거할 수 있는데 큰 조치를 먼저 하면 데이터와 증거를 잃는다.

---

### 7. 한 번에 한 변수만 바꾼다

나쁜 디버깅:

```text
API 주소 변경
DB schema 변경
UI 상태 코드 수정
dependency 업데이트
캐시 삭제
```

을 한 번에 한다.

문제가 사라져도 무엇이 원인이었는지 알 수 없다.

좋은 디버깅:

```text
가설 1개
→ 최소 변경 1개
→ 같은 재현 절차
→ 전후 비교
```

원인이 확인된 뒤 별도 리팩터링을 한다.

---

### 8. 경계값은 버그가 숨어 있는 곳이다

조건이 `80 이상 합격`이라면 대표 테스트는:

```text
79
80
81
```

이다.

사용자 입력 길이 제한이 100자라면:

```text
99
100
101
빈 값
```

을 본다.

날짜, 수량, 비율, 페이지 번호, 배열 인덱스도 경계에서 많이 깨진다.

정상값 하나만 성공했다고 기능을 승인하지 않는다.

---

### 9. 실패 케이스를 테스트로 고정한다

버그를 고쳤다면 가능하면 그 실패를 다시 발생시키는 테스트를 만든다.

예:

```text
버그: 빈 검색어에서 crash
```

수정 후 테스트:

```text
입력: ""
기대: 안내문 표시
기대하지 않음: crash
```

이 테스트가 남아 있으면 같은 버그가 나중에 다시 들어왔을 때 자동으로 잡을 수 있다.

---

### 10. 회귀시험 — 고친 기능 외에 기존 기능도 본다

**회귀시험(regression test)**은 수정 때문에 원래 되던 기능이 깨졌는지 다시 확인하는 시험이다.

예를 들어 빈 검색어 validation을 고쳤다.

그 다음 최소한:

```text
빈 검색어
정상 검색어
한 글자 검색어
긴 검색어
네트워크 실패
기존 검색 결과 탭
```

등 관련 경로를 다시 확인한다.

수정한 케이스 하나만 통과했다고 전체 기능 PASS는 아니다.

---

### 11. PASS는 말이 아니라 증거다

좋지 않은 보고:

```text
코드상 문제 없어 보임
아마 정상
PASS
```

좋은 보고:

```text
테스트 명령: ./gradlew test
결과: 320/320 PASS
실기기: Android 16 Galaxy Tab
재현 케이스: 5/5 PASS
회귀 체크: 검색/저장/재실행 PASS
```

실행하지 않았다면:

```text
NOT-RUN
```

이라고 적는다.

AI가 “테스트 통과했습니다”라고 말해도 실제 실행 결과가 없으면 증거가 아니다.

---

### 12. 실제 사례 — 6개월 수익률이 특정 종목만 이상함

증상:

```text
미원화학, 밸로프 등 일부 종목의 6개월 변동률이 외부 사이트와 다름
```

가능한 가설:

```text
H1 기준일이 다름
H2 수정주가/분할 반영 방식이 다름
H3 6개월 시작 거래일 선택이 다름
H4 종목 코드 mapping 오류
H5 캐시된 옛 값
```

실험:

```text
1. 대상 종목 1개 고정
2. 현재가 원본 확인
3. 6개월 기준일 계산 확인
4. 시작일 실제 거래가격 확인
5. corporate action 반영 여부 확인
6. 앱 계산식 재현
```

UI를 먼저 고치지 않는다.

---

### 13. 실제 사례 — PER 값이 많이 비어 있음

증상:

```text
전체 종목 중 PER 미연결 비율이 높음
```

가설:

```text
EPS 누락
적자 회사 처리 오류
티커/DART mapping 실패
분기/TTM 기준 불일치
parser 필드명 불일치
```

“네이버에서 보이니까 그냥 크롤링”으로 바로 해결하기 전에 누락 원인을 유형별로 집계한다.

```text
HOLD 100개
├─ EPS 없음 40
├─ mapping 실패 30
├─ 적자 처리 20
└─ 기타 10
```

원인 유형을 알면 가장 많이 복구할 수 있는 작업부터 진행할 수 있다.

---

### 14. 실제 사례 — 수정 후 다른 화면이 깨짐

검색 화면 버그를 수정했는데 홈 화면 정렬이 망가졌다.

이런 일이 생기는 이유:

- 공유 상태 변경
- 공통 함수 수정
- 모델 타입 변경
- API 응답 변환 변경

그래서 수정 범위를 정할 때 **영향받을 수 있는 주변 기능**을 함께 적는다.

```text
직접 영향: 검색
간접 영향: 홈 정렬, 상세 화면, 저장 데이터
```

회귀시험 범위를 정하는 데 도움이 된다.

## 장 끝 미니 프로젝트 — 실제 버그 하나를 과학실험처럼 해결하기

안전한 작은 버그 하나를 고른다.

반드시 다음 순서를 따른다.

```text
1. 증상 문장 작성
2. 재현 3회
3. 로그/데이터 증거 확보
4. 가설 최소 3개
5. 가장 싼 실험
6. 후보 제거
7. 최소 수정
8. 같은 조건 재검증
9. 관련 회귀시험
10. 결과 기록
```

정답을 맞히는 것보다 **왜 다른 후보를 제거했는지 설명할 수 있는가**를 평가한다.

## 핵심 용어

| 용어 | 뜻 |
|---|---|
| reproduce | 같은 조건에서 버그를 다시 발생시키는 것 |
| observation | 실제로 확인한 사실 |
| hypothesis | 원인이라고 예상해 시험하는 설명 |
| isolation | 시스템을 나눠 실패 범위를 좁히는 것 |
| minimal change | 가설 검증에 필요한 최소 수정 |
| boundary test | 기준값 주변 입력을 시험하는 것 |
| regression test | 수정 후 기존 기능이 깨졌는지 다시 보는 시험 |
| evidence | PASS/FAIL 판단을 뒷받침하는 실제 실행 기록 |
| rollback | 문제가 생기면 이전 정상 상태로 복구하는 것 |

---

## 이 장을 끝내고 할 수 있어야 하는 것

1. 버그를 재현 가능한 문장으로 바꾼다.
2. 관찰과 추론을 분리한다.
3. 원인 가설을 여러 개 세우고 증거와 연결한다.
4. 시스템을 단계별로 격리한다.
5. 파괴적 조치보다 값싼 실험부터 한다.
6. 한 번에 한 변수만 바꾼다.
7. 경계값을 설계한다.
8. 수정 케이스와 주변 회귀 기능을 다시 시험한다.
9. 실행하지 않은 검증을 PASS라고 쓰지 않는다.
