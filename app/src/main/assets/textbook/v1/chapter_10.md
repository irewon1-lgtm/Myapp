## V1-C10. 느림·멈춤·오류를 찾는 법 — 초보자용 디버깅 절차

**이 장의 대상:** 문제가 생기면 일단 재설치하거나 코드를 많이 바꿔보는 사람. `baseline`, `ANR`, `regression`, `hypothesis` 같은 말을 처음 듣는 사람.

**이 장의 목표:** 오류를 고치는 일을 “찍어서 맞히기”가 아니라 **재현 → 관찰 → 범위 좁히기 → 가설 → 최소 수정 → 같은 조건 재검증**이라는 순서로 할 수 있게 된다.

---

### 1. 디버깅은 무엇일까?

프로그램에서 기대와 다른 결과가 나왔을 때 원인을 찾고 수정하는 과정을 **디버깅(debugging)**이라고 부른다.

> **디버깅 = 왜 기대한 대로 동작하지 않는지 증거를 모아 원인을 찾고 고치는 과정**

“에러 메시지를 없애는 것”만이 디버깅은 아니다.

값이 틀리거나, 느리거나, 가끔 중복되거나, 특정 기기에서만 실패하는 것도 모두 디버깅 대상이다.

---

### 2. 버그라는 말

**버그(bug)**는 프로그램이 기대한 대로 동작하지 않는 문제를 흔히 부르는 말이다.

예:

```text
버튼을 눌렀는데 아무 반응 없음
계산 결과가 틀림
앱이 종료됨
데이터가 중복 저장됨
특정 폰만 알림 안 옴
```

버그가 있다는 사실과 원인이 무엇인지는 별개다.

---

### 3. 증상과 원인을 구분하기

사용자가 보는 것은 대부분 **증상(symptom)**이다.

예:

```text
증상: 화면에 데이터가 없다
```

가능한 원인은 많다.

```text
API 요청 실패
JSON 파싱 실패
DB 저장 실패
잘못된 필터
UI 상태 연결 실패
```

따라서:

> **보이는 증상 = 원인**

이라고 생각하면 안 된다.

---

### 4. 좋은 문제 설명은 구체적이다

나쁜 설명:

> 앱이 이상해요.

더 좋은 설명:

> Android 16 태블릿에서 검색어를 비워둔 채 검색 버튼을 누르면 앱이 종료된다. 정상 기대값은 “검색어를 입력하세요” 안내문이다. 5회 시도 중 5회 재현된다.

이 설명에는:

```text
환경
입력
행동
실제 결과
기대 결과
재현 빈도
```

가 들어 있다.

---

### 5. 재현이란 무엇일까?

같은 조건에서 문제를 다시 발생시키는 것을 **재현(reproduce)**이라고 부른다.

> **재현 = 버그가 생기는 조건과 단계를 다시 따라가 같은 문제를 만드는 것**

버그를 고치기 전에 재현할 수 있으면 매우 유리하다.

수정 후 같은 절차로 다시 확인할 수 있기 때문이다.

---

### 6. 재현 절차 쓰기

예:

```text
1. 앱 실행
2. 검색 화면 이동
3. 검색어를 비워둠
4. 검색 버튼 누름
5. 앱 종료 확인
```

기대 결과:

```text
"검색어를 입력하세요" 표시
```

실제 결과:

```text
앱 크래시
```

이 정도로 적으면 다른 사람도 같은 조건을 만들 수 있다.

---

### 7. 재현 빈도

버그가 항상 생기지 않을 수 있다.

```text
10번 중 10번
10번 중 3번
100번 중 1번
```

빈도를 기록한다.

가끔 생기는 동시성 문제에서는 빈도 자체가 중요한 단서다.

---

### 8. 환경도 재현 조건이다

같은 코드인데 한 기기에서만 실패할 수 있다.

기록할 수 있는 항목:

```text
앱 버전
Android 버전
기기 모델
계정
네트워크
언어/지역
설치 경로
데이터 상태
```

모든 항목을 항상 기록할 필요는 없지만 차이가 의심되면 비교한다.

---

### 9. 관찰과 추론을 구분한다

관찰:

```text
HTTP status=500
```

추론:

```text
서버 DB가 깨졌다
```

첫 문장은 실제로 본 사실이다.

둘째 문장은 원인에 대한 추측이다.

디버깅에서는 이 둘을 구분한다.

> **관찰 = 확인한 사실**
>
> **추론 = 그 사실을 바탕으로 생각한 설명**

---

### 10. 가설이란 무엇일까?

원인일 수 있다고 생각한 설명을 **가설(hypothesis)**이라고 부른다.

예:

```text
가설 A: 서버 응답이 비어 있다
가설 B: 파싱에 실패했다
가설 C: UI 필터가 모두 제거했다
```

가설은 정답이 아니다.

실험으로 틀렸는지 맞았는지 확인해야 한다.

---

### 11. 좋은 가설에는 예측이 있다

가설:

> API 인증 토큰이 만료되어 401이 발생한다.

예측:

```text
맞다면 요청 로그에 401이 보일 것이다.
토큰 갱신 후 같은 요청은 성공할 것이다.
```

가설을 세울 때 “맞다면 무엇을 볼 수 있어야 하는가?”를 같이 적는다.

---

### 12. 한 번에 하나만 바꾼다

버그가 생겼다고 다음을 동시에 하면 안 된다.

```text
앱 재설치
캐시 삭제
DB 초기화
라이브러리 업데이트
서버 재배포
코드 10곳 수정
```

문제가 사라져도 무엇이 원인이었는지 알 수 없다.

좋은 순서:

```text
가설 하나
↓
최소한의 변경 하나
↓
같은 테스트
↓
결과 기록
```

---

### 13. 최소 수정이란 무엇일까?

원인과 관련된 가장 작은 범위만 바꾸는 것을 **최소 수정(minimal change)**이라고 생각할 수 있다.

예:

```text
문제: 빈 검색어 validation 없음
```

좋은 수정:

```text
빈 검색어 검사 추가
```

나쁜 수정:

```text
검색 화면 전체 디자인 변경
API 구조 변경
DB schema 변경
동시에 라이브러리 업데이트
```

버그 수정과 리팩터링을 섞지 않는다.

---

### 14. 범위 좁히기

문제가 긴 흐름에 있을 때 중간 지점을 확인한다.

예:

```text
사용자 입력
→ API 요청
→ 서버
→ JSON
→ DB
→ UI
```

API 응답까지 정상이라면 앞부분은 우선순위가 낮아진다.

DB 저장까지 정상이라면 UI 쪽으로 더 좁힐 수 있다.

이 방식은 큰 문제를 반씩 줄이는 **이진 탐색(binary search)**과 비슷한 사고다.

---

### 15. “마지막 정상 지점” 찾기

예:

```text
입력: 정상
요청: 정상
응답: 정상
파싱: 정상
DB 저장: 정상
UI state: 비정상
```

마지막 정상은 DB 저장이다.

따라서 DB 이전 단계보다 **DB→UI state 전달**을 먼저 본다.

> **마지막 정상 지점 = 문제 범위를 줄이는 강력한 기준**

---

### 16. 기준선은 무엇일까?

수정 전 상태를 숫자나 결과로 기록해둔다.

이를 **기준선(baseline)**이라고 한다.

예:

```text
앱 시작 시간: 4.2초
검색 성공률: 10/10
메모리: 380MB
```

수정 후 같은 조건으로 비교한다.

---

### 17. 성능 문제도 먼저 재현한다

“앱이 느리다”를 구체적으로 바꾼다.

나쁜 설명:

> 전체적으로 답답함.

좋은 설명:

> 홈 화면에서 종목 상세로 이동할 때 평균 2.8초가 걸린다. 데이터가 이미 로컬에 있는 상태에서도 동일하다.

이제 네트워크가 아닌 UI/DB 후보가 더 중요할 수 있다.

---

### 18. 성능 측정 지점을 나눈다

예:

```text
버튼 클릭       0ms
DB 조회 완료   600ms
데이터 변환    900ms
UI 렌더 완료  2800ms
```

어디서 시간이 많이 늘었는지 확인한다.

전체 시간만 보고 추측하지 않는다.

---

### 19. 크래시는 무엇일까?

앱이 오류로 비정상 종료되는 것을 **크래시(crash)**라고 부른다.

크래시에서는:

```text
예외 종류
stack trace
파일/줄 번호
입력 데이터
앱 버전
```

을 확인한다.

같은 줄에서 계속 크래시가 나면 강한 단서다.

---

### 20. ANR은 무엇일까?

Android 앱이 오랫동안 사용자 입력에 응답하지 않으면 **ANR(Application Not Responding)** 상황이 발생할 수 있다.

크래시와 다르다.

```text
크래시 → 앱 비정상 종료
ANR     → 앱은 살아 있지만 너무 오래 응답하지 않음
```

메인 스레드에서 긴 작업을 수행하는 것이 대표 후보 중 하나다.

---

### 21. 무한루프 확인

앱이 CPU를 매우 많이 사용하고 멈춰 있다면 종료되지 않는 반복을 의심할 수 있다.

예:

```python
n = 0
while n < 10:
    print(n)
```

이 코드는 `n`이 바뀌지 않으므로 계속 반복될 수 있다.

수정:

```python
n = 0
while n < 10:
    print(n)
    n = n + 1
```

반복문에서는 **종료 조건에 영향을 주는 값이 변하는지** 본다.

---

### 22. null이라는 말

프로그램에서 값이 없음을 표현하는 방식으로 `null`, `None`, `nil` 같은 값을 사용할 수 있다.

언어마다 다르다.

> **null 계열 값 = 값이 없음을 표현하는 특별한 상태**

값이 있다고 가정하고 접근하면 오류가 날 수 있다.

```text
price = null
price.toString()  ← 언어/상황에 따라 오류 가능
```

Python에서는 `None`을 사용한다.

---

### 23. 경계값은 무엇일까?

조건이:

```text
80점 이상 합격
```

이라면 가장 중요한 테스트는:

```text
79
80
81
```

이다.

조건 바로 아래·같음·위 값을 **경계값(boundary value)**이라고 부른다.

버그는 경계에서 많이 생긴다.

---

### 24. 정상값만 테스트하면 부족하다

검색 길이가 1~20자라면 다음을 시험한다.

```text
0자
1자
20자
21자
한글
영어
이모지
공백만
매우 긴 문자열
```

정상 한 케이스만 통과했다고 기능이 안전한 것은 아니다.

---

### 25. 테스트 케이스란 무엇일까?

**테스트 케이스(test case)**는 입력과 기대 결과를 정해 기능을 확인하는 한 가지 시험 상황이다.

예:

```text
입력: score=80
기대: PASS
```

이렇게 기대값이 명확해야 실제 결과와 비교할 수 있다.

---

### 26. 회귀시험이란 무엇일까?

버그 하나를 고친 뒤 기존에 잘 되던 기능이 깨질 수 있다.

수정 후 관련 기존 기능을 다시 검사하는 것을 **회귀시험(regression test)**이라고 부른다.

> **regression test = 수정 때문에 기존 기능이 망가지지 않았는지 다시 확인하는 테스트**

---

### 27. 고친 버그를 테스트로 남긴다

예전에 빈 검색어에서 크래시가 났다면 테스트를 하나 만든다.

```text
입력: 빈 문자열
기대: 안내문 표시
앱 크래시 금지
```

이 테스트가 계속 실행되면 같은 버그가 다시 들어오는 것을 막는 데 도움이 된다.

---

### 28. 자동 테스트와 수동 테스트

#### 자동 테스트

코드가 반복해서 실행하며 결과를 검사한다.

장점:

```text
빠른 반복
일관된 검사
회귀 방지
```

#### 수동 테스트

사람이 실제 앱을 누르고 확인한다.

필요한 경우:

```text
실제 터치 느낌
알림 표시
기기별 UI
카메라/센서
```

둘은 서로 대체가 아니라 보완 관계다.

---

### 29. 단위 테스트란 무엇일까?

작은 함수나 로직 한 단위를 검사하는 테스트를 **단위 테스트(unit test)**라고 부른다.

예:

```text
등급 계산 함수
입력: 80
출력: A
```

작고 빠르게 실행할 수 있다.

---

### 30. 통합 테스트란 무엇일까?

여러 부분이 연결될 때 정상인지 확인하는 테스트를 **통합 테스트(integration test)**라고 한다.

예:

```text
API 응답
→ parser
→ DB 저장
```

각 부분은 정상이어도 연결에서 실패할 수 있다.

---

### 31. E2E 테스트란 무엇일까?

사용자 흐름을 처음부터 끝까지 검사하는 것을 **End-to-End(E2E) 테스트**라고 부른다.

예:

```text
앱 실행
→ 로그인
→ 검색
→ 상세 진입
→ 저장
→ 앱 재실행
→ 저장값 확인
```

실제 사용자 경험에 가깝지만 느리고 환경 영향을 많이 받을 수 있다.

---

### 32. 테스트 피라미드 맛보기

일반적으로 많은 작은 테스트와 적절한 수의 통합/E2E 테스트를 조합한다.

```text
      E2E
    통합 테스트
  많은 단위 테스트
```

무조건 이 모양만 정답은 아니지만 테스트 비용과 속도를 생각하는 데 도움이 된다.

---

### 33. PASS는 증거가 있어야 한다

“코드 보니까 될 것 같다”는 PASS가 아니다.

좋은 완료 보고:

```text
테스트 명령 실행
실행 결과 PASS
빌드 성공
실제 설치 성공
재현 케이스 5/5 통과
```

실행하지 못했다면:

```text
NOT RUN
```

이라고 적는다.

---

### 34. 스크린샷만으로 기능을 증명할 수 있을까?

스크린샷은 UI 상태의 한 순간을 보여준다.

하지만:

```text
버튼이 실제 눌리는지
데이터가 DB에 저장됐는지
앱 재실행 후 유지되는지
서버 요청이 성공했는지
```

까지 모두 증명하지는 못한다.

기능별로 맞는 증거가 필요하다.

---

### 35. 로그만으로도 부족할 수 있다

로그에 `SUCCESS`라고 찍는 코드 자체가 잘못됐을 수 있다.

따라서 중요한 작업은 결과 데이터를 실제로 확인한다.

예:

```text
로그: save success
실제 DB row count: 0
```

로그와 결과가 다르면 실제 결과를 우선 조사한다.

---

### 36. AI가 “완료했습니다”라고 말했을 때

AI가 코드를 작성하고:

> 완료했습니다. 모두 정상입니다.

라고 말해도 검증이 끝난 것은 아니다.

확인해야 한다.

```text
실제 파일이 바뀌었는가?
빌드했는가?
테스트했는가?
테스트 로그가 있는가?
실제 앱을 실행했는가?
기존 기능이 보존됐는가?
```

AI의 문장은 증거가 아니다.

---

### 37. diff는 무엇일까?

코드 변경 전후 차이를 보여주는 것을 **diff**라고 부른다.

예:

```diff
- if (name != null)
+ if (!name.isNullOrBlank())
```

AI가 많은 파일을 바꿨다면 diff를 먼저 보고 의도한 범위만 변경했는지 확인한다.

Git 장에서 더 자세히 배운다.

---

### 38. 롤백을 준비한다

수정 전에 정상 상태를 보존한다.

```text
Git commit
백업
DB snapshot
설정 기록
```

문제가 생기면 원래 상태로 돌아갈 수 있어야 한다.

복구 방법이 없는 대규모 수정은 위험하다.

### 39. 실제 예제 — 주가 변동률이 이상함

증상:

> 특정 종목 6개월 상승률이 외부 사이트와 크게 다르다.

잘못된 접근:

> UI 숫자만 직접 수정.

좋은 접근:

```text
1. 기준일 확인
2. 6개월 전 기준 가격 확인
3. 주식분할/병합 여부 확인
4. 조정주가 사용 여부 확인
5. 계산식 확인
6. 데이터 저장값 확인
7. UI 표시값 확인
```

숫자가 처음 달라지는 단계가 원인 후보다.

### 44. 초보자가 자주 하는 오해

#### 오해 1. 에러 메시지가 가리키는 줄이 항상 근본 원인이다

아니다. 잘못된 값이 더 앞에서 만들어졌을 수 있다.

#### 오해 2. 여러 곳을 한 번에 고치면 빨리 해결된다

원인 확인이 어려워진다.

#### 오해 3. 한 번 성공하면 수정 완료다

반복 재현과 회귀시험이 필요하다.

#### 오해 4. 자동 테스트만 통과하면 실제 기기 확인은 필요 없다

기능에 따라 실제 환경 검증이 필요하다.

#### 오해 5. AI가 PASS라고 말하면 증거가 된다

아니다.

### 47. 종합 미션

상황:

> 앱에서 “저장” 버튼을 누르면 가끔 같은 일정이 두 개 생긴다. 20번 시도 중 4번 발생한다.

좋은 조사:

```text
1. 클릭 이벤트 횟수 기록
2. 네트워크 요청 ID 기록
3. 서버 요청 수 기록
4. DB insert 수 기록
5. 중복 발생 시 요청 순서 비교
6. 버튼 중복 입력 또는 retry 여부 확인
7. idempotency 정책 확인
```

가설:

```text
A. 버튼이 두 번 클릭됨
B. 네트워크 retry가 두 번 insert함
C. 서버 중복 방지 없음
```

각 가설이 맞다면 보여야 할 로그를 정하고 하나씩 확인한다.

### 48. 한 장 요약

1. 디버깅은 추측이 아니라 증거 수집 과정이다.
2. 증상과 원인은 다르다.
3. 재현 가능한 문제로 만들어야 수정 검증이 가능하다.
4. 관찰과 추론을 분리한다.
5. 가설에는 “맞다면 무엇이 보여야 하는가”를 적는다.
6. 한 번에 하나의 변화만 시험한다.
7. 마지막 정상 지점을 찾으면 범위를 줄일 수 있다.
8. 성능 문제는 수정 전에 기준선을 측정한다.
9. 경계값과 실패 케이스를 테스트한다.
10. 수정 후 회귀시험을 한다.
11. PASS는 실제 실행 증거가 있어야 한다.
12. AI의 완료 보고는 증거가 아니다.
13. 변경 전 정상 상태를 보존하고 rollback 가능하게 한다.

다음 장은 V1의 마지막 장이다. 지금까지 배운 모든 개념을 사용해 **하나의 실제 장애를 처음부터 끝까지 해결하는 프로젝트**를 진행한다.
