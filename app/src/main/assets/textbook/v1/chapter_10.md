# TRACK 10 · 느림·멈춤·오류를 찾는 법

이 TRACK은 `코딩을 잘하는 사람 = 오류가 없는 사람`이라는 생각을 버리는 과정이다.

실제 개발에서는 오류가 반드시 생긴다.

중요한 능력은 **문제가 생겼을 때 추측으로 마구 고치지 않고, 증거로 원인을 좁혀 실제로 검증하는 것**이다.

---

## BLOCK 01 · 버그란 무엇인가

### LESSON 01 · 기대한 동작과 실제 동작의 차이

프로그램이 원래 의도한 방식과 다르게 동작하는 문제를 흔히 **버그(bug)**라고 부른다.

예:

```text
기대: 저장 버튼을 누르면 메모가 저장된다.
실제: 버튼을 눌러도 메모가 사라진다.
```

한 줄 뜻:

> bug = 프로그램이 기대한 동작과 다르게 움직이는 결함

### LESSON 02 · 버그를 정확히 말하기

나쁜 설명:

```text
앱 이상함
```

좋은 설명:

```text
Android 14에서 메모 작성 후 저장 버튼을 누르면
화면에는 성공 메시지가 뜨지만 앱을 다시 열면 메모가 없다.
```

버그 설명이 구체적일수록 재현하기 쉽다.

---

## BLOCK 02 · 증상과 원인

### LESSON 01 · 보이는 현상이 원인은 아니다

화면이 하얗게 보인다.

이것은 **증상(symptom)**이다.

원인은:

```text
데이터 로딩 실패
화면 상태 오류
CSS 문제
렌더링 예외
네트워크 timeout
```

중 하나일 수 있다.

### LESSON 02 · 증상 하나로 원인을 단정하지 않기

`흰 화면 = 네트워크 문제`처럼 연결하면 안 된다.

먼저 증상을 정확히 기록하고 원인은 후보로 남긴다.

---

## BLOCK 03 · 기대값과 실제값

### LESSON 01 · 무엇이 달랐는지 적는다

디버깅의 출발점은 두 줄이다.

```text
Expected: 무엇이 일어나야 했는가?
Actual: 실제로 무엇이 일어났는가?
```

예:

```text
Expected: 2 + 3 = 5
Actual: 2 + 3 = 23
```

### LESSON 02 · '안 된다'를 숫자와 상태로 바꾸기

```text
느림
```

대신:

```text
Expected: 1초 이내
Actual: 평균 7.4초
```

라고 적으면 측정 가능한 문제가 된다.

---

## BLOCK 04 · 재현이란 무엇인가

### LESSON 01 · 같은 문제를 다시 만들어 보기

문제가 생겼던 조건을 다시 만들어 같은 증상이 나타나는지 확인하는 것을 **재현(reproduction)**이라고 부른다.

한 줄 뜻:

> 재현 = 같은 조건에서 같은 문제를 다시 일으켜 보는 것

### LESSON 02 · 재현 절차

예:

```text
1. 앱을 완전히 종료한다.
2. 네트워크를 Wi-Fi로 연결한다.
3. 사용자 A로 로그인한다.
4. 검색창에 'ABC' 입력한다.
5. 검색 버튼을 두 번 빠르게 누른다.
6. 오래된 결과가 마지막에 나타나는지 확인한다.
```

누구나 같은 절차를 따라 할 수 있어야 좋다.

---

## BLOCK 05 · 항상 재현되는 버그와 가끔 재현되는 버그

### LESSON 01 · deterministic

같은 입력과 같은 조건이면 항상 같은 결과가 나오는 성질을 **결정적(deterministic)**이라고 부른다.

항상 재현되는 버그는 비교적 조사하기 쉽다.

### LESSON 02 · 비결정적 문제

같은 것처럼 보이는 조건에서도 가끔만 나타나는 문제를 **비결정적(nondeterministic)**이라고 부를 수 있다.

예:

```text
100번 중 3번 실패
```

이런 문제는 비동기 순서, 경쟁 상태, 외부 네트워크 같은 숨은 조건이 있을 수 있다.

---

## BLOCK 06 · 최소 재현

### LESSON 01 · 문제와 관계없는 부분을 제거하기

큰 앱 전체에서 오류를 찾기 어려우면 문제를 일으키는 데 필요한 최소 기능만 남긴다.

이렇게 만든 작은 예를 **최소 재현(minimal reproduction)**이라고 부른다.

### LESSON 02 · 왜 유용한가

큰 앱에는 수천 개의 변수와 기능이 있다.

최소 재현에서는:

```text
문제와 관련된 코드만 남음
외부 영향 감소
다른 사람도 빠르게 실행 가능
```

해서 원인을 찾기 쉬워진다.

---

## BLOCK 07 · 가설이란 무엇인가

### LESSON 01 · 아직 확인되지 않은 원인 후보

증상:

```text
저장 버튼 후 데이터가 사라짐
```

원인 후보:

```text
DB 저장 함수가 호출되지 않음
저장은 됐지만 조회 쿼리가 틀림
앱 종료 전에 transaction이 commit되지 않음
```

이런 확인 전 설명을 **가설(hypothesis)**이라고 부른다.

### LESSON 02 · 가설과 사실을 구분한다

```text
사실: 로그에 INSERT 호출 기록이 없음
가설: 저장 버튼 event handler가 실행되지 않았을 수 있음
```

가설을 사실처럼 말하지 않는다.

---

## BLOCK 08 · 실험

### LESSON 01 · 가설 하나를 시험하기

가설:

```text
버튼 클릭 handler가 호출되지 않는다.
```

실험:

```text
handler 첫 줄에 로그를 추가하고 버튼 클릭
```

결과:

```text
로그가 찍힘
```

그러면 `handler가 아예 호출되지 않는다`는 가설은 기각할 수 있다.

### LESSON 02 · 한 번에 하나만 바꾸기

코드 20곳을 동시에 수정하면 어떤 변경이 효과가 있었는지 모른다.

가능하면 한 가설에 한 실험을 대응시킨다.

## BLOCK 09 · 범위를 절반씩 줄이기

### LESSON 01 · binary search 사고

문제가 100단계 중 어디서 생겼는지 모른다고 하자.

50단계 지점의 값이 정상인지 확인한다.

```text
50까지 정상 → 문제는 51~100
50에서 이미 오류 → 문제는 1~50
```

이런 식으로 범위를 절반씩 줄일 수 있다.

### LESSON 02 · 코드에서도 사용한다

긴 데이터 처리 파이프라인에서 중간 결과를 확인해 처음 틀어지는 지점을 찾는다.

무작정 모든 줄을 보는 것보다 빠를 수 있다.

## BLOCK 10 · print debugging

### LESSON 01 · 값 출력으로 흐름 확인하기

간단한 디버깅 방법은 필요한 위치에 로그나 출력문을 넣는 것이다.

```python
print("before", value)
result = calculate(value)
print("after", result)
```

이런 방식을 흔히 **print debugging**이라고 부른다.

### LESSON 02 · 장점과 한계

장점:

```text
간단함
어디서나 사용 가능
실행 순서를 볼 수 있음
```

한계:

```text
로그가 너무 많아질 수 있음
민감정보 노출 위험
실시간 내부 상태를 자세히 보기 어려움
```

---

## BLOCK 11 · 디버거란 무엇인가

### LESSON 01 · 실행을 멈추고 내부를 보는 도구

**디버거(debugger)**는 프로그램 실행을 특정 지점에서 멈추고 변수 값, 호출 경로 등을 확인할 수 있는 도구다.

한 줄 뜻:

> debugger = 프로그램을 실행하면서 내부 상태를 조사할 수 있게 도와주는 도구

### LESSON 02 · breakpoint

디버거가 실행을 멈출 지점을 **브레이크포인트(breakpoint)**라고 부른다.

코드의 특정 줄에 breakpoint를 걸고 그 줄에 도달했을 때 실행을 멈춘다.

---

## BLOCK 12 · step over, step into, step out

### LESSON 01 · step over

현재 줄을 실행하고 다음 줄로 이동하되, 호출한 함수 안으로 깊게 들어가지 않는 기능이다.

### LESSON 02 · step into

현재 줄이 함수를 호출하면 그 함수 내부로 들어가 한 줄씩 보는 기능이다.

### LESSON 03 · step out

현재 함수의 나머지를 실행하고 호출한 곳으로 돌아가는 기능이다.

이 세 기능을 이용해 `어느 함수부터 값이 달라지는지` 추적한다.

---

## BLOCK 13 · watch와 변수 검사

### LESSON 01 · 특정 값을 계속 보기

디버거에서 관심 있는 변수 값을 계속 표시하도록 설정할 수 있다.

이를 **watch** 기능이라고 부른다.

### LESSON 02 · 상태 변화 추적

```text
count: 0
count: 1
count: 2
count: -999
```

처럼 예상하지 못한 값으로 바뀌는 순간을 찾을 수 있다.

---

## BLOCK 14 · assertion

### LESSON 01 · 절대 깨지면 안 되는 조건을 코드로 적기

프로그램이 정상이라면 반드시 참이어야 하는 조건을 검사하는 것을 **assertion(어설션)**이라고 부른다.

예:

```python
assert age >= 0
```

`나이는 음수가 아니어야 한다`는 가정을 검사한다.

### LESSON 02 · assertion과 사용자 입력 검증은 다르다

사용자가 잘못된 값을 넣을 수 있는 상황은 정상적인 오류 처리로 다뤄야 한다.

assertion은 개발 중 내부 가정이 깨졌는지 찾는 용도로 많이 사용한다.

---

## BLOCK 15 · 테스트란 무엇인가

### LESSON 01 · 원하는 동작을 자동으로 확인하기

코드가 기대한 결과를 내는지 확인하는 절차를 **테스트(test)**라고 부른다.

사람이 직접 눌러 보는 테스트도 있고 코드로 자동 실행하는 테스트도 있다.

### LESSON 02 · 테스트는 버그가 없다는 증명인가

아니다.

테스트는 **시험한 조건에서 기대 결과가 나왔다는 증거**다.

시험하지 않은 조건까지 모두 정상이라고 보장하지 않는다.

---

## BLOCK 16 · unit test

### LESSON 01 · 작은 단위 검사

함수나 클래스처럼 작은 코드 단위를 따로 검사하는 테스트를 **단위 테스트(unit test)**라고 부른다.

예:

```python
def add(a, b):
    return a + b

assert add(2, 3) == 5
```

### LESSON 02 · 장점

작은 단위에서 실패하면 원인 범위를 좁히기 쉽다.

많은 경우 빠르게 실행할 수 있다.

---

## BLOCK 17 · integration test

### LESSON 01 · 여러 부분을 연결해 검사

DB, API, 서비스 같은 여러 구성요소가 함께 정상 동작하는지 확인하는 테스트를 **통합 테스트(integration test)**라고 부른다.

예:

```text
API 요청
→ 서비스 로직
→ DB 저장
→ 응답 확인
```

단위 테스트에서 정상인 코드도 실제 연결에서 실패할 수 있다.

---

## BLOCK 18 · E2E test

### LESSON 01 · 사용자 흐름 전체 검사

**E2E(end-to-end) test**는 사용자의 시작부터 끝까지 전체 흐름을 검사한다.

예:

```text
앱 실행
→ 로그인
→ 상품 선택
→ 결제
→ 주문 완료 화면
```

실제 사용자 흐름을 넓게 검증하지만 단위 테스트보다 느리고 실패 원인을 찾기 어려울 수 있다.

---

## BLOCK 19 · regression test

### LESSON 01 · 고친 뒤 예전 기능이 깨지지 않았나

버그 하나를 고쳤는데 다른 기능이 망가질 수 있다.

기존에 정상 동작하던 기능이 다시 깨지는 현상을 **회귀(regression)**라고 부른다.

이를 확인하는 테스트를 **회귀 테스트(regression test)**라고 한다.

### LESSON 02 · 버그를 고치면 테스트를 남긴다

가능하면 발견된 버그를 재현하는 테스트를 먼저 만든다.

```text
수정 전 → 테스트 실패
수정 후 → 테스트 성공
```

그러면 같은 버그가 다시 들어오는 것을 막는 안전망이 된다.

---

## BLOCK 20 · 경계값

### LESSON 01 · 문제는 경계에서 많이 생긴다

나이 입력이 1~120만 허용된다고 하자.

테스트할 값:

```text
0
1
120
121
```

최솟값과 최댓값 바로 주변을 **경계값(boundary value)**이라고 부른다.

### LESSON 02 · 배열 경계

배열에 10개가 있으면 인덱스 범위를 잘못 계산해 마지막 원소에서 오류가 나는 문제가 흔하다.

`처음`, `마지막`, `비어 있음`, `한 개만 있음`을 꼭 시험한다.

---

## BLOCK 21 · equivalence partition

### LESSON 01 · 비슷하게 동작하는 입력을 그룹으로 나누기

모든 숫자를 하나씩 테스트할 수는 없다.

비슷하게 처리되는 입력 범위를 그룹으로 나눈다.

예:

```text
0 이하 → 잘못된 값
1~120 → 정상
121 이상 → 잘못된 값
```

이렇게 테스트 입력을 동작 그룹으로 나누는 방법을 **동등 분할(equivalence partitioning)**이라고 부른다.

---

## BLOCK 22 · flaky test

### LESSON 01 · 같은 코드인데 테스트가 가끔 실패한다

같은 변경이 없는데 테스트가 어떤 날은 성공하고 어떤 날은 실패한다면 **flaky test**일 수 있다.

원인 후보:

```text
시간 의존
네트워크 의존
race condition
공유 데이터
무작위 값
```

### LESSON 02 · 실패한 테스트를 무조건 다시 돌려서 초록색 만들지 않는다

재실행해서 성공했다고 원인이 해결된 것은 아니다.

왜 가끔 실패하는지 조사해야 한다.

---

## BLOCK 23 · heisenbug

### LESSON 01 · 조사하려고 하면 사라지는 버그

로그를 추가하거나 디버거를 붙이면 실행 타이밍이 달라져 버그가 사라지는 경우가 있다.

이런 문제를 **Heisenbug**라고 부른다.

### LESSON 02 · 비동기와 경쟁 상태에서 자주 어렵다

타이밍이 원인인 race condition은 로그 출력 때문에 실행 속도가 달라져 재현이 안 될 수 있다.

이때 더 정밀한 trace나 재현 조건 제어가 필요하다.

---

## BLOCK 24 · deadlock

### LESSON 01 · 서로 기다리느라 영원히 못 움직이는 상태

작업 A가 자원 1을 가지고 자원 2를 기다린다.

작업 B는 자원 2를 가지고 자원 1을 기다린다.

```text
A: 1 보유, 2 기다림
B: 2 보유, 1 기다림
```

둘 다 상대가 놓기를 기다려 진행하지 못한다.

이를 **교착상태(deadlock)**라고 부른다.

### LESSON 02 · 멈춤 문제의 한 후보

앱이 멈췄다고 모두 deadlock은 아니다.

무한 반복, 긴 I/O, UI thread blocking 등 다른 원인도 있다.

---

## BLOCK 25 · 무한 반복

### LESSON 01 · 끝나지 않는 loop

```python
while True:
    pass
```

처럼 종료 조건 없이 계속 도는 반복은 CPU를 계속 사용할 수 있다.

의도적으로 서버 루프를 만드는 경우도 있지만 종료나 대기 없이 돌면 문제가 될 수 있다.

### LESSON 02 · 증상

```text
CPU 사용률 높음
앱 반응 없음
배터리 소모
```

등이 나타날 수 있다.

---

## BLOCK 26 · performance regression

### LESSON 01 · 기능은 되는데 느려짐

새 버전에서 결과는 맞지만 1초 걸리던 작업이 10초 걸린다면 **성능 회귀(performance regression)**다.

### LESSON 02 · 성능도 테스트한다

```text
수정 전 평균 1.2초
수정 후 평균 1.1초
```

처럼 기준값을 두고 비교한다.

한 번 측정만으로 결론 내리지 않고 여러 번 측정해 변동을 본다.

## BLOCK 27 · 이분법적 격리

### LESSON 01 · 기능 절반을 끄기

문제가 여러 모듈 중 어디 있는지 모르면 절반을 비활성화해 본다.

```text
A+B+C+D에서 실패
A+B만 실행 → 정상
C+D만 실행 → 실패
```

범위가 C+D로 줄었다.

### LESSON 02 · Git bisect

Git에서는 어느 커밋부터 버그가 생겼는지 이분 탐색 방식으로 찾는 **git bisect** 기능이 있다.

좋은 커밋과 나쁜 커밋을 알려주면 중간 커밋을 차례로 시험해 범위를 줄인다.

## BLOCK 28 · 원인 수정과 우회책

### LESSON 01 · workaround

근본 원인을 고치지 않고 문제를 피하는 임시 방법을 **우회책(workaround)**이라고 부른다.

예:

```text
앱을 재시작하면 일시적으로 정상
```

### LESSON 02 · workaround를 fix라고 부르지 않는다

재시작으로 증상이 사라져도 메모리 누수 원인은 그대로일 수 있다.

보고서에서:

```text
임시 우회 가능
근본 수정 미완료
```

라고 구분한다.

---

## BLOCK 29 · Clean Pass의 의미

### LESSON 01 · 다시 처음부터 검증하기

수정 직후 관련 테스트 하나만 성공했다고 끝내지 않는다.

변경된 상태에서 처음부터 같은 절차로 다시 검증하는 것을 이 교재에서는 **CLEAN PASS**라고 부른다.

### LESSON 02 · 서로 다른 실패 유형을 검사한다

좋은 CLEAN PASS는 같은 버튼을 20번 누르는 것이 아니다.

예:

```text
정상 입력
빈 입력
최대 길이
네트워크 없음
서버 500
빠른 연속 클릭
앱 재시작
```

처럼 서로 다른 실패 유형을 실제로 시험한다.

### LESSON 03 · 실행하지 않은 것은 PASS가 아니다

코드를 읽어 보니 될 것 같다는 것은 **정적 검토**다.

실제 테스트를 실행하지 않았다면:

```text
예상 PASS
```

라고도 쓰지 않는다.

정확히:

```text
미실행
```

이라고 기록한다.

## BLOCK 30 · 증거 수준

### LESSON 01 · 추정

```text
코드상 정상으로 보임
```

은 추정이다.

### LESSON 02 · 시뮬레이션

가상의 입력으로 머릿속 또는 모델에서 검토한 것은 시뮬레이션이다.

실제 실행 결과가 아니다.

### LESSON 03 · 실제 실행

실제 프로그램이나 테스트를 실행해 로그와 결과를 얻은 것은 실행 증거다.

### LESSON 04 · 운영 검증

실제 운영 환경에서 사용자 경로까지 확인한 것은 더 강한 증거가 될 수 있다.

환경별로 결과가 다를 수 있으므로 어떤 환경에서 확인했는지 함께 기록한다.

## BLOCK 31 · 오류 보고서

### LESSON 01 · 좋은 보고서 구조

```text
증상
기대 결과
실제 결과
환경
재현 단계
최초 실패 증거
원인 가설
검증 실험
수정 내용
수정 후 테스트
회귀 테스트
남은 위험
```

### LESSON 02 · '완료'라는 단어

다음이 없으면 완료라고 부르지 않는다.

```text
문제 재현

수정 적용
같은 조건에서 재검증
관련 회귀 검증
```

## BLOCK 32 · TRACK 10 핵심 용어 사전

| 용어 | 아주 쉬운 뜻 |
|---|---|
| bug | 기대 동작과 실제 동작이 다른 결함 |
| symptom | 사용자나 시스템에서 보이는 문제 현상 |
| reproduction | 같은 문제를 다시 일으켜 보는 것 |
| deterministic | 같은 조건에서 같은 결과가 나오는 성질 |
| minimal reproduction | 문제를 일으키는 최소 코드와 조건 |
| hypothesis | 아직 확인되지 않은 원인 후보 |
| debugger | 실행 중 프로그램 내부를 조사하는 도구 |
| breakpoint | 디버거가 실행을 멈출 코드 위치 |
| watch | 특정 변수 값을 계속 관찰하는 기능 |
| assertion | 반드시 참이어야 하는 내부 조건 검사 |
| unit test | 작은 코드 단위를 따로 검사하는 테스트 |
| integration test | 여러 구성요소의 연결을 검사하는 테스트 |
| E2E test | 사용자 전체 흐름을 처음부터 끝까지 검사하는 테스트 |
| regression | 수정으로 기존 기능이 다시 깨지는 현상 |
| boundary value | 입력 범위의 경계와 바로 주변 값 |
| flaky test | 같은 코드에서도 가끔 성공·실패가 바뀌는 테스트 |
| Heisenbug | 관찰 방법 때문에 재현 여부가 달라지는 버그 |
| deadlock | 작업들이 서로 기다리며 진행하지 못하는 상태 |
| performance regression | 기능은 맞지만 이전보다 성능이 나빠진 회귀 |
| workaround | 근본 원인을 고치지 않고 증상을 피하는 임시 방법 |
| CLEAN PASS | 수정 후 처음부터 독립된 실패 유형을 다시 검증하는 절차 |

## BLOCK 33 · TRACK 10 종합 훈련

### LESSON 01 · 버그 티켓 만들기

나쁜 티켓:

```text
로그인 안 됨
```

좋은 티켓을 작성한다.

```text
환경:
앱 버전:
사용자 상태:
재현 단계:
Expected:
Actual:
빈도:
로그 request ID:
```

### LESSON 02 · 가설 3개 만들기

증상:

```text
검색 결과가 가끔 이전 검색어로 돌아감
```

가설:

```text
1. race condition
2. 캐시 키 오류
3. 화면 상태 업데이트 순서 문제
```

각 가설마다 검증 실험 하나씩 적는다.

### LESSON 03 · 회귀 범위 정하기

검색 race condition을 고쳤다면:

```text
한 번 검색
빠른 연속 검색
검색 취소
네트워크 실패
화면 이동 후 복귀
앱 재시작
```

을 서로 다른 회귀 항목으로 잡는다.

## BLOCK 34 · TRACK 10 완료 기준

다음을 할 수 있어야 한다.

- symptom과 root cause를 구분한다.
- Expected/Actual을 명확히 적는다.
- 재현 절차를 다른 사람이 따라 할 수 있게 작성한다.
- 최소 재현을 만들 수 있다.
- 사실과 가설을 구분한다.
- 한 가설에 한 실험을 연결한다.
- debugger와 breakpoint를 사용할 이유를 설명한다.
- unit/integration/E2E test의 차이를 설명한다.
- regression test가 왜 필요한지 설명한다.
- boundary value를 고를 수 있다.
- flaky test를 재실행만 해서 숨기면 안 되는 이유를 말한다.
- race condition, deadlock, 무한 반복을 서로 구분한다.
- workaround와 root fix를 구분한다.
- 실제 실행하지 않은 검증을 PASS라고 부르지 않는다.

### TRACK 끝 미니 프로젝트 · 버그를 처음부터 끝까지 고치기

작은 앱에서 실제 버그 하나를 만든다.

예:

```python
def total(price, count):
    return price + count
```

목표는 곱셈인데 코드가 덧셈이다.

다음 문서를 실제로 작성한다.

```text
1. 증상
2. Expected
3. Actual
4. 재현 단계
5. 실패 테스트
6. 원인 가설
7. 실험
8. 코드 수정
9. 같은 테스트 재실행
10. 추가 경계값 테스트
11. 회귀 테스트
12. 실제 결과 증거
```

이 프로젝트의 핵심은 `*로 바꾸는 것`이 아니다.

**버그를 증거로 재현하고 수정하고 다시 검증하는 전체 절차를 몸에 익히는 것**이다.
