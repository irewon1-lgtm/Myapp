## V1-C01. 시스템 전체 그림과 디지털 표현


**원본 Lesson 매핑:** V1-01, V1-02, V1-03


### 1. 현실 문제에서 시작하기

아침에 Galaxy에서 주식 앱을 켰는데 첫 화면은 뜨지만 종목 데이터가 비어 있다고 하자. 초보자는 흔히 “앱이 고장났다”고 한 덩어리로 생각한다. 그러나 실제 시스템은 한 덩어리가 아니다. 손가락 입력은 Android의 이벤트 처리로 들어가고, 앱 프로세스의 코드가 실행되며, 필요한 데이터가 로컬 파일이나 데이터베이스에서 읽히고, 부족하면 네트워크를 통해 서버/API에 요청을 보낸다. 서버가 응답한 바이트는 다시 네트워크 계층을 거쳐 앱으로 들어오고, 문자열과 숫자로 해석된 뒤 화면 상태가 바뀐다. 이 중 어느 한 단계만 실패해도 사용자는 똑같이 “화면이 이상하다”고 느낄 수 있다.

이 장의 목적은 컴퓨터 구조를 시험문제처럼 외우는 것이 아니다. 앞으로 앱·API·DB·Git·AI를 배울 때 길을 잃지 않도록 **시스템 지도를 머릿속에 만드는 것**이다. 어떤 오류를 보더라도 “입력 → 앱 프로세스 → 운영체제 → 저장장치/네트워크 → 외부 서비스 → 응답 → 화면”이라는 경로에 놓을 수 있으면 문제를 훨씬 빨리 좁힐 수 있다.

### 2. Mental Model

```text
사용자 입력
   ↓
[앱 UI]
   ↓  이벤트/상태 변경
[앱 프로세스]
   ↓            ↘
[운영체제]      [로컬 DB/파일]
   ↓
[네트워크 장치]
   ↓
[인터넷 / DNS / 서버 / API]
   ↓
응답 바이트 → 해석(JSON/문자/숫자) → 앱 상태 → 화면
```

이 그림에서 중요한 것은 “앱”과 “운영체제”와 “서버”를 같은 것으로 보지 않는 것이다. 앱은 사용자가 설치한 프로그램이고, 실행될 때 하나 이상의 프로세스로 존재한다. 운영체제는 프로세스가 CPU, 메모리, 파일, 네트워크 같은 자원을 안전하게 쓰도록 중재한다. 서버는 내 기기 밖에 있을 수도 있고, 같은 기기에서 로컬 서비스로 실행될 수도 있다. 클라우드는 마법의 장소가 아니라 다른 컴퓨터와 저장장치, 네트워크, 운영 소프트웨어를 묶어 제공하는 서비스다.

### 3. 핵심 개념 해부


#### 하드웨어·운영체제·앱의 경계

하드웨어는 CPU, RAM, 저장장치, 네트워크 칩처럼 실제 연산과 저장·통신을 수행하는 물리적 자원이다. 운영체제는 이 자원을 여러 앱이 안전하게 공유하도록 관리한다. 앱은 운영체제 위에서 자신의 기능을 수행한다. 예를 들어 카메라 앱이 사진을 찍을 때 앱이 센서를 직접 마음대로 조종하는 것이 아니라, 운영체제가 제공하는 드라이버와 권한 체계를 통해 접근한다.

이 구분이 실전에서 중요한 이유는 증상이 같아도 원인이 다르기 때문이다. 사진 저장이 실패했을 때 앱 코드 버그일 수도 있고, 저장공간 부족일 수도 있으며, 권한 거부나 파일 경로 문제일 수도 있다. “앱을 다시 설치하면 되겠지”는 원인을 확인하지 않은 조치다. 먼저 어느 계층이 실패했는지 증거를 수집해야 한다.


#### 프로그램·프로세스·파일

프로그램은 저장장치에 놓인 코드와 자원의 묶음이고, 프로세스는 그 프로그램이 실제로 실행 중인 상태다. 같은 앱을 종료했다 다시 켜면 같은 설치 파일을 사용하지만 새 프로세스가 생길 수 있다. 프로세스에는 현재 실행 위치, 메모리, 열린 파일, 네트워크 연결 같은 상태가 붙는다.

파일은 이름이나 확장자보다 **바이트의 연속**에 가깝다. 운영체제와 프로그램이 그 바이트를 약속된 형식으로 해석한다. `.jpg`라는 이름을 붙였다고 아무 파일이나 사진이 되지 않는 이유가 이것이다. 뒤 장에서 파일 형식과 MIME을 더 자세히 다룬다.


#### 비트·바이트·용량

비트(bit)는 0 또는 1이라는 두 상태 중 하나를 표현하는 최소 단위다. 8비트는 1바이트(byte)다. 저장공간, 네트워크 전송량, 메모리 크기를 비교할 때 단위를 통일해야 한다. 예를 들어 200MB짜리 APK, 4GB RAM, 500Mbps 인터넷은 모두 숫자가 커 보여도 서로 다른 대상을 측정한다.

또한 저장장치 제조사가 쓰는 1GB=10억 바이트와 운영체제·도구가 2진 단위를 쓰는 방식은 표시값 차이를 만든다. 실무에서는 “정확한 단위가 무엇인지”를 확인하고 비교해야 한다. 숫자 자체보다 단위와 측정대상을 먼저 읽는 습관이 중요하다.


#### 문자·Unicode·UTF-8

문자는 화면에 보이는 글자이고, 컴퓨터 내부에서는 숫자 규칙으로 표현된다. Unicode는 문자에 코드 포인트를 부여하는 표준이고, UTF-8은 그 코드 포인트를 실제 바이트열로 인코딩하는 대표적 방식이다. 그래서 `A`, `가`, `😀`은 화면에서는 각각 한 글자처럼 보여도 UTF-8에서 차지하는 바이트 수가 다를 수 있다.

이 차이는 API 길이 제한, 데이터베이스 필드 크기, 파일 크기, 문자열 자르기에서 실제 버그가 된다. “문자 수 10개니까 10바이트겠지”라고 가정하면 한글이나 이모지에서 깨질 수 있다. 더 나아가 사용자에게 한 글자로 보이는 이모지가 여러 코드 포인트로 구성되는 경우도 있기 때문에, ‘보이는 글자 수’와 ‘코드 포인트 수’와 ‘바이트 수’를 구분해야 한다.


#### 클라우드와 데이터 흐름

클라우드에 저장한다는 말은 데이터가 사라지는 것이 아니라 **내 기기 밖의 시스템으로 복제·전송·보관**된다는 뜻이다. 사진 동기화, Gmail, 웹 앱, 주식 API는 모두 요청과 응답, 인증, 저장, 네트워크에 의존한다. 따라서 클라우드 장애를 앱 자체 오류로 오인하지 않으려면 로컬 상태와 원격 상태를 나눠 봐야 한다.

예를 들어 앱은 정상 실행되고 캐시된 과거 데이터도 보이는데 새 데이터만 갱신되지 않는다면 UI나 설치파일보다 네트워크·인증·서버/API 쪽을 먼저 의심할 수 있다. 반대로 인터넷이 정상인데 앱만 시작 즉시 종료된다면 로컬 프로세스나 호환성, 저장 데이터, 권한 쪽이 우선이다.


### 3A. 개념을 연결해서 생각하기 — “보이는 화면”에서 “바이트”까지

Power User가 가장 먼저 익혀야 할 습관은 화면을 최종 결과로만 보지 않는 것이다. 화면에 `삼성전자 75,000`이 보였다면 최소한 세 종류의 표현을 거쳤다. 서버나 로컬 DB에는 숫자나 문자열 형태로 저장되어 있었고, 네트워크를 탔다면 바이트열로 전송되었으며, 앱은 그 바이트를 다시 JSON/객체/상태로 해석해 글자와 숫자로 그렸다. **보이는 값은 긴 변환 사슬의 마지막 단계**다.

이 관점을 익히면 “화면의 숫자가 틀림”을 곧바로 UI 버그라고 부르지 않는다. 원본 API부터 틀렸는지, parser에서 단위를 잘못 바꿨는지, DB에 오래된 cache가 남았는지, UI formatting에서 퍼센트와 비율을 혼동했는지 순서대로 확인할 수 있다. 한 번의 오류가 여러 계층을 지나며 다른 모양으로 보인다는 사실을 이해하는 것이 중요하다.

또 하나의 중요한 감각은 **상태(state)**다. 프로그램은 입력을 받고, 내부 상태를 바꾸고, 그 상태에 따라 출력을 만든다. 같은 버튼을 눌러도 로그인 여부, 네트워크 연결, 권한, 저장된 cache, 서버 상태가 다르면 결과가 달라진다. 그래서 버그 보고에는 버튼 이름만 적는 것이 아니라 “그 순간 상태가 무엇이었는가”를 적어야 한다.

디지털 표현에서는 “숫자가 숫자 그대로 저장된다”는 생각도 버려야 한다. 정수, 실수, 문자열은 서로 다른 규칙으로 바이트가 된다. 예를 들어 API가 `"1200"`이라는 문자열을 보내는 것과 `1200`이라는 숫자를 보내는 것은 화면에서는 같아 보일 수 있지만 정렬·계산·검증에서는 다르다. `"100" < "20"`처럼 문자열 정렬이 숫자 정렬과 다른 결과를 만들 수도 있다. 이후 데이터 장에서 타입을 배우는 이유가 여기서 시작된다.

문자도 마찬가지다. Unicode와 UTF-8을 자세히 외우는 것이 목표는 아니지만, **표현층이 있다는 것**은 반드시 기억해야 한다. 사용자가 입력한 이름이 앱에서는 정상인데 CSV로 내보낸 뒤 깨진다면 입력 자체보다 저장/열기 단계의 인코딩이 바뀌었을 수 있다. “한글이 깨졌다 → UTF-8로 바꿔라”가 아니라 어느 단계에서 어떤 바이트가 어떤 규칙으로 해석됐는지 본다.

마지막으로 클라우드를 하나의 컴퓨터처럼 생각하지 않는다. cloud API 뒤에는 인증, load balancer, application server, DB, object storage, cache가 있을 수 있다. 지금 단계에서 각각을 구현할 필요는 없지만, 장애가 “클라우드가 안 됨” 한 문장으로 끝나지 않는다는 감각을 가진다. 이 시스템 지도는 이후 API·DB·네트워크·보안의 기준 좌표가 된다.


### 4. Worked Examples


#### Worked Example A — 앱 화면이 비었을 때 계층 분리

1. **화면 자체가 열리는가?** 열리면 설치/기본 프로세스 시작은 어느 정도 성공했다.
2. **오프라인에서도 보이는 로컬 정보가 있는가?** 있으면 로컬 저장 경로는 일부 정상일 가능성이 높다.
3. **다른 앱에서 인터넷이 되는가?** 되면 기기 전체 네트워크 장애 가능성은 낮아진다.
4. **같은 서비스 웹페이지는 되는가?** 웹은 되고 앱만 안 되면 앱 인증·API 버전·앱 설정을 본다.
5. **오류 시간과 메시지를 기록한다.** `401`, `403`, `timeout`, `unknown host`처럼 보이는 단서는 서로 완전히 다른 층을 가리킨다.
6. **한 번에 하나만 바꾼다.** 앱 재설치, 공유기 재부팅, 계정 로그아웃을 동시에 해버리면 무엇이 원인이었는지 영원히 알 수 없다.

이 접근의 핵심은 정답을 찍는 것이 아니라 후보를 체계적으로 줄이는 것이다.


#### Worked Example B — 문자 수와 바이트 수

Python이나 브라우저 콘솔을 사용할 수 있다면 다음과 같은 비교를 해볼 수 있다.

```python
samples = ["ABC", "가나다", "😀"]
for s in samples:
    print(s, len(s), len(s.encode("utf-8")))
```

`ABC`는 보통 문자 수와 UTF-8 바이트 수가 같지만, 한글과 이모지는 그렇지 않다. 여기서 중요한 것은 Python 문법 암기가 아니라 **같은 문자열을 서로 다른 측정기준으로 볼 수 있다는 사실**이다. API가 “최대 20 characters”라고 썼는지 “20 bytes”라고 썼는지는 구현에 직접 영향을 준다.


### 4A. 미니 사례집 — 같은 증상, 다른 원인

**사례 1: 앱 화면이 빈다.**  
A 사용자는 비행기 모드에서도 과거 데이터가 보인다. B 사용자는 앱을 열자마자 crash한다. 둘 다 “데이터가 안 보인다”고 말하지만 A는 최신 데이터 fetch 경로, B는 process 시작/로컬 상태 경로가 우선이다.

**사례 2: 파일이 너무 크다.**  
200MB APK와 200MB RAM 사용량은 숫자와 단위가 같아도 해결법이 다르다. APK는 다운로드·저장·설치시간과 관련되고, RAM은 실행 중 메모리 압박과 관련된다. 단위를 통일하는 것과 **측정대상을 동일시하는 것**은 다르다.

**사례 3: 한글만 저장이 실패한다.**  
UI에서는 15자로 보이는데 서버가 20바이트 제한을 갖고 있다면 영문과 한글의 byte 수 차이가 문제일 수 있다. 해결 전에 서버 스펙을 확인하고, 앱 검증과 서버 검증이 같은 기준인지 맞춘다.

**사례 4: 같은 계정인데 PC 웹은 최신, 앱은 과거 데이터.**  
서버가 다르다고 단정하기 전에 앱의 local cache, sync 주기, API base URL, 로그인 account/tenant가 같은지 확인한다. “같은 서비스”가 같은 데이터 경로를 의미하지 않을 수 있다.


### 5. 그럴듯하지만 틀린 판단

1. ‘앱이 안 된다’는 한 문장만으로 앱 코드가 원인이라고 단정한다.

2. MB·GB 숫자만 비교하고 저장공간·RAM·네트워크 대역폭이라는 측정대상을 구분하지 않는다.

3. 문자 한 글자는 언제나 1바이트라고 생각한다.

4. 클라우드 저장은 내 기기와 무관하므로 로컬 네트워크나 인증 문제의 영향을 받지 않는다고 생각한다.


### 5A. 현장에서 쓰는 30초 판정표

| 질문 | YES라면 | NO라면 |
|---|---|---|
| 앱 자체가 실행되는가? | 설치/시작 단계는 일부 통과 | 설치·호환성·process 시작부터 확인 |
| 오프라인 과거 데이터는 보이는가? | local read 경로 일부 정상 | local DB/file/state 확인 |
| 다른 인터넷 앱은 정상인가? | 기기 전체 network 장애 가능성 감소 | Wi-Fi/mobile/VPN/DNS부터 |
| 웹 버전은 정상인가? | 앱 고유 설정·인증·cache 후보 증가 | 공통 backend/account 후보 증가 |
| 영문만 되고 한글/이모지만 실패하는가? | encoding/byte 제한 후보 증가 | 다른 validation 규칙 확인 |
| 문제를 재현할 수 있는가? | 가설 실험 진행 | 먼저 조건을 좁혀 재현성 확보 |

이 표는 원인을 자동으로 알려주는 표가 아니다. **다음에 확인할 가장 값싼 증거를 고르는 표**다. 한 번의 YES/NO로 결론내리지 않는다.


### 6. Guided Lab

**목표:** Galaxy에서 앱 하나가 실행되어 원격 데이터를 화면에 보여주기까지의 흐름을 8단계로 그린다.

1. 앱 아이콘을 누르는 순간을 시작점으로 적는다.
2. Android가 앱 프로세스를 시작한다고 표시한다.
3. 앱이 로컬 설정/DB를 읽는 단계를 추가한다.
4. 네트워크 요청을 만들고 DNS/인터넷을 통해 서버로 보낸다고 적는다.
5. 서버가 요청을 처리하고 응답 바이트를 보낸다.
6. 앱이 JSON/문자/숫자로 해석한다.
7. 상태가 갱신되고 UI가 다시 그려진다.
8. 각 단계 옆에 “실패했을 때 보일 증거”를 하나씩 쓴다.

**완료 증거:** 흐름도 한 장 + 실패 후보 8개 + 그중 실제로 휴대폰에서 확인할 수 있는 증거 3개.


### 7. Independent Lab

사진 파일 하나, APK 하나, RAM 용량, 인터넷 속도를 골라 모두 숫자와 단위를 기록한다. 서로 직접 비교 가능한 것과 비교 불가능한 것을 구분하고, 왜 그런지 설명한다. 이어서 `ABC`, `가나다`, 가족 이모지처럼 복합 이모지가 포함된 문자열을 골라 “보이는 글자 수/코드 포인트 감각/UTF-8 바이트 수”가 항상 같지 않음을 확인한다.


### 8. Debug Challenge

**상황:** 서버는 “닉네임 최대 20바이트”를 요구한다. 앱 개발자가 `문자 수 <= 20`만 검사했다. 영문 닉네임은 정상인데 한글·이모지 사용자는 저장 실패가 난다.

**과제:** 1) 실패를 재현한다. 2) 문자 수와 바이트 수를 각각 기록한다. 3) 원인 가설을 세운다. 4) 서버 규칙과 동일한 기준으로 검사한다. 5) 영문·한글·이모지 세 케이스를 다시 검증한다.

핵심은 “인코딩 문제”라는 말을 외우는 것이 아니라, **어떤 측정값이 서로 달랐는지 증거로 보여주는 것**이다.


### 9. AI Audit

AI에게 “앱에서 한글이 깨지는 이유를 고쳐줘”라고만 말해 답을 받은 뒤 다음을 감사한다.

- AI가 UTF-8을 무조건 정답으로 단정했는가, 실제 입력/저장/전송 인코딩을 확인했는가?
- 문자열 손실 지점이 앱, 파일, DB, API 중 어디인지 구분했는가?
- 원본 데이터를 백업하지 않고 변환부터 하라고 했는가?
- 문자 수와 바이트 수를 혼동했는가?
- 재현 케이스와 회귀테스트를 제안했는가?

AI의 답이 길고 그럴듯해도 증거와 실패지점이 없으면 승인하지 않는다.


### 10. 회상 문제

1. 프로그램과 프로세스의 차이를 휴대폰 앱 예로 설명하라.

2. 운영체제가 필요한 이유를 앱 권한 예로 설명하라.

3. RAM 8GB와 저장공간 256GB를 같은 의미로 보면 안 되는 이유는?

4. 1바이트는 몇 비트인가?

5. 문자 수와 UTF-8 바이트 수가 달라질 수 있는 이유는?

6. 클라우드 장애와 로컬 앱 장애를 구분하기 위해 먼저 볼 증거 세 가지는?

7. 확장자와 파일의 실제 바이트 내용은 어떤 관계인가?

8. 한 번에 여러 설정을 바꾸는 것이 디버깅에 나쁜 이유는?


### 11. 전이 문제

1. 메신저에서 사진은 보이는데 새 메시지만 전송되지 않는다. 시스템 지도 위에 가능한 실패지점을 최소 4개 표시하라.

2. 한국어 이름만 API 저장에 실패한다. 인코딩·바이트 제한·DB 필드 중 무엇을 어떤 순서로 검증할지 써라.

3. 앱이 오프라인에서도 과거 데이터는 보이지만 최신 데이터만 안 보인다. 설치 재시작보다 먼저 확인할 증거를 제시하라.
