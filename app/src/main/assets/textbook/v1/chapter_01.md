## V1-C01. 컴퓨터와 코드의 첫 지도

**대상:** 코딩을 처음 배우는 사람. `API`, `JSON`, `서버`, `캐시` 같은 말을 처음 듣는 사람.

**이 장의 목표:** 컴퓨터 용어를 많이 외우는 것이 아니다. 앱 화면에 값 하나가 나타나기까지 어떤 단계가 있는지 이해하고, 숫자·문자열·상태·JSON·파싱·캐시가 왜 실제 오류와 연결되는지 설명할 수 있게 되는 것이다.

---

### 1. 프로그램·코드·실행을 한 번에 잡기

컴퓨터 프로그램은 입력을 받아 정해진 규칙대로 처리하고 결과를 만든다. 계산기, 카카오톡, 주식 앱은 기능은 다르지만 이 기본 구조는 같다.

```text
입력 → 처리 → 결과
```

주식 앱에서 `AAPL`을 검색한다고 해보자.

```text
입력: AAPL
처리: 종목을 찾고 필요한 데이터를 준비함
결과: 가격과 회사 정보가 화면에 나타남
```

컴퓨터가 따라야 할 명령을 사람이 읽을 수 있는 형태로 적은 것이 **코드(code)**다. 코드가 실제로 동작하는 것을 **실행(run)**이라고 한다.

```python
print("AAPL")
```

이 한 줄은 `AAPL`이라는 값을 출력한다. 지금 중요한 것은 `print`를 외우는 것이 아니라 **코드는 실행되어야 결과가 나온다**는 점이다.

코드는 보통 위에서 아래로 흐른다.

```python
print("첫째")
print("둘째")
```

결과:

```text
첫째
둘째
```

조건문·반복문·함수처럼 실행 순서를 바꾸는 문법은 뒤에서 배운다. 이 장에서는 코드가 **값을 만들고, 바꾸고, 전달한다**는 감각만 잡으면 된다.

---

### 2. 값·타입·변수·상태 — 앱이 무엇을 기억하는가

프로그램이 다루는 실제 내용을 **값(value)**이라고 한다.

```text
1200
"1200"
"삼성전자"
true
null
```

겉으로 비슷해 보여도 값에는 종류가 있다. 이 종류를 **타입(type)**이라고 한다.

| 값 | 의미 | 대표 타입 |
|---|---|---|
| `1200` | 계산 가능한 수 | 숫자 |
| `"1200"` | 글자 네 개 | 문자열 |
| `true` | 참 | 불리언/논리값 |
| `null` | 값이 없음 | null |

여기서 가장 먼저 제대로 이해해야 할 것은 **숫자와 문자열의 차이**다.

```python
print(10 + 20)
```

결과는 `30`이다.

```python
print("10" + "20")
```

결과는 `1020`이다.

따옴표가 붙은 `"10"`은 숫자처럼 생겼지만 글자다. 사람 눈에는 거의 같아 보여도 프로그램 입장에서는 다른 데이터다.

#### 왜 이 차이가 실전에서 중요할까?

서버가 가격을 숫자로 보낼 수도 있고 문자열로 보낼 수도 있다.

```json
{"price": 1200}
```

```json
{"price": "1200"}
```

화면에는 둘 다 `1,200`처럼 표시할 수 있다. 하지만 합계·정렬·비교를 하면 결과가 달라질 수 있다.

예를 들어 문자열 정렬은 글자 순서를 비교하므로 `"100"`과 `"20"`을 숫자처럼 비교하지 않는다. 데이터 타입을 잘못 해석하면 화면은 멀쩡한데 계산만 틀리는 버그가 생길 수 있다.

#### 변수

값에 이름을 붙여 다시 사용할 수 있게 하는 것을 **변수(variable)**라고 한다.

```python
price = 1200
name = "AAPL"
```

`price`라는 이름이 숫자 `1200`을 가리키고, `name`이 문자열 `"AAPL"`을 가리킨다.

변수의 값은 바뀔 수 있다.

```python
price = 1200
price = 1250
print(price)
```

결과는 `1250`이다.

#### 상태

프로그램이 현재 기억하고 있는 상황을 **상태(state)**라고 한다.

예를 들어 주식 앱은 이런 상태를 가질 수 있다.

```text
검색어: AAPL
로딩중: 예
현재가격: 아직 없음
오류: 없음
```

잠시 뒤 서버 응답이 오면 상태가 바뀐다.

```text
검색어: AAPL
로딩중: 아니오
현재가격: 200
오류: 없음
```

화면은 보통 이 상태를 보고 다시 그려진다. 그래서 **같은 화면이라도 내부 상태가 다르면 다른 결과가 나타날 수 있다.**

이 지점이 단순한 변수 설명보다 중요하다. 실제 앱 버그를 볼 때는 “버튼을 눌렀다”만 기록하지 말고 **그 순간 어떤 상태였는가**를 함께 봐야 한다.

### 3. 실행 중 기억과 오래 남는 저장은 다르다

앱을 실행하는 동안 변수와 상태는 메모리에 존재한다. 하지만 앱을 완전히 종료했는데도 로그인 정보, 설정, 메모, 과거 데이터가 남아 있다면 그것은 어딘가에 따로 저장된 것이다.

저장 방식은 여러 가지다.

- 파일
- 앱 내부 저장소
- 데이터베이스
- 서버의 데이터베이스
- 클라우드 저장소

이 장에서 각각의 구현법을 배울 필요는 없다. 핵심은 하나다.

> **실행 중 잠깐 기억하는 상태와 앱을 꺼도 남아야 하는 데이터는 구분해야 한다.**

예를 들어 앱에서 가격이 이상하게 보일 때 이런 일이 가능하다.

```text
서버 최신가격: 200
앱에 저장된 과거가격: 180
현재 화면: 180
```

화면에 숫자가 보인다는 사실만으로 최신 데이터를 받았다고 단정할 수 없다.

파일·경로·형식은 다음 장에서 깊게 다룬다.

---

### 4. 내 앱 혼자 할 수 없는 일 — 클라이언트·서버·요청·응답

최신 주가처럼 내 휴대폰에 없는 정보가 필요하면 다른 컴퓨터와 통신해야 한다.

요청을 보내는 쪽을 **클라이언트(client)**, 요청을 받아 처리하는 쪽을 **서버(server)**라고 부른다.

```text
내 앱  ── 요청 ──>  서버
내 앱  <─ 응답 ───  서버
```

**요청(request)**은 “이 데이터를 주세요”라는 메시지이고, **응답(response)**은 서버가 돌려주는 결과다.

예:

```text
요청: AAPL 정보를 주세요.
응답: 이름 Apple, 가격 200
```

서버는 꼭 거대한 물리 컴퓨터 한 대를 뜻하지 않는다. 실무에서는 요청을 처리하는 프로그램이나 시스템 역할을 서버라고 부르는 경우가 많다.

#### API

프로그램끼리 아무 형식으로나 대화하면 서로 이해할 수 없다. 어떤 주소로 어떤 정보를 보내고 어떤 형식의 결과를 받을지 약속이 필요하다. 이 약속된 접점을 **API(Application Programming Interface)**라고 한다.

처음에는 이렇게 기억하면 충분하다.

> **API = 프로그램끼리 기능이나 데이터를 주고받는 약속된 창구**

예를 들어 서버가 다음과 같은 규칙을 제공한다고 하자.

```text
GET /stocks/AAPL
```

앱은 이 규칙에 맞춰 요청하고, 서버는 약속된 형식으로 응답한다.

API와 서버는 같은 말이 아니다.

```text
서버 = 요청을 처리하는 쪽
API  = 그 서버와 대화하는 규칙과 창구
```

### 5. JSON을 제대로 읽기

API 응답에서 매우 자주 만나는 데이터 형식이 **JSON**이다. 여기서부터는 실제로 코딩을 할 때 자주 틀리므로 조금 깊게 본다.

다음 데이터를 보자.

```json
{
  "symbol": "AAPL",
  "price": 200,
  "active": true
}
```

뜻은 단순하다.

```text
symbol → AAPL
price  → 200
active → true
```

JSON은 **이름과 값을 일정한 규칙으로 표현하는 데이터 형식**이다.

#### 이름과 값

```json
"price": 200
```

`"price"`는 이름(key), `200`은 값(value)이다.

#### 문자열과 숫자

```json
"symbol": "AAPL"
```

`"AAPL"`은 문자열이다.

```json
"price": 200
```

`200`은 숫자다.

이 차이는 앞에서 본 타입과 그대로 연결된다.

#### 참/거짓과 값 없음

```json
{
  "marketOpen": true,
  "previousClose": null
}
```

`true`는 참, `null`은 값이 없음을 표현한다.

`null`과 숫자 `0`은 같은 뜻이 아니다.

```text
0    = 값이 실제로 0
null = 값이 없음/알 수 없음/제공되지 않음
```

재무 데이터에서 누락값을 0으로 바꾸면 분석 결과가 크게 왜곡될 수 있다.

#### 여러 값을 배열로 묶기

한 종목이 아니라 여러 종목을 보낼 수 있다.

```json
[
  {"symbol": "AAPL", "price": 200},
  {"symbol": "MSFT", "price": 430}
]
```

대괄호 `[ ]`는 여러 값을 순서대로 묶는 **배열(array)**을 표현한다.

#### 중첩 구조

실제 API는 한 단계보다 깊을 수 있다.

```json
{
  "stock": {
    "symbol": "AAPL",
    "quote": {
      "price": 200,
      "currency": "USD"
    }
  }
}
```

가격을 찾으려면 구조를 단계별로 따라가야 한다.

```text
stock → quote → price
```

초보자가 API 응답에서 가장 많이 하는 실수 중 하나가 “화면에 price가 있으니 그냥 `price`를 찾으면 되겠지”라고 생각하는 것이다. 실제로는 **어느 객체 안의 어느 필드인지 경로를 확인해야 한다.**

#### JSON이 잘못되면

다음은 올바르지 않은 JSON의 예다.

```json
{
  "symbol": "AAPL",
  "price": 200,
}
```

환경에 따라 마지막 쉼표를 허용하지 않아 읽기 오류가 발생할 수 있다.

또 이런 경우도 문제다.

```json
{
  "price": "two hundred"
}
```

문법은 맞지만 프로그램이 숫자를 기대했다면 타입 오류가 생길 수 있다.

**문법이 맞는 데이터와 의미가 맞는 데이터는 별개다.**

#### JSON과 데이터베이스는 다르다

JSON은 데이터를 표현하는 형식이고, 데이터베이스는 데이터를 저장·조회·수정하도록 관리하는 시스템이다.

```text
JSON = 전달/표현 형식
DB   = 저장·조회 시스템
```

둘을 같은 것으로 생각하면 이후 API와 데이터 수집 구조를 이해하기 어렵다.

### 6. 파싱·변환·검증 — 받은 데이터를 바로 믿지 않는 이유

서버에서 JSON 텍스트가 도착했다고 앱이 즉시 숫자와 객체로 사용할 수 있는 것은 아니다. 정해진 형식을 읽어서 프로그램이 사용할 구조로 바꾸는 과정을 **파싱(parsing)**이라고 한다.

```text
서버가 보낸 JSON 텍스트
        ↓ 파싱
프로그램 안의 문자열·숫자·객체·배열
```

파싱 자체가 성공했다고 데이터가 모두 정상인 것도 아니다.

예를 들어 앱은 가격이 숫자라고 기대한다.

```json
{"price": 200}
```

그런데 서버가 다음처럼 보냈다고 하자.

```json
{"price": "200"}
```

문법상 JSON은 정상이다. 하지만 프로그램이 숫자 계산을 하려면 문자열을 숫자로 바꾸거나 오류로 처리해야 한다.

#### 변환

데이터의 타입이나 단위를 바꾸는 것을 **변환(transformation)**이라고 생각하면 된다.

```python
text_price = "200"
price = int(text_price)
```

여기서는 문자열 `"200"`을 숫자 `200`으로 바꾼다.

하지만 아무 문자열이나 숫자로 바꿀 수 있는 것은 아니다.

```python
int("two hundred")
```

이 코드는 정상 숫자로 변환할 수 없다.

#### 검증

받은 데이터가 우리가 기대한 조건을 만족하는지 확인하는 것을 **검증(validation)**이라고 한다.

예:

```text
price 필드가 존재하는가?
price가 숫자인가?
currency가 USD/KRW 중 하나인가?
날짜가 미래 값은 아닌가?
필수 값이 null은 아닌가?
```

데이터 수집 앱에서 중요한 순서는 다음과 같다.

```text
받는다 → 구조 확인 → 타입 확인 → 단위 확인 → 계산 → 저장/표시
```

이 순서를 건너뛰면 틀린 값이 정상 값처럼 앱에 들어갈 수 있다.

### 7. 캐시·상태·UI — 맞는 데이터를 받았는데 화면이 틀릴 수도 있다

**캐시(cache)**는 이미 얻은 데이터를 빠르게 다시 쓰기 위해 잠시 보관하는 방식이다.

예를 들어 앱이 어제 받은 가격 `180`을 저장해 두었다가 실행 직후 먼저 보여주고, 백그라운드에서 최신 가격 `200`을 다시 받을 수 있다.

```text
앱 시작
↓
캐시 가격 180 표시
↓
최신 데이터 요청
↓
서버 응답 200
↓
앱 상태를 200으로 변경
↓
화면을 200으로 다시 그림
```

여기에는 여러 실패 지점이 있다.

1. 서버가 200을 보냈지만 앱이 응답을 읽지 못함
2. 파싱은 성공했지만 상태를 200으로 갱신하지 않음
3. 상태는 200인데 화면이 예전 상태를 보고 있음
4. 화면은 200을 받았지만 표시 과정에서 단위를 잘못 바꿈
5. 캐시 만료 규칙이 잘못되어 180을 최신 값처럼 사용함

#### UI

사용자가 보고 누르고 입력하는 화면 부분을 **사용자 인터페이스(UI)**라고 한다.

가격이 화면에서 틀렸다고 해서 원인이 반드시 UI 코드에 있는 것은 아니다. 화면은 긴 데이터 흐름의 마지막 단계다.

```text
원본 데이터
→ 서버/API
→ 네트워크 응답
→ 파싱
→ 검증/변환
→ 앱 상태
→ 표시용 변환
→ UI
```

주가를 예로 들면 표시 직전에 이런 변환이 있을 수 있다.

```text
원본 비율: 0.153
화면 표시: 15.3%
```

만약 코드가 `0.153%`라고 표시하면 원본 데이터는 맞아도 **표시 단위 변환**이 틀린 것이다.

반대로 원본 API가 이미 틀렸다면 UI를 아무리 고쳐도 정확한 숫자가 나오지 않는다.

### 8. 바이트와 문자 인코딩 — 필요한 만큼만 이해하기

컴퓨터에 저장되는 파일과 네트워크로 전송되는 데이터는 결국 바이트 단위로 표현된다.

**비트(bit)**는 0 또는 1의 두 상태 중 하나를 나타내는 최소 단위이고, 일반적으로 8비트를 묶어 **1바이트(byte)**라고 한다.

```text
8 bit = 1 byte
```

이 장에서 이진수 계산을 할 필요는 없다. 바이트를 배우는 이유는 세 가지다.

- 파일 크기를 이해하기 위해
- 네트워크 전송량을 이해하기 위해
- 문자 깨짐을 이해하기 위해

#### 글자도 바이트로 저장된다

`A`, `가`, `😀` 같은 문자를 컴퓨터에 저장하려면 어떤 문자를 어떤 숫자로 표현할지 약속이 필요하다.

**유니코드(Unicode)**는 여러 언어의 문자에 번호를 부여하는 표준이고, **UTF-8**은 그 문자를 실제 바이트로 저장하는 대표 인코딩 방식이다.

중요한 것은 번호를 외우는 것이 아니다.

```text
문자 → 정해진 규칙으로 바이트로 저장
바이트 → 같은 규칙으로 읽으면 원래 문자로 복원
```

저장할 때와 읽을 때 규칙이 다르면 한글이 깨질 수 있다.

예를 들어 CSV가 앱에서는 정상인데 다른 프로그램에서 한글이 깨졌다면 이런 질문을 한다.

```text
파일 자체가 손상됐나?
아니면 같은 바이트를 다른 인코딩으로 읽었나?
```

이 차이는 다음 장의 파일 형식에서 다시 다룬다.

### 9. 한 숫자가 화면까지 오는 전체 경로

이제 실제 주식 앱을 기준으로 한 번에 연결해 보자.

사용자가 `AAPL`을 검색했고 화면에 `200 USD`가 표시되었다고 하자.

가능한 전체 흐름은 다음과 같다.

```text
1. 사용자가 AAPL 입력
2. 앱 상태에 검색어 저장
3. API 요청 생성
4. 서버가 종목 데이터 조회
5. JSON 응답 전송
6. 앱이 JSON 파싱
7. price가 숫자인지 검증
8. 필요한 단위 변환
9. 앱 상태를 최신 데이터로 교체
10. UI가 상태를 읽어 200 USD 표시
```

이 흐름을 이해하면 화면 숫자가 틀렸을 때 무작정 “UI 버그”라고 하지 않는다.

#### 사례 A — API가 틀린 값을 보냄

```json
{"symbol":"AAPL","price":20}
```

화면이 `20`을 정확히 표시했다면 UI는 오히려 정상이다. 원본 데이터나 서버 쪽을 확인해야 한다.

#### 사례 B — 서버는 200인데 앱이 문자열로 처리

```json
{"price":"200"}
```

화면 표시만 할 때는 정상처럼 보일 수 있다. 하지만 정렬이나 계산에서 문제가 생길 수 있다.

#### 사례 C — 최신 값은 200인데 캐시 180이 계속 보임

네트워크 요청 자체가 실패했는지, 요청은 성공했지만 상태 갱신이 실패했는지, 캐시 정책이 잘못됐는지 나눠 확인한다.

#### 사례 D — 원본 값 0.153을 0.153%로 표시

원본과 파싱은 정상인데 표시용 변환이 틀린 것이다.

이 네 사례는 **같은 “화면 숫자가 이상함”이라는 증상에도 원인이 전혀 다를 수 있다**는 것을 보여준다.

### 10. 오류를 볼 때 쓰는 첫 번째 진단표

문제가 생겼을 때 아래 순서로 “마지막으로 정상인 단계”를 찾는다.

| 확인 | 질문 | 증거 예 |
|---|---|---|
| 입력 | 사용자가 입력한 값이 앱에 들어왔나? | 검색어 로그/상태 |
| 요청 | API 요청이 만들어졌나? | 요청 로그 |
| 서버 | 서버가 응답했나? | 상태코드/응답 |
| 데이터 | 응답 구조와 타입이 맞나? | JSON 원문 |
| 파싱 | 앱이 데이터를 읽었나? | 파싱 결과 |
| 상태 | 새 값이 앱 상태에 들어갔나? | 상태 로그 |
| 표시 | UI가 최신 상태를 표시하나? | 화면/formatter 결과 |

예를 들어 응답 JSON에 `price: 200`이 있고 파싱 결과도 200인데 화면만 180이라면 서버보다 **상태·캐시·표시 단계**를 먼저 의심하는 것이 합리적이다.

이런 식으로 문제 범위를 좁히는 것을 **격리(isolation)**라고 부른다.

---

## 실습 1 — 결과를 실행 전에 예상하기

다음 코드의 결과를 먼저 생각한 뒤 실행한다.

```python
price = 100
price = 120
print(price)
```

예상 결과를 한 줄로 적는다.

다음 코드는 어떨까?

```python
print(10 + 20)
print("10" + "20")
```

두 줄이 왜 다른지 설명한다.

---

## 실습 2 — JSON 읽기

다음 JSON에서 각 질문의 답을 찾는다.

```json
{
  "stock": {
    "symbol": "AAPL",
    "quote": {
      "price": 200,
      "currency": "USD",
      "previousClose": null
    }
  }
}
```

1. 종목 코드는 무엇인가?
2. 가격은 숫자인가 문자열인가?
3. 통화는 무엇인가?
4. `previousClose`는 0이라는 뜻인가?
5. 가격을 찾는 경로를 `stock → ...` 형식으로 적어보라.

---

## 실습 3 — 어떤 단계가 의심스러운가

상황:

```text
API 원문: {"price": 200}
파싱 로그: price=200
앱 상태 로그: price=200
화면: 0.2
```

가장 먼저 어디를 확인해야 할까?

- 서버 데이터
- 네트워크 연결
- 화면 표시용 단위/변환 코드

정답은 마지막 항목이다. 앞 단계에 이미 200이라는 증거가 있기 때문이다.

---

## 실습 4 — 타입 오류 찾기

다음 두 데이터는 어떻게 다른가?

```json
{"revenue": 1500}
```

```json
{"revenue": "1500"}
```

화면에 같은 값이 보이더라도 계산 코드에서 어떤 문제가 생길 수 있는지 한 문장으로 적어본다.

---

## 실습 5 — 직접 작은 데이터 흐름 만들기

다음 코드를 실행한다.

```python
response = {"symbol": "AAPL", "price": 200}
price = response["price"]
display = str(price) + " USD"
print(display)
```

그 다음 값을 바꾼다.

```python
response = {"symbol": "MSFT", "price": 430}
```

출력이 어떻게 바뀌는지 확인한다.

마지막으로 `price`를 문자열로 바꿔본다.

```python
response = {"symbol": "MSFT", "price": "430"}
```

현재 코드는 여전히 출력될 수 있다. 그래서 **화면에 보인다는 사실만으로 타입이 정상이라고 할 수 없다**는 점을 확인한다.

## 장 끝 미니 프로젝트 — 화면의 숫자 하나를 추적하라

네가 실제 사용하는 앱에서 숫자 하나를 고른다. 주가, 방문 횟수, 점수, 일정 개수 등 무엇이든 된다.

아래 표를 채운다.

| 단계 | 내가 확인할 것 |
|---|---|
| 입력 | 어떤 행동이 이 값을 요청/변경하는가 |
| 원본 | 값은 어디서 오는가 |
| 전달 | API/파일/DB 중 무엇을 거치는가 |
| 형식 | 숫자/문자열/null 중 무엇인가 |
| 변환 | 단위나 계산이 들어가는가 |
| 상태 | 앱이 어떤 값으로 기억하는가 |
| 표시 | 최종 화면에서 어떻게 표현하는가 |

모든 칸을 실제로 알 필요는 없다. 모르는 칸에는 `모름`이라고 적는다. 중요한 것은 **화면의 결과를 한 덩어리로 보지 않고 단계로 나누는 습관**이다.

## 핵심 용어 정리

| 용어 | 이 장에서의 뜻 |
|---|---|
| 코드(code) | 컴퓨터가 수행할 명령을 사람이 읽을 수 있게 적은 것 |
| 실행(run) | 코드를 실제로 동작시키는 것 |
| 값(value) | 프로그램이 다루는 실제 데이터 |
| 타입(type) | 값의 종류 |
| 변수(variable) | 값에 붙인 이름 |
| 상태(state) | 프로그램이 현재 기억하는 상황 |
| 서버(server) | 요청을 받아 처리하고 결과를 주는 쪽 |
| API | 프로그램끼리 대화하는 약속된 창구 |
| JSON | 이름과 값을 규칙적으로 표현하는 데이터 형식 |
| 배열(array) | 여러 값을 순서대로 묶은 구조 |
| 파싱(parsing) | 정해진 형식을 읽어 프로그램이 사용할 구조로 해석하는 과정 |
| 검증(validation) | 받은 값이 기대한 구조·타입·범위를 만족하는지 확인하는 과정 |
| 캐시(cache) | 이미 얻은 데이터를 빠르게 다시 쓰기 위해 임시 보관하는 방식 |
| UI | 사용자가 보고 누르고 입력하는 화면 부분 |
| 바이트(byte) | 데이터 크기와 저장·전송에서 사용하는 기본 단위 중 하나 |
| UTF-8 | 문자를 바이트로 표현하는 대표 인코딩 방식 |
| 격리(isolation) | 정상 단계와 실패 단계를 나누어 원인 범위를 좁히는 방법 |

## 이 장을 끝내고 할 수 있어야 하는 것

다음 질문에 자기 말로 답할 수 있으면 된다.

1. 숫자 `1200`과 문자열 `"1200"`은 왜 다른가?
2. 변수와 상태는 어떤 관계가 있는가?
3. API와 JSON은 같은 것인가?
4. `null`과 `0`은 왜 다른가?
5. 파싱과 검증은 무엇이 다른가?
6. 캐시 때문에 과거 값이 화면에 남을 수 있는 이유는 무엇인가?
7. 화면 숫자가 틀렸을 때 왜 UI부터 고치면 안 되는가?
8. API 원문 → 파싱 → 상태 → 화면 흐름을 말로 설명할 수 있는가?

답하기 어려운 항목만 해당 단원으로 돌아가 다시 본다. 처음부터 장 전체를 반복해서 읽을 필요는 없다.
