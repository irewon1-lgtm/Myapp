## V1-C02. 파일과 폴더 — 경로·형식·인코딩·무결성

**대상:** 파일은 열고 옮길 수 있지만 `경로`, `확장자`, `인코딩`, `해시`, `MIME`이 실제 오류와 어떻게 연결되는지 모르는 사람.

**이 장의 목표:** 파일 문제를 “안 열려요”로 끝내지 않고 **위치 → 존재 → 권한 → 형식 → 내용 → 무결성** 순서로 좁힐 수 있게 되는 것이다.

---

### 1. 파일·폴더·경로는 한 묶음으로 이해한다

파일은 저장된 데이터이고, 폴더는 파일을 정리하는 공간이다. 개발에서 더 중요한 것은 **파일 이름만이 아니라 정확한 위치**다.

```text
MyApp/
  app/
    config.json
  backup/
    config.json
```

두 파일은 이름이 같지만 다른 파일이다.

파일의 위치를 표현한 주소를 **경로(path)**라고 한다.

```text
MyApp/app/config.json
```

AI에게 “config.json을 고쳐줘”라고만 하면 잘못된 파일을 수정할 수 있다. 실제 작업에서는 가능한 한 경로까지 지정한다.

#### 절대경로와 상대경로

**절대경로(absolute path)**는 시작 지점부터 전체 위치를 적는다.

```text
/storage/emulated/0/Download/report.csv
```

**상대경로(relative path)**는 현재 기준 위치에서부터 적는다.

```text
data/report.csv
```

상대경로가 특히 많이 문제를 만든다. 같은 코드라도 프로그램의 **현재 작업 폴더(working directory)**가 다르면 다른 위치를 찾기 때문이다.

```python
path = "data/report.csv"
```

현재 위치가 `MyApp/`이면 `MyApp/data/report.csv`를 찾지만, 현재 위치가 `MyApp/tools/`라면 `MyApp/tools/data/report.csv`를 찾을 수 있다.

그래서 `File not found`가 나오면 파일을 다시 만들기 전에 세 가지를 본다.

```text
1. 프로그램의 현재 작업 폴더는 어디인가?
2. 코드가 계산한 최종 경로는 무엇인가?
3. 그 경로에 파일이 실제로 존재하는가?
```

`./`는 현재 폴더, `../`는 한 단계 위 폴더를 가리킬 때 자주 쓰인다. 기호 자체를 외우는 것보다 **상대경로는 기준 위치가 필요하다**는 점이 핵심이다.

---

### 2. 확장자와 실제 파일 형식은 다르다

파일 이름 끝의 `.txt`, `.csv`, `.png`, `.zip`, `.apk` 같은 부분을 **확장자(extension)**라고 한다.

확장자는 파일 종류를 짐작하는 데 도움을 주지만 실제 내용을 바꾸지는 않는다.

```text
photo.png → 이름만 photo.jpg로 변경
```

이름은 JPG처럼 보이지만 내부 데이터가 자동으로 JPEG 형식으로 변환되지는 않는다.

```text
이름 변경 ≠ 형식 변환
```

실제 형식 변환은 원본을 읽고 다른 형식 규칙으로 다시 저장하는 과정이 필요하다.

#### 텍스트와 바이너리

JSON·CSV·TXT는 보통 사람이 글자로 읽을 수 있는 **텍스트 파일**이다. 이미지·ZIP·APK는 특정 규칙으로 해석해야 하는 **바이너리(binary) 파일**이다.

ZIP을 텍스트 편집기로 열었는데 이상한 글자가 나온다고 파일이 깨진 것은 아니다. 도구가 파일 형식을 이해하지 못한 것이다.

#### MIME type

웹이나 앱이 데이터를 주고받을 때 파일 종류를 알려주는 정보로 **MIME type**을 사용한다.

```text
text/plain
text/csv
application/json
image/png
```

확장자, MIME, 실제 바이트 내용은 서로 맞는 것이 정상적이다. 업로드가 거절되거나 브라우저가 이상하게 처리하면 셋을 함께 확인한다.

### 3. 텍스트 파일에서 가장 흔한 실제 문제 — 인코딩

텍스트도 저장될 때는 바이트가 된다. 문자를 어떤 바이트로 저장하고 다시 어떻게 글자로 읽을지 규칙이 필요한데, 이것이 **문자 인코딩(character encoding)**이다.

UTF-8은 현재 매우 널리 쓰이는 인코딩 방식이다.

문제는 저장할 때와 읽을 때 다른 규칙을 쓰면 생긴다.

```text
원래: 안녕하세요
잘못 해석: ì•ˆë…•í•˜ì„¸ìš”
```

이런 현상을 봤을 때 파일명을 바꾸는 것은 해결책이 아니다.

확인 순서는 다음과 같다.

```text
1. 파일이 어떤 인코딩으로 저장됐는가?
2. 읽는 프로그램은 어떤 인코딩으로 열고 있는가?
3. 중간 변환 과정에서 다시 저장되지는 않았는가?
```

#### CSV에서 특히 자주 생기는 이유

CSV는 단순한 텍스트 파일이다. Excel 같은 프로그램이 자동 추정으로 인코딩과 구분자를 판단하면, 작성 프로그램과 해석 방식이 달라져 한글이나 열 구분이 깨질 수 있다.

예:

```csv
name,revenue,margin
A회사,1200,13.2
```

확인해야 할 것은 파일명이 아니라:

- 문자 인코딩
- 구분자(쉼표/세미콜론/탭 등)
- 따옴표 처리
- 줄바꿈 방식
- 헤더와 열 수

이다.

### 4. CSV·JSON·ZIP을 같은 종류로 생각하면 안 된다

이 세 파일은 역할이 완전히 다르다.

| 형식 | 주된 역할 | 사람이 바로 읽기 |
|---|---|---|
| CSV | 표 데이터 표현 | 비교적 쉬움 |
| JSON | 구조화된 데이터 표현 | 비교적 쉬움 |
| ZIP | 여러 파일 묶음/압축 | 전용 도구 필요 |

#### CSV

```csv
symbol,price
AAPL,200
MSFT,430
```

행과 열 중심이다.

#### JSON

```json
{
  "symbol": "AAPL",
  "quote": {
    "price": 200,
    "currency": "USD"
  }
}
```

중첩 구조와 타입을 표현하기 좋다.

#### ZIP

ZIP은 여러 파일을 하나의 묶음으로 만들고 압축할 수 있다. ZIP을 풀면 내부에 원래 파일들이 다시 나온다.

중요한 구분:

```text
압축(compression) = 크기를 줄이거나 여러 파일을 묶는 목적
인코딩(encoding)  = 데이터를 다른 표현 규칙으로 바꾸는 것
암호화(encryption)= 키 없이는 내용을 이해하기 어렵게 만드는 것
```

Base64는 인코딩이지 암호화가 아니다. ZIP도 기본적으로 “ZIP이니까 안전하다”는 뜻이 아니다.

### 5. 파일이 있는데도 못 읽는 이유 — 권한과 잠금

파일 경로가 맞고 실제로 존재해도 읽거나 쓸 수 없을 수 있다.

대표 원인:

- 현재 앱/사용자에게 읽기 권한이 없음
- 쓰기 권한이 없음
- Android에서 해당 파일 접근 권한이 만료됨
- 다른 프로그램이 파일을 잠그고 있음
- 읽기 전용 위치에 쓰려고 함

따라서 `Permission denied`는 “파일이 없다”와 다른 문제다.

```text
File not found      → 위치/존재 문제 가능성
Permission denied   → 권한 문제 가능성
Unsupported format  → 형식 문제 가능성
Decode error        → 인코딩/형식 문제 가능성
```

오류 메시지를 한 덩어리로 보지 않고 종류를 나누는 습관이 중요하다.

Android에서는 보안 때문에 앱마다 접근 가능한 저장공간이 제한될 수 있다. 그래서 PC에서 익숙한 임의 절대경로를 앱 코드에 박아 넣는 방식이 항상 안전하지 않다.

### 6. 해시 — 파일이 같은지 확인하는 강한 방법

파일 이름과 크기가 같아도 내용이 같은 파일이라는 보장은 없다.

파일 전체 내용을 계산해 고정 길이의 값으로 만든 것을 **해시(hash)**라고 한다. 배포 파일 검증에서 자주 사용하는 알고리즘 중 하나가 **SHA-256**이다.

예를 들어 어떤 APK의 SHA-256이 다음과 같다고 하자.

```text
A1B2...9F
```

다시 받은 APK의 해시가 정확히 같다면 실무적으로 **같은 바이트 내용**이라는 매우 강한 근거가 된다.

#### 해시가 알려주는 것과 알려주지 않는 것

해시가 같으면:

- 다운로드 전후 파일이 같은지 비교할 수 있다.
- 어느 빌드 산출물인지 식별하는 데 도움이 된다.

하지만 해시만으로는:

- 파일이 악성인지
- 믿을 수 있는 제작자가 만들었는지
- 앱 서명이 정상인지

를 보장하지 않는다.

```text
무결성(integrity) ≠ 신뢰성(trust)
```

그래서 실제 앱 배포에서는 해시 외에도 출처와 서명 확인이 중요하다.

### 7. 안전한 파일 작업 — 삭제와 덮어쓰기를 조심한다

파일 자동화에서 가장 위험한 것은 코드가 실패하는 것보다 **잘못된 파일을 성공적으로 삭제하거나 덮어쓰는 것**이다.

예를 들어 AI가 다음 명령을 만들었다고 하자.

```text
삭제 대상: /some/path/*
```

실행 전에 최소한 확인한다.

```text
현재 위치는 어디인가?
대상 경로를 정확히 계산했는가?
몇 개 파일이 대상인가?
원본 백업이 있는가?
삭제 대신 이동/복사로 먼저 시험할 수 있는가?
```

#### 안전한 자동화 패턴

파일 이름을 대량 변경한다고 하자.

바로 변경하지 말고:

```text
1. 대상 목록 출력
2. 새 이름 미리보기
3. 충돌 여부 확인
4. 작은 샘플 2~3개로 시험
5. 전체 실행
6. 결과 개수와 오류 확인
```

이런 **미리보기(dry run) → 작은 실행 → 전체 실행** 순서가 안전하다.

이 방식은 2025년 이후 실용 입문서들이 강조하는 “실제 작업을 하되 작은 단계로 검증한다”는 흐름과도 맞는다.

---

### 8. 파일 문제를 6단계로 진단한다

파일 문제는 다음 순서로 보면 빠르다.

```text
1. 존재
2. 경로
3. 권한
4. 형식
5. 내용 해석
6. 무결성/출처
```

#### 사례 A — AI가 파일을 만들었다는데 안 보임

먼저 “파일 이름”을 찾는 게 아니라 실제 생성 경로를 확인한다. 생성 도구가 다른 작업 공간에 저장했을 수 있다.

#### 사례 B — CSV 한글이 깨짐

파일 존재와 경로는 정상이다. 그 다음 인코딩과 가져오기 방식을 본다.

#### 사례 C — `.png`를 `.jpg`로 이름만 바꿨더니 오류

확장자와 실제 내부 형식이 다르다. 올바른 이미지 변환이 필요하다.

#### 사례 D — 다운로드한 APK가 이전 파일과 같은지 확인

이름과 크기보다 SHA-256을 비교한다. 설치 신뢰성은 앱 서명과 출처도 별도로 확인한다.

#### 사례 E — 파일은 존재하지만 앱이 읽지 못함

`Permission denied`나 Android URI 권한 문제인지 본다. 파일을 새로 만드는 것은 첫 해결책이 아니다.

## 실습 2 — 파일 이름과 형식 구분

다음 판단이 맞는지 틀리는지 말한다.

1. `photo.jpg`라는 이름이면 실제 데이터도 반드시 JPEG다.
2. ZIP을 텍스트 편집기로 열어 글자가 깨지면 ZIP은 반드시 손상됐다.
3. JSON 파일도 실제 내용이 JSON 문법에 맞는지 확인해야 한다.
4. Base64는 암호화이므로 비밀번호를 숨기는 데 안전하다.

정답: 1 틀림 / 2 틀림 / 3 맞음 / 4 틀림.

## 실습 4 — CSV 검증

파일:

```csv
name,revenue,margin
A,1200,12.5
B,900,
C,"1,400",15.1
```

질문:

1. B의 margin은 0인가, 값이 비어 있는가?
2. C의 revenue를 단순 쉼표 분리하면 어떤 문제가 생길 수 있는가?
3. revenue 단위가 원인지 백만원인지 파일만 보고 확정할 수 있는가?

핵심은 **파일이 열렸다는 것과 데이터 의미가 검증됐다는 것은 다르다**는 점이다.

## 핵심 용어

| 용어 | 뜻 |
|---|---|
| 경로(path) | 파일 위치를 표현한 주소 |
| 절대경로 | 시작 지점부터 전체 위치를 적은 경로 |
| 상대경로 | 현재 기준 위치에서 적은 경로 |
| working directory | 상대경로 계산의 기준이 되는 현재 작업 폴더 |
| 확장자(extension) | 파일 이름 끝의 종류 힌트 |
| MIME type | 전달되는 데이터 종류를 나타내는 정보 |
| 인코딩 | 문자와 바이트 사이의 표현 규칙 |
| CSV | 표 데이터를 텍스트로 표현하는 형식 |
| JSON | 구조화된 데이터를 표현하는 형식 |
| ZIP | 여러 파일을 묶거나 압축하는 대표 형식 |
| 해시(hash) | 파일 내용으로 계산한 고정 길이 지문 |
| SHA-256 | 무결성 비교에 자주 쓰는 해시 알고리즘 |
| 무결성 | 내용이 의도치 않게 바뀌지 않았는지에 관한 성질 |

## 이 장을 끝내고 할 수 있어야 하는 것

1. 파일 이름과 경로가 왜 다른지 설명할 수 있다.
2. 상대경로 오류에서 working directory를 확인해야 하는 이유를 말할 수 있다.
3. 확장자 변경과 실제 형식 변환이 다르다는 것을 설명할 수 있다.
4. 인코딩 오류와 파일 손상을 구분할 수 있다.
5. CSV·JSON·ZIP의 역할 차이를 말할 수 있다.
6. `Permission denied`와 `File not found`를 같은 문제로 취급하지 않는다.
7. 해시가 무엇을 보장하고 무엇을 보장하지 않는지 말할 수 있다.
8. 대량 파일 변경 전에 미리보기·샘플 시험·복구 경로를 준비할 수 있다.
