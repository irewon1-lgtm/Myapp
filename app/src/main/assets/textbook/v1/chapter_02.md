## V1-C02. 파일·경로·형식·무결성

**원본 Lesson 매핑:** V1-04, V1-05, V1-06

### 1. 현실 문제에서 시작하기

파일을 “이름이 붙은 문서” 정도로 이해하면 실제 작업에서 계속 막힌다. AI가 ZIP을 만들었다는데 어디에 생겼는지 못 찾고, `.png`를 `.jpg`로 이름만 바꿨는데 이미지가 깨지며, 다운로드한 APK가 같은 파일인지 확인할 방법도 없다. 앱 개발에서도 경로 하나가 틀리면 정상 코드가 파일을 못 찾고, 확장자와 실제 형식이 다르면 업로드 서버가 거절한다.

이 장에서는 파일을 **위치(path) + 바이트(content) + 해석 규칙(format/MIME) + 무결성(hash)**으로 본다. 이 네 요소를 분리하면 “파일이 없다”, “파일은 있는데 못 연다”, “열리지만 내용이 깨졌다”, “전송 중 바뀌었다”를 서로 다른 문제로 진단할 수 있다.

### 2. Mental Model

```text
사용자가 보는 이름
  └─ report.csv
       │
       ├─ 경로: /Download/report.csv
       ├─ 실제 바이트: 72 65 70 6f ...
       ├─ 형식 규칙: CSV 텍스트
       ├─ MIME: text/csv (환경에 따라 다를 수 있음)
       └─ SHA-256: 내용 동일성 확인용 지문
```

**상대경로**는 현재 작업 위치를 기준으로 해석되고, **절대경로**는 루트부터 위치를 지정한다. 문제는 프로그램마다 “현재 작업 위치”가 다를 수 있다는 점이다. 따라서 자동화·빌드·테스트에서는 “내 컴퓨터에서는 됨”을 피하려면 경로를 명시적으로 다뤄야 한다.

### 3. 핵심 개념 해부

#### 경로를 위치 식별자로 보기

경로는 파일 이름과 다르다. 같은 `config.json`이라는 이름이 여러 폴더에 동시에 존재할 수 있다. 절대경로는 전체 위치를 지정해 모호함이 적지만 환경이 바뀌면 깨질 수 있고, 상대경로는 프로젝트 이동에 유리하지만 현재 작업 디렉터리를 잘못 가정하면 실패한다. `.`은 현재 위치, `..`는 상위 위치를 뜻하는 식의 규칙도 shell·운영체제의 경로 해석과 연결된다.

실무에서는 경로 문자열을 눈으로만 보지 말고 “프로그램이 실제로 어느 디렉터리를 기준으로 계산했는가”를 확인해야 한다. 로그에 최종 해석된 경로를 출력하는 것만으로도 많은 파일 오류가 즉시 드러난다.

#### 확장자·MIME·실제 내용

확장자는 주로 사람이 파일 종류를 추측하기 쉽게 붙이는 이름의 일부다. 확장자가 실제 데이터를 변환하지는 않는다. PNG 바이트를 가진 파일 이름을 `.jpg`로 바꿔도 JPEG 데이터가 되는 것은 아니다. 프로그램은 확장자, 파일 시그니처, MIME, 내부 구조를 이용해 형식을 판별할 수 있다.

MIME type은 네트워크나 앱 간 전달에서 “이 데이터는 어떤 종류로 해석해야 하는가”를 설명하는 메타데이터다. 잘못된 MIME은 브라우저나 서버가 파일을 다른 방식으로 처리하게 만들 수 있다. 따라서 업로드 오류를 볼 때 파일 이름뿐 아니라 서버가 받은 Content-Type과 실제 바이트를 같이 봐야 한다.

#### 텍스트와 바이너리

텍스트 파일도 결국 바이트지만 문자 인코딩 규칙에 따라 해석한다. 바이너리 파일은 이미지, 압축파일, 실행파일처럼 특정 포맷 구조를 가진다. 텍스트 편집기로 ZIP을 열어 글자가 깨진다고 파일이 손상된 것은 아니다. 반대로 바이너리 파일을 텍스트처럼 읽고 다시 저장하면 바이트가 변해 실제로 손상될 수 있다.

이 구분은 Git, API, 데이터 처리에서도 중요하다. JSON·CSV는 보통 텍스트이고, APK·ZIP·이미지는 바이너리다. 자동화 스크립트가 파일을 어떤 모드로 읽고 쓰는지 확인해야 한다.

#### 압축·인코딩·암호화 구분

압축은 중복을 줄여 데이터 크기를 줄이는 것이고, 인코딩은 표현 방식을 바꾸는 것이며, 암호화는 키 없이는 내용을 이해하기 어렵게 만드는 보안 변환이다. ZIP은 여러 파일 묶음과 압축을 제공하지만 ZIP이라고 해서 자동으로 보안이 확보되는 것은 아니다. Base64는 흔히 인코딩일 뿐 암호화가 아니다.

이 셋을 혼동하면 “Base64로 숨겼으니 안전하다”, “ZIP이니까 원본과 동일하다” 같은 잘못된 결론이 나온다. 목적이 크기 감소인지, 전송 호환성인지, 기밀성인지 먼저 정해야 한다.

#### 해시와 무결성

SHA-256 같은 해시 함수는 임의 길이 입력을 고정 길이 값으로 요약한다. 원본 바이트가 조금만 달라져도 일반적으로 완전히 다른 해시가 나온다. 그래서 다운로드 전후 파일이 같은지, 빌드 산출물이 정확히 어떤 것인지 식별하는 데 유용하다.

해시는 “파일이 안전하다”를 증명하지 않는다. 악성 파일도 해시를 가질 수 있다. 해시는 **내가 비교하려는 기준 파일과 동일한 바이트인지** 확인하는 도구다. 신뢰할 수 있는 출처의 기대 해시가 있어야 의미가 커진다.

### 3A. 개념을 연결해서 생각하기 — “파일이 있다”는 말의 다섯 가지 의미

실무에서 “파일이 있다”는 말은 모호하다. 디렉터리 목록에 이름이 보인다는 뜻일 수도 있고, 읽을 권한이 있다는 뜻일 수도 있으며, 프로그램이 기대한 형식으로 해석된다는 뜻일 수도 있다. 실제로는 다음 조건이 모두 맞아야 사용 가능한 파일이 된다.

1. 프로그램이 계산한 경로가 맞다.
2. 그 경로에 항목이 존재한다.
3. 현재 사용자/process가 읽거나 쓸 권한이 있다.
4. 바이트 내용이 기대한 format과 일치한다.
5. 파일이 손상되지 않았고, 필요한 경우 기대 버전과 동일하다.

이 다섯 단계를 분리하면 `FileNotFound`, `Permission denied`, `Unsupported format`, checksum mismatch가 서로 다른 오류라는 것이 명확해진다. 초보자가 흔히 하는 실수는 이 모든 문제를 “파일이 깨졌다”로 부르는 것이다.

경로 설계에서는 **누가 경로를 결정해야 하는가**도 중요하다. 앱 내부 리소스라면 프로젝트/패키지 기준 경로가 적절할 수 있고, 사용자가 고르는 문서라면 OS의 파일 선택기를 통해 URI/handle을 받는 편이 안전하다. 사용자 기기의 `/storage/...` 같은 절대경로를 코드에 박는 것은 환경 의존성을 크게 만든다.

파일 형식은 “어떻게 읽을지”에 대한 계약이다. CSV는 구분자, quote, newline, encoding 규칙에 따라 같은 텍스트라도 다르게 해석될 수 있다. JSON은 구조와 타입이 있고, ZIP은 내부 directory entry와 압축 데이터가 있다. “확장자”는 계약의 힌트일 뿐 계약 자체가 아니다. 서버 업로드에서는 MIME/Content-Type이 또 하나의 힌트가 된다.

무결성은 **같음(sameness)**을 다룬다. SHA-256이 동일하면 실무적으로 같은 바이트라고 판단하는 데 매우 강한 근거가 되지만, “신뢰할 수 있음(trustworthiness)”과는 다르다. 공격자가 만든 파일의 해시도 계산할 수 있다. 따라서 배포에서는 해시뿐 아니라 서명, 출처, TLS, release provenance 같은 신뢰 사슬이 추가된다. 이 장에서는 그 차이를 인식하는 수준까지 배운다.

압축과 인코딩을 구분하는 것도 중요하다. Base64는 binary를 텍스트 채널에 안전하게 실어 보내기 위해 표현을 바꾸지만 크기가 오히려 커질 수 있다. ZIP/GZIP은 크기를 줄이는 목적이 주다. 암호화는 기밀성을 위한 것이고 별도의 키 관리가 필요하다. “변환됐다”는 공통점 때문에 셋을 한 종류로 보면 보안판단을 잘못한다.

### 4. Worked Examples

#### Worked Example A — 경로 오류

프로그램이 `./data/report.csv`를 읽는다고 하자. 터미널에서 프로젝트 폴더에 있을 때는 성공하지만 IDE에서 실행하면 실패한다. 이유는 `./`가 파일이 있는 위치가 아니라 **프로세스의 현재 작업 디렉터리**를 기준으로 해석되기 때문이다.

진단 순서:
1. 현재 작업 디렉터리를 출력한다.
2. 프로그램이 계산한 전체 경로를 출력한다.
3. 그 경로에 파일이 실제 존재하는지 확인한다.
4. 프로젝트 루트 기준 경로가 필요한지, 사용자 선택 파일이 필요한지 설계를 다시 결정한다.

#### Worked Example B — 확장자만 바꾸기

`photo.png`를 복사해 이름만 `photo.jpg`로 바꾼 뒤 이미지 정보 도구나 MIME 판별 도구로 확인한다. 이름은 JPG처럼 보이지만 실제 내부 형식은 PNG인 것을 확인할 수 있다. 올바른 변환은 디코딩한 픽셀 데이터를 JPEG 인코더로 다시 쓰는 과정이다.

이 예제는 “이름”과 “내용”을 분리하는 감각을 만든다. API 업로드, 파일 공유, 썸네일 생성에서 같은 원리가 반복된다.

### 4A. 미니 사례집

**사례 1 — AI가 파일을 만들었다는데 못 찾음**  
파일명을 다시 묻기 전에 출력된 실제 sandbox path와 현재 conversation attachment 여부를 확인한다. 파일 제목과 실제 filesystem path를 같은 것으로 보지 않는다.

**사례 2 — CSV가 Excel에서 한글 깨짐**  
확장자는 맞다. 이제 encoding, delimiter, BOM 필요성, Excel의 import 방식, 실제 byte를 본다. 파일명을 `.xlsx`로 바꾸는 것은 해결이 아니다.

**사례 3 — APK 재다운로드 후 같은 파일인지 궁금함**  
크기와 이름을 비교하는 것보다 SHA-256을 계산한다. 공식 release hash 또는 이전에 기록한 hash와 비교한다. 앱 서명 검증은 별도 단계다.

**사례 4 — ZIP은 풀리지만 내부 한 파일만 손상**  
archive 생성 전/후 각 파일 해시를 비교하고, 전송 중 변형인지 압축 전 원본이 이미 손상됐는지 구분한다.

### 5. 그럴듯하지만 틀린 판단

1. 상대경로는 언제나 파일이 있는 폴더 기준이라고 생각한다.
2. 확장자를 바꾸면 실제 포맷도 변환된다고 생각한다.
3. Base64를 암호화라고 생각한다.
4. 해시가 같다는 사실을 ‘안전한 파일’이라는 보안 보증으로 오해한다.

### 5A. 파일 문제 진단표

`존재 → 경로해석 → 권한 → 형식 → 무결성 → 신뢰` 순서로 본다.

- **존재하지 않음:** 생성 단계/다운로드 단계 확인.
- **존재하지만 못 찾음:** working directory와 path 계산 확인.
- **찾지만 못 읽음:** permission, lock, URI grant 확인.
- **읽지만 해석 실패:** format, MIME, encoding, version 확인.
- **해석되지만 내용 불일치:** checksum/hash, source data 확인.
- **내용 동일하지만 신뢰 불명:** signature/source/provenance 확인.

이 순서는 “파일 문제”를 한 종류로 뭉치지 않게 한다.

### 5B. 실전에서 자주 만나는 경계조건

경로 문제는 운영체제마다 구분자와 대소문자 처리 차이가 있을 수 있다. 개발자가 Windows에서 만든 프로젝트가 Linux CI에서만 깨지는 대표 이유 중 하나가 파일 이름 대소문자다. `Logo.png`와 `logo.png`를 같은 것으로 취급하는 환경과 다른 것으로 취급하는 환경이 섞이면 배포 뒤에만 오류가 나타날 수 있다. 따라서 파일명 규칙을 단순하게 유지하고 CI 환경에서도 검증한다.

공백·한글·특수문자가 포함된 경로도 도구마다 quoting 규칙이 다르다. shell에서는 공백이 인자 구분으로 해석될 수 있어 `"My Files/report.csv"`처럼 적절한 quoting이 필요하다. AI가 경로를 문자열로 만들어줄 때 실제 대상 경로와 quoting이 맞는지 확인한다.

CSV와 JSON 같은 텍스트 형식은 “열리느냐”만으로 성공을 판단하지 않는다. 숫자열이 문자열로 들어갔는지, 날짜 timezone이 사라졌는지, NULL과 빈문자열이 섞였는지 확인해야 한다. 파일 형식은 구조와 의미를 함께 전달한다.

큰 파일에서는 전체를 메모리에 한 번에 읽는 방식이 문제를 만들 수 있다. 수 GB 로그를 단순 `read()`하면 메모리가 부족할 수 있으므로 streaming/line-by-line 처리 같은 방식이 필요하다. 이 원리는 나중의 데이터 처리와 API streaming에도 연결된다.

해시를 기록할 때는 **어떤 시점의 어떤 파일**인지 같이 남긴다. `final.apk` 같은 이름만 있으면 새 빌드가 덮어쓴 뒤 예전 hash와 연결이 끊긴다. version, commit SHA, build timestamp, file hash를 같이 기록하면 산출물 provenance가 훨씬 명확해진다.

### 6. Guided Lab

**ZIP 무결성 실습**

1. 텍스트 파일 두 개와 작은 이미지를 한 폴더에 넣는다.
2. 압축 전 각 파일 SHA-256을 기록한다.
3. ZIP을 만든다.
4. 다른 폴더에 압축을 푼다.
5. 압축 해제된 각 파일의 SHA-256을 다시 계산한다.
6. 동일/불일치를 표로 정리한다.
7. 파일 하나를 한 글자 수정한 뒤 해시가 어떻게 바뀌는지 확인한다.

완료 증거는 `원본 해시 / 해제 후 해시 / 수정 후 해시` 3열 표다.

### 7. Independent Lab

경로가 포함된 작은 프로젝트를 새 폴더로 복사한 뒤 어디가 깨지는지 확인한다. 절대경로를 하드코딩한 케이스와 프로젝트 상대경로를 쓴 케이스를 비교하고, 어떤 경로 전략이 이 프로젝트에 적합한지 이유를 적는다.

### 8. Debug Challenge

**상황:** 파일 업로드 API가 `unsupported media type`을 반환한다. 개발자는 확장자가 `.jpg`라서 서버 버그라고 주장한다.

증거를 수집하라: 실제 파일 시그니처/메타데이터, MIME/Content-Type, 서버가 기대하는 형식. 수정은 파일을 실제 포맷으로 변환하거나 올바른 MIME을 전송하는 최소 변경이어야 한다. 확장자만 다시 바꾸는 것은 허용하지 않는다.

### 9. AI Audit

AI에게 “이 APK가 다운로드 중 손상됐는지 확인하는 방법”을 물어본다. 답에서 다음을 검사한다.

- SHA-256처럼 내용 비교가 가능한 방법을 제안하는가?
- 비교 기준이 될 신뢰할 수 있는 해시가 필요하다는 점을 말하는가?
- 파일 크기만 같으면 동일하다고 단정하지 않는가?
- 해시 검증과 앱 서명 검증을 같은 것으로 혼동하지 않는가?
- 원본을 덮어쓰기 전에 보존하도록 하는가?

추가로 AI가 제시한 명령이 원본 파일을 덮어쓰는지, 해시 비교 대상이 같은 빌드·같은 출처인지, MIME/확장자만 보고 포맷을 단정하지 않았는지 확인한다. 변환이 필요하면 반드시 복사본에서 수행하고 변환 전후 hash와 실제 열기 결과를 함께 남긴다.
