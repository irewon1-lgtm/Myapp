# TRACK 02 · 파일과 폴더를 처음부터

TRACK 01에서 컴퓨터가 정보를 저장할 때 파일이라는 단위를 사용한다는 것을 배웠다.

이번 TRACK은 파일을 실제로 이해하는 과정이다.

특히 다음 말을 **처음 듣는 사람**을 기준으로 한다.

- 경로
- 확장자
- 형식
- 바이트
- 인코딩
- Unicode
- UTF-8
- 압축
- 무결성
- 해시
- SHA-256

이 단어들을 한 문장에 몰아넣지 않는다. 하나씩 뜻을 만든 뒤 다음 단어로 간다.

---

## BLOCK 01 · 파일을 다시 정확히 잡기

### LESSON 01 · 파일은 왜 필요한가

컴퓨터를 껐다 켜도 남겨야 하는 정보가 있다.

예를 들어:

- 사진
- 메모
- 동영상
- 문서
- 프로그램을 이루는 자료

이런 정보를 저장해서 다시 찾을 수 있어야 한다.

컴퓨터는 저장된 정보를 **파일(file)**이라는 단위로 다룰 수 있다.

한 줄 뜻:

> 파일 = 저장된 정보를 이름 있는 하나의 단위로 다루는 것

### LESSON 02 · 파일 이름

파일에는 보통 사람이 구분하기 위한 이름이 있다.

```text
가족사진.jpg
계약서.pdf
메모.txt
```

`가족사진`, `계약서`, `메모` 같은 부분은 사람이 파일을 찾기 쉽게 붙인 이름이다.

그런데 뒤에 붙은 `.jpg`, `.pdf`, `.txt`는 무엇일까?

곧 **확장자**라는 이름으로 배운다.

---

## BLOCK 02 · 폴더와 정리

### LESSON 01 · 파일이 너무 많아지면

파일이 열 개면 이름만 보고 찾을 수 있다. 파일이 십만 개라면 어렵다.

그래서 파일을 묶어 정리하는 **폴더(folder)**를 사용한다.

```text
문서
 ├─ 계약
 ├─ 세금
 └─ 공부
```

폴더 안에 다른 폴더를 넣을 수도 있다.

### LESSON 02 · 같은 이름의 파일도 다른 폴더에 있을 수 있다

다음 두 파일은 이름은 같지만 위치가 다르다.

```text
여행/사진.jpg
가족/사진.jpg
```

`사진.jpg`라는 이름만으로는 어떤 파일인지 충분하지 않을 수 있다.

그래서 **어디에 있는 파일인지 나타내는 방법**이 필요하다.

그게 다음 BLOCK의 `경로`다.

---

## BLOCK 03 · 경로란 무엇인가

### LESSON 01 · 파일의 주소

**경로(path)**는 파일이나 폴더가 어디에 있는지 나타내는 위치 정보다.

처음에는 `파일의 주소`처럼 생각하면 쉽다.

예:

```text
사진/가족/2026/생일.jpg
```

사람말로 읽으면:

```text
사진 폴더 안의
가족 폴더 안의
2026 폴더 안의
생일.jpg 파일
```

한 줄 뜻:

> 경로 = 파일이나 폴더의 위치를 나타내는 정보

### LESSON 02 · `/`와 `\`가 보이는 이유

운영체제와 상황에 따라 폴더를 나누는 표시가 다르게 보일 수 있다.

예:

```text
photos/family/baby.jpg
```

또는 Windows에서:

```text
C:\photos\family\baby.jpg
```

지금은 슬래시의 모든 규칙을 외우지 않는다.

핵심은 **경로가 여러 폴더를 차례로 지나 파일의 위치를 나타낸다**는 것이다.

---

## BLOCK 04 · 절대 경로와 상대 경로

### LESSON 01 · 출발점부터 모두 적는 방법

어떤 위치를 처음부터 끝까지 분명하게 적는 경로를 **절대 경로(absolute path)**라고 부른다.

예를 들어 Windows에서는 다음처럼 볼 수 있다.

```text
C:\Users\Min\Documents\memo.txt
```

현재 어디에 있든 이 경로는 특정 위치를 가리키려고 한다.

### LESSON 02 · 현재 위치를 기준으로 적는 방법

현재 내가 `Documents` 폴더에 있다고 하자.

그 안에 있는 `memo.txt`를 굳이 처음부터 다 적지 않고:

```text
memo.txt
```

처럼 표현할 수도 있다.

현재 위치를 기준으로 표현하는 경로를 **상대 경로(relative path)**라고 부른다.

아주 쉽게:

```text
절대 경로 = 전체 주소
상대 경로 = 지금 있는 곳을 기준으로 한 주소
```

### LESSON 03 · 왜 경로 오류가 생길까

프로그램이 파일을 못 찾는다고 하자.

파일이 실제로 없는 경우도 있지만, 파일은 있는데 **프로그램이 다른 위치를 보고 있는 경우**도 있다.

그래서 파일 문제를 볼 때는 먼저 다음을 나눈다.

```text
파일이 없는가?
아니면
경로가 잘못되었는가?
```

## BLOCK 05 · 확장자란 무엇인가

### LESSON 01 · 파일 이름 뒤의 부분

다음 파일을 보자.

```text
photo.jpg
report.pdf
memo.txt
```

마지막의 `.jpg`, `.pdf`, `.txt` 같은 부분을 보통 **확장자(file extension)**라고 부른다.

한 줄 뜻:

> 확장자 = 파일 이름 끝에 붙어 파일의 종류를 구분하는 데 자주 쓰이는 표시

### LESSON 02 · 확장자가 파일 내용 그 자체는 아니다

중요한 점이 있다.

파일 이름을 바꾼다고 내용이 자동으로 바뀌지는 않는다.

예를 들어 실제 PNG 사진 파일의 이름만 억지로:

```text
photo.png
```

에서

```text
photo.txt
```

로 바꿨다고 해서 사진 내용이 글자 파일로 변하는 것은 아니다.

즉:

```text
파일 이름/확장자
```

와

```text
파일 안의 실제 데이터 형식
```

은 구분해야 한다.

---

## BLOCK 06 · 형식이란 무엇인가

### LESSON 01 · 데이터를 저장하는 약속

컴퓨터가 정보를 저장할 때는 아무렇게나 적는 것이 아니라 일정한 규칙이 필요하다.

사진 파일은 사진 정보를 저장하는 규칙이 있고, PDF는 문서 정보를 저장하는 규칙이 있다.

이처럼 데이터를 어떤 구조와 규칙으로 저장하는지를 **파일 형식(file format)**이라고 부른다.

한 줄 뜻:

> 파일 형식 = 파일 안의 데이터를 어떤 규칙으로 저장하고 읽을지 정한 약속

### LESSON 02 · 프로그램은 형식을 알아야 읽을 수 있다

한국어로 적힌 글을 한국어를 모르는 사람이 보면 읽기 어렵다.

파일도 비슷하다.

프로그램이 파일 안의 데이터가 어떤 규칙으로 되어 있는지 알아야 제대로 해석할 수 있다.

따라서 `파일이 존재한다`와 `프로그램이 그 파일을 제대로 읽을 수 있다`는 다른 문제다.

---

## BLOCK 07 · 텍스트 파일이란 무엇인가

### LESSON 01 · 사람이 읽는 글자를 담은 파일

사람이 읽을 수 있는 글자를 중심으로 저장한 파일을 흔히 **텍스트 파일(text file)**이라고 부른다.

예:

```text
오늘 할 일
1. 공부
2. 운동
```

이런 내용이 들어 있는 `.txt` 파일을 생각하면 된다.

### LESSON 02 · 화면에 글자가 보인다고 모두 같은 형식은 아니다

PDF에도 글자가 보이고, 웹페이지에도 글자가 보인다.

그렇다고 모든 파일이 단순 텍스트 파일이라는 뜻은 아니다.

파일 안에는 글자 외의 구조 정보가 함께 들어갈 수 있다.

따라서 **사람 눈에 보이는 결과**와 **파일 내부 저장 방식**을 구분해야 한다.

---

## BLOCK 08 · 0과 1, 비트와 바이트

### LESSON 01 · 컴퓨터는 결국 작은 상태를 조합한다

컴퓨터 내부에서는 정보를 전기적인 상태로 표현한다.

기초를 이해하기 위해 흔히 두 상태를 `0`과 `1`로 나타낸다고 배운다.

이때 하나의 `0` 또는 `1`처럼 두 상태 중 하나를 나타내는 아주 작은 정보 단위를 **비트(bit)**라고 부른다.

한 줄 뜻:

> bit = 0 또는 1처럼 두 상태 중 하나를 나타내는 아주 작은 정보 단위

### LESSON 02 · 바이트

비트 하나만으로는 표현할 수 있는 것이 매우 적다.

그래서 여러 비트를 묶어서 사용한다.

일반적으로 **8개의 비트**를 묶은 단위를 **바이트(byte)**라고 부른다.

```text
8 bit = 1 byte
```

파일 크기에서 `KB`, `MB`, `GB` 같은 말을 보는 이유도 결국 저장되는 정보의 양을 나타내기 위해서다.

지금은 단위 변환을 외우는 것이 목표가 아니다.

중요한 것은 **글자도 사진도 결국 컴퓨터 안에서는 저장할 수 있는 데이터로 바뀌어야 한다**는 점이다.

---

## BLOCK 09 · 글자를 숫자로 표현해야 하는 이유

### LESSON 01 · 컴퓨터가 '가'라는 글자를 그대로 아는 것은 아니다

사람은 종이에 `가`라는 글자를 보면 글자로 이해한다.

컴퓨터는 글자를 저장하려면 그 글자를 어떤 숫자와 연결해서 표현할 규칙이 필요하다.

예를 들어 단순한 가상의 규칙을 만들어 보자.

```text
A → 1
B → 2
C → 3
```

이 규칙을 서로 알고 있다면 숫자 `1`을 보고 `A`로 바꿀 수 있다.

실제 컴퓨터의 문자 처리는 훨씬 더 큰 규칙을 사용하지만 기본 생각은 같다.

### LESSON 02 · 같은 숫자를 서로 다르게 해석하면 문제가 생긴다

보내는 사람은 `1 = A`라고 생각했는데 받는 사람은 `1 = 가`라고 생각한다면 같은 숫자를 보고 다른 글자를 보여 줄 수 있다.

따라서 글자를 저장하고 주고받으려면 **어떤 규칙으로 숫자와 글자를 연결했는지** 약속이 필요하다.

이제 `인코딩`이라는 말을 배울 준비가 되었다.

---

## BLOCK 10 · 인코딩이란 무엇인가

### LESSON 01 · 먼저 아주 쉬운 뜻

**인코딩(encoding)**은 정보를 정해진 규칙에 따라 다른 표현으로 바꾸는 과정이다.

문자 이야기에서는 보통 **글자를 컴퓨터가 저장하거나 전달할 수 있는 형태로 표현하는 규칙과 과정**을 말할 때 자주 등장한다.

한 줄 뜻:

> 문자 인코딩 = 글자를 컴퓨터가 저장할 수 있도록 정해진 규칙에 따라 숫자와 바이트로 표현하는 방법

여기서 `바이트`는 앞에서 배운 데이터 단위다.

### LESSON 02 · 인코딩은 암호가 아니다

`인코딩`이라는 말을 처음 들으면 `숨겨 놓는 것`이라고 생각하기 쉽다.

하지만 일반적인 문자 인코딩의 목적은 비밀을 숨기는 것이 아니다.

목적은 **서로 같은 규칙으로 문자를 저장하고 읽기 위해서**다.

비밀을 숨기기 위한 기술은 뒤의 보안 TRACK에서 `암호화`라는 이름으로 따로 배운다.

### LESSON 03 · 왜 글자가 깨질까

어떤 프로그램이 글자를 한 규칙으로 저장했다.

다른 프로그램이 다른 규칙이라고 생각하고 읽었다.

그러면 사람이 원한 글자가 아니라 이상한 문자가 보일 수 있다.

이것을 흔히 `문자 깨짐`이라고 말한다.

원인을 아주 단순하게 표현하면:

```text
저장할 때 사용한 문자 규칙
≠
읽을 때 사용한 문자 규칙
```

일 수 있다.

## BLOCK 11 · ASCII는 무엇인가

### LESSON 01 · 초창기 문자 약속의 한 예

컴퓨터에서 문자를 숫자로 표현하기 위한 오래된 표준 가운데 **ASCII**가 있다.

지금 당장 표 전체를 외울 필요는 없다.

예를 들어 ASCII에서는 영어 대문자 `A`가 특정 숫자 값과 연결되어 있다.

중요한 사실은 이것이다.

> 여러 컴퓨터가 같은 문자 규칙을 사용하면 같은 데이터를 같은 글자로 해석하기 쉬워진다.

### LESSON 02 · 세상에는 영어만 있지 않다

영어 알파벳과 몇 가지 기호만 생각해서는 한국어, 일본어, 아랍어, 다양한 기호를 모두 표현하기 어렵다.

그래서 훨씬 더 많은 문자를 함께 다룰 수 있는 큰 체계가 필요해졌다.

그 다음에 **Unicode**가 등장한다.

---

## BLOCK 12 · Unicode는 무엇인가

### LESSON 01 · 세계의 많은 문자에 번호를 정하는 큰 약속

**Unicode(유니코드)**는 세계의 수많은 문자를 일관되게 다루기 위해 각 문자에 번호를 정하는 큰 표준이다.

아주 쉽게 말하면:

> Unicode = 여러 나라의 글자와 기호를 공통된 번호 체계로 다루기 위한 큰 약속

`가`, `A`, `🙂` 같은 문자와 기호를 각각 구분할 수 있게 한다.

### LESSON 02 · Unicode와 UTF-8은 같은 말이 아니다

여기서 초보자가 많이 헷갈린다.

Unicode는 **어떤 문자에 어떤 번호를 대응시킬지 정하는 큰 체계**에 가깝다.

그 번호를 실제 바이트로 저장하는 방법에는 여러 방식이 있을 수 있다.

그 가운데 매우 널리 쓰이는 방식 하나가 **UTF-8**이다.

다음 BLOCK에서 UTF-8만 따로 배운다.

---

## BLOCK 13 · UTF-8은 무엇인가

### LESSON 01 · Unicode 문자를 실제 바이트로 저장하는 널리 쓰이는 방식

**UTF-8**은 Unicode의 문자 정보를 실제 바이트로 표현하는 매우 널리 쓰이는 방식이다.

처음에는 다음 정도로 기억하면 충분하다.

```text
Unicode = 어떤 문자인지 정하는 큰 번호 체계
UTF-8 = 그 문자를 바이트로 저장하는 대표적인 방법 중 하나
```

### LESSON 02 · 왜 웹과 파일에서 UTF-8을 자주 볼까

UTF-8은 다양한 언어의 문자를 다룰 수 있고 널리 지원되기 때문에 웹과 텍스트 파일에서 매우 자주 사용된다.

설정 파일이나 HTML 문서에서 `UTF-8`이라는 말을 보게 되는 이유다.

지금은 UTF-8의 비트 배열을 외우는 것이 목표가 아니다.

먼저 다음 질문에 답할 수 있으면 된다.

> 왜 파일을 읽을 때 문자 인코딩이 맞아야 하는가?

답: 같은 바이트라도 어떤 문자 규칙으로 해석하느냐에 따라 원하는 글자가 안 나올 수 있기 때문이다.

---

## BLOCK 14 · 문자 깨짐을 실제로 생각하기

### LESSON 01 · '안녕하세요'가 이상하게 보일 때

원래 파일에는 한국어가 저장되어 있다.

그런데 프로그램이 잘못된 문자 인코딩으로 읽으면 화면에 이상한 문자가 나타날 수 있다.

이때 무작정 파일이 망가졌다고 단정하지 않는다.

먼저 두 가능성을 나눈다.

```text
1. 파일의 실제 바이트가 이미 망가졌다.
2. 파일은 괜찮지만 읽는 인코딩을 잘못 선택했다.
```

둘은 다른 문제다.

### LESSON 02 · 문제를 확인하는 순서

문자 깨짐이 생기면 초보 단계에서는 다음을 확인한다.

1. 원래 어떤 글자가 나와야 하는가?
2. 파일은 어떤 인코딩으로 저장되었는가?
3. 프로그램은 어떤 인코딩으로 읽고 있는가?
4. 같은 파일을 다른 정상 프로그램에서는 어떻게 읽는가?

이런 식으로 원인을 나누는 것이 디버깅이다.

## BLOCK 15 · 텍스트와 바이너리

### LESSON 01 · 바이너리라는 말

**바이너리(binary)**라는 말은 기본적으로 `두 가지 상태`와 관련된 뜻을 가진다.

컴퓨터에서는 0과 1로 표현되는 데이터를 이야기할 때 자주 등장한다.

파일 이야기에서는 사람이 바로 글자로 읽는 텍스트 파일과 대비해서, 사진·실행 파일처럼 전용 규칙으로 해석해야 하는 데이터를 흔히 `바이너리 파일`이라고 부르기도 한다.

### LESSON 02 · 바이너리 파일을 글자처럼 열면 이상하게 보일 수 있다

사진 파일을 단순한 글자 편집기로 열었다고 하자.

사람이 읽기 어려운 기호들이 보일 수 있다.

사진 데이터가 반드시 망가진 것은 아니다.

**사진 형식으로 해석해야 할 데이터를 글자로 해석하려 했기 때문**일 수 있다.

이것은 매우 중요한 사고방식이다.

> 데이터가 이상한가, 아니면 내가 해석 방법을 잘못 선택했는가?

## BLOCK 16 · 파일 복사와 이동

### LESSON 01 · 복사

파일을 **복사(copy)**하면 원래 파일을 남겨 두고 같은 내용을 가진 다른 파일을 만든다.

```text
원본 A
↓ 복사
원본 A + 복사본 B
```

### LESSON 02 · 이동

파일을 **이동(move)**하면 파일의 위치를 다른 곳으로 옮긴다.

사용자에게는 파일이 사라진 것처럼 보여도 실제로는 다른 폴더로 이동한 것일 수 있다.

파일을 못 찾을 때 `삭제되었다`고 바로 단정하지 말아야 하는 이유다.

## BLOCK 17 · 삭제와 휴지통

### LESSON 01 · 삭제가 항상 즉시 완전 소멸을 뜻하지는 않는다

운영체제와 앱에 따라 파일을 삭제하면 먼저 휴지통 같은 곳으로 이동할 수 있다.

반대로 어떤 삭제 방식은 복구가 훨씬 어렵거나 불가능할 수 있다.

따라서 코딩 중 파일을 지우는 명령은 특별히 조심해야 한다.

### LESSON 02 · 안전한 습관

중요한 파일을 바꾸기 전에:

1. 원본 위치를 확인한다.
2. 복사본을 만든다.
3. 복사본에서 먼저 시험한다.
4. 결과를 확인한 뒤 원본에 적용한다.

이 습관은 파일뿐 아니라 코드와 데이터베이스 작업에서도 이어진다.

## BLOCK 18 · 압축이란 무엇인가

### LESSON 01 · 같은 정보를 더 작게 표현하기

파일은 공간을 차지한다.

어떤 데이터는 반복되는 부분을 더 효율적으로 표현해서 필요한 저장공간을 줄일 수 있다.

이런 과정을 **압축(compression)**이라고 부른다.

한 줄 뜻:

> 압축 = 데이터를 더 적은 공간으로 표현하도록 바꾸는 과정

### LESSON 02 · ZIP 파일

여러 파일을 하나로 묶고 압축할 때 `.zip` 형식을 자주 본다.

압축된 ZIP 안의 파일을 다시 일반 파일로 꺼내는 과정을 **압축 해제**라고 부른다.

`압축`과 `암호화`는 같은 말이 아니다.

압축의 기본 목적은 크기를 줄이거나 여러 파일을 묶는 것이다.

## BLOCK 19 · 데이터가 망가지지 않았다는 뜻

### LESSON 01 · 먼저 '무결성'이라는 어려운 말을 쓰지 않고 이해하기

친구에게 다음 메모를 보냈다고 하자.

```text
계좌번호 마지막 네 자리: 1234
```

친구가 받은 메모가:

```text
계좌번호 마지막 네 자리: 1284
```

로 바뀌었다면 중요한 정보가 달라졌다.

우리는 데이터가 전달되거나 저장되는 동안 **원래 의도한 내용이 멋대로 바뀌지 않았는지** 확인하고 싶을 수 있다.

### LESSON 02 · 이제 '무결성'이라는 이름 붙이기

데이터가 정해진 규칙과 원래 의도한 상태를 유지하고 있는 성질을 이야기할 때 **무결성(integrity)**이라는 말을 사용한다.

초보 단계에서 아주 쉽게 기억하면:

> 무결성 = 데이터가 엉뚱하게 바뀌거나 깨지지 않고 올바른 상태를 유지하고 있는가

이것은 단순히 `파일이 열리는가`보다 넓은 생각이다.

파일은 열리지만 내용 한 부분이 잘못 바뀌었을 수도 있다.

### LESSON 03 · 무결성과 정확성

예를 들어 원본 데이터 자체가 처음부터 틀렸다면 파일이 전송 중 전혀 바뀌지 않았더라도 내용은 틀릴 수 있다.

따라서:

```text
무결성이 유지되었다
```

와

```text
그 데이터의 내용이 현실의 정답이다
```

는 완전히 같은 말이 아니다.

이 구분은 나중에 데이터베이스와 보안에서 다시 깊게 배운다.

## BLOCK 20 · 파일이 같은지 어떻게 확인할까

### LESSON 01 · 파일 크기만 같으면 같은 파일일까

두 파일의 크기가 모두 `10MB`라고 하자.

크기가 같다는 사실만으로 내용이 완전히 같다고 말할 수 없다.

두 개의 다른 사진도 우연히 같은 크기가 될 수 있다.

파일 이름도 마찬가지다.

```text
app.apk
app.apk
```

이름이 같아도 내용은 다를 수 있다.

### LESSON 02 · 모든 내용을 직접 비교하는 방법

가장 직접적인 생각은 두 파일의 모든 바이트를 하나씩 비교하는 것이다.

파일이 작으면 가능하다.

하지만 파일이 매우 크고 많은 파일을 빠르게 확인해야 한다면 더 편리한 방법이 필요할 수 있다.

여기서 `해시`라는 개념으로 넘어간다.

## BLOCK 21 · 해시를 아주 처음부터

### LESSON 01 · 긴 데이터를 짧은 대표값으로 계산하기

**해시(hash)**는 어떤 데이터를 정해진 계산 방법에 넣어 일정한 형태의 결과값을 만드는 방법과 그 결과를 이야기할 때 쓰이는 말이다.

아주 쉽게는 **데이터에서 계산해 낸 지문 같은 값**으로 비유할 수 있다.

```text
파일 내용
↓
정해진 해시 계산
↓
해시값
```

중요: 해시값은 파일 이름이 아니다. 파일의 내용을 바탕으로 계산한다.

### LESSON 02 · 한 글자만 바뀌어도 결과가 달라질 수 있다

원본:

```text
HELLO
```

수정본:

```text
HELLo
```

둘은 한 글자만 다르다.

좋은 암호학적 해시 함수에서는 이렇게 입력이 조금 달라지면 해시 결과도 크게 달라지는 성질을 기대한다.

따라서 원본에서 계산한 해시와 내가 받은 파일에서 계산한 해시를 비교하면 **파일 내용이 같은지 확인하는 데 도움**을 받을 수 있다.

### LESSON 03 · 해시는 원본 내용을 보여 주는 요약문이 아니다

해시값을 보고 `이 파일은 무슨 내용이다`라고 읽는 것이 아니다.

해시는 책의 요약문처럼 내용을 설명해 주지 않는다.

또 같은 해시 함수를 사용하면 같은 입력에서는 같은 결과를 얻을 수 있어 비교에 활용할 수 있다.

## BLOCK 22 · SHA-256이란 무엇인가

### LESSON 01 · 해시를 계산하는 방법에도 종류가 있다

`해시`는 하나의 특정 프로그램 이름이 아니다.

해시값을 계산하는 방법에도 여러 종류가 있다.

그 가운데 널리 사용되는 암호학적 해시 알고리즘 하나가 **SHA-256**이다.

`알고리즘(algorithm)`이라는 말은 어떤 문제를 풀기 위한 절차나 방법이라고 우선 이해하면 된다. 뒤에서 더 깊게 배운다.

한 줄 뜻:

> SHA-256 = 데이터를 입력받아 256비트 길이의 해시값을 만드는 널리 쓰이는 해시 방식

### LESSON 02 · 왜 다운로드 페이지에 SHA-256이 적혀 있을까

프로그램 파일을 다운로드하는 페이지에서 다음처럼 긴 문자열을 볼 수 있다.

```text
SHA-256: 8f3a...예시...
```

제공자가 원본 파일의 SHA-256 값을 공개했다고 하자.

내가 받은 파일에서도 SHA-256을 계산한다.

```text
제공자 값 = ABC123...
내 파일 값 = ABC123...
```

같다면 **내 파일의 바이트가 제공자가 해시를 계산한 파일과 같다는 강한 확인 근거**가 된다.

다르면 같은 파일이라고 보면 안 된다.

### LESSON 03 · '해시가 같으니 무조건 안전한 프로그램'은 아니다

여기서 매우 중요한 구분이 있다.

해시가 제공자의 값과 같다는 것은 주로 **받은 파일이 그 제공자가 기준으로 삼은 파일과 같은지** 확인하는 데 도움을 준다.

하지만 제공자 파일 자체가 악성 프로그램이라면 해시가 같아도 악성일 수 있다.

따라서:

```text
해시 일치 = 같은 내용인지 확인하는 근거
```

이지,

```text
해시 일치 = 프로그램이 무조건 안전함
```

은 아니다.

## BLOCK 23 · 체크섬이라는 말

### LESSON 01 · 오류 확인을 위한 계산값

파일이나 데이터가 바뀌었는지 확인하기 위해 데이터로부터 어떤 값을 계산해 두는 방법들을 넓게 이야기할 때 **체크섬(checksum)**이라는 말을 접할 수 있다.

아주 쉽게:

> 체크섬 = 데이터가 바뀌었는지 확인하는 데 쓰는 계산 결과값

해시값도 이런 확인 목적으로 사용될 수 있지만, 모든 체크섬이 보안 목적의 강한 암호학적 해시와 같은 것은 아니다.

### LESSON 02 · 왜 구분이 필요한가

간단한 오류 검출용 계산은 우연한 전송 오류를 찾는 데 충분할 수 있다.

하지만 누군가 일부러 데이터를 바꾸려고 하는 상황에서는 더 강한 성질이 필요하다.

보안 목적에서는 오래되고 약한 방법보다 현재 목적에 맞는 검증 방법을 선택해야 한다.

구체적인 공격과 보안 선택은 보안 TRACK에서 다룬다.

## BLOCK 24 · 해시와 암호화는 다르다

### LESSON 01 · 암호화라는 말부터 정의

**암호화(encryption)**는 허가되지 않은 사람이 내용을 쉽게 읽지 못하도록 데이터를 다른 형태로 바꾸는 방법을 말한다.

정상적인 사용자는 필요한 비밀 정보인 `키(key)` 등을 이용해 다시 원래 내용을 읽을 수 있게 설계한다.

`키`의 정확한 종류는 보안 TRACK에서 별도로 배운다.

### LESSON 02 · 해시와의 차이

초보 단계에서는 목적부터 구분하자.

```text
해시
→ 데이터로부터 비교용 값을 계산
→ 보통 원본으로 되돌리는 기능을 목표로 하지 않음

암호화
→ 내용을 읽기 어렵게 바꿈
→ 올바른 방법과 키로 다시 읽을 수 있게 설계
```

따라서 비밀번호를 저장하는 문제에서도 단순 암호화와 해시를 구분해야 한다. 이 주제는 보안 TRACK에서 제대로 배운다.

## BLOCK 25 · 파일 권한을 맛보기

### LESSON 01 · 파일이 있는데 왜 못 읽을까

파일이 실제로 존재해도 프로그램이 읽을 권한이 없으면 열지 못할 수 있다.

**권한(permission)**은 누가 어떤 행동을 할 수 있는지 정하는 규칙이다.

예를 들어:

```text
읽기 가능
수정 가능
실행 가능
```

같은 권한이 있을 수 있다.

### LESSON 02 · 파일 문제를 한 덩어리로 보지 않기

`파일을 못 읽는다`는 증상만으로 원인을 하나로 정하면 안 된다.

가능한 원인을 나눠 보자.

```text
파일이 없음
경로가 틀림
권한이 없음
파일 형식이 예상과 다름
문자 인코딩을 잘못 읽음
파일 내용이 손상됨
```

이렇게 문제를 나누는 습관이 중요하다.

권한 자체는 TRACK 05에서 더 깊게 배운다.

---

## BLOCK 26 · 파일 손상이라는 말

### LESSON 01 · 파일이 손상되었다는 것은 무엇인가

저장 또는 전달 과정에서 파일 데이터의 일부가 원래와 다르게 바뀌거나 사라져 정상적으로 해석하기 어려운 상태를 흔히 **파일 손상(corruption)**이라고 말한다.

예:

- 다운로드가 중간에 비정상적으로 끝남
- 저장장치 문제로 일부 데이터가 잘못 기록됨
- 프로그램 오류가 잘못된 내용을 덮어씀

### LESSON 02 · 열리지 않는다고 무조건 손상은 아니다

파일이 안 열린다고 바로 손상이라고 단정하지 않는다.

다시 순서를 확인한다.

```text
존재?
↓
경로?
↓
권한?
↓
형식?
↓
필요하면 인코딩?
↓
내용 손상 여부?
```

증상 하나에 원인 하나만 있다고 생각하지 않는 습관이 중요하다.

---

## BLOCK 27 · 백업이란 무엇인가

### LESSON 01 · 하나뿐인 원본을 바로 고치지 않기

**백업(backup)**은 원본에 문제가 생겼을 때 복구할 수 있도록 중요한 데이터를 별도로 보관하는 것이다.

한 줄 뜻:

> 백업 = 문제가 생겼을 때 되돌릴 수 있도록 따로 보관한 복사본

### LESSON 02 · 복사본 하나가 항상 완벽한 백업은 아니다

같은 저장장치의 같은 폴더에 복사본 하나를 두는 것보다, 중요한 자료라면 서로 다른 장애에 대비할 수 있는 위치를 고려할 수 있다.

하지만 구체적인 백업 전략은 상황마다 다르다.

지금은 **수정 전에 되돌릴 수단이 있는가?**라는 질문을 습관으로 만든다.

## BLOCK 28 · 파일 문제 진단 순서

### LESSON 01 · 아무거나 만지지 않고 확인하기

어떤 프로그램이 `파일을 읽을 수 없습니다`라고 한다.

다음 순서로 확인한다.

1. 정확히 어떤 파일을 읽으려는가?
2. 그 파일이 실제로 존재하는가?
3. 프로그램이 보는 경로가 맞는가?
4. 읽을 권한이 있는가?
5. 기대한 파일 형식이 맞는가?
6. 글자 문제라면 인코딩이 맞는가?
7. 원본과 내용이 달라졌는지 확인할 근거가 있는가?

이 순서를 외우기보다 **원인을 층별로 나누는 생각**을 익힌다.

### LESSON 02 · 증거를 남긴다

수정하기 전에 현재 상태를 기록한다.

예:

```text
파일 이름: report.txt
경로: C:\study\report.txt
크기: 12,340 bytes
예상 인코딩: UTF-8
현재 증상: 한글이 깨져 보임
```

그 다음 한 가지씩 바꿔 확인한다.

이렇게 해야 무엇이 실제 원인이었는지 알 수 있다.

## BLOCK 29 · 인코딩 실습

### LESSON 01 · 같은 글자를 저장하고 읽기

텍스트 편집기에서 다음 글자를 저장한다고 하자.

```text
안녕하세요 ABC 123
```

가능하다면 UTF-8로 저장한다.

그 파일을 UTF-8을 지원하는 다른 편집기로 열어 같은 글자가 보이는지 확인한다.

목표는 명령을 외우는 것이 아니라 다음 흐름을 직접 이해하는 것이다.

```text
사람의 글자
↓
정해진 인코딩으로 바이트 저장
↓
같은 규칙으로 읽기
↓
사람의 글자로 표시
```

### LESSON 02 · 일부러 잘못 읽어보기

사용 중인 도구가 허용한다면 다른 문자 인코딩으로 열어 보고 글자가 어떻게 달라지는지 관찰한다.

도구가 지원하지 않는다면 억지로 할 필요 없다.

핵심 질문:

> 파일 내용 자체가 바뀐 것인가, 아니면 읽는 규칙만 달라진 것인가?

이 질문을 구분할 수 있으면 된다.

## BLOCK 30 · 해시 실습의 생각

### LESSON 01 · 두 파일 준비

다음 내용의 텍스트 파일 A를 만든다.

```text
hello
```

복사해서 파일 B를 만든다.

처음에는 A와 B의 내용이 같다.

같은 해시 방법으로 계산하면 같은 해시값이 나와야 한다.

### LESSON 02 · 한 글자 바꾸기

B를 다음처럼 바꾼다.

```text
Hello
```

첫 글자만 대문자로 바뀌었다.

다시 같은 해시 방법으로 계산한다.

해시값이 달라지는 것을 확인한다.

여기서 배울 것은 긴 명령어가 아니다.

```text
내용이 같음 → 같은 해시 함수에서 같은 해시값
내용이 바뀜 → 해시값도 달라질 가능성이 매우 큼
```

이라는 개념을 직접 확인하는 것이다.

## BLOCK 31 · TRACK 02 핵심 용어 사전

| 용어 | 아주 쉬운 뜻 |
|---|---|
| 파일 | 저장된 정보를 이름 있는 하나의 단위로 다루는 것 |
| 폴더 | 파일과 다른 폴더를 묶어 정리하는 공간 |
| 경로 | 파일이나 폴더가 있는 위치를 나타내는 정보 |
| 절대 경로 | 출발점부터 전체 위치를 나타낸 경로 |
| 상대 경로 | 현재 위치를 기준으로 나타낸 경로 |
| 확장자 | 파일 이름 끝에 붙어 종류를 구분하는 데 자주 쓰는 표시 |
| 파일 형식 | 파일 안의 데이터를 저장하고 읽는 규칙 |
| 텍스트 파일 | 사람이 읽는 글자를 중심으로 다루는 파일 |
| bit | 두 상태 중 하나를 나타내는 아주 작은 정보 단위 |
| byte | 일반적으로 8개의 bit를 묶은 단위 |
| 인코딩 | 정보를 정해진 규칙에 따라 다른 표현으로 바꾸는 과정 |
| Unicode | 세계의 많은 문자에 공통된 번호를 정하는 큰 문자 표준 |
| UTF-8 | Unicode 문자를 바이트로 저장하는 널리 쓰이는 방식 |
| 바이너리 | 컴퓨터의 두 상태 표현과 관련된 말이며 파일에서는 텍스트와 대비해 쓰이기도 함 |
| 압축 | 데이터를 더 적은 공간으로 표현하도록 바꾸는 과정 |
| 무결성 | 데이터가 엉뚱하게 변하거나 깨지지 않고 올바른 상태를 유지하는 성질 |
| 해시 | 데이터로부터 정해진 계산을 통해 대표값을 만드는 방법 또는 그 결과 |
| SHA-256 | 256비트 해시값을 만드는 널리 쓰이는 암호학적 해시 방식 |
| 체크섬 | 데이터 변화나 오류를 확인하는 데 쓰는 계산 결과값 |
| 암호화 | 허가되지 않은 사람이 내용을 쉽게 읽지 못하게 데이터를 바꾸는 방법 |
| 권한 | 누가 어떤 행동을 할 수 있는지 정하는 규칙 |
| 파일 손상 | 파일 데이터 일부가 원래와 다르게 망가져 정상 해석이 어려운 상태 |
| 백업 | 문제가 생겼을 때 복구하도록 별도로 보관한 복사본 |

## BLOCK 32 · TRACK 02 종합 훈련

### LESSON 01 · 다음 말을 구분하기

다음 질문을 자기 말로 답한다.

1. 파일 이름과 파일 형식은 왜 완전히 같은 말이 아닌가?
2. 경로와 파일 이름은 무엇이 다른가?
3. Unicode와 UTF-8은 왜 같은 말로 외우면 안 되는가?
4. 문자 깨짐은 파일이 완전히 손상되었을 때만 생기는가?
5. 파일 크기가 같으면 내용도 반드시 같은가?
6. 해시와 암호화의 목적은 어떻게 다른가?
7. 해시가 같으면 그 프로그램은 무조건 안전한가?

### LESSON 02 · 오류 상황 분석

상황:

```text
어제까지 정상적으로 보이던 한글 메모가
새 프로그램에서 열자 이상한 문자로 보인다.
```

바로 `파일이 손상됐다`고 결론 내리지 않는다.

확인할 후보를 적는다.

```text
파일 자체는 같은가?
새 프로그램이 어떤 인코딩으로 읽는가?
다른 프로그램에서는 정상인가?
원본 해시가 있다면 현재 파일과 같은가?
```

### LESSON 03 · 다운로드 파일 확인 사고 훈련

어떤 사이트가 프로그램 파일과 SHA-256 값을 함께 제공했다.

해야 할 일을 순서대로 설명한다.

```text
1. 공식적으로 신뢰할 출처인지 확인
2. 파일 다운로드
3. 받은 파일의 SHA-256 계산
4. 제공된 값과 비교
5. 다르면 같은 파일로 간주하지 않음
```

그리고 반드시 덧붙인다.

> 해시 일치는 파일 내용 일치를 확인하는 근거이지, 프로그램의 모든 안전성을 보증하는 것은 아니다.

## BLOCK 33 · TRACK 02 완료 기준

이 TRACK을 끝내려면 다음을 자기 말로 설명할 수 있어야 한다.

- 파일과 폴더의 차이
- 경로가 필요한 이유
- 절대 경로와 상대 경로의 기본 차이
- 확장자와 실제 파일 형식이 다른 개념인 이유
- bit와 byte의 가장 기본적인 관계
- 글자를 저장할 때 인코딩이 필요한 이유
- Unicode가 무엇을 해결하려는 표준인지
- UTF-8이 무엇인지
- 문자 깨짐이 왜 발생할 수 있는지
- 텍스트와 바이너리 데이터를 왜 같은 방식으로 읽으면 안 될 수 있는지
- 압축과 암호화의 기본 목적 차이
- 무결성이 무엇인지
- 해시가 무엇인지
- SHA-256이 무엇인지
- 해시 일치가 의미하는 것과 의미하지 않는 것
- 파일이 안 열릴 때 존재·경로·권한·형식·인코딩·손상을 나눠 확인하는 방법

### TRACK 끝 미니 프로젝트 · 파일 검증 노트 만들기

임의의 작은 텍스트 파일을 하나 만든다.

다음 정보를 기록하는 검증 노트를 만든다.

```text
파일 이름:
저장 위치:
확장자:
내가 기대하는 파일 형식:
문자 인코딩:
파일 크기:
SHA-256 값:
백업 위치:
```

그 다음 파일 안의 글자 하나를 바꾸고 다시 SHA-256을 계산한다.

마지막으로 두 값을 비교하고 다음 질문에 답한다.

> 왜 파일 이름은 그대로인데 해시값은 달라졌는가?

이 질문에 `파일 내용이 달라졌기 때문`이라고 설명하고, 해시가 어떤 역할을 하는지도 말할 수 있으면 이번 TRACK의 핵심을 이해한 것이다.
