# TRACK 06 · 설치·버전·의존성 이해하기

앱이 잘 돌아가다가 업데이트 후 갑자기 깨지는 경우가 있다.

이 TRACK에서는 `최신 버전인데 왜 안 돼?`를 이해할 수 있도록 **설치 → 버전 → 라이브러리 → 의존성 → 빌드 → 배포 파일 → 데이터 변경 → 되돌리기** 순으로 배운다.

---

## BLOCK 01 · 설치란 무엇인가

### LESSON 01 · 파일 하나를 복사하는 것보다 넓다

프로그램을 **설치(install)**한다는 것은 프로그램이 실행될 수 있도록 필요한 파일과 정보를 운영체제에 배치하고 등록하는 과정이다.

프로그램에 따라:

```text
파일 복사
설정 등록
바로가기 생성
권한 설정
필요한 다른 구성요소 확인
```

같은 작업이 함께 일어날 수 있다.

### LESSON 02 · 설치 파일과 설치된 프로그램

다운로드한 설치 파일과 실제로 설치된 프로그램은 같은 대상이 아니다.

예:

```text
다운로드한 app.apk
↓ 설치
Android 안에 설치된 앱
```

설치 파일을 삭제해도 이미 설치된 앱은 남아 있을 수 있다.

---

## BLOCK 02 · 패키지란 무엇인가

### LESSON 01 · 관련 파일을 묶어 배포하기

프로그램은 파일 하나만으로 이루어지지 않을 수 있다.

코드, 이미지, 설정, 라이브러리 등을 한 단위로 묶어 설치하거나 배포할 수 있다.

이런 묶음을 **패키지(package)**라고 부른다.

한 줄 뜻:

> 패키지 = 프로그램 배포와 설치를 위해 관련 파일과 정보를 묶은 단위

### LESSON 02 · Android 패키지

Android의 APK도 앱을 설치하기 위한 패키지 파일이다.

APK는 `Android Package`의 줄임말로 생각하면 된다.

나중에 AAB라는 다른 배포 형식도 배운다.

---

## BLOCK 03 · 버전은 왜 필요한가

### LESSON 01 · 같은 프로그램도 시간이 지나며 달라진다

앱을 수정하면 어제의 앱과 오늘의 앱이 다를 수 있다.

어떤 상태의 프로그램인지 구분하기 위해 **버전(version)**을 붙인다.

예:

```text
1.0.0
1.1.0
2.0.0
```

### LESSON 02 · 버전 번호는 단순 장식이 아니다

버전은:

```text
어떤 코드인가?
어떤 기능이 들어 있는가?
어떤 버그가 수정되었는가?
어떤 다른 구성요소와 맞는가?
```

를 추적하는 기준이 된다.

---

## BLOCK 04 · Semantic Versioning 맛보기

### LESSON 01 · 1.2.3의 세 숫자

많은 소프트웨어 프로젝트가 **Semantic Versioning**이라는 버전 규칙을 사용한다.

보통:

```text
MAJOR.MINOR.PATCH
```

형태다.

### LESSON 02 · PATCH

버그 수정처럼 기존 사용 방법을 깨지 않는 작은 수정은 PATCH 번호를 올리는 식으로 표현할 수 있다.

```text
1.2.3 → 1.2.4
```

### LESSON 03 · MINOR

기존 사용 방법을 유지하면서 새 기능을 추가할 때 MINOR를 올리는 규칙을 사용할 수 있다.

```text
1.2.4 → 1.3.0
```

### LESSON 04 · MAJOR

기존 사용 방법과 호환되지 않는 큰 변경이 있으면 MAJOR를 올리는 규칙을 사용할 수 있다.

```text
1.3.0 → 2.0.0
```

모든 프로젝트가 이 규칙을 정확히 쓰는 것은 아니다. 실제 프로젝트의 버전 정책을 확인해야 한다.

---

## BLOCK 05 · 호환성이란 무엇인가

### LESSON 01 · 서로 함께 사용할 수 있는가

두 프로그램이나 구성요소가 문제없이 함께 동작할 수 있는 성질을 **호환성(compatibility)**이라고 부른다.

예:

```text
앱 버전 2.0
서버 API 버전 1.0
```

이 둘이 서로 기대하는 데이터 형식이 다르면 오류가 날 수 있다.

### LESSON 02 · 최신 = 항상 호환

최신 라이브러리를 설치했다고 기존 코드와 자동으로 맞는다는 보장은 없다.

새 버전이 오래된 기능을 없앴을 수도 있고 사용 방법을 바꿨을 수도 있다.

---

## BLOCK 06 · 라이브러리란 무엇인가

### LESSON 01 · 이미 만들어진 코드를 가져다 쓰기

날짜 계산, 네트워크 통신, 이미지 처리 같은 기능을 매번 처음부터 만들 필요는 없다.

다른 사람이 만들어 둔 재사용 가능한 코드를 **라이브러리(library)**라고 부른다.

한 줄 뜻:

> 라이브러리 = 다른 프로그램에서 가져다 사용할 수 있도록 만들어 둔 코드 묶음

### LESSON 02 · 라이브러리도 버전이 있다

내 앱이:

```text
Library A 1.5
```

에서 잘 동작했는데 `2.0`에서는 사용 방법이 달라질 수 있다.

그래서 앱 코드뿐 아니라 **사용하는 라이브러리 버전도 기록해야 한다.**

---

## BLOCK 07 · 의존성이란 무엇인가

### LESSON 01 · 내 프로그램이 다른 것에 기대고 있다

내 앱이 Library A가 있어야 동작한다고 하자.

그렇다면 내 앱은 Library A에 **의존(depend)**한다.

이 관계를 **의존성(dependency)**이라고 부른다.

한 줄 뜻:

> 의존성 = 내 프로그램이 동작하기 위해 필요한 다른 코드나 구성요소와의 관계

### LESSON 02 · 의존성이 없으면

필요한 라이브러리가 설치되지 않았거나 잘못된 버전이면 빌드나 실행이 실패할 수 있다.

따라서 오류가 내 코드가 아니라 의존성 문제일 수도 있다.

---

## BLOCK 08 · 간접 의존성

### LESSON 01 · 내가 직접 고르지 않은 라이브러리도 들어올 수 있다

내 앱이 A를 사용하고, A가 B를 사용한다고 하자.

```text
내 앱 → A → B
```

나는 B를 직접 선택하지 않았지만 앱은 B에도 간접적으로 의존한다.

이런 것을 **전이 의존성(transitive dependency)**이라고 부른다.

### LESSON 02 · 왜 복잡해질까

A는 B 1.0을 원하고, C는 B 2.0을 원할 수 있다.

```text
내 앱 → A → B 1.0
내 앱 → C → B 2.0
```

이런 **버전 충돌(version conflict)**을 빌드 도구가 해결해야 한다.

---

## BLOCK 09 · 패키지 관리자

### LESSON 01 · 의존성을 설치하고 관리하는 도구

언어와 플랫폼에는 외부 라이브러리를 내려받고 버전을 관리하는 도구가 있다.

이런 도구를 **패키지 관리자(package manager)**라고 부른다.

예:

```text
npm
pip
Gradle
```

Gradle은 단순 패키지 관리자보다 더 넓은 빌드 시스템이지만 의존성 관리 역할도 한다.

### LESSON 02 · 설치 명령 하나가 많은 일을 한다

예를 들어 `npm install`은 설정 파일을 읽어 필요한 패키지를 내려받고 의존성 구조를 만든다.

따라서 설치가 느리거나 실패하면 네트워크, 버전 충돌, 권한, 저장공간 등 여러 원인이 있을 수 있다.

---

## BLOCK 10 · 의존성 설정 파일

### LESSON 01 · 무엇이 필요한지 적어 두기

프로젝트는 필요한 라이브러리와 버전을 설정 파일에 기록한다.

예를 들어 Node.js 프로젝트에서는 `package.json`을 많이 사용한다.

```json
{
  "dependencies": {
    "example": "1.2.3"
  }
}
```

### LESSON 02 · 설정 파일과 실제 설치 상태는 다를 수 있다

설정 파일에 `1.2.3`이라고 적혀 있어도 현재 컴퓨터에 실제 설치된 상태가 다를 수 있다.

따라서 오류를 볼 때:

```text
설정에 무엇이 적혀 있는가?
실제로 무엇이 설치되어 있는가?
```

를 나눠 본다.

## BLOCK 11 · lock 파일

### LESSON 01 · 정확히 어떤 버전 조합을 썼는지 기록하기

의존성 설정이 `1.x`처럼 범위를 허용하면 설치 시점에 다른 세부 버전이 선택될 수 있다.

팀원마다 다른 버전이 설치되면 `내 컴퓨터에서는 되는데 다른 사람 컴퓨터에서는 안 됨` 문제가 생길 수 있다.

그래서 실제 선택된 정확한 의존성 버전들을 기록하는 **lock 파일**을 사용한다.

예:

```text
package-lock.json
poetry.lock
gradle.lockfile
```

### LESSON 02 · lock 파일의 목적

한 줄 뜻:

> lock 파일 = 같은 의존성 조합을 다시 만들 수 있도록 실제 결정된 버전을 기록한 파일

lock 파일을 무조건 지우는 것을 문제 해결 방법처럼 사용하면 재현성을 잃을 수 있다.

## BLOCK 12 · 빌드란 무엇인가

### LESSON 01 · 소스 코드를 실행·배포 가능한 결과로 만드는 과정

프로젝트에는 사람이 작성한 코드, 이미지, 설정, 라이브러리가 있다.

이 재료들을 검사하고 변환하고 묶어서 실행하거나 배포할 결과물을 만드는 과정을 **빌드(build)**라고 부른다.

한 줄 뜻:

> 빌드 = 소스 코드와 필요한 자원을 실제 실행·배포 가능한 결과물로 만드는 과정

### LESSON 02 · 빌드는 단순 압축이 아니다

빌드 과정에는:

```text
코드 변환
문법/타입 검사
의존성 연결
리소스 처리
패키징
최적화
```

등이 들어갈 수 있다.

프로젝트마다 과정이 다르다.

## BLOCK 13 · 컴파일

### LESSON 01 · 코드를 다른 형태로 변환하기

**컴파일(compile)**은 사람이 작성한 소스 코드를 컴퓨터가 실행하거나 다른 도구가 처리할 수 있는 다른 형태로 변환하는 과정이다.

언어마다 방식이 다르다.

Kotlin 코드는 Android 빌드 과정에서 여러 단계를 거쳐 앱이 실행할 형식으로 변환된다.

### LESSON 02 · 컴파일 오류

코드 문법이나 타입이 맞지 않으면 빌드 중 컴파일 단계에서 실패할 수 있다.

이때 앱을 실행하기도 전에 오류가 발견된다.

## BLOCK 14 · 빌드 결과물

### LESSON 01 · artifact

빌드가 끝나 만들어진 파일을 **빌드 산출물(build artifact)** 또는 줄여서 **artifact**라고 부른다.

예:

```text
APK
AAB
JAR
ZIP
```

한 줄 뜻:

> artifact = 빌드 과정이 만들어 낸 결과 파일

### LESSON 02 · 소스 코드와 artifact는 다르다

GitHub에 최신 코드가 있어도 사용자의 휴대폰에는 오래된 APK가 설치되어 있을 수 있다.

```text
Git 최신 코드
≠
배포된 APK
≠
기기에 설치된 앱
```

이 세 상태를 구분해야 한다.

## BLOCK 15 · Debug와 Release

### LESSON 01 · 개발용 빌드

개발 중에는 디버깅 정보를 많이 넣고 테스트하기 편한 **Debug 빌드**를 사용한다.

### LESSON 02 · 배포용 빌드

사용자에게 배포하는 빌드는 **Release 빌드**라고 부른다.

Release에서는 최적화, 서명, 보안 설정 등이 달라질 수 있다.

따라서:

```text
Debug에서 됨 = Release에서도 반드시 됨
```

이 아니다.

## BLOCK 16 · 서명이란 무엇인가

### LESSON 01 · 누가 만든 앱인지 확인하는 디지털 증명

Android 앱은 설치와 업데이트 과정에서 앱의 **디지털 서명(signature)**을 사용한다.

서명은 개인키를 이용해 생성하고 공개키 쪽 정보로 검증할 수 있다.

초보 단계에서는:

> 앱 서명 = 이 앱이 같은 발행자에게서 나온 업데이트인지 확인하는 중요한 디지털 증명

### LESSON 02 · 서명 키를 잃어버리면

기존 앱과 같은 서명으로 업데이트해야 하는 상황에서 서명 키를 잃으면 큰 문제가 생길 수 있다.

따라서 서명 키는 일반 코드보다 더 강하게 보호해야 한다.

## BLOCK 17 · Android versionCode와 versionName

### LESSON 01 · 사용자에게 보이는 버전 이름

Android에서는 사용자가 보는 `1.2.0` 같은 값을 **versionName**으로 설정할 수 있다.

### LESSON 02 · 업데이트 순서를 판단하는 숫자

Android에는 **versionCode**라는 정수 값도 있다.

새 업데이트는 이전보다 더 큰 versionCode를 사용해야 한다.

```text
versionName = 사람이 보는 버전 표시
versionCode = 시스템이 업데이트 순서를 판단하는 숫자
```

## BLOCK 18 · API 호환성

### LESSON 01 · 함수 사용 방법이 바뀔 수 있다

라이브러리 1.0에서는:

```text
loadData(url)
```

를 사용했는데 2.0에서는 사용 방법이 바뀔 수 있다.

기존 코드가 새 라이브러리에서 더 이상 동작하지 않으면 **호환성이 깨졌다**고 말할 수 있다.

### LESSON 02 · deprecated

곧 없어질 예정이거나 더 이상 권장하지 않는 기능에 **deprecated** 표시를 붙이는 경우가 있다.

한 줄 뜻:

> deprecated = 아직 쓸 수 있을 수 있지만 앞으로 제거될 수 있어 사용을 권장하지 않는 기능

경고를 무시하고 계속 사용하면 다음 큰 버전에서 빌드가 깨질 수 있다.

---

## BLOCK 19 · breaking change

### LESSON 01 · 기존 코드를 깨뜨리는 변경

새 버전에서 기존 사용 방법을 그대로 쓸 수 없게 만드는 변경을 **breaking change**라고 부른다.

예:

```text
함수 이름 삭제
필수 인자 추가
데이터 형식 변경
```

### LESSON 02 · release note

버전 업데이트 전에 **release note(릴리스 노트)**를 읽는다.

릴리스 노트에는 새 기능, 수정된 버그, 알려진 문제, breaking change 등이 적혀 있을 수 있다.

AI에게 요약을 맡기더라도 원문에서 중요한 변경을 직접 확인한다.

## BLOCK 20 · 구성과 환경

### LESSON 01 · 같은 코드인데 환경이 다르면

프로그램은:

```text
운영체제 버전
Java 버전
Node 버전
환경변수
라이브러리 버전
```

에 따라 결과가 달라질 수 있다.

이런 실행 조건을 넓게 **환경(environment)**이라고 부른다.

### LESSON 02 · 재현 가능한 환경

버그를 다른 컴퓨터에서도 재현하려면 버전과 설정을 기록해야 한다.

예:

```text
Windows 11
Java 17
Gradle 8.x
Android SDK 35
```

`내 컴퓨터에서 됨`보다 훨씬 좋은 정보다.

## BLOCK 21 · 데이터 구조가 바뀌는 업데이트

### LESSON 01 · 코드만 바뀌는 것이 아니다

앱 업데이트에서 데이터베이스 구조가 바뀔 수 있다.

예:

기존 사용자 테이블:

```text
id
name
```

새 버전:

```text
id
name
email
```

기존 데이터를 새 구조에 맞게 옮겨야 할 수 있다.

### LESSON 02 · migration

기존 데이터나 구조를 새 버전 형식으로 옮기는 작업을 **마이그레이션(migration)**이라고 부른다.

한 줄 뜻:

> migration = 기존 데이터와 구조를 새 버전이 사용하는 형태로 안전하게 바꾸는 과정

---

## BLOCK 22 · 마이그레이션 실패

### LESSON 01 · 새 앱은 설치됐는데 데이터가 안 열린다

코드는 새 버전인데 데이터베이스가 예전 구조로 남아 있으면 앱이 오류를 낼 수 있다.

따라서 업데이트 테스트에서는:

```text
새로 설치
```

만 테스트하면 부족하다.

기존 버전 사용자가 업데이트하는 경로도 시험해야 한다.

### LESSON 02 · upgrade path

버전 A에서 B로 올라가는 실제 경로를 **업그레이드 경로(upgrade path)**라고 부른다.

```text
1.0 → 1.1
1.1 → 2.0
1.0 → 2.0
```

각 경로가 모두 같은 결과를 보장하는지 확인해야 할 수 있다.

## BLOCK 23 · 롤백

### LESSON 01 · 새 버전이 문제면 되돌리기

새 버전을 배포했는데 심각한 오류가 생겼을 때 이전 정상 버전으로 되돌리는 것을 **롤백(rollback)**이라고 부른다.

한 줄 뜻:

> rollback = 변경을 취소하고 이전 정상 상태로 되돌리는 것

### LESSON 02 · 데이터가 바뀌었다면 단순히 앱만 되돌려도 안 될 수 있다

새 버전이 데이터 구조를 변경했다면 앱 파일만 이전 버전으로 되돌렸을 때 예전 앱이 새 데이터 구조를 읽지 못할 수 있다.

따라서 배포 전에 **코드 롤백 + 데이터 호환성**을 함께 생각해야 한다.

---

## BLOCK 24 · canary와 단계적 배포

### LESSON 01 · 모든 사용자에게 한 번에 보내지 않기

새 버전을 아주 적은 사용자에게 먼저 배포해 문제를 관찰한 뒤 점차 범위를 늘릴 수 있다.

이런 접근을 **카나리 배포(canary deployment)** 또는 단계적 배포 전략이라고 부른다.

### LESSON 02 · 왜 필요한가

개발 환경에서는 잡히지 않은 문제가 실제 사용자 환경에서 발견될 수 있다.

작은 범위부터 배포하면 전체 피해를 줄일 수 있다.

---

## BLOCK 25 · CI와 자동 빌드 맛보기

### LESSON 01 · 사람이 매번 수동으로 확인하면 빠뜨릴 수 있다

코드가 바뀔 때마다 자동으로 빌드와 테스트를 실행하는 시스템을 만들 수 있다.

**CI(Continuous Integration)**는 개발자가 자주 코드를 합치면서 자동 빌드와 테스트로 문제를 빨리 찾는 개발 방식과 시스템을 말한다.

### LESSON 02 · 자동화 결과도 증거를 봐야 한다

CI 화면에 초록색 체크가 있다고 해서 내가 원하는 모든 기능이 검증됐다는 뜻은 아니다.

어떤 테스트가 실제 실행됐는지 확인해야 한다.

## BLOCK 26 · 업데이트 문제 진단 순서

### LESSON 01 · 무엇이 바뀌었는지 먼저 찾기

업데이트 후 깨졌다면:

```text
앱 코드가 바뀌었나?
라이브러리 버전이 바뀌었나?
빌드 도구가 바뀌었나?
운영체제 버전이 바뀌었나?
서버 API가 바뀌었나?
데이터 구조가 바뀌었나?
환경변수가 바뀌었나?
```

를 나눈다.

### LESSON 02 · 정상 조합과 실패 조합 비교

예:

```text
정상: 앱 1.4 + API 2 + DB schema 5
실패: 앱 1.5 + API 2 + DB schema 5
```

차이는 앱 버전뿐이다.

이런 비교는 원인을 좁히는 강한 증거가 된다.

## BLOCK 27 · TRACK 06 핵심 용어 사전

| 용어 | 아주 쉬운 뜻 |
|---|---|
| install | 프로그램이 실행되도록 파일과 정보를 배치하고 등록하는 과정 |
| package | 배포·설치를 위해 관련 파일과 정보를 묶은 단위 |
| version | 프로그램의 특정 상태를 구분하는 번호나 이름 |
| compatibility | 서로 함께 문제없이 사용할 수 있는 성질 |
| library | 다른 프로그램이 재사용할 수 있도록 만든 코드 묶음 |
| dependency | 내 프로그램이 필요로 하는 다른 코드와의 관계 |
| transitive dependency | 내가 쓰는 라이브러리가 또 필요로 하는 간접 의존성 |
| package manager | 외부 패키지 설치와 버전을 관리하는 도구 |
| lock file | 실제 사용한 정확한 의존성 버전을 기록한 파일 |
| build | 소스와 자원을 실행·배포 가능한 결과물로 만드는 과정 |
| compile | 소스 코드를 다른 실행·처리 가능한 형태로 변환하는 과정 |
| artifact | 빌드가 만든 결과 파일 |
| Debug | 개발과 디버깅을 위한 빌드 형태 |
| Release | 실제 배포를 위한 빌드 형태 |
| signature | 앱의 발행자와 업데이트 연속성을 확인하는 디지털 서명 |
| deprecated | 앞으로 제거될 수 있어 사용을 권장하지 않는 기능 |
| breaking change | 기존 사용 방법과 호환되지 않게 만드는 변경 |
| migration | 기존 데이터와 구조를 새 버전 형태로 옮기는 과정 |
| upgrade path | 이전 버전에서 새 버전으로 올라가는 실제 경로 |
| rollback | 변경을 취소하고 이전 정상 상태로 되돌리는 것 |
| canary deployment | 작은 사용자 범위에 먼저 새 버전을 배포하는 방식 |
| CI | 코드 변경마다 자동 빌드·테스트를 수행하는 통합 방식 |

## BLOCK 28 · TRACK 06 종합 훈련

### LESSON 01 · 업데이트 후 앱이 안 켜진다

가능한 후보를 나눈다.

```text
APK 서명 문제
Android 버전 호환성
라이브러리 충돌
데이터 migration 실패
환경 설정 누락
빌드 설정 변경
```

처음부터 `코드 버그` 하나로 단정하지 않는다.

### LESSON 02 · lock 파일이 왜 필요한지 설명하기

친구에게 이렇게 설명할 수 있어야 한다.

```text
의존성 범위만 적어 두면 설치 날짜에 따라 다른 세부 버전이 들어갈 수 있다.
lock 파일은 실제 선택된 버전을 기록해서 같은 조합을 다시 만들기 쉽게 한다.
```

### LESSON 03 · 배포 전 체크

```text
Debug 빌드 성공?
Release 빌드 성공?
서명 검증?
기존 버전에서 업데이트 테스트?
신규 설치 테스트?
데이터 migration 테스트?
롤백 방법?
```

## BLOCK 29 · TRACK 06 완료 기준

다음을 자기 말로 설명할 수 있어야 한다.

- 설치 파일과 설치된 프로그램이 다른 이유
- 패키지와 라이브러리의 차이
- 버전이 필요한 이유
- 의존성과 전이 의존성이 무엇인지
- lock 파일이 재현성에 왜 중요한지
- 빌드와 컴파일의 차이
- artifact가 무엇인지
- Debug와 Release 빌드가 왜 다를 수 있는지
- Android 앱 서명이 왜 중요한지
- breaking change가 무엇인지
- migration이 왜 필요한지
- 새로 설치 테스트와 업데이트 테스트가 왜 둘 다 필요한지
- rollback이 데이터 구조 때문에 어려울 수 있는 이유
- 자동 CI가 성공했다고 모든 기능이 검증됐다고 단정하면 안 되는 이유

### TRACK 끝 미니 프로젝트 · 안전한 업데이트 계획서

가상의 앱 `1.4.0 → 2.0.0` 업데이트를 설계한다.

조건:

```text
라이브러리 A: 1.x → 2.x
DB schema: 4 → 5
Android 최소 버전 변경
Release 서명 유지 필요
```

작성할 것:

```text
변경 목록
breaking change 후보
의존성 버전 고정 방법
migration 순서
신규 설치 테스트
기존 사용자 upgrade test
Release 빌드 검증
서명 검증
rollback 조건
```

이 계획을 작성할 수 있으면 `업데이트 = 최신 파일 덮어쓰기`가 아니라는 것을 이해한 것이다.
