## V1-C06. 설치·버전·의존성 — “내 폰에서는 되는데 왜 저 폰에서는 안 되지?”

**이 장의 대상:** 앱 설치와 업데이트는 해봤지만 `버전`, `패키지`, `의존성`, `설정`, `빌드`가 왜 중요한지 모르는 사람.

**이 장의 목표:** “최신 버전이면 무조건 좋다”는 생각에서 벗어나 **어떤 버전 조합과 설정에서 정상 동작했는지 기록하고, 변경을 한 번에 하나씩 검증하는 방법**을 익힌다.

---

### 1. 설치한다는 것은 무엇일까?

앱 파일을 가지고 있다고 해서 바로 앱을 사용할 수 있는 것은 아니다.

운영체제가 그 앱을 기기에 등록하고 실행할 수 있게 준비해야 한다.

이를 **설치(install)**라고 부른다.

```text
앱 패키지 파일 준비
↓
운영체제가 확인
↓
필요한 파일 배치
↓
앱 정보 등록
↓
실행 가능
```

설치 과정에서 서명, 권한, 버전, 저장공간, 호환성 같은 조건을 확인할 수 있다.

---

### 2. APK는 무엇일까?

Android에서 앱 설치에 사용되는 대표 패키지 형식이 **APK**다.

초보자에게는 다음 정도면 충분하다.

> **APK = Android 앱을 설치하기 위해 필요한 파일 묶음**

APK 안에는 앱 코드와 이미지, 설정 정보 등이 포함될 수 있다.

ZIP처럼 내부적으로 묶음 구조를 사용할 수 있지만, 목적과 설치 규칙이 다르다.

---

### 3. 패키지라는 말

**패키지(package)**는 관련된 코드와 파일을 묶어 배포하거나 설치하기 쉽게 만든 단위라는 뜻으로 여러 곳에서 사용된다.

Android 앱 패키지, Python 패키지, npm 패키지처럼 상황마다 세부 의미는 다르다.

지금은:

> **패키지 = 설치하거나 재사용하기 좋게 묶어 놓은 소프트웨어 단위**

라고 생각한다.

---

### 4. 버전은 무엇일까?

앱이나 라이브러리가 바뀌면 어떤 상태인지 구분할 번호가 필요하다.

예:

```text
1.0.0
1.1.0
2.0.0
```

이런 숫자를 **버전(version)**이라고 부른다.

> **버전 = 소프트웨어가 어느 시점의 상태인지 구분하는 번호나 이름**

버전이 다르면 기능, 버그, 호환성이 달라질 수 있다.

---

### 5. “최신”이 항상 “호환”은 아니다

새 버전에는 새로운 기능과 버그 수정이 들어갈 수 있다.

하지만 다른 라이브러리나 운영체제와 맞지 않을 수도 있다.

예:

```text
앱 1.0 + 라이브러리 A 2.4 → 정상
앱 1.0 + 라이브러리 A 3.0 → 빌드 실패
```

그래서:

> **최신 버전 = 무조건 안전한 버전**

이 아니다.

중요한 것은 **검증된 조합**이다.

---

### 6. 의존성은 무엇일까?

앱이 모든 기능을 처음부터 직접 만들지는 않는다.

다른 사람이 만든 라이브러리를 가져와 사용할 수 있다.

그 라이브러리가 없으면 내 프로그램이 제대로 동작하지 않을 수 있다.

이를 **의존성(dependency)**이라고 부른다.

> **의존성 = 내 프로그램이 실행되거나 빌드될 때 필요한 외부 코드나 패키지**

예:

```text
내 앱
├─ 네트워크 라이브러리
├─ JSON 처리 라이브러리
└─ 데이터베이스 라이브러리
```

---

### 7. 라이브러리란 무엇일까?

**라이브러리(library)**는 다른 프로그램에서 재사용할 수 있도록 만들어 놓은 코드 묶음이다.

예:

```text
날짜 계산
HTTP 통신
이미지 표시
DB 연결
암호화
```

이런 기능을 직접 처음부터 다 만들지 않고 검증된 라이브러리를 사용할 수 있다.

하지만 라이브러리도 버전이 바뀌므로 관리가 필요하다.

---

### 8. 의존성 사슬

내 앱이 라이브러리 A를 쓰고, A가 다시 B를 쓸 수 있다.

```text
내 앱
↓
라이브러리 A
↓
라이브러리 B
```

이런 연결을 **의존성 사슬**이라고 생각할 수 있다.

어느 하나의 버전이 바뀌어도 전체 빌드에 영향을 줄 수 있다.

---

### 9. 의존성 충돌은 무엇일까?

내 앱의 두 기능이 서로 다른 버전의 같은 라이브러리를 요구할 수 있다.

```text
기능 A → library X 1.x 필요
기능 B → library X 2.x 필요
```

도구가 적절한 버전을 선택하지 못하거나, 선택된 버전에서 한 기능이 깨질 수 있다.

이를 **의존성 충돌(dependency conflict)**이라고 부를 수 있다.

초보자는 오류 메시지에 버전 번호가 여러 개 보이면 이 가능성을 생각해본다.

---

### 10. 빌드는 무엇일까?

소스코드를 바로 앱으로 설치하는 것이 아니라 여러 단계를 거쳐 실행 가능한 결과물을 만든다.

이 과정을 **빌드(build)**라고 부른다.

Android 예시로 아주 단순화하면:

```text
소스코드
↓
필요한 라이브러리 확인
↓
코드 변환/컴파일
↓
리소스 묶기
↓
APK/AAB 같은 산출물 생성
```

> **빌드 = 소스코드와 자원을 실제 실행·배포 가능한 결과물로 만드는 과정**

---

### 11. 컴파일은 무엇일까?

사람이 작성한 코드를 기계나 실행 환경이 처리할 수 있는 형태로 바꾸는 과정 중 하나를 **컴파일(compile)**이라고 한다.

모든 언어가 같은 방식으로 동작하지는 않는다.

지금은:

> **컴파일 = 작성한 코드를 실행 가능한 형태로 바꾸는 과정의 한 종류**

정도로 이해한다.

---

### 12. 빌드 실패와 실행 실패는 다르다

#### 빌드 실패

앱 설치파일을 만드는 단계에서 실패한다.

예:

```text
문법 오류
라이브러리 버전 충돌
설정 누락
```

#### 실행 실패

빌드는 성공했지만 실제 앱을 켜면 문제가 생긴다.

예:

```text
서버 주소 오류
권한 문제
데이터 마이그레이션 오류
```

둘을 같은 “앱 안 됨”으로 부르면 진단이 느려진다.

---

### 13. 설정은 코드와 다르다

프로그램의 행동을 바꾸는 값 중에는 코드가 아닌 **설정(configuration)**으로 관리하는 것이 좋은 것들이 있다.

예:

```text
API 서버 주소
로그 레벨
기능 켜기/끄기
재시도 횟수
```

같은 코드라도 설정이 다르면 다른 결과가 나올 수 있다.

> **설정 = 프로그램이 어떻게 동작할지 바꾸는 값**

---

### 14. 개발 환경과 운영 환경

앱을 만들 때 실제 사용자에게 서비스하는 환경과 개발자가 시험하는 환경을 나눌 수 있다.

```text
개발(dev)   → 테스트용
운영(prod)  → 실제 사용자용
```

`dev`, `prod` 같은 영어를 볼 수 있다.

> **development = 개발용 환경**
>
> **production = 실제 서비스 운영 환경**

운영 서버에 테스트 데이터를 보내거나 반대로 테스트 앱이 운영 DB를 수정하지 않도록 구분이 중요하다.

---

### 15. 환경별 설정 파일

프로젝트에 다음과 같은 설정이 있을 수 있다.

```text
config-dev.json
config-prod.json
```

두 파일은 이름만 비슷하고 실제 서버 주소나 키가 다를 수 있다.

잘못된 설정을 읽으면 앱은 정상 빌드되지만 엉뚱한 서버에 접속할 수 있다.

따라서 실행 시 실제 적용된 설정을 확인할 방법이 있어야 한다.

---

### 16. 비밀값과 설정을 구분하기

모든 설정이 공개돼도 되는 것은 아니다.

```text
theme=dark           → 일반 설정
api_base_url=...     → 공개 가능할 수도 있음
api_secret=...       → 비밀값
```

비밀키, 비밀번호, 토큰은 별도 보호가 필요하다.

Chapter 5에서 배운 **secret** 개념을 적용한다.

---

### 17. 버전 고정은 왜 할까?

의존성을 항상 `latest`로만 가져오면 어느 날 빌드 결과가 달라질 수 있다.

그래서 검증된 버전을 고정하는 경우가 많다.

```text
libraryA = 2.4.1
```

> **버전 고정 = 어떤 버전을 사용할지 명확하게 정하는 것**

이렇게 하면 같은 소스에서 비슷한 환경을 재현하기 쉬워진다.

---

### 18. lock 파일은 무엇일까?

패키지 관리 도구는 실제 선택된 의존성 버전을 기록하는 **lock 파일**을 사용할 수 있다.

예:

```text
package-lock.json
poetry.lock
```

도구마다 형식이 다르다.

> **lock 파일 = 실제로 사용하기로 결정된 의존성 버전 조합을 기록한 파일**

무작정 지우기 전에 역할을 이해해야 한다.

---

### 19. 재현 가능성이란 무엇일까?

내 컴퓨터에서는 빌드되는데 다른 컴퓨터에서는 안 된다면 환경 차이가 있을 수 있다.

**재현 가능성(reproducibility)**은 같은 입력과 환경에서 같은 결과를 다시 만들 수 있는 정도를 말한다.

좋은 프로젝트는 다음을 기록한다.

```text
언어 버전
빌드 도구 버전
의존성 버전
환경변수
설정 파일
빌드 명령
```

---

### 20. 버전 번호 읽기 맛보기

많은 프로젝트가 다음처럼 세 부분 버전을 쓴다.

```text
1.4.2
```

종종 다음 의미를 따르는 **Semantic Versioning** 규칙을 사용하기도 한다.

```text
주 버전.부 버전.수정 버전
```

하지만 모든 프로젝트가 완전히 같은 규칙을 지키는 것은 아니다.

따라서 버전 숫자만 보고 호환성을 확정하지 않는다.

릴리스 노트를 함께 본다.

---

### 21. 릴리스 노트는 무엇일까?

새 버전에 무엇이 바뀌었는지 기록한 문서를 **릴리스 노트(release notes)** 또는 changelog라고 부를 수 있다.

예:

```text
1.2.0
- 로그인 오류 수정
- 최소 Android 버전 변경
- DB schema 변경
```

업데이트 전 이런 변경사항을 확인하면 위험을 줄일 수 있다.

---

### 22. 깨지는 변경이란 무엇일까?

새 버전이 이전 사용 방법과 호환되지 않는 변경을 포함할 수 있다.

이를 **breaking change**라고 부른다.

> **breaking change = 기존 코드를 그대로 쓰면 깨질 수 있는 호환성 변경**

예:

```text
기존 함수 이름 삭제
API 필드 이름 변경
설정 형식 변경
DB schema 변경
```

---

### 23. 업데이트 전에 확인할 것

무작정 “모두 최신으로 업데이트”하지 않는다.

체크리스트:

1. 현재 정상 버전 기록
2. 변경할 패키지 하나 지정
3. 릴리스 노트 확인
4. breaking change 확인
5. 빌드
6. 테스트
7. 실제 실행 확인
8. 문제 있으면 rollback

한 번에 많은 것을 바꾸면 원인을 찾기 어렵다.

---

### 24. 롤백은 무엇일까?

업데이트 후 문제가 생겼을 때 이전 정상 상태로 되돌리는 것을 **롤백(rollback)**이라고 한다.

> **rollback = 문제가 생긴 변경을 취소하고 이전 정상 상태로 돌아가는 것**

롤백하려면 정상 버전을 알고 있어야 한다.

그래서 업데이트 전 기준 상태를 기록한다.

---

### 25. 데이터 마이그레이션이라는 말

앱 버전이 바뀌면서 저장 데이터 구조도 바뀔 수 있다.

예:

```text
구버전 DB: name, price
신버전 DB: name, price, currency
```

기존 데이터를 새 구조로 옮기는 과정을 **마이그레이션(migration)**이라고 한다.

> **migration = 기존 데이터를 새로운 구조에 맞게 안전하게 옮기는 과정**

앱 파일만 업데이트했다고 사용자 데이터가 자동으로 완벽히 변환된다고 가정하면 안 된다.

---

### 26. 업데이트 설치와 새 설치는 다를 수 있다

새 설치는 빈 상태에서 시작한다.

업데이트 설치는 기존 데이터와 설정을 유지한 채 새 버전으로 올라간다.

따라서:

```text
신규 설치 → 정상
기존 사용자 업데이트 → 오류
```

가 가능하다.

이 경우 설치파일 자체보다 **migration, 오래된 설정, 캐시**를 확인해야 한다.

---

### 27. Android versionCode와 versionName 맛보기

Android 앱에는 사용자에게 보여주는 버전 이름과 업데이트 판단에 사용하는 내부 버전 번호가 있을 수 있다.

예:

```text
versionName = 1.2.4
versionCode = 24
```

세부 규칙은 Android 개발에서 다시 배운다.

지금은:

> **화면에 보이는 버전 문자열과 시스템이 업데이트 순서를 판단하는 값이 다를 수 있다.**

라고 이해한다.

---

### 28. 서명이란 무엇일까?

Android 앱은 누가 만든 패키지인지와 변조 여부를 확인하기 위해 **디지털 서명(signature)**을 사용한다.

아주 쉽게 말하면:

> **서명 = 이 앱 패키지가 같은 발행 주체에서 나온 것인지 확인하는 중요한 증거**

기존 앱과 다른 키로 서명된 APK는 업데이트 설치가 거부될 수 있다.

보안의 자세한 원리는 V7에서 배운다.

---

### 29. 같은 패키지 이름만으로 같은 앱은 아니다

업데이트가 되려면 여러 조건이 맞아야 한다.

대표적으로:

```text
패키지 식별자
서명
버전 조건
기기 호환성
```

등이 관련될 수 있다.

따라서 “파일 이름이 똑같다”는 사실만으로 같은 앱 업데이트라고 판단하지 않는다.

---

### 30. 최소 Android 버전

앱이 너무 새로운 Android 기능을 사용하면 오래된 기기에서는 설치되지 않을 수 있다.

프로젝트에는 지원하는 최소 OS 버전 조건이 있다.

> **최소 버전 = 앱이 지원하기로 한 가장 낮은 운영체제 버전**

설치 실패 시 기기 Android 버전과 앱 요구 버전을 비교한다.

---

### 31. CPU 아키텍처와 호환성 맛보기

앱에 포함된 네이티브 라이브러리에 따라 기기의 CPU 아키텍처와 호환성 문제가 생길 수 있다.

`arm64-v8a` 같은 말을 볼 수 있다.

첫 단계에서는 외우지 않는다.

> **같은 Android라도 기기 하드웨어와 앱 바이너리 조합이 맞아야 할 수 있다.**

정도로 이해한다.

---

### 32. 실제 예제 — 모두 latest로 올린 뒤 빌드 실패

상황:

```text
정상 상태
library A 2.4
library B 5.1

한 번에 업데이트
library A latest
library B latest
빌드 실패
```

좋은 대응:

1. 변경 전 정상 버전 확인
2. 변경 목록 확인
3. 한 패키지씩 되돌리거나 업데이트
4. 매 단계 빌드
5. 실패가 처음 생긴 변경 찾기

전체를 계속 랜덤하게 바꾸지 않는다.

---

### 33. 실제 예제 — 새 설치는 되는데 업데이트는 실패

이런 경우 다음 후보를 본다.

```text
서명 차이
versionCode 조건
기존 데이터 migration
기존 설정/캐시
저장공간
```

APK가 “깨졌다”고 바로 결론내리지 않는다.

---

### 34. 실제 예제 — 개발 서버에만 연결됨

개발자 폰에서는 정상인데 사용자 폰에서는 데이터가 안 나온다.

코드에 테스트 서버 주소가 박혀 있을 수 있다.

확인:

```text
현재 적용된 API base URL
빌드 variant
환경 설정
서버 접근 가능 여부
```

코드 자체와 환경 설정을 분리해 본다.

---

### 35. 버전 비교표 만들기

문제가 생기면 다음 표를 만든다.

| 항목 | 정상 환경 | 실패 환경 |
|---|---|---|
| 앱 버전 | 1.2.3 | 1.2.4 |
| Android | 16 | 16 |
| DB schema | 5 | 6 |
| API | v2 | v2 |
| library A | 2.4 | 2.5 |

한 줄씩 비교하면 변화가 보인다.

---

### 36. 코드로 버전 정보를 기록하는 맛보기

```python
app_version = "1.2.4"
runtime = "Android 16"
print(app_version)
print(runtime)
```

실제 앱에서는 더 자동화된 방법을 사용하지만, 중요한 습관은 **실행 환경을 기록하는 것**이다.

---

### 37. 초보자가 자주 하는 오해

#### 오해 1. 최신 버전은 무조건 최고다

호환성 검증이 필요하다.

#### 오해 2. 빌드 성공이면 앱 기능도 정상이다

실행과 실제 기능 테스트가 별도로 필요하다.

#### 오해 3. 신규 설치 테스트만 통과하면 업데이트도 안전하다

기존 데이터 migration 문제가 있을 수 있다.

#### 오해 4. lock 파일은 필요 없는 자동 생성 파일이다

재현 가능한 의존성 조합에 중요할 수 있다.

#### 오해 5. APK 파일 이름이 같으면 같은 앱이다

서명, 패키지, 버전 등도 봐야 한다.

### 38. 용어사전

| 쉬운 말 | 영어 | 뜻 |
|---|---|---|
| 설치 | install | 프로그램을 기기에 등록해 실행 가능하게 준비하는 과정 |
| 패키지 | package | 배포·설치를 위해 묶은 소프트웨어 단위 |
| 버전 | version | 소프트웨어 상태를 구분하는 번호나 이름 |
| 라이브러리 | library | 재사용하도록 만든 코드 묶음 |
| 의존성 | dependency | 내 프로그램이 필요로 하는 외부 코드나 패키지 |
| 빌드 | build | 소스와 자원을 실행·배포 가능한 결과물로 만드는 과정 |
| 컴파일 | compile | 코드를 실행 환경이 처리할 형태로 바꾸는 과정의 한 종류 |
| 설정 | configuration | 프로그램 행동을 바꾸는 값 |
| lock 파일 | lock file | 실제 선택된 의존성 버전 조합 기록 |
| 재현 가능성 | reproducibility | 같은 조건에서 같은 결과를 다시 만드는 성질 |
| 깨지는 변경 | breaking change | 기존 사용법과 호환되지 않을 수 있는 변경 |
| 롤백 | rollback | 이전 정상 상태로 되돌리는 것 |
| 마이그레이션 | migration | 기존 데이터를 새 구조로 옮기는 과정 |
| 서명 | signature | 소프트웨어 발행 주체와 무결성을 확인하는 증거 |

---

### 39. 종합 미션

상황:

> 어제까지 정상인 앱을 업데이트했다. 새 설치 기기에서는 정상인데 기존 사용자 기기에서만 실행 직후 종료된다.

확인 순서 예:

1. 구버전→신버전 업데이트 경로 재현
2. 크래시 로그 확인
3. DB schema/version 비교
4. migration 코드 확인
5. 기존 설정과 캐시 확인
6. 새 설치와 업데이트 설치 상태 비교
7. 수정 후 실제 업데이트 경로 다시 테스트

“신버전 APK가 고장”이라고 한 줄로 결론내리지 않는다.

---

### 40. 한 장 요약

1. 설치는 앱을 실행 가능하게 기기에 등록하는 과정이다.
2. APK는 Android 앱 설치 패키지다.
3. 버전은 소프트웨어 상태를 구분한다.
4. 최신 버전이 항상 호환되는 것은 아니다.
5. 의존성은 내 프로그램이 필요로 하는 외부 코드다.
6. 빌드는 소스에서 배포 가능한 결과물을 만드는 과정이다.
7. 빌드 성공과 실행 성공은 다르다.
8. 설정이 다르면 같은 코드도 다르게 동작할 수 있다.
9. lock 파일은 의존성 재현에 중요할 수 있다.
10. 업데이트 전 정상 버전을 기록하고 한 번에 작은 변경만 한다.
11. 신규 설치와 업데이트 설치는 별도로 테스트한다.
12. 문제가 생기면 rollback 가능한 상태를 유지한다.

다음 장에서는 오류를 찾는 가장 중요한 증거 중 하나인 **로그**를 처음부터 배운다.
