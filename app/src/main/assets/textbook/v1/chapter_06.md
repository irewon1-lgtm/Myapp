## V1-C06. 설치·버전·의존성 — 업데이트가 왜 깨지는가

**목표:** 앱 업데이트나 빌드 실패를 “버전 문제” 한마디로 끝내지 않고 **패키지·의존성·환경·설정·데이터 migration·서명** 중 어디가 깨졌는지 좁힐 수 있게 된다.

---

### 1. 설치 파일과 실행 환경은 분리해서 본다

Android 앱을 예로 들면 APK는 설치 패키지다. APK가 정상 파일이라고 해서 모든 기기에서 항상 정상 실행된다는 뜻은 아니다.

실행에는 여러 조건이 붙는다.

```text
앱 패키지
기기 OS 버전
CPU/ABI
필요 권한
저장 데이터
서명
외부 서버/API
```

그래서 “APK 다운로드 성공”과 “앱 설치 성공”, “실행 성공”은 서로 다른 단계다.

---

### 2. 버전은 숫자 하나가 아니라 호환성의 기록이다

버전은 보통 변경 이력을 구분하기 위한 식별자다.

```text
1.0.0
1.1.0
2.0.0
```

일부 프로젝트는 **Semantic Versioning** 같은 규칙을 쓰지만 모든 프로젝트가 똑같이 따르는 것은 아니다.

중요한 것은 숫자 모양을 외우는 것이 아니라 **어떤 변경이 들어갔는지와 무엇과 호환되는지**다.

예:

```text
앱 1.4 → API v1 기대
앱 2.0 → API v2 기대
```

서버는 v2만 제공하는데 오래된 앱이 v1을 요청하면 앱 코드가 멀쩡해도 통신이 실패할 수 있다.

---

### 3. 의존성 — 내 코드가 혼자 실행되지 않는 이유

앱은 외부 라이브러리와 프레임워크를 사용한다. 내 코드가 실행되기 위해 필요한 외부 코드나 패키지를 **의존성(dependency)**이라고 한다.

```text
내 앱
├─ UI 라이브러리
├─ 네트워크 라이브러리
├─ JSON 라이브러리
└─ DB 라이브러리
```

문제는 라이브러리끼리 서로 특정 버전을 요구할 수 있다는 것이다.

```text
Library A → Library C 2.x 필요
Library B → Library C 1.x 필요
```

이런 충돌이 있으면 빌드가 실패하거나 런타임 문제가 생길 수 있다.

#### 최신 버전이 무조건 답이 아닌 이유

모든 의존성을 한 번에 최신으로 올리면:

- API가 바뀔 수 있음
- 삭제된 함수가 있을 수 있음
- 설정 형식이 달라질 수 있음
- 최소 OS 요구사항이 바뀔 수 있음
- 서로 호환되지 않는 조합이 생길 수 있음

업데이트는 **변경 목록을 알고 작은 단위로 검증**하는 것이 안전하다.

---

### 4. lock 파일과 재현 가능한 환경

패키지 관리 도구는 실제 설치된 정확한 버전을 기록하는 파일을 만들 수 있다. 흔히 **lock file**이라고 부른다.

목적은 단순하다.

```text
내 PC에서 설치한 버전 조합
= CI에서 설치한 버전 조합
= 동료 PC에서 설치한 버전 조합
```

이 조합이 최대한 같아야 “내 컴퓨터에서는 되는데 다른 곳에서는 안 됨”을 줄일 수 있다.

lock 파일을 무조건 수정하면 안 된다는 뜻은 아니다. 업데이트할 때는 **의도적으로 변경됐는지** 확인해야 한다.

---

### 5. 빌드 — 소스코드가 설치 가능한 결과물로 바뀌는 과정

소스코드를 실제 앱으로 만들 때 컴파일, 리소스 처리, 패키징, 서명 등 여러 단계가 들어간다. 이 전체 과정을 **빌드(build)**라고 부른다.

```text
소스코드
↓
컴파일/처리
↓
리소스 결합
↓
패키징
↓
서명
↓
APK/AAB 등 산출물
```

빌드가 성공했다고 앱 기능이 정상이라는 뜻은 아니다.

```text
빌드 성공 ≠ 설치 성공 ≠ 실행 성공 ≠ 기능 정상
```

각 단계는 별도로 검증한다.

---

### 6. 설정과 코드를 분리한다

개발 환경과 운영 환경은 다를 수 있다.

```text
개발 API: https://dev.example.com
운영 API: https://api.example.com
```

이 주소가 코드 곳곳에 직접 박혀 있으면 환경 전환이 어렵고 실수도 늘어난다.

설정 파일이나 환경변수로 분리하면:

```text
같은 코드
+ 개발 설정
+ 운영 설정
```

형태로 관리하기 쉬워진다.

특히 API key나 secret은 코드에 직접 넣지 않는다.

---

### 7. migration — 코드 업데이트보다 더 위험한 데이터 업데이트

앱 버전이 바뀌면서 DB 구조가 바뀔 수 있다.

기존:

```text
users(id, name)
```

새 버전:

```text
users(id, name, email)
```

기존 사용자 DB를 새 구조로 바꾸는 과정을 **migration**이라고 한다.

신규 설치에서는 새 DB가 처음부터 만들어지므로 정상인데, 기존 사용자가 업데이트했을 때만 실패할 수 있다.

이 패턴은 매우 중요하다.

```text
신규 설치 정상
업데이트 사용자 실패
→ migration 후보가 매우 강함
```

#### migration 검증

최소한 다음을 본다.

```text
구버전 DB 준비
↓
신버전 앱으로 실제 업데이트
↓
schema version 확인
↓
row 수와 주요 데이터 확인
↓
기능 테스트
```

신규 설치만 테스트하고 업데이트를 검증했다고 말하면 안 된다.

---

### 8. 서명 — 같은 앱인지 확인하는 중요한 신원 정보

Android 앱은 디지털 서명을 사용한다. 기존 앱을 업데이트하려면 패키지 식별자와 서명 조건이 맞아야 한다.

그래서 같은 앱처럼 보여도 다른 키로 서명된 APK는 기존 앱 위에 업데이트되지 않을 수 있다.

업데이트 실패에서 확인할 것:

```text
package name
version code
signing certificate
minSdk/targetSdk
ABI
```

사용자가 “파일은 받았는데 설치가 안 됨”이라고 말하면 다운로드 문제만 볼 것이 아니라 설치 단계 증거를 확인한다.

---

### 9. rollback — 정상 상태로 돌아갈 수 있어야 한다

업데이트 전에 정상 상태를 보존해야 한다.

보존 대상 예:

- Git commit
- DB backup
- 설정 snapshot
- 이전 APK
- release hash

문제가 생겼을 때 이전 정상 상태로 되돌리는 것을 **rollback**이라고 한다.

하지만 DB migration이 이미 파괴적으로 실행된 뒤라면 APK만 이전 버전으로 되돌린다고 데이터가 자동 복구되는 것은 아니다.

그래서 업데이트는 **코드 rollback과 데이터 rollback을 따로 생각**한다.

---

### 10. 실제 사례 — 패키지를 전부 최신으로 올린 뒤 빌드 실패

잘못된 대응:

```text
A/B/C/D 전부 다른 버전으로 다시 바꿈
```

무엇이 원인인지 더 알기 어려워진다.

더 좋은 흐름:

```text
1. 마지막 정상 commit 확인
2. 변경된 dependency 목록 확인
3. 한 그룹씩 되돌리거나 올려 비교
4. build log에서 최초 실패 확인
5. 원인 패키지 조합 고정
6. 전체 회귀시험
```

---

### 11. 실제 사례 — 내 폰에서는 되는데 가족 폰에서는 설치 실패

확인 순서:

```text
파일 해시 같은가?
기존 설치 앱 package/signature 같은가?
OS 버전 조건 만족하는가?
CPU/ABI가 지원되는가?
저장공간 충분한가?
설치 프로그램 오류 메시지는 무엇인가?
```

한 기기만 실패한다고 앱 코드 전체를 다시 만들 필요는 없다.

---

### 12. release note와 changelog를 읽는 이유

라이브러리 업데이트 전에 변경사항을 확인한다.

특히 찾아볼 것:

```text
Breaking changes
Deprecated/removed API
Minimum version change
Migration guide
Security fix
Known issue
```

AI에게 요약을 맡길 수 있지만 최종 판단은 공식 문서 원문과 실제 빌드/테스트로 한다.

## 실습 1 — 단계 구분

다음 상태는 어느 단계까지 성공한 것인가?

```text
APK 다운로드 성공
설치 버튼 누르면 "앱을 설치할 수 없습니다"
```

다운로드는 성공했지만 설치는 실패했다.

---

## 실습 2 — 신규 설치와 업데이트 비교

```text
신규 설치: 정상
구버전에서 업데이트: 앱 시작 시 crash
```

우선순위 높은 후보 두 개:

- DB migration
- 이전 설정/저장 데이터 호환성

---

## 실습 3 — 버전 변경 감사

변경:

```text
libraryA 2.4 → 3.0
libraryB 1.8 → 2.0
runtime 17 → 21
```

한 번에 전부 바꾸면 어떤 문제가 있는가?

원인과 효과를 분리하기 어렵다.

---

## 실습 4 — rollback 계획

업데이트 전 기록할 것:

```text
현재 정상 commit
현재 DB schema version
DB backup 위치
현재 release APK/hash
현재 환경설정
```

여기에 하나를 더 추가한다.

## 장 끝 미니 프로젝트 — 업데이트 실패 보고서 만들기

가상의 업데이트 실패를 분석한다.

```text
v1.4 → v1.5 업데이트
신규 설치는 정상
기존 사용자 20%에서 시작 crash
DB schema가 v7 → v8로 변경됨
```

다음 항목을 채운다.

## 핵심 용어

| 용어 | 뜻 |
|---|---|
| 버전 | 소프트웨어 변경 상태를 구분하는 식별자 |
| dependency | 내 코드가 실행되기 위해 필요한 외부 패키지/라이브러리 |
| lock file | 실제 사용할 dependency 버전 조합을 고정/기록하는 파일 |
| build | 소스코드를 실행/배포 가능한 산출물로 만드는 과정 |
| configuration | 환경별 설정값 |
| migration | 기존 데이터 구조를 새 버전 구조로 변환하는 과정 |
| signing | 앱 제작/배포 신원을 확인하는 디지털 서명 과정 |
| rollback | 이전 정상 상태로 되돌리는 작업 |
| changelog/release note | 버전별 변경사항 기록 |

---

## 이 장을 끝내고 할 수 있어야 하는 것

1. 다운로드·설치·실행·기능 정상 단계를 구분한다.
2. 최신 dependency가 항상 안전하지 않은 이유를 설명한다.
3. lock file과 재현 가능한 환경의 목적을 말한다.
4. build 성공을 기능 PASS로 착각하지 않는다.
5. 신규 설치 정상/업데이트 실패에서 migration을 의심할 수 있다.
6. 앱 서명이 업데이트에 영향을 줄 수 있음을 안다.
7. release 변경 전 rollback 경로를 준비한다.
