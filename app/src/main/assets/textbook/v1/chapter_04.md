## V1-C04. 컴퓨터가 일하는 곳 — 메모리·저장장치·CPU를 처음부터

**이 장의 대상:** `RAM`, `CPU`, `캐시`, `가상메모리`라는 말을 들어봤지만 정확히 무슨 역할인지 모르는 사람.

**이 장의 목표:** “앱이 느리다”는 말을 CPU 문제라고 바로 단정하지 않고 **계산, 메모리, 저장장치, 네트워크, 화면 처리**를 나누어 생각할 수 있게 된다.

---

### 1. 스마트폰 안에는 여러 종류의 자원이 있다

스마트폰은 한 종류의 부품만으로 움직이지 않는다.

아주 단순하게 나누면 다음 자원이 함께 일한다.

```text
CPU        → 계산과 명령 실행
RAM        → 실행 중 필요한 정보를 빠르게 놓아두는 작업 공간
저장장치    → 앱, 사진, 파일을 오래 보관
GPU        → 화면·그래픽 계산에 강함
NPU        → 일부 AI 연산에 특화
네트워크    → 다른 기기와 데이터 통신
```

처음부터 세부 구조를 외울 필요는 없다.

중요한 것은 **“느리다”는 증상 하나에도 여러 자원이 원인이 될 수 있다**는 사실이다.

---

### 2. CPU는 무엇일까?

**CPU**는 프로그램의 명령을 실행하고 계산하는 핵심 장치다.

긴 영어 이름은 지금 외우지 않는다.

> **CPU = 프로그램 명령을 실제로 처리하는 중심 계산 장치**

예:

```text
숫자 더하기
조건 비교하기
반복문 실행하기
함수 호출하기
데이터 변환하기
```

이런 작업은 CPU가 관여한다.

#### 공장 비유

CPU를 공장의 작업자라고 생각해볼 수 있다.

작업자가 처리해야 할 일이 너무 많으면 줄이 길어질 수 있다.

하지만 느림이 항상 작업자 부족 때문인 것은 아니다.

부품이 안 오거나 창고에서 물건을 못 찾는 문제도 있을 수 있다.

컴퓨터도 비슷하다.

---

### 3. RAM은 무엇일까?

앱이 실행되는 동안 필요한 데이터를 빠르게 읽고 쓰기 위한 작업 공간이 필요하다.

그 역할을 하는 대표 자원이 **RAM**이다.

> **RAM = 실행 중인 프로그램이 빠르게 쓰는 임시 작업 공간**

예를 들어 앱이 실행되면:

```text
화면 상태
현재 변수 값
이미 불러온 이미지
서버에서 받은 데이터
실행 중 코드에 필요한 정보
```

등이 메모리에 올라갈 수 있다.

---

### 4. RAM과 저장장치는 다르다

초보자가 가장 많이 헷갈리는 부분이다.

#### RAM

```text
빠름
실행 중 작업에 사용
용량이 비교적 작음
전원이 꺼지면 내용이 유지되지 않는 영역이 중심
```

#### 저장장치

```text
앱 파일, 사진, 문서 등을 오래 보관
RAM보다 느린 경우가 많음
용량이 큼
전원을 꺼도 파일이 남음
```

비유하면:

```text
RAM       = 책상 위
저장장치   = 서랍장
```

책상 위에는 지금 작업 중인 서류를 올려두고, 서랍에는 오래 보관할 자료를 넣는다.

---

### 5. “메모리가 부족하다”는 말

앱이 많은 데이터를 한꺼번에 메모리에 올리면 RAM 사용량이 커질 수 있다.

예:

```text
초대형 이미지 여러 장
수십만 행 데이터
큰 JSON 전체
사용하지 않는 객체를 계속 보관
```

메모리가 부족하면 앱이 느려지거나 운영체제가 프로세스를 종료할 수도 있다.

하지만 “메모리 사용량이 높다”는 숫자 하나만으로 버그라고 단정하면 안 된다.

운영체제는 남는 메모리를 캐시로 활용하기도 한다.

측정값을 맥락과 함께 봐야 한다.

---

### 6. 메모리 누수란 무엇일까?

더 이상 필요하지 않은 데이터를 계속 붙잡고 있으면 메모리 사용량이 점점 늘어날 수 있다.

이런 문제를 흔히 **메모리 누수(memory leak)**라고 부른다.

> **메모리 누수 = 필요 없어진 데이터를 계속 참조해서 메모리가 회수되지 못하는 문제**

예:

```text
화면을 열 때마다 10MB 증가
화면을 닫아도 줄지 않음
다시 열면 또 10MB 증가
```

이런 패턴이 반복되면 의심할 수 있다.

한 번의 높은 값보다 **시간에 따른 변화**가 중요하다.

---

### 7. 저장장치가 느리면 어떤 일이 생길까?

앱이 파일이나 DB에서 많은 데이터를 읽는 작업을 한다고 하자.

저장장치 접근이 느리거나 데이터 양이 너무 크면 화면 반응도 느려질 수 있다.

이런 작업을 **입출력(I/O)**이라고 부른다.

> **I/O = 파일, 디스크, 네트워크 등에서 데이터를 읽고 쓰는 작업**

CPU가 한가해도 저장장치에서 데이터가 오기를 기다리느라 느릴 수 있다.

그래서:

> CPU 사용률이 낮다고 앱이 빠른 것은 아니다.

---

### 8. CPU가 바쁜 것과 I/O를 기다리는 것은 다르다

두 상황을 비교해보자.

#### 상황 A

```text
복잡한 계산 1억 번
```

CPU가 계속 바쁠 수 있다.

#### 상황 B

```text
큰 파일 읽기
```

CPU가 계산을 많이 하지 않아도 파일 데이터가 오기를 기다릴 수 있다.

둘 다 사용자는 “느리다”고 느끼지만 병목은 다르다.

> **병목(bottleneck) = 전체 속도를 가장 크게 제한하는 지점**

---

### 9. GPU는 무엇일까?

**GPU**는 많은 비슷한 계산을 동시에 처리하는 데 강한 장치로 발전해 왔다.

특히 그래픽과 이미지 처리에 많이 사용된다.

게임 화면, 애니메이션, 영상 처리 등에 관여할 수 있다.

> **GPU = 그래픽과 대량 병렬 계산에 강한 연산 장치**

모든 계산을 GPU로 보내면 빨라지는 것은 아니다.

작업 종류에 따라 적합한 장치가 다르다.

---

### 10. NPU는 무엇일까?

최근 스마트폰에서는 **NPU**라는 말을 자주 본다.

일부 인공지능 연산을 효율적으로 처리하도록 만든 장치다.

> **NPU = 특정 AI 연산을 효율적으로 처리하도록 설계된 연산 장치**

CPU, GPU, NPU는 모두 계산을 하지만 잘하는 작업이 다르다.

초보자는 제품 이름보다 **작업 특성에 따라 연산 장치가 나뉠 수 있다**는 점을 기억하면 된다.

---

### 11. 캐시는 무엇일까?

Chapter 1에서 캐시를 “다시 빨리 쓰기 위해 잠깐 저장해두는 것”이라고 배웠다.

컴퓨터 시스템에는 여러 층의 캐시가 있을 수 있다.

```text
CPU 캐시
메모리 캐시
앱 캐시
브라우저 캐시
네트워크 캐시
```

모두 정확히 같은 구조는 아니지만 공통 아이디어는 비슷하다.

> **다시 필요할 가능성이 높은 데이터를 가까운 곳에 두어 빠르게 쓰려는 것**

---

### 12. 캐시는 왜 문제를 만들기도 할까?

캐시는 속도를 높이지만 오래된 데이터가 남을 수 있다.

예:

```text
서버 최신 값 = 120
앱 캐시 값   = 100
```

앱이 캐시만 보여주면 사용자는 100을 보게 된다.

이때 “데이터가 틀렸다”는 증상은 실제 서버 오류가 아니라 **캐시 갱신 문제**일 수 있다.

그래서 디버깅할 때:

```text
이 값은 어디서 읽었는가?
캐시인가?
서버 최신값인가?
저장 시각은 언제인가?
```

를 확인한다.

---

### 13. 캐시 삭제를 무조건 첫 조치로 하면 안 되는 이유

문제가 생겼을 때 “캐시 삭제부터 해보세요”라는 말을 자주 본다.

가끔 해결되지만 원인을 가릴 수 있다.

캐시를 지우기 전에:

1. 현재 잘못된 값이 무엇인지 기록
2. 캐시에 실제 어떤 값이 있는지 확인
3. 서버 값과 비교
4. 캐시 정책을 확인

하면 원인을 찾는 데 더 도움이 된다.

무조건 삭제하면 증거가 사라질 수 있다.

---

### 14. 가상메모리는 무엇일까?

운영체제는 각 프로세스가 메모리를 사용하는 방식을 안전하게 관리한다.

이 과정에서 **가상메모리(virtual memory)**라는 개념을 사용한다.

첫 단계에서는 다음처럼 이해하자.

> **가상메모리 = 각 프로그램에게 자기만의 메모리 공간처럼 보이게 관리하는 운영체제의 메모리 방식**

실제 물리 RAM과 프로그램이 보는 주소가 단순히 1:1로 같은 것은 아니다.

세부 페이지 테이블 구조까지 외울 필요는 없다.

---

### 15. 왜 프로세스끼리 메모리를 마음대로 못 보게 할까?

앱 A가 앱 B의 메모리를 마음대로 읽을 수 있다면 개인정보와 보안 문제가 심각해진다.

운영체제는 프로세스 사이에 경계를 만든다.

이런 **격리(isolation)**는 시스템 안정성과 보안에 중요하다.

> **격리 = 서로 영향을 주면 안 되는 영역을 분리해 두는 것**

Android 앱의 sandbox와 연결되는 개념은 Chapter 9에서 다시 배운다.

---

### 16. 사용자 공간과 커널 공간

운영체제는 매우 중요한 핵심 기능을 일반 앱과 분리한다.

일반 앱이 실행되는 영역을 **사용자 공간(user space)**이라고 부르고, 운영체제 핵심 기능이 동작하는 영역을 **커널 공간(kernel space)**이라고 부를 수 있다.

지금은 이렇게만 기억한다.

```text
앱 → 운영체제에게 요청 → 하드웨어/자원 사용
```

앱이 모든 하드웨어를 직접 마음대로 제어하는 구조가 아니다.

---

### 17. 커널은 무엇일까?

**커널(kernel)**은 운영체제의 핵심 부분이다.

프로세스, 메모리, 장치, 파일 시스템 같은 자원을 관리한다.

> **커널 = 운영체제에서 하드웨어와 시스템 자원을 관리하는 핵심 부분**

초보자는 커널 코드를 작성할 필요 없다.

다만 로그에서 `kernel`, `permission`, `driver` 같은 말을 볼 때 “앱 코드보다 더 아래 계층의 문제일 수 있구나”라고 생각할 수 있으면 된다.

---

### 18. 시스템 호출이라는 말

일반 프로그램이 파일을 읽거나 네트워크를 사용하려면 운영체제 기능을 요청해야 한다.

이 경계를 넘는 요청을 설명할 때 **시스템 호출(system call)**이라는 용어를 사용한다.

지금은 세부 함수 이름을 외우지 않는다.

> **시스템 호출 = 프로그램이 운영체제 핵심 기능을 사용하기 위해 요청하는 통로**

---

### 19. 드라이버는 무엇일까?

카메라, 저장장치, 네트워크 칩 같은 하드웨어를 운영체제가 다루려면 장치별 제어 소프트웨어가 필요하다.

이를 **드라이버(driver)**라고 부른다.

> **드라이버 = 운영체제가 특정 하드웨어와 대화하도록 돕는 소프트웨어**

카메라 앱이 센서를 직접 제어하는 것이 아니라 여러 계층을 거칠 수 있다는 뜻이다.

---

### 20. 앱이 느리면 어디부터 볼까?

무작정 CPU부터 보지 않는다.

먼저 증상을 구체화한다.

```text
앱 시작이 느린가?
버튼 누른 뒤 결과가 느린가?
스크롤만 끊기는가?
파일 저장이 느린가?
네트워크 데이터만 늦는가?
화면이 멈추는가?
```

증상 종류에 따라 후보가 달라진다.

---

### 21. CPU 병목 예시

다음 상황을 생각해보자.

```text
복잡한 계산을 반복
CPU 사용률 높음
네트워크 사용 거의 없음
계산이 끝날 때까지 결과가 늦음
```

CPU 계산이 병목일 가능성이 있다.

하지만 측정 없이 “CPU가 원인”이라고 쓰면 안 된다.

실제 CPU 사용량과 실행 시간을 측정해야 한다.

---

### 22. 메모리 병목 예시

```text
앱 사용 시간이 길어질수록 RAM 사용량 계속 증가
화면 전환 후에도 줄지 않음
결국 앱 종료
```

메모리 누수 후보를 볼 수 있다.

하지만 캐시가 정상적으로 늘어난 것인지도 구분해야 한다.

그래서 시간에 따른 그래프가 도움이 된다.

---

### 23. I/O 병목 예시

```text
DB에서 수십만 행 조회
CPU는 매우 높지 않음
조회가 끝날 때까지 화면 지연
```

데이터 읽기와 처리 경로를 본다.

필요한 행만 읽을 수 있는지, 인덱스가 있는지, 한 번에 너무 많은 데이터를 가져오는지 확인할 수 있다.

DB 최적화는 중급 과정에서 자세히 배운다.

---

### 24. 네트워크 병목 예시

```text
앱 UI는 빠르게 반응
로컬 화면 전환도 빠름
서버 데이터만 5초 이상 늦음
```

네트워크 또는 서버 응답 지연을 의심할 수 있다.

이때 CPU 최적화를 해도 문제가 해결되지 않을 가능성이 높다.

---

### 25. 화면 렌더링 병목 예시

스크롤할 때만 화면이 끊기고 데이터 계산은 이미 끝났다고 하자.

UI 렌더링이나 이미지 처리, 너무 많은 컴포넌트 생성 등을 확인할 수 있다.

`렌더링(rendering)`이라는 말은:

> **렌더링 = 화면에 보일 결과를 실제로 그려내는 과정**

이라고 이해하면 된다.

---

### 26. 측정하지 않은 최적화의 문제

개발자는 가끔 “여기가 느릴 것 같아”라고 추측하고 코드를 바꾼다.

하지만 실제 병목이 다른 곳일 수 있다.

좋은 순서는:

```text
1. 느림 재현
2. 시간을 측정
3. 자원 사용 측정
4. 가장 큰 병목 후보 찾기
5. 하나만 수정
6. 같은 조건으로 다시 측정
```

이다.

---

### 27. 기준선이란 무엇일까?

수정 전 성능을 기록해두어야 개선됐는지 비교할 수 있다.

이를 **기준선(baseline)**이라고 한다.

예:

```text
수정 전 앱 시작: 3.2초
수정 후 앱 시작: 1.8초
```

“빨라진 것 같음”보다 훨씬 명확하다.

> **baseline = 비교를 위한 수정 전 기준값**

---

### 28. 평균만 보면 안 되는 이유

앱 실행 시간이:

```text
1초
1초
1초
10초
```

라면 평균만 보고는 “가끔 매우 느린 문제”가 가려질 수 있다.

여러 번 측정하고 최댓값, 중앙값, 느린 케이스 조건을 함께 본다.

성능도 버그처럼 **재현 조건**이 중요하다.

---

### 29. 단위 읽기

성능 자료에는 여러 단위가 나온다.

```text
ms = 밀리초
s  = 초
MB = 메가바이트
GB = 기가바이트
%  = 사용률
```

숫자만 보지 말고 무엇을 측정한 숫자인지 확인한다.

`100MB`와 `100ms`는 같은 100이어도 전혀 다른 의미다.

---

### 30. Python으로 아주 작은 성능 감각 익히기

다음 코드를 보자.

```python
count = 0
for i in range(100000):
    count = count + 1
print(count)
```

반복 횟수가 커질수록 해야 할 계산량이 늘어난다.

아직 정확한 시간 측정을 배우지 않아도 된다.

중요한 것은:

> **프로그램이 더 많은 일을 하면 보통 더 많은 시간이나 자원이 필요할 수 있다.**

---

### 31. 메모리와 파일 저장을 구분하는 연습

다음 상황을 분류한다.

#### 상황 A

앱에서 검색어를 입력했는데 앱을 완전히 종료하고 다시 켜면 사라진다.

메모리에만 있던 값일 수 있다.

#### 상황 B

사진을 저장하고 폰을 재부팅해도 남아 있다.

저장장치에 기록된 파일일 가능성이 높다.

이 차이가 RAM과 저장장치의 핵심 감각이다.

---

### 32. 실제 예제 — 이미지 때문에 앱이 종료됨

상황:

```text
작은 이미지 10장 → 정상
고해상도 이미지 500장 → 앱 종료
```

가능한 원인 후보:

- 이미지를 너무 크게 메모리에 올림
- 해상도를 줄이지 않음
- 화면 밖 이미지도 계속 보관
- 메모리 누수

무조건 “폰 성능이 안 좋아서”라고 결론내리지 않는다.

---

### 33. 실제 예제 — 시작만 느림

앱 실행 시 5초가 걸리지만 실행 후에는 빠르다.

가능한 후보:

```text
초기 DB 로딩
설정 파일 읽기
네트워크 초기 요청
큰 이미지 디코딩
너무 많은 초기 객체 생성
```

“앱 전체 성능이 느림”이 아니라 **시작 단계**로 범위를 좁힌다.

---

### 34. 실제 예제 — 스크롤만 끊김

데이터 로딩은 끝났고 버튼도 빠른데 목록을 스크롤할 때만 끊긴다.

이 경우 네트워크보다:

```text
렌더링
이미지 크기
한 화면에 만드는 UI 수
불필요한 재계산
```

같은 후보가 더 중요할 수 있다.

증상과 원인 후보를 연결하는 연습이 필요하다.

---

### 35. 초보자가 자주 하는 오해

#### 오해 1. RAM과 저장공간은 같은 것이다

아니다.

#### 오해 2. CPU 사용률이 낮으면 앱은 반드시 빠르다

아니다. I/O나 네트워크를 기다릴 수 있다.

#### 오해 3. 메모리를 많이 쓰면 항상 버그다

아니다. 캐시 등 정상 사용일 수 있다. 패턴과 한계를 봐야 한다.

#### 오해 4. 캐시를 지우면 원인이 해결된 것이다

증상만 사라지고 원인이 남을 수 있다.

#### 오해 5. GPU가 CPU보다 항상 빠르다

작업 종류에 따라 다르다.

#### 오해 6. 최적화는 코드부터 고치는 것이다

측정이 먼저다.

### 36. 용어사전

| 쉬운 말 | 영어 | 뜻 |
|---|---|---|
| CPU | CPU | 프로그램 명령을 처리하는 중심 연산 장치 |
| 메모리 | memory/RAM | 실행 중 빠르게 쓰는 작업 공간 |
| 저장장치 | storage | 앱과 파일을 오래 보관하는 장치 |
| 입출력 | I/O | 파일·네트워크 등에서 데이터를 읽고 쓰는 작업 |
| GPU | GPU | 그래픽·병렬 계산에 강한 연산 장치 |
| NPU | NPU | 일부 AI 계산에 특화된 연산 장치 |
| 캐시 | cache | 다시 빨리 쓰기 위해 데이터를 가까이 보관하는 것 |
| 메모리 누수 | memory leak | 필요 없는 데이터를 계속 잡아 메모리가 회수되지 않는 문제 |
| 가상메모리 | virtual memory | 프로세스별 메모리 공간을 관리하는 운영체제 방식 |
| 격리 | isolation | 서로 영향 주면 안 되는 영역을 분리하는 것 |
| 커널 | kernel | 시스템 자원을 관리하는 운영체제 핵심 부분 |
| 드라이버 | driver | 운영체제가 하드웨어를 제어하도록 돕는 소프트웨어 |
| 렌더링 | rendering | 화면을 실제로 그리는 과정 |
| 병목 | bottleneck | 전체 속도를 가장 크게 제한하는 지점 |
| 기준선 | baseline | 수정 전 비교 기준값 |

### 37. 확인 문제

1. RAM과 저장장치의 가장 큰 차이를 설명해보자.

3. 캐시가 오래된 값을 보여주는 문제는 왜 생길 수 있는가?
4. 메모리 누수는 어떤 패턴으로 의심할 수 있는가?
5. 최적화 전에 기준선을 측정하는 이유는 무엇인가?

### 38. 종합 진단 연습

상황:

> 앱 첫 실행은 6초 걸리지만 이후 화면 이동은 빠르다. CPU 최고 사용률은 높지 않다. 앱 실행 직후 큰 JSON 파일과 이미지 여러 장을 읽는다.

가능한 첫 판단:

- CPU만 원인이라고 보기 어렵다.
- 파일 읽기와 이미지 디코딩 같은 I/O 후보를 본다.
- 각 단계에 시간을 기록한다.
- 파일 읽기 시간을 분리 측정한다.
- 이미지 처리 시간을 분리 측정한다.

수정하기 전에 **어디에서 몇 초가 걸리는지**부터 확인한다.

### 39. 한 장 요약

1. CPU는 계산과 명령 실행을 담당한다.
2. RAM은 실행 중 빠르게 쓰는 작업 공간이다.
3. 저장장치는 앱과 파일을 오래 보관한다.
4. I/O는 파일이나 네트워크에서 데이터를 읽고 쓰는 작업이다.
5. 느림의 원인은 CPU뿐 아니라 메모리, I/O, 네트워크, UI일 수 있다.
6. 캐시는 속도를 높이지만 오래된 데이터를 보여줄 수 있다.
7. 메모리 누수는 시간에 따라 계속 증가하는 패턴을 관찰해야 한다.
8. 가상메모리와 격리는 프로세스가 안전하게 메모리를 쓰도록 돕는다.
9. 커널은 운영체제 핵심 자원 관리 부분이다.
10. 최적화 전에 반드시 재현하고 측정한다.
11. 수정 전 기준선을 남기고 수정 후 같은 조건으로 다시 측정한다.

다음 장에서는 프로그램이 파일과 시스템을 다룰 때 필요한 **권한, 터미널, 명령어, 환경변수**를 가장 쉬운 단계부터 배운다.
