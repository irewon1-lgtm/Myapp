## V1-C04. 메모리·연산장치·커널 경계

**원본 Lesson 매핑:** V1-09, V1-10, V1-11, V1-12

### 1. 현실 문제에서 시작하기

휴대폰이 느릴 때 “용량이 부족해서 그래”라는 말을 자주 한다. 하지만 저장공간 부족, RAM 부족, CPU 과부하, GPU 렌더링 문제, NPU 추론 부하, 네트워크 대기는 서로 다른 자원 문제다. 숫자가 모두 GB·%·초로 표시되다 보니 초보자는 한 원인으로 뭉뚱그리기 쉽다.

이 장은 하드웨어 상세 설계가 목적이 아니다. **어떤 작업이 어떤 자원을 쓰고, 그 자원이 부족할 때 어떤 증거가 나타나는지** 구분하는 실전 감각을 만든다. 또한 앱이 하드웨어를 직접 다루는 것이 아니라 커널·드라이버·system call 같은 운영체제 경계를 통과한다는 사실을 연결한다.

### 2. Mental Model

```text
앱(user space)
   ↓ system call / framework
OS kernel
   ├─ CPU scheduler
   ├─ virtual memory
   ├─ file system
   ├─ network stack
   └─ device drivers
        ↓
CPU / RAM / storage / GPU / NPU / network hardware
```

앱은 “파일을 읽어라”라고 요청하지만 실제 저장장치의 전기신호를 직접 다루지 않는다. 운영체제와 드라이버가 중간 경계를 만든다. 이 경계 때문에 권한·격리·오류처리가 가능하고, 동시에 성능 진단에서는 어느 계층이 느린지 구분해야 한다.

### 3. 핵심 개념 해부

#### RAM·저장장치·캐시

RAM은 실행 중 데이터와 코드가 빠르게 접근되는 휘발성 메모리다. 저장장치는 앱과 사진을 전원이 꺼져도 유지한다. 캐시는 더 느린 원본에 매번 접근하지 않도록 최근·자주 쓰는 데이터를 가까이에 복사해 두는 전략이다.

저장공간이 200GB 남았다고 RAM 부족이 해결되는 것은 아니다. 반대로 RAM이 넉넉해도 저장공간이 꽉 차면 앱 업데이트나 파일 저장이 실패할 수 있다. 진단 시 “어느 자원의 잔량/사용률을 보고 있는가”부터 확인한다.

#### 가상메모리와 주소공간

각 프로세스는 자신만의 가상 주소공간을 가진 것처럼 동작한다. 운영체제는 이를 물리 메모리와 매핑하고 프로세스 간 격리를 제공한다. 그래서 한 앱이 다른 앱의 임의 메모리를 직접 읽지 못하도록 경계가 생긴다.

메모리 압박이 심해지면 앱이 종료되거나 OOM이 발생할 수 있다. Android는 필요에 따라 중요도가 낮은 프로세스를 종료할 수 있으므로 “앱이 백그라운드에 있었으니 상태가 메모리에 계속 남아 있을 것”이라고 가정하면 안 된다. 중요한 상태는 영속 저장을 고려해야 한다.

#### CPU·GPU·NPU를 작업 성격으로 구분

CPU는 범용 제어와 다양한 연산을 유연하게 처리한다. GPU는 많은 유사 연산을 병렬로 수행하는 데 강하고, NPU는 신경망 추론처럼 특정 AI 계산을 효율적으로 처리하도록 설계된 경우가 많다. 그러나 ‘AI=무조건 NPU’, ‘그래픽=무조건 GPU’처럼 단순화하면 실제 플랫폼 차이를 놓친다.

실전에서는 작업 종류와 측정치를 본다. JSON 파싱·앱 로직이 CPU를 쓰고, 화면 렌더링이 GPU에 영향을 주며, 온디바이스 모델은 장치 지원에 따라 CPU/GPU/NPU를 사용할 수 있다. 병목은 하드웨어 이름보다 **처리시간·사용률·대기시간**으로 확인한다.

#### CPU-bound와 I/O-bound

CPU-bound는 계산 자체가 병목인 경우고, I/O-bound는 디스크·네트워크·DB처럼 외부 결과를 기다리는 시간이 큰 경우다. 둘은 해결법이 다르다. CPU-bound는 알고리즘 개선·병렬 처리·하드웨어 가속이 후보이고, I/O-bound는 비동기 처리·캐시·배치·네트워크 최적화가 후보가 된다.

무작정 스레드를 늘리는 것은 측정 없는 처방이다. 먼저 프로파일이나 로그로 시간이 어디서 소비되는지 확인한다.

#### 커널·드라이버·system call

커널은 프로세스 스케줄링, 메모리, 파일, 네트워크, 장치 접근 같은 핵심 자원을 관리한다. user space 앱은 제한된 인터페이스를 통해 커널 기능을 요청한다. 드라이버는 특정 하드웨어와 운영체제 사이의 구체적 연결을 담당한다.

이 구조를 알면 “앱 코드가 정상인데 카메라가 안 된다” 같은 상황에서 권한, OS API, 드라이버/장치 상태라는 다른 후보를 떠올릴 수 있다. 다만 초보 단계에서 system call 번호나 커널 내부 구현을 암기할 필요는 없다.

### 3A. 개념을 연결해서 생각하기 — “느림”을 자원 모델로 번역하기

메모리·CPU·저장장치·GPU·NPU를 각각 따로 외우기보다 **작업이 어디서 시간을 소비하는지**로 연결해서 본다. 사용자가 버튼을 눌렀을 때 앱은 입력 검증, 로컬 DB 조회, 이미지 디코딩, 네트워크 호출, AI 추론, UI 렌더링을 연속으로 수행할 수 있다. 이 중 어느 단계가 길어도 사용자는 하나의 “느림”으로 느낀다.

RAM은 실행 중 상태를 담는 공간이지만 모든 데이터가 영구히 남아 있는 저장소가 아니다. 앱을 background로 보냈을 때 process가 종료될 수 있기 때문에 중요한 작업진행을 메모리 변수에만 두면 복원되지 않는다. 반대로 DB에 모든 중간값을 무조건 저장하면 I/O가 늘고 구조가 복잡해질 수 있다. **상태의 수명(lifetime)**과 복구 필요성을 보고 어디에 둘지 선택한다.

cache는 성능을 높이지만 새로운 종류의 버그를 만든다. 오래된 데이터(stale), invalidation 실패, 저장공간 증가, 서로 다른 계층 cache 불일치가 대표적이다. “cache를 넣으면 빨라진다”보다 “원본은 무엇이고 언제 cache를 버리는가”를 먼저 정해야 한다. Power User는 cache hit/miss 개념을 이해하되 복잡한 CPU cache replacement algorithm까지 외울 필요는 없다.

가상메모리는 “RAM보다 큰 프로그램을 돌리기 위한 기술” 하나로만 이해하면 좁다. 더 중요한 실용적 의미는 **process마다 독립된 주소공간을 제공해 격리와 관리가 쉬워진다**는 것이다. 어떤 앱의 잘못된 포인터가 다른 앱 메모리를 그대로 덮어쓰지 못하게 하는 기반 중 하나다. Android sandbox와 연결해서 이해하면 기억하기 쉽다.

CPU/GPU/NPU의 구분에서도 마케팅 명칭보다 workload 특성을 본다. 순차 제어와 다양한 분기 로직은 CPU에 적합하고, 같은 종류의 많은 연산은 GPU 등 병렬 장치가 유리할 수 있으며, 특정 neural network operator를 효율적으로 처리하는 accelerator가 NPU 계열이다. 그러나 실제 Android 앱은 driver, framework, model format, vendor support에 따라 어떤 장치를 쓸지가 달라진다. **하드웨어 이름만 보고 성능을 예측하지 않는다.**

커널 경계는 보안과 안정성의 핵심이다. 앱은 파일시스템·네트워크·장치에 직접 임의 접근하는 대신 OS가 제공하는 API를 통해 요청한다. 이 구조 덕분에 권한검사, scheduling, isolation이 가능하다. 따라서 `permission denied`, `resource busy`, `out of memory` 같은 오류는 “앱 코드 한 줄” 밖의 운영체제 상태를 반영할 수 있다.

### 4. Worked Examples

#### Worked Example A — 저장공간 vs RAM

상황 A: 사진을 찍을 때 `storage full`이 뜨지만 앱 전환은 부드럽다. 저장공간을 본다.  
상황 B: 여러 앱을 오가면 앱이 자주 다시 로드되지만 저장공간은 충분하다. 메모리 압박을 의심한다.  
상황 C: 특정 연산에서 기기가 뜨거워지고 처리속도가 점점 느려진다. CPU/GPU 부하와 thermal throttling을 본다.

같은 “느림”이라도 관찰 증거가 다르다.

#### Worked Example B — 파일 읽기의 경계

앱 코드가 `read(file)`을 호출한다고 생각해 보자. 실제 흐름은 애플리케이션 함수 → 런타임/프레임워크 → 운영체제 파일 API → 커널 파일시스템 → 저장장치 드라이버 → 장치 → 데이터 반환으로 이어진다. 오류가 `permission denied`라면 파일 내용 이전에 접근경계에서 막힌 것이다. `file not found`라면 경로/이름 해석을 먼저 본다.

### 4A. 미니 사례집

**사례 1 — 저장공간 100GB 남았는데 앱이 자꾸 다시 로드됨**  
저장공간과 RAM을 분리한다. 여러 앱을 오갈 때 process가 재생성된다면 memory pressure/lifecycle을 본다.

**사례 2 — AI 모델 파일 다운로드는 빠른데 추론이 느림**  
network는 이미 끝났다. model loading, CPU/GPU/NPU backend, thermal, input size를 측정한다.

**사례 3 — 기기가 뜨거워지며 점점 느림**  
처음 속도와 10분 후 속도를 나란히 기록한다. thermal throttling과 지속 부하를 의심하되 실제 temperature/performance trace로 확인한다.

**사례 4 — 앱 파일읽기만 실패**  
파일은 존재한다. path, permission, storage scope, OS API, device health 순으로 본다. 저장장치 하드웨어 고장을 첫 후보로 두지 않는다.

### 5. 그럴듯하지만 틀린 판단

1. 저장공간과 RAM을 같은 ‘용량’으로 취급한다.
2. CPU 사용률이 낮으면 앱 성능 문제는 없다고 생각한다.
3. AI 기능은 항상 NPU를 사용한다고 생각한다.
4. 앱이 하드웨어를 직접 제어한다고 생각한다.

### 5A. 자원 진단 표

| 증상 | 우선 확인 | 흔한 오진 |
|---|---|---|
| 앱이 자주 재시작/상태소실 | process lifecycle, RAM pressure, state persistence | 저장공간 삭제 |
| 파일 저장 실패 | free storage, path, permission, quota | RAM 부족 |
| 계산만 느림 | CPU/GPU/NPU workload, input size, thermal | 인터넷 탓 |
| 요청 대기 길음 | network/server timing | CPU 업그레이드 |
| 시간이 갈수록 느림 | leak, thermal, cache growth | 무조건 재부팅 |
| 한 기능만 권한오류 | OS permission/sandbox | 앱 전체 재설치 |

표의 목적은 원인을 단정하는 것이 아니라 **다음 측정값을 정하는 것**이다.

### 5B. 모바일 하드웨어 수치를 읽는 법

사양표의 숫자는 실제 앱 성능과 일대일 대응하지 않는다. CPU core 수가 많아도 모든 작업이 병렬화되지 않으며, 최대 clock은 지속 성능이 아니다. 발열과 전력 제한 때문에 장시간 부하에서는 동작 주파수가 낮아질 수 있다.

RAM도 “많을수록 앱 하나가 모두 쓸 수 있다”는 뜻이 아니다. OS와 다른 앱이 메모리를 공유하고, Android는 process 중요도와 memory pressure에 따라 background process를 종료할 수 있다. 따라서 앱은 process death 후에도 필요한 사용자 상태를 복구할 수 있어야 한다.

저장장치는 용량뿐 아니라 I/O latency와 throughput이 있다. 작은 DB random read와 대용량 sequential file copy는 같은 저장장치를 전혀 다르게 사용한다. “SSD/UFS니까 빠름”으로 끝내지 않고 실제 workload를 본다.

GPU/NPU 성능도 model architecture, precision, supported operator, memory transfer overhead의 영향을 받는다. accelerator로 보내기 위해 데이터를 변환하는 비용이 작지 않으면 작은 작업에서는 CPU가 더 나을 수도 있다. AI 앱을 최적화할 때 vendor benchmark보다 자신의 model/input에서 측정한다.

커널·driver 문제를 의심할 때는 앱에서 임의로 low-level 설정을 건드리기보다 OS update, official device diagnostics, crash/ANR trace를 먼저 본다. Power User의 목표는 kernel hacker가 되는 것이 아니라 **문제가 앱 경계 밖에 있다는 증거를 확보하는 것**이다.

### 6. Guided Lab

Galaxy의 설정/디바이스 케어 등에서 저장공간과 메모리 정보를 각각 기록한다. 앱 여러 개를 실행하기 전후 메모리 상태를 비교하고, 큰 파일을 다운로드하기 전후 저장공간을 비교한다. 값이 어떻게 다르게 변하는지 표로 남긴다.

그 다음 `계산`, `파일 읽기`, `웹 요청`, `화면 애니메이션`, `온디바이스 AI 추론` 다섯 작업을 CPU/GPU/NPU/I/O 후보에 배치하되 “실제 플랫폼에서는 측정으로 확인해야 함” 표시를 추가한다.

### 7. Independent Lab

“앱이 5초 동안 멈춘다”는 한 문장만 주어진 상태에서 CPU/RAM/storage/network/server 각각을 검증할 수 있는 관찰 항목을 하나씩 설계하라. 측정 전에는 어느 것도 원인으로 확정하지 않는다.

### 8. Debug Challenge

**상황:** 이미지 분석 기능이 처음에는 1초인데 10분 사용하면 4초로 느려진다. 네트워크는 사용하지 않는다.

가설: 메모리 누수, CPU/GPU 지속부하, thermal throttling, 캐시 변화. 각 가설을 구분할 증거를 정하고 한 번에 하나씩 실험한다. 단순 재부팅으로 증상을 없애고 끝내지 않는다.

### 9. AI Audit

AI가 “RAM이 부족하니 사진을 지우세요”라고 답했다면 저장공간과 RAM을 혼동한 것이다. AI 제안이 어떤 자원 지표를 근거로 하는지, 측정값이 있는지, OS가 해당 자원을 어떻게 관리하는지, 수정이 사용자 데이터 손실을 일으키는지 검사한다.

첫 판단: disk/DB I/O wait 후보를 본다.  
증거 없이 바로 수정하지 말고, 이 판단을 반박할 수 있는 확인 항목도 하나 적는다.

**드릴 4. 온디바이스 모델인데 인터넷을 끄면 안 됨**  
첫 판단: model/resource가 원격에서 추가 fetch되는지, 기능이 정말 on-device인지 확인한다.  
증거 없이 바로 수정하지 말고, 이 판단을 반박할 수 있는 확인 항목도 하나 적는다.

**드릴 5. 앱 crash가 OOM과 함께 발생**  
첫 판단: heap growth, bitmap/model allocation, lifecycle release를 본다.  
증거 없이 바로 수정하지 말고, 이 판단을 반박할 수 있는 확인 항목도 하나 적는다.

**드릴 6. 카메라 접근 실패**  
첫 판단: 앱 코드뿐 아니라 permission→framework→driver/device 경계를 본다.  
증거 없이 바로 수정하지 말고, 이 판단을 반박할 수 있는 확인 항목도 하나 적는다.

이 미니드릴의 목표는 정답 암기가 아니다. **증상 → 계층 → 확인할 증거**를 30초 안에 연결하는 습관을 만드는 것이다.
