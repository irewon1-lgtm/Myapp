## V1-C04. 컴퓨터가 일하는 곳 — CPU·RAM·저장장치·I/O·병목

**목표:** “앱이 느리다”를 한 문장으로 끝내지 않고 CPU, 메모리, 저장장치, 네트워크, UI 작업 중 어디가 병목인지 증거로 좁힐 수 있게 된다.

---

### 1. CPU·RAM·저장장치는 역할이 다르다

세 개를 길게 외울 필요는 없다.

```text
CPU        = 계산과 명령 실행
RAM        = 실행 중 빠르게 쓰는 작업 공간
저장장치    = 앱·파일·데이터를 오래 보관
```

앱이 실행되면 필요한 코드와 데이터 일부가 RAM에 올라가고 CPU가 명령을 처리한다. 앱을 종료해도 남아야 하는 파일과 DB는 저장장치에 보관된다.

#### 왜 이 구분이 중요한가

“용량이 부족하다”라는 말도 무엇이 부족한지에 따라 다르다.

```text
저장공간 부족 → 새 파일/업데이트 저장 실패 가능
RAM 부족      → 앱 강제 종료·재로딩·성능 저하 가능
CPU 과부하    → 계산이 늦어지고 UI 반응 저하 가능
```

숫자가 커 보인다고 서로 비교하면 안 된다.

```text
8GB RAM
256GB 저장공간
100Mbps 네트워크
```

측정 대상과 단위가 다르다.

---

### 2. I/O — 계산보다 기다리는 시간이 더 길 수 있다

**I/O(Input/Output)**는 프로그램이 외부에서 데이터를 읽거나 쓰는 작업을 넓게 가리킨다.

대표 예:

- 파일 읽기/쓰기
- DB 읽기/쓰기
- 네트워크 요청/응답
- 디스크에서 이미지 읽기

CPU 계산은 매우 빠른데 파일이나 네트워크를 기다리느라 앱이 느릴 수 있다.

```text
CPU 계산 2ms
파일 읽기 80ms
네트워크 응답 500ms
```

이 상황에서 CPU를 더 빠르게 해도 전체 체감 속도는 크게 안 바뀔 수 있다.

#### 병목

전체 작업 중 가장 오래 걸리거나 흐름을 제한하는 지점을 **병목(bottleneck)**이라고 한다.

```text
총 1000ms
CPU 50ms
DB 100ms
네트워크 800ms
UI 50ms
```

우선순위는 네트워크 쪽이다.

성능 개선은 “느려 보이는 코드”를 고르는 것이 아니라 **측정값에서 가장 큰 병목을 찾는 일**이다.

---

### 3. 메모리 문제는 두 종류로 나눠 본다

메모리 관련 문제를 모두 “RAM 부족”이라고 부르면 안 된다.

#### 실제 사용량이 너무 큰 경우

큰 이미지, 거대한 리스트, 중복 데이터 등을 한꺼번에 들고 있을 수 있다.

```text
이미지 1000장 원본을 동시에 메모리에 올림
```

필요한 크기로 줄여 읽거나 일부만 유지하는 방식이 필요할 수 있다.

#### 사용이 끝난 데이터가 계속 남는 경우

더 이상 필요 없는 객체를 계속 참조하면 메모리가 회수되지 않을 수 있다. 이를 흔히 **메모리 누수(memory leak)**라고 부른다.

초급 단계에서 가비지 컬렉션 세부를 외울 필요는 없다.

핵심은:

```text
정상: 작업 종료 → 필요 없는 데이터 해제 가능
문제: 화면을 떠나도 큰 데이터가 계속 참조됨
```

앱을 오래 사용할수록 메모리 사용량이 계속 증가한다면 누수 후보를 본다.

---

### 4. 캐시는 속도를 올리지만 오래된 데이터를 만들 수 있다

캐시는 느린 작업을 반복하지 않기 위해 이전 결과를 저장해 다시 쓰는 방식이다.

예:

```text
첫 이미지 로딩: 네트워크에서 500ms
두 번째 로딩: 캐시에서 20ms
```

하지만 캐시는 두 문제를 만든다.

1. 너무 많이 저장하면 메모리/저장공간을 많이 사용한다.
2. 갱신 규칙이 틀리면 오래된 데이터를 보여준다.

그래서 캐시에는 보통 이런 질문이 따라온다.

```text
언제 저장하는가?
얼마나 오래 유효한가?
언제 지우는가?
새 데이터와 충돌하면 무엇을 우선하는가?
```

성능과 정확성 사이의 균형이 필요하다.

---

### 5. 가상메모리는 RAM을 무한하게 만드는 마법이 아니다

운영체제는 프로그램마다 메모리 주소 공간을 관리하고 필요에 따라 실제 RAM과 저장장치를 조합해 사용할 수 있다. 이런 메모리 관리 체계를 설명할 때 **가상메모리(virtual memory)**라는 개념이 나온다.

초보자에게 중요한 것은 세부 페이지 테이블이 아니다.

> **프로그램이 보는 메모리와 실제 물리 RAM의 배치가 1:1로 단순하지 않다.**

그리고 저장장치를 RAM 대신 쓰는 상황은 일반적으로 훨씬 느리다. “저장공간이 많으니 RAM도 충분하다”는 결론은 틀리다.

---

### 6. CPU·GPU·NPU는 잘하는 일이 다르다

모든 연산을 CPU만 하는 것은 아니다.

```text
CPU = 범용적인 순차/분기 작업에 강함
GPU = 많은 비슷한 계산을 병렬로 처리하는 데 강함
NPU = 신경망/AI 연산에 특화된 가속기
```

그렇다고 GPU/NPU를 쓰면 무조건 빨라지는 것은 아니다.

데이터를 옮기는 비용, 지원되는 연산, 모델 크기, 드라이버와 라이브러리 등의 조건이 맞아야 한다.

앱이 느리다는 이유만으로 “GPU를 써야 한다”고 결론내리는 것은 성능 진단이 아니다.

---

### 7. 커널과 앱의 경계

앱은 하드웨어를 마음대로 직접 제어하지 않는다. 운영체제의 **커널(kernel)**이 CPU, 메모리, 파일, 네트워크, 장치 같은 자원을 관리하고 앱의 요청을 중재한다.

아주 단순하게 보면:

```text
앱 코드
↓
운영체제 API
↓
커널
↓
하드웨어/장치
```

파일 읽기, 네트워크 전송, 카메라 사용처럼 자원 접근이 필요한 작업은 운영체제 경계를 거친다.

이 개념은 권한과 보안을 이해할 때 중요하다. 앱이 “원한다”고 해서 모든 파일이나 장치를 쓸 수 있는 것은 아니다.

---

### 8. 성능 문제는 baseline부터 만든다

**baseline**은 비교 기준이다.

예를 들어 검색이 느리다고 하자.

```text
수정 전 검색: 평균 1.8초
```

코드를 바꾼 뒤:

```text
수정 후 검색: 평균 1.2초
```

같은 조건으로 측정했다면 개선을 말할 근거가 생긴다.

반대로:

```text
수정 전: 집 Wi-Fi
수정 후: 회사 5G
```

처럼 조건이 달라지면 코드 개선 효과인지 환경 차이인지 알기 어렵다.

#### 측정할 수 있는 것

- 실행 시간
- CPU 사용률
- 메모리 사용량
- 파일/DB I/O 시간
- 네트워크 지연
- 렌더링 시간
- 요청 횟수

처음부터 모든 지표를 모을 필요는 없다. **가설과 관련된 지표만 측정한다.**

---

### 9. 실제 사례 — 리스트 스크롤이 끊김

가능한 원인은 여러 개다.

```text
A. 화면마다 큰 이미지를 원본 크기로 디코딩
B. 스크롤 때마다 DB를 다시 조회
C. UI 스레드에서 무거운 계산
D. 네트워크 이미지를 반복 다운로드
E. 불필요하게 전체 리스트를 다시 렌더링
```

전부 가능하므로 한 번에 다 고치지 않는다.

진단 예:

```text
1. 네트워크를 끊어도 끊기는가?
2. 이미지 없는 목록에서는 부드러운가?
3. CPU가 급증하는가?
4. 메모리가 계속 증가하는가?
5. DB 조회가 스크롤마다 실행되는가?
```

이런 비교로 후보를 제거한다.

---

### 10. 실제 사례 — 앱 시작이 5초 걸림

시작 단계별 시간을 기록했다고 하자.

```text
앱 프로세스 시작   300ms
DB migration      2700ms
설정 읽기          100ms
네트워크 요청      1400ms
첫 화면 렌더링      500ms
```

가장 큰 병목은 DB migration이다.

여기서 버튼 색이나 이미지 캐시부터 고치는 것은 우선순위가 아니다.

만약 migration이 첫 실행에만 발생한다면 “항상 느림”과 “업데이트 직후 한 번 느림”도 구분해야 한다.

---

### 11. 성능 최적화에서 흔한 잘못된 행동

#### 측정 없이 리팩터링

코드를 예쁘게 정리했다고 빨라진다는 보장은 없다.

#### 가장 눈에 띄는 코드부터 고침

긴 함수가 병목일 수도 있지만 실제 시간은 짧을 수 있다.

#### 한 번에 여러 최적화

무엇이 효과가 있었는지 알 수 없다.

#### 평균만 봄

평균 100ms라도 일부 사용자가 3초를 경험한다면 문제가 될 수 있다. 필요하면 최악값이나 상위 지연 구간도 본다.

#### 기능을 깨면서 빠르게 만듦

정확성이나 데이터 안정성을 잃은 성능 개선은 성공이 아니다.

## 실습 1 — 병목 찾기

```text
파싱 30ms
DB 70ms
네트워크 900ms
UI 50ms
```

우선 조사할 곳은 어디인가?

정답: 네트워크.

---

## 실습 2 — RAM과 저장공간 구분

상황:

```text
저장공간 100GB 남음
앱을 오래 쓰면 메모리 사용량이 계속 올라가고 결국 종료됨
```

저장공간이 충분하다는 사실은 RAM/메모리 누수 문제를 반박하지 못한다.

---

## 실습 3 — 캐시 판단

```text
첫 실행: 가격 180 표시
1초 뒤: 200으로 갱신
```

이 동작 자체는 캐시 사용 전략일 수 있다.

하지만 10분 뒤에도 180만 보인다면 어떤 것을 볼까?

```text
캐시 만료
최신 요청 성공 여부
상태 갱신
```

---

## 실습 4 — 잘못된 비교 찾기

```text
수정 전: Galaxy Tab, Wi-Fi
수정 후: 고성능 PC, 유선인터넷
```

이 결과만으로 코드가 빨라졌다고 결론내릴 수 없다. 조건이 다르기 때문이다.

## 핵심 용어

| 용어 | 뜻 |
|---|---|
| CPU | 명령과 계산을 수행하는 범용 연산장치 |
| RAM | 실행 중 빠르게 사용하는 작업 메모리 |
| 저장장치 | 파일과 앱 데이터를 오래 보관하는 장치 |
| I/O | 파일·DB·네트워크 등과 데이터를 읽고 쓰는 작업 |
| 병목(bottleneck) | 전체 속도를 가장 크게 제한하는 지점 |
| 캐시(cache) | 느린 작업 결과를 재사용하기 위해 저장하는 방식 |
| 가상메모리 | 운영체제가 프로그램의 메모리 주소 공간을 관리하는 체계 |
| GPU | 대량 병렬 계산에 강한 연산장치 |
| NPU | 신경망 연산에 특화된 가속기 |
| 커널(kernel) | 운영체제에서 자원과 하드웨어 접근을 관리하는 핵심 부분 |
| baseline | 수정 전후를 비교하기 위한 기준 측정값 |

---

## 이 장을 끝내고 할 수 있어야 하는 것

1. CPU·RAM·저장장치 역할을 구분한다.
2. I/O가 전체 성능 병목이 될 수 있음을 설명한다.
3. 메모리 부족과 저장공간 부족을 같은 것으로 보지 않는다.
4. 캐시의 속도 이점과 오래된 데이터 위험을 같이 설명한다.
5. GPU/NPU가 무조건 빠른 해결책이 아님을 안다.
6. 성능 개선 전 baseline을 측정해야 하는 이유를 설명한다.
7. 느린 기능을 CPU/메모리/I/O/네트워크/UI 후보로 나눌 수 있다.
