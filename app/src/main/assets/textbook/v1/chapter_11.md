## V1-C11. 종합 시스템 장애 진단 프로젝트

**목표:** 앞 10장에서 배운 개념을 따로 말하는 수준을 넘어, 실제 장애 하나를 **증상 정의 → 계층 분리 → 증거 수집 → 가설 → 최소 수정 → 회귀시험 → 인계**까지 끝낼 수 있게 된다.

이 장에서는 새 용어를 거의 추가하지 않는다. 이미 배운 도구를 실제 문제에 적용한다.

---

### 프로젝트 진행 규칙

모든 프로젝트는 다음 순서를 지킨다.

```text
1. 증상을 검증 가능한 문장으로 작성
2. 정상 비교군과 실패 비교군 확보
3. 시스템 경로를 단계로 분리
4. 원본 증거 보존
5. 원인 가설 3개 이상 작성
6. 가장 싸고 안전한 실험부터 진행
7. 원인이 확인되면 최소 수정
8. 원래 실패 케이스 재검증
9. 관련 정상 기능 회귀시험
10. 남은 위험과 rollback 기록
```

금지:

- 원인 확인 전 전체 재설치
- 여러 수정 동시 적용
- 실행하지 않은 테스트를 PASS 처리
- AI 설명을 실행 증거처럼 사용
- 실패 데이터를 임의 숫자로 채움

# 프로젝트 A. 가족 일정 앱 — 배우자 폰만 알림이 안 온다

## A-1. 증상

```text
엄마 폰: 일정 추가 알림 정상
아빠 폰: 일정 추가 알림 정상
배우자 폰: 알림 미수신
사용자 본인 폰: 작성자라 알림 대상 제외
```

나쁜 문제 정의:

```text
FCM이 고장났다.
```

좋은 문제 정의:

```text
같은 일정 이벤트에서 수신 대상 3명 중 2명은 정상 수신하고,
배우자 기기만 5회 연속 화면 알림이 표시되지 않는다.
```

## A-2. 시스템 지도

```text
일정 저장
↓
서버 이벤트 생성
↓
수신자 계산
↓
각 기기 token 조회
↓
push provider 요청
↓
배우자 기기 수신
↓
Android 권한/channel/background 정책
↓
알림 표시
```

## A-3. 가설

```text
H1 배우자 기기 token이 오래됨
H2 배우자 기기 알림 channel이 꺼짐
H3 서버 수신자 계산에서 배우자 제외
H4 provider가 배우자 token 전송을 거절
H5 배터리/백그라운드 제한
```

## A-4. 비교표

| 항목 | 엄마 정상 | 배우자 실패 |
|---|---|---|
| 앱 버전 | | |
| 로그인 계정 | | |
| token 등록 시각 | | |
| notification permission | | |
| channel | | |
| battery restriction | | |
| provider response | | |

## A-5. 가장 싼 실험

재설치보다 먼저:

```text
서버 수신자 목록 확인
token 비교
provider response 비교
permission/channel 비교
```

## A-6. 완료 기준

```text
배우자 기기 동일 이벤트 5회 중 5회 정상 수신
엄마/아빠 기존 수신 유지
작성자 제외 규칙 유지
앱 재실행 후에도 정상
```

단 한 번 성공은 완료가 아니다.

# 프로젝트 B. 국내주식 앱 — 6개월 수익률이 외부 데이터와 다르다

## B-1. 증상

```text
일부 종목에서 앱의 6개월 변동률이
신뢰 가능한 외부 원자료 계산과 크게 다름
```

## B-2. 시스템 지도

```text
종목 코드
↓
가격 데이터 소스
↓
현재 기준일
↓
6개월 전 목표일
↓
실제 거래일 선택
↓
수정주가/corporate action 처리
↓
수익률 계산
↓
DB 저장
↓
API/UI 표시
```

## B-3. 가설

```text
H1 6개월 기준일 계산이 잘못됨
H2 휴장일 처리 오류
H3 주식분할/병합 반영 차이
H4 종목 코드 mapping 오류
H5 과거 cache 값
H6 퍼센트 표시 변환 오류
```

## B-4. 한 종목을 처음부터 손계산한다

예:

```text
현재가 = 12,000
6개월 기준 가격 = 10,000
```

단순 수익률:

```text
(12,000 - 10,000) / 10,000 × 100 = 20%
```

앱이 2000%라고 표시한다면 원본 가격보다 표시/스케일 문제가 강할 수 있다.

앱이 -30%라면 시작 가격이나 corporate action 처리부터 본다.

## B-5. 전체 수정 전에 원인 유형 집계

샘플 50종목을 검사해서:

```text
기준일 오류 20
분할 반영 오류 8
mapping 오류 5
정상 17
```

처럼 유형을 나눈다.

가장 큰 원인부터 수정한다.

## B-6. 완료 기준

```text
샘플 종목 원자료 재계산과 허용 오차 내 일치
분할/병합 종목 별도 PASS
휴장일 경계 PASS
기존 정상 종목 회귀 PASS
```

# 프로젝트 C. APK 업데이트 — 신규 설치는 되는데 기존 사용자 업데이트가 실패한다

## C-1. 증상

```text
v1.4 신규 설치: 정상
v1.4 → v1.5 업데이트: 일부 기기 시작 crash
v1.5 신규 설치: 정상
```

이 패턴은 중요하다.

신규 설치와 업데이트의 차이는 **기존 데이터·설정·서명·migration 경로**다.

## C-2. 시스템 지도

```text
기존 APK/package/signature
↓
새 APK 설치
↓
앱 시작
↓
기존 설정 로드
↓
DB migration
↓
새 코드가 옛 데이터 읽기
↓
첫 화면
```

## C-3. 가설

```text
H1 DB migration 실패
H2 구버전 설정값 형식 호환 실패
H3 package/signature 불일치
H4 특정 OS/ABI 문제
H5 오래된 cache 데이터 파싱 실패
```

## C-4. upgrade fixture 만들기

실제 구버전 데이터를 보존한 테스트 환경을 만든다.

```text
v1.4 설치
↓
샘플 데이터 생성
↓
DB/설정 상태 기록
↓
v1.5로 실제 업데이트
↓
로그·schema·row count 비교
```

신규 설치만으로 migration 테스트를 대신하지 않는다.

## C-5. rollback 설계

업데이트 전:

```text
정상 v1.4 APK
Git commit
DB backup
schema version
설정 snapshot
```

을 보존한다.

DB가 이미 새 구조로 바뀐 뒤 옛 APK로 돌아가면 오히려 더 깨질 수 있으므로 데이터 rollback 가능성도 따로 본다.

## C-6. 완료 기준

```text
구버전→신버전 실제 업데이트 PASS
신규 설치 PASS
기존 데이터 row count 보존
핵심 기능 회귀 PASS
서명 검증 PASS
```

# 프로젝트 D. 자동 수집 — 같은 데이터가 두 번 저장된다

## D-1. 증상

```text
09:00 자동 수집이 하루 한 번 실행돼야 하는데
일부 날짜에 동일 데이터가 2세트 저장됨
```

## D-2. 시스템 지도

```text
scheduler
↓
job 생성
↓
worker 실행
↓
API 요청
↓
데이터 변환
↓
DB 저장
↓
완료 기록
```

## D-3. 로그에 필요한 ID

```text
scheduleId
jobId
runId
sourceKey
date
```

이 ID가 없으면 중복 실행인지 중복 저장인지 구분하기 어렵다.

## D-4. 가설

```text
H1 scheduler가 두 번 trigger
H2 worker timeout 후 retry가 기존 작업과 겹침
H3 앱/서버 두 곳에서 같은 자동화 실행
H4 저장 단계에 중복 방지 key 없음
H5 성공했는데 완료 응답만 유실되어 재실행
```

## D-5. idempotency

같은 작업을 여러 번 실행해도 최종 결과가 의도치 않게 중복되지 않도록 만드는 성질을 **멱등성(idempotency)**이라고 한다.

예:

```text
unique key = (symbol, metric, asOfDate)
```

같은 날짜·종목·지표 데이터가 다시 오면 새 행을 무조건 추가하지 않고 기존 데이터 갱신/거절 정책을 적용할 수 있다.

단, 실제 key 설계는 데이터 의미에 맞아야 한다.

## D-6. 완료 기준

```text
정상 1회 실행 → 1세트 저장
동일 job 강제 재실행 → 중복 0
worker retry → 중복 0
동시 실행 시뮬레이션 → 중복 0
로그에서 모든 run 추적 가능
```

# 종합 훈련 1. 증거 장부 만들기

장애 조사에서 본 것과 추측을 섞지 않는다.

| 시각 | 관찰한 사실 | 출처 | 해석/가설 | 상태 |
|---|---|---|---|---|
| 09:00:01 | provider 200 | server log | provider까지 요청 전달 | 확인 |
| 09:00:05 | 화면 알림 없음 | 실제 기기 | channel/OS 후보 | 미확인 |

`확인`과 `추정`을 분리하면 AI가 그럴듯한 결론을 추가해도 잡아낼 수 있다.

# 종합 훈련 2. 최소수정 계획

수정 전에 적는다.

```text
원인:
수정 파일:
변경할 함수:
변경하지 않을 기능:
데이터 schema 변경 여부:
rollback 방법:
```

예:

```text
원인: 최신 검색 응답보다 오래된 응답이 뒤늦게 화면을 덮음
수정: requestId 비교 후 stale response 무시
보존: API schema/DB/UI 디자인 변경 없음
```

이렇게 수정 범위를 제한하면 AI의 과잉 변경도 줄일 수 있다.

# 종합 훈련 3. 테스트 매트릭스

한 번 성공이 아니라 조건 조합으로 검증한다.

예: 알림 기능

| 케이스 | 기대 |
|---|---|
| 권한 ON + channel ON | 수신 |
| 권한 OFF | 미표시/안내 |
| channel OFF | 해당 채널 미표시 |
| token 갱신 | 새 token으로 수신 |
| 앱 재실행 | 계속 정상 |
| 네트워크 일시 실패 | 정책에 따른 retry |

예: 주가 계산

| 케이스 | 기대 |
|---|---|
| 일반 거래일 | 원자료와 일치 |
| 6개월 기준일 휴장 | 정의된 거래일 선택 |
| 분할 종목 | 수정주가 정책 일치 |
| 원자료 없음 | HOLD/명확한 결측 |
| 값 0 | 결측과 구분 |

## V1을 끝낸 뒤의 상태

V1을 마쳤다고 모든 코드를 직접 짤 수 있는 것은 아니다. 대신 다음 기반이 생겨야 한다.

- 파일과 경로를 정확히 지정한다.
- 타입·JSON·상태·캐시를 구분한다.
- 프로세스·비동기·race를 이해한다.
- CPU/RAM/I/O 병목을 측정한다.
- 터미널 명령을 무작정 복붙하지 않는다.
- dependency·migration·rollback을 이해한다.
- 로그에서 최초 실패를 찾는다.
- DNS/TLS/HTTP 단계를 나눈다.
- Android 권한·알림·background 흐름을 이해한다.
- 버그를 가설과 증거로 해결한다.

이 기반 위에서 V2의 Python 코딩을 배우면 문법을 외우는 데서 끝나지 않고 **코드가 시스템에서 왜 그렇게 동작하는지** 연결할 수 있다.
