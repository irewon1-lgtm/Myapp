## V1-C11. 종합 시스템 장애 진단 프로젝트 — 처음부터 끝까지 실제로 해결하기

**이 장의 대상:** 앞의 10개 Chapter를 읽고 이제 하나의 실제 문제를 처음부터 끝까지 해결하는 과정을 연습하려는 사람.

**이 장의 목표:** 정답을 맞히는 것이 아니라 **문제 정의 → 재현 → 계층 분리 → 증거 수집 → 가설 → 실험 → 최소 수정 → 회귀검증 → 보고서**를 스스로 완성한다.

이 장은 V1의 마지막 장이다. 앞에서 배운 용어를 다시 설명하지만, 이번에는 실제 장애 안에서 사용한다.

---

### 1. 실제 문제는 친절하게 이름표를 달고 오지 않는다

현실에서 사용자는 이렇게 말한다.

```text
앱이 이상해요.
어제부터 알림이 안 와요.
업데이트하고 데이터가 사라졌어요.
주가가 이상하게 보여요.
검색이 가끔 멈춰요.
```

아무도 처음부터:

> “DNS 장애입니다.”

> “DB migration bug입니다.”

라고 정확히 알려주지 않는다.

개발자는 **보이는 증상에서 실제 원인까지 거슬러 올라가야 한다.**

---

### 2. 첫 번째 원칙 — 해결책보다 문제 정의

문제를 고치기 전에 문제를 정확히 적는다.

나쁜 문제 정의:

> 알림 안 옴.

좋은 문제 정의:

> 배우자 Android 16 기기에서 가족 일정 수정 알림이 오지 않는다. 엄마 Android 기기에서는 동일 이벤트 알림이 온다. 앱 버전은 두 기기 모두 1.5.0이다. 5번 테스트 중 배우자 기기 0/5 수신, 엄마 기기 5/5 수신.

이제 비교할 수 있는 정보가 생겼다.

---

### 3. 문제 정의에 원인을 넣지 않는다

나쁜 예:

> FCM 버그 때문에 알림이 안 온다.

아직 FCM이 원인인지 확인하지 않았다.

더 좋은 표현:

> 서버 이벤트 생성 후 배우자 기기에서 알림이 표시되지 않는다.

원인 추측을 제외하고 **관찰된 현상**만 적는다.

---

### 4. 재현 조건 고정

문제를 다시 만들 수 있어야 수정 전후를 비교할 수 있다.

예:

```text
기기: Galaxy A
앱 버전: 1.5.0
계정: 배우자
네트워크: Wi-Fi
행동: 일정 제목 수정 후 저장
기대: 배우자 기기에 10초 이내 알림
실제: 알림 없음
```

같은 조건으로 여러 번 반복한다.

---

### 5. 비교군을 만든다

정상 기기나 정상 계정이 있으면 매우 큰 도움이 된다.

예:

```text
엄마 폰 → 정상
배우자 폰 → 실패
```

둘을 비교하면 서버 공통 영역이 원인인지, 기기별 영역이 원인인지 빠르게 좁힐 수 있다.

> **비교군 = 정상과 실패를 나란히 비교하기 위한 기준 대상**

---

### 6. 시스템 지도를 먼저 그린다

알림 흐름을 예로 들면:

```text
일정 저장
↓
서버 이벤트 생성
↓
수신자 목록 계산
↓
push token 조회
↓
push provider 전송
↓
기기 수신
↓
Android 알림 권한/채널
↓
사용자 화면 표시
```

이 지도를 먼저 그리면 “어디를 확인해야 할지”가 보인다.

---

### 7. 마지막 정상 지점을 찾는다

각 단계에 실제 증거를 채운다.

```text
일정 저장          → 정상
서버 이벤트 생성    → 정상
수신자 목록         → 배우자 포함
push token          → ???
provider 전송       → ???
기기 표시           → 실패
```

아직 모르는 부분을 `???`로 둔다.

이제 다음 확인은 push token이다.

---

### 8. 증거 장부 만들기

조사 중 기억만 믿지 않는다.

표로 남긴다.

| 번호 | 확인 항목 | 결과 | 증거 |
|---|---|---|---|
| E01 | 서버 이벤트 생성 | PASS | server log 21:03:12 |
| E02 | 배우자 수신자 포함 | PASS | receiver list |
| E03 | 배우자 token 존재 | FAIL | DB row 없음 |
| E04 | 엄마 token 존재 | PASS | DB row 존재 |

이 표가 있으면 추측과 사실이 섞이지 않는다.

---

### 9. 가설을 최소 세 개 만든다

하나의 원인에 너무 일찍 집착하지 않는다.

예:

```text
가설 A: 배우자 push token이 서버에 등록되지 않았다.
가설 B: 알림 권한이 꺼져 있다.
가설 C: provider가 해당 token 전송을 거부했다.
```

각 가설마다 “맞다면 무엇이 보여야 하는가?”를 적는다.

---

### 10. 가장 싼 실험부터 한다

전체 앱 재설치는 비싸고 데이터를 지울 수 있다.

먼저 비용이 작은 확인을 한다.

```text
권한 상태 확인
DB token 조회
provider response 확인
앱 버전 확인
```

> **좋은 디버깅은 큰 변경보다 작은 확인으로 가설을 빠르게 탈락시키는 과정**이다.

---

### 11. 실험은 한 번에 하나만

가설 A를 확인하면서 동시에:

```text
앱 재설치
권한 변경
서버 재배포
DB 초기화
```

를 하지 않는다.

한 번에 하나만 바꿔야 결과의 의미가 남는다.

---

### 12. 조사 중 원본을 보존한다

변경 전 상태를 남긴다.

예:

```text
Git commit
DB snapshot
설정 export
로그 저장
화면 캡처
```

조사 과정에서 증거를 없애지 않는다.

---

### 13. 프로젝트 A — 가족 알림 한 기기만 실패

#### 증상

엄마 기기는 알림을 받는다.

배우자 기기는 받지 못한다.

#### 시스템 지도

```text
일정 이벤트
→ backend
→ receiver list
→ token
→ push provider
→ Android
→ notification channel
→ 화면
```

#### 비교표

| 항목 | 엄마 | 배우자 |
|---|---|---|
| 앱 버전 | 1.5.0 | 1.5.0 |
| 로그인 계정 | 정상 | 정상 |
| 알림 권한 | ON | ON |
| 채널 | ON | ON |
| token DB | 있음 | 없음 |

이 시점에서 token 등록 문제 가설이 강해진다.

---

### 14. 프로젝트 A — 가설 검증

가설:

> 배우자 폰의 push token이 서버에 등록되지 않았다.

맞다면:

```text
기기에는 로컬 token이 있을 수 있음
서버 DB에는 해당 token 없음
등록 API 로그가 없거나 실패
```

확인 결과:

```text
기기 token 생성 → 확인
등록 API → 401 실패
서버 DB → token 없음
```

이제 원인을 한 단계 더 깊게 본다.

---

### 15. 프로젝트 A — root cause와 symptom 구분

단순히 token을 DB에 수동 입력하면 알림이 올 수 있다.

하지만 이것은 **증상 수정**일 수 있다.

실제 root cause가:

> token 등록 API가 인증 실패로 401을 반환함

이라면 인증 갱신 흐름을 고쳐야 재발을 막을 수 있다.

> **root cause = 문제가 반복되는 근본 원인**

---

### 16. 프로젝트 A — 최소 수정

원인:

```text
앱 시작 시 access token 만료
refresh 수행 전 push token 등록 API 호출
401 발생
재시도 없음
```

최소 수정 후보:

```text
인증 준비 완료 후 token 등록
401 시 적절한 refresh 후 제한된 재시도
```

알림 UI 디자인까지 동시에 바꾸지 않는다.

---

### 17. 프로젝트 A — 회귀검증

수정 후 테스트:

```text
신규 설치 → token 등록 PASS
기존 설치 → token 갱신 PASS
로그아웃/로그인 → 등록 PASS
앱 재실행 → 중복 token 없음
엄마 기기 알림 → 5/5
배우자 기기 알림 → 5/5
```

기존 정상 기기도 다시 확인한다.

---

### 18. 프로젝트 B — 업데이트 후 데이터가 사라짐

#### 증상

```text
새 설치 → 정상
1.4.0에서 1.5.0 업데이트 → 기존 데이터 0개로 보임
```

이 비교만으로도 강한 단서가 있다.

신규 설치 자체보다 **업데이트 경로** 문제일 가능성이 크다.

---

### 19. 프로젝트 B — 시스템 지도

```text
구버전 DB
↓
앱 업데이트
↓
DB schema migration
↓
신버전 DB
↓
repository 조회
↓
UI 표시
```

각 단계에서 row count를 기록한다.

---

### 20. 프로젝트 B — 증거 수집

```text
업데이트 전 row count = 124
migration 시작
migration 완료 로그 있음
업데이트 후 row count = 0
```

추가 확인:

```text
DB 파일 경로가 바뀌었는가?
새 DB를 새로 만든 것은 아닌가?
구 DB 테이블 이름이 변경됐는가?
```

---

### 21. 프로젝트 B — 가설

```text
A. migration이 기존 테이블을 삭제했다.
B. 신버전이 다른 DB 파일을 열고 있다.
C. 계정 ID가 달라져 필터 결과가 0이다.
```

각 가설을 별도로 확인한다.

### 22. 프로젝트 B — 파괴적 조치를 미룬다

이 상황에서 “앱 데이터 삭제 후 다시 로그인”을 하면 증상이 사라질 수 있다.

하지만 기존 데이터와 증거도 함께 사라진다.

먼저 구버전 DB 사본을 만든다.

```text

```

그 사본으로 업그레이드 테스트를 반복한다.

### 25. 프로젝트 C — 계산식부터 적는다

### 26. 프로젝트 C — 주식분할 사례

주식분할이 있었는데 과거 가격을 조정하지 않았다면 상승률이 크게 왜곡될 수 있다.

예:

```text
분할 전 가격 100
2:1 분할
조정 후 비교 기준은 50에 해당
```

단순 가격 숫자만 가져오면 잘못된 비교가 될 수 있다.

이것은 “UI 문제”가 아니라 데이터 방법론 문제다.

### 34. 프로젝트 F — 자동화가 중복 실행


### 35. 프로젝트 F — run id 사용

각 실행에 고유 ID를 붙인다.

```text
run_id=20260915-0900-A
```

로그와 DB 기록에 같은 ID를 남기면 어떤 실행이 어떤 결과를 만들었는지 추적하기 쉽다.

중복 방지에도 활용할 수 있다.

---

### 36. 프로젝트 F — 멱등성

같은 작업이 다시 실행되어도 결과가 중복되지 않게 설계하는 성질을 **멱등성(idempotency)**이라고 부른다.

예:

```text
같은 run_id는 한 번만 저장
같은 일정 ID는 update하지 duplicate insert하지 않음
```

자동화와 API에서 매우 중요한 개념이다.

---

### 37. 사고 대응의 우선순위

실제 운영 장애에서는 먼저 사용자 피해를 줄여야 할 수 있다.

예:

```text
새 버전에서 크래시 급증
```

가능한 대응:

```text
문제 기능 비활성화
이전 버전 rollback
트래픽 우회
```

서비스를 안정화한 뒤 근본 원인을 조사할 수 있다.

> **복구와 근본수정은 순서가 다를 수 있다.**

### 38. 임시조치와 영구수정

임시조치:

```text
문제 기능 끄기
재시도 횟수 줄이기
특정 데이터 수동 보정
```

영구수정:

```text

```

보고서에 둘을 구분한다.

### 39. 재발 방지는 무엇일까?

버그 하나를 고치고 끝내지 않는다.

재발 방지 예:

```text
회귀 테스트 추가
모니터링 추가
validation 강화
runbook 작성
코드 리뷰 규칙 개선
```

같은 종류의 실수를 시스템적으로 줄인다.

---

### 40. runbook은 무엇일까?

반복 장애에 대응하는 절차를 문서로 정리한 것을 **runbook**이라고 부른다.

예:

```text
알림 미수신 점검 순서
1. event log
2. receiver list
3. token
4. provider response
5. device permission
```

다음 사람이 같은 조사를 처음부터 다시 하지 않아도 된다.

---

### 41. 완료 기준을 미리 정한다

“되는 것 같음”이 아니라 구체적인 기준을 정한다.

예:

```text
실패 재현 5/5
수정 후 0/20 실패
정상 기기 20/20 유지
자동 테스트 PASS
release build PASS
실제 Android 설치 PASS
```

이 기준을 만족해야 COMPLETE라고 기록한다.

---

### 42. NOT-RUN을 정직하게 적는다

실제 기기가 없어서 테스트하지 못했다면:

```text
Android 14 physical device: NOT-RUN
```

이라고 쓴다.

“코드상 문제 없어 보임”을 PASS로 바꾸지 않는다.

정직한 미검증 표시는 품질의 일부다.

---

### 43. 증거 패키지 만들기

작업 종료 시 다음을 묶는다.

```text
재현 절차
원인 설명
코드 diff
테스트 결과
빌드 결과
실기기 결과
데이터 검증 결과
남은 위험
rollback 방법
```

다음 사람이 이어받을 수 있는 상태로 만든다.

---

### 44. HANDOFF는 무엇일까?

다른 사람이나 AI에게 작업을 넘길 때 현재 상태를 설명하는 문서를 **handoff**라고 부를 수 있다.

좋은 handoff에는:

```text
무엇을 완료했는가
무엇이 미완료인가
현재 commit은 무엇인가
어떤 테스트가 PASS인가
어떤 테스트는 NOT-RUN인가
다음 작업은 무엇인가
```

가 포함된다.

---

### 45. AI와 함께 디버깅할 때의 규칙

AI에게:

> 고쳐줘.

만 말하지 않는다.

더 좋은 지시:

```text
증상: 빈 검색어에서 crash
재현: 5/5
기대: 안내문
보존: DB/API 구조 변경 금지
수정 범위: SearchScreen
완료 조건: 관련 unit test + regression suite + debug/release build
```

AI가 수정 범위를 넘지 않도록 성공 조건을 고정한다.

---

### 46. AI가 많이 바꿨다면 멈춘다

작은 버그인데 AI가 30개 파일을 변경했다면 이유를 확인한다.

```text
왜 이 파일이 바뀌었는가?
원인 수정에 필요한가?
기존 기능을 보존했는가?
```

불필요한 변경은 되돌리는 편이 좋을 수 있다.

### 52. 최종 용어사전

| 쉬운 말 | 영어 | 뜻 |
|---|---|---|
| 비교군 | comparison/control | 정상과 실패를 비교하기 위한 기준 대상 |
| 증거 장부 | evidence log | 조사한 사실과 근거를 기록한 표 |
| 근본 원인 | root cause | 문제가 반복되는 가장 근본적인 원인 |
| 임시조치 | mitigation/workaround | 사용자 영향을 빠르게 줄이기 위한 임시 대응 |
| 영구수정 | permanent fix | 근본 원인을 해결하는 수정 |
| 재발 방지 | prevention | 같은 문제가 다시 생기지 않게 하는 조치 |
| 멱등성 | idempotency | 같은 작업이 반복돼도 의도치 않은 중복 결과가 생기지 않는 성질 |
| runbook | runbook | 반복 장애 대응 절차 문서 |
| handoff | handoff | 다른 사람에게 작업 상태를 넘기는 기록 |
| rollback | rollback | 이전 정상 상태로 되돌리기 |

### 53. 최종 종합 미션

다음 문제를 종이에 직접 해결해본다.

> Android 주식 앱에서 특정 종목의 6개월 상승률이 외부 공식 데이터와 다르다. 앱은 42%, 외부는 15%다. 다른 종목은 대부분 정상이다. 최근 이 종목은 주식분할을 했다.

#### 1단계: 증상 정의

어떤 종목, 어떤 기준일, 어떤 앱 버전인지 적는다.

#### 2단계: 계산식

앱의 6개월 상승률 정의를 적는다.

#### 3단계: 데이터 추적

```text
현재 가격
과거 가격
조정 여부
계산 결과
DB 저장값
API 값
UI 표시값
```

을 표로 만든다.

#### 4단계: 가설

```text
A. 분할 조정 안 됨
B. 기준일 잘못 선택
C. UI 퍼센트 포맷 오류
```

#### 5단계: 검증

각 가설에 필요한 증거를 찾는다.

#### 6단계: 최소 수정

실제 원인만 수정한다.

#### 7단계: 회귀검증

분할 종목과 일반 종목 모두 다시 계산한다.

#### 8단계: 기록

수정 전후 값과 데이터 출처를 남긴다.

이 미션을 혼자 순서대로 수행할 수 있다면 V1의 목표를 달성한 것이다.

### 54. 한 권 최종 요약

V1에서 가장 중요한 것은 영어 용어를 많이 외운 것이 아니다.

가장 중요한 습관은 다음 다섯 가지다.

1. **모르는 용어가 나오면 뜻부터 확인한다.**
2. **문제를 한 덩어리로 보지 않고 단계로 나눈다.**
3. **보이는 증상과 실제 원인을 구분한다.**
4. **추측보다 로그·값·테스트 같은 증거를 본다.**
5. **수정 후 같은 조건으로 다시 검증한다.**

이 다섯 가지가 잡히면 다음 권에서 코드를 더 깊게 배울 준비가 된 것이다.
