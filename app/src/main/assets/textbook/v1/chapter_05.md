## V1-C05. 권한과 터미널 첫걸음 — 명령어를 무서워하지 않는 법

**이 장의 대상:** 터미널 화면을 보면 겁부터 나고, `PATH`, `환경변수`, `관리자 권한`, `pipe` 같은 말을 처음 듣는 사람.

**이 장의 목표:** 터미널에서 명령을 실행하기 전에 **현재 위치, 대상, 권한, 결과, 위험성**을 확인하는 습관을 만든다. 영어 명령을 통째로 외우는 것이 아니라 “이 명령이 무엇을 읽고 무엇을 바꾸는지”를 이해한다.

---

### 1. 권한은 왜 필요할까?

휴대폰에 여러 앱이 설치되어 있다고 하자.

메모 앱이 은행 앱의 데이터를 마음대로 읽을 수 있다면 매우 위험하다.

그래서 운영체제는 누가 무엇을 할 수 있는지 제한한다.

이 규칙을 **권한(permission)**이라고 한다.

> **권한 = 어떤 사용자나 프로그램이 무엇을 읽고, 쓰고, 실행할 수 있는지 정하는 규칙**

---

### 2. 읽기·쓰기·실행

파일 권한을 설명할 때 대표적으로 세 행동을 생각할 수 있다.

```text
읽기 → 내용을 볼 수 있음
쓰기 → 내용을 바꿀 수 있음
실행 → 프로그램으로 실행할 수 있음
```

모든 운영체제가 같은 방식으로 표시하는 것은 아니지만 기본 생각은 같다.

파일이 존재한다고 해서 현재 사용자가 반드시 읽거나 수정할 수 있는 것은 아니다.

---

### 3. 사용자라는 개념

컴퓨터에는 여러 사용자 계정이 있을 수 있다.

같은 파일이라도:

```text
사용자 A → 읽기 가능
사용자 B → 읽기 불가
관리자    → 더 넓은 권한
```

처럼 다르게 설정될 수 있다.

프로그램도 특정 사용자 권한으로 실행된다.

따라서 오류 메시지에 `Permission denied`가 보이면 “파일이 없다”와는 다른 문제다.

> **Permission denied = 존재할 수는 있지만 현재 권한으로 접근이 거부됨**

---

### 4. 관리자 권한은 만능 버튼이 아니다

권한 문제가 생겼다고 모든 명령을 관리자 권한으로 실행하는 습관은 위험하다.

권한이 강해질수록 실수했을 때 피해 범위도 커진다.

예를 들어 잘못된 삭제 명령을 일반 사용자 권한으로 실행하면 일부 파일에서 막힐 수 있지만, 관리자 권한이면 더 넓은 범위를 지울 수 있다.

> **필요한 만큼만 권한을 사용하는 것**이 기본 원칙이다.

이를 **최소 권한 원칙(least privilege)**이라고 부른다.

---

### 5. 터미널은 무엇일까?

컴퓨터를 사용할 때 보통 아이콘과 버튼을 누른다.

하지만 명령어를 글자로 입력해 컴퓨터를 조작하는 화면도 있다.

이를 흔히 **터미널(terminal)**이라고 부른다.

> **터미널 = 명령어를 글자로 입력하고 결과를 보는 창**

검은 화면에 글자가 나온다고 특별한 해킹 도구가 아니다.

개발, 파일 관리, 서버 운영, Git, 빌드에서 매우 자주 사용한다.

---

### 6. 셸은 무엇일까?

터미널 창 안에서 사람이 입력한 명령을 해석해주는 프로그램이 있다.

이를 **셸(shell)**이라고 부른다.

> **터미널 = 명령을 입력하는 창**
>
> **셸 = 그 명령을 읽고 실행하도록 연결하는 프로그램**

둘을 완전히 같은 것으로 생각하지 않는다.

대표적인 셸로 `bash`, `zsh`, PowerShell 등이 있다.

이름은 지금 외우지 않아도 된다.

---

### 7. 명령어는 문장처럼 읽는다

다음 명령을 보자.

```text
ls
```

환경에 따라 현재 폴더의 파일 목록을 보여주는 명령으로 사용할 수 있다.

처음에는 “ls를 외워야 한다”보다:

```text
이 명령은 무엇을 읽는가?
무엇을 바꾸는가?
결과는 어디에 나오는가?
```

를 생각한다.

파일 목록만 보여주는 명령은 비교적 안전하지만, 삭제나 덮어쓰기 명령은 훨씬 조심해야 한다.

---

### 8. 현재 위치 확인이 먼저다

터미널에서 파일 명령을 실행할 때 가장 먼저 확인할 것이 **현재 위치**다.

Unix 계열에서는 `pwd` 같은 명령으로 현재 작업 경로를 확인할 수 있다.

```text
pwd
```

예시 결과:

```text
/home/user/MyApp
```

명령어 이름을 외우는 것보다 중요한 습관은:

> **파일을 바꾸는 명령 전에 내가 어느 폴더에 있는지 확인한다.**

---

### 9. 목록을 보고 대상 확인하기

현재 폴더에 무엇이 있는지 확인한 뒤 작업한다.

예:

```text
ls
```

결과:

```text
app
README.md
data
```

이제 `data`라는 폴더가 실제로 있다는 사실을 눈으로 확인할 수 있다.

추측으로 경로를 입력하지 않는다.

---

### 10. 폴더 이동

터미널에서는 현재 작업 폴더를 바꿀 수 있다.

예:

```text
cd data
```

`cd`는 `change directory`의 줄임말이다.

영어를 외우지 않아도 된다.

> **cd = 현재 작업 폴더를 바꾸는 명령으로 많이 사용됨**

이동 후 다시 현재 위치를 확인하는 습관을 들인다.

---

### 11. 명령의 기본 구조

명령은 대략 다음 형태를 가질 수 있다.

```text
명령어  옵션  대상
```

예를 들어:

```text
command --option file.txt
```

모든 명령이 정확히 같은 규칙은 아니지만, 읽을 때 다음을 분리한다.

```text
무슨 명령인가?
어떤 옵션을 켰는가?
어떤 파일/폴더가 대상인가?
```

AI가 긴 명령을 만들어줘도 이 세 가지를 먼저 찾는다.

---

### 12. 옵션은 무엇일까?

명령의 동작 방식을 바꾸는 추가 설정을 **옵션(option)**이라고 부른다.

예:

```text
--help
--version
-r
-f
```

옵션 하나 때문에 삭제 범위나 덮어쓰기 방식이 크게 달라질 수 있다.

따라서 처음 보는 옵션은 실행 전에 도움말이나 공식 문서를 확인한다.

---

### 13. `--help`를 활용하는 습관

많은 명령은 도움말 옵션을 제공한다.

예:

```text
command --help
```

이 명령이 어떤 인수를 받는지, 어떤 옵션이 있는지 확인할 수 있다.

AI 설명만 믿기보다 실제 설치된 도구의 도움말을 확인하면 버전 차이도 알 수 있다.

---

### 14. 출력은 어디로 갈까?

터미널 명령을 실행하면 결과가 화면에 글자로 표시될 수 있다.

이 결과를 다른 명령으로 넘기거나 파일에 저장할 수도 있다.

이 개념을 이해하면 긴 명령도 작은 흐름으로 나눠 읽을 수 있다.

---

### 15. 파이프란 무엇일까?

한 명령의 출력을 다음 명령의 입력으로 연결하는 기능을 흔히 **파이프(pipe)**라고 한다.

기호 `|`를 사용하는 셸이 많다.

예를 들어 개념적으로:

```text
명령 A | 명령 B
```

는:

```text
명령 A의 결과
↓
명령 B가 입력으로 받음
```

이라는 뜻이다.

> **pipe = 한 프로그램의 출력을 다음 프로그램의 입력으로 연결하는 통로**

---

### 16. 리다이렉션은 무엇일까?

화면에 나오는 출력을 파일로 보내는 기능을 **리다이렉션(redirection)**이라고 부른다.

예시 개념:

```text
명령 결과 > output.txt
```

이때 매우 중요한 점은 `>`가 파일을 새로 쓰거나 기존 내용을 덮어쓸 수 있다는 것이다.

따라서 실제 명령의 동작을 확인하지 않고 사용하면 안 된다.

> **redirection = 입력이나 출력이 향하는 곳을 바꾸는 기능**

---

### 17. 덮어쓰기와 추가쓰기를 구분하기

셸에 따라 `>`와 `>>`가 다르게 동작할 수 있다.

일반적인 의미 예:

```text
>   새로 쓰기 또는 덮어쓰기
>>  기존 파일 뒤에 추가
```

하지만 환경에 따라 정확한 동작을 확인해야 한다.

초보자에게 중요한 것은:

> **파일로 출력을 보낼 때 기존 데이터가 사라질 수 있는지 확인한다.**

---

### 18. 환경변수는 무엇일까?

프로그램은 실행할 때 외부 설정값을 읽을 수 있다.

이때 자주 사용하는 방식 중 하나가 **환경변수(environment variable)**다.

> **환경변수 = 프로그램 밖에서 이름과 값 형태로 전달하는 실행 환경 설정**

예:

```text
APP_ENV=production
LOG_LEVEL=debug
```

프로그램 코드 안에 값을 직접 박아 넣지 않고 환경에 따라 다른 설정을 줄 수 있다.

---

### 19. 왜 환경변수를 사용할까?

같은 코드를 여러 환경에서 사용할 수 있다.

```text
개발 환경 → 테스트 서버 주소
운영 환경 → 실제 서버 주소
```

코드를 매번 수정하는 대신 설정을 밖에서 바꾸면 관리하기 쉬워진다.

또한 API 키 같은 비밀값을 코드 저장소에 직접 적지 않기 위해 환경변수를 사용하기도 한다.

단, 환경변수라고 자동으로 안전해지는 것은 아니다.

로그에 출력하면 여전히 노출될 수 있다.

---

### 20. PATH는 무엇일까?

터미널에서:

```text
python
```

처럼 프로그램 이름만 입력했는데 실행될 수 있다.

컴퓨터는 어디에서 `python` 실행파일을 찾을까?

여러 폴더를 순서대로 찾아볼 수 있는데, 그 검색 경로 목록과 관련된 대표 환경변수가 **PATH**다.

> **PATH = 명령 이름만 입력했을 때 실행파일을 찾는 폴더 목록**

---

### 21. PATH 문제는 어떻게 보일까?

프로그램이 설치되어 있는데도:

```text
command not found
```

같은 메시지가 나온다고 하자.

가능한 원인:

```text
실제로 설치 안 됨
설치됐지만 PATH에 없음
명령 이름을 틀림
터미널을 재시작해야 반영됨
다른 버전이 먼저 잡힘
```

무조건 재설치하기 전에 실제 실행파일 위치와 PATH를 확인한다.

---

### 22. 환경변수와 PATH를 혼동하지 말자

`PATH` 자체도 환경변수다.

하지만 모든 환경변수가 PATH인 것은 아니다.

```text
환경변수
├─ PATH
├─ HOME
├─ APP_ENV
└─ API_KEY
```

이렇게 큰 범주와 특정 이름을 구분한다.

---

### 23. 비밀값은 무엇일까?

API 키, 비밀번호, 토큰처럼 노출되면 위험한 값을 **비밀값(secret)**이라고 부른다.

예:

```text
API_KEY
DB_PASSWORD
ACCESS_TOKEN
```

이런 값은:

```text
공개 GitHub
스크린샷
로그
에러 메시지
AI에게 보내는 프롬프트
```

에 그대로 남지 않도록 주의해야 한다.

---

### 24. 코드에 비밀값을 직접 쓰면 왜 위험할까?

예:

```python
api_key = "REAL_SECRET_123"
```

이 파일을 GitHub에 올리면 비밀값이 함께 공개될 수 있다.

나중에 파일을 지워도 Git 기록에 남아 있을 수 있다.

더 나은 구조는 환경이나 보안 저장소에서 읽는 것이다.

```python
api_key = "환경에서 읽기"
```

실제 구현 방식은 플랫폼마다 다르다.

---

### 25. 로그에 비밀값을 찍지 않는다

다음 코드는 위험할 수 있다.

```python
print(api_key)
```

개발 중에는 편해 보여도 로그 파일, CI, 오류 보고서에 남을 수 있다.

대신:

```text
API key loaded: yes
```

처럼 실제 값을 숨긴 상태만 기록할 수 있다.

---

### 26. 삭제 명령을 실행하기 전 5초 규칙

AI가 다음과 같은 긴 삭제 명령을 만들었다고 하자.

처음 보는 옵션과 경로가 포함되어 있다.

바로 복사해서 실행하지 않는다.

실행 전 최소한 다음을 확인한다.

1. 현재 위치 `pwd`
2. 대상 경로가 실제로 무엇인지
3. 하위 폴더까지 지우는 옵션인지
4. 와일드카드 `*`가 어디까지 확장되는지
5. 복구 가능한 백업이 있는지

이 5초 확인이 큰 사고를 막을 수 있다.

---

### 27. 와일드카드는 무엇일까?

셸에서 `*` 같은 문자를 사용해 여러 파일을 한꺼번에 가리킬 수 있다.

이를 흔히 **와일드카드(wildcard)**라고 부른다.

예:

```text
*.txt
```

은 여러 `.txt` 파일과 매칭될 수 있다.

편리하지만 삭제 명령과 함께 사용할 때 위험 범위가 커질 수 있다.

> **여러 파일을 대상으로 하는 패턴은 실행 전에 실제 대상 목록을 먼저 확인한다.**

---

### 28. 복사·이동·삭제 명령은 특히 조심한다

파일을 읽기만 하는 명령보다 다음 행동은 데이터에 변화를 준다.

```text
복사
이동
이름 변경
덮어쓰기
삭제
권한 변경
```

따라서 실행 전후 결과를 검증한다.

```text
작업 전 파일 목록
↓
명령 실행
↓
작업 후 파일 목록
```

---

### 29. 한 번에 여러 명령을 실행할 때

긴 명령줄에는 여러 작업이 이어져 있을 수 있다.

초보자는 전체를 한 덩어리로 실행하지 말고 가능하면 단계별로 나눈다.

```text
1단계 실행
결과 확인
2단계 실행
결과 확인
```

이렇게 하면 어느 단계에서 문제가 생겼는지 찾기 쉽다.

---

### 30. 명령어를 실행하기 전 말로 번역하기

예를 들어 어떤 명령이 있다고 하자.

```text
tool --force data/* > result.txt
```

정확한 도구를 모른다면 실행하지 않는다.

먼저 말로 바꿔본다.

```text
tool이라는 프로그램 실행
--force 옵션 사용
data 아래 여러 항목 대상
결과를 result.txt로 보냄
```

그 뒤 `--force`가 정확히 무엇인지 공식 도움말에서 확인한다.

**모르는 옵션은 모르는 상태로 실행하지 않는다.**

---

### 31. 실제 예제 — 명령은 되는데 다른 파일을 고침

현재 위치:

```text
/home/user/test
```

사용자는 운영용 파일을 고친다고 생각하고:

```text
config.json
```

을 수정했다.

하지만 실제로는 테스트 폴더의 config였다.

이 문제는 코드 로직이 아니라 **현재 작업 위치 확인 실패**다.

작업 전에 전체 경로를 확인하면 예방할 수 있다.

---

### 32. 실제 예제 — 프로그램 설치했는데 명령이 안 됨

상황:

```text
Python 설치 완료
터미널: python 명령을 찾을 수 없음
```

가능한 확인 순서:

1. 설치 위치 확인
2. 실행파일이 실제 존재하는지 확인
3. 정확한 명령 이름 확인
4. PATH에 설치 경로가 포함됐는지 확인
5. 새 터미널에서 다시 확인

무조건 여러 버전을 계속 재설치하지 않는다.

---

### 33. 실제 예제 — API 키가 GitHub에 올라감

코드에:

```text
API_KEY=abc123...
```

이 들어간 상태로 공개 저장소에 커밋했다.

단순히 다음 커밋에서 지우는 것만으로 충분하지 않을 수 있다.

일반적인 대응은:

```text
키 폐기/회전
새 키 발급
Git 기록 노출 여부 확인
보관 방식 수정
로그·CI 노출 확인
```

이다.

비밀값 사고에서는 “지웠다”보다 **기존 비밀값을 더 이상 사용할 수 없게 만드는 것**이 중요하다.

---

### 34. 코드 읽기 — 환경 설정

```python
environment = "test"
log_level = "debug"
print(environment)
```

이 코드는 설정 값을 변수에 넣고 출력한다.

실제 환경변수 사용 문법을 배우기 전에 “환경마다 설정 값이 달라질 수 있다”는 개념을 연습하는 코드다.

---

### 35. 직접 해보기 — 명령 안전 체크리스트 만들기

아래 문장을 직접 적어본다.

```text
[ ] 현재 폴더 확인
[ ] 대상 파일 확인
[ ] 명령 설명 확인
[ ] 위험 옵션 확인
[ ] 백업/rollback 확인
[ ] 실행 후 결과 확인
```

터미널을 사용할 때 이 체크리스트를 습관처럼 적용한다.

### 36. 초보자가 자주 하는 오해

#### 오해 1. 권한 오류가 나면 관리자 권한으로 실행하면 끝이다

아니다. 왜 그 권한이 필요한지 먼저 확인한다.

#### 오해 2. 터미널은 전문가만 쓰는 도구다

아니다. 글자로 명령을 입력하는 인터페이스일 뿐이다.

#### 오해 3. 명령이 짧으면 안전하다

아니다. 짧은 삭제 명령도 큰 피해를 낼 수 있다.

#### 오해 4. 환경변수에 넣으면 비밀값은 절대 노출되지 않는다

아니다. 로그, 프로세스, 설정 등을 통해 노출될 가능성을 관리해야 한다.

#### 오해 5. PATH에 추가하면 프로그램이 설치된다

아니다. PATH는 이미 존재하는 실행파일을 찾는 경로와 관련된 설정이다.

### 37. 용어사전

| 쉬운 말 | 영어 | 뜻 |
|---|---|---|
| 권한 | permission | 누가 어떤 자원을 사용할 수 있는지 정한 규칙 |
| 최소 권한 | least privilege | 필요한 만큼만 권한을 주는 원칙 |
| 터미널 | terminal | 글자로 명령을 입력하고 결과를 보는 창 |
| 셸 | shell | 입력한 명령을 해석해 실행하도록 연결하는 프로그램 |
| 옵션 | option | 명령 동작을 바꾸는 추가 설정 |
| 파이프 | pipe | 한 명령 출력을 다음 명령 입력으로 연결하는 기능 |
| 리다이렉션 | redirection | 입출력이 향하는 곳을 바꾸는 기능 |
| 환경변수 | environment variable | 프로그램 실행 환경에서 이름과 값으로 전달하는 설정 |
| PATH | PATH | 실행파일을 찾는 폴더 목록 |
| 비밀값 | secret | 노출되면 안 되는 키·토큰·비밀번호 |
| 와일드카드 | wildcard | 여러 파일을 패턴으로 선택하는 문자 표현 |

3. 터미널과 셸의 차이는 무엇인가?
4. PATH는 프로그램을 설치하는 기능인가?
5. API 키를 로그에 출력하면 왜 위험한가?
6. 긴 명령을 실행하기 전에 어떤 세 가지를 최소 확인해야 하는가?

### 39. 종합 미션

AI가 다음 작업을 제안했다고 가정한다.

> 관리자 권한으로 프로젝트 폴더의 캐시와 빌드 파일을 전부 삭제한 뒤 환경변수를 다시 설정하세요.

바로 실행하지 말고 질문한다.

1. 정확히 어떤 폴더를 삭제하는가?
2. 사용자 데이터도 포함되는가?
3. 삭제 대상 목록을 먼저 볼 수 있는가?
4. 관리자 권한이 정말 필요한가?
5. 현재 환경변수는 어떤 값인가?
6. 비밀값이 터미널 기록에 남는가?
7. 복구 방법은 있는가?

이 질문을 할 수 있다면 이번 장의 핵심을 이해한 것이다.

### 40. 한 장 요약

1. 권한은 누가 무엇을 할 수 있는지 제한한다.
2. 관리자 권한은 필요할 때만 사용한다.
3. 터미널은 글자로 명령을 입력하는 창이다.
4. 셸은 명령을 해석하는 프로그램이다.
5. 파일 변경 명령 전에는 현재 위치와 대상을 확인한다.
6. 옵션 하나가 명령 동작을 크게 바꿀 수 있다.
7. 파이프는 한 명령의 출력을 다음 명령 입력으로 연결한다.
8. 리다이렉션은 출력이 향하는 곳을 바꾼다.
9. 환경변수는 프로그램 외부 설정을 전달하는 방식이다.
10. PATH는 실행파일 검색 경로 목록이다.
11. 비밀값을 코드, 로그, 공개 저장소에 노출하지 않는다.
12. 삭제·덮어쓰기·권한 변경은 실행 전에 대상과 복구 방법을 확인한다.

다음 장에서는 앱과 라이브러리를 설치할 때 왜 **버전, 의존성, 설정 차이**가 문제를 만드는지 처음부터 배운다.
