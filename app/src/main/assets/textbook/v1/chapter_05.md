## V1-C05. 권한과 터미널 첫걸음 — 명령을 안전하게 실행하는 법

**목표:** 터미널 명령을 복붙하는 사람이 아니라, **현재 위치·대상·권한·입출력·환경**을 확인한 뒤 안전하게 실행할 수 있는 사람이 되는 것이다.

---

### 1. 터미널과 셸은 같은 말이 아니다

**터미널(terminal)**은 명령을 입력하고 결과를 보는 창이다.

**셸(shell)**은 입력한 명령을 해석하고 프로그램을 실행하는 소프트웨어다.

```text
사람이 명령 입력
↓
터미널에 표시
↓
셸이 명령 해석
↓
프로그램 실행
↓
결과가 터미널에 표시
```

초보자에게 중요한 것은 셸 종류를 외우는 게 아니라, **내가 적은 문자열이 어떤 프로그램을 어떤 옵션으로 실행하는지** 확인하는 습관이다.

---

### 2. 명령은 보통 “프로그램 + 옵션 + 대상”으로 읽는다

예:

```bash
ls -l data
```

대략 이렇게 읽는다.

```text
ls   = 실행할 명령
-l   = 동작 방식을 바꾸는 옵션
 data = 대상
```

명령마다 문법은 다르지만 이 구조로 보면 긴 명령도 덜 무섭다.

AI가 긴 명령을 만들어줬다면 실행 전 최소한 다음을 찾는다.

```text
무슨 프로그램을 실행하는가?
어떤 옵션이 붙었는가?
어느 파일/폴더가 대상인가?
삭제·덮어쓰기·권한 상승이 있는가?
```

---

### 3. 현재 위치가 명령 결과를 바꾼다

파일 장에서 배운 상대경로가 터미널에서도 그대로 중요하다.

현재 위치를 확인하는 대표 명령:

```bash
pwd
```

현재 폴더의 파일을 보는 대표 명령:

```bash
ls
```

폴더를 이동하는 대표 명령:

```bash
cd data
```

여기서 핵심은 명령어 세 개를 암기하는 것이 아니다.

> **파일을 건드리는 명령은 현재 위치와 대상 경로를 먼저 확인한다.**

잘못된 폴더에서 삭제 명령을 실행하면 명령 자체는 “성공”하면서 중요한 파일을 지울 수 있다.

---

### 4. 권한 — 할 수 있는 일의 범위

운영체제는 모든 프로그램이 모든 파일과 장치에 마음대로 접근하지 못하게 제한한다.

대표 권한 개념:

```text
읽기(read)   = 내용 확인
쓰기(write)  = 내용 변경
실행(execute)= 프로그램/스크립트 실행
```

실제 권한 체계는 운영체제마다 다르지만 핵심은 같다.

```text
파일이 존재함 ≠ 현재 사용자가 읽을 수 있음
명령이 있음   ≠ 현재 사용자가 실행할 수 있음
```

#### 관리자 권한

더 넓은 시스템 권한으로 명령을 실행할 수 있는 환경이 있다. Linux 계열에서는 `sudo`를 볼 수 있다.

관리자 권한은 오류를 해결하는 마법이 아니다.

```text
Permission denied
→ 무조건 sudo
```

이 습관은 위험하다.

먼저 확인한다.

```text
왜 이 권한이 필요한가?
대상 경로가 맞는가?
일반 권한으로 해결할 방법은 없는가?
이 명령이 시스템 전체를 바꾸는가?
```

---

### 5. 표준입력·표준출력·표준오류

터미널 프로그램은 보통 입력과 출력 통로를 가진다.

간단히:

```text
표준입력(stdin)  = 프로그램이 기본으로 입력을 받는 통로
표준출력(stdout) = 정상 결과를 보내는 통로
표준오류(stderr) = 오류 메시지를 보내는 통로
```

왜 굳이 나눌까?

정상 결과는 파일에 저장하면서 오류는 화면에서 보고 싶을 수 있기 때문이다.

---

### 6. 리다이렉션 — 출력을 다른 곳으로 보낸다

명령 결과를 파일로 보낼 수 있다.

```bash
some-command > result.txt
```

`>`는 출력 방향을 바꾸는 **리다이렉션(redirection)**에서 자주 보는 기호다.

주의할 점은 기존 파일을 덮어쓸 수 있다는 것이다.

추가 모드에서 자주 쓰는 형태:

```bash
some-command >> result.txt
```

환경에 따라 동작이 다를 수 있으므로 중요한 파일에 바로 쓰지 말고 새 파일로 먼저 시험한다.

---

### 7. 파이프 — 한 프로그램의 출력을 다음 프로그램 입력으로

파이프 기호 `|`는 한 명령의 출력을 다른 명령의 입력으로 연결할 때 쓴다.

```text
명령 A 출력
   ↓
명령 B 입력
```

예:

```bash
cat app.log | grep ERROR
```

개념적으로는:

```text
로그 읽기 → ERROR가 있는 줄만 찾기
```

실무에서는 더 간단한 형태가 있을 수도 있지만, 여기서 중요한 것은 **명령을 작은 도구로 연결할 수 있다**는 점이다.

파이프를 이해하면 긴 명령을 볼 때 각 단계가 무슨 데이터를 넘기는지 추적할 수 있다.

---

### 8. 환경변수 — 코드 밖에서 설정값 전달하기

프로그램은 실행 환경에 따라 다른 설정을 필요로 한다.

예:

```text
개발 서버 주소
운영 서버 주소
로그 레벨
API 키
```

이런 값을 코드에 직접 박아두는 대신 **환경변수(environment variable)**로 전달할 수 있다.

개념:

```text
APP_ENV=production
API_BASE_URL=https://example.com
```

프로그램은 실행할 때 이 값을 읽는다.

#### 왜 좋은가

코드와 설정을 분리할 수 있다.

```text
같은 코드 + 개발 설정
같은 코드 + 운영 설정
```

특히 비밀값을 소스코드에 직접 넣는 일을 줄일 수 있다.

---

### 9. PATH — 명령 이름만 썼는데 프로그램을 찾는 이유

터미널에서 전체 경로를 적지 않고:

```bash
python
```

처럼 실행해도 셸이 프로그램을 찾는 경우가 있다.

셸은 **PATH**라는 환경변수에 등록된 폴더들을 순서대로 확인한다.

```text
명령 이름 입력
↓
PATH에 등록된 폴더 검색
↓
실행 파일 발견
↓
실행
```

그래서 “설치했는데 command not found”가 나오면 설치 자체뿐 아니라 PATH 문제일 수 있다.

반대로 같은 이름의 실행 파일이 여러 개 있으면 의도와 다른 버전이 먼저 선택될 수 있다.

---

### 10. 가장 위험한 부분 — secret을 화면과 로그에 남기지 않는다

API key, 토큰, 비밀번호 같은 값을 **비밀값(secret)**이라고 부른다.

나쁜 예:

```python
api_key = "REAL_SECRET_VALUE"
print(api_key)
```

문제:

- 소스 저장소에 올라갈 수 있음
- 로그에 남을 수 있음
- 화면 공유/스크린샷에 노출될 수 있음
- AI 프롬프트에 그대로 들어갈 수 있음

더 안전한 방향:

```text
코드에는 비밀값을 직접 저장하지 않음
↓
환경변수/보안 저장소에서 로드
↓
로그에는 실제 값을 출력하지 않음
```

비밀값을 이미 공개 저장소에 올렸다면 단순히 줄을 지우는 것만으로 충분하지 않을 수 있다. **키 폐기/재발급**이 필요할 수 있다.

---

### 11. 명령 실행 전 30초 감사

AI가 다음 명령을 제안했다고 하자.

```bash
some-tool --force --recursive /some/path
```

실행 전 확인:

```text
1. some-tool이 무엇인가?
2. --force는 무엇을 강제로 하는가?
3. --recursive는 하위 폴더 전체에 영향을 주는가?
4. /some/path가 내가 원하는 경로가 맞는가?
5. 삭제/덮어쓰기인가?
6. 되돌릴 방법이 있는가?
7. 관리자 권한이 필요한가?
```

내용을 이해하지 못하면 실행하지 않는다.

---

### 12. 실제 사례 — Python 버전이 예상과 다름

터미널에서 `python`을 실행했는데 프로젝트가 기대한 버전과 다르다고 하자.

가능한 원인:

- 여러 Python 설치
- PATH 순서
- 가상환경 미활성화
- IDE와 터미널이 다른 실행 파일 사용

따라서 “Python이 설치 안 됨”이라고 바로 결론내리지 않는다.

확인할 것:

```text
어떤 python 실행 파일이 선택됐는가?
버전은 무엇인가?
현재 환경은 무엇인가?
IDE도 같은 실행 파일을 쓰는가?
```

---

### 13. 실제 사례 — 로그를 파일에 저장했더니 기존 내용이 사라짐

명령:

```bash
command > app.log
```

기존 `app.log`가 덮어써지는 환경이었다면 이전 로그가 사라질 수 있다.

이 문제는 “로그 프로그램 버그”가 아니라 **리다이렉션 방식** 문제다.

그래서 중요한 파일을 대상으로 처음 명령을 시험할 때는 새 임시 파일을 사용한다.

## 장 끝 미니 프로젝트 — AI 명령 감사표

AI에게 파일 정리나 빌드 명령 하나를 만들어달라고 한다. **실제로 실행하기 전에** 아래 표를 채운다.

| 항목 | 확인 |
|---|---|
| 실행 프로그램 | |
| 옵션 | |
| 대상 경로 | |
| 읽기/쓰기/삭제 여부 | |
| 관리자 권한 여부 | |
| 비밀값 포함 여부 | |
| 실패하면 영향 | |
| 되돌리는 방법 | |

표를 다 채울 수 없는 명령은 이해하지 못한 부분이 있다는 뜻이다.

---

## 핵심 용어

| 용어 | 뜻 |
|---|---|
| 터미널 | 명령을 입력하고 결과를 보는 인터페이스 |
| 셸(shell) | 명령을 해석하고 프로그램을 실행하는 소프트웨어 |
| 옵션 | 명령 동작을 바꾸는 인자 |
| 권한(permission) | 읽기·쓰기·실행 등 허용된 작업 범위 |
| stdin/stdout/stderr | 기본 입력/정상 출력/오류 출력 통로 |
| redirection | 입력·출력 방향을 파일 등으로 바꾸는 것 |
| pipe | 한 명령의 출력을 다음 명령 입력으로 연결하는 방식 |
| 환경변수 | 실행 환경에서 프로그램에 전달하는 설정값 |
| PATH | 명령 실행 파일을 찾기 위해 검색하는 폴더 목록 |
| secret | API key·토큰·비밀번호 같은 비밀값 |

---

## 이 장을 끝내고 할 수 있어야 하는 것

1. 터미널과 셸을 구분한다.
2. 긴 명령을 프로그램·옵션·대상으로 나눠 읽는다.
3. 파일 명령 전 현재 위치와 경로를 확인한다.
4. Permission denied에 무조건 관리자 권한을 쓰지 않는다.
5. 리다이렉션과 파이프의 데이터 흐름을 설명한다.
6. 환경변수와 PATH의 역할을 말할 수 있다.
7. 비밀값을 코드·로그·공개 저장소에 노출하지 않는다.
8. AI가 만든 명령을 실행 전 감사할 수 있다.
