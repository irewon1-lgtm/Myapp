## V1-C05. 권한·터미널·환경변수

**원본 Lesson 매핑:** V1-13, V1-14, V1-15, V1-16

### 1. 현실 문제에서 시작하기

AI가 “터미널에서 이 명령을 실행하세요”라고 답했는데 사용자는 명령이 무엇을 바꾸는지 모른 채 복사해 붙여 넣는 경우가 많다. 이 상태에서 `sudo`, 삭제 명령, 환경변수 변경을 섞으면 작은 문제를 큰 문제로 만들 수 있다. 반대로 터미널을 전혀 모르고 있으면 로그를 검색하고 빌드 상태를 확인하는 기본 작업조차 AI에게 완전히 의존하게 된다.

이 장의 목표는 명령어 백과사전을 외우는 것이 아니다. **명령 = 프로그램 + 옵션 + 인자 + 입력/출력 + 종료상태**라는 구조를 이해하고, 권한을 최소화하며, 결과를 눈으로 검증하는 능력을 만든다.

### 2. Mental Model

```text
shell prompt
  ↓
명령어 + 옵션 + 인자
  ↓
새 process 실행
  ├─ stdin  ← 입력
  ├─ stdout → 정상 결과
  ├─ stderr → 오류/진단
  └─ exit code → 성공/실패 신호

환경변수(PATH, HOME, ...)
  └─ 실행되는 process에 전달되는 설정
```

### 3. 핵심 개념 해부

#### 사용자·그룹·최소권한

운영체제는 파일과 자원마다 누가 읽고, 쓰고, 실행할 수 있는지 권한을 둔다. 관리자/root 권한은 강력하지만 모든 문제를 관리자 권한으로 해결하면 보안 경계를 없애는 셈이다. `permission denied`는 성가신 장애가 아니라 보호장치가 제대로 작동한다는 신호일 수 있다.

실전 원칙은 “필요한 작업에 필요한 최소 권한만”이다. 파일 한 개 접근이 필요한데 전체 폴더 권한을 과도하게 풀거나 관리자 실행으로 우회하지 않는다.

#### 명령 구조와 exit code

대부분의 CLI는 `command --option argument` 같은 구조를 가진다. 옵션은 동작 방식을 바꾸고 인자는 대상이나 값을 준다. 명령 실행 후 화면에 아무 것도 안 나왔다고 실패한 것이 아니다. stdout, stderr, exit code를 구분해야 자동화에서 정확한 판정을 할 수 있다.

AI가 제안한 명령을 실행하기 전에는 “무엇을 읽는가/쓰는가/삭제하는가/네트워크를 쓰는가/권한을 요구하는가”를 해석한다. 이해되지 않는 파괴적 옵션은 실행하지 않는다.

#### pipe와 redirection

파이프는 한 프로그램의 출력을 다른 프로그램의 입력으로 연결해 작은 도구를 조합한다. redirection은 출력을 파일로 보내거나 입력을 파일에서 가져온다. 예를 들어 수천 줄 로그에서 `ERROR`만 골라 새 파일에 저장할 수 있다.

중요한 위험은 `>`가 기존 파일을 덮어쓸 수 있다는 점처럼 도구마다 부작용이 있다는 것이다. 따라서 “명령이 짧다 = 안전하다”가 아니다. 먼저 샘플 출력에 실행하고, 원본을 보존한다.

#### PATH와 명령 탐색

shell에 `python`이나 `git`을 입력하면 운영체제는 PATH에 나열된 디렉터리에서 실행파일을 찾는다. 설치는 되었지만 PATH에 없으면 `command not found`가 날 수 있다. 반대로 PATH 앞쪽에 같은 이름의 다른 실행파일이 있으면 예상과 다른 버전이 실행된다.

그래서 `which`/`where` 계열 도구나 실행파일의 실제 위치를 확인하는 습관이 중요하다. “재설치”보다 먼저 지금 어떤 파일이 실행되고 있는지 확인한다.

#### 환경변수와 secret

환경변수는 process에 설정값을 전달하는 한 방법이다. API key나 환경별 URL을 코드에 하드코딩하지 않도록 도울 수 있지만, 환경변수도 자동으로 안전한 금고가 되는 것은 아니다. process 목록, 로그, 빌드 설정에 노출될 수 있으므로 secret manager와 플랫폼 보안기능을 상황에 맞게 사용해야 한다.

환경변수는 부모 프로세스에서 자식 프로세스로 전달되는 경우가 많다. 터미널에서 값을 바꿨는데 이미 실행 중인 앱에는 적용되지 않는 이유를 이해하는 데 도움이 된다.

### 3A. 개념을 연결해서 생각하기 — 터미널은 “강력한 버튼”이 아니라 관찰 가능한 프로그램 실행환경

GUI에서는 버튼을 누르면 내부에서 어떤 프로그램이 어떤 인자로 실행됐는지 숨겨질 때가 많다. 터미널은 그 구조를 더 직접 보여준다. 그래서 초보자에게 위험해 보이지만, 제대로 배우면 오히려 **무엇을 실행했는지 기록하고 재현하기 쉬운 도구**가 된다.

명령 한 줄을 읽을 때는 왼쪽부터 “실행파일은 무엇인가 → 옵션은 무엇인가 → 대상 인자는 무엇인가 → 입력은 어디서 오는가 → 출력은 어디로 가는가”로 해체한다. 예를 들어 `grep ERROR app.log > errors.txt`는 `grep` 프로그램이 `ERROR` 패턴과 `app.log` 파일을 인자로 받고 정상출력을 `errors.txt`로 보낸다. 한 줄 전체를 주문처럼 외울 필요가 없다.

exit code는 자동화에서 특히 중요하다. 사람이 화면 문장을 읽을 때는 “Success!”를 보면 성공이라 생각할 수 있지만 프로그램은 지역화된 문장이나 버전 변경에 취약하다. 잘 설계된 CLI는 성공/실패 상태를 exit code로 표현한다. CI가 테스트 실패를 감지하는 것도 이 원리와 연결된다.

권한은 **누가 무엇을 할 수 있는가**에 대한 정책이다. 문제를 해결하려고 권한을 넓히면 증상은 사라질 수 있지만 원인을 해결한 것이 아닐 수 있다. 예를 들어 한 설정파일만 읽으면 되는데 전체 프로젝트를 `777`로 풀면 future attack surface와 accidental write 가능성을 키운다. minimum permission을 찾는 과정이 곧 설계다.

PATH는 “어떤 명령을 실행할 것인가”에 영향을 주므로 supply-chain과도 연결된다. 앞쪽 디렉터리에 악성 혹은 오래된 동일 이름 executable이 있으면 사용자는 정상 도구라고 생각하고 다른 파일을 실행할 수 있다. 따라서 `command -v`, `which`, `where` 같은 위치 확인은 단순 troubleshooting을 넘어 **실행 대상 검증**이다.

환경변수는 configuration 전달 통로다. 개발/운영 API URL, feature flag, credential이 섞이기 쉽기 때문에 중요도와 보안수준을 분리해야 한다. secret을 환경변수에 넣는 것이 소스에 하드코딩하는 것보다 나을 수 있지만, 프로세스 환경을 볼 수 있는 도구나 crash report, CI log로 노출될 가능성은 여전히 있다. “코드에 안 보임 = 안전”이 아니다.

### 4. Worked Examples

#### Worked Example A — stdout/stderr/exit code

정상 명령과 존재하지 않는 파일을 읽는 명령을 각각 실행해 본다. 화면에 나타나는 정상출력과 오류출력을 분리하고 종료코드를 확인한다. 자동화에서는 화면 문장을 문자열로 억지 판독하기보다 가능하면 exit code와 구조화된 결과를 활용한다.

#### Worked Example B — PATH 문제

도구를 설치했는데 `tool: command not found`가 난다.

1. 설치 위치를 확인한다.
2. 현재 PATH를 확인한다.
3. 설치 폴더가 PATH에 들어 있는지 본다.
4. 새 shell에 반영되는 설정인지 확인한다.
5. PATH를 무작정 맨 앞에 추가하기 전에 동일 이름 실행파일 충돌을 확인한다.

### 4A. 미니 사례집

**사례 1 — 빌드 명령이 내 PC에서만 됨**  
내 shell PATH에 전역 설치 도구가 숨어 있다. CI clean environment에서는 없다. dependency를 프로젝트에 명시한다.

**사례 2 — AI가 모든 권한을 열라고 함**  
먼저 실패 대상 파일/폴더 하나의 owner와 권한을 본다. 특정 user/group만 필요한 권한을 준다.

**사례 3 — 로그필터 명령이 원본을 덮어씀**  
redirection 방향을 잘못 썼다. 실습은 복사본에서 하고, destructive write 전에는 output path를 눈으로 확인한다.

**사례 4 — API key가 CI 로그에 찍힘**  
환경변수는 사용했지만 debug print가 전체 환경을 출력했다. secret masking과 log redaction을 추가한다.

### 5. 그럴듯하지만 틀린 판단

1. permission denied가 나면 무조건 관리자 권한으로 실행한다.
2. 명령어가 화면에 아무것도 출력하지 않으면 실패라고 생각한다.
3. PATH를 바꾸면 이미 실행 중인 모든 앱에 즉시 적용된다고 생각한다.
4. 환경변수에 넣은 API key는 어떤 상황에서도 안전하다고 생각한다.

### 5A. AI가 준 명령 실행 전 체크

- **읽기만 하는가, 쓰는가, 삭제하는가?**
- **현재 디렉터리는 어디인가?**
- **wildcard가 예상보다 넓은 범위를 잡지 않는가?**
- **관리자/root 권한이 정말 필요한가?**
- **secret이 command history나 log에 남는가?**
- **실행파일 실제 경로와 버전은 무엇인가?**
- **실패 시 원복 가능한가?**
- **복사본/테스트폴더에서 먼저 실행할 수 있는가?**

이 중 하나라도 답을 모르면 바로 실행하지 않고 명령을 더 작은 단위로 분해한다.

### 5B. 안전한 터미널 사용 습관

터미널 명령을 실행하기 전에 `pwd` 또는 현재 위치를 확인하는 습관은 단순하지만 강력하다. 같은 삭제 명령도 홈 디렉터리와 임시 테스트폴더에서 영향범위가 완전히 다르다. 작업 디렉터리를 명시적으로 바꾸고 대상 파일을 먼저 `list`하는 두 단계가 사고를 줄인다.

wildcard(`*`)는 편리하지만 예상보다 많은 파일을 매칭할 수 있다. 삭제·이동·권한변경과 조합할 때는 먼저 읽기 전용 명령으로 실제 매칭 목록을 본다. AI가 만든 명령에서 wildcard가 보이면 특히 범위를 확인한다.

shell history는 재현에는 좋지만 secret이 남을 수 있다. API key를 명령 인자로 직접 넣으면 history나 process list에 기록될 수 있다. 도구가 secure prompt, secret file, credential store를 지원하는지 확인한다.

pipe chain이 길어지면 어느 단계에서 데이터가 달라졌는지 찾기 어렵다. 처음에는 각 명령을 따로 실행하고 중간출력을 확인한 뒤 합친다. 이것은 프로그래밍에서 작은 함수로 분해하는 원칙과 같다.

오류가 나면 관리자 권한으로 재실행하기 전에 “이 명령이 쓰려는 정확한 경로와 owner는 누구인가?”를 확인한다. 개발 프로젝트 폴더가 root 소유로 바뀌어 매번 sudo가 필요해지는 상황은 권한을 해결한 것이 아니라 더 꼬이게 만든 것이다.

### 6. Guided Lab

테스트용 폴더에서 안전한 명령 5개를 실행하고 표를 만든다: 명령, 인자, stdout, stderr, exit code, 파일 변경 여부. 이어 100줄짜리 샘플 로그에서 특정 문자열을 검색하고, 결과를 새 파일로 저장하되 원본은 유지한다. 마지막으로 실행 중인 `python` 또는 사용 가능한 CLI 도구의 실제 경로를 확인한다.

### 7. Independent Lab

AI가 제안한 5개의 터미널 명령을 골라 “읽기 전용/파일 수정/삭제/네트워크/권한상승”으로 분류하고, 실행 전 확인할 조건을 각각 적는다. 실제 위험 명령을 실행할 필요는 없다.

### 8. Debug Challenge

**상황:** 어제까지 되던 빌드가 오늘 `command not found`로 실패한다. 재설치하지 말고 shell 종류, PATH, 실행파일 실제 위치, 가상환경 활성화 여부, 터미널 재시작 여부를 순서대로 확인한다. 각 확인 결과를 기록해 어떤 한 가지 변경이 문제를 만들었는지 좁힌다.

### 9. AI Audit

AI가 `sudo chmod -R 777 ...` 같은 과도한 권한변경을 제안하면 즉시 반려한다. 왜 필요한지, 어느 파일만 접근하면 되는지, 더 좁은 권한으로 가능한지, 원복방법이 있는지 묻는다. 명령은 실행결과보다 **영향범위**를 먼저 검토한다.

### 9B. 핵심용어를 한 문장으로 다시 말하기

- **stdin**: 프로그램이 외부에서 입력을 받는 기본 통로다.
- **stdout**: 정상 결과를 다음 프로그램이나 화면으로 보내는 기본 통로다.
- **stderr**: 오류·진단 정보를 stdout과 분리해 보내는 통로다.
- **exit code**: 프로세스가 끝날 때 성공/실패 상태를 기계가 읽을 수 있게 남기는 값이다.
- **PATH**: 명령 이름만 입력했을 때 실행파일을 찾는 디렉터리 목록이다.
- **환경변수**: process가 실행될 때 읽을 수 있는 외부 설정값이다.
- **least privilege**: 작업에 필요한 최소 권한만 주는 원칙이다.

이 일곱 용어를 명령 예제 하나에 모두 연결해 설명할 수 있으면 이 장의 구조를 잡은 것이다.
