## V1-C03. 프로그램이 실행된다는 뜻 — 프로세스·스레드·동시성을 처음부터

**이 장의 대상:** 앱을 설치하고 실행해본 적은 있지만 `프로세스`, `스레드`, `백그라운드`, `동시성`이 무엇인지 모르는 사람.

**이 장의 목표:** “앱이 멈췄다”는 말을 더 잘게 나눌 수 있게 된다. 설치된 프로그램과 실행 중인 프로그램을 구분하고, 한 앱 안에서도 여러 작업이 서로 영향을 줄 수 있다는 것을 이해한다.

---

### 1. 설치되어 있다는 것과 실행 중이라는 것은 다르다

휴대폰에 앱이 설치되어 있다고 하자.

아이콘이 보인다고 해서 그 앱이 지금 계속 일을 하고 있는 것은 아니다.

설치된 상태는 대략 다음과 같다.

```text
앱 파일이 저장장치에 있음
↓
아이콘과 정보가 등록됨
↓
필요할 때 실행할 수 있음
```

하지만 사용자가 앱을 누르면 새로운 일이 시작된다.

```text
앱 실행
↓
운영체제가 메모리와 실행 공간을 준비
↓
프로그램 코드가 실제로 동작
```

이 차이를 이해하는 것이 이번 장의 출발점이다.

---

### 2. 프로그램과 프로세스의 차이

**프로그램(program)**은 저장장치에 있는 코드와 자료의 묶음이다.

**프로세스(process)**는 그 프로그램이 실제로 실행되고 있는 상태다.

쉬운 비유를 써보자.

```text
요리책        = 프로그램
실제로 요리 중 = 프로세스
```

요리책은 서랍에 있어도 존재한다.

하지만 누군가 그 책을 펼치고 실제로 요리해야 “실행 중”이다.

앱도 비슷하다.

> **프로그램 = 저장되어 있는 명령 묶음**
>
> **프로세스 = 그 프로그램이 지금 실행 중인 상태**

---

### 3. 앱을 껐다 켜면 같은 프로세스일까?

보통 앱을 완전히 종료한 뒤 다시 실행하면 새로운 실행 상태가 만들어질 수 있다.

같은 APK를 사용하더라도 실행 상태는 달라질 수 있다.

프로세스 안에는 예를 들어 이런 정보가 있다.

```text
현재 어디까지 실행했는지
현재 변수 값은 무엇인지
어떤 파일을 열고 있는지
어떤 네트워크 연결을 사용 중인지
메모리에 무엇이 올라가 있는지
```

그래서 “앱 파일은 똑같다”와 “실행 중 상태도 똑같다”는 같은 말이 아니다.

---

### 4. 운영체제는 왜 프로세스를 관리할까?

스마트폰에서는 여러 앱이 함께 존재한다.

메신저, 브라우저, 음악, 지도, 주식 앱 등이 동시에 자원을 사용하려 한다.

운영체제는 각 앱이 CPU, 메모리, 파일, 네트워크 같은 자원을 사용할 수 있도록 관리한다.

> **운영체제(OS) = 여러 프로그램이 기기 자원을 안전하게 쓰도록 관리하는 기본 소프트웨어**

앱이 하드웨어를 마음대로 직접 사용하지 못하게 경계를 만들어주는 것도 중요한 역할이다.

---

### 5. 프로세스 안에서도 여러 일이 일어난다

앱 하나를 실행했다고 해서 항상 한 가지 일만 하는 것은 아니다.

예를 들어 주식 앱을 생각해 보자.

```text
화면 버튼 반응
가격 데이터 요청
이미지 불러오기
로컬 DB 저장
알림 등록
로그 기록
```

이런 일들이 서로 다른 시점에 진행될 수 있다.

사용자 입장에서는 한 앱이지만 내부에서는 여러 작업이 협력한다.

---

### 6. 스레드는 무엇일까?

프로세스 안에서 실제 실행 흐름을 나누어 생각할 때 **스레드(thread)**라는 말을 사용한다.

처음에는 다음처럼만 이해하자.

> **스레드 = 프로세스 안에서 명령을 실행해 나가는 하나의 작업 흐름**

비유하면 큰 주방이 프로세스라면 여러 요리사가 각각의 작업 흐름처럼 움직일 수 있다.

다만 실제 컴퓨터 내부는 이 비유보다 복잡하다.

지금은 “한 프로세스 안에서도 여러 실행 흐름이 있을 수 있다”는 감각만 잡는다.

---

### 7. 메인 스레드와 화면

Android 앱에서 사용자가 보는 화면을 갱신하는 중요한 실행 흐름을 흔히 **메인 스레드(main thread)** 또는 **UI 스레드(UI thread)**라고 부른다.

> **메인/UI 스레드 = 화면 입력과 화면 갱신을 담당하는 중심 실행 흐름**

버튼을 눌렀을 때 빨리 반응하려면 이 흐름이 오랫동안 막히지 않아야 한다.

---

### 8. 왜 화면이 멈출까?

메인 스레드에서 너무 오래 걸리는 일을 직접 처리한다고 해보자.

예를 들면:

```text
아주 큰 파일 읽기
느린 네트워크 응답 기다리기
복잡한 계산 오래 하기
대량 DB 작업
```

그동안 화면을 처리할 여유가 없으면 사용자는 앱이 멈춘 것처럼 느낄 수 있다.

```text
사용자 터치
↓
메인 스레드가 긴 작업 중
↓
터치 처리 지연
↓
화면 멈춘 것처럼 보임
```

이것이 “화면이 멈춤 = 앱 전체가 죽음”이 아닐 수 있는 이유다.

---

### 9. 백그라운드 작업은 무엇일까?

화면을 막지 않도록 오래 걸리는 일을 다른 실행 흐름이나 작업 시스템에서 처리할 수 있다.

이를 일반적으로 **백그라운드 작업(background work)**이라고 부른다.

> **백그라운드 작업 = 사용자가 화면을 쓰는 동안 뒤쪽에서 진행되는 작업**

예:

```text
이미지 다운로드
데이터 동기화
로그 저장
파일 압축
서버 요청
```

다만 “백그라운드면 무조건 안전하다”는 뜻은 아니다.

Android에는 배터리, 수명주기, 작업 제한 같은 별도 규칙이 있다. Chapter 9에서 다시 다룬다.

---

### 10. 비동기라는 말

네트워크 요청은 결과가 즉시 오지 않는다.

요청을 보낸 뒤 몇 밀리초 또는 몇 초 후에 응답이 올 수 있다.

이처럼 “지금 요청했지만 결과는 나중에 도착할 수 있다”는 흐름을 설명할 때 **비동기(asynchronous)**라는 말을 자주 쓴다.

> **비동기 = 어떤 일을 시작하고, 결과를 기다리는 동안 다른 일을 계속할 수 있는 방식**

반대로 한 일이 끝날 때까지 다음 일을 기다리는 흐름을 **동기(synchronous)**라고 부르기도 한다.

지금은 문법보다 차이만 이해한다.

---

### 11. 식당 비유로 비동기 이해하기

손님이 주문을 했다.

#### 동기적으로 기다린다면

```text
주문
↓
주방 앞에서 음식이 나올 때까지 아무것도 못 함
↓
음식 수령
```

#### 비동기적으로 처리한다면

```text
주문
↓
번호표 받음
↓
자리에 앉아 다른 일을 함
↓
음식 준비 완료 알림
↓
수령
```

앱도 네트워크 요청을 보낸 뒤 화면 전체를 얼려버리는 것보다 다른 UI 동작을 계속 허용하는 편이 좋은 경우가 많다.

---

### 12. 동시에 여러 일이 진행된다는 뜻

**동시성(concurrency)**은 여러 작업이 같은 시간 구간에 함께 진행되는 상황을 다룬다.

완전히 같은 순간에 여러 CPU 코어가 실행하는지보다 먼저 중요한 것은:

> 여러 작업의 순서가 서로 영향을 줄 수 있다는 사실

이다.

예:

```text
작업 A: 데이터 다운로드
작업 B: 화면 새로고침
작업 C: DB 저장
```

A가 끝나기 전에 B가 잘못 실행되면 비어 있는 데이터를 화면에 보여줄 수 있다.

---

### 13. 작업 순서가 왜 중요할까?

다음 흐름이 있다고 하자.

```text
1. 서버에서 데이터 받기
2. 받은 데이터 저장하기
3. 저장된 데이터를 화면에 보여주기
```

정상 순서는 1→2→3이다.

그런데 잘못된 순서가 되면:

```text
3. 화면 표시
1. 데이터 도착
2. 저장
```

처음 화면에는 값이 없을 수 있다.

따라서 비동기 코드를 읽을 때는 “무엇이 먼저 끝나야 하는가?”를 확인한다.

---

### 14. 공유 상태는 무엇일까?

여러 작업이 같은 값을 읽고 바꾸면 문제가 생길 수 있다.

예:

```text
잔액 = 100
```

두 작업이 동시에 10씩 빼려고 한다.

둘 다 처음 값 100을 읽고 각각 90을 저장하면 최종 값이 90이 될 수 있다.

하지만 실제로 두 번 빠졌다면 기대값은 80이다.

이처럼 여러 작업이 같은 데이터를 건드릴 때 주의가 필요하다.

> **공유 상태 = 여러 작업이 함께 읽거나 바꾸는 공통 데이터**

---

### 15. 레이스 조건은 무엇일까?

여러 작업의 실행 순서에 따라 결과가 달라지는 문제를 **레이스 조건(race condition)**이라고 부른다.

영어가 어렵지만 뜻은 단순하다.

> **레이스 조건 = 누가 먼저 실행되느냐에 따라 결과가 달라지는 오류 상황**

예:

```text
A가 먼저 끝나면 정상
B가 먼저 끝나면 오류
```

이런 버그는 항상 발생하지 않고 “가끔” 발생할 수 있어서 찾기 어렵다.

---

### 16. 가끔 발생하는 버그를 무시하면 안 되는 이유

사용자가 말한다.

> “10번 중 1번 저장이 안 돼요.”

초보자는 “대부분 되니까 괜찮다”고 생각할 수 있다.

하지만 동시성 문제는 실행 시점이나 네트워크 속도에 따라 가끔만 발생할 수 있다.

따라서:

```text
몇 번 중 몇 번 발생했는가?
어떤 조건에서 발생했는가?
작업 순서가 달랐는가?
```

를 기록해야 한다.

---

### 17. 순서를 기록하는 가장 쉬운 방법 — 로그

작업이 언제 시작하고 끝나는지 로그를 남기면 흐름을 볼 수 있다.

```text
10:00:00 request start
10:00:01 UI refresh
10:00:02 response received
10:00:03 DB save
```

이 기록을 보면 UI refresh가 응답보다 먼저 일어났다는 단서를 얻을 수 있다.

로그는 Chapter 7에서 훨씬 자세히 배운다.

---

### 18. Python으로 실행 순서 감각 익히기

아래 코드는 아직 동시성 코드가 아니다.

순서를 읽는 기초 연습이다.

```python
print("1. 시작")
print("2. 데이터 준비")
print("3. 화면 표시")
```

실행 결과:

```text
1. 시작
2. 데이터 준비
3. 화면 표시
```

이 순서를 정확히 읽을 수 있어야 나중에 순서가 바뀌는 코드를 이해할 수 있다.

---

### 19. 상태 변화 추적하기

```python
status = "대기"
print(status)
status = "다운로드 중"
print(status)
status = "완료"
print(status)
```

실행 결과:

```text
대기
다운로드 중
완료
```

이 코드는 하나의 작업 상태가 시간에 따라 바뀌는 모습을 단순하게 표현한다.

앱에서도 비슷한 상태를 가질 수 있다.

```text
LOADING
SUCCESS
ERROR
```

영어를 몰라도 뜻은 각각 “불러오는 중 / 성공 / 오류”라고 이해하면 된다.

---

### 20. 로딩 화면이 필요한 이유

서버 응답이 즉시 오지 않는다면 사용자는 기다리는 중인지 앱이 멈춘 것인지 구분하기 어렵다.

그래서 화면에 다음처럼 상태를 보여줄 수 있다.

```text
데이터를 불러오는 중입니다...
```

응답이 오면:

```text
데이터 표시
```

실패하면:

```text
불러오기에 실패했습니다. 다시 시도하세요.
```

좋은 UI는 현재 비동기 상태를 사용자에게 알려준다.

---

### 21. 오류 상태도 하나의 상태다

앱이 실패했을 때 상태를 숨기지 않는다.

예를 들어:

```text
loading = false
error = "network timeout"
```

처럼 실패 정보를 보존할 수 있다.

“데이터 없음”과 “불러오기 실패”는 다른 상황이다.

```text
데이터 없음 = 정상적으로 조회했지만 결과가 0개
오류       = 조회 과정 자체가 실패
```

이 차이는 실제 앱 품질에서 매우 중요하다.

---

### 22. 앱이 멈춘 것처럼 보일 때 첫 질문

다음 순서로 생각해본다.

1. 터치가 아예 반응하지 않는가?
2. 화면 애니메이션도 멈췄는가?
3. 네트워크 작업만 늦는가?
4. 백그라운드 저장만 실패하는가?
5. 앱 프로세스가 종료됐는가?
6. 오류 메시지가 있는가?

“멈춤”이라는 한 단어를 더 구체적인 증상으로 바꾸는 것이 중요하다.

---

### 23. ANR이라는 말

Android에서 앱이 사용자 입력에 너무 오래 응답하지 않는 상황에서 **ANR**이라는 말을 볼 수 있다.

`Application Not Responding`의 약자다.

영어는 외우지 않아도 된다.

> **ANR = 앱이 너무 오래 사용자 입력에 응답하지 않는 상태**

주된 원인 후보 중 하나가 메인 스레드를 오래 막는 작업이다.

하지만 모든 멈춤이 ANR인 것은 아니다.

---

### 24. 크래시와 멈춤은 다르다

**크래시(crash)**는 앱이 오류로 비정상 종료되는 상황이다.

```text
멈춤: 앱은 살아 있지만 반응이 늦거나 없음
크래시: 앱 실행이 비정상적으로 종료됨
```

둘은 증상도 진단 방법도 다르다.

앱이 홈 화면으로 튕겼다면 크래시 로그를 확인할 수 있다.

화면은 그대로인데 입력이 안 된다면 메인 스레드 차단이나 무한루프 등을 의심할 수 있다.

---

### 25. 무한루프가 화면을 멈추게 할 수 있다

다음 코드를 보자.

```python
while True:
    print("계속")
```

`True`가 계속 참이므로 끝없이 반복할 수 있다.

종료 조건이 없는 반복은 CPU 시간을 계속 사용할 수 있다.

UI 스레드에서 이런 일이 생기면 앱 반응에 큰 문제가 생길 수 있다.

반복문은 Python 장에서 자세히 배우지만 지금은:

> **끝나는 조건이 없는 작업은 위험할 수 있다.**

정도로 기억한다.

---

### 26. 오래 걸리는 작업과 큰 계산

다음과 같은 작업은 시간이 오래 걸릴 수 있다.

```text
수십만 행 데이터 정리
대형 이미지 처리
파일 압축
네트워크 타임아웃 대기
DB 대량 조회
```

무조건 다른 스레드로 보내라는 단순 규칙을 외우기보다 먼저:

1. 실제로 얼마나 걸리는가?
2. UI 반응을 막는가?
3. 취소가 필요한가?
4. 결과가 언제 필요한가?

를 판단한다.

---

### 27. 작업 취소도 중요하다

사용자가 화면을 떠났는데 오래된 네트워크 요청이 계속 진행될 수 있다.

나중에 그 결과가 돌아와 이미 다른 화면의 상태를 덮어쓰면 문제가 생길 수 있다.

그래서 비동기 작업에서는:

```text
이 작업이 아직 필요한가?
화면이 살아 있는가?
취소해야 하는가?
```

를 고려한다.

Android의 수명주기와 연결되는 내용은 Chapter 9에서 다룬다.

---

### 28. 같은 버튼을 빠르게 여러 번 누르면?

사용자가 저장 버튼을 5번 연속 누른다고 하자.

앱이 매 클릭마다 서버 요청을 보내면 같은 데이터가 여러 번 저장될 수 있다.

이런 문제를 막기 위해:

```text
버튼 일시 비활성화
중복 요청 방지
요청 ID 사용
멱등성 설계
```

같은 방법을 사용할 수 있다.

`멱등성`은 중급 자동화와 API 장에서 자세히 배운다.

지금은 **중복 실행도 동시성 문제의 한 형태가 될 수 있다**는 감각만 가진다.

---

### 29. 실제 예제 — 검색 결과가 가끔 뒤집힌다

사용자가 빠르게 두 번 검색했다.

```text
첫 번째: AAPL
두 번째: MSFT
```

AAPL 요청은 느리고 MSFT 요청은 빨랐다.

순서:

```text
AAPL 요청 시작
MSFT 요청 시작
MSFT 응답 도착
화면에 MSFT 표시
AAPL 응답 늦게 도착
화면이 AAPL로 다시 바뀜
```

사용자는 마지막에 MSFT를 검색했는데 AAPL이 보인다.

이것이 작업 완료 순서가 사용자 입력 순서와 다를 수 있는 문제다.

해결에는 최신 요청만 반영하는 등의 설계가 필요할 수 있다.

---

### 30. 실제 예제 — 저장 버튼 중복

사용자가 버튼을 빠르게 두 번 눌렀다.

```text
요청 1 → 주문 생성
요청 2 → 주문 생성
```

결과가 중복될 수 있다.

진단할 때 확인한다.

```text
클릭 이벤트가 몇 번 발생했는가?
네트워크 요청이 몇 번 전송됐는가?
서버가 몇 번 처리했는가?
DB 행이 몇 개 생겼는가?
```

문제 위치가 UI인지 서버인지 DB인지 분리한다.

### 31. 실제 예제 — 앱 종료 후 작업

앱 화면을 닫았는데 업로드가 계속되어야 하는 작업이 있을 수 있다.

반대로 화면을 떠나면 즉시 취소해야 하는 작업도 있다.

모든 백그라운드 작업을 같은 방식으로 처리하면 안 된다.

```text
짧은 화면 전용 작업
장시간 보장되어야 하는 작업
사용자에게 진행을 알려야 하는 작업
```

목적에 맞는 Android 작업 방식을 선택해야 한다.

이 내용은 지금 외우지 않는다.

### 32. 작업 흐름을 표로 적는 습관

복잡해지면 머릿속으로만 생각하지 말고 적는다.

| 시각 | 작업 | 상태 |
|---|---|---|
| 10:00:00 | 검색 클릭 | 시작 |

### 34. 코드 읽기 연습 — 상태 변화

```python
state = "IDLE"
print(state)
state = "LOADING"
print(state)
state = "SUCCESS"
print(state)
```

우리말로 읽으면:

```text
처음: 대기
그 다음: 불러오는 중
마지막: 성공
```

코딩을 배우면서 영어 상수를 자주 보겠지만 의미를 먼저 한국어로 바꿔 읽는 습관을 만든다.

---

### 35. 코드 읽기 연습 — 작업 목록

```python
tasks = ["화면", "네트워크", "저장"]
for task in tasks:
    print(task)
```

아직 `for` 문법을 완벽히 몰라도 된다.

이 코드는 목록의 값을 하나씩 출력한다.

결과:

```text
화면
네트워크
저장
```

중요한 것은 코드를 한 줄씩 의미로 바꾸는 능력이다.

### 36. 용어사전

| 쉬운 말 | 영어 | 뜻 |
|---|---|---|
| 프로그램 | program | 저장된 코드와 자료의 묶음 |
| 프로세스 | process | 프로그램이 실제 실행 중인 상태 |
| 스레드 | thread | 프로세스 안의 실행 흐름 |
| 메인 스레드 | main thread | 앱의 중심 실행 흐름 |
| UI 스레드 | UI thread | 화면 처리와 관련된 중심 실행 흐름 |
| 백그라운드 | background | 화면 뒤에서 진행되는 작업 |
| 비동기 | asynchronous | 결과를 기다리는 동안 다른 일을 계속할 수 있는 흐름 |
| 동기 | synchronous | 일이 끝날 때까지 다음 흐름이 기다리는 방식 |
| 동시성 | concurrency | 여러 작업이 같은 시간 구간에 함께 진행되는 문제를 다루는 개념 |
| 공유 상태 | shared state | 여러 작업이 함께 읽거나 바꾸는 데이터 |
| 레이스 조건 | race condition | 실행 순서에 따라 결과가 달라지는 오류 |
| 크래시 | crash | 앱이 비정상 종료되는 상황 |
| ANR | Application Not Responding | Android 앱이 오래 응답하지 않는 상태 |

### 39. 한 장 요약

1. 설치된 프로그램과 실행 중 프로세스는 다르다.
2. 프로세스 안에는 하나 이상의 실행 흐름이 있을 수 있다.
3. Android의 UI 반응은 메인/UI 스레드가 오래 막히지 않는 것이 중요하다.
4. 오래 걸리는 작업은 화면과 분리해 처리하는 경우가 많다.
5. 비동기 작업은 결과가 나중에 도착할 수 있다.
6. 요청 순서와 응답 순서는 다를 수 있다.
7. 여러 작업이 같은 상태를 바꾸면 실행 순서 문제가 생길 수 있다.
8. 레이스 조건은 “가끔” 나타날 수 있다.
9. 멈춤과 크래시는 같은 증상이 아니다.
10. 작업 시작·완료 시각을 로그로 남기면 순서를 확인하기 쉽다.
11. 문제를 해결할 때 “어떤 작업이 언제 무엇을 바꿨는가”를 본다.

다음 장에서는 프로그램이 실행될 때 사용하는 **메모리, 저장장치, CPU**를 아주 기초부터 배운다.
