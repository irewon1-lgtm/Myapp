# TRACK 03 · 프로그램이 실행된다는 뜻

이번 TRACK에서는 `프로그램을 실행한다`는 말을 더 깊게 이해한다.

특히 다음과 같은 말을 처음부터 만든다.

- 프로세스
- 작업
- 순차 실행
- 기다림
- 동기
- 비동기
- 콜백
- Promise
- async
- await
- 이벤트
- 이벤트 루프
- 작업 대기열
- 마이크로태스크
- 타임아웃
- 취소
- 경쟁 상태

중요한 규칙:

> 위 단어들을 한꺼번에 외우지 않는다. 앞의 개념을 이해한 다음에만 다음 단어가 등장한다.

---

## BLOCK 01 · 저장된 프로그램과 실행 중인 프로그램

### LESSON 01 · 설치되어 있다는 것

휴대폰에 계산기 앱이 설치되어 있다고 하자.

앱을 열지 않아도 계산기 앱의 파일은 저장공간에 남아 있다.

즉:

```text
프로그램 파일이 저장되어 있음
```

과

```text
프로그램이 지금 일을 하고 있음
```

은 같은 말이 아니다.

### LESSON 02 · 실행한다는 것

앱을 누르면 운영체제가 프로그램을 실제로 동작시킬 준비를 한다.

프로그램의 코드가 실행되고 필요한 메모리를 사용하며 화면을 만들 수 있다.

이제 `실행 중인 프로그램`이라는 상태가 생긴다.

---

## BLOCK 02 · 프로세스란 무엇인가

### LESSON 01 · 실행 중인 프로그램을 가리키는 말

**프로세스(process)**는 실행 중인 프로그램의 한 인스턴스를 가리킬 때 사용하는 말이다.

`인스턴스(instance)`라는 단어가 아직 어렵다면 지금은 이렇게 생각한다.

> 프로세스 = 지금 실제로 실행되고 있는 프로그램의 작업 공간

프로그램 파일이 `설계도`라면 프로세스는 그 설계도를 가지고 실제로 일을 시작한 상태에 비유할 수 있다.

### LESSON 02 · 같은 프로그램이 여러 번 실행될 수도 있다

컴퓨터에서는 같은 프로그램을 여러 번 실행해서 여러 프로세스가 생기는 경우도 있다.

각 프로세스는 운영체제가 관리하는 실행 단위다.

세부 구조는 나중에 운영체제 TRACK에서 더 깊게 다룬다.

---

## BLOCK 03 · 작업이란 무엇인가

### LESSON 01 · 프로그램 안에는 여러 일이 있다

앱 하나도 동시에 많은 일을 해야 할 수 있다.

예:

```text
버튼 눌림 확인
화면 그리기
파일 읽기
인터넷에서 데이터 받기
계산하기
```

이처럼 프로그램이 해야 하는 각각의 일을 편하게 **작업(task)**이라고 부르자.

`task`는 문맥에 따라 더 구체적인 기술적 의미로도 쓰이지만 지금은 `해야 할 일 하나`라는 뜻부터 잡는다.

### LESSON 02 · 모든 작업의 시간이 같지는 않다

숫자 두 개를 더하는 일은 매우 빨리 끝날 수 있다.

인터넷으로 큰 파일을 받는 일은 몇 초 또는 더 오래 걸릴 수 있다.

따라서 프로그램을 이해하려면 `무슨 일을 하는가`뿐 아니라 **그 일이 언제 시작되고 언제 끝나는가**도 봐야 한다.

---

## BLOCK 04 · 순서대로 실행한다는 것

### LESSON 01 · 첫 번째 일이 끝난 뒤 두 번째 일

다음처럼 세 일이 있다고 하자.

```text
A. 문을 연다
B. 방에 들어간다
C. 불을 켠다
```

A가 끝난 뒤 B, B가 끝난 뒤 C를 수행하면 순서가 명확하다.

프로그램도 여러 작업을 차례대로 수행할 수 있다.

이를 **순차 실행(sequential execution)**이라고 부를 수 있다.

### LESSON 02 · 코드에서 순서 보기

```python
print("A")
print("B")
print("C")
```

결과:

```text
A
B
C
```

이 작은 예에서는 앞줄이 끝난 뒤 다음 줄이 실행된다.

하지만 실제 프로그램에는 오래 걸리는 작업이 섞인다. 그때 `기다림` 문제가 생긴다.

---

## BLOCK 05 · 기다린다는 것은 무엇인가

### LESSON 01 · 일이 끝날 때까지 다음 일을 못 한다면

카페에서 커피를 주문했다고 하자.

커피가 나올 때까지 5분 동안 계산대 앞에서 아무것도 못 하고 서 있어야 한다면 비효율적일 수 있다.

프로그램도 어떤 작업의 결과를 기다려야 할 수 있다.

예:

```text
인터넷 요청 시작
↓
서버가 답할 때까지 기다림
↓
답이 도착
```

### LESSON 02 · 기다림 자체가 항상 나쁜 것은 아니다

어떤 결과가 반드시 있어야 다음 계산을 할 수 있다면 기다려야 한다.

예:

```text
총합 계산에 필요한 숫자 파일을 읽음
↓
파일 값이 있어야 합계를 계산 가능
```

문제는 `기다려야 하는 부분` 때문에 **관계없는 다른 일까지 모두 멈춰 버리는가**다.

---

## BLOCK 06 · 블로킹이라는 말

### LESSON 01 · 다른 진행을 막고 있는 상태

어떤 작업이 끝날 때까지 그 실행 흐름이 다음 일을 진행하지 못하고 기다리는 상황을 설명할 때 **블로킹(blocking)**이라는 말을 쓴다.

`block`은 막는다는 뜻과 연결해서 기억하면 된다.

한 줄 뜻:

> 블로킹 = 어떤 작업을 기다리느라 해당 실행 흐름이 다음 일을 진행하지 못하는 상태

### LESSON 02 · 화면이 멈춘 것처럼 보이는 이유

사용자가 버튼을 눌렀다.

프로그램이 큰 파일을 읽는 일을 시작했다.

만약 화면을 그리는 일과 버튼 반응을 처리해야 하는 흐름이 그 파일 읽기가 끝날 때까지 막혀 버리면 화면이 멈춘 것처럼 보일 수 있다.

따라서 시간이 오래 걸리는 작업은 어디에서 어떻게 기다리게 할지 중요하다.

---

## BLOCK 07 · 동기라는 말

### LESSON 01 · 결과를 기다리며 흐름을 맞추는 방식

프로그래밍에서 **동기(synchronous)**라는 말은 문맥에 따라 세부 뜻이 있지만 초보 단계에서는 다음 상황부터 이해한다.

```text
작업 A 시작
↓
A가 끝날 때까지 기다림
↓
A 결과 받음
↓
다음 작업 B 진행
```

한 줄 뜻:

> 동기 방식 = 앞 작업의 완료와 결과를 기다리면서 다음 흐름을 이어 가는 방식

### LESSON 02 · 동기 방식이 나쁜 것은 아니다

동기 방식은 순서를 이해하기 쉽고 결과가 반드시 필요한 경우 자연스럽다.

작은 계산처럼 즉시 끝나는 작업은 동기적으로 처리해도 문제가 없을 수 있다.

중요한 것은 `동기 = 나쁨`이라고 외우지 않는 것이다.

**작업의 성격과 기다리는 시간이 문제다.**

---

## BLOCK 08 · 비동기를 말하기 전에 상황부터

### LESSON 01 · 라면 물을 올리고 다른 일을 하기

물을 끓이는 데 5분 걸린다고 하자.

물을 올린 뒤 5분 동안 냄비만 바라볼 필요는 없다.

그동안 식탁을 닦을 수도 있다.

```text
물 끓이기 시작
↓
기다리는 동안 식탁 닦기
↓
물이 끓음
↓
다음 요리 진행
```

핵심은 **기다리는 동안 다른 일을 진행할 수 있다**는 것이다.

### LESSON 02 · 프로그램에서도 비슷한 문제가 있다

앱이 인터넷에서 사진을 받는 데 3초 걸린다고 하자.

사진이 오는 동안 버튼 터치나 화면 움직임까지 모두 멈출 필요는 없다.

프로그램은 사진 요청을 시작해 두고, 그 작업이 끝났을 때 결과를 처리하도록 구성할 수 있다.

이제 `비동기`라는 이름을 붙일 준비가 되었다.

---

## BLOCK 09 · 비동기란 무엇인가

### LESSON 01 · 한 줄 정의

**비동기(asynchronous)**는 시간이 걸리는 작업의 완료를 그 자리에서 계속 붙잡고 기다리지 않고, 다른 일을 진행하다가 나중에 결과가 준비되었을 때 이어서 처리할 수 있게 구성하는 방식이다.

아주 쉽게:

> 비동기 = 기다리는 동안 다른 일을 할 수 있게 만드는 방식

### LESSON 02 · 동기와 비동기 비교

동기적인 흐름의 간단한 그림:

```text
A 시작
A 완료
B 시작
B 완료
```

비동기 작업이 섞인 흐름의 간단한 그림:

```text
A 시작
A는 시간이 걸림
B를 진행할 수 있음
A 완료 소식이 옴
A 결과 처리
```

중요:

`비동기`가 `모든 일이 정확히 동시에 실행된다`는 뜻은 아니다.

동시에 실제 계산되는지, 번갈아 처리되는지는 다른 개념이다.

---

## BLOCK 10 · 비동기에서 가장 중요한 질문

### LESSON 01 · 언제 끝나는가

비동기 작업에서는 코드를 읽을 때 다음 네 가지를 찾는다.

```text
1. 작업은 어디서 시작되는가?
2. 완료되기 전까지 무엇을 할 수 있는가?
3. 완료 사실을 어떻게 알게 되는가?
4. 결과를 어디에서 사용하는가?
```

이 네 질문이 잡히면 비동기 코드를 이해하기 훨씬 쉬워진다.

### LESSON 02 · 시작 순서와 완료 순서는 다를 수 있다

작업 A를 먼저 시작하고 작업 B를 나중에 시작해도 B가 더 빨리 끝날 수 있다.

```text
A 시작 ─────────────── 완료
B 시작 ─── 완료
```

따라서 `먼저 시작했으니 반드시 먼저 끝난다`고 생각하면 안 된다.

이 차이가 나중에 경쟁 상태를 이해하는 바닥이 된다.

---

## BLOCK 11 · 콜백을 배우기 전에 '끝나면 할 일'

### LESSON 01 · 완료 후 행동을 미리 정하기

세탁기를 돌린다고 하자.

세탁기가 끝났을 때 알림이 오면 빨래를 꺼낸다.

```text
세탁 시작
↓
다른 일
↓
세탁 완료 알림
↓
빨래 꺼내기
```

프로그램에서도 `이 작업이 끝났을 때 이 일을 해`라고 미리 정할 수 있다.

### LESSON 02 · 이제 콜백이라는 이름 붙이기

다른 작업이 끝났을 때 호출해서 실행하도록 넘겨 주는 함수를 **콜백(callback)**이라고 부른다.

`call back`은 `나중에 다시 불러 준다`는 느낌으로 기억하면 처음 이해하기 쉽다.

한 줄 뜻:

> 콜백 = 어떤 일이 끝나거나 특정 사건이 생겼을 때 나중에 실행하도록 넘겨 둔 함수

---

## BLOCK 12 · 콜백의 아주 작은 예

### LESSON 01 · JavaScript 예제

```javascript
setTimeout(function () {
  console.log("끝났어");
}, 1000);
```

처음 보는 기호가 많다. 한꺼번에 외우지 않는다.

이 코드는 `약간의 시간이 지난 뒤 안쪽 함수를 실행하라`는 예로 볼 수 있다.

여기서 안쪽의:

```javascript
function () {
  console.log("끝났어");
}
```

부분이 나중에 실행할 함수다.

### LESSON 02 · 콜백이 많아지면 읽기 어려울 수 있다

비동기 작업이 여러 단계로 이어지면서 콜백 안에 또 콜백을 계속 넣으면 코드의 구조가 깊어져 읽기 어려워질 수 있다.

이 문제를 다루는 여러 방법 가운데 JavaScript에서는 `Promise`라는 구조를 많이 사용한다.

다음 BLOCK에서 Promise만 따로 배운다.

---

## BLOCK 13 · Promise를 배우기 전에 '미래 결과표'

### LESSON 01 · 아직 결과가 없지만 나중에 정해질 수 있다

택배를 주문했다고 하자.

지금 당장 물건을 손에 들고 있지는 않다.

하지만 주문 정보에는 이런 상태가 있을 수 있다.

```text
배송 중
배송 완료
배송 실패
```

미래에 결과가 정해지는 일을 표현할 수 있는 틀이 있으면 편리하다.

### LESSON 02 · Promise라는 이름

JavaScript의 **Promise**는 비동기 작업의 미래 결과를 나타내는 객체다.

`객체(object)`는 아직 깊게 배우지 않았다. 지금은 `여러 정보와 기능을 묶어 다루는 값` 정도로 임시 이해한다. 객체는 별도 과정에서 정확하게 배운다.

Promise의 핵심 상태를 아주 쉽게 보면:

```text
아직 결과 없음
→ 성공해서 결과가 생김
또는
→ 실패해서 이유가 생김
```

한 줄 뜻:

> Promise = 나중에 성공 결과나 실패 이유가 정해질 비동기 작업을 다루는 JavaScript 구조

## BLOCK 14 · Promise의 세 상태

### LESSON 01 · pending

아직 작업이 끝나지 않은 상태를 **pending**이라고 부른다.

쉽게:

> pending = 아직 기다리는 중

### LESSON 02 · fulfilled

작업이 성공적으로 끝나 결과가 준비된 상태를 **fulfilled**라고 부른다.

쉽게:

> fulfilled = 성공해서 결과가 준비됨

### LESSON 03 · rejected

작업이 실패해서 실패 이유가 정해진 상태를 **rejected**라고 부른다.

쉽게:

> rejected = 실패해서 이유가 생김

이 세 단어를 단순 암기하지 않는다. `기다리는 중 → 성공 또는 실패`라는 상태 변화로 이해한다.

## BLOCK 15 · then과 catch

### LESSON 01 · 성공하면 할 일

Promise가 성공했을 때 결과를 받아 다음 일을 연결할 때 JavaScript에서 `.then(...)`을 사용할 수 있다.

```javascript
getData().then(function (data) {
  console.log(data);
});
```

사람말:

```text
getData 작업을 시작한다.
성공하면 data를 받아서 보여 준다.
```

`getData`는 예시 이름이다.

### LESSON 02 · 실패하면 할 일

실패했을 때 처리할 일을 `.catch(...)`로 연결할 수 있다.

```javascript
getData()
  .then(function (data) {
    console.log(data);
  })
  .catch(function (error) {
    console.log("실패");
  });
```

여기서 중요한 것은 문법 암기가 아니라 **성공 경로와 실패 경로가 둘 다 존재한다**는 것이다.

## BLOCK 16 · async라는 말

### LESSON 01 · 함수 앞의 async

JavaScript에서 함수 앞에 `async`를 붙이면 그 함수를 비동기 결과를 다루기 편한 형태로 사용할 수 있다.

```javascript
async function loadData() {
  // 작업
}
```

한 줄 뜻:

> async = 이 함수를 Promise 기반 비동기 흐름으로 다루겠다는 표시

### LESSON 02 · async라고 쓰면 자동으로 모든 일이 동시에 되는가

아니다.

`async`라는 단어 하나가 CPU를 여러 개 만들어 주는 것이 아니다.

또 함수 안의 모든 작업이 자동으로 빠르게 끝나는 것도 아니다.

`async`는 JavaScript에서 Promise를 반환하는 함수와 `await` 문법을 사용하기 위한 중요한 문법이다.

---

## BLOCK 17 · await라는 말

### LESSON 01 · 비동기 결과가 준비될 때까지 그 함수의 다음 부분을 기다리기

`await`는 `async` 함수 안에서 Promise의 결과가 준비될 때까지 **그 함수의 다음 진행을 잠시 멈춘 것처럼** 작성할 수 있게 해 준다.

```javascript
async function loadData() {
  const data = await getData();
  console.log(data);
}
```

사람말:

```text
getData를 시작한다.
그 결과가 준비될 때까지 이 함수의 다음 줄은 기다린다.
결과가 오면 data에 넣는다.
data를 보여 준다.
```

### LESSON 02 · await가 프로그램 전체를 멈춘다는 뜻은 아니다

매우 중요하다.

`await`가 있다고 해서 JavaScript 프로그램 전체와 컴퓨터 전체가 얼어붙는다는 뜻은 아니다.

해당 async 함수의 이어지는 부분은 결과를 기다리지만, 실행 환경은 다른 이벤트나 작업을 처리할 수 있다.

이것이 `await`를 단순히 `그냥 동기처럼 멈춤`으로 외우면 안 되는 이유다.

## BLOCK 18 · 오류 처리와 try/catch

### LESSON 01 · 비동기 작업도 실패한다

인터넷 연결이 끊길 수 있다.

파일이 없을 수 있다.

사용자가 권한을 거부할 수 있다.

따라서 `성공했을 때` 코드만 만들면 부족하다.

### LESSON 02 · try와 catch

JavaScript에서 오류가 생길 수 있는 코드를 `try` 안에서 실행하고 오류가 발생하면 `catch`에서 처리하는 형태를 사용할 수 있다.

```javascript
async function loadData() {
  try {
    const data = await getData();
    console.log(data);
  } catch (error) {
    console.log("불러오기 실패");
  }
}
```

사람말:

```text
일단 시도한다.
성공하면 결과를 사용한다.
문제가 발생하면 실패 처리를 한다.
```

`error` 객체의 자세한 구조는 뒤에서 배운다.

## BLOCK 19 · 이벤트란 무엇인가

### LESSON 01 · 프로그램에게 '무슨 일이 생겼다'는 사실

사용자가 버튼을 눌렀다.

키보드 키를 눌렀다.

타이머 시간이 되었다.

데이터가 도착했다.

이처럼 프로그램이 반응할 수 있는 `어떤 일이 발생했다`는 것을 **이벤트(event)**라고 부른다.

한 줄 뜻:

> 이벤트 = 프로그램이 반응할 수 있는 어떤 사건이 발생했다는 것

### LESSON 02 · 이벤트 처리

버튼을 눌렀을 때 실행할 함수를 등록할 수 있다.

```javascript
button.addEventListener("click", function () {
  console.log("버튼 눌림");
});
```

지금은 `addEventListener`를 외우지 않는다.

핵심은:

```text
click 이벤트가 생기면
등록한 함수를 실행한다
```

라는 구조다.

## BLOCK 20 · JavaScript는 일을 어떻게 이어 받을까

### LESSON 01 · 한 번에 읽어야 할 것이 너무 많다

JavaScript 코드에는 다음이 섞일 수 있다.

- 지금 바로 실행할 코드
- 나중에 끝나는 비동기 작업
- 버튼 클릭 같은 이벤트
- 타이머가 끝났을 때 실행할 함수

실행 환경은 이런 `나중에 할 일`을 언제 실행할지 관리해야 한다.

이제 **이벤트 루프**를 이해하기 위한 바닥이 만들어졌다.

### LESSON 02 · 먼저 '실행 중인 코드가 있는가'를 본다

JavaScript는 일반적인 브라우저 실행 흐름에서 현재 실행 중인 JavaScript 코드가 끝난 뒤, 준비된 다음 작업을 실행하도록 조정한다.

정확한 내부 구조는 실행 환경에 따라 세부 차이가 있지만 큰 생각은 다음과 같다.

```text
지금 실행 중인 코드
↓ 끝남
준비된 다음 작업 확인
↓
다음 코드 실행
```

## BLOCK 21 · 호출 스택이란 무엇인가

### LESSON 01 · 함수가 어디까지 실행 중인지 기억해야 한다

함수 A가 함수 B를 부르고, B가 함수 C를 부를 수 있다.

프로그램은 `지금 어떤 함수 안에 있고, 끝나면 어디로 돌아가야 하는가`를 기억해야 한다.

JavaScript의 실행을 설명할 때 **호출 스택(call stack)**이라는 구조를 사용한다.

한 줄 뜻:

> 호출 스택 = 현재 실행 중인 함수 호출의 순서를 쌓아 관리하는 구조

`stack`은 쌓아 올린 접시를 생각하면 쉽다. 가장 마지막에 올린 접시를 먼저 꺼내는 모습과 비슷하다.

### LESSON 02 · 왜 알아야 하나

오류 메시지에서 `stack trace`라는 말을 볼 수 있다.

어떤 함수가 다른 함수를 부르다가 오류가 났는지 경로를 보여 줄 때 호출 스택의 정보가 도움이 된다.

자세한 오류 추적은 로그 TRACK에서 다시 배운다.

## BLOCK 22 · 작업 대기열이란 무엇인가

### LESSON 01 · 준비된 일을 바로 실행할 수 없다면

현재 JavaScript 코드가 실행 중인데 버튼 클릭 처리나 타이머 완료 같은 일이 준비되었다고 하자.

현재 코드를 중간에서 무조건 끊고 아무렇게나 끼어들게 하면 실행 흐름을 이해하기 어려워진다.

그래서 `나중에 실행할 준비가 된 작업`을 기다리게 하는 구조를 설명할 때 **작업 대기열(task queue)**이라는 말을 사용한다.

한 줄 뜻:

> task queue = 실행할 준비가 되었지만 차례를 기다리는 작업들이 놓이는 대기 줄

### LESSON 02 · 대기열은 무조건 '먼저 들어온 모든 것부터' 하나뿐인가

JavaScript 실행 환경에는 작업 종류에 따라 서로 다른 대기 구조와 우선 처리 규칙이 있다.

그래서 `대기열이 하나뿐이고 무조건 모든 작업이 같은 규칙으로 처리된다`고 외우면 나중에 틀린다.

그중 중요한 구분 하나가 `task`와 `microtask`다.

## BLOCK 23 · 이벤트 루프란 무엇인가

### LESSON 01 · 이제 이름 붙이기

현재 실행 중인 코드가 끝났는지 보고, 실행할 준비가 된 다음 작업을 적절한 규칙에 따라 실행 흐름으로 가져오는 반복적인 조정 과정을 설명할 때 **이벤트 루프(event loop)**라는 말을 쓴다.

아주 쉽게:

> 이벤트 루프 = 지금 코드가 끝났는지 확인하고 기다리던 다음 일을 실행하도록 계속 조정하는 구조

### LESSON 02 · 이벤트 루프가 인터넷 요청 자체를 하는 것은 아니다

이벤트 루프가 모든 일을 직접 수행한다고 생각하면 안 된다.

브라우저나 Node.js 같은 실행 환경에는 타이머, 네트워크, 파일 입출력 등을 처리하는 다른 기능들이 있다.

비동기 작업이 끝나고 `이제 이어서 실행할 코드가 준비되었다`는 상황을 JavaScript 실행 흐름과 연결하는 데 이벤트 루프가 중요한 역할을 한다.

## BLOCK 24 · 마이크로태스크란 무엇인가

### LESSON 01 · Promise 뒤의 작업은 별도 우선순위 규칙이 있다

Promise가 완료되어 `.then(...)`이나 `await` 이후의 이어지는 코드가 준비될 때, JavaScript에서는 이런 작업을 **마이크로태스크(microtask)**라는 대기 종류로 다룬다.

한 줄 뜻:

> microtask = 현재 실행 중인 코드가 끝난 뒤 일반적인 다음 task보다 먼저 처리되는 별도 대기 종류의 작은 작업

### LESSON 02 · 왜 이것을 알아야 하나

다음처럼 타이머와 Promise가 함께 있을 때 단순히 `코드에 먼저 적힌 순서`만 보고 결과를 예측하면 틀릴 수 있다.

```javascript
console.log("A");

setTimeout(function () {
  console.log("B");
}, 0);

Promise.resolve().then(function () {
  console.log("C");
});

console.log("D");
```

일반적인 브라우저나 Node.js 환경에서 기대하는 출력은:

```text
A
D
C
B
```

이유를 한 단계씩 본다.

1. 지금 실행 중인 동기 코드에서 A를 출력한다.
2. 타이머의 콜백 B는 나중 작업으로 준비된다.
3. Promise의 C도 나중 작업으로 준비되는데 microtask 쪽이다.
4. D를 출력하고 현재 코드가 끝난다.
5. microtask인 C를 먼저 처리한다.
6. 그 다음 타이머 작업 B를 처리한다.

이제 `microtask`를 배운 이유가 생겼다.

## BLOCK 25 · 타임아웃이란 무엇인가

### LESSON 01 · 영원히 기다릴 수는 없다

인터넷 요청을 보냈는데 서버가 아무 답도 하지 않는다고 하자.

프로그램이 영원히 기다리면 사용자도 무엇이 일어나는지 모른 채 기다릴 수 있다.

그래서 `이 시간보다 오래 걸리면 실패로 처리하자`라는 제한을 둘 수 있다.

이런 시간 제한을 **타임아웃(timeout)**이라고 부른다.

한 줄 뜻:

> timeout = 정해 둔 시간 안에 작업이 끝나지 않으면 더 이상 정상 대기로 보지 않는 시간 제한

### LESSON 02 · 타임아웃 시간이 짧다고 항상 좋은가

너무 짧으면 정상적으로 조금 느린 요청도 실패로 처리할 수 있다.

너무 길면 실제 장애인데도 사용자가 너무 오래 기다릴 수 있다.

따라서 타임아웃 값은 작업의 성격과 네트워크 환경 등을 고려해 정해야 한다.

## BLOCK 26 · 취소란 무엇인가

### LESSON 01 · 더 이상 필요 없는 작업

사용자가 검색창에 `사과`를 검색했다.

곧바로 마음을 바꿔 `바나나`를 검색했다.

첫 번째 검색 작업이 아직 끝나지 않았더라도 이제 그 결과가 필요 없을 수 있다.

이때 진행 중인 작업을 **취소(cancellation)**할 수 있는 구조가 도움이 된다.

한 줄 뜻:

> 취소 = 아직 끝나지 않은 작업을 더 이상 계속하거나 결과에 반영하지 않도록 중단시키는 것

### LESSON 02 · 취소했다고 모든 외부 작업이 완전히 사라진다는 뜻은 아니다

프로그램에서 결과 처리를 취소해도 이미 서버로 보낸 요청이 서버 쪽에서는 처리되고 있을 수 있다.

어떤 수준까지 취소되는지는 기술과 시스템 구조에 따라 다르다.

따라서 `취소 버튼 눌렀으니 세상 모든 곳에서 작업이 사라졌다`고 단정하면 안 된다.

---

## BLOCK 27 · 경쟁 상태를 배우기 전에 순서 문제

### LESSON 01 · 먼저 시작한 요청이 늦게 끝날 수 있다

사용자가 검색을 두 번 빠르게 했다.

```text
1번 요청: 사과 검색 ────────── 4초 후 완료
2번 요청: 바나나 검색 ── 1초 후 완료
```

2번 요청이 나중에 시작했지만 먼저 끝났다.

화면에는 바나나 결과가 나타났다.

그런데 조금 뒤 1번의 사과 결과가 도착해서 화면을 다시 덮어썼다면 사용자는 `바나나`를 검색했는데 `사과`를 보게 된다.

### LESSON 02 · 이제 경쟁 상태라는 이름

여러 작업의 실행 또는 완료 순서가 달라질 때 결과가 달라지는 문제를 **경쟁 상태(race condition)**라고 부른다.

한 줄 뜻:

> race condition = 여러 작업 중 무엇이 먼저 끝나거나 값을 바꾸느냐에 따라 결과가 달라져 버리는 문제

`race`는 누가 먼저 도착하는지 겨루는 경주를 떠올리면 된다.

---

## BLOCK 28 · 경쟁 상태를 막는 기본 생각

### LESSON 01 · 최신 요청인지 확인하기

앞의 검색 문제에서는 각 요청에 번호를 붙일 수 있다.

```text
사과 요청 = 1
바나나 요청 = 2
```

결과가 도착했을 때 `이 결과가 아직 최신 요청인가?`를 확인하고 최신이 아니면 화면에 반영하지 않는 방법을 생각할 수 있다.

### LESSON 02 · 오래된 작업 취소하기

새 검색이 시작되면 이전 검색을 취소할 수도 있다.

어떤 방법이 더 적합한지는 시스템 구조에 따라 다르다.

핵심은 **완료 순서가 시작 순서와 다를 수 있다는 사실을 코드가 고려해야 한다**는 것이다.

## BLOCK 29 · 동시성과 병렬성

### LESSON 01 · 동시성

여러 작업이 서로 겹쳐 진행될 수 있도록 다루는 성질을 **동시성(concurrency)**이라고 부른다.

한 개의 작업을 조금 진행하고 다른 작업으로 바꾸는 식으로도 여러 작업이 겹쳐 진행되는 것처럼 다룰 수 있다.

### LESSON 02 · 병렬성

여러 작업이 실제 같은 시간에 서로 다른 처리 자원에서 실행되는 것을 설명할 때 **병렬성(parallelism)**이라는 말을 사용한다.

초보 단계의 구분:

```text
동시성 = 여러 일을 겹쳐 다루는 구조
병렬성 = 여러 일을 실제로 같은 시간에 실행하는 것
```

비동기, 동시성, 병렬성은 관련은 있지만 같은 말이 아니다.

## BLOCK 30 · 스레드란 무엇인가

### LESSON 01 · 프로세스 안의 실행 흐름

프로세스 안에서 코드를 실행하는 흐름을 설명할 때 **스레드(thread)**라는 말을 사용한다.

한 프로세스가 하나 이상의 스레드를 가질 수 있다.

아주 쉽게:

> 스레드 = 프로세스 안에서 명령을 실행해 나가는 흐름

### LESSON 02 · 비동기 = 새 스레드라는 공식은 틀리다

매우 중요하다.

비동기 코드를 썼다고 무조건 새로운 스레드가 하나 생기는 것은 아니다.

JavaScript에서는 이벤트 루프와 실행 환경의 비동기 기능을 이용해 한 JavaScript 실행 스레드에서도 여러 기다림을 효율적으로 다룰 수 있다.

따라서:

```text
비동기 = 멀티스레드
```

라고 외우면 안 된다.

`멀티스레드`는 여러 스레드를 사용하는 구조다. 더 깊은 내용은 운영체제와 서버 과정에서 다룬다.

## BLOCK 31 · 실제 비동기 코드 읽기

### LESSON 01 · fetch 예제를 보기 전에 의미부터

웹에서 데이터를 받는 JavaScript 예제에 `fetch`라는 기능을 자주 본다.

`fetch`는 네트워크 요청을 시작하고 Promise를 돌려준다.

아직 HTTP 세부는 배우지 않았다. 여기서는 `시간이 걸릴 수 있는 데이터 요청`이라고만 본다.

```javascript
async function load() {
  const response = await fetch("/data");
  console.log("도착");
}
```

한 줄씩 사람말로 바꾼다.

```text
load라는 비동기 함수를 만든다.
/data에 데이터를 요청한다.
그 요청 결과가 준비될 때까지 load 함수의 다음 줄은 기다린다.
결과가 준비되면 "도착"을 보여 준다.
```

### LESSON 02 · 실패 경로 추가

```javascript
async function load() {
  try {
    const response = await fetch("/data");
    console.log("도착");
  } catch (error) {
    console.log("요청 실패");
  }
}
```

이제 성공과 실패 두 경로가 있다.

중요한 질문:

```text
작업 시작 위치는?
완료를 기다리는 위치는?
성공 후 코드는?
실패 후 코드는?
```

## BLOCK 32 · 비동기 오류를 찾는 순서

### LESSON 01 · '비동기 오류'라는 말로 끝내지 않는다

`비동기 오류가 났다`는 말은 너무 넓다.

다음처럼 쪼갠다.

1. 작업 자체가 시작되지 않았는가?
2. 작업은 시작됐지만 끝나지 않는가?
3. 성공 결과는 왔는데 처리 코드가 틀렸는가?
4. 실패했는데 실패 처리를 하지 않았는가?
5. 두 작업 결과가 순서 때문에 서로 덮어썼는가?
6. 너무 오래 걸려 타임아웃 되었는가?
7. 취소된 작업의 결과를 다시 반영했는가?

### LESSON 02 · 시간 순서를 적는다

비동기 문제는 시간 순서를 적으면 보이기 시작한다.

```text
12:00:00.000 요청 A 시작
12:00:00.100 요청 B 시작
12:00:01.000 요청 B 완료
12:00:01.050 화면에 B 반영
12:00:04.000 요청 A 완료
12:00:04.050 화면에 A 반영 ← 문제
```

이 기록만 봐도 `오래된 A 결과가 최신 B 화면을 덮었다`는 의심을 만들 수 있다.

## BLOCK 33 · TRACK 03 핵심 용어 사전

| 용어 | 아주 쉬운 뜻 |
|---|---|
| 프로세스 | 지금 실제로 실행되고 있는 프로그램의 작업 공간 |
| 작업 | 프로그램이 해야 하는 일 하나 |
| 순차 실행 | 일을 정한 순서대로 차례차례 실행하는 것 |
| 블로킹 | 어떤 작업을 기다리느라 해당 실행 흐름이 다음 일을 진행하지 못하는 상태 |
| 동기 | 앞 작업의 완료와 결과를 기다리며 다음 흐름을 이어 가는 방식 |
| 비동기 | 기다리는 동안 다른 일을 진행하고 결과가 준비되면 이어 처리할 수 있게 하는 방식 |
| 콜백 | 특정 일이 끝나거나 사건이 생겼을 때 나중에 실행하도록 넘겨 둔 함수 |
| Promise | 나중에 성공 결과나 실패 이유가 정해질 비동기 작업을 다루는 JavaScript 구조 |
| pending | 아직 결과를 기다리는 Promise 상태 |
| fulfilled | Promise 작업이 성공해 결과가 준비된 상태 |
| rejected | Promise 작업이 실패한 상태 |
| async | Promise 기반 비동기 함수를 만들고 await를 사용할 수 있게 하는 JavaScript 문법 |
| await | Promise 결과가 준비될 때까지 해당 async 함수의 다음 부분을 기다리게 하는 문법 |
| 이벤트 | 프로그램이 반응할 수 있는 어떤 사건 |
| 호출 스택 | 현재 실행 중인 함수 호출 순서를 쌓아 관리하는 구조 |
| task queue | 실행할 준비가 되었지만 차례를 기다리는 작업들의 대기 줄 |
| 이벤트 루프 | 현재 실행이 끝난 뒤 준비된 다음 일을 실행하도록 계속 조정하는 구조 |
| microtask | 현재 코드가 끝난 뒤 일반 task보다 먼저 처리되는 별도 대기 종류의 작업 |
| timeout | 정한 시간 안에 끝나지 않은 작업을 더 이상 정상 대기로 보지 않는 시간 제한 |
| cancellation | 더 이상 필요 없는 진행 중 작업을 중단하거나 결과 반영을 막는 것 |
| race condition | 여러 작업의 완료 순서에 따라 결과가 달라져 버리는 문제 |
| 동시성 | 여러 일을 겹쳐 다룰 수 있도록 구성하는 성질 |
| 병렬성 | 여러 일을 실제 같은 시간에 실행하는 것 |
| 스레드 | 프로세스 안에서 명령을 실행해 나가는 흐름 |

## BLOCK 34 · TRACK 03 종합 훈련

### LESSON 01 · 동기와 비동기를 자기 말로 설명하기

금지 답변:

```text
동기는 synchronous고 비동기는 asynchronous다.
```

이것은 영어를 바꿔 적은 것뿐이다.

좋은 설명은 이런 내용을 포함해야 한다.

```text
동기: 필요한 앞 작업이 끝나기를 기다리며 다음으로 진행하는 흐름
비동기: 시간이 걸리는 작업의 완료를 계속 붙잡지 않고 다른 일을 하다가 결과가 준비되면 이어 처리하는 흐름
```

### LESSON 02 · 출력 순서 예상

다음 코드의 출력 순서를 실행 전에 적는다.

```javascript
console.log("1");

Promise.resolve().then(function () {
  console.log("2");
});

setTimeout(function () {
  console.log("3");
}, 0);

console.log("4");
```

일반적인 환경에서 예상:

```text
1
4
2
3
```

그 이유를 `현재 코드 → microtask → 다음 task` 순서로 설명한다.

### LESSON 03 · 경쟁 상태 분석

두 검색 요청의 시작 시간과 완료 시간을 직접 만들어 보고, 오래된 요청이 나중에 도착해서 최신 화면을 덮는 상황을 설명한다.

해결 후보도 두 개 이상 적는다.

```text
최신 요청 번호 확인
이전 요청 취소
```

### TRACK 끝 미니 프로젝트 · 최신 검색 결과만 보여 주기

가상의 검색 앱을 설계한다.

사용자가 매우 빠르게 세 번 검색한다고 하자.

```text
요청 1: 서울
요청 2: 부산
요청 3: 제주
```

각 요청의 완료 시간이 달라질 수 있다.

목표:

> 가장 마지막에 사용자가 검색한 `제주`의 결과만 최종 화면에 남게 한다.

코드를 작성하기 전에 다음을 문장으로 설계한다.

1. 요청이 시작될 때 번호를 어떻게 붙일 것인가?
2. 결과가 도착했을 때 최신 요청인지 어떻게 확인할 것인가?
3. 오래된 결과는 어떻게 처리할 것인가?
4. 요청이 실패하면 어떤 상태를 보여 줄 것인가?
5. 너무 오래 걸리면 timeout을 어떻게 생각할 것인가?
6. 새 요청이 오면 이전 요청을 취소할 것인가?

이 설계를 자기 말로 설명할 수 있으면 비동기 개념을 단순 문법 암기보다 훨씬 깊게 이해한 것이다.
