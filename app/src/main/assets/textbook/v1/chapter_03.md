## V1-C03. 프로그램이 실행된다는 뜻 — 프로세스·스레드·비동기

**목표:** 앱이 “실행 중”이라는 말을 정확히 이해하고, 멈춤·느림·순서 꼬임을 **프로세스 / 스레드 / 비동기 / 공유 상태** 관점으로 나눠 볼 수 있게 된다.

---

### 1. 설치된 앱과 실행 중인 앱은 다르다

APK가 설치되어 있다는 사실과 앱이 지금 실행 중이라는 사실은 다르다.

저장장치에 있는 프로그램이 실제로 실행되면 운영체제는 메모리와 자원을 배정하고 실행 상태를 만든다. 이 실행 중인 단위를 **프로세스(process)**라고 한다.

```text
설치된 앱 파일
   ↓ 실행
프로세스
   ↓ 종료
실행 상태 사라짐
```

앱이 강제 종료되면 설치 파일이 지워지는 것이 아니라 **프로세스가 끝나는 것**이다.

이 구분은 장애 진단에서 중요하다.

```text
앱 아이콘이 있다        → 설치됨
앱을 누르면 즉시 꺼진다 → 프로세스 시작 후 실패 가능
앱은 열리지만 멈춘다    → 프로세스는 살아 있지만 내부 작업이 막혔을 가능성
```

---

### 2. 하나의 프로세스 안에서도 여러 일이 진행된다

앱은 한 가지 일만 하지 않는다.

예를 들어 주식 앱은 동시에 이런 일을 할 수 있다.

```text
사용자 터치 처리
화면 그리기
네트워크 요청
DB 읽기
이미지 로딩
로그 기록
```

프로세스 안에서 실행 흐름을 나누는 대표 단위가 **스레드(thread)**다.

초보자는 스레드를 “한 프로그램 안에서 일을 진행하는 실행 흐름” 정도로 이해하면 된다.

중요한 것은 이름보다 **어떤 일이 어느 실행 흐름에서 돌아가고 있는가**다.

---

### 3. UI 스레드를 막으면 화면이 멈춘다

Android 같은 UI 앱에는 화면 이벤트와 그리기를 담당하는 중심 실행 흐름이 있다. 보통 **메인 스레드(main thread)** 또는 **UI 스레드(UI thread)**라고 부른다.

이 스레드에서 오래 걸리는 일을 붙잡고 있으면 화면이 입력에 반응하지 못한다.

나쁜 흐름:

```text
버튼 클릭
↓
UI 스레드에서 10초짜리 네트워크 작업 시작
↓
화면 입력 처리 못 함
↓
사용자는 앱이 멈췄다고 느낌
```

좋은 흐름:

```text
버튼 클릭
↓
긴 작업은 별도 비동기 작업으로 시작
↓
UI는 계속 반응
↓
결과가 오면 상태만 갱신
↓
화면 다시 그림
```

실제 Android에서는 프레임워크와 라이브러리가 세부 실행 방식을 관리해주지만, 원리는 같다.

> **오래 걸리는 작업을 UI를 담당하는 흐름에 그대로 묶어두면 안 된다.**

---

### 4. 비동기란 “나중에 끝날 수 있는 작업”을 다루는 방식이다

네트워크 요청을 보내면 결과가 즉시 오지 않는다. 파일 읽기나 DB 작업도 시간이 걸릴 수 있다.

이런 작업의 완료를 기다리는 동안 프로그램 전체를 멈추지 않도록 다루는 방식을 **비동기(asynchronous)**라고 한다.

동기적인 사고:

```text
1번 끝날 때까지 기다림
→ 2번 시작
→ 2번 끝날 때까지 기다림
→ 3번 시작
```

비동기 작업이 있는 흐름:

```text
네트워크 요청 시작
→ 기다리는 동안 다른 일 가능
→ 응답 도착
→ 응답 처리
```

비동기와 스레드는 같은 말이 아니다.

```text
비동기 = 완료를 기다리는 방식/흐름에 관한 개념
스레드 = 실행 흐름을 구성하는 단위
```

비동기 코드는 여러 스레드를 쓸 수도 있고, 하나의 스레드에서 이벤트 방식으로 처리될 수도 있다. 초급 단계에서 구현 세부를 외울 필요는 없지만 **둘을 같은 단어로 취급하지는 않는다.**

---

### 5. 가장 어려운 부분 — 완료 순서를 믿으면 안 된다

두 네트워크 요청을 거의 동시에 보냈다고 하자.

```text
요청 A 시작
요청 B 시작
```

A를 먼저 시작했다고 A가 반드시 먼저 끝나는 것은 아니다.

```text
A 시작 ───────────────→ A 완료
B 시작 ─────→ B 완료
```

검색창을 생각해보자.

사용자가 먼저 `AP`를 검색하고 곧바로 `AAPL`을 검색했다.

```text
요청 1: AP
요청 2: AAPL
```

요청 2가 먼저 완료되어 `AAPL` 결과를 화면에 보여줬는데, 뒤늦게 요청 1이 도착해서 화면을 `AP` 결과로 덮어쓰면 버그가 생긴다.

```text
사용자가 마지막으로 원하는 것: AAPL
화면 최종 결과: AP
```

이것은 단순 네트워크 오류가 아니다. **비동기 결과의 순서와 상태 갱신 규칙**이 잘못된 것이다.

해결 전략의 예:

- 최신 요청 ID를 기록한다.
- 이전 요청을 취소한다.
- 응답이 현재 검색어와 같은지 확인한다.
- 오래된 결과는 버린다.

구현법보다 중요한 것은 **“마지막에 도착한 응답 = 최신 의도”가 아닐 수 있다**는 사실이다.

---

### 6. 공유 상태와 경쟁 상태

여러 작업이 같은 값을 읽고 바꾸면 순서에 따라 결과가 달라질 수 있다.

이를 이해하기 위해 단순한 카운터를 생각해보자.

현재 값:

```text
count = 10
```

작업 A와 B가 동시에 1씩 증가시키려고 한다.

이론상 기대 결과는 12다.

하지만 둘 다 먼저 10을 읽은 뒤 각각 11을 저장하면 최종 결과는 11이 될 수 있다.

```text
A: 10 읽음
B: 10 읽음
A: 11 저장
B: 11 저장
최종: 11
```

여러 실행 흐름이 같은 상태를 두고 경쟁하면서 결과가 실행 순서에 따라 달라지는 문제를 **경쟁 상태(race condition)**라고 한다.

초보자가 기억할 핵심:

> **공유 상태를 여러 작업이 동시에 바꾸면 순서 문제가 생길 수 있다.**

모든 앱에서 직접 lock이나 mutex를 작성해야 한다는 뜻은 아니다. 프레임워크가 안전한 상태 갱신 방식을 제공하는 경우도 많다. 하지만 AI가 만든 병렬 코드가 있다면 “같은 값을 여러 곳에서 동시에 바꾸는가?”를 확인할 수 있어야 한다.

---

### 7. 비동기 오류는 성공 경로만 보면 놓친다

네트워크 코드가 다음처럼 보인다고 하자.

```text
요청 시작
→ 성공 응답
→ 화면 갱신
```

실제 앱에는 다른 경로도 있다.

```text
요청 시작
├─ 성공
├─ timeout
├─ 서버 오류
├─ 사용자 취소
├─ 앱 종료
└─ 새 요청이 이전 요청을 대체
```

비동기 코드는 **정상 완료만 생각하면 부족하다.**

특히 확인할 것:

- 로딩 상태가 실패 후에도 계속 남지 않는가?
- 실패 메시지가 이전 성공 데이터를 지워버리는가?
- 화면을 떠난 뒤 도착한 응답이 옛 화면 상태를 건드리는가?
- 재시도 때문에 같은 작업이 중복 실행되지 않는가?

---

### 8. 실제 사례 — 버튼을 두 번 눌렀더니 데이터가 두 번 저장됨

저장 버튼을 빠르게 두 번 눌렀다.

```text
클릭 1 → 저장 요청 A
클릭 2 → 저장 요청 B
```

서버나 앱이 중복을 막지 않으면 같은 데이터가 두 번 저장될 수 있다.

가능한 대책:

- 요청 중에는 버튼을 잠시 비활성화
- 서버에서 중복 요청 식별
- 동일 작업을 여러 번 해도 결과가 중복되지 않게 설계

마지막 성질을 **멱등성(idempotency)**이라고 부른다. 이 용어는 API/자동화 장에서 더 자세히 배운다. 여기서는 **비동기 작업이 중복될 수 있다**는 점만 연결한다.

---

### 9. 실제 사례 — 로딩 표시가 영원히 사라지지 않음

앱 상태:

```text
loading = true
```

정상 성공 경로에서는 마지막에:

```text
loading = false
```

로 바뀐다.

그런데 오류가 났을 때 `false`로 바꾸는 코드가 없다면 로딩 표시가 영원히 남을 수 있다.

```text
요청 시작 → loading=true
↓
오류 발생
↓
오류 경로에서 loading=false 누락
↓
화면은 계속 로딩 중
```

이 버그는 “네트워크가 느리다”가 아니라 **실패 경로의 상태 정리 문제**다.

---

### 10. 프로세스가 죽는 것과 ANR은 다르다

앱이 갑자기 종료되는 **크래시(crash)**와 화면이 오랫동안 반응하지 않는 **ANR(Application Not Responding)**은 같은 증상이 아니다.

```text
크래시 → 프로세스가 오류로 종료될 수 있음
ANR    → 프로세스는 살아 있지만 UI 응답이 막혀 있을 수 있음
```

둘 다 사용자에게는 “앱이 이상하다”로 보이지만 진단 방향이 다르다.

크래시에서는 예외/stack trace를 찾고, ANR에서는 메인 스레드가 무엇을 하고 있었는지 보는 것이 중요하다.

---

### 11. 진단 순서 — 멈춤과 순서 꼬임을 볼 때

| 질문 | 확인 이유 |
|---|---|
| 프로세스가 살아 있는가? | 종료/크래시인지 구분 |
| UI가 터치에 반응하는가? | UI 스레드 차단 후보 |
| 긴 작업이 어디서 실행되는가? | main thread 작업 여부 |
| 동시에 여러 요청이 있는가? | 완료 순서 문제 후보 |
| 같은 상태를 여러 작업이 바꾸는가? | race 후보 |
| 실패/취소 경로가 상태를 정리하는가? | loading 고착 등 확인 |
| 이전 요청 결과를 버리는 규칙이 있는가? | stale result 방지 |

## 실습 1 — 완료 순서 예측

```text
A 요청: 3초 걸림
B 요청: 1초 걸림
A를 먼저 시작하고 0.1초 뒤 B 시작
```

어느 요청이 먼저 끝날 가능성이 높은가?

정답: B. **시작 순서와 완료 순서는 다를 수 있다.**

---

## 실습 2 — 오래된 검색 결과 찾기

```text
12:00:00 검색어 = "AP"     → 요청 1
12:00:01 검색어 = "AAPL"   → 요청 2
12:00:02 요청 2 완료 → AAPL 표시
12:00:03 요청 1 완료 → AP 표시
```

버그는 무엇인가?

`요청 1`은 마지막에 도착했지만 현재 사용자의 검색어보다 오래된 요청이다. 화면을 갱신하면 안 된다.

---

## 실습 3 — 공유 상태 추적

두 작업이 같은 카운터를 수정한다.

```text
초기 count = 5
A가 5 읽음
B가 5 읽음
A가 6 저장
B가 6 저장
```

기대값과 실제값은?

```text
기대: 7
실제: 6
```

왜 이런 일이 가능한지 한 문장으로 설명한다.

---

## 실습 4 — 로딩 상태 디버깅

다음 흐름에서 빠진 것을 찾는다.

```text
요청 시작 → loading=true
성공 → data 저장 → loading=false
실패 → error 저장
```

실패 경로에서도 `loading=false`가 필요하다.

---

## 실습 5 — 앱 멈춤 분류

상황 A:

```text
앱을 누르자 즉시 종료되고 stack trace가 남음
```

상황 B:

```text
화면은 보이지만 8초 동안 터치에 전혀 반응하지 않음
```

A는 크래시, B는 UI 스레드 차단/ANR 가능성을 우선 본다.

## 장 끝 미니 프로젝트 — 비동기 상태표 만들기

네가 만든 앱 또는 자주 쓰는 앱에서 네트워크 기능 하나를 고른다.

예: 검색, 로그인, 일정 저장, 주가 조회.

다음 표를 작성한다.

| 항목 | 내용 |
|---|---|
| 작업 시작 조건 | |
| 로딩 중 상태 | |
| 성공 시 상태 | |
| 실패 시 상태 | |
| 사용자가 취소하면 | |
| 같은 작업을 두 번 시작하면 | |
| 더 최신 요청이 오면 | |
| 화면을 떠난 뒤 결과가 오면 | |

모르는 항목은 `모름`이라고 적는다. 이 표를 만들 수 있으면 비동기 버그를 “가끔 이상함”에서 구체적인 상태 문제로 바꿀 수 있다.

---

## 핵심 용어

| 용어 | 뜻 |
|---|---|
| 프로세스(process) | 실행 중인 프로그램의 작업 단위 |
| 스레드(thread) | 프로세스 안의 실행 흐름 단위 |
| 메인/UI 스레드 | 화면 이벤트와 UI 작업을 담당하는 중심 실행 흐름 |
| 비동기(asynchronous) | 오래 걸리는 작업 완료를 기다리는 동안 전체 흐름을 막지 않도록 다루는 방식 |
| 공유 상태 | 여러 작업이 함께 읽거나 바꾸는 상태 |
| 경쟁 상태(race condition) | 실행 순서에 따라 공유 상태 결과가 달라지는 문제 |
| 크래시(crash) | 오류 등으로 앱 프로세스가 종료되는 현상 |
| ANR | 앱이 일정 시간 사용자 입력에 응답하지 않는 상태 |

---

## 이 장을 끝내고 할 수 있어야 하는 것

1. 설치된 프로그램과 실행 중 프로세스를 구분한다.
2. 프로세스와 스레드를 같은 것으로 말하지 않는다.
3. UI 스레드에서 긴 작업을 하면 왜 화면이 멈출 수 있는지 설명한다.
4. 비동기와 스레드가 같은 개념이 아님을 설명한다.
5. 시작 순서와 완료 순서가 다를 수 있음을 이해한다.
6. 오래된 네트워크 응답이 최신 화면을 덮는 버그를 찾을 수 있다.
7. 공유 상태가 race condition을 만들 수 있음을 설명한다.
8. 크래시와 ANR의 진단 방향을 구분한다.
