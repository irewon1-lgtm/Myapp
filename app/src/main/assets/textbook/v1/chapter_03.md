## V1-C03. 프로세스와 동시성

**원본 Lesson 매핑:** V1-07, V1-08

### 1. 현실 문제에서 시작하기

앱이 “켜져 있다”는 말은 실제로는 코드가 프로세스 안에서 실행되고 있다는 뜻이다. 그런데 사용자가 보는 한 앱 안에서도 여러 작업이 동시에 진행된다. 화면을 그리는 동안 네트워크 응답을 기다리고, 데이터베이스를 읽고, 알림을 처리할 수 있다. 이때 모든 일을 한 줄로 막아버리면 화면이 멈추고, 공유 상태를 아무 규칙 없이 여러 작업이 바꾸면 간헐적 버그가 생긴다.

Android 공식 문서에서 기본 앱 구성요소는 같은 Linux 프로세스와 main thread에서 실행되며, 긴 작업으로 UI thread를 막으면 화면이 멈추고 ANR이 발생할 수 있다고 설명한다. 이 장의 목표는 스레드 문법을 외우는 것이 아니라 **프로세스·스레드·작업·상태의 관계를 보고 “멈춤”과 “경쟁”을 구분하는 능력**이다.

### 2. Mental Model

```text
설치된 앱 파일
   ↓ 실행
[Process PID 1234]
   ├─ Main/UI Thread: 터치, 화면 갱신
   ├─ Worker A: 네트워크/계산
   └─ Worker B: 파일/DB 작업
          ↓
       공유 상태
```

동시성(concurrency)은 여러 작업의 진행이 겹치는 구조이고, 병렬성(parallelism)은 실제로 같은 순간에 여러 연산이 수행되는 경우를 뜻한다. 초보 단계에서 둘의 엄밀한 구현보다 중요한 것은 **순서가 달라져도 결과가 안전한가**, **UI를 막고 있지 않은가**다.

### 3. 핵심 개념 해부

#### 프로그램과 프로세스

프로그램은 저장된 코드이고 프로세스는 실행 중인 프로그램 인스턴스다. 운영체제는 프로세스마다 PID 같은 식별자를 부여하고 메모리와 자원 상태를 관리한다. 프로세스가 종료되면 그 실행 상태는 사라지지만 설치된 앱 파일은 남는다. 그래서 “강제 종료”와 “삭제”는 전혀 다른 조치다.

부모/자식 프로세스, foreground/background라는 개념은 작업이 어디에서 시작됐고 사용자와 얼마나 직접 연결되어 있는지 이해하는 데 도움을 준다. Android에서는 사용자가 화면에서 보는 앱의 중요도에 따라 프로세스가 메모리 압박 시 종료될 수 있다는 사실도 중요하다.

#### 스레드와 UI thread

스레드는 프로세스 안에서 실행 흐름을 나누는 단위다. Android에서 main thread는 사용자 입력과 UI 그리기를 담당한다. 이 스레드에서 느린 네트워크 호출이나 긴 계산을 직접 수행하면 사용자의 터치와 화면 갱신이 대기하게 된다.

따라서 “비동기로 돌려라”를 주문처럼 외울 것이 아니라 어떤 작업이 오래 걸릴 수 있는지, 결과를 다시 UI에 반영할 때 어떤 스레드 규칙을 따라야 하는지 이해해야 한다. UI는 반응성이 핵심이고, 작업 분리는 그 반응성을 보존하기 위한 수단이다.

#### 종료코드와 관찰 가능한 상태

프로세스가 종료될 때 성공/실패 상태를 숫자로 남기는 도구들이 많다. 터미널 명령의 exit code, 앱 crash, system log는 서로 다른 수준의 종료 증거다. “창이 닫혔다”만 보지 말고 종료 시점과 이유를 기록해야 한다.

프로세스 목록, CPU/RAM 사용량, 시작/종료 시간은 문제를 재현하는 데 중요한 객관적 자료다. 특히 백그라운드 작업이 남아 있는지, 같은 서비스가 중복 실행되는지 확인할 때 유용하다.

#### race condition 감각

두 작업이 같은 값을 읽고 수정할 때 순서에 따라 결과가 달라지는 문제를 race condition이라고 부른다. 예를 들어 잔액 100에서 두 작업이 동시에 `+10`을 수행하면서 둘 다 먼저 100을 읽고 110을 저장하면 최종값이 120이 아니라 110이 될 수 있다.

실전에서 race는 항상 재현되지 않는다는 점이 어렵다. 그래서 “가끔 틀린다”를 사용자 실수로 치부하지 않고, 공유 상태·동시 업데이트·중복 요청·트랜잭션 여부를 확인해야 한다.

#### 동시성 문제와 성능 문제 구분

앱이 느리다고 해서 무조건 스레드를 늘리는 것은 위험하다. CPU가 이미 포화된 상황에서 작업을 더 쪼개면 오버헤드가 늘 수 있고, 공유 상태 문제가 커질 수 있다. 네트워크 대기처럼 I/O를 기다리는 작업과 실제 CPU 계산을 구분해야 한다.

반응성 문제는 “UI thread가 막혔는가?”, 데이터 오류는 “작업 순서에 따라 상태가 달라지는가?”, 자원 문제는 “CPU/RAM이 부족한가?”처럼 질문을 분리한다.

### 3A. 개념을 연결해서 생각하기 — 동시성의 핵심은 “순서가 통제되는가”

동시성은 어려운 단어가 많지만 Power User에게 가장 중요한 질문은 하나다. **같은 상태를 둘 이상의 작업이 만졌을 때 순서가 바뀌어도 결과가 맞는가?** 이 질문으로 race, 중복요청, double click, background sync 충돌을 같은 가족의 문제로 볼 수 있다.

예를 들어 일정 제목을 두 기기에서 동시에 바꾼다. A는 `병원 점심`, B는 `원장 미팅`으로 저장한다. 서버가 단순 last-write-wins이면 먼저 저장한 변경이 조용히 사라질 수 있다. 이 문제가 스레드 하나의 문제는 아니지만 **동시에 진행되는 작업의 상태 충돌**이라는 본질은 같다. DB transaction, version field, optimistic concurrency control 같은 도구가 뒤에서 등장한다.

UI thread 문제는 다른 종류다. 공유상태 충돌이 없어도 한 작업이 main thread를 오래 점유하면 사용자 입력이 처리되지 않는다. 네트워크 요청은 계산을 많이 하지 않더라도 응답을 기다리는 동안 thread를 막을 수 있다. 따라서 “CPU가 높지 않으니 괜찮다”가 아니다.

비동기 코드는 오류처리를 더 복잡하게 만들 수 있다. 작업이 시작된 뒤 화면이 닫혔거나 사용자가 취소했을 수 있다. 결과가 늦게 도착해 이미 새 화면의 상태를 덮어쓰는 stale response 문제도 생긴다. 그래서 시작/완료뿐 아니라 **소유자(lifecycle), 취소, 최신성, 중복**을 함께 본다.

Android에서는 앱 process가 항상 살아있다는 보장도 없다. background에 갔다가 process가 종료될 수 있으므로 중요한 작업 상태를 메모리 변수 하나에만 두면 복구에 실패한다. `saved state`, persistent DB, work scheduler 같은 플랫폼 도구를 목적에 맞게 쓰는 이유가 여기에 있다.

동시성에서 “lock을 걸면 끝”이라는 생각도 피한다. lock은 race를 막을 수 있지만 잘못 쓰면 deadlock이나 성능 병목을 만들 수 있다. 가능한 경우 immutable data, single-writer, atomic DB operation, idempotent API처럼 **공유 변경 자체를 단순화하는 설계**가 더 좋다.

### 4. Worked Examples

#### Worked Example A — UI freeze

사용자가 버튼을 누르면 8초 걸리는 작업을 main thread에서 직접 수행한다고 가정한다. 그 8초 동안 터치 이벤트와 화면 그리기가 처리되지 못한다. 사용자는 앱이 죽었다고 느낀다.

개선의 핵심은 계산/네트워크를 백그라운드 작업으로 옮기고, 진행 상태를 표시하며, 완료 결과만 안전하게 UI 상태에 반영하는 것이다. 단순히 “스레드를 하나 만든다”가 아니라 취소·오류·중복 클릭까지 고려해야 한다.

#### Worked Example B — 순서가 달라지는 카운터

두 작업이 `count`를 각각 1 증가시키는 상황을 표로 적는다.

```text
A: count 읽기 = 0
B: count 읽기 = 0
A: 1 저장
B: 1 저장
최종 = 1  (기대한 2가 아님)
```

이 표는 race가 왜 생기는지 가장 단순하게 보여준다. 해결은 공유 상태를 안전하게 업데이트하거나, DB transaction/atomic operation/직렬화된 처리처럼 **한 번의 변경을 하나의 단위로 보장**하는 것이다.

### 4A. 미니 사례집

**사례 1 — 두 번 눌린 저장 버튼**  
UI에서 버튼 비활성화는 사용자 경험에는 도움되지만 서버 중복생성을 완전히 막지 못한다. 네트워크 retry나 두 기기 요청도 있기 때문이다. 서버 idempotency/unique key까지 생각한다.

**사례 2 — 느린 요청이 최신 화면을 덮음**  
검색어 `A` 요청 후 바로 `AB`를 검색했다. `AB` 응답이 먼저 왔는데 늦게 도착한 `A` 응답이 화면을 덮었다. request generation/token으로 최신 요청만 반영한다.

**사례 3 — background sync와 수동수정 충돌**  
사용자가 수동으로 값을 고치는 순간 background refresh가 오래된 서버값을 저장했다. version/timestamp/merge policy가 필요하다.

**사례 4 — main thread에서 DB 전체조회**  
작업은 “로컬”이지만 데이터가 많아지면 UI를 막을 수 있다. 로컬 작업=항상 즉시 완료라는 가정을 버린다.

### 5. 그럴듯하지만 틀린 판단

1. 앱 아이콘이 하나이므로 실행 흐름도 하나라고 생각한다.
2. 백그라운드 스레드는 무조건 빠르고 안전하다고 생각한다.
3. 가끔만 발생하는 오류는 코드 문제가 아니라고 생각한다.
4. UI freeze와 process crash를 같은 현상으로 취급한다.

### 5A. 동시성 판정 질문

1. 둘 이상의 작업이 같은 상태를 읽거나 쓰는가?
2. 작업 완료 순서가 바뀔 수 있는가?
3. 같은 요청이 두 번 실행돼도 결과가 안전한가?
4. 화면/lifecycle이 사라진 뒤 결과가 도착할 수 있는가?
5. 실패 후 retry가 중복효과를 만들 수 있는가?
6. 사용자가 기다리는 UI thread를 막고 있는가?

두 개 이상 YES라면 단순 “스레드 하나 추가”보다 상태·idempotency·취소·transaction을 함께 설계한다.

### 5B. 동시성에서 반드시 생각할 세 가지: 소유권·순서·중복

**소유권:** 이 상태를 누가 바꿀 수 있는가? 여러 thread, 여러 device, server와 client가 모두 쓸 수 있다면 conflict 정책이 필요하다. 가능하면 하나의 source of truth를 정하고 나머지는 복제본으로 취급한다.

**순서:** 작업 A가 B보다 먼저 완료된다는 보장이 있는가? network 요청은 시작 순서와 응답 순서가 다를 수 있다. 따라서 “마지막에 도착한 응답을 무조건 화면에 쓴다”는 코드는 오래된 응답이 최신 상태를 덮어쓸 수 있다.

**중복:** 동일 작업이 두 번 실행돼도 안전한가? 모바일 네트워크는 끊겼다가 재시도될 수 있고 사용자는 버튼을 여러 번 누를 수 있으며 서버 worker도 retry할 수 있다. payment, 주문, 일정 생성처럼 부작용이 있는 API는 idempotency가 중요하다.

동시성 버그를 찾을 때 sleep 시간을 늘려 “고치는” 접근은 위험하다. 우연히 timing window를 숨길 뿐이다. shared state 접근을 명시적으로 모델링하고, 테스트에서는 작업 순서를 바꾸거나 동시 요청을 넣어 race를 드러내야 한다.

UI에서는 loading state도 동시성 상태다. 한 화면에서 요청 A와 B가 동시에 실행되는데 boolean `isLoading` 하나만 쓰면 A가 끝나는 순간 B가 아직 실행 중인데 spinner가 꺼질 수 있다. request count, 독립 상태, structured concurrency 등 더 정확한 모델이 필요할 수 있다.

복잡한 동시성 도구를 모두 배울 필요는 없다. 먼저 **공유 mutable state를 줄이고, 중복을 안전하게 만들고, 최신 작업만 반영하고, lifecycle에 맞춰 취소**하는 네 가지 원칙을 적용한다.

### 6. Guided Lab

휴대폰이나 PC에서 실행 중 프로세스 하나를 선택해 시작 시간, CPU 사용량, RAM 사용량, foreground/background 상태를 기록한다. 가능하면 앱을 종료했다 다시 실행해 PID가 바뀌는지도 확인한다. 관찰이 어려운 플랫폼에서는 제공된 프로세스 로그 샘플을 사용한다.

이어 두 작업이 한 카운터를 갱신하는 순서를 종이에 4가지로 배열하고 어떤 순서에서 손실 업데이트가 생기는지 표시한다.

### 7. Independent Lab

“네트워크 응답을 기다리는 동안 화면 로딩 애니메이션은 계속 움직여야 한다”는 요구사항을 만족하는 처리 흐름을 그림으로 설계하라. UI thread, worker, 결과 상태, 오류, 취소를 모두 표시한다.

### 8. Debug Challenge

**상황:** 저장 버튼을 빠르게 두 번 누르면 같은 주문이 가끔 두 번 생성된다. 로그에는 두 요청 모두 정상 200이 찍힌다.

단순히 버튼을 1초 비활성화하는 것만으로 끝내지 말고, 클라이언트 중복 클릭, 서버 idempotency, DB uniqueness/transaction 중 어느 층에서 중복을 막아야 하는지 증거를 수집하고 최소 안전설계를 제안한다.

### 9. AI Audit

AI가 “ANR을 해결하려면 모든 코드를 background thread로 옮겨라”라고 답했다면 반려한다. 어떤 작업이 main thread를 막는지 측정하고, UI 업데이트 규칙과 lifecycle/cancellation을 고려해야 한다. AI 답에서 `무엇이 느린지 측정했는가`, `공유 상태를 어떻게 보호하는가`, `오류/취소는 어떻게 처리하는가`, `회귀테스트가 있는가`를 체크한다.

### 9A. 진단 미니드릴 — 증상을 보면 첫 질문부터 고른다

**드릴 1. 앱이 화면 회전 직후 이전 요청 결과로 덮인다**  
첫 판단: 요청 소유자/lifecycle과 stale response를 의심한다. 요청 ID 또는 최신 generation을 기록한다.  
증거 없이 바로 수정하지 말고, 이 판단을 반박할 수 있는 확인 항목도 하나 적는다.

**드릴 2. 저장 버튼을 세 번 눌렀더니 레코드가 세 개 생긴다**  
첫 판단: UI debounce만 보지 말고 server idempotency와 DB unique constraint를 함께 확인한다.  
증거 없이 바로 수정하지 말고, 이 판단을 반박할 수 있는 확인 항목도 하나 적는다.

**드릴 3. CPU는 낮은데 UI가 멈춘다**  
첫 판단: I/O wait 또는 main-thread blocking을 확인한다. CPU 수치만으로 반응성을 판정하지 않는다.  
증거 없이 바로 수정하지 말고, 이 판단을 반박할 수 있는 확인 항목도 하나 적는다.

**드릴 4. 백그라운드 후 돌아오니 입력값이 사라졌다**  
첫 판단: process death와 state persistence를 구분한다. 메모리 변수만 사용했는지 확인한다.  
증거 없이 바로 수정하지 말고, 이 판단을 반박할 수 있는 확인 항목도 하나 적는다.

**드릴 5. 두 기기에서 같은 일정을 수정했다**  
첫 판단: 스레드가 달라도 concurrency 문제다. version/conflict policy가 필요하다.  
증거 없이 바로 수정하지 말고, 이 판단을 반박할 수 있는 확인 항목도 하나 적는다.

**드릴 6. retry 후 결제가 두 번 됐다**  
첫 판단: 부작용 API의 idempotency key와 server-side 중복방지 증거를 확인한다.  
증거 없이 바로 수정하지 말고, 이 판단을 반박할 수 있는 확인 항목도 하나 적는다.

이 미니드릴의 목표는 정답 암기가 아니다. **증상 → 계층 → 확인할 증거**를 30초 안에 연결하는 습관을 만드는 것이다.
