# TRACK 09 · Android 앱이 실제로 사는 곳

이번 TRACK은 Android 앱을 `APK 파일 하나`로 보지 않게 만드는 과정이다.

앱이 설치되고, 실행되고, 화면을 잃고, 백그라운드로 가고, 운영체제에 의해 프로세스가 종료되고, 알림을 받고, 데이터를 동기화하는 전체 생애를 배운다.

---

## BLOCK 01 · Android는 무엇인가

### LESSON 01 · 휴대폰 운영체제

**Android**는 스마트폰, 태블릿 등에서 사용하는 운영체제다.

운영체제는 앱이 화면, 저장공간, 카메라, 네트워크 같은 장치를 안전하게 사용할 수 있도록 관리한다.

### LESSON 02 · 앱은 Android 위에서 실행된다

앱이 카메라를 직접 마음대로 제어하는 것이 아니라 Android가 제공하는 기능을 통해 카메라를 요청한다.

따라서 앱 코드가 맞아도 운영체제 권한이나 백그라운드 정책 때문에 기능이 제한될 수 있다.

---

## BLOCK 02 · APK와 설치된 앱

### LESSON 01 · APK

**APK(Android Package)**는 Android 앱을 설치할 수 있도록 코드와 자원을 묶은 패키지 파일이다.

예:

```text
MyApp.apk
```

### LESSON 02 · APK 파일과 설치 상태는 다르다

APK를 다운로드했다고 앱이 설치된 것은 아니다.

```text
APK 다운로드
↓
설치 승인
↓
Android가 앱 설치
↓
앱 실행 가능
```

APK 파일을 새로 다운로드했는데 설치하지 않았다면 기존 설치 앱은 그대로다.

---

## BLOCK 03 · 패키지 이름

### LESSON 01 · 앱의 고유한 이름

Android 앱은 보통:

```text
com.example.myapp
```

같은 **패키지 이름(package name)** 또는 애플리케이션 ID로 구분된다.

사용자가 보는 앱 이름과 다르다.

```text
화면 이름: 내 주식앱
패키지 식별자: com.example.stockapp
```

### LESSON 02 · 이름이 같아도 다른 앱일 수 있다

사용자에게 보이는 이름이 같아도 패키지 식별자가 다르면 Android에서는 다른 앱으로 설치될 수 있다.

---

## BLOCK 04 · 앱 샌드박스

### LESSON 01 · 앱마다 자기 공간을 나누기

Android는 앱마다 파일과 데이터를 따로 보호한다.

이렇게 앱을 서로 격리하는 구조를 **샌드박스(sandbox)**라고 부른다.

한 줄 뜻:

> 앱 샌드박스 = 한 앱이 다른 앱의 내부 데이터에 마음대로 접근하지 못하도록 분리하는 보호 구조

### LESSON 02 · 왜 필요한가

메모 앱이 은행 앱의 내부 파일을 마음대로 읽을 수 있다면 큰 보안 문제가 된다.

앱 샌드박스는 이런 접근을 기본적으로 제한한다.

---

## BLOCK 05 · Manifest

### LESSON 01 · 앱의 기본 정보를 Android에 알려주는 파일

Android 앱에는 **AndroidManifest.xml**이라는 중요한 설정 파일이 있다.

여기에는 앱의 구성 요소와 권한 같은 정보를 선언한다.

한 줄 뜻:

> Manifest = Android에게 이 앱이 어떤 구성과 권한을 사용하는지 알려주는 설정 파일

### LESSON 02 · 권한도 Manifest에 선언한다

예를 들어 인터넷 사용 권한을 선언할 수 있다.

하지만 어떤 권한은 Manifest에 적는 것만으로 충분하지 않고 사용자에게 실행 중 허가를 받아야 한다.

---

## BLOCK 06 · 권한이란 무엇인가

### LESSON 01 · 위험한 기능을 아무 앱이나 쓰지 못하게

카메라, 마이크, 위치, 연락처는 개인 정보와 연결될 수 있다.

Android는 앱이 이런 기능을 사용할 때 **권한(permission)** 규칙을 적용한다.

### LESSON 02 · 선언과 사용자 허용

앱 개발자가 Manifest에 권한을 적었다고 사용자가 자동으로 허용한 것은 아니다.

일부 권한은 실행 중 사용자에게:

```text
이 앱이 카메라를 사용하도록 허용하시겠습니까?
```

와 같은 승인을 받아야 한다.

---

## BLOCK 07 · 권한 상태가 바뀔 수 있다

### LESSON 01 · 사용자가 나중에 끌 수 있다

사용자는 설정에서 권한을 취소할 수 있다.

따라서 앱은 `예전에 허용했으니 영원히 허용`이라고 가정하면 안 된다.

### LESSON 02 · 권한이 없을 때의 화면

좋은 앱은 권한이 없으면 그냥 죽는 것이 아니라:

```text
왜 필요한지 설명
권한 요청
거부 시 대체 흐름
```

을 제공한다.

---

## BLOCK 08 · Activity란 무엇인가

### LESSON 01 · 사용자 화면 하나의 주요 단위

Android의 전통적인 앱 구조에서 **Activity**는 사용자가 상호작용하는 화면을 제공하는 핵심 구성 요소다.

한 줄 뜻:

> Activity = Android 앱에서 사용자 화면과 상호작용을 담당하는 주요 구성 요소

### LESSON 02 · Activity = 화면 그림 그 자체는 아니다

Activity 안에 여러 View나 Compose UI가 표시될 수 있다.

따라서 `Activity`와 `버튼 하나`, `화면 디자인`을 같은 말로 생각하지 않는다.

---

## BLOCK 09 · 생명주기라는 말

### LESSON 01 · 화면도 태어나고 멈추고 사라진다

Activity는 항상 같은 상태로 존재하지 않는다.

생성되고, 사용자에게 보이고, 다른 화면이 올라오며 멈추고, 파괴될 수 있다.

이런 상태 변화의 흐름을 **생명주기(lifecycle)**라고 부른다.

한 줄 뜻:

> lifecycle = Android 구성 요소가 생성되고 활성화되고 멈추고 파괴되는 상태 변화 과정

---

## BLOCK 10 · onCreate

### LESSON 01 · Activity가 만들어질 때

Activity가 새로 생성될 때 Android는 `onCreate`라는 생명주기 메서드를 호출한다.

여기서 초기 화면 설정 등을 한다.

### LESSON 02 · onCreate는 앱 평생 한 번만인가

아니다.

화면 회전, 프로세스 재생성 등 상황에 따라 Activity가 다시 만들어져 `onCreate`가 다시 호출될 수 있다.

그래서 중요한 상태를 단순히 메모리 변수 하나에만 두면 잃을 수 있다.

---

## BLOCK 11 · foreground와 background

### LESSON 01 · foreground

사용자가 지금 보고 상호작용하는 앱이 **foreground(포그라운드)**에 있다고 말한다.

쉽게:

> foreground = 사용자가 지금 앞에서 보고 있는 상태

### LESSON 02 · background

홈 버튼을 누르거나 다른 앱으로 이동하면 이전 앱은 화면 앞에서 사라진다.

이처럼 사용자 앞에 보이지 않는 상태를 **background(백그라운드)**라고 부른다.

백그라운드 앱은 배터리와 보안을 위해 여러 제한을 받을 수 있다.

---

## BLOCK 12 · 앱이 백그라운드라고 계속 살아 있는 것은 아니다

### LESSON 01 · 프로세스 종료

Android는 메모리가 필요하거나 정책에 따라 백그라운드 앱의 프로세스를 종료할 수 있다.

사용자가 앱 화면을 떠났다고 프로세스가 영원히 메모리에 남는 것이 아니다.

### LESSON 02 · process death

운영체제가 앱 프로세스를 종료하는 일을 흔히 **process death**라고 부른다.

앱을 다시 열면 이전 메모리 변수들이 사라졌을 수 있다.

따라서 중요한 사용자 데이터는 영구 저장소에 저장해야 한다.

---

## BLOCK 13 · 상태 저장

### LESSON 01 · 화면 상태와 영구 데이터 구분

예:

```text
현재 선택한 탭 = 화면 상태
사용자가 작성한 메모 = 영구 보존 필요 데이터
```

모든 값을 같은 방법으로 저장할 필요는 없다.

### LESSON 02 · SavedState

Activity가 다시 만들어질 때 복원할 작은 화면 상태를 저장하기 위해 **saved instance state** 같은 Android 기능을 사용할 수 있다.

더 큰 데이터는 데이터베이스나 파일에 저장하는 것이 적절할 수 있다.

---

## BLOCK 14 · Service란 무엇인가

### LESSON 01 · 화면 없이도 수행할 작업

Android의 **Service**는 사용자 화면을 직접 제공하지 않으면서 백그라운드에서 작업할 수 있는 구성 요소다.

하지만 `Service = 제한 없이 영원히 백그라운드 실행`은 아니다.

Android 버전이 올라가며 백그라운드 Service 실행에는 강한 제한이 생겼다.

---

## BLOCK 15 · Foreground Service

### LESSON 01 · 사용자가 알아야 하는 장시간 작업

음악 재생, 운동 추적처럼 사용자가 알고 있어야 하는 지속 작업은 **Foreground Service**로 실행할 수 있다.

이 서비스는 보통 지속적인 알림을 표시해야 한다.

### LESSON 02 · 왜 알림을 보여 주나

앱이 뒤에서 오래 실행 중이라는 사실을 사용자가 알 수 있게 하기 위해서다.

몰래 계속 실행되는 것을 줄이는 보안·배터리 정책과 연결된다.

---

## BLOCK 16 · WorkManager

### LESSON 01 · 지금 당장 정확히 실행될 필요는 없는 백그라운드 작업

데이터 동기화, 로그 업로드 같은 작업을 안정적으로 예약할 때 Android Jetpack의 **WorkManager**를 사용할 수 있다.

한 줄 뜻:

> WorkManager = 조건을 만족할 때 반드시 실행되어야 하는 지연 가능한 백그라운드 작업을 예약하는 Android 도구

### LESSON 02 · 정확히 10:00:00에 실행하는 도구는 아니다

WorkManager는 배터리 최적화를 고려해 적절한 시점에 작업을 실행한다.

정확한 시각 알람과 목적이 다르다.

---

## BLOCK 17 · AlarmManager

### LESSON 01 · 특정 시각에 깨우기

**AlarmManager**는 미래의 특정 시각에 앱 작업을 깨우는 기능을 제공한다.

Android 버전과 권한 정책에 따라 정확한 알람에는 제한이 있다.

### LESSON 02 · exact alarm

정확한 시간 실행이 꼭 필요한 일부 앱은 **exact alarm** 권한과 API를 사용할 수 있다.

하지만 배터리에 영향을 주기 때문에 모든 앱이 마음대로 사용하도록 허용되지는 않는다.

---

## BLOCK 18 · Doze

### LESSON 01 · 휴대폰을 오래 쓰지 않을 때 배터리 절약

Android는 기기를 오래 사용하지 않을 때 백그라운드 네트워크와 작업을 제한하는 **Doze** 모드를 사용할 수 있다.

한 줄 뜻:

> Doze = 사용하지 않는 기기의 배터리를 아끼기 위해 백그라운드 작업을 제한하는 절전 상태

### LESSON 02 · 예약 작업이 늦어질 수 있다

`15분마다 실행`하도록 요청한 작업이 실제로 정확히 15분마다 실행되지 않을 수 있다.

운영체제가 배터리를 위해 실행 시점을 조정하기 때문이다.

---

## BLOCK 19 · 배터리 최적화

### LESSON 01 · 제조사 정책도 영향을 줄 수 있다

Android 기본 정책 외에 스마트폰 제조사가 추가 배터리 관리 기능을 넣을 수 있다.

삼성 Galaxy에서도 `절전`, `백그라운드 사용 제한` 같은 설정이 앱 동작에 영향을 줄 수 있다.

### LESSON 02 · 앱 코드만 보면 안 되는 이유

알림이 안 온다고 앱 코드 버그만 의심하면 원인을 놓칠 수 있다.

```text
앱 설정
Android 알림 권한
배터리 최적화
백그라운드 제한
서버 전송 여부
네트워크 상태
```

를 나눠 확인한다.

---

## BLOCK 20 · 알림이란 무엇인가

### LESSON 01 · 앱 밖에서도 사용자에게 정보를 보여 주기

**알림(notification)**은 앱이 현재 화면 앞에 없어도 Android 시스템 영역에 정보를 표시하는 기능이다.

예:

```text
새 메시지
일정 알림
다운로드 완료
```

### LESSON 02 · 앱 내부 팝업과 시스템 알림은 다르다

앱 화면 안에 띄운 작은 팝업은 앱이 꺼져 있으면 보이지 않는다.

시스템 알림은 Android 알림 시스템에 게시된다.

---

## BLOCK 21 · Notification Channel

### LESSON 01 · 알림 종류별 설정

Android 8 이상에서는 알림을 **채널(notification channel)**에 넣어 관리한다.

예:

```text
긴급 알림
일반 소식
마케팅
```

사용자는 채널마다 소리, 진동, 표시 여부를 설정할 수 있다.

### LESSON 02 · 코드에서 켰는데 알림이 안 오는 이유

사용자가 해당 채널을 껐으면 앱이 알림을 게시해도 표시되지 않을 수 있다.

따라서 앱 설정과 Android 채널 설정을 모두 확인한다.

---

## BLOCK 22 · 알림 권한

### LESSON 01 · Android 13 이후 알림 권한

최근 Android에서는 앱이 알림을 보내기 위해 사용자에게 알림 권한을 요청해야 할 수 있다.

사용자가 거부하면 알림이 표시되지 않는다.

### LESSON 02 · 권한 상태를 확인한다

`알림 코드 실행됨`과 `사용자 화면에 알림 표시됨` 사이에 운영체제 권한이 있다.

이 경계를 기억한다.

---

## BLOCK 23 · Push notification

### LESSON 01 · 서버에서 앱으로 알림 보내기

사용자의 폰에서 예약한 로컬 알림 말고, 서버에서 `새 메시지가 왔다`는 신호를 보내 알림을 띄울 수 있다.

이런 방식을 **푸시 알림(push notification)**이라고 부른다.

### LESSON 02 · FCM

Android 앱에서 많이 사용하는 푸시 전송 서비스가 **Firebase Cloud Messaging(FCM)**이다.

큰 흐름:

```text
앱이 FCM 토큰 받음
↓
서버가 그 토큰을 저장
↓
서버가 FCM에 메시지 전송
↓
FCM이 기기로 전달
↓
앱/Android가 알림 처리
```

각 단계가 실패할 수 있다.

---

## BLOCK 24 · FCM token

### LESSON 01 · 기기 앱 인스턴스를 찾아가는 식별값

FCM은 설치된 앱 인스턴스에 **등록 토큰(registration token)**을 제공한다.

서버는 이 토큰을 대상으로 메시지를 보낼 수 있다.

### LESSON 02 · 토큰은 바뀔 수 있다

앱 재설치, 데이터 삭제 등 상황에서 FCM 토큰이 바뀔 수 있다.

서버가 오래된 토큰만 가지고 있으면 알림이 실패할 수 있다.

따라서 토큰 갱신을 서버와 동기화해야 한다.

---

## BLOCK 25 · 로컬 데이터와 서버 데이터

### LESSON 01 · 폰 안의 데이터

앱은 데이터베이스나 파일에 데이터를 저장할 수 있다.

이 데이터는 인터넷이 없어도 읽을 수 있다.

### LESSON 02 · 서버 데이터

여러 기기에서 같은 데이터를 공유하려면 서버에 저장하고 기기끼리 동기화해야 할 수 있다.

```text
폰 A 로컬 데이터
↕
서버
↕
폰 B 로컬 데이터
```

---

## BLOCK 26 · 동기화

### LESSON 01 · 서로 다른 복사본을 맞추기

여러 곳에 있는 데이터의 변경 내용을 서로 맞추는 과정을 **동기화(sync)**라고 부른다.

한 줄 뜻:

> 동기화 = 여러 위치의 데이터가 같은 최신 상태를 유지하도록 변경 내용을 주고받는 과정

### LESSON 02 · 동시에 수정하면

폰 A와 폰 B가 인터넷이 끊긴 동안 같은 일정을 서로 다르게 수정했다고 하자.

다시 연결되면 어느 값을 최종값으로 쓸지 결정해야 한다.

이것을 **충돌(conflict)** 문제라고 부른다.

---

## BLOCK 27 · 동기화 충돌 해결

### LESSON 01 · last-write-wins

가장 마지막 수정 시간을 가진 값을 선택하는 방법을 **last-write-wins**라고 부른다.

간단하지만 항상 옳지는 않다.

사용자 A의 중요한 수정이 단순히 시계가 늦어서 덮어써질 수 있다.

### LESSON 02 · merge

서로 다른 필드 변경을 합칠 수 있다면 **merge(병합)**할 수 있다.

예:

```text
폰 A: 제목 수정
폰 B: 메모 수정
```

서로 다른 항목이면 둘 다 보존할 수 있다.

---

## BLOCK 28 · 오프라인 우선 설계

### LESSON 01 · 인터넷이 없어도 앱을 사용할 수 있게

사용자가 지하철에서 인터넷이 끊겨도 메모를 작성할 수 있게 만들 수 있다.

로컬 데이터에 먼저 저장하고 연결이 돌아오면 서버와 동기화하는 방식을 **offline-first**라고 부른다.

### LESSON 02 · 큐

아직 서버에 보내지 못한 작업을 순서대로 저장해 둘 수 있다.

이 대기 목록을 **queue(큐)**라고 부른다.

예:

```text
일정 추가
일정 수정
사진 업로드
```

연결이 돌아오면 차례로 전송한다.

---

## BLOCK 29 · 재시도

### LESSON 01 · 한 번 실패했다고 영원히 포기하지 않기

네트워크는 잠깐 끊길 수 있다.

실패한 작업을 다시 시도하는 것을 **retry(재시도)**라고 부른다.

### LESSON 02 · 무한 재시도는 위험하다

서버가 완전히 장애인데 0.1초마다 계속 요청하면 서버와 배터리에 부담을 준다.

재시도 간격을 점점 늘리는 **exponential backoff** 같은 전략을 사용할 수 있다.

초보 뜻:

> 실패가 계속되면 재시도 사이의 기다리는 시간을 점점 늘린다.

---

## BLOCK 30 · 백업과 복원

### LESSON 01 · 앱 데이터 백업

Android는 앱 데이터의 일부를 클라우드에 백업하고 새 기기에서 복원하는 기능을 제공할 수 있다.

하지만 모든 데이터가 자동 백업 대상은 아니다.

### LESSON 02 · 민감한 데이터

인증 토큰, 암호화 키 같은 값은 백업 정책을 신중히 정해야 한다.

새 기기에 그대로 복원하면 보안 문제가 될 수 있다.

---

## BLOCK 31 · WebView란 무엇인가

### LESSON 01 · 앱 안에서 웹페이지 보여 주기

**WebView**는 Android 앱 안에 웹 콘텐츠를 표시할 수 있는 구성 요소다.

웹으로 만든 화면을 앱 껍데기 안에서 보여 주는 앱도 있다.

### LESSON 02 · 네이티브 앱과 WebView 앱

**네이티브(native)** 화면은 Android UI 기술로 직접 만든다.

WebView 앱은 많은 UI와 로직을 웹페이지에서 불러올 수 있다.

```text
네이티브 앱 업데이트 → APK를 다시 설치해야 할 수 있음
WebView가 보는 웹페이지 업데이트 → 서버의 웹페이지만 바꾸면 즉시 반영 가능
```

그래서 어떤 앱은 APK를 매번 설치하지 않아도 화면이 바뀌는 것처럼 보일 수 있다.

---

## BLOCK 32 · 자동 업데이트 구조

### LESSON 01 · Play Store 없이도 APK 업데이트 안내는 가능하다

앱이 서버에서 `최신 버전 정보`를 확인하고 새 APK 다운로드 링크를 보여 줄 수 있다.

하지만 Android 보안 정책 때문에 새 APK를 사용자가 설치 승인해야 하는 경우가 일반적이다.

### LESSON 02 · 스토어 업데이트

Google Play 같은 앱 스토어를 이용하면 스토어가 업데이트 배포와 설치 흐름을 관리한다.

어떤 방식이 맞는지는 배포 대상과 운영 환경에 따라 다르다.

다음 경계를 차례대로 확인한다.

### LESSON 02 · 앱이 데이터를 못 맞춘다

```text
충돌 해결?
```

한 덩어리로 보지 않는다.

## BLOCK 34 · TRACK 09 핵심 용어 사전

| 용어 | 아주 쉬운 뜻 |
|---|---|
| APK | Android 앱 설치용 패키지 파일 |
| package name | Android가 앱을 구분하는 고유 식별 이름 |
| sandbox | 앱마다 내부 데이터를 분리하는 보호 구조 |
| Manifest | 앱 구성과 권한 등을 Android에 알리는 설정 파일 |
| permission | 앱이 위험한 기능을 사용할 수 있는지 정한 권한 |
| Activity | 사용자 화면과 상호작용을 담당하는 주요 Android 구성 요소 |
| lifecycle | 구성 요소가 생성·활성·중지·파괴되는 상태 변화 과정 |
| foreground | 사용자가 지금 보고 있는 상태 |
| background | 사용자 화면 앞에 보이지 않는 상태 |
| process death | Android가 앱 프로세스를 종료하는 것 |
| Service | 화면 없이 작업하는 Android 구성 요소 |
| Foreground Service | 지속 알림과 함께 실행되는 사용자 인지 장시간 서비스 |
| WorkManager | 지연 가능하지만 실행 보장이 필요한 백그라운드 작업 예약 도구 |
| AlarmManager | 미래 시각에 앱 작업을 깨우는 Android 기능 |
| Doze | 배터리를 위해 백그라운드 작업을 제한하는 절전 상태 |
| notification | Android 시스템이 사용자에게 표시하는 알림 |
| notification channel | 알림 종류별 사용자 설정 단위 |
| push notification | 서버에서 기기로 전송되는 알림 방식 |
| FCM | Google의 푸시 메시지 전송 서비스 |
| FCM token | 설치된 앱 인스턴스를 대상으로 메시지를 보낼 때 쓰는 식별값 |
| sync | 여러 위치의 데이터를 최신 상태로 맞추는 과정 |
| conflict | 여러 곳에서 같은 데이터를 다르게 수정해 생기는 충돌 |
| offline-first | 인터넷 없이도 로컬에서 먼저 동작하고 나중에 동기화하는 설계 |
| retry | 실패한 작업을 다시 시도하는 것 |
| WebView | 앱 안에서 웹 콘텐츠를 표시하는 Android 구성 요소 |

## BLOCK 35 · TRACK 09 종합 훈련

### LESSON 01 · 알림 장애 분석

상황:

```text
엄마 폰은 알림이 옴
배우자 폰은 안 옴
```

바로 서버 전체 장애라고 결론 내리지 않는다.

비교할 것:

```text
두 기기의 FCM token
알림 권한
notification channel
앱 버전
배터리 설정
로그인 사용자 연결
서버 대상 토큰
```

### LESSON 02 · 업데이트 방식 설명

왜 WebView 기반 앱은 서버 화면만 바꾸면 UI가 즉시 바뀔 수 있는데 네이티브 APK 코드를 바꾸면 다시 설치가 필요할 수 있는지 자기 말로 설명한다.

### LESSON 03 · process death 실험

앱에 임시 숫자를 메모리 변수에만 저장한다.

Android가 앱 프로세스를 종료한 뒤 다시 열었을 때 그 숫자가 사라지는지 확인한다.

그 다음 영구 저장소에 저장한 값과 비교한다.

## BLOCK 36 · TRACK 09 완료 기준

다음을 설명할 수 있어야 한다.

- APK 파일과 설치된 앱의 차이
- package name이 왜 필요한지
- 앱 sandbox가 왜 중요한지
- Manifest와 런타임 권한의 차이
- Activity lifecycle이 무엇인지
- 앱이 background로 갔다고 프로세스가 영원히 살아 있는 것이 아닌 이유
- Foreground Service와 WorkManager의 목적 차이
- Doze와 배터리 정책이 예약 작업에 영향을 주는 이유
- notification channel과 알림 권한을 구분하는 방법
- FCM push가 서버에서 기기까지 가는 단계
- FCM token이 바뀔 수 있다는 사실
- sync와 conflict가 무엇인지
- retry를 무한히 빠르게 하면 왜 문제인지
- WebView와 네이티브 앱 업데이트 방식의 차이

### TRACK 끝 미니 프로젝트 · 알림·동기화 진단 지도

가상의 가족 일정 앱을 그린다.

```text
폰 A
폰 B
서버 DB
FCM
Android 알림 시스템
```

일정 추가부터 다른 폰 알림 표시까지 화살표를 그린다.

각 화살표에:

```text
성공 증거
실패 가능성
확인 방법
```

을 적는다.

이 지도를 만들 수 있으면 `알림이 안 와요`를 하나의 문제로 보지 않고 단계별로 진단할 수 있다.
