## V1-C09. Android 권한·동기화·백업

**원본 Lesson 매핑:** V1-24, V1-25

### 1. 현실 문제에서 시작하기

앱이 사진·위치·마이크에 접근하지 못하면 사용자는 “권한 켜면 되지”라고 생각하기 쉽다. 그러나 좋은 앱은 필요한 순간에 최소 권한만 요구해야 하고, 사용자가 거부해도 가능한 기능은 계속 제공해야 한다. Android 공식 문서도 민감 데이터와 제한된 동작을 permission으로 보호하고, 필요한 권한 수를 최소화하라고 권장한다.

또 “동기화되어 있으니 백업됐다”는 착각은 위험하다. 동기화는 변경을 여러 장치에 반영하는 것이고, 실수로 삭제한 내용도 그대로 퍼뜨릴 수 있다. 백업은 특정 시점의 복구 가능성을 보존하는 목적이 더 크다.

### 2. Mental Model

```text
앱 데이터
├─ app-specific storage  → 앱 전용, 삭제 시 함께 제거될 수 있음
├─ shared/user-selected  → 사용자와 다른 앱이 접근하는 목적
├─ DB / preferences
└─ cloud sync
       ↕
    remote copy

Backup:
현재 상태와 독립된 복구점/버전
```

### 3. 핵심 개념 해부

#### Android app sandbox

Android는 앱마다 데이터와 프로세스를 격리하는 sandbox를 제공한다. 앱이 다른 앱의 내부 데이터를 마음대로 읽지 못하는 것이 기본이다. 기능이 필요하면 platform API, permission, 사용자 선택 같은 명시적 경로를 사용한다.

이 격리는 불편함이 아니라 보안 기본선이다. 파일 접근 오류를 해결한다고 sandbox 전체를 우회하려 하면 설계가 잘못된 것이다.

#### install-time·runtime·special permission

Android permission은 성격에 따라 설치 시 자동 부여되는 권한, 사용 중 사용자 승인이 필요한 runtime permission, 강력한 special access 등으로 나뉜다. 카메라·마이크·위치 같은 민감 기능은 사용자 맥락과 함께 요청해야 한다.

권한을 이미 받았다고 영원히 유지된다고 가정하지 않는다. 사용자가 설정에서 취소할 수 있고 OS 정책이 바뀔 수 있다. 매 접근 전 필요한 상태를 안전하게 처리한다.

#### 최소권한과 사용자 설명

앱이 사진 한 장을 사용자가 고르게 하는 기능이라면 전체 저장소 접근보다 시스템 선택기를 쓰는 방법이 더 적절할 수 있다. Android Storage Access Framework는 사용자가 직접 문서를 선택하는 방식으로 권한 범위를 줄일 수 있다.

좋은 권한 UX는 ‘왜 필요한지’, ‘거부하면 어떤 기능만 제한되는지’를 명확히 한다. 앱 전체를 막는 과잉권한 설계를 피한다.

#### 동기화 vs 백업

동기화(sync)는 여러 위치의 현재 상태를 맞추는 것이 핵심이다. 양방향 sync는 한 장치의 삭제나 잘못된 수정도 다른 장치에 반영할 수 있다. 백업은 현재 상태와 분리된 복구용 사본이나 version history를 유지한다.

따라서 cloud 폴더가 실시간 동기화된다고 해서 랜섬웨어·실수 삭제에 자동 안전한 것은 아니다. 복구 시점, 보존기간, 버전기록, 별도 사본을 확인한다.

#### 3-2-1과 실제 복구시험

중요 데이터에는 흔히 여러 사본, 서로 다른 매체/위치, 오프사이트 사본을 두는 3-2-1 원칙을 참고할 수 있다. 그러나 숫자 자체를 종교처럼 따르기보다 데이터 가치와 복구시간에 맞춰 설계한다.

가장 중요한 것은 **백업이 존재하는지보다 복구가 실제로 되는지 테스트하는 것**이다. 암호화키나 계정이 없어서 복구할 수 없는 백업은 실전에서 무용하다.

### 3A. 개념을 연결해서 생각하기 — 모바일에서는 “사용자 통제”가 설계의 일부다

Android permission은 개발자가 기능을 얻기 위해 통과해야 하는 장애물이 아니라 사용자가 자신의 데이터와 센서를 통제하는 인터페이스다. 그래서 권한 요청은 기능의 맥락에서 늦게(late) 요청하고, 거부됐을 때 앱 전체가 무너지지 않도록 graceful degradation을 제공하는 것이 좋다.

저장소도 permission 하나로 끝나지 않는다. 앱 전용 데이터, 사용자에게 남아야 하는 media/document, structured DB, preferences는 수명과 공유범위가 다르다. Android 공식 storage guidance는 app-specific storage, shared storage, preferences, database 등 선택지를 구분한다. 사용자에게 소유권이 있는 사진을 app-specific directory에만 저장하면 앱 제거 시 함께 사라져 기대를 깨뜨릴 수 있다.

동기화는 분산상태 문제다. 휴대폰 A, 휴대폰 B, 서버가 각각 같은 일정의 복사본을 갖고 있을 때 offline edit와 reconnect가 일어나면 conflict가 발생한다. “마지막 저장이 이긴다”는 정책은 단순하지만 중요한 변경을 조용히 잃을 수 있다. version, updatedAt, merge rule, 사용자 선택 등 domain에 맞는 정책이 필요하다.

백업은 failure domain을 분리해야 한다. 폰과 같은 계정의 cloud sync만 믿으면 계정 탈취나 실수삭제가 모두 영향을 줄 수 있다. 반대로 보안이 필요한 데이터는 무분별한 외부 복사본이 위험하다. 데이터 가치·민감도·복구목표를 균형 있게 본다.

RPO와 RTO 개념도 실용적으로 알아두면 좋다. RPO는 “최대 어느 시점까지 데이터 손실을 감수할 수 있는가”, RTO는 “얼마나 빨리 복구해야 하는가”라는 질문이다. 개인 사진과 일일 생성 가능한 cache, 영업 CRM 기록은 서로 다른 답을 가진다. 백업 빈도와 비용은 이 요구에서 나온다.

복구시험은 반드시 실제로 수행해야 한다. 백업 파일의 존재만 보고 PASS하지 않는다. 별도 테스트 계정/기기나 안전한 환경에서 restore하고 데이터 개수·핵심 필드·첨부파일이 맞는지 확인한다.

### 4. Worked Examples

#### Worked Example A — 사진 첨부 권한

사용자가 CRM에 사진 한 장을 첨부한다고 하자. 앱이 전체 사진 라이브러리를 상시 읽을 필요가 있는지 먼저 묻는다. 시스템 사진 선택기나 SAF처럼 사용자가 선택한 항목만 접근하는 방법이 있다면 권한과 개인정보 범위를 줄일 수 있다.

#### Worked Example B — sync 사고

문서 폴더를 두 PC와 cloud에 동기화한다. 한 PC에서 실수로 폴더를 삭제했더니 삭제가 cloud와 다른 PC에 전파되었다. sync는 제대로 작동했지만 backup은 실패한 것이다. version history나 독립 백업에서 삭제 전 상태를 복원해야 한다.

### 4A. 미니 사례집

**사례 1 — 알림 권한 거부**  
핵심 일정 조회 기능은 계속 제공하고, 알림 기능만 제한한다. 사용자가 기능을 켜려 할 때 설정 경로를 안내한다.

**사례 2 — 사진을 앱 내부에만 저장**  
앱 삭제 뒤 사진도 사라져 사용자 기대를 위반했다. shared/media storage 또는 export/backup 설계를 검토한다.

**사례 3 — 두 기기에서 일정 동시수정**  
server updatedAt만 믿고 last-write-wins. 중요한 변경이 사라진다. version conflict를 사용자에게 보여줄지 결정한다.

**사례 4 — cloud sync 폴더 삭제 전파**  
sync 성공, backup 실패. version history/immutable backup에서 복원한다.

### 5. 그럴듯하지만 틀린 판단

1. 권한을 많이 받으면 앱이 더 안정적이라고 생각한다.
2. 한 번 승인된 runtime permission은 영원히 유지된다고 생각한다.
3. cloud sync와 backup을 같은 것으로 생각한다.
4. 백업 파일이 존재하면 복구 가능성도 자동 보장된다고 생각한다.

### 5A. 데이터 저장·권한 선택 질문

- 이 데이터의 **소유자**는 앱인가 사용자 본인인가?
- 앱 제거 후에도 남아야 하는가?
- 다른 앱/기기와 공유해야 하는가?
- 민감한가?
- offline에서도 필요한가?
- conflict가 생기면 자동 merge 가능한가?
- 최대 허용 데이터 손실(RPO)은?
- 복구까지 허용시간(RTO)은?
- 실제 restore를 테스트했는가?

이 질문에 답한 뒤 storage/permission/sync/backup 수단을 선택한다.

### 5B. 백업은 기술보다 정책이 먼저다

모든 데이터를 같은 주기로 백업할 필요는 없다. 다시 다운로드 가능한 AI 모델 cache는 백업가치가 낮고, 수년간 쌓인 CRM 방문기록은 가치가 높다. 데이터 분류표를 만들어 `재생성 가능 / 중요 / 민감 / 법적 보존 필요 / 사용자 소유`를 구분하면 backup 우선순위가 선명해진다.

암호화 backup에서는 key가 또 다른 단일 실패점이 된다. 백업 파일은 있는데 복호화 key를 잃어버리면 복구할 수 없다. 반대로 key를 backup과 같은 위치에 평문으로 두면 도난 시 기밀성이 무너진다. 개인 앱 수준에서도 key recovery와 account recovery를 함께 생각해야 한다.

동기화 conflict는 “누가 최신인가”만으로 풀리지 않는다. 서로 다른 필드를 바꾼 두 수정은 자동 merge할 수 있고, 같은 필드를 바꿨다면 사용자 선택이 필요할 수 있다. 일정 제목과 완료 여부처럼 field별 의미가 다르기 때문이다.

알림 permission처럼 기능 자체에 필수적이지 않은 권한은 onboarding 시작 시 한꺼번에 요구하기보다 사용자가 기능을 켜는 순간 요청하는 편이 이해하기 쉽다. Android 공식 best practice도 사용자 행동과 permission 요청을 연관시키는 것을 권장한다.

백업정책의 마지막 문장은 항상 **“복구를 실제로 시험했는가?”**다. backup job 성공로그만 통과조건으로 두지 않는다. restore한 뒤 record count, 중요 첨부, 최신시점, 권한/소유자까지 검증한다.

### 6. Guided Lab

Galaxy 설정에서 사용하는 앱 3개의 권한을 조사한다. 기능별로 `필수/선택/불필요`를 분류하고, 불필요한 권한을 줄였을 때 어떤 기능이 영향을 받는지 예상한다. 민감 정보가 있다면 실제 데이터를 공유하지 말고 권한 종류만 기록한다.

### 7. Independent Lab

가족 일정 앱의 권한정책과 백업정책을 설계하라. 알림, 사진 첨부, 위치 기능이 있다고 가정하되, 사용자가 위치를 거부해도 일정 기능은 작동해야 한다. DB가 손상됐을 때 마지막 정상 시점으로 복구하는 절차도 포함한다.

### 8. Debug Challenge

**상황:** 앱을 재설치했더니 사용자가 만든 로컬 데이터가 사라졌다. app-specific storage 특성, cloud sync 여부, Auto Backup/자체 백업 설정, 로그인 계정, restore log를 확인한다. ‘재설치하면 데이터가 돌아올 것’이라는 가정을 먼저 버린다.

### 9. AI Audit

AI가 기능 구현을 위해 `모든 파일 접근` 같은 강한 권한을 제안하면 더 좁은 API가 있는지 확인한다. Android 공식 문서의 현재 permission workflow와 저장소 접근방식을 기준으로 검토하고, AI가 오래된 Android 버전 관행을 답했을 가능성을 의심한다.

### 9B. 권한 거부를 정상 상태로 설계하기

사용자가 권한을 거부하는 것은 오류가 아니라 정상 사용자 선택이다. 따라서 화면 상태도 `권한 있음/없음`을 정상 분기로 가져야 한다. 권한이 없을 때 crash하거나 빈 화면만 띄우는 대신, 어떤 기능이 제한되는지 설명하고 권한 없이 가능한 대안을 제공한다.

또한 permission을 재요청할 때 사용자를 압박하지 않는다. 기능을 사용하려는 맥락에서 왜 필요한지 설명하고, 시스템 설정에서 사용자가 직접 변경할 수 있는 경로를 제공한다. 이 원칙은 위치·카메라·마이크뿐 아니라 notification permission과 파일 접근에도 적용된다.

권한과 백업은 편의기능이 아니라 사용자 신뢰와 데이터 수명에 직접 연결되는 제품 설계 문제다.
