## V1-C09. Android 앱이 실제로 사는 곳 — 권한·백그라운드·알림·동기화

**목표:** Android 앱 문제를 앱 코드 한 곳의 문제로 보지 않고 **앱 sandbox / 권한 / OS 정책 / 백그라운드 실행 / 알림 채널 / push token / 저장 / 동기화**로 나눠 볼 수 있게 된다.

---

### 1. Android 앱은 서로 분리된 공간에서 실행된다

Android는 앱마다 서로 분리된 실행·저장 영역을 제공한다. 이를 설명할 때 **sandbox**라는 말을 쓴다.

핵심은 단순하다.

```text
앱 A 데이터
앱 B 데이터
```

기본적으로 서로 마음대로 읽고 쓰지 못하게 막는다.

이 구조 덕분에 앱 하나가 다른 앱의 개인정보를 쉽게 훔치는 것을 줄일 수 있다.

그래서 PC 파일시스템에서 가능한 경로 접근을 Android 앱에서 그대로 기대하면 안 된다.

---

### 2. 권한은 설치됐다고 자동으로 생기지 않는다

카메라, 위치, 알림 등 일부 기능은 사용자 허가가 필요하다.

Android에서는 실행 중 사용자에게 요청하는 권한을 **runtime permission**이라고 한다.

흐름:

```text
기능 실행 시도
↓
권한 있는지 확인
├─ 있음 → 기능 실행
└─ 없음 → 사용자에게 요청 또는 기능 제한
```

중요한 점은 사용자가 권한을 거절할 수 있다는 것이다.

앱은 “권한이 반드시 허용된다”고 가정하면 안 된다.

#### 최소 권한

앱이 필요한 기능에 필요한 만큼만 권한을 요구하는 원칙을 **최소 권한(least privilege)**이라고 한다.

예를 들어 단순 메모 앱이 연락처·위치·마이크 권한까지 요구한다면 이유를 따져봐야 한다.

---

### 3. 알림은 권한 하나만 보면 부족하다

알림이 안 오는 문제는 여러 단계가 있다.

```text
서버 이벤트 생성
↓
push 요청
↓
push provider
↓
기기 token
↓
앱/OS 수신
↓
알림 권한
↓
notification channel
↓
화면 표시
```

어느 한 단계만 실패해도 사용자는 “알림이 안 왔다”고 느낀다.

따라서:

```text
알림 권한 ON
```

이라는 사실만으로 전체 경로가 정상이라고 말할 수 없다.

---

### 4. push token은 기기와 앱을 찾는 주소표 역할을 한다

FCM 같은 push 서비스는 기기/앱 인스턴스를 식별하는 **token**을 사용한다.

이 token은 영원히 고정된 값이라고 가정하면 안 된다.

변경될 수 있는 상황:

- 앱 재설치
- 앱 데이터 초기화
- 기기/서비스 상태 변경
- provider token 갱신

서버가 오래된 token을 계속 쓰면 알림이 실패할 수 있다.

그래서 앱은 새 token을 얻었을 때 서버 등록을 갱신해야 한다.

---

### 5. notification channel — 권한과 별도인 표시 설정

Android는 알림을 채널별로 관리할 수 있다.

예:

```text
일정 알림
마케팅 알림
중요 경고
```

앱 전체 알림 권한이 켜져 있어도 특정 채널이 꺼져 있거나 소리가 비활성화되어 있을 수 있다.

그래서 실제 진단에서는:

```text
앱 전체 알림 권한
채널 존재 여부
채널 중요도
사용자가 채널을 끄지 않았는지
```

를 따로 본다.

---

### 6. 백그라운드 실행은 OS 정책의 영향을 받는다

앱이 화면에 보이지 않을 때도 작업해야 하는 경우가 있다.

예:

- 일정 동기화
- 데이터 업로드
- 정기 갱신

하지만 Android는 배터리와 자원 보호를 위해 백그라운드 실행을 제한한다.

그래서 “앱이 꺼져 있어도 정확히 1초 단위로 계속 실행” 같은 가정은 위험하다.

#### WorkManager

지연 허용이 가능한 백그라운드 작업에는 **WorkManager** 같은 Android 제공 도구를 사용할 수 있다.

핵심은 이름을 외우는 것이 아니라:

```text
백그라운드 작업은 OS가 관리하는 제약 안에서 설계해야 한다.
```

는 점이다.

---

### 7. 배터리 최적화와 제조사 설정

일부 기기/제조사 설정은 백그라운드 활동을 더 강하게 제한할 수 있다.

같은 APK인데:

```text
엄마 폰: 알림 정상
배우자 폰: 알림 실패
```

라면 공통 서버 코드보다 기기별 차이를 우선 비교할 가치가 있다.

비교 후보:

- 앱 버전
- 알림 권한
- notification channel
- battery/background restriction
- token 등록 시각
- 계정/기기 연결 상태

---

### 8. 앱 저장공간은 여러 종류가 있다

Android 앱은 내부 저장소, DB, 설정 저장소, 사용자가 선택한 파일 등 여러 방식으로 데이터를 저장할 수 있다.

문제는 **어디에 저장했느냐에 따라 삭제/백업/권한 규칙이 다를 수 있다**는 것이다.

예:

```text
앱 삭제 → 앱 내부 데이터도 사라질 수 있음
사용자 문서 → 앱 삭제 후에도 남을 수 있음
클라우드 동기화 → 서버에 별도 사본 존재 가능
```

그래서 “앱 삭제하면 데이터가 지워지나?”는 저장 위치를 알아야 답할 수 있다.

---

### 9. sync와 backup은 다르다

**동기화(sync)**는 여러 기기/서버 상태를 맞추는 과정이다.

**백업(backup)**은 원본이 사라져도 복구할 수 있도록 별도 사본을 보관하는 것이다.

동기화는 삭제도 동기화할 수 있다.

```text
폰에서 일정 삭제
↓
서버에도 삭제 반영
↓
다른 폰에서도 삭제
```

이 구조는 최신 상태 유지에는 좋지만 실수 복구용 백업은 아닐 수 있다.

```text
sync ≠ backup
```

---

### 10. 앱 lifecycle — 화면이 보인다고 항상 같은 상태가 아니다

Android 화면은 생성·일시정지·재개·종료 같은 생명주기를 가진다.

세부 콜백 이름을 외울 필요는 없지만, 화면을 떠났다가 돌아올 때 코드가 다시 실행되거나 상태가 복원될 수 있다는 점은 알아야 한다.

예:

```text
화면 A 열기
↓
화면 B로 이동
↓
A 일시 중지/백그라운드
↓
A로 돌아옴
```

이때 네트워크 요청을 매번 다시 실행하면 중복 요청이 생길 수 있고, 반대로 필요한 갱신을 전혀 하지 않으면 오래된 화면이 남을 수 있다.

---

### 11. 프로세스 종료와 상태 복원

운영체제는 백그라운드 앱 프로세스를 종료할 수 있다.

사용자가 앱을 다시 열었을 때:

```text
프로세스가 계속 살아 있던 경우
```

와

```text
프로세스가 종료됐다가 새로 만들어진 경우
```

의 동작이 달라질 수 있다.

중요 상태를 메모리에만 두면 프로세스 종료 후 사라질 수 있다.

그래서 어떤 상태는 저장하고 어떤 상태는 다시 계산할지 설계해야 한다.

---

### 12. 실제 사례 — 배우자 폰만 알림이 안 옴

정상폰과 실패폰을 표로 비교한다.

| 항목 | 정상폰 | 실패폰 |
|---|---|---|
| 앱 버전 | 1.5 | 1.5 |
| 알림 권한 | ON | ON |
| 일정 채널 | ON | OFF |
| token 최신 등록 | 예 | 예 |
| battery 제한 | 없음 | 없음 |

이 경우 서버 전체 장애보다 **채널 설정**이 강한 후보다.

비교군을 쓰면 불필요한 서버 재배포를 줄일 수 있다.

---

### 13. 실제 사례 — 앱 재설치 후 알림이 끊김

가능한 흐름:

```text
재설치
↓
새 push token 발급
↓
서버에는 이전 token만 존재
↓
서버가 옛 token으로 전송
↓
알림 실패
```

확인:

```text
현재 기기 token
서버 등록 token
등록 시각
provider 응답
```

---

### 14. 실제 사례 — 일정은 동기화됐는데 복구가 안 됨

사용자가 일정을 실수로 삭제했고 삭제가 서버와 가족 기기에 동기화됐다.

```text
모든 기기 상태는 동일함
하지만 삭제 전 데이터는 없음
```

동기화는 정상 작동했다. 문제는 백업/버전 기록이 없다는 것이다.

---

### 15. Android 문제 진단 순서

```text
1. 앱 버전/기기/계정 확인
2. 재현 조건 확인
3. 앱 권한 확인
4. OS/채널/배터리 설정 확인
5. token/서버 등록 확인
6. provider 응답 확인
7. lifecycle/background 실행 확인
8. 저장·동기화·복구 경로 확인
```

앱을 바로 삭제·재설치하면 token과 로컬 상태가 바뀌어 원인 증거를 잃을 수 있다.

## 실습 1 — 알림 경로 순서 세우기

다음을 올바른 순서로 배열한다.

```text
기기 token
서버 이벤트
알림 권한/채널
push provider
화면 표시
```

가능한 흐름:

```text
서버 이벤트 → push provider → 기기 token → OS/앱 수신 → 권한/채널 → 표시
```

## 실습 3 — 한 기기만 실패할 때

서버 공통 기능은 정상이고 한 기기만 실패한다.

우선 비교할 항목 세 개를 적는다.

## 실습 4 — 재설치 전에 할 일

알림 문제를 해결하려고 앱을 지우기 전에 저장할 증거:

```text
현재 앱 버전

최근 provider 응답

```

## 장 끝 미니 프로젝트 — 한 기능의 Android 의존성 지도

기능 하나를 고른다.

예: 일정 알림, 사진 업로드, 주가 자동갱신.

| 층 | 필요한 것 |
|---|---|
| 앱 UI | |
| 앱 상태/DB | |
| runtime permission | |
| background 정책 | |
| OS 설정 | |
| 서버 | |
| push/API provider | |
| 복구/backup | |

빈 칸을 채우면서 “앱 코드만 고치면 되는 문제인가?”를 판단한다.

---

## 핵심 용어

| 용어 | 뜻 |
|---|---|
| sandbox | 앱별 실행·데이터 접근을 분리하는 보안 경계 |
| runtime permission | 실행 중 사용자에게 허용을 요청하는 권한 |
| least privilege | 필요한 최소 권한만 주는 원칙 |
| push token | push 서비스가 앱/기기 인스턴스를 식별하는 값 |
| notification channel | Android에서 알림 종류별 설정 단위 |
| background work | 앱이 전면에 없을 때 수행하는 작업 |
| WorkManager | 제약을 고려해 백그라운드 작업을 예약하는 Android 도구 |
| lifecycle | 화면/앱 상태 변화에 따른 생명주기 |
| sync | 여러 위치의 최신 상태를 맞추는 과정 |
| backup | 복구를 위해 별도 사본을 보관하는 것 |

---

## 이 장을 끝내고 할 수 있어야 하는 것

1. Android sandbox가 왜 필요한지 설명한다.
2. 권한 ON 하나만으로 알림 전체 경로가 정상이라고 말하지 않는다.
3. push token이 바뀔 수 있음을 안다.
4. notification channel과 앱 전체 알림 권한을 구분한다.
5. 백그라운드 실행이 OS 정책 영향을 받음을 설명한다.
6. sync와 backup을 구분한다.
7. 한 기기만 실패할 때 정상 기기와 비교군을 만든다.
8. 재설치 전에 원인 증거를 저장한다.
