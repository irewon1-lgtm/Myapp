## V1-C09. Android 앱이 실제로 사는 곳 — 권한·저장·백그라운드·동기화·백업

**이 장의 대상:** Android 앱을 매일 쓰지만 앱마다 권한, 알림, 저장 방식, 백그라운드 제한이 왜 다른지 모르는 사람.

**이 장의 목표:** Android에서 앱 하나가 **설치 → 실행 → 권한 요청 → 데이터 저장 → 백그라운드 작업 → 알림 → 동기화 → 백업 → 업데이트**되는 전체 흐름을 이해한다.

---

### 1. Android 앱은 운영체제 안에서 살아간다

Android 앱은 혼자 모든 것을 할 수 없다.

카메라, 위치, 파일, 알림, 네트워크 같은 기능을 사용할 때 운영체제의 규칙을 따라야 한다.

```text
앱
↓ 요청
Android 운영체제
↓ 허용/차단/중재
카메라·저장장치·네트워크·알림 등
```

따라서 앱 문제가 항상 앱 코드 하나의 문제는 아니다.

운영체제 설정과 권한, 배터리 정책도 영향을 줄 수 있다.

---

### 2. 앱 샌드박스는 무엇일까?

Android는 앱마다 데이터를 분리해 보호한다.

이를 설명할 때 **샌드박스(sandbox)**라는 말을 사용한다.

> **sandbox = 앱이 다른 앱의 내부 데이터에 마음대로 접근하지 못하도록 분리한 실행·저장 영역**

앱 A가 앱 B의 개인 파일을 그냥 읽을 수 없도록 막는 것이 기본 원칙이다.

---

### 3. 샌드박스가 왜 중요한가?

만약 모든 앱이 서로의 파일을 마음대로 읽을 수 있다면:

```text
은행 앱 로그인 정보
메신저 개인 데이터
사진 앱 내부 파일
업무 앱 데이터
```

가 쉽게 노출될 수 있다.

그래서 운영체제는 앱별 식별자와 권한 체계를 사용해 경계를 만든다.

---

### 4. 앱 권한은 무엇일까?

일부 기능은 사용자의 허락이 필요하다.

예:

```text
카메라
마이크
위치
연락처
알림
사진/미디어 접근
```

이 허락을 **앱 권한(permission)**이라고 부른다.

Chapter 5에서 배운 권한 개념이 Android에 적용된 것이다.

---

### 5. 설치 시 권한과 실행 중 권한

예전에는 설치할 때 많은 권한을 한꺼번에 주는 방식이 흔했다.

현재 Android에서는 민감한 권한을 **실행 중(runtime)**에 사용자에게 요청하는 경우가 많다.

이를 **런타임 권한(runtime permission)**이라고 한다.

> **runtime permission = 앱을 사용하는 도중 실제 기능이 필요할 때 사용자에게 묻는 권한**

---

### 6. 권한을 거부해도 앱이 설명해야 한다

사용자가 카메라 권한을 거부했다고 앱이 그냥 종료되면 좋지 않다.

더 좋은 흐름:

```text
카메라 권한 필요
↓
사용자에게 이유 설명
↓
권한 요청
↓
허용 → 기능 실행
거부 → 대체 안내 또는 기능 제한 설명
```

권한 거부는 예외 상황이 아니라 정상적으로 처리해야 할 사용자 선택이다.

---

### 7. 최소 권한 원칙을 Android에 적용하기

필요하지 않은 권한을 요구하지 않는다.

예를 들어 단순 계산기 앱이 위치와 연락처 권한을 요구한다면 사용자는 의심할 수 있다.

> **기능에 필요한 최소 권한만 요청한다.**

보안뿐 아니라 사용자 신뢰에도 중요하다.

---

### 8. 권한이 허용됐는데 기능이 안 될 수도 있다

권한만 있으면 모든 것이 끝나는 것은 아니다.

예:

```text
카메라 권한 허용
하지만 카메라 다른 앱이 사용 중
```

또는:

```text
알림 권한 허용
하지만 앱 알림 채널 꺼짐
```

처럼 여러 조건이 있다.

따라서 `permission granted` 하나만 보고 전체 기능 정상이라고 확정하지 않는다.

---

### 9. 앱 내부 저장은 무엇일까?

앱이 자기 샌드박스 안에 파일과 DB를 저장할 수 있다.

다른 앱이 일반적으로 직접 접근하기 어려운 영역이다.

예:

```text
사용자 설정
로컬 DB
캐시
내부 파일
```

앱 삭제 시 이 데이터가 함께 지워질 수 있다.

정확한 동작은 저장 위치와 백업 정책에 따라 다르다.

---

### 10. 사용자가 보는 파일과 앱 내부 파일은 다르다

`Download` 폴더에 있는 PDF처럼 사용자가 직접 보는 파일과 앱 내부 DB는 성격이 다르다.

```text
공유 저장 공간의 파일 → 사용자가 파일 관리자에서 볼 수 있음
앱 내부 데이터       → 앱 전용 영역 중심
```

이 구분을 알아야 “파일 관리자에 없는데 앱 데이터는 왜 남아 있지?” 같은 질문을 이해할 수 있다.

---

### 11. Scoped Storage라는 말

최근 Android는 앱이 공유 저장공간 전체를 마음대로 다루지 못하도록 접근 범위를 제한한다.

이 정책을 설명할 때 **Scoped Storage**라는 표현을 사용한다.

처음에는:

> **Scoped Storage = 앱이 필요한 파일과 영역만 더 안전하게 접근하도록 범위를 제한하는 Android 저장 정책**

정도로 이해한다.

---

### 12. 파일 선택기는 왜 안전한가?

사용자가 직접 파일을 고르는 방식은 앱에게 전체 저장공간 권한을 주지 않고도 특정 파일 접근을 허용할 수 있다.

```text
사용자: 이 PDF를 선택
↓
Android: 앱에 선택한 파일 접근 권한 부여
↓
앱: 해당 파일 읽기
```

이때 `content://...` 같은 URI를 받을 수 있다.

Chapter 2에서 배운 URI가 여기서 실제로 등장한다.

---

### 13. 앱 캐시는 무엇일까?

Android 앱도 임시 데이터를 캐시에 저장할 수 있다.

예:

```text
이미지 썸네일
최근 API 응답
임시 계산 결과
```

캐시는 지워져도 앱 핵심 데이터가 망가지지 않도록 설계하는 것이 좋다.

하지만 실제 앱마다 구현은 다르다.

---

### 14. “데이터 삭제”와 “캐시 삭제”는 다르다

설정 화면에서 비슷한 버튼을 볼 수 있다.

#### 캐시 삭제

임시 데이터를 지우는 목적.

#### 데이터 삭제

앱 내부 저장 데이터와 설정을 초기화하는 더 강한 조치가 될 수 있다.

따라서 사용자 데이터가 중요하다면 **데이터 삭제를 문제 해결 첫 단계로 쓰면 안 된다.**

---

### 15. 앱을 종료하면 백그라운드 작업도 끝날까?

항상 그렇지는 않다.

일부 작업은 앱 화면이 없어도 계속되어야 할 수 있다.

예:

```text
파일 업로드
예약된 동기화
알림 예약
음악 재생
```

Android는 배터리와 성능을 위해 백그라운드 실행을 엄격히 관리한다.

---

### 16. 백그라운드 제한은 왜 있을까?

앱 수십 개가 화면이 꺼진 뒤에도 계속 CPU와 네트워크를 사용하면 배터리가 빠르게 줄어든다.

그래서 Android는 백그라운드 활동을 제한한다.

```text
배터리 절약
과도한 네트워크 방지
발열 감소
리소스 공정 배분
```

앱 개발자는 운영체제 정책에 맞는 작업 방식을 사용해야 한다.

---

### 17. WorkManager란 무엇일까?

Android에서는 나중에 반드시 수행되어야 하는 지연 가능한 백그라운드 작업에 **WorkManager** 같은 도구를 사용할 수 있다.

초보자는 API 문법을 외우지 않는다.

> **WorkManager = Android가 적절한 시점에 보장성 있는 백그라운드 작업을 수행하도록 돕는 작업 관리자**

예:

```text
로그 업로드
데이터 동기화
서버에 결과 전송
```

---

### 18. Foreground Service는 무엇일까?

사용자에게 보이는 알림을 유지하면서 장시간 실행해야 하는 작업에는 **Foreground Service**라는 구조가 사용될 수 있다.

예:

```text
운동 기록
내비게이션
음악 재생
```

> **Foreground Service = 사용자가 진행 중임을 알 수 있게 알림을 보여주며 장시간 실행하는 서비스 방식**

모든 백그라운드 작업에 쓰는 것은 아니다.

---

### 19. 알림은 앱 화면과 별도다

앱이 꺼져 있어도 시스템 알림이 표시될 수 있다.

알림에는 여러 층이 있다.

```text
서버가 알림 이벤트 생성
↓
푸시 서비스로 전송
↓
기기 수신
↓
앱/시스템 처리
↓
알림 채널 설정
↓
사용자 화면 표시
```

한 단계만 실패해도 사용자는 “알림이 안 옴”이라고 느낀다.

---

### 20. 알림 권한

최신 Android에서는 앱 알림 표시 자체에 사용자 권한이 필요한 버전이 있다.

따라서:

```text
서버 전송 성공
```

과:

```text
사용자에게 알림 표시 성공
```

은 다르다.

기기 알림 권한을 확인해야 한다.

---

### 21. 알림 채널은 무엇일까?

Android 앱은 알림 종류를 **채널(channel)**로 나눌 수 있다.

예:

```text
중요 일정
마케팅
일반 안내
```

사용자는 채널별로 소리와 표시를 끌 수 있다.

앱 전체 알림이 켜져 있어도 특정 채널이 꺼져 있을 수 있다.

---

### 22. 배터리 최적화가 알림에 영향을 줄 수 있을까?

기기 제조사와 Android 버전에 따라 백그라운드 제한이 강하게 적용될 수 있다.

앱이 force-stop 되었거나 배터리 제한 대상이면 일부 백그라운드 동작이 예상과 다를 수 있다.

따라서 알림 문제에서는:

```text
앱 권한
알림 채널
배터리 제한
앱 상태
푸시 토큰
서버 전송 결과
```

를 나눠 본다.

---

### 23. 푸시 토큰은 무엇일까?

푸시 서비스는 특정 앱 설치를 구분하기 위한 토큰을 사용할 수 있다.

이를 흔히 **device token**, **push token**이라고 부른다.

> **푸시 토큰 = 서버가 특정 앱 설치로 알림을 보내기 위해 사용하는 식별값**

앱 재설치나 환경 변화로 토큰이 바뀔 수 있다.

서버가 오래된 토큰을 가지고 있으면 알림이 실패할 수 있다.

---

### 24. 특정 가족 한 명만 알림이 안 올 때

모두 같은 서버를 사용하는데 한 기기만 실패한다면 비교군이 생긴다.

정상 기기와 실패 기기를 비교한다.

| 항목 | 정상 | 실패 |
|---|---|---|
| 앱 버전 | 동일? | 동일? |
| 알림 권한 | ON | ? |
| 채널 | ON | ? |
| push token | 최신 | ? |
| 서버 수신자 목록 | 포함 | ? |
| provider 응답 | 성공 | ? |

전체 서버를 다시 만들기 전에 기기별 차이를 본다.

---

### 25. 동기화란 무엇일까?

여러 기기나 서버의 데이터를 같은 상태로 맞추는 것을 **동기화(sync)**라고 부른다.

예:

```text
폰에서 일정 추가
↓
서버 저장
↓
태블릿이 새 일정 받음
```

> **동기화 = 여러 위치의 데이터를 최신 상태로 맞추는 과정**

---

### 26. 동기화와 백업은 다르다

이 차이는 매우 중요하다.

#### 동기화

한 곳의 변경이 다른 곳에도 반영된다.

삭제도 동기화될 수 있다.

#### 백업

원본이 사라졌을 때 복구하기 위해 별도 사본을 보관한다.

```text
동기화 = 같은 상태 유지
백업   = 과거 상태 복구 가능성 확보
```

동기화가 켜져 있다고 백업이 된 것은 아니다.

---

### 27. 잘못된 삭제가 동기화되는 문제

사용자가 폰에서 일정을 실수로 삭제했다.

동기화 시스템이라면 서버와 다른 기기에서도 삭제될 수 있다.

백업이나 휴지통, 버전 기록이 없다면 복구하기 어려울 수 있다.

그래서 중요한 데이터는 동기화와 별도로 백업 정책을 설계한다.

---

### 28. 백업은 존재만 확인하면 안 된다

백업 파일이 있다고 복구가 보장되는 것은 아니다.

**복원(restore)** 테스트가 필요하다.

```text
백업 생성
↓
복원 테스트
↓
데이터 수 확인
↓
앱 정상 실행 확인
```

> **restore = 백업 데이터를 실제 사용 가능한 상태로 되돌리는 것**

---

### 29. 자동 백업과 수동 백업

Android와 앱은 다양한 백업 방식을 사용할 수 있다.

어떤 데이터가 자동 백업 대상인지, 암호화되는지, 계정과 연결되는지 앱마다 다르다.

따라서 “Android가 알아서 백업하겠지”라고 가정하지 않는다.

중요한 데이터는 앱 정책과 실제 복구 테스트를 확인한다.

---

### 30. 앱 업데이트와 데이터 보존

APK를 업데이트해도 기존 데이터가 보존되는 것이 일반적인 기대지만, migration 오류가 있으면 데이터가 사라진 것처럼 보일 수 있다.

확인할 것:

```text
DB schema migration
계정 로그인 상태
서버 동기화
로컬 데이터 경로
앱 패키지 identity
```

Chapter 6 내용과 연결된다.

---

### 31. 앱 삭제와 업데이트는 다르다

#### 업데이트

기존 앱 위에 새 버전을 설치.

#### 삭제 후 재설치

기존 앱을 제거하고 새로 설치.

앱 내부 데이터가 지워질 가능성이 다르다.

따라서 “업데이트가 안 되니까 삭제 후 재설치”를 첫 해결책으로 쓰면 중요한 데이터와 증거를 잃을 수 있다.

---

### 32. Force Stop은 무엇일까?

Android 설정에서 **강제 종료(Force stop)**를 할 수 있다.

이 상태에서는 앱의 일부 백그라운드 동작과 알림 흐름이 영향을 받을 수 있다.

사용자가 직접 앱을 다시 실행하기 전까지 동작이 제한될 수 있다.

알림 문제에서 force-stop 여부도 확인한다.

---

### 33. 앱 수명주기 맛보기

Android 화면은 항상 영원히 살아 있는 것이 아니다.

화면이 나타나고, 가려지고, 사라질 수 있다.

이를 **수명주기(lifecycle)**라고 부른다.

> **lifecycle = 앱이나 화면이 생성되고 보이고 사라지는 상태 변화 과정**

비동기 작업이 끝났을 때 화면이 이미 사라졌을 수 있으므로 안전하게 상태를 처리해야 한다.

---

### 34. 화면 회전도 상태 테스트다

기기를 회전하면 화면이 다시 만들어질 수 있다.

입력 중이던 값이 사라지거나 네트워크 요청이 중복되면 상태 관리 문제가 드러난다.

테스트 예:

```text
검색어 입력
↓
화면 회전
↓
검색어 유지되는가?
요청이 중복되는가?
```

---

### 35. 프로세스가 죽었다가 다시 살아날 수 있다

메모리 부족이나 시스템 정책으로 백그라운드 앱 프로세스가 종료될 수 있다.

사용자가 돌아왔을 때 앱은 필요한 상태를 다시 복구해야 한다.

메모리에만 저장한 값은 사라질 수 있다.

그래서 중요한 상태는 적절한 저장 전략이 필요하다.

---

### 36. WebView 앱과 네이티브 앱

Android 앱 안에 WebView로 웹을 표시할 수 있다.

이 경우:

```text
웹 코드 업데이트
네이티브 APK 업데이트
```

가 서로 다를 수 있다.

그래서 어떤 앱은 서버 웹페이지를 바꾸면 즉시 화면이 바뀌고, 어떤 앱은 새 APK를 설치해야 한다.

앱 구조를 먼저 확인한다.

---

### 37. 자동 업데이트는 왜 앱마다 다를까?

업데이트 방식은 배포 구조에 따라 다르다.

예:

```text
Play Store 배포
기업용 MDM
앱 자체 업데이트 기능
WebView로 서버 콘텐츠 로드
```

WebView 앱은 웹 콘텐츠가 서버에서 바뀌어 자동으로 새 화면이 보일 수 있다.

네이티브 코드가 바뀌면 APK 자체 업데이트가 필요할 수 있다.

---

### 38. 실제 예제 — 알림이 한 기기만 안 옴

진단 순서:

1. 서버에서 이벤트 생성됐는가?
2. 해당 사용자/기기가 수신자에 포함됐는가?
3. push token이 등록됐는가?
4. provider 전송 응답은 성공인가?
5. 기기 알림 권한은 ON인가?
6. 채널은 ON인가?
7. 앱이 force-stop 상태인가?
8. 배터리 제한은 어떤가?

한 번에 앱 재설치하지 않는다.

---

### 39. 실제 예제 — 일정이 다른 기기에 안 보임

가능한 흐름:

```text
폰 A에서 일정 저장
↓
로컬만 저장됐나?
↓
서버 업로드됐나?
↓
폰 B가 동기화 요청했나?
↓
응답에 일정이 포함됐나?
↓
폰 B DB 저장됐나?
↓
UI에 표시됐나?
```

각 단계에서 실제 데이터가 있는지 확인한다.

---

### 40. 실제 예제 — 업데이트 후 데이터가 사라짐

신규 설치는 정상인데 업데이트 사용자만 데이터가 비어 있다.

우선:

```text
migration
계정 전환
동기화 복구
DB 경로
```

를 본다.

기존 데이터를 지우기 전에 사본을 보존한다.

---

### 41. 실제 예제 — 권한을 켰는데 카메라 안 됨

확인:

```text
앱 권한 허용 여부
카메라가 다른 앱에서 사용 중인지
앱 내부 오류 로그
기기 정책
하드웨어 문제
```

권한은 하나의 단계일 뿐이다.

---

### 42. Android 문제를 보는 기본 층

```text
앱 UI
↓
앱 상태/코드
↓
앱 내부 저장
↓
Android 권한/정책
↓
백그라운드/배터리
↓
네트워크
↓
서버/푸시 서비스
```

이 지도에 문제를 올려놓고 마지막 정상 지점을 찾는다.

---

### 43. 초보자가 자주 하는 오해

#### 오해 1. 권한이 ON이면 기능은 무조건 정상이다

아니다.

#### 오해 2. 동기화는 백업과 같다

아니다.

#### 오해 3. 알림이 안 오면 서버만 문제다

기기 토큰, 권한, 채널 등 여러 단계가 있다.

#### 오해 4. 업데이트 오류는 삭제 후 재설치하면 끝이다

데이터와 증거가 사라질 수 있다.

#### 오해 5. WebView 앱도 모든 변경에 APK 재설치가 필요하다

웹 콘텐츠만 바뀌는 경우는 다를 수 있다.

### 44. 용어사전

| 쉬운 말 | 영어 | 뜻 |
|---|---|---|
| 샌드박스 | sandbox | 앱별 실행·데이터 영역을 분리한 구조 |
| 런타임 권한 | runtime permission | 앱 사용 중 필요한 순간 요청하는 권한 |
| Scoped Storage | Scoped Storage | 공유 저장소 접근 범위를 제한하는 Android 정책 |
| WorkManager | WorkManager | 보장성 있는 백그라운드 작업을 관리하는 Android 도구 |
| Foreground Service | Foreground Service | 사용자에게 알림을 보여주며 장시간 실행하는 서비스 방식 |
| 알림 채널 | notification channel | Android 알림 종류별 설정 단위 |
| 푸시 토큰 | push token | 특정 앱 설치를 식별해 알림을 보내는 값 |
| 동기화 | sync | 여러 위치의 데이터를 최신 상태로 맞추는 것 |
| 백업 | backup | 원본 손실에 대비한 별도 사본 |
| 복원 | restore | 백업에서 실제 사용 가능한 상태로 되돌리는 것 |
| 강제 종료 | force stop | Android가 앱 실행을 강제로 멈춘 상태 |
| 수명주기 | lifecycle | 앱/화면의 생성·표시·종료 상태 변화 |
| WebView | WebView | 앱 안에서 웹 콘텐츠를 표시하는 영역 |

### 45. 확인 문제

1. sandbox가 필요한 이유는 무엇인가?
2. runtime permission을 사용자가 거부하면 앱은 어떻게 해야 하는가?
3. cache 삭제와 data 삭제의 차이는 무엇인가?
4. sync와 backup의 차이는 무엇인가?
5. 서버에서 push 전송이 성공했는데도 알림이 안 보일 수 있는 이유를 세 가지 말해보자.
6. 업데이트 실패 때 삭제 후 재설치를 첫 단계로 하면 왜 위험한가?

---

### 46. 종합 미션

상황:

> 엄마 폰은 가족 일정 알림이 오는데 배우자 폰만 안 온다. 앱 버전은 같다.

조사표를 만든다.

```text
[ ] 배우자 계정이 수신자 목록에 있는가?
[ ] 배우자 폰 push token이 최신인가?
[ ] provider send 결과는 성공인가?
[ ] 알림 권한은 켜져 있는가?
[ ] 해당 notification channel은 켜져 있는가?
[ ] 앱 force-stop 여부는?
[ ] 배터리 제한 상태는?
[ ] 같은 일정 이벤트 로그가 두 기기에서 어떻게 다른가?
```

이렇게 정상 기기와 실패 기기의 차이를 비교하면 전체 시스템을 재설치하는 것보다 훨씬 빨리 좁힐 수 있다.

---

### 47. 한 장 요약

1. Android 앱은 운영체제 샌드박스 안에서 실행된다.
2. 민감 기능은 runtime permission이 필요할 수 있다.
3. 앱 내부 데이터와 사용자가 보는 공유 파일은 다르다.
4. Android는 배터리를 위해 백그라운드 작업을 제한한다.
5. WorkManager와 Foreground Service는 목적이 다르다.
6. 알림은 서버→푸시 서비스→기기→권한/채널→표시 여러 단계로 나뉜다.
7. push token은 특정 앱 설치를 구분하는 값이다.
8. 동기화와 백업은 다르다.
9. 백업은 실제 restore 테스트를 해야 의미가 있다.
10. 업데이트와 삭제 후 재설치는 데이터 영향이 다르다.
11. Android 문제는 앱 코드뿐 아니라 권한·OS 정책·배터리·네트워크를 함께 본다.

다음 장에서는 지금까지 배운 자원·로그·네트워크·Android 지식을 이용해 **느림, 멈춤, 크래시, 데이터 오류를 실제로 진단하는 방법**을 배운다.
