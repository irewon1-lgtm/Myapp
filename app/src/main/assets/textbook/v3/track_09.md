# TRACK 09 · 보안과 데이터 보호

이 TRACK은 보안을 처음 배우는 사람을 기준으로 시작한다.

보안은 어려운 암호 공식이나 해커 영화 장면부터 배우지 않는다.

먼저 아주 단순한 질문부터 시작한다.

```text
누가 이 데이터를 볼 수 있어야 하는가?
누가 이 기능을 실행할 수 있어야 하는가?
사용자가 보낸 값은 어디까지 믿어도 되는가?
비밀번호는 왜 그대로 저장하면 안 되는가?
파일이 바뀌지 않았다는 것은 어떻게 확인할까?
서버 비밀키가 코드에 들어가면 왜 위험할까?
```

이 질문을 하나씩 따라가면 인증, 권한, hash, encryption, signature, certificate, SQL injection, XSS, CSRF, secret 관리가 서로 연결된다.

이 TRACK의 목표는 보안 용어를 외우는 것이 아니다.

> **어떤 데이터를 지켜야 하는지 찾고, 어디를 믿으면 안 되는지 구분하고, 공격이 가능한 경로를 생각하고, 실제 코드에서 위험한 부분을 찾아 수정할 수 있는 것**

이다.

## BLOCK 01 · 보안은 무엇을 지키고 누구를 어디까지 믿을지 정하는 일이다

### LESSON 01 · 자산·공격자·기밀성·무결성·가용성·인증·권한·신뢰 경계를 한 흐름으로 이해한다

#### 1. 보안은 먼저 `무엇을 지킬 것인가`에서 시작한다

쇼핑몰 앱을 만든다고 하자.

이 앱에는 지켜야 할 것이 많다.

```text
사용자 이름과 주소
비밀번호
주문 내역
결제 정보
관리자 기능
회사 내부 데이터
서버 API key
서비스가 정상 동작하는 상태
```

이처럼 우리가 보호해야 하는 것을 넓게 **자산(asset)**이라고 부른다.

`asset`이라는 영어를 외우는 것이 중요한 것이 아니다.

사람말로 바꾸면:

> **잃거나 노출되거나 망가지면 문제가 되는 것**

이다.

예를 들어 사용자의 공개 닉네임과 카드 번호는 같은 수준으로 보호할 데이터가 아니다.

카드 번호나 비밀번호는 노출 피해가 훨씬 크다.

따라서 보안 설계의 첫 질문은 항상 비슷하다.

```text
우리가 가진 것 중 무엇이 중요한가?
그것이 노출되면 어떤 일이 생기는가?
그것이 바뀌면 어떤 일이 생기는가?
그것을 사용할 수 없게 되면 어떤 일이 생기는가?
```

#### 2. 공격자는 꼭 후드티를 입은 외부 해커만 뜻하지 않는다

보호 규칙을 우회해 자산에 접근하거나 서비스를 방해하려는 사람이나 프로그램을 **공격자(attacker)**라고 부른다.

하지만 공격자를 너무 좁게 생각하면 안 된다.

예를 들어:

```text
외부 인터넷 사용자
로그인한 일반 사용자
퇴사했지만 계정이 남아 있는 직원
권한을 잘못 사용한 관리자
악성 자동화 프로그램
도난당한 휴대폰을 가진 사람
```

모두 상황에 따라 위험 주체가 될 수 있다.

즉:

```text
외부인 = 항상 위험
내부 사용자 = 항상 안전
```

처럼 단순하게 나누면 안 된다.

#### 3. 보안에서 자주 보는 세 가지 목표

보안을 처음 배울 때 세 가지 큰 목표를 많이 사용한다.

첫째는 **기밀성(confidentiality)**이다.

사람말:

> **보면 안 되는 사람이 데이터를 읽지 못하게 하는 것**

예:

```text
다른 사용자가 내 주민번호를 보면 안 됨
일반 직원이 관리자 비밀번호를 보면 안 됨
인터넷 중간의 제3자가 로그인 비밀번호를 읽으면 안 됨
```

둘째는 **무결성(integrity)**이다.

사람말:

> **허가되지 않은 사람이 데이터를 마음대로 바꾸지 못하고, 데이터가 올바른 상태를 유지하는 것**

예:

```text
주문 금액이 몰래 100,000원 → 1원으로 바뀌면 안 됨
다운로드한 APK가 중간에서 다른 파일로 바뀌면 안 됨
사용자 권한이 임의로 admin으로 바뀌면 안 됨
```

셋째는 **가용성(availability)**이다.

사람말:

> **정상 사용자가 필요할 때 서비스를 사용할 수 있는 것**

예:

```text
로그인 서버가 계속 죽어 아무도 로그인 못 함
DB가 멈춰 주문을 조회할 수 없음
공격으로 서버가 요청을 처리하지 못함
```

이 세 가지를 흔히 CIA triad라고 부른다.

영어 약자보다 실제 상황을 구분하는 것이 더 중요하다.

#### 4. 보안 문제는 `무엇이 잘못될 수 있는가`를 먼저 생각한다

다음 쇼핑몰 기능을 보자.

```text
사용자가 자신의 주문을 조회한다.
```

정상 흐름은 단순하다.

하지만 보안 관점에서는 다른 질문을 한다.

```text
다른 사람 주문 번호를 넣으면 볼 수 있나?
로그인하지 않아도 URL만 알면 볼 수 있나?
관리자 API를 일반 사용자가 직접 호출할 수 있나?
주문 ID에 이상한 문자열을 넣으면 서버는 어떻게 되나?
```

`무엇이 잘못될 수 있는가`라는 가능성을 **위협(threat)**이라고 생각할 수 있다.

그리고 공격자가 실제로 이용할 수 있는 약점을 **취약점(vulnerability)**이라고 부른다.

예:

```text
위협
다른 사용자의 주문을 읽을 수 있다.

취약점
서버가 주문의 소유자를 확인하지 않는다.
```

이 둘을 구분하면 문제를 더 정확히 볼 수 있다.

#### 5. risk는 `있다/없다`만 보는 것이 아니다

취약점이 있다고 모두 같은 위험은 아니다.

예를 들어:

```text
A: 로그인 화면의 버튼 색이 잘못 보임
B: 누구나 관리자 API를 호출할 수 있음
```

둘 다 문제지만 피해 크기가 다르다.

보안에서는 보통:

```text
발생 가능성
×
발생했을 때 피해 크기
```

를 함께 보며 위험을 판단한다.

이것을 **risk** 관점이라고 생각하면 된다.

정확한 보안 평가 방법은 더 복잡하지만 초급에서는:

> **가능성과 피해를 함께 본다.**

이 정도를 확실히 잡는다.

#### 6. 신뢰 경계는 `여기부터는 그대로 믿지 않는다`라는 선이다

내 프로그램 안에서 직접 만든 값과 인터넷에서 사용자가 보내온 값은 같은 수준으로 믿을 수 없다.

예를 들어:

```text
브라우저
↓ 사용자 입력
서버
↓
DB
```

브라우저에서 서버로 넘어오는 지점은 중요한 **신뢰 경계(trust boundary)**다.

왜냐하면 사용자는 우리가 만든 정상 화면만 사용한다는 보장이 없기 때문이다.

정상 UI에는:

```text
수량 1~10만 입력 가능
```

이라고 만들어도 공격자는 직접 HTTP 요청을 만들어:

```json
{"quantity": -999999}
```

를 보낼 수 있다.

그래서 서버는:

> `프론트엔드가 검사했으니 괜찮겠지.`

라고 믿으면 안 된다.

신뢰 경계에서는 다시 검증한다.

대표적인 경계:

```text
브라우저 → 서버
모바일 앱 → 서버
서버 → 외부 결제 API
사용자 업로드 파일 → 서버 저장소
일반 사용자 → 관리자 기능
프로그램 → 운영체제 명령
```

#### 7. 인증은 `누구인가`, 권한은 `무엇을 할 수 있는가`

보안에서 초보자가 가장 많이 섞는 두 단어가 있다.

**인증(authentication)**은:

> **너 누구야?**

를 확인하는 것이다.

예:

```text
비밀번호 확인
일회용 인증코드
passkey
생체 인증
세션 확인
token 확인
```

그런데 사용자가 누구인지 안다고 모든 일을 허용할 수는 없다.

**인가/권한 확인(authorization)**은:

> **이 사용자가 이 작업을 해도 되는가?**

를 판단하는 것이다.

예를 들어 민수가 로그인했다.

```text
인증 결과
현재 사용자 = 민수
```

민수가 자신의 주문 100번을 보는 것은 허용할 수 있다.

하지만 다른 사용자의 주문 200번을 보려고 한다.

```text
GET /orders/200
```

주문 번호를 안다고 볼 권한이 생기는 것은 아니다.

서버는:

```text
order.userId == currentUser.id ?
```

같은 권한 확인을 해야 한다.

정리:

```text
인증 = 누구인가?
권한 = 무엇을 할 수 있는가?
```

#### 8. 화면에서 버튼을 숨기는 것은 권한 보호가 아니다

관리자가 아니면 `삭제` 버튼을 숨겼다고 하자.

```text
일반 사용자 화면
[삭제 버튼 없음]
```

겉으로는 안전해 보인다.

하지만 공격자는 화면을 거치지 않고 API를 직접 호출할 수 있다.

```http
DELETE /admin/users/123
```

서버가 권한을 확인하지 않으면 UI를 숨긴 것은 아무 의미가 없다.

따라서 중요한 권한 검사는 **서버에서** 수행해야 한다.

#### 9. 최소 권한 원칙은 사고가 났을 때 피해 범위를 줄인다

웹 서버가 DB에 접속한다고 하자.

필요한 기능은:

```text
users 조회
orders 생성
orders 수정
```

정도인데 DB 계정에:

```text
모든 table 삭제
모든 DB 삭제
새 관리자 계정 생성
```

권한까지 주면 어떨까?

서버 하나가 침해되었을 때 공격자가 할 수 있는 일이 너무 많아진다.

그래서:

> **필요한 작업에 필요한 최소 권한만 준다.**

는 원칙을 사용한다.

이것을 **least privilege**, 최소 권한 원칙이라고 부른다.

#### 10. threat modeling은 공격당한 뒤가 아니라 만들기 전에 생각하는 것이다

기능 하나를 만들기 전에 다음 질문을 해 본다.

예: 프로필 사진 업로드 기능.

```text
무엇을 지켜야 하나?
→ 서버 저장공간, 다른 사용자 데이터, 서버 실행 권한

누가 입력을 보내나?
→ 인터넷 사용자

어떤 위험이 있나?
→ 너무 큰 파일, 실행 파일, 잘못된 이미지, 악성 파일

어디가 신뢰 경계인가?
→ 업로드 파일이 서버로 들어오는 지점

어떤 방어가 필요한가?
→ 크기 제한, 형식 검증, 안전한 저장 위치, 새 파일명, 실행 차단
```

이렇게 **설계 전에 공격 경로를 생각하는 것**이 threat modeling의 기본 감각이다.

#### 11. 초보자가 자주 하는 착각

**착각 1 — 로그인만 있으면 보안이 끝난다**

로그인은 인증의 일부다. 로그인 후에도 각 기능의 권한 확인이 필요하다.

**착각 2 — 내 앱 화면에서 입력을 제한했으니 서버는 믿어도 된다**

서버 API는 직접 호출할 수 있다. 서버에서 다시 검증한다.

**착각 3 — 내부 사용자니까 안전하다**

내부 계정도 탈취되거나 권한을 오용할 수 있다.

**착각 4 — 보안은 공격을 100% 막는 기술이다**

현실에서는 위험을 줄이고, 탐지하고, 피해 범위를 제한하고, 복구할 수 있게 만드는 것도 중요하다.

#### 12. 책을 덮고 확인한다

1. 자산은 무엇인가?
2. 기밀성·무결성·가용성을 각각 실제 예로 설명해 보라.
3. 인증과 권한의 차이는 무엇인가?
4. UI에서 관리자 버튼을 숨기는 것만으로 부족한 이유는 무엇인가?
5. 신뢰 경계에서 입력을 다시 검사해야 하는 이유는 무엇인가?
6. 최소 권한 원칙이 사고 피해를 줄이는 이유는 무엇인가?
7. 프로필 사진 업로드 기능에서 가능한 위협을 세 가지 말해 보라.

## BLOCK 02 · encoding·hash·password·encryption·signature는 모두 다른 도구다

### LESSON 01 · 표현 바꾸기부터 파일 검증·비밀번호 저장·암호화·전자서명·인증서까지 순서대로 연결한다

#### 1. 먼저 encoding과 encryption을 분리한다

다음 문자열이 있다고 하자.

```text
hello
```

이 문자열을 컴퓨터가 저장하거나 전송하려면 어떤 바이트로 표현할지 정해야 한다.

TRACK 01에서 UTF-8을 배웠다.

이처럼 정보를 정해진 규칙에 따라 다른 표현으로 바꾸는 것을 **encoding**이라고 부른다.

예:

```text
문자 → UTF-8 bytes
binary → Base64 text
```

Base64 예를 보자.

```text
hello
↓ Base64
 aGVsbG8=
```

겉으로는 알아보기 어렵지만 보안 장벽이 아니다.

누구나 규칙을 알면 다시 되돌릴 수 있다.

그래서:

```text
Base64로 비밀번호 저장
```

은 비밀번호 보호가 아니다.

중요한 구분:

```text
encoding
→ 표현 방식을 바꾼다.

 encryption
→ key 없이는 내용을 읽기 어렵게 보호한다.
```

#### 2. hash는 원본을 숨기기 위한 암호화와도 다르다

파일 하나가 있다고 하자.

```text
myapp.apk
```

다운로드한 파일이 공식 파일과 정확히 같은지 확인하고 싶다.

파일 전체를 사람 눈으로 비교하기는 어렵다.

그래서 파일에서 짧은 대표값을 계산한다.

```text
파일 bytes
↓ hash function
긴 고정 길이 값
```

암호학적 **hash function**은 임의 길이 입력에서 고정 길이의 hash 값을 만든다.

대표적인 예로 SHA-256이 있다.

```text
hello
↓ SHA-256
2cf24dba5f...
```

같은 bytes를 넣으면 같은 hash가 나온다.

파일이 조금이라도 바뀌면 보통 매우 다른 hash가 나온다.

#### 3. hash는 `되돌려 푸는 암호`가 아니다

초보자는 종종 이렇게 생각한다.

```text
원문 → hash
hash → 복호화 → 원문
```

하지만 일반적인 cryptographic hash에는 `복호화` 절차가 없다.

암호화는 key가 있으면 원문을 되찾도록 설계한다.

hash는 원본을 되찾기 위한 reversible 변환이 아니다.

정리:

```text
encoding
→ 표현 변경

hash
→ 입력에서 대표값 계산

 encryption
→ key로 보호하고 복호화 가능하게 설계
```

#### 4. hash collision은 왜 이론적으로 가능할까

hash 결과 길이는 정해져 있다.

하지만 입력은 사실상 무한히 많다.

그러면 언젠가는 서로 다른 두 입력이 같은 hash 결과를 가질 수밖에 없다.

이것을 **collision**이라고 부른다.

좋은 암호학적 hash는 공격자가 실제로 충돌을 찾아 악용하기 매우 어렵도록 설계된다.

지금 수학을 깊게 공부할 필요는 없다.

중요한 것은:

> `hash가 같다 = 수학적으로 절대 같은 파일이라는 무한한 증명`이 아니라, 안전한 hash를 올바르게 사용했을 때 매우 강한 동일성 검증 근거가 된다.

는 점이다.

#### 5. APK의 SHA-256은 무엇을 알려 주는가

공식 사이트가 다음 hash를 제공했다고 하자.

```text
공식 APK SHA-256
ABCDEF...
```

내가 받은 파일도 계산한다.

```text
내 파일 SHA-256
ABCDEF...
```

같다면 bytes가 같은 강한 증거가 된다.

하지만 주의할 점이 있다.

공격자가 파일과 공식 사이트의 hash 표시를 **둘 다** 바꿀 수 있다면?

가짜 파일과 가짜 hash를 함께 보여 줄 수 있다.

즉 hash만으로는:

```text
파일이 서로 같은가?
```

는 강하게 비교할 수 있지만:

```text
이 파일을 정말 신뢰하는 제작자가 제공했는가?
```

까지 혼자 증명하지는 못한다.

그 문제에서 **digital signature**가 등장한다.

#### 6. 비밀번호를 원문 그대로 저장하면 왜 위험한가

사용자가 비밀번호를 만든다.

```text
mySecret123!
```

서버 DB에 그대로 저장했다고 하자.

```text
email             password
user@example.com  mySecret123!
```

DB가 유출되는 순간 비밀번호가 그대로 노출된다.

많은 사람은 다른 사이트에서도 비슷한 비밀번호를 재사용한다.

피해가 다른 서비스로 퍼질 수 있다.

그래서 비밀번호는 보통 원문을 다시 읽을 필요가 없도록 설계한다.

로그인 시:

```text
사용자가 입력한 비밀번호
↓ 같은 password hashing 과정
계산된 값
↓
DB에 저장된 password hash와 비교
```

한다.

#### 7. 그런데 왜 그냥 SHA-256 한 번이면 안 될까

SHA-256은 매우 빠르게 계산하도록 만들어졌다.

일반 파일 검증에는 장점이다.

하지만 비밀번호 공격에서는 단점이 된다.

공격자는:

```text
123456
password
qwerty
...
```

수많은 후보를 빠르게 계산해 유출된 hash와 비교할 수 있다.

그래서 비밀번호 저장에는 일부러 계산 비용을 높인 전용 password hashing 도구를 사용한다.

대표적으로:

```text
Argon2
bcrypt
scrypt
```

같은 계열이 있다.

직접 `나만의 암호 함수`를 만들어서는 안 된다.

검증된 라이브러리와 최신 권장 설정을 사용한다.

#### 8. salt는 같은 비밀번호가 같은 결과로 보이는 문제를 줄인다

두 사용자가 같은 비밀번호를 쓴다고 하자.

```text
user A password = hello123
user B password = hello123
```

단순하게 같은 방식으로 hash하면 같은 결과가 나올 수 있다.

그래서 각 사용자에게 무작위 **salt**를 함께 사용한다.

```text
password + random salt
↓
password hash
```

A와 B가 같은 비밀번호를 사용해도 서로 다른 salt 때문에 저장 결과가 달라질 수 있다.

salt는 보통 hash와 함께 저장할 수 있다.

`숨겨야 하는 두 번째 비밀번호`가 아니라 공격자가 미리 계산해 둔 대규모 표를 재사용하기 어렵게 만드는 장치다.

#### 9. encryption은 `읽어야 하지만 아무나 읽으면 안 되는 데이터`에 필요하다

비밀번호는 원문을 다시 읽을 필요가 없다.

하지만 어떤 데이터는 나중에 원문이 필요하다.

예:

```text
사용자가 저장한 민감 메모
일부 개인정보
백업 데이터
```

이때는 암호화가 필요할 수 있다.

암호화는:

```text
원문
+ key
↓
암호문
```

으로 바꾸고:

```text
암호문
+ 올바른 key
↓
원문
```

으로 복호화할 수 있도록 설계한다.

그래서 key 관리가 매우 중요하다.

#### 10. 대칭키 암호는 같은 비밀키를 사용한다

**symmetric encryption**은 같은 비밀 key를 암호화와 복호화에 사용하는 방식이다.

아주 단순화하면:

```text
비밀 key K

평문 + K → 암호문
암호문 + K → 평문
```

대표적으로 AES 계열을 많이 접하게 된다.

장점:

```text
빠르다
큰 데이터 암호화에 적합하다
```

어려운 점:

```text
상대방과 key를 어떻게 안전하게 공유할까?
```

이다.

#### 11. 비대칭키는 public key와 private key를 나눈다

**asymmetric cryptography**에서는 서로 연관된 두 key를 사용한다.

```text
public key
→ 다른 사람에게 공개 가능

private key
→ 소유자만 안전하게 보관
```

이 구조는 암호화뿐 아니라 전자서명과 key 교환에서 매우 중요하다.

초급에서는 수학보다 역할을 먼저 잡는다.

```text
public = 공개해도 되는 쪽
private = 절대 함부로 공개하면 안 되는 쪽
```

#### 12. digital signature는 `내용을 숨기는 기능`이 아니다

전자서명을 암호화와 섞기 쉽다.

전자서명의 핵심 질문은:

```text
이 데이터가 정말 그 사람이 만든 것인가?
중간에서 바뀌지 않았는가?
```

이다.

아주 단순화하면:

```text
제작자
데이터 + private key
↓
signature 생성
```

검증자는:

```text
데이터 + signature + public key
↓
검증
```

한다.

전자서명은 내용을 숨기기 위한 것이 아니다.

공개된 문서에도 서명을 붙일 수 있다.

#### 13. certificate는 public key와 신원을 연결한다

HTTPS 사이트에 접속할 때 브라우저는 서버가 제시한 **certificate(인증서)**를 확인한다.

인증서는 대략 이런 문제를 해결하는 데 도움을 준다.

```text
이 public key가 정말 example.com의 것인가?
```

인증기관(CA) 체인, 도메인, 유효기간 등 여러 정보를 검증한다.

그래서 HTTPS 연결을 매우 단순화하면:

```text
서버가 certificate 제시
↓
브라우저가 신뢰 가능한지 검증
↓
안전한 key 협상
↓
암호화된 HTTP 통신
```

과 연결된다.

TRACK 06의 TLS와 여기의 key·certificate가 이제 이어진다.

#### 14. key를 암호화 코드 안에 박아 넣으면 안 된다

다음은 위험한 예다.

```javascript
const API_KEY = "super-secret-real-key";
```

코드가 GitHub, APK, 로그, 에러 메시지 등으로 노출되면 secret도 함께 노출될 수 있다.

특히 모바일 앱에 포함된 secret은 사용자가 앱 파일을 분석할 수 있기 때문에 `앱 안에 넣었으니 안전`하다고 생각하면 안 된다.

민감한 key는 서버 측 비밀 저장소, 환경 설정, 권한이 제한된 secret 관리 시스템 등 적절한 위치에서 관리해야 한다.

#### 15. 이번 LESSON에서 반드시 구분할 다섯 가지

```text
encoding
→ 표현 바꾸기

hash
→ 입력의 대표값 계산

password hashing
→ 비밀번호 추측 공격을 어렵게 저장

 encryption
→ key로 내용을 숨기고 필요하면 복호화

 digital signature
→ 누가 만들었는지와 변조 여부를 검증하는 데 사용
```

이 다섯 가지를 섞지 않는 것이 핵심이다.

## BLOCK 03 · 웹 공격은 `사용자 데이터가 명령으로 바뀌는 순간`과 `신뢰 경계`에서 많이 시작한다

### LESSON 01 · SQL injection·XSS·CSRF·SSRF·path traversal·command injection·secret·file upload를 실제 위험 코드로 배운다

#### 1. 가장 먼저 `사용자 입력은 데이터다`라는 규칙을 잡는다

사용자가 이름을 입력했다.

```text
민수
```

우리는 이 값을 데이터로 다루고 싶다.

그런데 프로그램이 이 입력을 SQL 문법, HTML 문법, 운영체제 명령처럼 해석하게 만들면 위험이 생긴다.

보안 공격의 많은 종류는 형태는 달라도 비슷한 질문으로 볼 수 있다.

> **외부에서 들어온 데이터가 프로그램의 명령이나 권한으로 해석되는 지점이 있는가?**

#### 2. SQL injection은 데이터를 SQL 문자열에 직접 섞을 때 시작할 수 있다

다음은 나쁜 예다.

```javascript
const sql = "SELECT * FROM users WHERE email = '" + email + "'";
```

정상 입력:

```text
minsu@example.com
```

이면 SQL은 대략:

```sql
SELECT * FROM users WHERE email = 'minsu@example.com'
```

가 된다.

그런데 공격자가 SQL 문법 조각을 입력하면 어떨까?

문자열 결합 때문에 사용자가 넣은 `데이터`가 SQL의 `문법`으로 섞일 수 있다.

이것이 **SQL injection**의 핵심 문제다.

해결의 기본은 데이터를 명령 문자열과 분리하는 것이다.

예:

```javascript
await db.query(
  "SELECT * FROM users WHERE email = $1",
  [email]
);
```

여기서 SQL 구조는 고정되어 있고 `email`은 parameter 값으로 전달된다.

핵심:

```text
나쁜 방향
SQL 문법 + 사용자 문자열 직접 연결

좋은 방향
SQL 문법과 사용자 값을 parameter로 분리
```

#### 3. XSS는 사용자 값이 브라우저에서 실행 가능한 코드가 되는 문제다

게시판 댓글 기능을 생각한다.

사용자가:

```text
안녕하세요
```

라고 썼다.

그런데 앱이 댓글 내용을 그대로 HTML로 넣는다.

```javascript
commentBox.innerHTML = userComment;
```

공격자가 script나 실행 가능한 HTML 조각을 넣으면 브라우저에서 실행될 수 있다.

이를 **XSS(Cross-Site Scripting)**라고 부른다.

핵심 질문:

> `사용자 데이터가 HTML/JavaScript 코드로 해석되는가?`

안전한 방향은 상황에 따라 textContent처럼 텍스트로 넣거나, 검증된 escaping/sanitization 도구와 프레임워크 안전 기본값을 사용하는 것이다.

```javascript
commentBox.textContent = userComment;
```

처럼 `이 값은 코드가 아니라 글자`라고 처리하는 것이 한 예다.

#### 4. SQL injection과 XSS는 공격 위치는 다르지만 공통 생각이 있다

```text
SQL injection
사용자 데이터 → SQL 명령 문법으로 해석

XSS
사용자 데이터 → HTML/JavaScript 실행 코드로 해석
```

공통:

```text
데이터와 명령의 경계가 무너짐
```

그래서 외부 입력을 다룰 때는:

```text
이 값은 어디에서 왔나?
어떤 parser가 읽나?
단순 데이터로 처리되나?
명령 문법으로 해석될 가능성이 있나?
```

를 확인한다.

#### 5. CSRF는 `사용자가 이미 로그인한 상태`를 악용한다

사용자가 은행 사이트에 로그인해 있다.

브라우저는 로그인 cookie를 자동으로 보낼 수 있다.

공격자가 다른 사이트에서 사용자의 브라우저를 이용해 은행에 원치 않는 요청을 보내게 만들면 문제가 생길 수 있다.

이런 종류의 공격을 **CSRF(Cross-Site Request Forgery)**라고 부른다.

핵심은:

```text
공격자가 비밀번호를 반드시 알 필요는 없다.
사용자의 브라우저가 이미 인증된 상태를 이용할 수 있다.
```

방어는 cookie의 SameSite 설정, CSRF token, 요청 출처 검증 등 애플리케이션 구조에 따라 선택한다.

#### 6. CORS와 CSRF는 같은 것이 아니다

TRACK 06에서 CORS를 배웠다.

CORS는 브라우저가 다른 origin의 응답을 JavaScript가 읽을 수 있는지와 관련된 정책이다.

CSRF는 인증된 브라우저를 이용해 원치 않는 요청을 보내게 하는 공격 문제다.

```text
CORS
→ 다른 origin 응답 접근 정책

CSRF
→ 사용자의 인증 상태를 악용한 원치 않는 요청
```

CORS를 설정했다고 CSRF가 자동 해결되는 것은 아니다.

#### 7. command injection은 사용자 값이 OS 명령이 되는 문제다

서버가 사용자가 준 파일명을 shell 명령에 직접 붙인다고 하자.

```javascript
exec("convert " + filename + " output.png");
```

사용자가 특별한 shell 문법을 넣으면 원하지 않는 명령이 실행될 수 있다.

이것이 **command injection** 위험이다.

가능하면 shell 문자열 결합을 피하고, 안전한 API를 사용하며, 허용할 입력을 강하게 제한한다.

#### 8. path traversal은 사용자가 서버의 다른 파일까지 올라가는 문제다

다운로드 API:

```text
/download?file=report.pdf
```

서버가 단순히:

```text
/uploads/ + 사용자입력
```

으로 경로를 만든다고 하자.

공격자가 `../` 같은 경로 이동 표현을 넣어 상위 폴더의 파일을 읽으려 할 수 있다.

이런 문제를 **path traversal**이라고 부른다.

방어 생각:

```text
사용자 입력을 실제 파일 경로로 직접 사용하지 않기
허용된 파일 ID를 DB에서 실제 경로로 매핑하기
최종 경로가 허용된 디렉터리 안인지 확인하기
```

#### 9. SSRF는 서버를 대신 요청 보내는 도구로 악용하는 문제다

이미지 URL을 받아 서버가 대신 다운로드한다고 하자.

```text
POST /fetch-image
url = https://example.com/a.png
```

서버가 사용자가 준 URL을 그대로 요청한다면 공격자는:

```text
내부 관리 서버
클라우드 메타데이터 주소
localhost 서비스
```

같이 외부에서 직접 접근하기 어려운 주소를 서버에게 요청하게 만들 수 있다.

이를 **SSRF(Server-Side Request Forgery)**라고 부른다.

그래서 서버가 외부 URL을 대신 요청하는 기능은:

```text
허용 protocol
허용 domain
redirect 처리
내부 IP 차단
응답 크기 제한
```

등을 신중히 검토한다.

#### 10. secret은 source code와 log에 남기지 않는다

다음 값들은 secret이 될 수 있다.

```text
DB password
API key
access token
private key
webhook secret
```

위험한 코드:

```javascript
const DB_PASSWORD = "real-production-password";
```

이 코드가 Git에 들어가면 기록에 오래 남을 수 있다.

나중에 줄을 삭제해도 과거 commit에 남아 있을 수 있다.

또 이런 로그도 위험하다.

```javascript
console.log(process.env);
```

환경변수 전체에 secret이 들어 있다면 로그 시스템으로 복사될 수 있다.

원칙:

```text
secret은 source에 넣지 않는다.
로그에 찍지 않는다.
클라이언트 앱에 비밀값을 넣고 안전하다고 믿지 않는다.
필요한 곳에만 최소 권한으로 제공한다.
노출되면 즉시 폐기/회전한다.
```

#### 11. 파일 업로드는 확장자 하나만 검사하면 부족하다

사용자가 `photo.jpg`를 업로드한다.

파일 이름 끝이 `.jpg`라고 실제 JPEG 이미지라고 믿을 수 있을까?

파일 이름은 사용자가 바꿀 수 있다.

```text
malware.exe
→
photo.jpg
```

처럼 이름만 바꿀 수 있다.

그래서 파일 업로드에서는 여러 층을 함께 본다.

```text
파일 크기 제한
허용 확장자
Content-Type/MIME 확인
실제 파일 signature/magic bytes 확인
파일 이름 새로 생성
사용자 입력 경로 제거
웹 루트 밖 안전한 위치 저장
실행 권한 제거
필요하면 이미지 재인코딩/악성코드 검사
```

모든 시스템에 모든 조치가 필요한 것은 아니지만 `확장자 하나만 보면 된다`는 생각은 위험하다.

#### 12. 사용자가 올린 파일 이름을 그대로 저장하면 경로와 충돌 문제가 생긴다

두 사용자가 모두:

```text
profile.jpg
```

를 올렸다고 하자.

서버가 같은 이름을 사용하면 덮어쓸 수 있다.

또 파일 이름에 특수문자나 경로 표현이 들어갈 수도 있다.

따라서 서버가 안전한 새로운 ID나 파일명을 만들어 저장하고 원래 파일명은 메타데이터로 따로 관리하는 방식이 일반적이다.

#### 13. 보안 오류를 사용자에게 너무 자세히 보여주지 않는다

DB query가 실패했다고 다음을 그대로 사용자에게 보내면:

```text
PostgreSQL error
host=10.0.0.15
user=admin
query=SELECT ...
stack trace=/srv/app/...
```

내부 구조 정보가 노출될 수 있다.

외부 응답:

```json
{
  "code": "INTERNAL_ERROR",
  "message": "요청을 처리하지 못했습니다"
}
```

내부 로그:

```text
추적에 필요한 상세 오류
단, secret은 제외
```

처럼 외부 정보와 내부 진단 정보를 구분한다.

#### 14. dependency도 공격 표면이 된다

내 코드가 안전해도 사용하는 library에 취약점이 있을 수 있다.

그래서:

```text
필요 없는 dependency 줄이기
출처가 불분명한 package 피하기
버전 업데이트 확인
취약점 공지 확인
lock file 관리
```

같은 공급망 관리도 보안의 일부다.

#### 15. 보안은 한 줄짜리 방어 함수가 아니라 여러 층이다

예를 들어 로그인 기능을 보호한다고 하자.

```text
TLS
↓
입력 validation
↓
password hashing
↓
rate limit
↓
안전한 session/token
↓
authorization
↓
로그와 이상행동 탐지
↓
secret 관리
```

한 가지 기술만 사용했다고 `보안 완료`라고 할 수 없다.

여러 층의 방어를 두는 생각을 **defense in depth**라고 부른다.

#### 16. 실제 코드 검토 순서

AI가 새 API 코드를 만들었다면 다음 순서로 본다.

```text
1. 외부 입력은 어디에서 들어오나?
2. validation은 어디서 하나?
3. 인증은 필요한가?
4. 권한은 어디서 확인하나?
5. SQL/HTML/shell/path에 사용자 값이 직접 들어가나?
6. secret이 코드나 로그에 보이나?
7. 업로드 파일은 어떤 제한이 있나?
8. 오류 응답이 내부 정보를 노출하나?
9. 외부 URL 요청 기능이 있나?
10. 실패했을 때 안전한 상태로 남나?
```

이 체크는 특정 프레임워크가 바뀌어도 계속 사용할 수 있다.

#### 17. TRACK 09 완료 기준

다음을 자기 말과 코드 예제로 설명할 수 있어야 한다.

- 자산, 위협, 취약점, risk를 구분한다.
- 기밀성·무결성·가용성을 사례로 구분한다.
- 인증과 권한을 구분한다.
- trust boundary와 least privilege를 설명한다.
- encoding, hash, encryption을 서로 다른 개념으로 설명한다.
- password를 원문으로 저장하면 안 되는 이유를 말한다.
- salt와 password hashing의 목적을 설명한다.
- symmetric/asymmetric cryptography의 큰 차이를 말한다.
- digital signature와 encryption의 목적을 구분한다.
- certificate와 TLS의 연결을 설명한다.
- parameterized query가 SQL injection 위험을 줄이는 이유를 설명한다.
- XSS에서 `데이터가 코드로 해석된다`는 문제를 설명한다.
- CSRF와 CORS를 구분한다.
- SSRF, path traversal, command injection의 신뢰 경계를 찾는다.
- secret을 source와 log에 넣지 않는 이유를 설명한다.
- 파일 업로드에서 확장자 하나만 검사하면 부족한 이유를 설명한다.

### TRACK 프로젝트 · 안전한 프로필 API 검토

다음 기능을 설계한다.

```text
로그인 사용자만 프로필 수정 가능
닉네임 변경
프로필 사진 업로드
기존 사진 삭제
```

단계별로 적는다.

```text
1. 어떤 자산을 보호할지 적는다.
2. 어떤 입력이 신뢰 경계를 통과하는지 표시한다.
3. 인증이 필요한 지점을 표시한다.
4. 다른 사용자 프로필을 수정하지 못하도록 권한 규칙을 적는다.
5. nickname을 DB에 저장할 때 parameterized query를 사용한다.
6. 이미지 크기와 형식을 검사한다.
7. 원본 파일명을 저장 경로로 직접 사용하지 않는다.
8. 서버가 새로운 안전한 파일 ID를 만든다.
9. secret은 코드에 넣지 않는다.
10. 오류 응답과 내부 로그를 분리한다.
11. 각 방어를 제거했을 때 어떤 공격이 가능한지 설명한다.
```

정답은 `보안 library를 하나 설치했다`가 아니다.

**어디가 경계이고, 어떤 데이터가 들어오며, 어떤 권한이 필요한지 단계별로 설명할 수 있어야 통과다.**
