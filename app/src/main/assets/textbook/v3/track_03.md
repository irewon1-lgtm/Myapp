# TRACK 03 · 자료구조와 알고리즘

TRACK 02에서는 값을 저장하고 조건·반복·함수로 작은 프로그램을 만드는 법을 배웠다.

이제 질문을 한 단계 바꾼다.

> 데이터가 10개가 아니라 10만 개라면 어떻게 저장하고 찾을까?

> 같은 정답을 내는 두 코드 중 어느 쪽이 더 적은 일을 할까?

이 TRACK은 `array`, `node`, `stack`, `tree`, `Big-O` 같은 단어를 따로 외우지 않는다.

먼저 실제 문제를 보고, 왜 그런 구조가 필요해졌는지를 이해한 다음 이름을 붙인다.

## BLOCK 01 · 데이터를 어떻게 담을지 선택하는 법

### LESSON 01 · array·dynamic array·linked list·node를 하나의 비교 이야기로 이해한다

#### 1. 자료구조는 어려운 이름의 모음이 아니다

학생 3명의 점수를 저장한다고 하자.

```python
scores = [80, 90, 100]
```

데이터가 적으면 어떤 방식으로 저장해도 큰 차이가 없어 보인다.

하지만 프로그램이 해야 할 일이 달라지면 저장 방법도 중요해진다.

예:

```text
500번째 값을 매우 자주 읽어야 한다.
중간에 값을 계속 끼워 넣어야 한다.
중복을 허용하면 안 된다.
가장 먼저 들어온 작업부터 처리해야 한다.
이름으로 매우 자주 찾아야 한다.
부모-자식 관계를 표현해야 한다.
친구 관계처럼 복잡한 연결을 표현해야 한다.
```

이 문제를 모두 같은 구조 하나로 가장 잘 처리하기는 어렵다.

데이터를 저장하고 사용하기 좋게 조직한 방식을 **자료구조(data structure)**라고 부른다.

핵심은 이름 암기가 아니다.

> 어떤 작업을 자주 할 것인가를 보고 적합한 저장 구조를 고른다.

#### 2. array는 순서와 위치가 중요한 구조다

가장 익숙한 모양부터 본다.

```text
위치     0    1     2     3
값      80   90   100    70
```

이런 식으로 순서가 있는 값을 다루는 대표적인 구조가 **array(배열)**다.

Python의 `list`는 내부 구현이 언어의 전형적인 고정 배열과 완전히 같지는 않지만 초급에서는 `순서 있는 여러 값을 index로 다룬다`는 감각을 연결해 볼 수 있다.

```python
scores = [80, 90, 100, 70]
print(scores[2])
```

결과:

```text
100
```

왜 빠를 수 있을까?

배열 계열 구조는 `몇 번째 위치인지`를 이용해 원하는 위치를 계산하기 좋다.

그래서 이미 index를 알고 있을 때 특정 위치 접근이 매우 빠른 것이 큰 장점이다.

#### 3. 중간에 끼워 넣으면 무슨 일이 생길까

다음 값이 있다고 하자.

```text
[A][B][C][D]
```

B와 C 사이에 X를 넣는다.

```text
[A][B][X][C][D]
```

연속된 위치를 유지해야 하는 배열 구조에서는 뒤의 값들이 자리를 옮겨야 할 수 있다.

```text
C 이동
D 이동
X 삽입
```

데이터가 수백만 개라면 이런 이동 비용이 커질 수 있다.

여기서 다른 저장 방식이 왜 필요한지 감이 생긴다.

#### 4. 크기가 늘어나는 배열은 어떻게 가능할까

Python list, Java의 ArrayList, JavaScript Array 같은 구조는 사용하면서 크기를 늘릴 수 있다.

이런 구조를 **동적 배열(dynamic array)**의 관점에서 이해할 수 있다.

처음부터 무한한 공간이 준비돼 있는 것은 아니다.

내부 공간이 꽉 차면 더 큰 공간을 마련하고 기존 값을 옮기는 식의 작업이 발생할 수 있다.

그렇다고 값을 하나 추가할 때마다 전체를 매번 복사하는 것은 아니다.

그래서 뒤에 값을 추가하는 작업은 많은 경우 평균적으로 빠르게 동작한다.

이 `가끔 비싼 작업이 있어도 여러 작업 전체 평균으로 보면 저렴하다`는 생각을 뒤에서 **amortized cost**라고 다시 만난다.

#### 5. 이제 연결 리스트가 왜 나오는지 문제부터 본다

다음 요구를 생각한다.

```text
현재 항목 바로 뒤에 새 항목을 자주 끼워 넣고 싶다.
```

배열처럼 값들을 꼭 연속된 위치에 놓지 않고, 각 데이터 조각이 `다음 데이터가 어디 있는지` 알려 주게 만들면 어떨까?

```text
[A | 다음] → [B | 다음] → [C | 끝]
```

이런 연결 구조를 **연결 리스트(linked list)**라고 부른다.

그리고 각각의 데이터 조각을 **노드(node)**라고 부른다.

#### 6. node를 단어 한 줄로 끝내지 않는다

노드 하나를 상자라고 생각한다.

```text
┌──────────────┐
│ 값: 10       │
│ 다음: ???    │
└──────────────┘
```

여기에는 크게 두 정보가 있다.

```text
내가 실제로 보관할 값
+
다음 노드가 어디 있는지 알려 주는 연결 정보
```

세 개를 만들면:

```text
[값 10 | 다음] → [값 20 | 다음] → [값 30 | 없음]
```

마지막의 `없음`은 `여기서 끝`이라는 뜻이다.

이제 첫 노드만 알고 있어도 다음 연결을 계속 따라갈 수 있다.

#### 7. 코드로 node를 처음 만든다

Python으로 아주 단순하게 표현한다.

```python
class Node:
    def __init__(self, value):
        self.value = value
        self.next = None
```

처음 보는 class 문법 때문에 핵심을 놓치지 않는다.

사람말로만 읽는다.

```text
Node라는 데이터 모양을 만든다.
새 Node를 만들 때 value를 받는다.
Node는 value를 기억한다.
처음에는 다음 Node가 없으므로 next를 None으로 둔다.
```

세 노드:

```python
a = Node(10)
b = Node(20)
c = Node(30)
```

아직은 연결되지 않았다.

```text
a [10 | None]
b [20 | None]
c [30 | None]
```

연결한다.

```python
a.next = b
b.next = c
```

결과:

```text
a
↓
[10 | next] → [20 | next] → [30 | None]
               ↑              ↑
               b              c
```

#### 8. 첫 노드부터 끝까지 따라가 본다

```python
current = a

while current is not None:
    print(current.value)
    current = current.next
```

결과:

```text
10
20
30
```

실행을 손으로 따라간다.

```text
current = a
→ 10 출력
→ a.next인 b로 이동

current = b
→ 20 출력
→ b.next인 c로 이동

current = c
→ 30 출력
→ c.next인 None으로 이동

current = None
→ while 조건 종료
```

이게 연결 구조의 핵심이다.

#### 9. 중간에 X를 넣는다

현재:

```text
A → B → C
```

목표:

```text
A → B → X → C
```

B가 원래 가리키던 C를 잃으면 안 된다.

그래서 순서를 생각한다.

```text
1. X가 먼저 C를 가리키게 한다.
2. B가 X를 가리키게 한다.
```

코드:

```python
x = Node("X")
x.next = b.next
b.next = x
```

이제:

```text
B → X → C
```

가 된다.

왜 `b.next = x`를 먼저 하지 않았는지도 설명할 수 있어야 한다.

기존 연결 정보를 덮어써 C를 잃을 위험이 있기 때문이다.

#### 10. 배열과 연결 리스트를 공정하게 비교한다

배열:

```text
장점
- index를 알면 특정 위치 접근이 매우 빠름
- 순서대로 읽기 좋음

단점 후보
- 중간 삽입/삭제에서 많은 값 이동이 생길 수 있음
```

연결 리스트:

```text
장점
- 삽입 위치의 노드를 이미 알고 있다면 주변 연결 변경으로 삽입 가능

단점
- 500번째 노드를 바로 계산해 찾아가기 어렵고 앞에서부터 따라가야 할 수 있음
- 각 노드에 연결 정보도 저장해야 함
```

여기서 중요한 문장:

> 연결 리스트의 삽입이 언제나 무조건 빠른 것이 아니다. 삽입할 노드를 찾는 비용은 별도로 들 수 있다.

#### 11. 단일 연결과 이중 연결

지금 구조는 다음 노드만 안다.

```text
A → B → C
```

이것을 **단일 연결 리스트(singly linked list)**라고 부른다.

앞과 뒤를 모두 기억하면:

```text
A ⇄ B ⇄ C
```

**이중 연결 리스트(doubly linked list)**라고 부른다.

뒤로 이동하기 쉬워지지만 각 노드가 더 많은 연결 정보를 보관해야 한다.

#### 12. node는 연결 리스트에서만 쓰는 말이 아니다

뒤에서 트리:

```text
부모 node
├─ 자식 node
└─ 자식 node
```

그래프:

```text
A node ─ B node
   \      /
    C node
```

같은 구조를 본다.

웹의 DOM에서도 요소가 tree의 node로 표현된다.

따라서 node를 `연결 리스트 단어`로만 외우지 않는다.

> node = 더 큰 연결 구조를 구성하는 데이터 한 조각

이라는 감각을 만든다.

## BLOCK 02 · 넣고 빼고 찾는 순서가 다른 자료구조들

### LESSON 01 · stack·queue·deque·set·map·hash table을 실제 문제로 구분한다

#### 1. 같은 여러 값이라도 꺼내는 규칙이 다를 수 있다

프린터 작업, 실행 취소, 회원 ID 목록, 전화번호부는 모두 여러 데이터를 다룬다.

하지만 필요한 동작은 다르다.

```text
가장 마지막 작업을 먼저 되돌리고 싶다.
가장 먼저 들어온 작업부터 처리하고 싶다.
중복을 막고 싶다.
이름으로 값을 빠르게 찾고 싶다.
```

그래서 서로 다른 자료구조가 나온다.

#### 2. stack은 마지막에 넣은 것을 먼저 꺼낸다

접시를 쌓는 모습을 생각한다.

```text
A 접시 올림
B 접시 올림
C 접시 올림
```

위에서 꺼내면:

```text
C
B
A
```

순서다.

이 구조가 **stack(스택)**이다.

`Last In, First Out`, 줄여서 **LIFO**라고 부른다.

```text
마지막에 들어온 것
→ 먼저 나감
```

Python list로 간단히 흉내 낸다.

```python
stack = []
stack.append("A")
stack.append("B")
stack.append("C")

print(stack.pop())
```

결과:

```text
C
```

#### 3. stack은 어디에 쓰일까

브라우저나 편집기의 실행 취소를 생각해 보자.

```text
글자 입력 A
글자 입력 B
글자 입력 C
```

가장 최근 행동 C부터 되돌리는 것이 자연스럽다.

또 함수 호출을 추적하는 call stack, 괄호 검사, DFS 같은 곳에서 stack 사고를 다시 만난다.

#### 4. queue는 먼저 들어온 것을 먼저 처리한다

은행 번호표 줄을 생각한다.

먼저 온 사람이 먼저 처리된다.

```text
A 들어옴
B 들어옴
C 들어옴

처리 순서
A → B → C
```

이것이 **queue(큐)**다.

`First In, First Out`, **FIFO**라고 부른다.

작업 대기열, 메시지 처리, BFS에서 queue 구조를 사용한다.

#### 5. list 앞에서 계속 삭제하면 비용이 생길 수 있다

Python list를 queue처럼 사용해서 맨 앞 항목을 계속 제거하면 뒤의 요소 위치를 옮기는 비용이 생길 수 있다.

이럴 때 Python에는 `collections.deque`가 있다.

```python
from collections import deque

queue = deque()
queue.append("A")
queue.append("B")
print(queue.popleft())
```

결과:

```text
A
```

#### 6. deque는 양쪽에서 넣고 뺄 수 있다

**deque(double-ended queue)**는 앞과 뒤 양쪽에서 값을 넣고 뺄 수 있는 구조다.

```text
앞 ← [A][B][C] → 뒤
```

```python
from collections import deque

d = deque(["B"])
d.appendleft("A")
d.append("C")
print(d)
```

#### 7. set은 중복 없는 값과 포함 확인에 유용하다

방문한 사용자 ID를 저장한다.

```python
visited = {10, 20, 30}
```

다시 20을 추가해도 중복 항목을 별도로 두지 않는다.

```python
visited.add(20)
```

또:

```python
if 20 in visited:
    print("이미 방문")
```

처럼 포함 여부를 확인할 수 있다.

그래프 탐색에서 `같은 node를 무한히 다시 방문하지 않기` 위해 자주 사용한다.

#### 8. key와 value가 필요한 상황

학생 번호로 이름을 찾는다고 하자.

```text
1001 → 민수
1002 → 지수
```

왼쪽처럼 찾는 기준을 **key**, 오른쪽에 연결된 정보를 **value**라고 부른다.

Python `dict`:

```python
students = {
    1001: "민수",
    1002: "지수"
}

print(students[1002])
```

결과:

```text
지수
```

#### 9. map은 key로 value를 찾는 추상적인 구조다

언어마다 이름이 다르게 보일 수 있다.

```text
Python dict
Java HashMap
JavaScript Map
```

모두 세부 구현은 다를 수 있지만 `key → value` 연결로 데이터를 찾는 생각을 공유한다.

#### 10. key를 빠르게 찾으려면 hash가 등장한다

전화번호부가 수백만 건이라면 key를 하나씩 처음부터 비교하는 것보다 더 빠른 방법이 필요하다.

**hash function(해시 함수)**은 key를 계산해 해시값을 만든다.

아주 단순한 그림:

```text
"minsu"
↓ hash 계산
42
↓
42와 관련된 저장 위치 확인
```

이 생각을 이용하는 대표 자료구조가 **hash table(해시 테이블)**이다.

평균적인 상황에서 key 기반 저장·검색·삭제를 빠르게 할 수 있다.

#### 11. hash는 마법의 완벽한 주소가 아니다

서로 다른 key가 같은 위치를 원할 수 있다.

```text
A → 5
B → 5
```

이것을 **hash collision(해시 충돌)**이라고 부른다.

충돌이 생겼다고 hash table이 바로 망가지는 것은 아니다.

충돌을 처리하는 전략이 있다.

대표 아이디어:

```text
chaining
→ 같은 위치에 여러 항목을 연결해 관리

open addressing
→ 다른 비어 있는 위치를 찾아 저장
```

세부는 구현마다 다르다.

#### 12. 자료구조용 hash와 보안용 hash는 목적이 다르다

`hash`라는 단어가 같아서 초보자가 자주 섞는다.

자료구조의 hash:

```text
목표
key를 빠르게 저장/찾을 위치 계산
```

암호학적 hash:

```text
목표
변조 확인, 공격에 강한 성질 등
```

요구 조건이 다르다.

보안 TRACK에서 SHA-256 같은 암호학적 hash를 별도로 배운다.

#### 13. 어떤 구조를 고를까

```text
가장 최근 항목을 먼저 처리
→ stack

먼저 들어온 항목부터 처리
→ queue

양쪽에서 넣고 빼기
→ deque

중복 제거/포함 확인
→ set

key로 value 찾기
→ map/dict/hash table 계열
```

이름을 외우기보다 문제 문장을 보고 선택한다.

#### 14. 책을 덮고 확인한다

1. stack과 queue의 꺼내는 순서를 각각 설명하라.
2. undo 기능에 stack이 어울리는 이유는 무엇인가?
3. queue와 deque의 차이는 무엇인가?
4. set은 어떤 문제에 유용한가?
5. key와 value를 전화번호부 예로 설명하라.
6. hash collision이 무엇인지 그림으로 설명하라.

## BLOCK 03 · 부모와 자식이 있는 계층 구조

### LESSON 01 · tree·binary tree·BST·balanced tree·heap·priority queue·trie를 한 계열로 이해한다

#### 1. 폴더 구조는 일렬로만 설명하기 어렵다

다음 폴더가 있다고 하자.

```text
사진
├─ 가족
│  ├─ 2025
│  └─ 2026
└─ 여행
   ├─ 제주
   └─ 부산
```

이 구조는 단순한 한 줄 목록보다 `부모-자식` 관계가 중요하다.

이런 계층 관계를 표현하는 대표 자료구조가 **tree(트리)**다.

#### 2. tree 용어를 그림으로 붙인다

```text
        A
       / \
      B   C
     / \
    D   E
```

여기서:

```text
A = root, 가장 위 node
A는 B,C의 parent
B,C는 A의 child
D,E = child가 없는 leaf
```

`root`, `parent`, `child`, `leaf`를 따로 암기하지 않고 그림에 붙인다.

#### 3. binary tree는 자식 수에 대한 규칙이다

각 node가 최대 두 개의 자식을 가지는 tree를 **binary tree(이진 트리)**라고 부른다.

```text
    A
   / \
  B   C
```

중요한 오해:

> binary tree라고 해서 값이 자동으로 정렬된 것은 아니다.

`자식이 최대 두 개`라는 구조 조건이다.

#### 4. Binary Search Tree는 값 배치 규칙이 추가된다

**BST(Binary Search Tree, 이진 탐색 트리)**는 일반적으로:

```text
왼쪽 서브트리 = 현재 값보다 작은 값
오른쪽 서브트리 = 현재 값보다 큰 값
```

같은 검색 규칙을 둔다.

예:

```text
      8
     / \
    3   10
   / \    \
  1   6    14
```

8보다 작은 값은 왼쪽, 큰 값은 오른쪽 방향으로 찾는다.

#### 5. BST가 항상 빠른 것은 아니다

값을 1,2,3,4 순서로 넣어 치우치면:

```text
1
 \
  2
   \
    3
     \
      4
```

거의 연결 리스트처럼 길어진다.

찾을 때 절반씩 줄이는 장점을 잃는다.

그래서 **tree height(높이)**가 중요하다.

#### 6. balanced tree는 너무 한쪽으로 늘어지는 문제를 줄인다

AVL tree, Red-Black tree 같은 구조는 균형을 유지해 높이가 지나치게 커지는 것을 막으려는 대표적인 tree다.

지금 회전 알고리즘을 외울 필요는 없다.

목적만 이해한다.

> 검색 tree가 한쪽으로 길게 늘어져 성능이 나빠지는 것을 줄인다.

#### 7. heap은 완전히 정렬된 tree가 아니다

가장 작은 값 또는 가장 큰 값을 빠르게 꺼내야 하는 문제가 있다.

예: 병원 대기 환자 중 가장 위급한 환자를 먼저 처리한다.

**heap**은 이런 최솟값/최댓값 우선 처리에 유용한 tree 기반 구조다.

min-heap에서는 부모가 자식보다 작거나 같은 규칙을 유지한다.

하지만 전체가 완전히 오름차순으로 정렬된 것은 아니다.

핵심:

```text
root에서 가장 중요한 최소/최대 값을 빠르게 확인
```

이다.

#### 8. priority queue는 우선순위로 꺼낸다

일반 queue:

```text
먼저 들어온 사람 먼저
```

**priority queue(우선순위 큐)**:

```text
우선순위가 가장 높은 항목 먼저
```

응급실, 작업 스케줄링 등이 예다.

heap은 priority queue를 구현하는 대표적인 방법 중 하나다.

#### 9. trie는 문자열 앞부분을 공유한다

검색 자동완성을 생각한다.

```text
car
cat
can
```

세 단어는 `ca`를 공유한다.

**trie(트라이)**는 문자열의 글자 경로를 tree처럼 저장한다.

```text
c
└─ a
   ├─ r
   ├─ t
   └─ n
```

접두사 검색, 자동완성 같은 문제에 사용할 수 있다.

#### 10. 같은 tree라도 목적이 다르다

```text
일반 tree
→ 계층 관계 표현

binary tree
→ 자식 최대 두 개

BST
→ 검색을 위한 값 배치 규칙 추가

balanced BST
→ 높이가 너무 커지지 않게 균형 유지

heap
→ 최소/최대 우선 처리

trie
→ 문자열 접두 경로 공유
```

`tree라는 이름이 붙었다`는 이유만으로 같은 용도라고 생각하면 안 된다.

#### 11. 실제 앱에서 tree를 만나는 곳

```text
파일/폴더 구조
웹 DOM 구조
조직도
메뉴 계층
댓글의 답글 구조
카테고리 트리
```

등에서 부모-자식 사고가 반복된다.

#### 12. 책을 덮고 확인한다

1. root, parent, child, leaf를 하나의 그림으로 설명하라.
2. binary tree와 BST는 무엇이 다른가?
3. BST가 한쪽으로 치우치면 왜 느려질 수 있는가?
4. heap과 완전히 정렬된 배열은 어떻게 다른가?
5. priority queue는 일반 queue와 무엇이 다른가?
6. trie가 자동완성에 유용한 이유는 무엇인가?

## BLOCK 04 · 친구 관계와 도로처럼 복잡하게 연결된 데이터

### LESSON 01 · graph·vertex·edge·방향·인접 리스트·인접 행렬을 직접 그린다

#### 1. tree로 표현하기 어려운 관계가 있다

친구 관계를 보자.

```text
A는 B와 친구
A는 C와 친구
B는 D와 친구
C도 D와 친구
D는 A와도 연결될 수 있음
```

부모 하나 아래 자식들처럼 단순한 계층이 아니다.

서로 여러 방향으로 복잡하게 연결된다.

이런 관계를 표현하는 대표 자료구조가 **graph(그래프)**다.

#### 2. graph의 대상 하나가 vertex/node다

```text
A
B
C
D
```

각 대상을 **vertex(정점)**라고 부른다.

문맥에 따라 node라고도 한다.

두 대상을 연결하는 관계를 **edge(간선)**라고 부른다.

```text
A ─ B
```

에서 A,B는 vertex, 가운데 선은 edge다.

#### 3. 방향이 있는 연결과 없는 연결

인스타그램 `팔로우`는 방향이 있을 수 있다.

```text
A → B
```

A가 B를 팔로우하지만 B가 A를 팔로우한다는 뜻은 아니다.

이런 graph를 **directed graph(방향 그래프)**라고 부른다.

반대로 단순한 `서로 친구` 관계를 양방향으로 본다면:

```text
A — B
```

**undirected graph(무방향 그래프)**로 표현할 수 있다.

#### 4. edge에 비용을 붙일 수도 있다

도로:

```text
서울 ─ 40km ─ 수원
```

처럼 연결마다 거리나 시간 같은 값이 있을 수 있다.

이런 값을 **weight(가중치)**라고 부른다.

```text
A --5--> B
```

`A에서 B까지 비용 5` 같은 의미를 표현할 수 있다.

#### 5. 코드에는 graph를 어떻게 저장할까 — adjacency list

각 node마다 연결된 이웃 목록을 저장한다.

```python
graph = {
    "A": ["B", "C"],
    "B": ["A", "D"],
    "C": ["A", "D"],
    "D": ["B", "C"]
}
```

이 방식이 **adjacency list(인접 리스트)**다.

사람말:

```text
A의 이웃은 B,C
B의 이웃은 A,D
...
```

#### 6. 표로 연결 여부를 저장할 수도 있다 — adjacency matrix

node가 A,B,C라면:

```text
    A B C
A   0 1 1
B   1 0 0
C   1 0 0
```

처럼 두 node가 연결됐는지 표 형태로 저장할 수 있다.

이것을 **adjacency matrix(인접 행렬)**라고 부른다.

#### 7. 둘 중 무엇이 무조건 좋은 것은 아니다

연결이 거의 없는 큰 graph를 생각한다.

사람 100만 명이 있는데 각 사람은 평균 10명과만 연결돼 있다.

인접 행렬은 100만×100만 칸을 생각해야 하므로 매우 많은 공간이 필요하다.

인접 리스트는 실제 연결만 저장하기 좋아서 이런 **sparse(희소)** graph에 유리할 수 있다.

반대로 node 수가 작고 서로 거의 모두 연결돼 있으며 `A와 B가 연결됐나?`를 즉시 확인해야 한다면 행렬 방식이 유리한 경우도 있다.

#### 8. tree와 graph의 차이를 같은 데이터로 비교한다

회사 조직도를 생각하면 보통 한 사람은 상위 관리자 하나 아래에 놓이는 계층으로 표현하기 쉽다.

```text
대표
├─ 개발팀장
│  ├─ 개발자 A
│  └─ 개발자 B
└─ 영업팀장
   └─ 영업사원 C
```

이 구조에서는 `부모-자식` 방향이 뚜렷해서 tree가 자연스럽다.

하지만 협업 관계를 표현하려고 하면 상황이 달라진다.

```text
개발자 A ↔ 개발자 B
개발자 A ↔ 영업사원 C
개발자 B ↔ 외부 디자이너 D
영업사원 C ↔ 외부 디자이너 D
```

한 사람이 여러 사람과 동시에 연결되고, 연결이 다시 서로 돌아올 수도 있다.

이때 억지로 parent 하나를 정하면 실제 관계를 잃는다.

그래서 중요한 질문은:

```text
이 데이터는 "누가 누구 아래에 있는가"가 핵심인가?
→ tree 후보

이 데이터는 "누가 누구와 연결되어 있는가"가 핵심인가?
→ graph 후보
```

이다.

자료구조를 고를 때 이름부터 떠올리는 것이 아니라 **현실 관계의 모양을 먼저 본다**.

#### 9. 무방향 graph를 코드로 저장할 때 한쪽만 넣으면 버그가 생긴다

친구 관계 A—B를 저장한다고 하자.

무방향 관계라면 사람말로는:

```text
A의 친구에 B가 있음
B의 친구에도 A가 있음
```

이어야 한다.

그런데 코드를 이렇게 만들었다고 하자.

```python
graph = {
    "A": ["B"],
    "B": []
}
```

A에서 보면 B가 친구인데 B에서 보면 A가 친구가 아니다.

현실 규칙과 저장 구조가 어긋났다.

무방향 graph를 adjacency list로 직접 저장할 때는 보통 양쪽 연결을 함께 기록한다.

```python
graph = {
    "A": ["B"],
    "B": ["A"]
}
```

반대로 팔로우처럼 방향이 있는 관계에서 양쪽을 자동으로 넣으면 또 틀린다.

```text
A가 B를 팔로우
≠
B도 A를 팔로우
```

즉 `directed인지 undirected인지`는 단순한 용어 문제가 아니라 **실제 저장 코드가 달라지는 조건**이다.

#### 10. weight도 실제로는 edge 정보로 저장해야 한다

도로 graph를 생각한다.

단순히:

```python
graph = {
    "서울": ["수원", "인천"]
}
```

만 저장하면 `연결되어 있다`는 사실은 알 수 있지만 거리나 시간은 알 수 없다.

거리까지 필요하면 edge에 정보를 함께 둔다.

예를 들어 아주 단순하게:

```python
graph = {
    "서울": [("수원", 40), ("인천", 35)],
    "수원": [("서울", 40)],
    "인천": [("서울", 35)]
}
```

사람말로 읽으면:

```text
서울에서 수원까지 연결, 비용 40
서울에서 인천까지 연결, 비용 35
```

이다.

실제 지도에서는 weight가 `거리`, `시간`, `통행료`처럼 문제 목적에 따라 달라질 수 있다.

같은 도로라도:

```text
최단 거리 경로
가장 빠른 경로
가장 싼 경로
```

의 답이 서로 다를 수 있다.

그래서 알고리즘을 고르기 전에 **edge의 weight가 무엇을 뜻하는지** 먼저 정해야 한다.

#### 11. adjacency list를 한 단계만 직접 따라가 본다

다음 graph를 사용한다.

```python
graph = {
    "A": ["B", "C"],
    "B": ["A", "D"],
    "C": ["A", "D"],
    "D": ["B", "C"]
}
```

A에서 시작해 `A와 직접 연결된 사람`만 찾는다면:

```python
for neighbor in graph["A"]:
    print(neighbor)
```

결과는:

```text
B
C
```

이다.

여기서는 아직 BFS나 DFS가 필요 없다.

그냥 `A의 이웃 목록`을 한 번 읽었다.

하지만 질문이:

> A에서 연결을 계속 따라가면 D까지 갈 수 있는가?

로 바뀌면 한 단계 이웃만 보는 것으로 부족하다.

```text
A
├─ B
│  └─ D
└─ C
   └─ D
```

처럼 연결을 여러 단계 따라가야 한다.

이때부터 `어떤 순서로 방문할지`, `이미 본 node를 어떻게 기억할지`가 필요해지고 다음 BLOCK의 BFS/DFS로 이어진다.

#### 12. 같은 node를 여러 경로에서 만날 수 있다

위 graph에서 D는 B를 통해서도 갈 수 있고 C를 통해서도 갈 수 있다.

```text
A → B → D
A → C → D
```

D를 처음 방문한 뒤에도 `처음 보는 node인가?`를 확인하지 않으면 D를 여러 번 처리할 수 있다.

처리가 단순 출력이면 큰 문제가 아닌 것처럼 보일 수 있다.

하지만 D를 방문할 때마다:

```text
DB 조회
네트워크 요청
비싼 계산
메시지 전송
```

같은 일을 한다면 중복 방문이 실제 비용이나 버그가 된다.

그래서 graph 탐색에서는 방문 여부가 단순 최적화가 아니라 **중복 처리 방지 규칙**이 되기도 한다.

#### 13. cycle이 있으면 무한히 돌 수 있다

```text
A → B → C → A
```

A에서 시작해 무조건 다음으로만 계속 가면:

```text
A → B → C → A → B → C → ...
```

끝나지 않는다.

그래서 graph 탐색에서는 `이미 방문한 node`를 기억하는 것이 중요하다.

보통 set을 사용한다.

```python
visited = set()
```

간단한 생각은 이렇다.

```text
처음 보는 node
→ visited에 기록하고 처리

이미 visited에 있는 node
→ 다시 깊게 들어가지 않음
```

이 개념이 BFS/DFS에서 바로 이어진다.

#### 14. visited를 잘못 쓰면 중복이 줄지 않을 수도 있다

예를 들어 node를 queue나 stack에 넣을 때는 아무 표시도 하지 않고, 실제로 꺼낸 뒤에만 visited에 표시한다고 하자.

서로 다른 두 경로가 같은 D를 거의 동시에 발견하면:

```text
B가 D 발견 → D를 대기열에 추가
C도 D 발견 → D를 또 대기열에 추가
```

처럼 중복 항목이 들어갈 수 있다.

그래서 BFS에서는 보통 **처음 발견해 queue에 넣는 순간 visited 처리**하는 방식이 자주 쓰인다.

이 세부 순서는 다음 BLOCK에서 실제 코드로 다시 본다.

지금은 다음 한 문장을 이해하면 된다.

> graph에서는 "어디까지 갔는가"뿐 아니라 "이미 무엇을 발견했는가"를 관리해야 한다.

#### 15. 실제로 graph인 것들

```text
도로 지도
지하철 노선
SNS 친구/팔로우
웹페이지 링크
컴퓨터 네트워크
작업 의존 관계
추천 시스템의 사용자-상품 관계
```

각 예에서 vertex와 edge가 무엇인지 직접 붙여 본다.

```text
도로 지도
vertex = 도시/교차로
edge = 도로
weight = 거리 또는 시간

SNS
vertex = 사용자
edge = 친구/팔로우 관계

웹
vertex = 페이지
edge = 링크

작업 의존 관계
vertex = 작업
edge = "이 작업이 먼저 끝나야 함" 관계
```

세상을 graph로 보는 순간 풀 수 있는 문제가 크게 늘어난다.

#### 16. 손으로 한 번 추적한다

다음 graph를 종이에 그린다.

```text
A — B — D
|   |
C — E
```

먼저 adjacency list를 직접 작성한다.

예:

```text
A: B, C
B: A, D, E
C: A, E
D: B
E: B, C
```

그 다음 질문에 답한다.

```text
A의 직접 이웃은 누구인가?
A에서 D까지 갈 수 있는가?
D와 C는 직접 연결됐는가?
B를 제거하면 A에서 D까지 여전히 갈 수 있는가?
```

마지막 질문처럼 node나 edge 하나가 사라졌을 때 연결성이 어떻게 변하는지도 graph 문제다.

단순히 용어를 외우는 것보다 실제 관계를 그려 보고 질문을 던져야 graph가 살아 있는 구조로 보인다.

#### 17. 잘못된 graph 코드를 읽고 원인을 찾는다

다음 코드를 보자.

```python
graph = {
    "A": ["B"],
    "B": ["C"],
    "C": ["A"]
}

current = "A"
while True:
    print(current)
    current = graph[current][0]
```

실행 흐름은:

```text
A
B
C
A
B
C
...
```

끝나지 않는다.

문법 오류가 아니다.

graph에 cycle이 있는데 `이미 방문한 node인지 확인하는 종료 규칙`이 없기 때문이다.

고치려면 최소한:

```text
visited를 둔다
↓
처음 보는 node만 계속 진행한다
↓
이미 본 node를 만나면 다시 확장하지 않는다
```

같은 정책이 필요하다.

이 예제는 `graph`, `cycle`, `visited`가 왜 한 묶음으로 나오는지 보여 준다.

## BLOCK 05 · 원하는 값을 찾고 순서를 정하는 방법

### LESSON 01 · linear/binary search와 네 가지 정렬을 손으로 따라간다

#### 1. search는 자료구조 안에서 원하는 값을 찾는 일이다

목록:

```text
[40, 10, 70, 20, 90]
```

여기서 20이 어디 있는지 찾는다.

가장 단순한 방법은 처음부터 하나씩 확인하는 것이다.

```text
40? 아니오
10? 아니오
70? 아니오
20? 찾음
```

이것이 **linear search(선형 탐색)**다.

#### 2. 코드로 linear search를 만든다

```python
def find(items, target):
    for index, item in enumerate(items):
        if item == target:
            return index
    return -1
```

찾으면 index를 돌려주고, 끝까지 없으면 -1을 돌려준다.

항목이 맨 마지막에 있거나 없으면 거의 전체를 확인해야 한다.

#### 3. 정렬된 데이터라면 절반씩 버릴 수 있다

전화번호부가 이름순으로 정렬돼 있다고 생각해 보자.

`민수`를 찾기 위해 첫 페이지부터 한 장씩 볼 필요가 없다.

가운데를 보고 찾는 범위를 줄일 수 있다.

숫자 목록:

```text
[10, 20, 30, 40, 50, 60, 70]
```

60을 찾는다.

가운데 40:

```text
60 > 40
→ 왼쪽 절반은 볼 필요 없음
```

남은:

```text
[50, 60, 70]
```

가운데 60을 찾는다.

이것이 **binary search(이진 탐색)**의 핵심이다.

#### 4. binary search에는 중요한 전제조건이 있다

데이터가 정렬돼 있어야 한다.

```text
[40, 10, 70, 20, 90]
```

처럼 무작위 순서에서 가운데 숫자만 보고 절반을 버리면 틀린 값을 버릴 수 있다.

따라서 알고리즘을 사용할 때는:

```text
이 방법이 맞으려면 어떤 조건이 먼저 필요하지?
```

를 확인해야 한다.

#### 5. 정렬(sort)은 순서를 만드는 일이다

```text
숫자 오름차순
가격 내림차순
이름 가나다순
```

처럼 값을 기준에 따라 순서대로 배치하는 것을 **sort(정렬)**라고 부른다.

정렬 알고리즘은 여러 가지가 있다.

모두 같은 결과를 만들 수 있지만 과정과 비용이 다르다.

#### 6. selection sort — 가장 작은 것을 앞으로

```text
[4, 2, 3, 1]
```

전체에서 가장 작은 1을 찾는다.

```text
[1, 2, 3, 4] 방향으로 첫 자리 확정
```

그 다음 남은 구간에서 다시 가장 작은 값을 찾는다.

이 방식을 **selection sort(선택 정렬)**라고 부른다.

아이디어는 매우 이해하기 쉽지만 큰 데이터에서는 비교를 많이 해야 한다.

#### 7. insertion sort — 카드 정리처럼 끼워 넣는다

손에 카드를 한 장씩 받는다고 하자.

이미 정렬된 카드들 사이에 새 카드를 알맞은 위치로 끼운다.

```text
정렬된 부분 [2, 5, 8]
새 카드 6
→ [2, 5, 6, 8]
```

이 생각이 **insertion sort(삽입 정렬)**다.

데이터가 이미 거의 정렬돼 있다면 좋은 성능을 낼 수 있는 경우가 있다.

#### 8. merge sort — 나누고 정렬하며 합친다

```text
[4,1,3,2]
↓ 반으로
[4,1] [3,2]
↓
[4] [1] [3] [2]
↓ 정렬하며 합침
[1,4] [2,3]
↓
[1,2,3,4]
```

이것이 **merge sort(병합 정렬)**의 큰 생각이다.

큰 문제를 작은 문제로 나눠 해결한 뒤 합치는 전략을 **divide and conquer(분할 정복)**라고 부른다.

#### 9. quick sort — pivot을 기준으로 나눈다

**quick sort(퀵 정렬)**은 기준값인 **pivot(피벗)**을 정하고:

```text
pivot보다 작은 값
pivot과 같은 값
pivot보다 큰 값
```

등으로 나누는 과정을 반복한다.

평균적으로 빠른 정렬로 널리 사용되지만 분할이 계속 매우 치우치면 최악 성능이 나빠질 수 있다.

#### 10. 정답만 같으면 알고리즘도 같은가

아니다.

10개 데이터에서는 어떤 방법이든 금방 끝날 수 있다.

10억 개가 되면 차이가 커진다.

그래서 알고리즘을 볼 때:

```text
정답이 맞는가?
얼마나 많은 일을 하는가?
얼마나 많은 메모리를 추가로 쓰는가?
입력 상태에 따라 결과가 달라지는가?
```

를 함께 본다.

이 질문이 다음 LESSON의 Big-O로 이어진다.

## BLOCK 06 · 빠르다는 말을 숫자 증가 방식으로 바꾼다

### LESSON 01 · 실행 횟수·Big-O·공간복잡도·amortized cost·재귀를 실제 숫자로 이해한다

#### 1. 코드가 빠르다는 말을 어떻게 비교할까

컴퓨터가 다르고 상황이 다르면 실제 실행 시간은 달라진다.

그래서 알고리즘 자체를 비교할 때는 입력 크기가 커지면 **작업량이 어떤 식으로 늘어나는가**를 본다.

먼저 실제 반복 횟수를 센다.

```python
for item in items:
    print(item)
```

항목이 10개면 대략 10번 처리한다.

100개면 100번.

1,000개면 1,000번.

입력 수 `n`에 비례해 늘어난다.

#### 2. 이중 반복은 얼마나 늘어날까

```python
for a in items:
    for b in items:
        compare(a, b)
```

10개:

```text
10 × 10 = 100
```

100개:

```text
100 × 100 = 10,000
```

1,000개:

```text
1,000 × 1,000 = 1,000,000
```

입력이 10배 늘었는데 작업은 100배 늘었다.

#### 3. Big-O는 증가 속도를 크게 표현한다

입력 크기가 커질 때 작업량 증가 형태를 표현하는 대표적인 표기법이 **Big-O**다.

처음에는 수학 증명보다 모양을 비교한다.

```text
O(1)
O(log n)
O(n)
O(n log n)
O(n²)
```

#### 4. O(1) — 입력이 커져도 거의 같은 수의 작업

배열에서 이미 index를 알고 있다.

```python
value = items[500]
```

items가 1,000개든 100만 개든 500번 위치를 계산해 읽는 작업의 큰 증가 형태는 입력 전체 크기에 비례하지 않는다.

이런 형태를 **O(1)**이라고 표현한다.

`정확히 CPU 명령 1개`라는 뜻은 아니다.

입력 규모가 커져도 작업량이 크게 늘지 않는다는 뜻이다.

#### 5. O(n) — 입력 개수만큼 한 번씩 본다

```python
for item in items:
    check(item)
```

n개를 하나씩 확인하므로 **O(n)**이라고 생각한다.

#### 6. O(n²) — 두 겹으로 많이 비교한다

n개 각각에 대해 다시 n개를 보는 형태는 **O(n²)**가 될 수 있다.

```text
n=10 → 100
n=100 → 10,000
n=1,000 → 1,000,000
```

증가가 매우 빠르다.

#### 7. O(log n) — 매번 절반씩 줄인다

binary search를 다시 본다.

```text
1,024
→ 512
→ 256
→ 128
→ 64
→ 32
→ 16
→ 8
→ 4
→ 2
→ 1
```

약 10단계다.

1,048,576개도 절반씩 줄이면 약 20단계 정도다.

입력이 1,024배 늘었는데 단계는 두 배 정도다.

이런 증가 형태를 **O(log n)**이라고 표현한다.

#### 8. O(n log n) — 효율적인 비교 정렬에서 자주 본다

merge sort처럼:

```text
여러 단계로 나누고
각 단계에서 전체 n개 정도를 처리
```

하는 구조에서 **O(n log n)** 형태를 자주 본다.

지금 수학식을 외우기보다:

```text
O(n)보다 보통 더 늘지만
O(n²)보다는 훨씬 천천히 늘어나는 중요한 형태
```

라고 감을 잡는다.

#### 9. 상수와 작은 항은 왜 크게 무시할까

```text
3n + 10
```

작업과:

```text
100n + 500
```

은 실제 속도는 다르다.

하지만 입력이 커질 때 둘 다 `n에 비례해서 증가`한다는 큰 형태가 같다.

Big-O는 이런 증가 차수를 중심으로 본다.

실제 성능 최적화에서는 상수 비용도 중요할 수 있으므로 Big-O가 모든 성능 정보를 말해 주는 것은 아니다.

#### 10. 시간만 보지 않고 메모리도 본다

해시 테이블은 추가 메모리를 사용해서 검색을 빠르게 만들 수 있다.

알고리즘이 입력 크기에 따라 추가 메모리를 얼마나 쓰는지 보는 관점이 **공간복잡도(space complexity)**다.

```text
더 많은 메모리
↔
더 빠른 처리
```

처럼 trade-off가 생길 수 있다.

#### 11. amortized cost — 가끔 비싼 작업을 평균으로 본다

동적 배열에 값을 뒤로 추가할 때 대부분은 빠르다.

가끔 공간이 꽉 차면 더 큰 공간으로 복사하는 비싼 작업이 생긴다.

하지만 여러 번의 append 전체 비용을 나눠 보면 한 번당 평균 비용은 작게 유지될 수 있다.

이런 분석을 **amortized analysis**라고 부른다.

그래서 동적 배열 append를 `amortized O(1)`이라고 설명한다.

`매번 절대 O(1)`과는 미묘하게 다르다.

#### 12. 재귀는 함수가 자기 자신을 다시 부르는 방식이다

예:

```python
def countdown(n):
    if n == 0:
        print("끝")
        return

    print(n)
    countdown(n - 1)
```

```python
countdown(3)
```

결과:

```text
3
2
1
끝
```

함수가 자기 자신을 다시 호출하는 방식을 **recursion(재귀)**이라고 부른다.

#### 13. 종료 조건이 없으면 문제가 생긴다

```python
def bad(n):
    bad(n + 1)
```

끝낼 조건이 없다.

함수 호출 정보가 계속 쌓여 결국 오류가 발생할 수 있다.

재귀에서는:

```text
언제 멈추는가?
입력이 멈추는 조건에 가까워지고 있는가?
```

를 확인해야 한다.

#### 14. call stack과 연결된다

함수가 함수를 호출하면 돌아갈 위치와 지역 상태 같은 호출 정보가 stack 구조로 관리된다.

그래서 재귀 호출도 call stack과 연결된다.

JavaScript TRACK에서 event loop를 배울 때 call stack을 다시 만난다.

#### 15. Big-O를 무조건 더 작은 것만 고르는 게임으로 보지 않는다

O(n) 알고리즘이 O(n log n)보다 이론적으로 더 좋다고 해도:

```text
입력 크기
실제 상수 비용
메모리
코드 단순성
정확성
라이브러리 최적화
```

등 실제 조건을 함께 본다.

Big-O는 중요한 도구지만 시스템 설계의 유일한 기준은 아니다.

## BLOCK 07 · graph를 실제로 탐색하고 문제 해결 전략을 만든다

### LESSON 01 · BFS·DFS·visited·greedy·DP·정확성·경계값을 하나의 문제 해결 흐름으로 배운다

#### 1. 친구 graph에서 A와 가장 가까운 F를 찾고 싶다

다음 친구 관계가 있다.

```text
A — B — D
|   |
C — E — F
```

A에서 F까지 몇 단계인지 찾고 싶다.

그래프를 어떻게 돌아다닐지 방법이 필요하다.

대표적인 두 방법이 **BFS**와 **DFS**다.

#### 2. BFS는 가까운 곳부터 넓게 본다

**BFS(Breadth-First Search, 너비 우선 탐색)**는 시작점과 가까운 node부터 층별로 탐색한다.

```text
A
↓ 1단계 이웃
B, C
↓ 2단계 이웃
D, E
↓ 3단계
F
```

먼저 발견한 가까운 후보를 먼저 처리해야 해서 queue를 자주 사용한다.

#### 3. BFS를 코드로 본다

```python
from collections import deque

def bfs(graph, start):
    queue = deque([start])
    visited = {start}

    while queue:
        current = queue.popleft()
        print(current)

        for next_node in graph[current]:
            if next_node not in visited:
                visited.add(next_node)
                queue.append(next_node)
```

한 번에 외우지 않는다.

```text
queue에 시작점 넣기
visited에 시작점 기록
↓
앞에서 하나 꺼냄
↓
이웃 확인
↓
처음 보는 이웃만 visited에 기록하고 queue 뒤에 추가
↓
queue가 빌 때까지 반복
```

#### 4. visited를 queue에 넣을 때 표시하는 이유

node를 꺼낼 때까지 visited 표시를 미루면 같은 node가 여러 부모에게서 queue에 중복 추가될 수 있다.

그래서 보통 `처음 발견해서 queue에 넣는 순간` visited 처리한다.

이렇게 작은 순서 차이가 실제 성능과 동작에 영향을 줄 수 있다.

#### 5. BFS는 비용이 같은 edge에서 최단 간선 수를 찾기 좋다

모든 edge를 한 번 이동하는 비용이 같다고 하자.

BFS는 가까운 단계부터 보므로 시작점에서 최소 edge 수 경로를 찾는 데 사용할 수 있다.

예:

```text
미로에서 최소 칸 수
친구 관계 몇 단계
```

단, edge마다 비용이 다르면 일반 BFS만으로 최저 비용을 구할 수 없는 경우가 있다.

#### 6. DFS는 한 길을 깊게 들어간다

**DFS(Depth-First Search, 깊이 우선 탐색)**는 한 경로를 가능한 깊게 따라갔다가 돌아온다.

```text
A
→ B
→ D
→ 더 갈 곳 없음
← B로 돌아감
→ E
...
```

stack 또는 recursion으로 구현할 수 있다.

#### 7. 재귀 DFS를 본다

```python
def dfs(graph, node, visited):
    if node in visited:
        return

    visited.add(node)
    print(node)

    for next_node in graph[node]:
        dfs(graph, next_node, visited)
```

핵심:

```text
이미 방문했으면 멈춤
↓
현재 node 방문 표시
↓
각 이웃에 대해 같은 일을 반복
```

#### 8. BFS와 DFS 중 하나가 항상 더 좋은가

아니다.

```text
가까운 단계의 답을 먼저 찾고 싶음
→ BFS가 자연스러운 경우

한 경로를 깊게 탐색하거나 구조 전체를 재귀적으로 방문
→ DFS가 자연스러운 경우
```

문제 성질을 보고 선택한다.

#### 9. greedy는 지금 가장 좋아 보이는 선택을 한다

동전 문제를 생각해 보자.

각 단계에서 가장 큰 동전을 먼저 쓰는 전략처럼 `현재 가장 좋아 보이는 선택`을 반복하는 방법을 **greedy algorithm(그리디)**이라고 부른다.

하지만 모든 문제에서 전체 최적을 보장하지 않는다.

왜 그 선택이 최종 최적으로 이어지는지 근거가 필요하다.

#### 10. 현재 최선이 전체 최선이 아닐 수 있다

어떤 동전 체계에서는 큰 동전부터 선택하면 최소 동전 수를 놓칠 수 있다.

즉:

```text
지금 보기 좋은 선택
≠
항상 전체 최적 결과
```

이다.

그리디를 쓸 때는 증명이나 문제의 알려진 성질이 필요하다.

#### 11. 같은 작은 문제를 반복하면 결과를 저장할 수 있다

피보나치 재귀를 단순하게 쓰면 같은 값을 여러 번 계산한다.

```text
fib(5)
→ fib(4), fib(3)

fib(4)
→ fib(3), fib(2)
```

`fib(3)`이 반복된다.

한 번 계산한 결과를 저장해 다시 쓰면 중복 계산을 줄일 수 있다.

이런 생각이 **dynamic programming(DP, 동적 계획법)**과 연결된다.

#### 12. memoization으로 결과를 기억한다

```python
cache = {}

def fib(n):
    if n in cache:
        return cache[n]

    if n <= 1:
        return n

    cache[n] = fib(n - 1) + fib(n - 2)
    return cache[n]
```

한 번 계산한 `fib(n)`을 dict에 저장한다.

같은 n이 다시 들어오면 바로 꺼내 쓴다.

이 방식을 **memoization**이라고 부른다.

#### 13. 알고리즘이 몇 개 예제에서 맞았다고 항상 맞는 것은 아니다

테스트:

```text
입력 1 → 맞음
입력 2 → 맞음
입력 3 → 맞음
```

세 개가 맞아도 모든 가능한 입력에서 항상 맞는다는 논리적 증명은 아니다.

알고리즘 진행 중 계속 유지되는 성질을 이용해 올바름을 설명하기도 한다.

이런 성질을 **invariant(불변식)**이라고 부른다.

예:

```text
삽입 정렬에서 처리된 앞쪽 구간은 항상 정렬되어 있다.
```

#### 14. 경계값이 버그를 많이 만든다

목록 알고리즘이라면:

```text
빈 목록 []
한 개 [5]
두 개 [2,1]
모두 같은 값 [1,1,1]
이미 정렬됨
역순 정렬됨
매우 큰 입력
```

을 확인한다.

`일반적인 예 하나`만 성공했다고 끝내지 않는다.
