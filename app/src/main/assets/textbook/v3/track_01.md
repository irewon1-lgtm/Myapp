# TRACK 01 · 컴퓨터와 프로그래밍의 언어

이 TRACK은 **코딩을 한 번도 배운 적이 없는 사람**을 기준으로 시작한다.

처음부터 `CPU`, `RAM`, `encoding`, `compiler` 같은 말을 외우게 하지 않는다. 먼저 눈앞의 상황을 이해하고, 그 상황에 이름을 붙이는 순서로 간다.

이 TRACK이 끝났을 때 목표는 단어 시험을 잘 보는 것이 아니다.

> 컴퓨터가 무엇을 하고 있는지, 프로그램과 코드가 어떤 관계인지, 내가 쓴 한 줄의 코드가 어떻게 실행되는지를 자기 말로 설명할 수 있는 것

이다.

## BLOCK 01 · 컴퓨터는 도대체 무엇을 하는 기계인가

### LESSON 01 · 입력을 받고, 규칙대로 처리하고, 결과를 내놓는다

#### 1. 어려운 부품 이름보다 먼저 전체 그림을 잡는다

컴퓨터를 처음 배울 때 가장 흔한 실수는 부품 이름부터 외우는 것이다.

```text
CPU
RAM
SSD
GPU
운영체제
프로세스
```

이렇게 단어부터 보면 서로 무슨 관계인지 알 수 없다.

먼저 훨씬 단순하게 생각한다.

컴퓨터는 기본적으로 다음 일을 반복하는 기계다.

```text
무언가를 받는다
↓
정해진 규칙대로 처리한다
↓
결과를 내놓는다
```

이 세 단계를 각각 **입력(input)**, **처리(processing)**, **출력(output)**이라고 부른다.

지금 영어를 외우지 않아도 된다. 먼저 뜻을 익힌다.

계산기를 예로 들어 보자.

우리가 계산기에 `2 + 3`을 누른다.

```text
입력
2, +, 3
```

계산기는 `더하기`라는 규칙을 수행한다.

```text
처리
2와 3을 더한다
```

그리고 화면에 `5`를 보여 준다.

```text
출력
5
```

이것이 이미 하나의 프로그램 동작이다.

#### 2. 스마트폰 앱도 결국 같은 구조다

사진 앱에서 사진 한 장을 연다고 생각하자.

```text
입력
사용자가 사진을 누름
↓
처리
어떤 사진인지 찾음
사진 파일을 읽음
화면 크기에 맞게 준비함
↓
출력
사진을 화면에 보여 줌
```

검색 앱도 마찬가지다.

```text
입력
검색어 "강남 맛집"
↓
처리
검색어를 서버에 보냄
검색 결과를 받음
화면에 표시할 모양으로 정리함
↓
출력
검색 결과 목록
```

게임도 같은 틀로 볼 수 있다.

```text
입력
사용자가 오른쪽 버튼을 누름
↓
처리
캐릭터 위치를 오른쪽으로 변경
충돌이 있는지 확인
↓
출력
화면에서 캐릭터가 오른쪽으로 움직임
```

여기서 중요한 것은 **코딩을 배우기 전에 프로그램을 입력→처리→출력으로 쪼개 보는 습관**이다.

나중에 코드가 복잡해져도 이 질문은 계속 쓸 수 있다.

```text
지금 이 함수는 무엇을 받는가?
무슨 처리를 하는가?
무엇을 돌려주는가?
```

#### 3. 컴퓨터는 사람처럼 의도를 알아서 읽지 않는다

사람에게 이렇게 말해 보자.

> 방 좀 적당히 정리해 줘.

사람은 주변을 보고 `적당히`가 무엇인지 어느 정도 추측할 수 있다.

컴퓨터에게는 이런 식의 애매한 규칙이 어렵다.

컴퓨터는 우리가 정한 명확한 규칙을 매우 빠르게 수행한다.

그래서 잘못된 규칙을 줘도 매우 빠르고 정확하게 잘못 수행할 수 있다.

예를 들어 할인 계산을 잘못 작성했다고 하자.

원래 원하는 규칙:

```text
10,000원에서 10% 할인
→ 9,000원
```

그런데 프로그램을:

```text
가격 + 할인액
```

으로 잘못 만들었다면 결과는:

```text
10,000 + 1,000
= 11,000
```

이 된다.

컴퓨터가 멍청해서가 아니다. **사람이 적어 준 규칙을 그대로 수행했기 때문**이다.

따라서 코딩에서 중요한 능력은 단순히 타자를 빨리 치는 것이 아니다.

```text
내가 원하는 규칙이 무엇인지 정하기
↓
그 규칙을 코드로 표현하기
↓
실제로 원하는 결과가 나오는지 확인하기
```

이 세 가지가 더 중요하다.

#### 4. 하드웨어와 소프트웨어를 처음 구분한다

이제 컴퓨터를 두 덩어리로 나눠 보자.

손으로 만질 수 있는 실제 장치가 있다.

```text
화면
키보드
CPU
RAM
SSD
카메라
스피커
```

이런 물리적인 장치와 부품을 **하드웨어(hardware)**라고 부른다.

반대로 카카오톡, 계산기, 사진 앱, Android 같은 프로그램도 있다.

이런 프로그램과 프로그램이 사용하는 논리적인 정보를 넓게 **소프트웨어(software)**라고 부른다.

아주 쉽게:

```text
하드웨어 = 실제 기계
소프트웨어 = 그 기계가 어떤 일을 하도록 만드는 프로그램 쪽
```

둘은 따로 놀지 않는다.

예를 들어 카메라 앱에서 사진을 찍으면:

```text
소프트웨어
카메라 앱이 "사진을 찍어"라고 요청
↓
하드웨어
카메라 센서가 빛을 받아 데이터 생성
↓
소프트웨어
사진 데이터를 파일로 정리
↓
하드웨어
저장장치에 기록
↓
하드웨어 + 소프트웨어
화면에 사진 표시
```

처럼 함께 움직인다.

#### 5. CPU, RAM, 저장장치를 책상 비유로 이해한다

이제 부품 이름을 붙여 보자.

컴퓨터 안에는 크게 다음 역할이 필요하다.

```text
계산하고 명령을 처리하는 곳
지금 당장 쓰는 정보를 빠르게 놓는 곳
오래 보관하는 곳
```

**CPU**는 프로그램 명령을 실제로 계산하고 처리하는 핵심 장치다.

CPU를 `일하는 사람`에 비유해 보자.

**RAM**은 실행 중인 프로그램이 지금 필요한 정보를 빠르게 사용할 수 있도록 두는 공간이다.

RAM은 `지금 일하는 책상`에 비유할 수 있다.

**저장장치(storage)**는 파일과 프로그램을 오래 보관하는 곳이다. PC에서는 SSD나 HDD가 대표적이다.

저장장치는 `책장이나 창고`에 비유할 수 있다.

```text
CPU = 책상에서 실제 작업하는 사람
RAM = 지금 펼쳐 놓은 자료가 있는 책상
SSD/HDD = 자료를 오래 넣어 두는 책장
```

비유는 완벽한 기술 설명은 아니지만 처음 역할을 구분하기에 좋다.

컴퓨터를 끄기 전 문서를 저장하지 않았다고 생각해 보자.

지금 작업 중인 일부 내용은 RAM에만 있을 수 있다.

전원이 꺼지면 그 내용은 사라질 수 있다.

반면 `저장`을 해서 SSD에 파일로 기록하면 전원을 껐다 켜도 남아 있다.

이 차이가 뒤에서 데이터베이스를 배울 때 다시 나온다.

#### 6. RAM이 많으면 저장공간도 많다는 뜻일까

아니다.

예를 들어 휴대폰 사양이:

```text
RAM 8GB
저장공간 256GB
```

라고 쓰여 있을 수 있다.

둘은 역할이 다르다.

```text
RAM 8GB
→ 앱이 실행되는 동안 빠르게 사용할 공간

저장공간 256GB
→ 사진, 영상, 앱 파일 등을 오래 보관할 공간
```

그래서:

```text
사진을 너무 많이 찍어서 저장공간 부족
```

과:

```text
앱을 너무 많이 동시에 켜서 RAM 부족
```

은 서로 다른 문제다.

#### 7. CPU 코어와 클럭은 지금 어느 정도만 알면 된다

CPU 설명을 보면 `8코어`, `3GHz` 같은 말이 나온다.

코어(core)는 CPU 안에서 일을 처리하는 실행 핵심이라고 처음 이해하면 된다.

여러 코어가 있으면 일을 나눠 할 가능성이 커진다.

하지만 코어가 두 배라고 모든 프로그램이 정확히 두 배 빨라지는 것은 아니다.

한 사람이 해야만 하는 순서 작업은 사람을 많이 데려와도 그대로일 수 있기 때문이다.

클럭(clock)은 CPU 내부 동작의 기본 주기와 관련된 속도 지표다.

하지만:

```text
GHz가 높다
=
무조건 모든 상황에서 더 빠르다
```

는 아니다.

지금은 성능 비교보다 **CPU가 명령을 처리하는 장치라는 역할**이 더 중요하다.

#### 8. 프로그램 하나를 전체 흐름으로 다시 본다

메모 앱에서 `저장` 버튼을 눌렀다고 하자.

```text
1. 화면 터치가 입력으로 들어온다.
2. 프로그램이 "저장 버튼이 눌렸다"는 사건을 처리한다.
3. RAM에 있던 현재 메모 내용을 읽는다.
4. 저장 규칙에 따라 파일이나 DB에 기록한다.
5. 저장 성공 표시를 화면에 보여 준다.
```

앞에서 배운 개념이 모두 들어 있다.

```text
입력 = 터치
처리 = 저장 코드 실행
RAM = 현재 메모 내용 사용
저장장치 = 데이터를 오래 기록
출력 = "저장 완료" 화면
```

이제 CPU, RAM, 저장장치를 따로 외우는 것이 아니라 **하나의 프로그램이 돌아갈 때 각각 무슨 역할을 하는지** 연결해서 볼 수 있다.

#### 9. 초보자가 자주 하는 착각

**착각 1 — CPU가 파일을 오래 저장한다**

CPU의 주 역할은 명령 처리다. 파일을 오래 보관하는 것은 저장장치의 역할이다.

**착각 2 — RAM과 저장공간은 같은 것이다**

둘 다 GB로 표시될 수 있지만 목적이 다르다.

**착각 3 — 컴퓨터는 내가 원하는 의도를 알아서 이해한다**

프로그램은 작성된 규칙을 수행한다. 규칙 자체가 틀리면 결과도 틀릴 수 있다.

**착각 4 — 코드가 실행되기만 하면 정답이다**

실행 성공과 결과 정확성은 다르다.

## BLOCK 02 · 파일과 데이터는 실제로 무엇인가

### LESSON 01 · 파일·폴더·경로에서 bit와 byte까지 한 흐름으로 이해한다

#### 1. 저장한 데이터는 어디에 남아 있을까

메모 앱에서 글을 쓰고 `저장`을 눌렀다고 하자.

앱을 완전히 종료하고 다시 켜도 글이 남아 있다.

그러면 그 글은 실행 중인 RAM에만 있었던 것이 아니다.

어딘가에 오래 저장되어 있어야 한다.

가장 익숙한 저장 단위가 **파일(file)**이다.

파일은 저장된 정보를 이름을 가진 하나의 단위로 다루는 것이다.

예:

```text
photo.jpg
memo.txt
report.pdf
music.mp3
```

파일 이름만 보고도 사람이 어느 정도 용도를 짐작할 수 있다.

#### 2. 폴더는 파일을 정리하는 상자다

파일이 수만 개라면 한곳에 모두 늘어놓기 어렵다.

그래서 파일과 다른 폴더를 묶어서 정리한다.

```text
내문서
├─ 업무
│  ├─ 보고서.pdf
│  └─ 매출.xlsx
└─ 사진
   ├─ 가족.jpg
   └─ 여행.jpg
```

이런 묶음 공간을 **폴더(folder)** 또는 시스템에 따라 directory라고 부른다.

중요한 것은 이름보다 계층 구조다.

```text
폴더 안에 파일이 있고
폴더 안에 또 다른 폴더가 있을 수 있다.
```

#### 3. 경로는 파일까지 가는 길 설명이다

`보고서.pdf`라는 파일이 여러 폴더에 있을 수도 있다.

그래서 파일 이름만으로는 정확한 위치를 알 수 없다.

예:

```text
업무/2026/9월/보고서.pdf
```

이렇게 파일이나 폴더의 위치를 나타내는 정보를 **경로(path)**라고 부른다.

사람말로 읽으면:

```text
업무 폴더 안으로 간다
→ 2026 폴더
→ 9월 폴더
→ 보고서.pdf 파일
```

이다.

프로그램에서 `파일을 찾을 수 없습니다`라는 오류가 나오면 정말 파일이 없는 것인지, 경로를 잘못 적은 것인지 구분해야 한다.

예를 들어 실제 구조가:

```text
study/
  python/
    hello.py
```

인데 프로그램에서:

```text
study/hello.py
```

를 찾으면 실패할 수 있다.

파일이 없는 것이 아니라 **찾는 위치가 틀린 것**이다.

#### 4. 절대 경로와 상대 경로를 아주 쉽게 구분한다

주소를 설명한다고 생각해 보자.

절대 경로는 처음부터 전체 위치를 말한다.

```text
서울특별시 → 송파구 → 어떤 도로 → 어떤 건물
```

상대 경로는 현재 위치를 기준으로 말한다.

```text
여기서 한 층 위
옆 방
현재 폴더 아래 images 폴더
```

프로그램도 같은 생각을 쓴다.

정확한 문법은 운영체제마다 다르지만 개념은:

```text
절대 경로 = 전체 위치 기준
상대 경로 = 현재 위치 기준
```

이다.

#### 5. 확장자는 파일 이름의 힌트다

파일 이름 끝에는 이런 것이 붙어 있다.

```text
.jpg
.txt
.pdf
.mp3
.py
```

이 부분을 **확장자(extension)**라고 부른다.

확장자는 사람이 파일 종류를 알아보기 쉽게 하는 중요한 힌트다.

하지만 매우 중요한 점이 있다.

`cat.jpg`의 이름을 `cat.txt`로 바꾼다고 사진 데이터가 글자로 변하는 것은 아니다.

왜냐하면:

```text
파일 이름
≠
파일 안쪽 실제 데이터 구조
```

이기 때문이다.

#### 6. 파일 형식은 데이터를 저장하는 규칙이다

PNG 파일과 JPEG 파일은 둘 다 이미지지만 내부에 데이터를 저장하는 규칙이 다르다.

PDF도 자신만의 규칙이 있다.

이처럼 파일 안의 데이터를 어떤 규칙으로 기록하고 읽을지를 **파일 형식(format)**이라고 부른다.

아주 쉽게:

```text
확장자 = 파일 이름에 붙은 표시
형식 = 실제 데이터가 저장된 방식
```

이다.

나중에 인터넷을 배울 때 `MIME type`도 같은 문제에서 나온다.

받은 데이터가 JSON인지 사진인지 PDF인지 알아야 올바르게 읽을 수 있기 때문이다.

#### 7. 결국 파일 안에는 무엇이 저장될까

텍스트 파일 안에 우리가 보는 것은:

```text
안녕하세요
```

라는 글자다.

사진 파일에서는 고양이 그림을 본다.

하지만 컴퓨터 저장장치 입장에서는 결국 데이터를 더 작은 단위로 표현해야 한다.

여기서 **bit**와 **byte**가 나온다.

bit는 정보를 표현하는 아주 작은 단위다.

처음에는 `0 또는 1 두 상태 중 하나를 표현하는 단위`라고 이해하면 충분하다.

```text
0
또는
1
```

8개의 bit를 묶은 단위를 일반적으로 **1 byte**라고 부른다.

```text
8 bit = 1 byte
```

예를 들어 아주 단순한 8bit를 적어 보면:

```text
01000001
```

같은 모양이 될 수 있다.

이 값이 어떤 뜻인지는 **어떤 규칙으로 해석하느냐**에 따라 달라진다.

이 지점이 다음 LESSON의 encoding으로 이어진다.

#### 8. 같은 byte라도 해석 규칙이 필요하다

상자 안에 숫자 `65`가 적혀 있다고 하자.

누군가는 이것을 단순 숫자 65로 볼 수 있다.

어떤 문자 규칙에서는 `A`와 연결될 수도 있다.

사진 형식에서는 이미지 데이터 일부일 수도 있다.

즉 컴퓨터에 저장된 byte를 사람이 의미 있는 정보로 보려면:

```text
이 byte들을 어떤 규칙으로 읽을 것인가?
```

가 필요하다.

파일 형식과 문자 encoding이 중요한 이유다.

#### 9. 파일 크기 표시를 읽는 감각

파일 크기에:

```text
KB
MB
GB
```

같은 단위가 나온다.

지금 정확한 단위 체계까지 외울 필요는 없지만 규모 감각은 필요하다.

```text
짧은 글자 파일 → 비교적 작음
고화질 사진 → 더 큼
긴 영상 → 훨씬 큼
```

왜냐하면 저장해야 하는 byte 수가 더 많기 때문이다.

나중에 네트워크에서 파일 다운로드 속도를 볼 때도:

```text
파일 크기
전송 속도
```

가 연결된다.

#### 10. 실제 코드에서 파일 경로를 처음 본다

아직 Python 문법을 외울 단계는 아니다.

그냥 다음 코드를 사람말로 읽어 본다.

```python
path = "study/memo.txt"
print(path)
```

한 줄씩 읽는다.

```text
path = "study/memo.txt"
→ path라는 이름으로 파일 위치 글자를 기억한다.

print(path)
→ 그 글자를 화면에 보여 준다.
```

아직 실제 파일을 열지는 않았다.

중요한 것은 코드에서도 경로가 결국 **문자 데이터**로 표현될 수 있다는 점이다.

#### 11. 초보자가 자주 하는 실수

**실수 1 — 파일 이름을 바꾸면 형식도 바뀐다고 생각한다.**

확장자를 바꾸는 것과 실제 데이터 변환은 다르다.

**실수 2 — 파일 없음과 경로 오류를 구분하지 않는다.**

찾는 위치가 틀려도 `파일을 못 찾음` 증상이 나온다.

**실수 3 — RAM에 있는 값과 저장된 파일을 같은 것으로 생각한다.**

실행 중 변수와 디스크에 저장된 파일은 생명주기가 다르다.

**실수 4 — 사진과 글자는 컴퓨터 안에서 완전히 다른 물질이라고 생각한다.**

둘 다 결국 byte 형태의 데이터로 저장되며, 해석 규칙이 다르다.

4. 8bit는 무엇이라고 부르는가?

## BLOCK 03 · 글자는 어떻게 숫자와 byte가 되는가

### LESSON 01 · encoding·Unicode·UTF-8을 문자 깨짐 문제부터 배운다

#### 1. 컴퓨터는 화면의 글자 모양을 그대로 저장할까

메모장에 다음 글자를 입력한다.

```text
가
```

사람은 이것을 한글 글자 `가`로 본다.

하지만 저장장치는 종이에 글씨를 그리는 방식으로 저장하지 않는다.

컴퓨터는 이 문자를 숫자와 byte로 표현할 규칙이 필요하다.

가장 단순한 가상 규칙을 만들어 보자.

```text
A → 1
B → 2
C → 3
```

이 규칙을 보내는 사람과 받는 사람이 둘 다 알고 있다면 숫자 `2`를 보고 `B`라고 해석할 수 있다.

그런데 보내는 사람은:

```text
A → 1
B → 2
```

라고 생각하고 받는 사람은:

```text
가 → 1
나 → 2
```

라고 생각한다면 같은 `2`를 전혀 다른 글자로 읽게 된다.

이것이 문자 encoding 문제를 이해하는 가장 기본적인 그림이다.

#### 2. encoding은 정보를 다른 표현으로 바꾸는 규칙이다

**인코딩(encoding)**은 정보를 정해진 규칙에 따라 다른 표현으로 바꾸는 과정 또는 그 규칙을 말할 때 사용하는 단어다.

문자에서는 아주 쉽게:

> 사람이 보는 글자를 컴퓨터가 저장하고 전송할 수 있는 byte 형태로 표현하는 규칙

이라고 이해한다.

반대로 byte를 다시 문자로 읽는 쪽에서는 같은 규칙을 알아야 한다.

```text
문자
↓ 같은 규칙으로 encoding
byte
↓ 같은 규칙으로 decoding
문자
```

#### 3. 문자 깨짐은 왜 생길까

파일을 UTF-8 방식으로 저장했는데 다른 방식이라고 착각하고 읽으면 한글이 깨져 보일 수 있다.

핵심은:

```text
저장할 때 사용한 규칙
≠
읽을 때 사용한 규칙
```

이면 같은 byte도 다른 문자로 해석될 수 있다는 것이다.

그러므로 `한글이 깨졌다`라는 증상을 보고 곧바로:

```text
파일 데이터가 완전히 파괴됐다
```

라고 결론 내리면 안 된다.

실제 byte는 그대로인데 읽는 encoding을 잘못 선택했을 수도 있다.

#### 4. 세상의 모든 문자를 어떻게 한 규칙에 담을까

영어 알파벳만 있으면 단순하다.

하지만 세상에는:

```text
한글
영어
중국어
일본어
아랍어
이모지
수학 기호
```

등 매우 많은 문자와 기호가 있다.

서로 다른 시스템이 제각각 번호를 정하면 데이터를 교환하기 어렵다.

그래서 다양한 문자와 기호에 공통된 번호를 부여하는 큰 표준이 필요해졌다.

그 대표적인 표준이 **Unicode(유니코드)**다.

아주 쉽게:

```text
Unicode
=
"이 문자는 어떤 문자다"라고 공통 번호를 정하는 큰 체계
```

라고 이해한다.

#### 5. Unicode와 UTF-8은 같은 말이 아니다

이 부분은 초보자가 자주 섞는다.

Unicode가 `문자와 번호의 큰 체계`라면 실제 파일이나 네트워크에는 결국 byte를 기록해야 한다.

Unicode의 문자를 byte로 표현하는 여러 방식이 있고, 그중 매우 널리 쓰이는 방식이 **UTF-8**이다.

```text
Unicode
→ 어떤 문자인지 정하는 큰 체계

UTF-8
→ 그 Unicode 문자를 실제 byte로 표현하는 대표적인 방식
```

완전히 같은 말은 아니다.

비유를 써 보자.

```text
Unicode = 전 세계 사람에게 고유한 주민번호 체계를 정한 것
UTF-8 = 그 번호를 실제 종이에 어떤 형식으로 적을지 정한 방법
```

비유가 기술적으로 완벽하지는 않지만 역할 차이를 잡는 데 도움이 된다.

#### 6. HTML에서 UTF-8을 실제로 만나게 된다

나중에 웹페이지를 만들면 다음 코드를 보게 된다.

```html
<meta charset="utf-8">
```

지금 문법을 외우지 않는다.

사람말로만 읽는다.

```text
이 문서를 읽을 때 문자 encoding으로 UTF-8을 사용하세요.
```

라는 정보를 브라우저에 알려 주는 것이다.

따라서 TRACK 01에서 배운 encoding은 단순 이론이 아니라 웹페이지에서도 바로 사용된다.

#### 7. HTTP에서도 문자 encoding이 다시 나온다

인터넷 통신을 배울 때 이런 문장을 보게 된다.

```http
Content-Type: text/html; charset=utf-8
```

처음 보면 영어가 가득하지만 지금 기준으로는 일부를 읽을 수 있다.

```text
charset=utf-8
→ 이 텍스트의 문자 encoding은 UTF-8입니다.
```

이렇게 앞에서 배운 개념이 뒤의 기술과 연결된다.

#### 8. Python에서 글자와 byte가 다른 것을 아주 살짝 본다

아직 자세한 Python 수업 전이므로 결과만 본다.

```python
text = "가"
data = text.encode("utf-8")

print(text)
print(data)
```

`text`는 사람이 다루기 쉬운 문자열이고, `data`는 UTF-8로 변환된 byte 데이터다.

다시 읽을 수 있다.

```python
restored = data.decode("utf-8")
print(restored)
```

핵심 흐름:

```text
"가"
↓ UTF-8 encode
bytes
↓ UTF-8 decode
"가"
```

이다.

지금 `encode`와 `decode` 함수 문법을 외우는 것이 목적이 아니다.

**문자와 byte 사이에 변환 규칙이 존재한다**는 것을 눈으로 보는 것이 목적이다.

#### 9. 다른 규칙으로 읽으면 왜 문제가 되는지 생각해 본다

어떤 사람이 UTF-8로 저장한 파일을 다른 문자 encoding으로 읽었다고 하자.

프로그램은 사람처럼:

> 아마 UTF-8인 것 같은데 알아서 고쳐 줄게.

라고 항상 판단할 수 있는 것이 아니다.

잘못된 글자가 나올 수 있다.

그래서 파일, 웹페이지, HTTP 응답 등에서는 encoding 정보를 정확히 다루는 것이 중요하다.

#### 10. encoding과 암호화는 같은가

아니다.

encoding은 데이터를 정해진 표현 방식으로 바꾸는 것이다.

보안을 위해 내용을 비밀로 숨기는 **암호화(encryption)**와 목적이 다르다.

예를 들어 UTF-8은 누구나 규칙을 알고 다시 읽을 수 있어야 한다.

비밀을 숨기는 것이 목적이 아니다.

이 구분은 보안 TRACK에서 매우 중요해진다.

```text
encoding
→ 표현 방법을 맞추는 것

암호화
→ 허가받지 않은 사람이 내용을 읽기 어렵게 보호하는 것
```

#### 11. 초보자가 자주 하는 실수

**실수 1 — Unicode와 UTF-8을 완전히 같은 말이라고 생각한다.**

역할이 다르다.

**실수 2 — 문자 깨짐을 무조건 파일 손상이라고 생각한다.**

encoding 불일치일 수도 있다.

**실수 3 — encoding을 보안 기능이라고 생각한다.**

표현 규칙과 비밀 보호는 다른 문제다.

**실수 4 — 화면의 글자가 파일 안에도 똑같은 모양으로 저장된다고 생각한다.**

실제로는 byte 표현으로 저장되고 프로그램이 그것을 해석해 글자로 보여 준다.

#### 12. 책을 덮고 확인한다

3. Unicode와 UTF-8을 각각 한 문장으로 설명해 보라.
4. `charset=utf-8`은 대략 무슨 뜻인가?

여기까지 설명되면 `UTF-8`은 외워야 할 외계어가 아니라 **문자를 byte로 표현하는 규칙 중 하나**로 보이기 시작한다.

## BLOCK 04 · 프로그램과 코드는 어떻게 실행되는가

### LESSON 01 · 운영체제·프로그램·프로그래밍 언어·소스 코드·실행을 연결한다

#### 1. 앱 아이콘을 눌렀을 때 무슨 일이 시작될까

휴대폰에서 계산기 앱을 누른다.

우리는 화면이 열리는 것만 본다.

하지만 내부에서는 컴퓨터가 저장장치에 있던 프로그램을 읽고, 실행에 필요한 정보를 준비하고, CPU가 명령을 처리할 수 있게 만든다.

이 과정에서 중요한 역할을 하는 것이 **운영체제(Operating System, OS)**다.

Android, Windows, macOS, Linux 같은 것이 운영체제다.

운영체제를 아주 쉽게 말하면:

> 여러 프로그램이 컴퓨터의 CPU, 메모리, 파일, 화면, 네트워크 같은 자원을 사용할 수 있도록 관리하는 핵심 소프트웨어

이다.

#### 2. 왜 앱마다 하드웨어를 직접 제어하지 않을까

만약 모든 앱이 화면, 저장장치, 네트워크 장치를 자기 마음대로 직접 제어한다면 서로 충돌하기 쉽다.

운영체제가 중간에서 자원을 관리한다.

예를 들어 앱이 파일을 읽고 싶을 때:

```text
앱
↓ 파일을 읽고 싶다고 요청
운영체제
↓ 저장장치와 파일 규칙 관리
데이터를 앱에 전달
```

하는 구조를 생각할 수 있다.

세부 구현은 훨씬 복잡하지만 지금은 역할을 이해하는 것이 중요하다.

#### 3. 커널이라는 말은 어디에 들어갈까

운영체제 설명에서 **커널(kernel)**이라는 말을 보게 된다.

커널은 운영체제에서 CPU 시간, 메모리, 장치 같은 핵심 자원을 관리하는 중심 부분이다.

처음부터 커널 구조를 공부할 필요는 없다.

지금은:

```text
운영체제
└─ 핵심 자원 관리를 담당하는 중심 부분에 kernel이 있다
```

정도로 잡는다.

#### 4. 프로그램이란 무엇인가

**프로그램(program)**은 컴퓨터가 특정 일을 하도록 만든 명령과 구조의 묶음이다.

계산기 프로그램은:

```text
숫자 입력 받기
연산자 받기
계산하기
결과 보여주기
```

같은 규칙을 가진다.

메신저 프로그램은 훨씬 많은 규칙을 가진다.

```text
로그인
대화 목록 불러오기
메시지 전송
알림 수신
사진 업로드
```

#### 5. 앱은 프로그램과 다른 것인가

**앱(application)**은 사용자가 특정 목적을 위해 사용하는 프로그램을 부르는 흔한 말이다.

```text
계산기 앱
지도 앱
메신저 앱
은행 앱
```

이다.

모든 문맥에서 `프로그램`과 `앱`의 범위가 완전히 똑같다고 외울 필요는 없다.

초급에서는 `앱도 프로그램의 한 형태`라고 이해하면 충분하다.

#### 6. 코드란 무엇인가

우리가 프로그램을 만들 때 컴퓨터에게 줄 규칙을 사람이 읽고 작성할 수 있는 형태로 적는다.

이런 명령과 규칙을 **코드(code)**라고 부른다.

예:

```python
print("안녕")
```

아직 Python을 배우지 않았지만 사람말로 읽어 보자.

```text
print
→ 화면에 값을 보여 주는 기능

("안녕")
→ 보여 줄 값으로 "안녕"을 전달
```

결과:

```text
안녕
```

#### 7. 프로그래밍 언어는 왜 필요할까

사람끼리도 서로 약속한 언어가 필요하다.

컴퓨터 프로그램을 작성할 때도 정해진 문법과 의미가 있는 언어가 필요하다.

이런 언어를 **프로그래밍 언어(programming language)**라고 부른다.

예:

```text
Python
JavaScript
Kotlin
Java
C
```

언어가 다르면 코드 모양도 달라질 수 있다.

Python:

```python
print("안녕")
```

JavaScript:

```javascript
console.log("안녕");
```

모양은 다르지만 둘 다 화면이나 콘솔에 글자를 보여 주려는 코드다.

따라서 코딩을 잘한다는 것은 특정 기호를 전부 외우는 것만을 뜻하지 않는다.

```text
값을 어떻게 다루는가
조건을 어떻게 표현하는가
반복을 어떻게 만드는가
기능을 어떻게 나누는가
```

같은 공통 생각이 더 오래 간다.

#### 8. 소스 코드란 무엇인가

개발자가 작성하고 읽는 프로그램 코드를 **소스 코드(source code)**라고 부른다.

예를 들어 `hello.py` 파일에:

```python
print("안녕")
```

을 적었다면 이 파일은 소스 코드를 담고 있다.

하지만 매우 중요한 차이가 있다.

```text
코드를 작성했다
≠
코드를 실행했다
```

파일에 글자를 적어 놓은 것만으로 프로그램이 자동 실행되는 것은 아니다.

#### 9. 실행(run, execute)이란 무엇인가

작성한 프로그램의 명령을 실제로 동작시키는 것을 **실행(run, execute)**이라고 부른다.

예:

```text
소스 코드 작성
print("안녕")
↓
실행
↓
출력
안녕
```

그리고 또 하나의 중요한 차이가 있다.

```text
실행됐다
≠
결과가 맞다
```

예를 들어:

```python
price = 10000
count = 3
print(price + count)
```

코드는 오류 없이 실행될 수 있다.

결과는:

```text
10003
```

하지만 우리가 원하는 것이 `가격 × 수량 = 총가격`이었다면 논리는 틀렸다.

원했던 결과는 30000이다.

즉:

```text
문법 오류 없음
실행 성공
```

만으로는 프로그램이 올바르다고 할 수 없다.

#### 10. interpreter와 compiler는 왜 등장할까

사람이 작성한 고수준 프로그래밍 언어를 CPU가 그대로 사람처럼 읽는 것은 아니다.

중간에 코드를 분석하고 실행 가능한 형태로 연결해 주는 도구와 과정이 필요하다.

여기서 **interpreter(인터프리터)**, **compiler(컴파일러)** 같은 용어가 나온다.

초급에서는 둘을 지나치게 정확히 갈라 외우지 않는다.

우선 다음만 잡는다.

```text
사람이 작성한 소스 코드
↓
언어 실행 환경/도구가 분석·변환
↓
컴퓨터가 실제 명령을 수행
```

Python은 흔히 interpreter 방식으로 설명되고, C 같은 언어는 compile 과정을 거쳐 실행 파일을 만드는 전형적인 예로 설명된다.

현대 언어 실행 방식은 내부적으로 더 복잡할 수 있으므로 `언어는 반드시 둘 중 하나`라고 단순화하지 않는다.

#### 11. process라는 말을 처음 만난다

저장장치에 있는 프로그램 파일과 실제로 실행 중인 프로그램은 구분할 필요가 있다.

실행 중인 프로그램의 한 인스턴스를 **process(프로세스)**라고 부른다.

비유:

```text
요리책 = 저장된 프로그램
실제로 주방에서 그 요리책대로 요리 중 = 실행 중인 process
```

같은 앱을 여러 창에서 실행하면 여러 실행 단위가 생길 수도 있다.

프로세스의 정확한 구조는 나중에 서버와 운영체제를 배울 때 더 다룬다.

#### 12. 전체 흐름을 하나로 연결한다

우리가 `hello.py` 파일을 만들었다고 하자.

```text
1. 저장장치에 hello.py라는 소스 파일이 있다.
2. 파일 안에는 프로그래밍 언어 문법으로 작성한 코드가 있다.
3. 사용자가 실행 명령을 내린다.
4. 운영체제가 프로그램 실행에 필요한 자원을 준비한다.
5. Python 실행 환경이 소스 코드를 읽고 실행한다.
6. CPU가 실제 명령 처리를 수행한다.
7. 필요한 값은 RAM에서 사용된다.
8. 결과가 화면에 출력된다.
```

앞에서 따로 배웠던 단어가 하나의 흐름으로 묶인다.

#### 13. 초보자가 자주 하는 실수

**실수 1 — 소스 파일을 저장하면 자동 실행됐다고 생각한다.**

저장과 실행은 다르다.

**실수 2 — 실행 성공을 정답 판정으로 생각한다.**

논리적으로 틀린 코드도 정상 실행될 수 있다.

**실수 3 — 프로그래밍 언어가 CPU가 직접 이해하는 자연어라고 생각한다.**

실행 환경과 변환 과정이 필요하다.

**실수 4 — 운영체제를 그냥 바탕화면이라고 생각한다.**

운영체제는 프로그램 실행과 자원 관리를 담당하는 핵심 소프트웨어다.

#### 14. 책을 덮고 확인한다

1. 프로그램과 소스 코드는 어떤 관계인가?
2. 코드를 작성하는 것과 실행하는 것은 왜 다른가?
3. 운영체제는 프로그램 실행에서 어떤 역할을 하는가?
4. `실행 성공 = 결과 정확`이 아닌 예를 하나 만들어 보라.
5. process를 저장된 프로그램 파일과 비교해 설명해 보라.

## BLOCK 05 · 첫 코드를 읽고, 실행하고, 일부러 망가뜨리고, 다시 고친다

### LESSON 01 · 코드를 외우지 않고 한 조각씩 읽는 첫 실습

#### 1. 이제 처음으로 코드를 직접 만진다

여기까지 읽었으면 다음 단어를 어느 정도 알고 있다.

```text
입력
처리
출력
값
파일
경로
프로그램
코드
실행
```

이제 아주 작은 Python 코드부터 시작한다.

```python
print("안녕하세요")
```

처음 코드를 볼 때 절대로 한 줄 전체를 통째로 외우지 않는다.

세 조각으로 나눈다.

```text
print
(
"안녕하세요"
)
```

#### 2. print는 무엇인가

`print`는 값을 화면의 콘솔 영역에 보여 주는 데 사용하는 Python의 기본 기능이다.

지금 `함수(function)`라는 정확한 개념을 아직 몰라도 된다.

일단:

```text
print = 값을 보여 달라고 요청하는 기능 이름
```

으로 생각한다.

다음 TRACK에서 함수라는 개념을 제대로 배운다.

#### 3. 괄호 안에는 무엇이 들어가는가

```python
print("안녕하세요")
```

에서 괄호 안의:

```python
"안녕하세요"
```

가 print에게 넘겨 주는 내용이다.

사람말로 바꾸면:

> print야, `안녕하세요`라는 글자를 보여 줘.

이다.

#### 4. 따옴표는 왜 있는가

Python은 `안녕하세요`를 그냥 코드 명령 이름으로 보는 것이 아니라 **글자 값**으로 다뤄야 한다.

그래서 문자열을 표현할 때 따옴표를 사용한다.

```python
"안녕하세요"
```

다음은 서로 다르다.

```python
print("hello")
```

과:

```python
print(hello)
```

두 번째 코드에서 `hello`라는 이름이 미리 정의되어 있지 않으면 오류가 날 수 있다.

왜냐하면 따옴표가 없으면 Python은 `hello`를 단순 글자 값이 아니라 **어떤 이름**으로 해석하기 때문이다.

변수는 다음 TRACK에서 제대로 배운다.

#### 5. 실행 전에 결과를 먼저 예상한다

코드를 보기만 하고 바로 실행하지 않는다.

```python
print("안녕하세요")
```

를 보고 먼저 종이에 적는다.

```text
내 예상:
안녕하세요
```

그 다음 실행한다.

실제 결과:

```text
안녕하세요
```

예상과 결과를 비교한다.

이 습관이 중요하다.

왜냐하면 나중에 코드가 길어져도:

```text
내가 예상한 실행 순서
vs
실제로 관찰한 실행 순서
```

의 차이가 버그를 찾는 출발점이 되기 때문이다.

#### 6. 두 줄이면 어떤 순서로 실행될까

```python
print("첫째")
print("둘째")
```

먼저 예상한다.

```text
첫째
둘째
```

실행하면 일반적으로 위에서 아래 순서로 나온다.

```text
첫째
둘째
```

이 아주 단순한 `위에서 아래로 실행된다`는 감각이 다음 TRACK의 조건문과 반복문을 이해하는 기반이다.

#### 7. 숫자를 출력해 본다

```python
print(10)
print(20)
```

결과:

```text
10
20
```

여기서 숫자에는 따옴표를 쓰지 않았다.

다음 둘을 비교한다.

```python
print(10)
print("10")
```

화면에는 둘 다 `10`처럼 보일 수 있다.

하지만 프로그램 안에서는 첫 번째는 숫자 값이고 두 번째는 글자 값이다.

이 차이는 다음 TRACK에서 계산할 때 매우 중요해진다.

#### 8. 첫 계산을 해 본다

```python
print(2 + 3)
```

사람말:

```text
2와 3을 더한 결과를 print로 보여 줘.
```

결과:

```text
5
```

입력·처리·출력 관점으로도 본다.

```text
코드에 들어 있는 값 = 2, 3
처리 = 더하기
출력 = 5
```

#### 9. 글자 `2 + 3`과 계산 `2 + 3`은 다르다

다음 두 코드를 비교한다.

```python
print(2 + 3)
```

```python
print("2 + 3")
```

첫 번째 결과:

```text
5
```

두 번째 결과:

```text
2 + 3
```

왜 다를까?

따옴표 안은 하나의 글자 값이기 때문이다.

Python에게 더하기 계산을 시킨 것이 아니라 `2 + 3`이라는 글자를 그대로 보여 달라고 한 것이다.

#### 10. 일부러 문법 오류를 만든다

올바른 코드:

```python
print("안녕")
```

따옴표 하나를 지워 보자.

```python
print("안녕)
```

이제 Python은 코드 구조를 올바르게 이해하기 어렵다.

이처럼 프로그래밍 언어의 문법 규칙을 어겨 코드를 해석하지 못하는 종류의 오류를 **syntax error(문법 오류)**라고 부른다.

중요한 것은 오류가 나왔다는 사실이 아니라:

```text
어느 부분의 규칙이 깨졌는가?
```

를 보는 것이다.

#### 11. 실행 중에 생기는 오류도 있다

문법은 맞아 보이는데 실행하다 문제가 생길 수도 있다.

예를 들어 아직 정의하지 않은 이름을 사용한다.

```python
print(user_name)
```

`user_name`이 존재하지 않으면 실행 중 오류가 발생한다.

정확한 오류 분류는 뒤에서 배우지만 지금은:

```text
문법 자체를 읽지 못함
vs
문법은 읽었지만 실행하면서 필요한 값이 없음
```

이라는 차이를 느낀다.

#### 12. 논리 오류는 더 조용해서 위험하다

가장 헷갈리는 것은 **오류 메시지 없이 잘못된 결과가 나오는 경우**다.

상품 가격이 10,000원이고 수량이 3개다.

잘못된 코드:

```python
price = 10000
count = 3
print(price + count)
```

실행은 된다.

결과:

```text
10003
```

하지만 원하는 총가격은:

```text
30000
```

이다.

코드는 멈추지 않았다. 오류 메시지도 없다.

우리가 세운 규칙이 틀렸다.

이런 종류를 넓게 **논리 오류(logic error)**라고 부른다.

이래서:

> 실행됐으니 됐다.

가 위험하다.

#### 13. 코드를 고칠 때의 첫 번째 기본 절차

앞으로 계속 사용할 절차다.

```text
1. 원하는 결과를 먼저 적는다.
2. 실행 전 현재 코드 결과를 예상한다.
3. 실제로 실행한다.
4. 예상과 실제를 비교한다.
5. 다르면 어느 줄부터 생각이 달라졌는지 찾는다.
6. 한 부분만 고친다.
7. 다시 실행한다.
8. 원래 문제와 다른 문제가 생기지 않았는지 확인한다.
```

이것이 디버깅의 아주 작은 시작이다.

#### 14. AI가 코드를 만들어 줘도 이 순서는 사라지지 않는다

앞으로 AI에게:

> 총가격 계산 코드 만들어 줘.

라고 하면 AI가 코드를 작성해 줄 수 있다.

그렇다고 사람이 할 일이 없어지는 것은 아니다.

반드시 확인한다.

```text
입력은 무엇인가?
계산식은 무엇인가?
예상 결과는 무엇인가?
실제로 실행했는가?
경계값에서도 맞는가?
```

AI가 만든 코드를 이해하지 않고 바로 사용하면 **틀린 규칙을 빠르게 실행하는 프로그램**을 만들 수 있다.

#### 15. 아주 작은 수정 실습

처음 코드:

```python
print("사과 가격")
print(1000)
```

수정 1 — 상품명을 바꾼다.

```python
print("바나나 가격")
print(1000)
```

수정 2 — 가격을 바꾼다.

```python
print("바나나 가격")
print(1500)
```

수정 3 — 두 개 가격을 계산한다.

```python
print("바나나 2개 가격")
print(1500 * 2)
```

한 번에 새로운 문법을 열 개 넣지 않았다.

```text
출력
→ 값 변경
→ 숫자 계산
```

순서로 한 단계씩 확장했다.

이 방식으로 다음 TRACK부터 실제 프로그래밍을 배운다.

#### 16. TRACK 01 전체를 하나로 연결한다

이제 다음 흐름을 말할 수 있어야 한다.

```text
사람이 소스 코드를 작성한다.
↓
파일로 저장한다.
↓
실행한다.
↓
운영체제와 실행 환경이 프로그램을 준비한다.
↓
CPU가 명령을 처리한다.
↓
실행 중 필요한 값은 RAM에서 사용된다.
↓
필요하면 파일이나 다른 저장소에 오래 기록한다.
↓
화면이나 파일 등으로 결과가 출력된다.
```

그리고 글자가 저장될 때는:

```text
문자
↓ encoding 규칙
byte
↓ 저장/전송
같은 규칙으로 해석
↓
문자
```

라는 흐름이 있다.

처음 TRACK에서 단어를 많이 외운 것이 아니라 **컴퓨터에서 프로그램 하나가 움직이는 큰 그림**을 만든 것이다.

#### 17. TRACK 01 완료 확인

책을 보지 않고 다음을 설명한다.

- 입력·처리·출력을 메모 앱 예로 설명한다.
- CPU·RAM·저장장치 차이를 설명한다.
- 파일·폴더·경로·확장자·형식 차이를 설명한다.
- bit와 byte 관계를 말한다.
- 문자 encoding이 왜 필요한지 설명한다.
- Unicode와 UTF-8을 구분한다.
- 프로그램·코드·소스 코드·실행을 연결해 설명한다.
- 실행 성공과 결과 정확성이 다른 이유를 말한다.
- 간단한 `print` 코드를 조각으로 읽는다.
- 문법 오류와 논리 오류가 왜 다른지 예를 든다.

### TRACK 프로젝트 · 첫 진단 노트 만들기

아래 코드를 직접 실행한다.

```python
print("내 첫 프로그램")
print(10 + 20)
print("10 + 20")
```

실행 전에 세 줄의 결과를 먼저 종이에 예상한다.

실행 후 실제 결과와 비교한다.

그 다음 다음 네 가지를 각각 한 번씩 바꾸고 다시 실행한다.

1. 글자 한 개 바꾸기
2. 숫자 한 개 바꾸기
3. `+`를 `*`로 바꾸기
4. 따옴표 하나를 일부러 지워 오류 만들기

마지막으로 노트에 다음 형식으로 적는다.

```text
내가 바꾼 것:
내 예상:
실제 결과:
왜 그렇게 됐는지:
```

코드를 많이 쓰는 것이 첫 목표가 아니다.

**작은 코드를 보고 결과를 예상하고, 실행하고, 변경 원인을 설명하는 것**이 첫 목표다.
