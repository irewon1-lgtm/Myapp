# 3장. 입력창·버튼·폼으로 사용자 입력 받기

지금까지 만든 기록장은 작성자가 미리 넣어 둔 문장을 보여 주었습니다. 실제 기록장이라면 사용자가 오늘 공부한 내용과 시간을 직접 적을 수 있어야 합니다. 그래서 입력창과 버튼을 만듭니다. 이때 아주 흔한 오해가 생깁니다. 화면에 입력창과 ‘저장’ 버튼이 보이면 저장 기능도 이미 생겼다고 느끼는 것입니다.

그러나 버튼에 ‘저장’이라는 글자를 적는 것은 버튼의 표시 내용을 정한 것입니다. 브라우저가 그 한국어를 이해해서 저장 위치를 만들고 데이터를 보관하는 것은 아닙니다. 입력을 어디에서 받고, 어떤 값이 유효하며, 제출했을 때 무엇을 할 것인지 별도로 정해야 합니다. 이 장에서는 입력 화면을 먼저 제대로 만듭니다. 값을 목록에 추가하는 동작은 8장, 다시 열어도 유지되는 저장은 9장에서 연결합니다.

## 3.1 입력창 하나를 읽는 네 가지 관점

가장 단순한 글자 입력창을 보겠습니다.

```html
<label for="topic">공부한 내용</label>
<input id="topic" name="topic" type="text">
```

`input`은 입력을 받는 요소입니다. `type="text"`는 이 입력창이 일반적인 한 줄 글자를 받는 형태라는 뜻입니다. 앞 장의 문단과 달리 `<input>` 안에 내용을 쓰고 `</input>`으로 닫는 형태가 아닙니다. 입력창의 값은 별도의 값으로 다룹니다.

`label`은 입력창의 설명입니다. `for="topic"`은 `id="topic"`인 입력 요소와 연결됩니다. 이 연결이 있으면 설명 글자를 눌렀을 때 해당 입력창으로 초점이 이동하는 등 사용하기 쉬워집니다. 화면을 읽어 주는 보조 기술에도 무엇을 입력하는 칸인지 전달할 수 있습니다. 단지 가까운 곳에 ‘공부한 내용’이라는 문단을 놓는 것과 의미가 다릅니다.[3][4][5]

`id`는 이 문서 안에서 요소를 찾기 위한 이름이고, `name`은 폼 데이터를 제출할 때 값에 붙이는 항목 이름으로 사용됩니다. 예제에서는 둘을 똑같이 `topic`이라고 정했지만 항상 같아야 하는 것은 아닙니다. 두 속성의 이름이 다르다는 것은 역할도 구별해야 한다는 신호입니다. 나중에 JavaScript는 `id`를 이용해 입력창을 찾을 수 있고, 폼 제출은 `name`을 이용해 이 값이 어느 항목인지 표시할 수 있습니다.

속성 값을 마음대로 바꿀 수 있는 것과 연결이 자동으로 유지되는 것은 다릅니다. `id`를 `study-topic`으로 바꾸면서 `label`의 `for`를 그대로 두면 연결이 끊어집니다. 변수 이름을 바꿨을 때 사용하는 곳도 함께 바꿔야 했던 것과 비슷합니다.

### 연습 3-1. 가까이 있는데 연결되지 않는 설명

다음 코드는 설명을 누르면 입력창으로 초점이 옮겨가지 않습니다. 어느 값을 맞춰야 할까요?

```html
<label for="minutes">공부한 시간</label>
<input id="duration" name="minutes" type="number">
```

### 풀이 3-1

`label`의 `for`는 `name`이 아니라 입력 요소의 `id`와 연결됩니다. 따라서 `for="duration"`으로 바꾸거나 입력의 `id`를 `minutes`로 맞출 수 있습니다. 이 예제에서는 이미 `duration`을 다른 코드에서 사용할 수 있으므로 설명 쪽을 `for="duration"`으로 바꾸는 작은 수정을 생각할 수 있습니다.

‘minutes라는 글자가 어딘가에 있으니 연결된다’가 아닙니다. 어떤 속성과 어떤 속성이 짝을 이루는지 알아야 합니다. 연결할 곳을 잘못 찾은 상태에서 CSS로 두 요소를 더 가깝게 붙이는 것은 다른 문제를 고치는 것입니다.

## 3.2 입력 종류를 고르면 기본 동작이 달라진다

공부한 내용은 글자로, 공부한 시간은 숫자로 받으려 합니다. `type="number"`를 사용하면 브라우저가 숫자 입력을 위한 동작을 제공할 수 있습니다. 모바일에서는 입력 종류에 맞는 키보드가 나타나기도 합니다. 구체적인 모양은 브라우저와 기기에 따라 달라질 수 있으므로, 특정 키보드가 반드시 똑같이 보인다고 가정하지 않습니다.

```html
<label for="minutes">공부한 시간(분)</label>
<input id="minutes" name="minutes" type="number" min="1" max="600" step="1">
```

`min="1"`은 유효한 최솟값, `max="600"`은 최댓값, `step="1"`은 이 범위에서 1단위 간격을 사용한다는 조건입니다. 이 기록장에서는 1분부터 600분까지의 정수로 정했습니다. 이 숫자가 모든 공부 앱의 정답은 아닙니다. 예제의 요구사항을 구체적으로 정한 것입니다. 범위를 정하지 않으면 ‘0분도 저장할 것인가’, ‘소수점 시간을 허용할 것인가’ 같은 질문을 프로그램이 대신 결정할 수 없습니다.

체크박스는 선택 여부를 받습니다. 글자 입력창의 내용과 달리 선택됐는지 아닌지가 중요한 값입니다. `select`는 여러 선택지 중에서 고르게 할 수 있고, `textarea`는 여러 줄의 문장을 입력받을 때 사용할 수 있습니다. 화면을 만들 때는 입력값의 성격에 맞는 요소를 고릅니다. 예쁘게 보이는 네모를 먼저 고른 뒤 의미를 끼워 맞추는 순서는 피하는 편이 좋습니다.

```html
<label>
  <input id="completed" type="checkbox">
  이 내용을 이해했습니다
</label>
```

이 예제에서는 `label` 안에 입력 요소를 넣어 연결했습니다. 설명과 입력을 연결하는 또 다른 방식입니다. 다만 체크박스가 선택되었다고 사람의 이해가 검증된 것은 아닙니다. 프로그램이 아는 것은 사용자가 이 항목을 선택했다는 상태뿐입니다. 실제 이해 여부를 판단하려면 설명하거나 문제를 푸는 별도의 활동이 필요합니다.

### 연습 3-2. 체크박스의 뜻을 과장하지 않기

사용자가 ‘이해했습니다’를 선택했습니다. 프로그램이 이 사실만으로 ‘시험에서 정답을 낼 수 있다’고 판단해도 될까요? 앱이 실제로 관찰한 정보와 추정한 정보를 구분해 보세요.

### 풀이 3-2

직접 관찰한 것은 체크박스가 선택되었다는 값입니다. 시험 정답 여부는 이 값만으로 확인하지 못했습니다. 앱에서는 이를 ‘사용자가 이해했다고 표시함’처럼 해석할 수 있습니다. 사람의 상태를 나타내는 입력은 현실 전체가 아니라 사용자가 제공한 표현이라는 점을 구분해야 합니다.

코딩에서 이런 구별은 의외로 중요합니다. 버튼 문구, 변수 이름, 사용자 선택을 실제 세계의 보증으로 오해하면 앱의 설명과 동작이 과장됩니다.

## 3.3 빈칸 안내와 실제 설명은 다르다

입력창 안에 연한 글씨로 예시를 넣을 때 `placeholder`를 사용합니다.

```html
<label for="topic">공부한 내용</label>
<input id="topic" name="topic" type="text" placeholder="예: HTML 제목과 문단">
```

예시는 무엇을 적을지 이해하는 데 도움이 됩니다. 그러나 사용자가 입력하면 placeholder는 보통 사라집니다. ‘이 칸에 무엇을 적는 것이었지?’라고 다시 확인하려고 할 때 설명이 없어질 수 있습니다. 따라서 placeholder를 항상 label의 대체물로 사용하지 않습니다. 이 예제에서는 설명은 밖에 남기고 예시는 안에 넣었습니다.[5]

또한 placeholder는 실제 입력값이 아닙니다. 사용자가 아무것도 적지 않았다면 ‘예: HTML 제목과 문단’이라는 문자열이 자동으로 입력된 것이 아닙니다. 기본값을 실제로 넣는 `value`와도 구별해야 합니다. 기본값을 넣어 놓으면 사용자가 그것을 그대로 제출할 가능성이 있으므로, 미리 입력할지 예시만 보여 줄지 판단해야 합니다.

오류를 표시할 공간도 미리 생각할 수 있습니다. ‘잘못됐습니다’만 보여 주기보다 무엇이 잘못됐고 어떻게 고칠 수 있는지 설명하는 편이 낫습니다. ‘시간은 1~600분의 정수로 적어 주세요’는 다음 행동이 분명합니다. 다만 경고가 뜨는 시점과 구현은 뒤의 JavaScript 장에서 연결합니다.

### 연습 3-3. 아무것도 적지 않았는데 값이 있다고 생각한 경우

입력창에 placeholder로 ‘30분’이 보입니다. 사용자는 그 칸을 건드리지 않고 제출했습니다. 개발자가 이 입력을 자동으로 30이라고 간주하면 어떤 오해가 생길까요?

### 풀이 3-3

placeholder를 실제 입력값으로 오해한 것입니다. 기본값을 넣고 싶다면 그 의도를 명확히 구현해야 하고, 빈칸이면 거절할 것이라면 별도 규칙이 필요합니다. 입력 예시를 보여 준 것만으로 사용자가 30을 입력했다고 볼 수 없습니다.

화면에 보이는 문자열과 입력 요소가 실제로 가지고 있는 값은 다를 수 있습니다. 8장에서 `value`를 읽을 때 이 구별이 다시 나타납니다.

## 3.4 폼은 여러 입력을 한 번의 제출로 묶는다

공부한 내용과 시간은 따로 입력하지만 하나의 기록을 만들 때 함께 사용합니다. `form`은 이런 입력들을 묶어 제출하는 구조입니다. 폼 안의 제출 버튼을 누르거나, 일부 입력창에서 Enter를 누르는 행동이 제출로 이어질 수 있습니다. 따라서 ‘추가’ 버튼의 클릭만 생각하는 것보다 폼의 제출 자체를 다루는 편이 입력 흐름을 일관되게 만들 수 있습니다.[4][5]

다음은 아직 JavaScript로 기록을 추가하지 않는 입력 화면의 전체 문서입니다. 추가 버튼은 의도적으로 `type="button"`으로 두었습니다. 입력창과 설명의 연결을 확인하는 단계이며, 이 버튼을 눌러도 저장하거나 기본 제출을 수행하지 않습니다. 8장에서 제출 버튼으로 바꾸고 처리 함수를 연결합니다.

```html demo
<!doctype html>
<html lang="ko">
  <head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>학습 기록 입력</title>
  </head>
  <body>
    <main>
      <h1>나의 학습 기록장</h1>
      <form id="record-form">
        <p>
          <label for="topic">공부한 내용</label>
          <input id="topic" name="topic" type="text"
                 required maxlength="80"
                 placeholder="예: HTML 요소 읽기">
        </p>
        <p>
          <label for="minutes">공부한 시간(분)</label>
          <input id="minutes" name="minutes" type="number"
                 required min="1" max="600" step="1">
        </p>
        <button type="button">기록 추가 — 다음 단계에서 연결</button>
      </form>
      <p>지금은 입력 화면만 만든 단계입니다.</p>
    </main>
  </body>
</html>
```

여기서 `required`는 값을 필수로 받는 조건이고 `maxlength="80"`은 이 글자 입력의 길이를 제한합니다. 브라우저의 기본 유효성 검사는 제출을 시도하거나 검사 기능을 호출하는 등의 상황에서 작동합니다. 지금 버튼을 일반 버튼으로 두었다는 이유만으로 누를 때마다 자동 검사가 실행되는 것은 아닙니다. 조건을 적어 놓는 것과 검사가 일어나는 사건을 구분해야 합니다.

버튼의 `type`은 명시하는 편이 좋습니다. 폼 안에서 종류를 생략한 버튼은 제출 버튼으로 동작할 수 있습니다. ‘도움말’ 버튼을 만들었는데 폼이 제출되어 화면이 바뀌면, 버튼 종류부터 확인할 수 있습니다. `type="button"`은 일반 동작용, `type="submit"`은 제출용입니다. `reset`은 폼 값을 처음 상태로 되돌릴 수 있지만 사용자가 적은 것을 뜻하지 않게 잃게 할 수 있으므로 필요 없이 넣지 않겠습니다.

### 연습 3-4. 도움말 버튼이 화면을 바꾼다

폼 안에 `<button>입력 방법 보기</button>`을 넣었습니다. 버튼을 눌렀더니 입력 검사가 뜨거나 화면이 다시 열립니다. 이 버튼이 기록 제출과 관계없는 도움말용이라면 어떤 속성을 명시하는 것이 좋을까요?

### 풀이 3-4

`<button type="button">입력 방법 보기</button>`처럼 종류를 명시합니다. 이후 도움말을 열어 주는 JavaScript를 따로 연결합니다. 글자에 ‘도움말’이라고 적었다고 브라우저가 일반 버튼으로 자동 분류하지는 않습니다. 버튼의 의미를 사람이 읽는 문구와 실제 동작을 지정하는 속성으로 각각 맞춰야 합니다.

## 3.5 기본 제출은 어디로 가는가?

HTML 폼은 원래 서버로 데이터를 보내는 데도 사용할 수 있습니다. `action`은 제출할 주소이고 `method`는 전송 방식입니다. 다음은 서버 연결의 모양을 설명하기 위한 부분 코드입니다. `/records`라는 서버가 이 책에서 이미 제공된다는 뜻은 아니므로 그대로 저장 기능이 완성되지는 않습니다.

```html
<form action="/records" method="post">
  <label for="server-topic">공부한 내용</label>
  <input id="server-topic" name="topic" type="text" required>
  <button type="submit">제출</button>
</form>
```

제출할 때 입력값에는 `name="topic"`이라는 항목 이름이 붙습니다. 서버는 약속된 항목을 받아 처리해야 합니다. 버튼을 누르는 일만으로 서버가 생기지는 않습니다. 우리가 나중에 만드는 브라우저 안의 기록장에서는 JavaScript가 폼의 제출 이벤트를 받아 기본 이동을 막고, 현재 화면의 목록을 바꿉니다. 두 방식은 모두 ‘제출’이라는 행동에서 출발할 수 있지만 이후 처리가 다릅니다.

`GET`과 `POST`는 HTTP 요청 방식입니다. 초반에는 GET 폼의 값이 주소의 질의 부분에 나타날 수 있다는 점, POST라고 자동으로 비밀이나 보안이 보장되는 것은 아니라는 점을 알아 두면 충분합니다. 민감한 값을 아무 주소나 로그에 넣지 않아야 하고, 실제 보안에는 HTTPS와 서버 측 권한·검사가 따로 필요합니다. 이 장의 목적은 보안 서버를 구현하는 것이 아니라, 입력 화면과 서버 처리를 같은 기능으로 착각하지 않게 하는 것입니다.

### 연습 3-5. 버튼 이름을 바꾸면 서버도 바뀔까?

버튼 문구를 ‘내 휴대폰에 저장’에서 ‘가족과 공유’로 바꿨습니다. 나머지 코드는 그대로입니다. 이 변경으로 여러 기기에서 같은 기록을 볼 수 있게 되었을까요?

### 풀이 3-5

아닙니다. 화면 문구만 바뀌었습니다. 공유하려면 기록이 어디에 저장되고 다른 기기가 어떤 권한으로 어떻게 읽는지 구현해야 합니다. 버튼 이름이 동작을 설명해야 하지만, 그 이름 자체가 동작을 구현하지는 않습니다. 오히려 기존 기능과 다른 이름을 붙이면 사용자에게 잘못된 기대를 줄 수 있습니다.

## 3.6 입력 검사에는 여러 단계가 있다

브라우저의 `required` 같은 기본 검사는 사용자에게 빠르게 문제를 알려 주는 데 도움이 됩니다. 하지만 모든 요구사항을 해결하지는 않습니다. 예를 들어 글자 입력창에 공백만 여러 개 넣으면, 길이는 있지만 의미 있는 주제는 없을 수 있습니다. 앞 트랙에서 문자열을 정리했던 것처럼 앞뒤 공백을 제거한 뒤 실제 내용이 남는지 확인해야 합니다. 이것은 뒤에서 `trim()`으로 구현하겠습니다.

검사는 사용자 경험과 데이터의 의미를 함께 생각합니다. ‘30’이라는 숫자를 입력했어도 단위가 초인지 분인지 다르면 기록의 뜻이 달라집니다. 그래서 label에 ‘분’을 적었습니다. 숫자 범위가 맞아도 업무상 허용되지 않는 조합이 있을 수 있습니다. 기본 요소의 검사, JavaScript의 규칙 검사, 실제 서비스를 만들 때의 서버 검사를 서로 대체물로 생각하지 않아야 합니다.

또한 브라우저에서 조건을 적었다고 외부의 잘못된 요청까지 모두 막는 것은 아닙니다. 사용자는 화면을 통하지 않고 서버에 요청을 보낼 수도 있습니다. 서버가 있는 서비스라면 서버는 자신이 받는 값을 다시 검사해야 합니다. 여기서는 개인 학습용 브라우저 앱을 만들지만, 앞으로 AI가 ‘프런트에서 검사했으니 안전하다’고 말할 때 무엇이 빠졌는지 알아볼 수 있어야 합니다.

### 연습 3-6. required면 충분하다는 주장

공부한 내용 입력창에 `required`를 붙였으니 공백만 있는 기록도 절대 들어올 수 없다는 설명을 들었습니다. 이 설명의 어떤 부분을 추가로 확인해야 할까요?

### 풀이 3-6

기본 필수 검사가 의미 있는 문장까지 판단하는 것은 아닙니다. 공백 문자열을 어떻게 처리할지 요구사항을 정하고, 앞뒤 공백을 정리한 값이 비었는지 확인해야 합니다. 또한 실제로 제출 검사나 JavaScript 검사가 실행되는 경로인지도 확인해야 합니다. 입력 조건을 선언한 것과 모든 추가 경로에서 조건이 지켜지는 것은 별개의 문제입니다.

지금은 입력창, 설명, 입력 종류, 제출의 경계를 만들었습니다. 화면이 아직 소박해 보이는 것은 정상입니다. 다음 장에서는 CSS가 어떤 요소를 골라 어떤 규칙을 적용하는지 배웁니다. 작고 불편한 입력창을 고칠 때도 구조를 다시 만들기보다 필요한 표현 규칙부터 수정할 수 있게 될 것입니다.
