# 11장. 고장 난 웹앱의 원인을 찾고 수정 검증하기

기록장의 추가 버튼이 작동하지 않습니다. 이 말을 들으면 무엇부터 고쳐야 할까요? 버튼이 너무 작아서 못 누르는 것인지, 눌러도 이벤트가 전달되지 않는 것인지, 함수가 시작했지만 입력 검사에서 멈춘 것인지, 저장에 실패한 것인지 아직 알 수 없습니다. ‘안 된다’는 관찰은 출발점이지만 원인은 아닙니다.

트랙3에서는 실행 흐름을 추적하고 가설을 세워 범위를 줄이는 연습을 했습니다. 이번에는 브라우저 화면, 스타일, JavaScript, 요청, 저장을 함께 다룹니다. 도구 이름을 많이 아는 것보다 각 도구가 어떤 질문에 답하는지 이해하는 것이 중요합니다. 무엇을 보아야 하는지 모르면 로그를 수백 줄 모아도 원인은 분명해지지 않습니다.

## 11.1 오류를 재현할 수 있는 문장으로 바꾸기

‘추가 버튼이 안 된다’를 다음처럼 바꾸어 봅시다. ‘주제에HTML, 시간에20을 적고 추가 버튼을 눌렀다. 목록에 새 기록이 생기기를 기대했다. 실제로 목록은 그대로였고 안내문도 바뀌지 않았다. 새로고침 뒤에도 같았다.’ 이것은 기대, 실제, 입력, 행동을 구분한 관찰입니다.

이렇게 적으면 다른 사람이 같은 조건을 만들어 볼 수 있습니다. 오류를 재현한다는 것은 비슷하게 느낀다는 뜻이 아니라, 같은 조건과 동작에서 같은 실패를 다시 관찰하는 것입니다. 매번 다른 입력과 다른 버전을 보면서 고쳤는지 판단하면 결과를 비교하기 어렵습니다.[1][2][3]

처음부터 모든 것을 기록할 필요는 없습니다. 사용한 주소나 앱 버전, 입력값, 누른 순서, 실제 메시지처럼 원인을 좁히는 정보를 남깁니다. 실제 고객 정보나 비밀번호처럼 민감한 입력은 그대로 공유하지 말고 같은 오류를 만드는 안전한 예시값으로 바꾸는 편이 좋습니다. 오류 재현과 개인정보 노출은 같은 목적이 아닙니다.

### 연습 11-1. 더 좋은 오류 보고 고르기

A는 ‘또 안 됨’입니다. B는 ‘시간에0을 입력하면 오류 안내가 나오지만,600을 입력해도 거절됩니다. 요구사항은1~600 허용입니다’입니다. B로 알 수 있는 조사 방향은 무엇인가요?

### 풀이 11-1

상한 경계600을 포함해야 하는데 제외하는 비교 연산자가 있는지 조사할 수 있습니다. 예를 들어 `< 600`과 `<= 600`의 차이가 후보입니다. B만으로 원인이 확정된 것은 아니지만 입력과 기대가 명확해 작은 테스트를 만들 수 있습니다. ‘또 안 된다’는 보고보다 재현과 비교가 쉬워집니다.

## 11.2 보이는 현상을 다섯 영역으로 나누기

웹앱은 여러 역할이 연결된 구조입니다. 첫 번째는 HTML 요소가 실제로 있는지, 두 번째는 CSS가 그 요소를 어떻게 보이게 하는지, 세 번째는 JavaScript가 어떤 값으로 실행되는지, 네 번째는 요청과 응답이 어떻게 끝나는지, 다섯 번째는 저장값을 읽고 쓰는지입니다. 이를 검사 순서의 무조건적인 정답으로 외울 필요는 없습니다. 증상에 따라 출발점이 달라집니다.

버튼이 아예 보이지 않으면 요소가 없는지 또는 스타일로 숨겼는지 살핍니다. 버튼은 보이지만 눌리지 않으면 겹치는 요소나 disabled, 이벤트 연결을 봅니다. 눌렀을 때 오류가 나면 실행 흐름과 실제 값을 봅니다. 로딩만 돌면 요청이 끝났는지와 finally 정리를 봅니다. 다시 열면 기록이 사라지면 저장과 복원 경로를 봅니다.

| 관찰 | 먼저 나눌 질문 |
|---|---|
| 버튼이 안 보임 | 요소가 없나, 있는데 숨겨졌나 |
| 버튼이 보이지만 무반응 | 입력이 도착하나, 처리 함수가 연결되었나 |
| 누르면 예외 발생 | 어느 줄에서 어떤 값으로 실패했나 |
| 로딩이 계속됨 | 요청이 끝나지 않았나, 끝났는데 표시를 안 지웠나 |
| 새로고침 뒤 사라짐 | 저장하지 않았나, 저장했는데 복원하지 않았나 |

이 구분은 문제를 넘겨짚기 위한 표가 아닙니다. 서로 다른 원인을 같은 ‘안 됨’으로 묶지 않기 위한 질문입니다. 실제 증거를 본 뒤 가설을 바꿀 수 있어야 합니다.

### 연습 11-2. 색이 안 바뀌는 두 원인

A앱은 CSS 파일 요청이404이고, B앱은 CSS를 정상으로 받았지만 더 구체적인 다른 규칙이 적용됩니다. 두 앱에 같은 강제 색상 규칙을 더하는 것이 적절할까요?

### 풀이 11-2

A는 파일 연결이나 게시 경로를 먼저 고쳐야 하고, B는 규칙의 적용 관계를 확인해야 합니다. A에 규칙을 더 적어도 해당 파일을 못 받으면 적용되지 않습니다. B는 파일을 이미 받았으므로 경로를 바꾸는 것이 원인 해결이 아닐 수 있습니다. 겉으로 비슷한 결과라도 실패한 단계가 다릅니다.

## 11.3 콘솔에서 값의 종류와 오류 위치를 읽기

다음 코드는 숫자처럼 보이는 문자열을 그대로 더합니다.

```javascript console
const rawMinutes = "20";
const total = 10 + rawMinutes;
console.log(total);
console.log(typeof rawMinutes);
```

```text
1020
string
```

결과만 보면 덧셈이 틀린 것처럼 느껴지지만, 실제로는 문자열 연결이 일어났습니다. typeof로 입력값의 종류를 관찰하면 가설을 좁힐 수 있습니다. 입력창에는20이 보여도 JavaScript의 value는 문자열일 수 있다는7장의 설명과 연결됩니다.

콘솔에 로그를 넣을 때는 ‘여기 왔다’만 반복하기보다 어떤 값을 확인하려는지 정하는 것이 좋습니다. 예를 들어 제출 함수에 진입했는지, 정리한 문자열이 비었는지, 숫자로 바꾼 결과가 유효한지 각각 질문이 달라집니다. 같은 값을 모든 줄에 출력하면 로그가 많아져도 새로운 정보를 얻지 못할 수 있습니다.

오류 메시지에는 실패한 파일과 줄 위치, 호출 경로가 함께 나타날 수 있습니다. 메시지의 마지막 영어 단어만 복사하기보다 첫 오류가 어디서 발생했는지 확인합니다. 하나의 오류 때문에 아래 기능들이 연쇄적으로 멈출 수도 있기 때문입니다. 가장 먼저 실패한 연결이 무엇인지 찾는 편이 수정 범위를 줄이는 데 도움이 됩니다.[1][3][4]

### 연습 11-3. 출력은 맞는데 계산이 틀린 입력

입력값을 console.log로 보니30이 찍혔습니다. 개발자는 ‘숫자가 맞다’고 결론 내렸습니다. 어떤 정보를 더 확인해야 하고 이유는 무엇인가요?

### 풀이 11-3

`typeof` 같은 방법으로 값의 종류도 확인해야 합니다. 콘솔에서30처럼 보인다는 사실만으로 숫자30과 문자열"30"을 확실히 구별했다고 할 수 없습니다. 실제 연산에서 문자열 연결이 되는지 숫자 덧셈이 되는지 영향을 주는 정보입니다. 표시된 모양과 내부 값의 종류를 함께 봅니다.

## 11.4 중단점은 고장을 만드는 버튼이 아니다

브라우저 개발자 도구에서는 특정 줄에서 실행을 멈추는 중단점을 둘 수 있습니다. 프로그램을 일부러 망가뜨리는 것이 아니라, 그 순간 변수값과 호출 상태를 관찰하기 위해 잠시 멈추는 것입니다. 한 줄씩 진행하면 어떤 조건을 통과했고 어느 대입에서 값이 바뀌었는지 볼 수 있습니다.[4]

예를 들어 제출 함수가 시작되는 줄에 중단점을 둡니다. 버튼을 눌러도 그곳에 멈추지 않으면 함수 진입 전 연결을 조사합니다. 멈췄다면 입력값과 조건을 읽습니다. 정상이라고 생각한 입력이 빈 문자열로 읽혔다면 잘못된 입력 요소를 선택했거나 너무 이른 시점에 값을 읽은 후보가 있습니다. 값을 관찰한 뒤에 가설을 바꾸는 것입니다.

개발자 도구의 정확한 메뉴와 단축키는 브라우저·기기에 따라 다릅니다. 데스크톱의 단축키를 갤럭시 태블릿에서 똑같이 누르라고 요구하지 않겠습니다. 모바일에서 전체 개발자 도구를 열기 어렵다면 교재의 작은 예제를 분리해서 실행하거나, 안전한 입력과 오류 메시지·동작 순서를 남겨 AI에게 같은 조건의 브라우저 테스트를 요구할 수 있습니다. 도구를 직접 열 수 있는 환경에서는 요소·콘솔·네트워크 관찰을 더할 수 있습니다.

중요한 것은 ‘도구를 열었다’가 아니라 ‘어느 줄에 도달했고 그때 무엇이었는가’를 알게 되는 것입니다. 화면 캡처만으로 보이지 않는 값은 실행 로그나 중단점이 필요할 수 있습니다. 반대로 버튼 위를 덮은 요소는 값 로그만으로 찾기 어려울 수 있습니다.

### 연습 11-4. 함수 입구까지 오지 않는 클릭

추가 처리 함수 첫 줄에 관찰 코드를 넣었는데 버튼을 눌러도 아무 기록이 남지 않습니다. 입력값 계산식을 먼저 고칠까요, 이벤트 전달 경로를 먼저 볼까요?

### 풀이 11-4

먼저 이벤트 전달 경로를 봅니다. 실제 버튼에 리스너를 연결했는지, 버튼이 비활성인지, 폼의 기본 유효성 검사에서 제출 자체가 막힌 것인지, 다른 요소가 클릭을 받는지 확인할 수 있습니다. 함수에 진입하지 않은 상태에서 내부 덧셈을 바꾸는 것은 관찰과 연결되지 않는 수정입니다.

## 11.5 계산 규칙은 화면에서 떼어 작게 시험하기

브라우저 화면 전체를 매번 열지 않고도 검사할 수 있는 규칙이 있습니다. 시간 범위를 검사하는 함수를 예로 들겠습니다.

```javascript console
function validMinutes(value) {
  return Number.isInteger(value) && value >= 1 && value <= 600;
}

function expectEqual(actual, expected, label) {
  if (actual !== expected) {
    throw new Error(label + ": 기대값과 실제값이 다릅니다.");
  }
}

expectEqual(validMinutes(1), true, "최솟값");
expectEqual(validMinutes(600), true, "최댓값");
expectEqual(validMinutes(0), false, "최솟값 바깥");
expectEqual(validMinutes(601), false, "최댓값 바깥");
expectEqual(validMinutes(1.5), false, "소수");
expectEqual(validMinutes("30"), false, "문자열");
console.log("시간 규칙 6개 검사 통과");
```

```text
시간 규칙 6개 검사 통과
```

expectEqual은 이 교재에서 만든 작은 검사 함수입니다. 실제값과 기대값이 다르면 예외를 발생시킵니다. 모든 검사를 통과했을 때만 마지막 출력까지 도달합니다. ‘검사 통과’라는 문자열을 항상 출력하는 것과 다릅니다. 검사가 실패하면 그 사실이 드러나는 구조가 필요합니다.

이 함수가 통과했다고 기록장 전체가 정상인 것은 아닙니다. 입력창에서 문자열을 숫자로 변환하는 과정, 제출 이벤트, 저장과 화면 갱신은 아직 별도 검사입니다. 작은 규칙 검사와 사용자 동작 검사는 서로 다른 범위를 다룹니다.[1][2]

수정할 때는 처음 고치려던 오류만 확인하지 말고 기존에 정상인 사례도 다시 확인합니다. 이를 회귀 검사라고 부릅니다. 예를 들어600을 허용하도록 고치면서601도 허용하게 만들 수 있습니다. 한 경계를 고친 뒤 다른 경계가 유지되는지 보는 것입니다.

### 연습 11-5. 테스트를 지워 통과시킨 경우

600을 허용해야 하는데 함수가 거절합니다. AI가 ‘검사 안정화’를 위해600 테스트 줄을 지웠습니다. 이것은 기능을 고친 것일까요? 어떤 변경을 요구해야 할까요?

### 풀이 11-5

아닙니다. 실패를 발견하던 검사를 제거한 것입니다. 요구사항이600을 포함한다면 구현을 수정하고600이 통과하는지 다시 검사해야 합니다. 또한601이 여전히 거절되는지도 확인합니다. 테스트의 목적은 녹색 표시를 만드는 것이 아니라 요구사항과 실제 결과의 어긋남을 발견하는 데 있습니다.

## 11.6 저장과 네트워크는 일부러 실패시켜 보기

정상 데이터만 사용하면 실패 처리는 한 번도 실행되지 않을 수 있습니다. 로컬 저장이 허용되지 않는 상황, JSON이 깨진 상황, 주제 요청이404인 상황, 응답이 늦는 상황을 따로 만들어 보아야 합니다. 실제 사용자의 원본 데이터를 망가뜨려 시험하는 것이 아니라 분리된 테스트 데이터와 환경에서 확인하는 것입니다.

주제 요청에서는 요청 주소, 상태 코드, 받은 본문, 걸린 시간을 확인합니다. 요청이 아예 시작되지 않은 것인지, 요청은 나갔는데 응답이 실패한 것인지, 응답은 왔는데 렌더링이 실패한 것인지 나눕니다. 네트워크 목록에서 응답이 끝난 것을 확인했는데 로딩만 남아 있다면 화면 상태 정리가 후보입니다. 반대로 요청이 계속 진행 중이라면 시간 제한과 취소 경로를 살펴야 합니다.[4][5]

저장 검사에서는 정상 기록을 몇 개 만든 뒤 새로고침하고 같은 값인지 확인합니다. 삭제와 완료 표시 뒤에도 반복합니다. 잘못된 JSON을 넣은 테스트에서는 앱이 원본을 빈값으로 덮어쓰지 않았는지까지 확인합니다. 오류 메시지가 나온다는 사실만으로 데이터가 보존됐다고 확정하지 않습니다. 저장소의 실제 문자열도 대조해야 합니다.

### 연습 11-6. 오류 안내는 있는데 데이터는 사라졌다

손상된 저장값을 넣었더니 앱이 ‘읽기 실패’라고 안내합니다. 그런데 개발자가 그 전에 빈 목록으로 저장했습니다. 이 검사는 무엇을 함께 확인하지 못했나요?

### 풀이 11-6

오류 안내의 존재만 확인하고 원본 보존을 확인하지 못했습니다. 테스트 전 저장 문자열과 테스트 뒤 문자열을 비교해야 합니다. 정상 복구처럼 보이는 메시지와 실제 데이터 변경이 다를 수 있습니다. 사용자의 기록을 다루는 기능에서는 화면뿐 아니라 저장된 상태를 확인하는 검사가 필요합니다.

## 11.7 파일 수정, 게시, 기기 수신을 구분하기

코드를 고쳐서 로컬 테스트가 통과했습니다. 그런데 사용자의 앱에는 이전 내용이 보입니다. 여기서는 코드의 논리만 보는 것보다 어떤 파일이 실제로 사용되는지 확인해야 합니다. 수정한 파일이 운영 경로에 게시됐는지, 게시된 파일의 버전이 무엇인지, 기기가 새 파일을 받았는지 각각 확인합니다.

캐시는 원인 후보 중 하나입니다. 그러나 확인 없이 브라우저의 모든 데이터를 지우는 것은 학습 기록도 잃게 할 수 있습니다. 먼저 정확한 주소와 버전, 게시 상태, 받은 파일을 비교하는 편이 안전합니다. 필요한 경우에도 캐시와 앱의 사용자 데이터는 구분해 처리해야 합니다. ‘초기화하면 된다’는 말이 무엇을 지우는지 분명해야 합니다.

AI에게 수정을 맡길 때도 요청을 작게 만들 수 있습니다. ‘앱이 안 되니 완벽하게 다시 만들어’보다 ‘600분 입력을 정상 허용해야 하는데 거절한다.1과600은 통과,0과601은 실패하는 검사를 유지하면서 비교 조건만 확인해 달라’는 요청은 작업 범위가 분명합니다. AI가 만든 수정이 맞는지는 결과와 검사를 통해 확인합니다. 설명이 자신감 있다는 사실은 실행 증거가 아닙니다.

### 연습 11-7. 완료 보고를 읽고 남은 질문 찾기

보고서에 ‘코드 수정 완료, 단위 테스트6개 통과’라고 적혀 있습니다. 사용자의 실제 휴대폰에도 반영됐다고 말하려면 무엇이 더 필요한가요?

### 풀이 11-7

운영 게시가 성공했는지와 게시된 파일이 수정본인지 확인해야 합니다. 이어서 실제 기기나 앱이 그 버전을 받았는지를 확인해야 합니다. 단위 테스트는 규칙의 일부를 검사한 결과이지 배포와 수신의 증거가 아닙니다. 실제 기기를 확인하지 못했다면 그 범위를 남겨야 합니다.

다음 장에서는 기록장을 하나의 프로그램으로 완성합니다. 새 문법을 과도하게 더하기보다 지금까지의 구조, 입력, 상태, 저장, 요청과 검사를 연결하겠습니다. 완성 코드를 보는 것으로 끝내지 않고, 요구사항 하나를 바꾸고 왜 그 위치를 고쳤는지 설명하는 것까지가 마지막 연습입니다.

다음 5종의 공개 본문을 참고했습니다. 오류 보고와 시간 검사, 데이터 보존 시나리오는 이 기록장에 맞춰 새로 작성했습니다.

1. [Eloquent JavaScript, 4th Edition — Bugs and Errors](https://eloquentjavascript.net/08_error.html), Marijn Haverbeke, 2024. 테스트·오류·예외 처리의 공개 본문을 확인했습니다. 2024년 보조 교재입니다.
2. [CS50 Web — Lecture 7: Testing, CI/CD](https://cs50.harvard.edu/web/notes/7/), Harvard University. 테스트의 역할과 자동 검증 관련 공개 강의 본문을 확인했습니다. 대규모 배포 체계 전체를 이번 초보자 수업의 필수 실습으로 요구하지 않습니다.
3. [MDN — What went wrong? Troubleshooting JavaScript](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Scripting/What_went_wrong), MDN Web Docs. 문법·논리 오류와 관찰을 통한 수정의 공개 교육 본문을 확인했습니다.

5. [Full Stack Open — Fundamentals of Web apps](https://fullstackopen.com/en/part0/fundamentals_of_web_apps/), University of Helsinki. 브라우저 도구로 문서와 요청을 확인하는 공개 본문을 참고했습니다. 도구로 확인한 범위를 넘어 실기기 검증을 주장하지 않는 방향으로 구성했습니다.
