# 6장. 휴대폰·태블릿에서도 읽고 누를 수 있는 화면

태블릿에서 보기 좋게 만든 기록장을 휴대폰으로 열었습니다. 입력창이 옆으로 밀려나고 버튼의 끝이 잘립니다. 글자가 작아서 크게 바꾸니 이번에는 안내문 아래쪽이 사라집니다. 이 문제를 ‘휴대폰이 작아서 어쩔 수 없다’고 끝내면 실제 사용하는 앱이 되기 어렵습니다. 화면 크기와 글자 크기가 달라질 수 있다는 조건을 처음부터 배치에 포함해야 합니다.

반응형 화면은 같은 문서를 다양한 크기의 공간에서 사용할 수 있게 구성하는 방식입니다. 기기 이름마다 완전히 별개의 페이지를 만드는 것만을 뜻하지 않습니다. 좁으면 한 열, 넓으면 두 열처럼 내용이 사용할 수 있는 공간에 따라 배치가 달라지게 할 수 있습니다. 이 장에서는 ‘작게 줄이면 다 들어간다’가 아니라 ‘읽고 조작할 수 있는 상태를 유지한다’를 기준으로 기록장을 고칩니다.[1][2][3][4]

## 6.1 기기 화면과 페이지가 사용하는 폭

1장에서 문서의 head에 다음 줄을 넣었습니다.

```html
<meta name="viewport" content="width=device-width, initial-scale=1">
```

viewport는 페이지를 보여 주는 영역과 관련된 개념입니다. 이 줄은 작은 화면에서 기기의 너비에 맞춰 페이지를 다루는 기본 설정에 사용합니다. 이 설정 없이 넓은 페이지를 축소해서 보여 주는 식으로 처리되면, 좁은 화면을 위한 스타일을 생각한 대로 보기 어려울 수 있습니다.

이 줄을 넣었다고 자동으로 모든 요소가 반응형이 되지는 않습니다. 본문에 `width: 1000px`인 상자를 고정해 놓으면 여전히 좁은 화면에서 넘칠 수 있습니다. 기본 설정과 실제 배치 규칙이 함께 맞아야 합니다. 브라우저 확대를 막는 속성을 추가해 강제로 화면을 맞추는 방법은 이 책의 해결책으로 쓰지 않겠습니다. 글자를 크게 보려는 사용자의 행동을 막기 때문입니다.

‘휴대폰 화면이 몇 픽셀인가’라는 숫자를 볼 때에도 주의가 필요합니다. 사진 해상도의 물리적 픽셀 수와 CSS에서 페이지 배치에 사용하는 픽셀 수는 같지 않을 수 있습니다. 이 책에서 화면 폭360px을 테스트한다고 하면 CSS의 화면 영역을 말하는 것입니다. 기기 광고의 해상도 숫자를 그대로 CSS 너비로 넣는 것이 아닙니다.

### 연습 6-1. viewport만 넣었는데 계속 넘친다

viewport 설정은 있지만 main에 `width: 1000px`가 있습니다. 휴대폰에서 가로로 넘친다고 합니다. 글자를 절반 크기로 줄이기 전에 어떤 규칙을 먼저 확인해야 할까요?

### 풀이 6-1

main의 고정 너비를 먼저 확인합니다. 사용 가능한 공간을 넘지 않도록 유연한 너비와 적절한 최대 너비를 사용할 수 있습니다. viewport는 페이지를 다루는 기본 조건이고, 개별 요소의 고정 크기를 무효로 만드는 명령이 아닙니다. 작은 글자로1000px 상자의 내용을 채워도 상자 자체가 휴대폰에 맞는 것은 아닙니다.

## 6.2 좁은 화면의 기본값에서 출발하기

기록장의 입력 두 개를 기본적으로 세로로 놓고, 충분히 넓을 때 가로로 나란히 놓겠습니다. CSS의 미디어 쿼리는 이런 조건에 맞는 규칙을 적용하는 데 사용합니다.

```css
.fields {
  display: grid;
  grid-template-columns: 1fr;
  gap: 16px;
}

@media (min-width: 600px) {
  .fields {
    grid-template-columns: minmax(0, 2fr) minmax(0, 1fr);
  }
}
```

기본 규칙에서는 한 열입니다. 화면 너비가600px 이상이라는 조건에 해당하면 안쪽 규칙이 적용되어 두 열이 됩니다. `@media`의 중괄호 안에 다시 `.fields` 규칙이 들어가는 형태입니다. 바깥 중괄호는 조건의 범위이고, 안쪽 중괄호는 선택자의 선언 범위입니다.

600이라는 수는 이 기록장의 예시 기준입니다. 모든 휴대폰과 태블릿을 나누는 공식 경계가 아닙니다. 실제로 내용을 넣어 보면서 한 열이 편한 범위와 두 열이 충분히 들어가는 범위를 찾는 것이 더 중요합니다. 한 종류의 기기 이름에만 맞추면 창을 나누어 쓰거나 화면을 회전했을 때 예상과 달라질 수 있습니다.

미디어 쿼리가 없어도 유연한 너비, 줄바꿈, 최대 너비만으로 많은 배치를 안정화할 수 있습니다. 작은 차이마다 조건을 수십 개 추가하기보다 기본 흐름이 얼마나 잘 적응하는지 먼저 확인합니다. 조건이 너무 많으면 어느 규칙이 현재 적용되는지 읽기 어려워집니다.

### 연습 6-2. 599와 600에서 무엇이 달라질까?

위 코드에서 CSS 화면 너비가599px인 경우와600px인 경우를 비교해 보세요. 600px에서만 입력 자체가 새로 생성되는 것일까요?

### 풀이 6-2

599px에서는 기본 한 열 규칙을 사용하고,600px에서는 두 열 규칙이 적용됩니다. 입력 요소가 새로 생성되는 것이 아니라 같은 요소의 배치가 바뀝니다. JavaScript로 값을 지우거나 폼을 새로 만드는 코드가 없으므로, 배치 변경 그 자체를 입력 내용의 초기화로 이해하면 안 됩니다.

미디어 쿼리는 표현 조건입니다. 데이터와 화면 표현을 구분하는 연습이 다음 장의 JavaScript로 이어집니다.

## 6.3 긴 글자는 오류가 아니라 정상적인 입력일 수 있다

샘플에 ‘HTML’처럼 짧은 단어만 넣으면 화면이 잘 맞아 보입니다. 실제 사용자는 ‘JavaScript에서 입력값을 숫자로 바꾸고 조건을 검사하는 법’처럼 긴 문장을 적을 수 있습니다. 이때 화면이 깨지면 사용자가 잘못 썼다는 뜻일까요? 허용한 길이 안의 입력이라면 배치가 그 조건을 감당해야 합니다.

기록 제목을 한 줄로만 고정하고 높이도 고정하면 긴 글자는 잘릴 수 있습니다. 중요한 정보를 일부러 줄여 보여 주는 설계가 필요한 경우도 있지만, 학습 내용을 읽는 본문에서는 전체 내용을 볼 수 있는 길을 남겨야 합니다. 아래 규칙은 긴 단어가 있을 때 줄바꿈 가능성을 넓히는 예입니다.

```css
.record-topic {
  overflow-wrap: anywhere;
}

.record {
  min-width: 0;
}
```

`overflow-wrap: anywhere`는 긴 문자열 때문에 넘칠 때 줄을 나눌 수 있게 하는 데 사용합니다. `min-width: 0`은 Flexbox나 Grid 항목이 내용의 최소 너비 때문에 줄어들지 못하는 상황에서 도움이 될 수 있습니다. 단순히 화면 전체에 `overflow: hidden`을 주어 넘친 내용을 잘라 버리는 것과 목적이 다릅니다.

코드는 문장과 다른 선택이 필요할 수 있습니다. 긴 코드 줄을 읽을 때 줄바꿈이 문법의 실제 줄바꿈처럼 오해되지 않도록 해야 합니다. 필요하면 코드 상자만 가로로 이동하게 하거나, 줄을 나누어 표시하되 원본 줄 구분을 유지하는 방식을 사용할 수 있습니다. 본문 전체가 옆으로 밀리는 문제와 코드 내부의 긴 줄을 읽는 문제를 같은 것으로 처리하지 않습니다.

### 연습 6-3. 가로 넘침을 숨기는 해결

긴 기록 때문에 페이지가 가로로 넘칩니다. AI가 body에 `overflow-x: hidden`만 추가했습니다. 스크롤 막대는 사라졌지만 기록 끝부분도 보이지 않습니다. 무엇을 추가로 확인해야 할까요?

### 풀이 6-3

넘침의 원인이 된 요소의 너비, 최소 너비, 줄바꿈, 고정 크기를 확인해야 합니다. 스크롤 막대를 감췄다고 내용이 읽을 수 있는 상태가 된 것은 아닙니다. 기록의 전체 문장이 실제로 보이는지 확인하고, 필요하면 요소가 줄어들거나 여러 줄로 늘어날 수 있도록 수정해야 합니다.

검사 기준을 ‘가로 스크롤 막대가 없는가’ 하나로만 정하면 이런 잘림을 놓칩니다. ‘필요한 내용이 잘리지 않고 보이는가’를 함께 보아야 합니다.

## 6.4 다크 모드는 색 두 개의 이름이 아니라 전체 관계다

밝은 화면에서는 어두운 글자가 잘 보입니다. 어두운 화면에서는 배경에 맞춰 글자, 테두리, 입력창, 링크, 오류 안내를 함께 살펴야 합니다. 검정 배경을 정했다고 자동으로 모든 글자가 읽기 좋아지는 것은 아닙니다. 일부 컴포넌트에 고정된 어두운 글자색이 남아 있을 수 있기 때문입니다.

공통 색을 사용자 정의 속성으로 모으면 테마를 연결하기 쉽습니다. 다음 예제는 운영체제의 색 선호에 반응하는 방식입니다. 사용자가 직접 누르는 테마 버튼의 상태를 저장하는 기능과는 별개입니다.

```css
:root {
  --paper: #f6f4ee;
  --ink: #202734;
  --field: #ffffff;
  --line: #69737d;
}

@media (prefers-color-scheme: dark) {
  :root {
    --paper: #151a20;
    --ink: #edf1f5;
    --field: #222a34;
    --line: #a0adba;
  }
}

body {
  background: var(--paper);
  color: var(--ink);
}

input {
  background: var(--field);
  color: var(--ink);
  border-color: var(--line);
}
```

이 규칙은 공통 값을 바꾸고 그 값을 사용하는 요소에 연결합니다. 버튼이나 오류 안내가 다른 색을 따로 사용한다면 그 조합도 확인해야 합니다. 색상표 몇 개가 있다는 이유만으로 접근성 기준을 모두 충족했다는 뜻은 아닙니다. 실제 전경색과 배경색의 대비, 사용자가 내용을 구별할 수 있는지를 도구와 눈으로 함께 점검해야 합니다.[5]

오류를 빨간색으로만 구별하는 것도 피합니다. 색을 구별하기 어려운 사용자가 있고, 색이 보이더라도 왜 오류인지 문장이 없으면 다음 행동을 알기 어렵습니다. ‘시간은1~600분의 정수로 적어 주세요’처럼 내용이 있는 안내를 함께 보여 줍니다. 완료 상태도 색 하나만 바꾸는 것보다 ‘완료’ 같은 텍스트를 함께 제공하는 것이 명확합니다.

### 연습 6-4. 어두운 화면에서 사라진 입력값

본문 글자는 밝게 바뀌었지만 입력한 글자는 거의 보이지 않습니다. input의 background는 어두운 값이고 color는 예전의 어두운 값으로 남았습니다. 어떤 수정을 하고 어떤 상태를 다시 확인해야 할까요?

### 풀이 6-4

input의 글자색도 현재 테마의 `--ink` 등에 연결합니다. 그다음 빈 입력창의 안내, 실제 입력값, 선택된 텍스트, 비활성 상태와 오류 상태를 살펴봅니다. 본문 한 곳만 확인하고 다크 모드 전체가 정상이라고 판단하지 않는 것입니다.

## 6.5 보이는 버튼과 누를 수 있는 버튼

버튼이 보여도 누르기 어려울 수 있습니다. 작은 글자만 터치할 수 있거나, 다른 요소가 위를 덮고 있거나, 버튼이 실제로 비활성화되어 있을 수 있습니다. 이 문제는 모양, 배치, 동작이 만나는 지점입니다. 우선 터치할 공간을 충분히 만들고 주변 요소와 구분해야 합니다.

다음의48px은 이 예제에서 선택한 버튼 최소 높이입니다. 모든 접근성 기준을 이 숫자 하나로 충족한다는 뜻은 아닙니다.

```css
button {
  min-height: 48px;
  padding: 10px 16px;
}

button:focus-visible,
input:focus-visible,
a:focus-visible {
  outline: 3px solid #aa6300;
  outline-offset: 3px;
}
```

초점은 키보드로 조작할 때 현재 대상이 어디인지 알려 주는 상태입니다. `focus-visible`에 표시를 주면 사용자가 이동한 위치를 더 쉽게 볼 수 있습니다. 모양이 거슬린다는 이유로 모든 outline을 제거하고 대체 표시도 넣지 않으면 키보드 사용자가 현재 위치를 잃을 수 있습니다.

가능하면 기본 `button`과 `a`를 목적에 맞게 사용합니다. 이동하는 것은 링크, 어떤 일을 실행하는 것은 버튼이라는 출발점이 유용합니다. 클릭 이벤트를 붙인 `div`는 겉보기 버튼이 될 수 있지만, 기본 버튼이 제공하는 키보드 동작과 의미를 저절로 얻는 것은 아닙니다. 처음부터 기본 요소를 사용하면 직접 보완해야 할 부분을 줄일 수 있습니다.[5]

투명한 상자가 버튼 위를 덮는 경우도 있습니다. 버튼의 클릭 함수만 계속 고쳐도 해결되지 않는 이유입니다. 클릭이 실제로 어느 요소에 도착하는지, 겹치는 요소가 있는지, `disabled`가 설정되어 있는지를 확인해야 합니다. 반대로 숨겨져야 하는 대화상자가 투명하기만 하고 입력을 가로채는 상황도 주의해야 합니다.

### 연습 6-5. 함수는 정상인데 터치가 안 된다

기록 추가 함수를 직접 실행하면 목록이 바뀝니다. 그런데 화면의 버튼을 손가락으로 누르면 아무 반응이 없습니다. 함수 내부만 고치기 전에 볼 후보를 세 가지 적어 보세요.

### 풀이 6-5

버튼이 비활성화되어 있는지, 다른 요소가 위를 덮는지, 실제 버튼에 이벤트가 연결되어 있는지를 볼 수 있습니다. 터치 영역이 너무 작거나 화면 밖으로 밀렸는지도 후보입니다. 함수가 작동한다는 사실은 그 함수까지 사용자의 입력이 제대로 전달된다는 증거와 다릅니다. 전달 경로를 나누어 확인하는 것입니다.

## 6.6 화면 검사를 실제 사용 장면으로 바꾸기

검사는 예쁜 스크린샷 한 장을 얻는 일이 아닙니다. 좁은 화면, 넓은 화면, 긴 글자, 빈 목록, 오류 안내, 글자 확대, 키보드 이동을 각각 넣어 보아야 합니다. 레이아웃이 깨지는 조건은 기본 샘플과 다를 수 있습니다. 특히 입력 오류 메시지가 나타났을 때 버튼을 밀어내거나, 완료 표시가 붙었을 때 제목이 잘리는 경우는 정상 화면만 보면 놓칩니다.

다음 표는 이 기록장에 사용할 관찰 계획입니다. 특정 표준의 완전한 적합성 검사를 대신하는 표는 아닙니다.

| 조건 | 확인할 실제 결과 |
|---|---|
| CSS 너비360px | 입력창·본문·버튼이 화면을 벗어나지 않는가 |
| 넓은 태블릿 화면 | 본문이 너무 넓게 퍼지지 않고 두 열이 자연스러운가 |
| 글자 크기 확대 | 안내문과 버튼 글자가 잘리지 않는가 |
| 긴 제목과 긴 오류 안내 | 높이가 늘어나고 다음 요소가 겹치지 않는가 |
| 키보드로 이동 | 현재 위치를 볼 수 있고 버튼을 실행할 수 있는가 |
| 밝은·어두운 배경 | 입력값·완료 상태·오류 이유를 구별할 수 있는가 |

### 연습 6-6. 통과했다는 말의 범위

개발자가 ‘360px 화면의 스크린샷이 예쁘게 나왔으므로 모든 갤럭시에서 검증 완료’라고 말합니다. 어떤 부분을 더 정확하게 표현해야 할까요?

### 풀이 6-6

360px이라는 특정 CSS 화면 조건에서 관찰한 결과라고 표현해야 합니다. 실제 기기의 브라우저, 글꼴, 입력 키보드, 화면 확대, 터치, 저장과 업데이트 수신까지 모두 검사한 것은 아닙니다. 검사를 작게 했다고 가치가 없는 것은 아닙니다. 확인한 범위를 정확하게 말하고 확인하지 않은 조건을 남기는 것이 중요합니다.

이제 화면은 단순히 예쁘게 보이는 문서를 넘어 여러 조건에서 읽고 누를 수 있는 구조가 되었습니다. 다음 장에서는 Python에서 배운 변수와 함수, 조건문을 JavaScript로 옮겨 읽습니다. 새 언어의 기호를 만나더라도 이미 아는 개념과 연결하면 버튼의 동작을 이해할 준비를 할 수 있습니다.

## 이 장의 참고자료와 확인 범위

다음 5종의 공개 자료를 참고했습니다. 기기 너비와 버튼 크기는 이 교재의 예시 설계값이며 공식 기준 전체를 대표하는 수치가 아닙니다.

1. [Learning Web Design, 6th Edition — 공식 목차](https://learningwebdesign.com/toc.html), Jennifer Niederst Robbins, 2025. 3장과19장의 장치·접근성·반응형·viewport·미디어 쿼리 관련 공개 목차를 참고했습니다. 유료 본문 전체를 통독한 것은 아닙니다.
2. [Murach’s HTML and CSS, 6th Edition](https://www.murach.com/shop/html-and-css-6th-edition-detail), Zak Ruvalcaba·Anne Boehm·Mary Delamater, 2024. 반응형 설계·미디어 쿼리·모바일 우선·테스트 관련 출판사 공개 항목을 확인한 보조 자료입니다.
3. [MDN — Responsive design](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/CSS_layout/Responsive_Design), MDN Web Docs. 유연한 배치·미디어 쿼리·viewport에 관한 공개 본문을 확인했습니다.
4. [web.dev — Learn Responsive Design](https://web.dev/learn/design), Google web.dev. 다양한 화면과 입력 방식에 적응하는 공식 교육 과정의 공개 자료를 확인했습니다.
5. [W3C WAI — Easy Checks](https://www.w3.org/WAI/test-evaluate/easy-checks/), W3C Web Accessibility Initiative. 접근성의 첫 점검에 관한 공개 자료를 참고했습니다. 확인 시 공개 페이지에 Draft 표시가 있었으며, 이 장의 점검표를 완전한 접근성 인증 절차로 표현하지 않습니다.
