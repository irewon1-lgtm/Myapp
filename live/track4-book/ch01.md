# 1장. 웹페이지는 어떻게 내 화면에 나타날까?

공부한 내용을 기록하는 작은 앱을 만든다고 생각해 봅시다. 화면 위에는 ‘나의 학습 기록장’이라는 제목이 있고, 그 아래에는 오늘 공부한 내용을 적는 입력창과 추가 버튼이 있습니다. 버튼을 누르면 기록이 목록에 나타납니다. 겉으로 보면 한 화면이지만, 그 안에는 서로 다른 일이 함께 들어 있습니다. 제목이 무엇인지 정하는 일, 제목을 어느 크기로 보여 줄지 정하는 일, 버튼을 눌렀을 때 목록을 바꾸는 일은 같은 일이 아닙니다.

이 차이를 모르면 AI가 만들어 준 파일을 받아도 어디를 고쳐야 할지 막막합니다. 제목 한 글자를 바꾸고 싶은데 JavaScript 전체를 다시 만들게 하거나, 버튼이 작아서 누르기 힘든데 서버를 고치려 할 수도 있습니다. 이 책에서 웹을 배우는 출발점은 태그 이름을 많이 외우는 것이 아닙니다. 눈앞의 화면을 몇 가지 역할로 나누어 보고, 바꾸려는 일이 어느 역할에 속하는지 판단하는 것입니다.

이 장에서는 아직 기록을 저장하지 않습니다. 작은 문서 하나가 화면에 나타나는 과정을 이해하고, 이후에 만들 앱의 세 파일을 구별합니다. 뒤의 장에서 기능이 늘어나더라도 이 구별은 계속 사용합니다.

## 1.1 화면을 보여 주는 프로그램과 자료를 보내는 프로그램

인터넷 주소를 눌렀을 때 열리는 Chrome이나 삼성 인터넷 같은 프로그램을 브라우저라고 부릅니다. 브라우저는 받은 자료를 해석하여 화면을 만들고, 우리가 누르거나 입력한 행동에 반응합니다. 여기서 ‘해석한다’는 말은 사람이 문장을 이해한다는 뜻이 아닙니다. 정해진 형식의 문서를 읽고, 그 형식의 규칙에 따라 요소를 만들고 배치한다는 뜻입니다.

서버는 요청을 받고 자료나 처리 결과를 보내주는 쪽입니다. 어떤 서버는 미리 만들어 둔 파일을 보냅니다. 어떤 서버는 요청한 사용자의 기록을 데이터베이스에서 찾아 결과를 만듭니다. 서버가 반드시 특별한 모양의 거대한 컴퓨터라는 뜻은 아닙니다. 이 책에서는 먼저 역할에 집중하겠습니다. 브라우저는 요청하고 보여 주는 쪽, 서버는 요청에 응답하는 쪽입니다. 같은 컴퓨터에서 두 역할을 실행할 수도 있습니다.

예를 들어 브라우저가 ‘기록장 첫 화면을 보내 주세요’라고 요청하면 서버가 HTML 문서를 보낼 수 있습니다. 브라우저는 HTML 안에서 CSS 파일이나 JavaScript 파일의 주소를 발견하고 그것들도 요청할 수 있습니다. 따라서 주소 하나를 눌렀다고 요청도 꼭 하나만 생기는 것은 아닙니다. 제목과 본문은 보이는데 이미지 한 장이 비어 있는 이유도 여기서 이해할 수 있습니다. 문서를 받은 일과 이미지 파일을 받은 일은 따로 성공하거나 실패할 수 있습니다.[3][4][5]

```text
브라우저 → HTML 문서 요청 → 서버
브라우저 ← HTML 문서 응답 ← 서버
브라우저 → 문서에 연결된 CSS 파일 요청 → 서버
브라우저 → 문서에 연결된 JavaScript 파일 요청 → 서버
브라우저 → 자료 해석, 화면 배치, 사용자 행동 처리
```

이 그림은 역할을 구분하려고 순서를 단순화한 것입니다. 실제 브라우저는 여러 파일을 겹쳐서 요청하고, 받은 자료를 처리하면서 화면을 만들기도 합니다. ‘모든 파일을 완전히 받은 뒤에야 무조건 첫 글자가 나온다’라는 규칙으로 외우지 않아야 합니다.

### 연습 1-1. 이미지 하나만 보이지 않는 이유

웹페이지의 제목과 본문은 보이지만 맨 위 사진만 비어 있습니다. 이 상황을 보고 ‘인터넷이 완전히 끊겼다’라고 바로 결론 내려도 될까요? 먼저 확인할 대상을 두 가지 적어 보세요.

### 풀이 1-1

인터넷이 완전히 끊겼다고 바로 확정할 수는 없습니다. 이미 저장해 둔 자료가 보일 수도 있고, 문서 요청은 성공했지만 이미지 요청만 실패했을 수도 있습니다. 사진의 파일 주소가 맞는지, 그 주소로 요청했을 때 파일을 실제로 받을 수 있는지를 먼저 확인할 수 있습니다. 사진을 숨기는 CSS가 있는지도 그다음 후보가 됩니다.

중요한 점은 ‘보이지 않는다’는 결과와 ‘어떤 요청 또는 표시 과정이 실패했다’는 원인을 구별하는 것입니다. 아직 도구를 능숙하게 사용하지 못해도, 한 화면이 여러 자료의 조합이라는 사실을 이해하면 조사 범위를 줄일 수 있습니다.

## 1.2 HTML, CSS, JavaScript를 한 화면에서 구별하기

HTML은 문서의 내용과 구조를 표시합니다. 제목, 문단, 목록, 입력창, 버튼처럼 무엇이 있는지를 나타냅니다. CSS는 그 요소를 어떻게 보여 줄지 정합니다. 글자 크기, 색, 여백, 배치가 여기에 속합니다. JavaScript는 값을 계산하고 조건을 판단하며 사용자 행동에 맞추어 문서나 데이터를 바꾸는 데 사용합니다.[1][2][3]

세 가지가 한 파일에 함께 들어갈 수도 있습니다. 따라서 ‘파일이 세 개니까 기능도 세 가지다’라는 식으로만 구분하면 안 됩니다. 먼저 역할이 있고, 그 역할을 관리하기 쉽도록 파일을 나누는 것입니다. 이 책에서는 파일 이름을 다음과 같이 정하겠습니다.

| 파일 이름 | 맡길 역할 | 수정 요청의 예 |
|---|---|---|
| index.html | 제목, 입력창, 목록 등 문서 구조 | 제목을 ‘공부 기록장’으로 바꾼다 |
| style.css | 글자, 여백, 색, 배치 | 작은 버튼을 더 크게 만든다 |
| app.js | 입력 처리, 계산, 목록 변경 | 빈 내용을 추가하지 못하게 한다 |

`index`, `style`, `app`이라는 이름 자체가 기능을 실행시키지는 않습니다. 예를 들어 JavaScript 파일을 `record.js`라고 이름 지어도 HTML에서 그 파일을 정확히 연결하면 사용할 수 있습니다. 이름은 사람이 정하는 것이고, 어떤 파일을 읽을지는 문서에 적힌 연결 정보가 결정합니다. 앞 트랙에서 `qty`라는 이름을 썼다고 컴퓨터가 자동으로 주문 수량을 알아내는 것이 아니었던 것과 같습니다.

### 연습 1-2. 무엇을 먼저 열어 볼까?

다음 세 요청을 받았습니다. ‘제목을 바꾸기’, ‘본문 줄 사이를 넓히기’, ‘추가 버튼을 눌렀을 때 빈 기록을 거절하기’입니다. 위 표의 구조로 만든 프로젝트라면 각각 어느 파일을 먼저 열어 볼지 정하고 이유를 설명해 보세요.

### 풀이 1-2

제목은 문서에 있는 내용이므로 `index.html`을 먼저 봅니다. 줄 사이 간격은 내용이 아니라 표현 방식이므로 `style.css`를 봅니다. 빈 기록을 거절하는 것은 입력값에 따라 실행을 달리하는 규칙이므로 `app.js`를 봅니다. 실제 프로젝트에서는 제목을 JavaScript가 만들어 넣기도 하므로 이 답이 모든 앱의 절대 법칙은 아닙니다. 지금 우리가 역할을 나눈 예제에서의 출발점입니다.

코드를 조사할 때는 먼저 이 정도 가설을 세우고, 실제로 그 파일이 해당 내용을 담당하는지 확인하면 됩니다. 파일 이름만 보고 확정하는 것도, 아무 판단 없이 모든 파일을 다시 만드는 것도 피하는 것입니다.

## 1.3 아주 작은 문서를 끝까지 읽어 보기

다음은 일부 조각이 아니라 작은 HTML 문서 전체입니다. 별도의 CSS나 JavaScript 파일 없이 제목과 문단을 보여 줍니다. 일반적인 웹 코드 편집 환경에서 HTML 문서로 열면 확인할 수 있습니다. 이 책의 코드 상자는 문법을 설명하는 교재이며, 코드를 읽는 것 자체와 앱 파일을 실행하는 일은 구별해야 합니다.

```html demo
<!doctype html>
<html lang="ko">
  <head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>나의 학습 기록장</title>
  </head>
  <body>
    <h1>나의 학습 기록장</h1>
    <p>오늘은 웹이 화면이 되는 과정을 배웠습니다.</p>
  </body>
</html>
```

맨 위의 `<!doctype html>`은 이 문서를 현대 HTML 문서로 처리하도록 알리는 선언입니다. 그다음 `html` 요소가 전체 문서를 감쌉니다. `lang="ko"`는 문서의 주된 언어가 한국어라는 정보입니다. 브라우저와 보조 기술이 문서를 다루는 데 사용하는 정보이지, 영어 문장을 자동으로 한국어로 번역하는 명령은 아닙니다.

`head`에는 문서에 관한 정보가 들어갑니다. `charset="utf-8"`은 문자를 해석할 때 사용할 인코딩을 알려 줍니다. 한글 같은 문자를 어떤 규칙으로 읽을지 일관되게 정하는 것입니다. `viewport` 줄은 작은 화면에서 페이지 너비를 기기 화면에 맞춰 다루는 데 필요합니다. 지금 모두 외울 필요는 없지만, 모바일용 문서에서 의미 없이 삭제할 줄은 아니라는 점을 알아 두면 됩니다.

`title` 안의 글은 브라우저 탭 등의 문서 제목으로 사용됩니다. 화면 본문에서 큰 제목으로 보이는 것은 `body` 안의 `h1`입니다. 두 곳에 같은 문장을 적었기 때문에 처음에는 하나처럼 느껴질 수 있습니다. 그러나 탭 이름을 바꾸는 일과 본문 제목을 바꾸는 일은 별개입니다.

`p`는 문단입니다. `<p>`로 문단을 시작하고 `</p>`로 끝냅니다. 그 사이의 문장이 문단 내용입니다. 들여쓰기는 사람이 문서의 포함 관계를 읽기 쉽게 해 줍니다. Python의 들여쓰기처럼 이 예제의 문단을 어떤 반복문에 넣는 기능을 하는 것은 아닙니다. HTML의 포함 관계는 태그의 구조로 표현합니다. 언어가 바뀌면 같은 공백도 역할이 달라질 수 있습니다.

### 연습 1-3. 본문 제목만 바꾸기

위 문서에서 브라우저 탭 이름은 그대로 두고, 화면 안의 제목만 ‘승원의 공부 기록’으로 바꾸려 합니다. 어느 줄을 어떻게 바꾸어야 할까요?

### 풀이 1-3

`<h1>나의 학습 기록장</h1>`을 `<h1>승원의 공부 기록</h1>`으로 바꿉니다. `title`은 수정하지 않습니다. 두 글자가 같은 문장이라는 이유만으로 자동 연결되어 있는 것은 아닙니다. 어느 부분이 어디에 나타나는지 구분하고 그 부분만 바꾸는 연습입니다.

반대로 탭 이름만 바꾸고 본문을 그대로 두려면 `title` 안의 내용만 바꾸면 됩니다. 앞으로 화면에 같은 숫자가 여러 번 보이더라도 ‘겉모습이 같다’와 ‘같은 데이터에서 나온다’를 구별해야 합니다.

## 1.4 파일을 연결한다는 것은 무엇일까?

문서가 커지면 모양과 동작을 다른 파일로 분리하는 편이 읽기 쉽습니다. 다음은 `head` 안에 추가할 연결 정보입니다. 문서 전체가 아니라 앞 문서의 `head` 안에 넣을 두 줄입니다.

```html
<link rel="stylesheet" href="style.css">
<script src="app.js" defer></script>
```

`link` 줄은 스타일시트로 사용할 파일이 `style.css`라는 것을 나타냅니다. `href`는 이 연결이 가리키는 주소입니다. `script` 줄의 `src`는 JavaScript 파일의 주소입니다. `defer`는 이처럼 외부의 일반 JavaScript 파일을 연결할 때, HTML 해석을 마친 뒤 스크립트를 실행하도록 하는 속성입니다. 아직 만들어지지 않은 입력창을 너무 일찍 찾는 문제를 피하는 데 도움이 됩니다. 모든 종류의 스크립트 로딩 방식을 이 한 속성으로 설명할 수 있는 것은 아니지만, 이 책의 예제에는 적합합니다.

여기서 경로란 파일을 찾기 위한 위치 표현입니다. `style.css`는 현재 문서의 위치를 기준으로 같은 폴더에 있는 파일을 가리키는 상대 경로입니다. 파일이 `css` 폴더 안에 있다면 `css/style.css`라고 적어야 합니다. 파일을 옮겨 놓고 연결 주소를 그대로 두면 브라우저는 예전 위치에서 찾으려 합니다. CSS 내용을 아무리 고쳐도 잘못된 주소가 저절로 바뀌지는 않습니다.

```text
study-log/
  index.html
  css/
    style.css
  app.js
```

위 구조에서 HTML의 CSS 연결은 `href="css/style.css"`가 됩니다. `/css/style.css`처럼 맨 앞에 `/`를 붙이면 사이트의 루트를 기준으로 찾는 다른 표현이 됩니다. 하위 경로에 게시할 때 결과가 달라질 수 있으므로, 앞의 슬래시를 장식처럼 넣거나 빼지 않아야 합니다.

### 연습 1-4. 코드는 맞는데 꾸밈이 적용되지 않는다

`style.css` 파일을 `assets` 폴더로 옮겼습니다. 그런데 HTML에는 여전히 `href="style.css"`라고 적혀 있습니다. 글자색이 바뀌지 않자 AI가 CSS에 강제 우선순위를 추가하자고 제안합니다. 이때 먼저 고쳐야 할 부분은 무엇인가요?

### 풀이 1-4

먼저 연결 주소를 `href="assets/style.css"`로 바꿔 실제 파일 위치와 맞춥니다. 스타일 규칙이 브라우저에 전달되지 않은 문제라면 규칙의 우선순위를 높여도 해결되지 않습니다. ‘파일을 받았는가’가 ‘받은 규칙 중 무엇이 적용되는가’보다 앞선 확인입니다.

수정 후에는 문서를 다시 열거나 새로고침해 새 연결이 사용되는지 확인합니다. 그래도 바뀌지 않으면 경로의 철자, 파일 이름의 대소문자, 실제로 열고 있는 문서가 수정한 문서인지 차례로 좁혀 볼 수 있습니다.

## 1.5 주소, 응답, 저장된 사본을 구별하기

웹 주소의 예로 `https://example.com/study/index.html`을 생각해 봅시다. `https`는 통신에 사용하는 방식, `example.com`은 접속 대상의 이름, `/study/index.html`은 그 대상 안에서 요청하는 경로입니다. 이 주소는 설명을 위한 예이며, 그곳에 우리의 기록장이 있다는 뜻은 아닙니다. 주소를 읽을 때 어디까지가 대상이고 어디부터가 요청한 경로인지 구분하는 연습을 하는 것입니다.

서버의 응답에는 결과를 나타내는 상태 코드가 포함될 수 있습니다. `200`은 정상 응답의 대표적인 예이고, `404`는 요청한 자원을 찾지 못했다는 뜻입니다. 이 숫자는 앱 전체의 품질 점수가 아닙니다. CSS 요청이 `404`여도 HTML 요청은 성공할 수 있습니다. 데이터 요청이 `200`이어도 우리가 기대한 모양의 데이터인지는 따로 검사해야 합니다. 응답을 받은 것과 내용을 올바르게 사용한 것은 같은 검사가 아닙니다.

브라우저는 받은 파일의 사본을 저장했다가 재사용하기도 합니다. 이를 캐시라고 부릅니다. 매번 똑같은 파일을 새로 받지 않아도 되므로 빠르게 열 수 있습니다. 하지만 개발할 때는 ‘내가 고친 파일’, ‘서버에 게시된 파일’, ‘브라우저가 사용 중인 사본’이 서로 다른 시점의 내용일 수 있습니다. 수정이 보이지 않을 때 캐시를 의심할 수 있지만, 모든 오류를 캐시 탓으로 돌려서는 안 됩니다. 실제 게시가 안 됐거나 다른 주소를 열고 있을 수도 있기 때문입니다.[4][5]

### 연습 1-5. 수정 완료라는 말에 무엇이 빠졌을까?

AI가 ‘제목을 수정했습니다’라고 말했습니다. 그러나 내 휴대폰에는 이전 제목이 보입니다. ‘AI가 파일을 고쳤다’ 이후에 확인해야 할 두 단계를 자신의 말로 적어 보세요.

### 풀이 1-5

고친 파일이 사용자가 여는 운영 주소에 게시되었는지 확인해야 합니다. 그다음 휴대폰의 브라우저나 앱이 새로 게시된 파일을 실제로 받았는지 확인해야 합니다. 로컬 수정, 운영 게시, 기기의 수신은 구분되는 단계입니다.

이 책의 마지막 부분에서는 이 차이를 이용해 오류 보고를 더 정확하게 만드는 연습을 합니다. 지금은 ‘수정했다’라는 한마디에 여러 단계가 섞일 수 있다는 것만 분명히 해 두면 됩니다. 확인 없이 서버 전체를 지우거나 기기 저장소를 모두 초기화하는 것은 원인에 비해 너무 큰 조치일 수 있습니다.

## 1.6 우리가 앞으로 만들 기록장의 범위

기록장은 처음에는 제목과 예시 기록만 있는 문서입니다. 입력창을 만들고, 글자를 읽기 쉽게 배치하고, 버튼을 누르면 목록을 바꾸고, 마지막에는 기록을 저장하게 됩니다. 이 과정에서 HTML, CSS, JavaScript가 각각 혼자서 모든 일을 하지 않는다는 점을 반복해서 보게 될 것입니다.

이 책에서 만드는 기본 기록장은 한 브라우저에서 개인 연습용으로 사용하는 앱입니다. 로그인, 여러 기기 간 자동 동기화, 병원이나 고객의 실제 정보 보관을 구현한 서비스가 아닙니다. 그런 기능에는 서버와 권한, 데이터 보호, 장애 대응이라는 추가 설계가 필요합니다. 작게 만든다는 것은 대충 만든다는 뜻이 아니라, 지금 책임질 범위를 정확히 정한다는 뜻입니다.

다음 장에서는 화면의 모양을 꾸미기 전에 문서의 의미를 정합니다. ‘큰 글씨’와 ‘제목’, ‘밑줄 친 글씨’와 ‘링크’가 왜 다른지부터 살펴보겠습니다. 그래야 나중에 글자 크기를 바꾸더라도 문서의 구조까지 무너지지 않습니다.
