# 10장. 인터넷에서 데이터 가져오기 — 요청·응답과 기다리는 작업

기록장의 주제 목록을 코드 안에 직접 적어 두면 내용을 바꿀 때마다 JavaScript를 수정해야 합니다. 다른 파일이나 서비스에서 주제를 받아 보여 준다면 어떨까요? 브라우저가 자료를 요청하고, 결과를 받은 뒤 목록을 만들면 됩니다. 이 장에서는 준비된 JSON 파일을 읽는 것에서 시작해 외부 API 응답을 사용하는 원리로 연결합니다.

요청은 계산과 시간이 다릅니다. `20 + 10`은 같은 실행 흐름에서 바로 계산할 수 있지만, 인터넷의 상대가 언제 응답할지는 정해져 있지 않습니다. 느릴 수도 있고, 파일이 없을 수도 있고, 응답 형식이 우리가 생각한 것과 다를 수도 있습니다. 따라서 성공 화면뿐 아니라 기다리는 중, 비어 있는 결과, 실패를 함께 설계해야 합니다. 계속 도는 로딩 표시를 이해하는 데 필요한 개념입니다.

## 10.1 API라는 말보다 요청할 자료부터 구체화하기

API는 다른 프로그램이나 기능을 사용할 때 따르는 약속이라고 이해할 수 있습니다. 이 장의 웹 API에서는 어떤 주소에 어떤 요청을 보내면 어떤 형식의 응답을 받을 수 있는지가 중요한 약속입니다. 모든 API가 인터넷 서비스인 것은 아니지만, 지금은 HTTP 요청으로 데이터를 사용하는 상황을 다룹니다.

먼저 서버 구현 없이 정적 JSON 파일 하나를 준비하겠습니다. 다음 내용으로 `topics.json`을 만들고 기록장의 HTML과 같은 폴더에 두는 상황입니다. 이 파일이 자동으로 존재하는 것은 아닙니다. 뒤의 실습 묶음에는 예제 파일을 함께 제공합니다.

```json file=topics.json
[
  { "id": "html", "title": "HTML의 의미 있는 구조" },
  { "id": "css", "title": "CSS의 선택과 배치" },
  { "id": "js", "title": "JavaScript의 값과 이벤트" }
]
```

전체는 배열이고, 각 항목은 id와 title을 가진 객체입니다. 이 파일은 학습 주제 목록을 담고 있을 뿐, 로그인을 처리하거나 사용자의 기록을 저장하는 서버 프로그램이 아닙니다. 정적 파일을 받아 읽는 것과 복잡한 API 서비스는 구현 규모가 다르지만, 요청과 응답을 구분하는 첫 연습에 사용할 수 있습니다.[1][2][3]

`fetch("./topics.json")`은 현재 문서 위치를 기준으로 이 파일을 요청합니다. 앞의 `./`는 현재 경로를 기준으로 한다는 뜻입니다. 루트 기준 `/topics.json`과 구별됩니다. 하위 폴더에 게시할 때는 이 차이가 중요할 수 있습니다. 파일을 직접 여는 환경에서는 요청이 제한될 수 있으므로 실제 요청 실습은 HTTP 또는 HTTPS로 제공되는 같은 출처에서 확인합니다.

### 연습 10-1. ‘API 연결’이라는 말에서 빠진 정보

AI에게 주제 API를 연결해 달라고 했더니 ‘연결 완료’라는 답을 받았습니다. 실제로 확인하려면 주소 외에 어떤 응답 정보를 알아야 할까요?

### 풀이 10-1

성공했을 때 배열인지 객체인지, 각 항목의 속성 이름과 값 종류는 무엇인지, 실패했을 때 어떤 상태와 본문을 받는지 알아야 합니다. 주소에 접속할 수 있다는 사실만으로 화면에 필요한 데이터 구조를 확인한 것은 아닙니다. 이 예제에서는 배열 안에 문자열 id와 title이 있다는 약속을 확인합니다.

## 10.2 fetch의 결과는 아직 데이터 배열이 아니다

다음은 데이터를 읽는 함수의 기본 형태입니다. JavaScript 파일에 넣을 수 있는 부분 코드이며 실제로 topics.json을 제공하는 출처가 필요합니다.

```javascript browser
async function fetchTopics() {
  const response = await fetch("./topics.json");
  if (!response.ok) {
    throw new Error("자료 요청 실패: " + response.status);
  }
  const data = await response.json();
  return data;
}
```

`fetch`는 요청의 진행 결과를 나타내는 Promise를 돌려줍니다. Promise는 작업이 나중에 성공하거나 실패할 결과를 다루는 값입니다. 지금 배열이 들어 있다고 생각하고 바로 반복하는 것과 다릅니다. `await`는 이 함수의 해당 진행을 결과가 준비될 때까지 기다리게 합니다. 그동안 브라우저 전체가 얼어서 모든 사용자 행동이 멈춰야 한다는 뜻은 아닙니다.[1][2][3]

함수 앞의 `async`는 이 함수가 비동기 결과를 다루는 함수임을 나타내고, 이 함수 안에서 await를 사용할 수 있게 합니다. async 함수의 호출 결과도 Promise입니다. 함수 안에서 data를 return했다고 호출한 바깥에서 항상 즉시 일반 배열을 받는 것으로 오해하면 안 됩니다. 호출한 쪽도 결과가 준비되는 시점을 다루어야 합니다.

첫 await로 받은 response는 응답 객체입니다. 상태 코드나 헤더, 본문을 읽는 기능 등을 다룰 수 있습니다. 우리가 원하는 주제 배열 그 자체는 아닙니다. `response.json()`으로 본문을 JSON으로 읽고, 그 작업도 비동기이므로 await로 결과를 받습니다. ‘요청 결과를 받는다’와 ‘본문을 데이터로 읽는다’라는 두 단계를 구별하세요.

`response.ok`는 성공 범위의 HTTP 상태인지 확인하는 데 사용합니다. fetch는404나500 같은 HTTP 오류 응답을 받았다고 반드시 Promise를 거절하는 것은 아닙니다. 응답을 받았다는 점에서는 작업이 이루어진 것이기 때문입니다. 네트워크 자체의 실패와 HTTP 응답 상태의 실패를 분리하여 검사해야 합니다.[3]

### 연습 10-2. catch가 안 잡았는데 성공일까?

요청한 파일이 없어서404 응답을 받았습니다. fetch 주변의 catch로 바로 이동하지 않았습니다. 그렇다면 파일을 정상으로 받았다고 결론 내릴 수 있을까요?

### 풀이 10-2

그럴 수 없습니다. fetch는 HTTP 오류 상태의 응답도 응답 객체로 제공할 수 있으므로 response.ok나 상태 코드를 확인해야 합니다. 파일 없음 안내 HTML을 JSON으로 읽으려 하면 그다음 단계에서 JSON 해석 오류가 생길 수도 있습니다. 먼저 상태를 검사하면 어떤 단계에서 실패했는지 더 명확하게 설명할 수 있습니다.

## 10.3 비동기 실행의 순서를 손으로 따라가기

작은 타이머로 기다리는 작업을 살펴보겠습니다. 아래 코드는 JavaScript 콘솔에서 실행할 수 있습니다. 실제 인터넷 요청이 아니라 비동기 순서를 관찰하기 위한 예제입니다.

```javascript console
console.log("첫 번째");
setTimeout(function later() {
  console.log("나중에 실행");
}, 0);
console.log("두 번째");
```

```text
첫 번째
두 번째
나중에 실행
```

0을 적었다고 가운데 함수가 즉시 끼어들어 실행되는 것은 아닙니다. 현재 진행 중인 코드가 끝난 뒤 예약된 처리가 실행됩니다. 정확한 지연 시간을 보장하는 예제가 아니라 ‘예약한 함수의 본문’과 ‘지금 이어서 실행하는 줄’을 구분하는 예제입니다.

fetch도 이런 시간 차이를 생각해야 합니다. ‘데이터를 요청해 놓는다’ 다음 줄에 바로 ‘받은 데이터를 사용한다’를 적으면 아직 결과가 준비되지 않았을 수 있습니다. Promise의 결과를 기다리는 방법에는 then도 있습니다. 이 책에서는 초보자가 위아래 순서로 읽기 쉬운 async와 await를 주로 사용하되, 기다리는 대상이 있는 지점을 명확히 하겠습니다.

```javascript browser
async function showTopicCount() {
  const topics = await fetchTopics();
  console.log(topics.length);
}
```

여기서 fetchTopics 호출에 await를 붙였기 때문에 이 함수 안에서는 주제 데이터가 준비된 뒤 length를 읽습니다. 함수 정의만 한 상태에서는 요청하지 않습니다. `showTopicCount()`를 호출할 때 이 흐름이 시작됩니다. 앞 장의 이벤트에 함수를 연결하면 사용자가 버튼을 누르는 순간 요청을 시작하게 만들 수 있습니다.

### 연습 10-3. Promise를 배열로 읽은 경우

`const topics = fetchTopics(); console.log(topics.length);`라고 적었습니다. fetchTopics는 위의 async 함수입니다. 왜 기대한 주제 수가 바로 나오지 않을 수 있나요?

### 풀이 10-3

topics에 직접 들어오는 것은 데이터 배열이 아니라 Promise입니다. async 함수 안에서 `const topics = await fetchTopics();`처럼 결과를 기다린 뒤 배열을 사용하거나 then으로 결과 처리를 연결해야 합니다. 변수 이름을 topics라고 붙였다는 이유만으로 값의 종류가 배열로 바뀌지 않습니다.

## 10.4 응답의 모양을 검사하기

서버에서 JSON을 받았다는 사실만으로 화면에 사용할 수 있다는 보장은 없습니다. 같은 주소가 실수로 다른 데이터를 보내거나, 외부 서비스의 형식이 바뀌거나, 일부 값이 빠질 수 있습니다. 데이터를 사용하기 전에 최소한의 구조를 검사하겠습니다.

```javascript console
function validTopics(data) {
  if (!Array.isArray(data)) {
    return false;
  }
  for (const item of data) {
    if (item === null || typeof item !== "object") {
      return false;
    }
    if (typeof item.id !== "string" || typeof item.title !== "string") {
      return false;
    }
    if (item.id.trim() === "" || item.title.trim() === "") {
      return false;
    }
  }
  return true;
}

console.log(validTopics([{ id: "html", title: "HTML 읽기" }]));
console.log(validTopics({ title: "배열이 아닙니다" }));
console.log(validTopics([{ id: "html", title: 30 }]));
```

```text
true
false
false
```

`Array.isArray`는 배열인지 확인합니다. `typeof`는 값의 종류를 나타내는 문자열을 얻는 연산자입니다. item이 객체라고 검사하기 전에 null도 따로 제외한 이유는 JavaScript의 typeof null 결과가 object라는 특성이 있기 때문입니다. 이 이상한 점을 지금 깊게 외우기보다, 실제로 속성을 읽을 수 있는지 검사하는 안전한 순서를 익히면 됩니다.

검사는 이 예제에 필요한 최소 조건입니다. 실제 서비스에서는 항목 수, 문자열 길이, id 중복 여부처럼 더 구체적인 제한을 추가할 수 있습니다. 모든 객체를 완벽하게 검증하는 일반 도구라고 과장하지 않습니다. 입력의 계약이 바뀌면 검사도 함께 바뀌어야 합니다.

### 연습 10-4. 정상 응답과 정상 데이터는 다르다

응답 상태는200이고 JSON 해석도 성공했습니다. 그런데 결과는 `{ "message": "점검 중" }`입니다. 이를 주제 배열로 반복하기 전에 어떤 검사가 실패해야 할까요?

### 풀이 10-4

배열인지 확인하는 검사가 실패해야 합니다. HTTP 응답 자체는 성공 범위일 수 있지만, 이 화면이 사용하기로 약속한 데이터 구조와 다릅니다. 사용자에게는 자료를 사용할 수 없다는 안내를 하고, 기존에 표시하던 정상 주제를 함부로 지우지 않는 설계를 고려할 수 있습니다.

## 10.5 로딩, 빈 결과, 실패를 서로 다른 상태로 만들기

주제가 세 개 있는 결과와 빈 배열을 받은 결과는 모두 유효한 JSON 배열일 수 있습니다. 빈 결과는 실패와 다릅니다. ‘현재 제공되는 주제가 없습니다’라고 안내할 수 있습니다. 네트워크가 끊긴 경우에는 ‘자료를 불러오지 못했습니다. 다시 시도해 주세요’처럼 다른 행동을 제안해야 합니다.

함수가 시작할 때는 로딩 상태를 보여 주고, 끝날 때는 성공이든 실패든 로딩을 끝내야 합니다. try와 catch 뒤에 `finally`를 사용하면 정리 작업을 한곳에 둘 수 있습니다. 다음은 기존 문서에 message와 load 버튼이 있고, 유효성 검사 함수가 같은 파일에 있다는 전제의 부분 코드입니다.

```javascript browser
async function loadTopics() {
  const button = document.querySelector("#load-topics");
  const message = document.querySelector("#topics-message");
  button.disabled = true;
  message.textContent = "주제를 불러오는 중입니다.";

  try {
    const data = await fetchTopics();
    if (!validTopics(data)) {
      throw new Error("주제 데이터의 형식이 맞지 않습니다.");
    }
    message.textContent = data.length === 0
      ? "현재 제공되는 주제가 없습니다."
      : data.length + "개의 주제를 받았습니다.";
  } catch (error) {
    message.textContent = "주제를 불러오지 못했습니다. 다시 시도해 주세요.";
    console.error("주제 요청 실패", error);
  } finally {
    button.disabled = false;
  }
}
```

요청 중에는 버튼을 비활성화하여 연속 클릭이 여러 요청을 만들지 않게 했습니다. finally에서 버튼을 다시 활성화하므로 오류가 나도 재시도할 수 있습니다. 단, 이 코드는 네트워크가 아주 오래 응답하지 않는 상황의 시간 제한까지 제공하지는 않습니다. 그 조건은 다음 절에서 추가합니다.

또한 이 예제는 받은 수를 안내할 뿐 실제 주제 목록을 그리는 함수까지 포함한 것은 아닙니다. 기능의 일부를 보여 줄 때는 무엇이 포함되지 않았는지 구별해야 합니다. 마지막 장의 완성 프로그램에서는 검증한 주제를 실제 목록에 표시합니다.

### 연습 10-5. 실패 후 버튼이 계속 잠겨 있다

요청 시작에 button.disabled를 true로 바꾸고, 성공했을 때만 false로 바꿉니다. 네트워크 오류 뒤에 어떤 문제가 생기며 어디에서 정리하면 좋을까요?

### 풀이 10-5

실패 경로에서는 다시 활성화되지 않아 사용자가 재시도하지 못할 수 있습니다. finally에서 성공과 실패에 공통으로 필요한 정리를 할 수 있습니다. 로딩 표시도 같은 원리로 생각합니다. ‘실패를 잡았다’는 것만으로 사용자 화면이 사용할 수 있는 상태로 돌아왔다는 뜻은 아닙니다.

## 10.6 무한히 기다리지 않기와 요청 순서의 문제

요청을 중지할 수 있는 신호로 AbortController를 사용할 수 있습니다. 다음 예제는5초 뒤에도 끝나지 않으면 중단을 요청하는 형태입니다.5초는 설명을 위한 앱의 정책값이지 인터넷 요청의 공식 정답 시간이 아닙니다.

```javascript browser
async function fetchTopicsWithTimeout() {
  const controller = new AbortController();
  const timer = setTimeout(function stopWaiting() {
    controller.abort();
  }, 5000);

  try {
    const response = await fetch("./topics.json", {
      signal: controller.signal
    });
    if (!response.ok) {
      throw new Error("요청 실패: " + response.status);
    }
    const data = await response.json();
    if (!validTopics(data)) {
      throw new Error("주제 데이터 형식 오류");
    }
    return data;
  } finally {
    clearTimeout(timer);
  }
}
```

controller는 중단을 요청할 수 있는 대상이고, signal은 그 요청을 fetch에 연결하는 신호입니다. 타이머는 나중에 abort를 호출하도록 예약합니다. 요청이 먼저 끝나면 clearTimeout으로 더 이상 필요 없는 예약을 정리합니다. 중단을 요청해도 서버가 이미 처리한 일을 되돌리는 기능은 아닙니다. 여기서는 기다리는 요청을 끊는 범위로 이해합니다.

검색창처럼 여러 요청을 연속으로 허용하면, 먼저 보낸 요청이 나중에 끝날 수도 있습니다. 최신 검색 결과를 먼저 보여 준 뒤 오래된 응답이 화면을 덮을 수 있습니다. 이런 경우 요청 번호를 비교하거나 이전 요청을 중단하는 방식이 필요합니다. 이 기록장에서는 버튼을 잠그는 간단한 방식으로 한 번에 한 요청만 하도록 시작합니다. 앱이 커질 때 어떤 조건이 달라지는지 알아 두면 됩니다.

### 연습 10-6. 두 번의 검색 결과가 뒤집힌 경우

A를 검색하고 곧바로B를 검색했습니다. B의 결과가 먼저 나오고 A의 결과가 나중에 왔습니다. 도착한 응답을 무조건 화면에 넣으면 어떤 문제가 생기나요?

### 풀이 10-6

사용자가 마지막으로 요청한 것은B인데 화면은 늦게 도착한A로 바뀔 수 있습니다. 요청을 보낸 순서와 응답이 도착한 순서가 항상 같다고 가정했기 때문입니다. 최신 요청에 해당하는 응답인지 확인하거나 이전 요청을 중단하는 등의 설계가 필요합니다. 단순히 await를 썼다는 사실만으로 여러 요청 전체의 최신성 문제가 자동 해결되지는 않습니다.

## 10.7 다른 출처와 비밀키의 경계

다른 사이트의 데이터를 요청할 때는 브라우저의 출처 간 접근 규칙에 영향을 받습니다. CORS 오류를 만났다고 무조건 `mode: "no-cors"`를 붙이면 JSON을 읽을 수 있게 되는 것은 아닙니다. 응답을 읽을 수 없는 형태가 될 수 있습니다. 서버가 어떤 출처의 접근을 허용하는지, 사용하려는 API가 브라우저 직접 호출을 지원하는지 확인해야 합니다.[3]

JavaScript 파일에 비밀 API 키를 넣고 배포하면 사용자가 그 파일을 받을 수 있는 구조입니다. 변수 이름을 숨기거나 화면에서 입력칸을 가린다고 서버 비밀이 되지 않습니다. 공개해도 되는 키와 서버에만 있어야 할 비밀키를 구분하고, 비밀이 필요한 작업은 적절한 서버 경로로 분리해야 합니다. 이 책의 예제 JSON 요청은 유료 API 키를 필요로 하지 않습니다.

이제 요청이 시작되었다는 사실, 응답을 받았다는 사실, 본문이 해석되었다는 사실, 데이터가 계약에 맞다는 사실을 나누어 볼 수 있습니다. 다음 장에서는 이 구별을 이용해 ‘버튼이 안 된다’, ‘자료가 안 뜬다’라는 막연한 증상을 정확한 조사로 바꾸겠습니다.
