# 9장. 화면 상태와 데이터 저장 — 새로고침해도 기록 남기기

기록을 두 개 추가한 뒤 새로고침했습니다. 목록이 사라졌습니다. 바로 전까지 눈앞에 있었으니 저장되어 있다고 느꼈지만, 앞 장의 코드는 현재 문서에 목록 항목을 붙였을 뿐입니다. 문서를 다시 불러오면 HTML에 처음 적혀 있던 상태에서 다시 시작합니다. 화면에 보이는 것과 다시 꺼낼 수 있게 보관한 것은 다른 일입니다.

이 장에서는 세 대상을 구별합니다. 프로그램이 지금 사용하는 기록 데이터, 그 데이터로 만든 화면, 브라우저 저장소에 적은 문자열입니다. 처음에는 세 개를 따로 다루는 것이 번거로워 보일 수 있습니다. 그러나 삭제한 기록이 되살아나거나 숫자는 바뀌었는데 화면은 그대로인 오류를 설명하려면 이 구별이 필요합니다. 앱의 상태가 어디에 있는지 명확하게 만드는 과정입니다.

## 9.1 화면 대신 데이터에 기준을 두기

앞 장에서는 추가할 때마다 li 요소를 만들었습니다. 이제 records라는 배열을 기록의 기준으로 두겠습니다.

```javascript console
let records = [
  { id: 1, topic: "HTML", minutes: 20, completed: false },
  { id: 2, topic: "CSS", minutes: 30, completed: true }
];

console.log(records.length);
console.log(records[1].completed);
```

```text
2
true
```

배열의 각 객체에는 기록 하나의 정보가 있습니다. `id`는 기록을 구별하는 이름 역할의 숫자입니다. 화면에서 몇 번째 보이는지와 같은 값일 필요는 없습니다. 첫 번째 항목을 지워도 두 번째 기록의 id가 자동으로1로 바뀌는 식으로 생각하지 않겠습니다. 위치와 정체성을 구분하면 정렬이나 필터를 적용할 때 다른 항목을 잘못 지우는 문제를 줄일 수 있습니다.

`completed`는 사용자가 완료 표시를 했는지 담은 참·거짓입니다. 이 배열처럼 앱이 현재 기억하고 있는 정보를 상태라고 부를 수 있습니다. 상태는 반드시 특별한 라이브러리로 만들어야 하는 것이 아닙니다. 지금의 작은 앱에서는 변수와 배열로도 그 개념을 배울 수 있습니다.[2][4][5]

화면은 이 상태를 표현합니다. 목록을 직접 조작하는 여러 코드가 제각각 기준이 되면 서로 어긋날 수 있습니다. 우리는 상태를 바꾸고, 그 상태로 화면을 다시 만드는 함수를 한곳에 두겠습니다. 이를 렌더링이라고 부르겠습니다. 복잡한 용어처럼 들리지만 여기서는 ‘현재 데이터를 사용해 화면 내용을 만든다’는 뜻입니다.

### 연습 9-1. 화면에서는 없어졌는데 다시 나타난다

삭제 버튼으로 li 요소만 제거했습니다. records 배열에는 해당 객체가 그대로 남아 있습니다. 이후 records를 사용해 목록을 다시 만들면 어떤 일이 생길까요?

### 풀이 9-1

배열에 남아 있는 기록이 다시 화면에 나타납니다. 화면의 요소를 지운 것과 기준 데이터에서 기록을 지운 것이 다르기 때문입니다. 삭제 요구를 구현하려면 어떤 상태가 기준인지 정하고 그 상태에서 대상 기록을 제거한 뒤 화면을 갱신해야 합니다.

이런 상황에서 ‘브라우저가 삭제를 취소했다’라고 설명하면 원인을 놓칩니다. 브라우저는 우리가 제공한 배열을 다시 보여 주었을 뿐입니다.

## 9.2 같은 데이터를 여러 번 그려도 중복되지 않게

다음은 기존 HTML에 `<ul id="records"></ul>`이 있다는 전제의 부분 코드입니다. records 배열을 화면에 표시하는 함수입니다.

```javascript
function renderRecords() {
  const list = document.querySelector("#records");
  list.replaceChildren();

  for (const record of records) {
    const item = document.createElement("li");
    const label = record.completed ? "완료" : "진행 중";
    item.textContent = record.topic + " · " + record.minutes + "분 · " + label;
    list.append(item);
  }
}
```

`replaceChildren()`을 인수 없이 호출하면 그 요소의 현재 자식 내용을 비웁니다. 그다음 배열의 항목을 하나씩 새로 붙입니다. 이렇게 하면 같은 배열을 두 번 렌더링해도 목록이 두 배로 쌓이지 않습니다. 배열의 내용을 지우는 명령이 아니라 화면 요소 안의 자식을 정리하는 명령입니다.

`condition ? A : B`는 조건에 따라 두 값 중 하나를 고르는 표현입니다. 여기서는 completed가 참이면 ‘완료’, 아니면 ‘진행 중’이라는 문자열을 label에 연결합니다. 처음에는 아래처럼 if 문으로 풀어 읽어도 됩니다.

```javascript
let label;
if (record.completed) {
  label = "완료";
} else {
  label = "진행 중";
}
```

두 코드를 아무 곳에나 함께 붙이라는 뜻은 아닙니다. 위 함수 안의 label 한 줄을 읽는 데 도움이 되는 대체 표현입니다. 짧은 표기와 긴 표기가 같은 단순 판단을 표현할 수 있다는 점을 비교하는 것입니다.

일반적인 대규모 앱에서는 전체 목록을 매번 새로 만들기보다 바뀐 부분만 갱신하는 방법도 사용합니다. 지금은 작은 기록장에서 상태와 화면의 관계를 분명하게 만드는 것이 우선입니다. 나중에 성능을 개선하더라도 무엇을 기준 데이터로 삼는지는 유지해야 합니다.

### 연습 9-2. 화면이 두 배가 된 이유

위 함수에서 `list.replaceChildren()`을 빼고 같은 records로 함수를 두 번 실행했습니다. records에는 두 개가 있습니다. 목록에는 몇 개가 생기고, 배열 항목 수도 함께 늘어날까요?

### 풀이 9-2

처음 두 개를 붙이고 다음에 다시 두 개를 붙이므로 화면에 네 개의 li가 생깁니다. 그러나 배열에 push한 코드가 없으므로 records 항목 수는 두 개입니다. 데이터의 수와 화면 요소의 수가 달라진 것입니다. 렌더링 함수가 같은 상태를 중복 없이 표현하는지도 검사해야 합니다.

## 9.3 브라우저 저장소는 문자열을 보관한다

`localStorage`는 같은 출처의 웹페이지가 브라우저에 문자열을 저장하고 다시 읽는 데 사용할 수 있는 기능입니다. 여기서 출처는 프로토콜, 호스트, 포트의 조합과 관련됩니다. 단순히 같은 회사 이름이나 비슷한 주소라는 이유로 저장소가 같아지는 것은 아닙니다.[1][2][3]

```javascript browser
localStorage.setItem("study-demo-topic", "HTML");
const savedTopic = localStorage.getItem("study-demo-topic");
console.log(savedTopic);
```

이 코드는 저장 기능을 사용할 수 있는 웹페이지의 브라우저 환경에서 실행하는 예제입니다. Python 실행창이나 DOM이 없는 JavaScript 계산 환경에서 그대로 사용할 수 있다는 뜻은 아닙니다. `setItem`은 이름과 문자열값을 저장하고, `getItem`은 그 이름으로 값을 읽습니다. 여기서는 ‘HTML’이라는 문자열을 얻습니다.

해당 이름의 값이 없으면 getItem은 null을 돌려줍니다. 빈 문자열을 저장한 경우와 값 자체가 없는 경우는 구별됩니다. 사용자의 브라우저 설정이나 저장 공간, 보안 조건에 따라 읽기나 쓰기가 실패할 수도 있습니다. 저장 기능이 있다는 사실을 모든 상황에서 성공한다는 보장으로 표현하지 않습니다.

배열과 객체를 저장하려면 문자열로 바꾸어야 합니다. JSON은 데이터를 문자열로 표현하는 널리 쓰이는 형식입니다. JavaScript의 모든 기능을 그대로 담는 형식은 아닙니다. 이 기록장처럼 문자열·숫자·참거짓·배열·단순 객체를 보관하는 예제를 생각하면 됩니다.

```javascript console
const record = { topic: "HTML", minutes: 20, completed: false };
const text = JSON.stringify(record);
console.log(text);
const restored = JSON.parse(text);
console.log(restored.minutes + 5);
```

```text
{"topic":"HTML","minutes":20,"completed":false}
25
```

`JSON.stringify`는 데이터를 JSON 문자열로 바꿉니다. `JSON.parse`는 형식에 맞는 JSON 문자열을 읽어 데이터로 만듭니다. 파일 확장자가 json이라고 모든 문자열이 올바른 JSON인 것은 아닙니다. 문법이 틀린 문자열을 parse하면 예외가 날 수 있습니다. 또 문법이 맞더라도 우리가 원하는 기록 구조인지 별도 확인해야 합니다.

### 연습 9-3. parse가 성공하면 기록인가?

문자열 `"123"`을 JSON.parse로 읽는 데 성공했습니다. 그렇다면 그것을 기록 배열이라고 생각하고 바로 반복해도 될까요?

### 풀이 9-3

아닙니다. JSON 문법에 맞는 숫자123으로 읽은 것이지 기록 배열로 확인한 것이 아닙니다. 배열인지, 각 항목에 topic과 minutes가 있는지, 값의 종류와 범위가 맞는지 따로 검사해야 합니다. ‘해석에 성공했다’와 ‘앱의 데이터 계약에 맞다’는 두 검사입니다.

## 9.4 이름 하나와 작은 저장 형식을 정하기

앱이 저장할 키를 하나 정하겠습니다. 다른 연습 데이터와 혼동하지 않도록 용도를 드러내는 이름을 사용합니다.

```javascript
const STORAGE_KEY = "study-log-v1";
```

이 이름에 기록 배열뿐 아니라 형식의 버전도 함께 저장하겠습니다. 예를 들어 저장할 데이터는 다음과 같습니다.

```json
{
  "version": 1,
  "records": [
    { "id": 1, "topic": "HTML", "minutes": 20, "completed": false }
  ]
}
```

version은 우리 저장 형식에 붙인 번호입니다. 앱이 커져 형식이 달라졌을 때 무슨 데이터를 읽고 있는지 구별하는 데 사용할 수 있습니다. 숫자를 넣었다고 자동 변환 기능이 생기는 것은 아닙니다. 다른 버전을 만났을 때 처리할 규칙을 별도로 작성해야 합니다.

다음은 저장하는 부분 코드입니다. 같은 파일에서 STORAGE_KEY와 records가 준비되어 있다는 전제입니다.

```javascript
function saveRecords() {
  const data = { version: 1, records: records };
  const text = JSON.stringify(data);
  localStorage.setItem(STORAGE_KEY, text);
}
```

`records: records`에서 콜론 왼쪽은 객체 안의 속성 이름, 오른쪽은 현재 변수의 값입니다. 둘의 철자가 같아서 처음에는 중복처럼 보이지만 역할은 다릅니다. 나중에 `{ records }`라는 짧은 표기를 만나더라도, 처음에는 이 긴 형태로 무엇을 저장하는지 읽는 편이 좋습니다.

저장이 실패할 수 있으므로 실제 앱에서는 예외를 처리해야 합니다. 화면에 추가됐지만 저장되지 않은 상황을 ‘저장 완료’라고 알리면 사용자가 데이터를 잃을 수 있습니다.

```javascript
function trySaveRecords() {
  try {
    saveRecords();
    return true;
  } catch (error) {
    console.error("기록을 저장하지 못했습니다.", error);
    return false;
  }
}
```

`try` 안에서 실패가 발생하면 catch에서 처리합니다. true 또는 false로 결과를 호출한 쪽에 돌려주면 화면 메시지를 달리 만들 수 있습니다. 이 코드가 저장 실패를 해결한 것은 아닙니다. 실패를 성공으로 위장하지 않고 알려 줄 수 있게 한 것입니다. 민감한 데이터 전체를 오류 로그에 찍는 방식은 피합니다.

### 연습 9-4. 안내문 하나가 데이터를 잃게 하는 경우

기록을 화면에 추가하고 저장을 시도했지만 예외가 발생했습니다. 앱은 무조건 ‘저장 완료’라고 보여 줍니다. 메시지를 어떻게 나누어야 할까요?

### 풀이 9-4

저장 성공을 확인한 경우에만 저장 완료라고 알려야 합니다. 화면에는 추가되었지만 저장에 실패한 경우에는 ‘현재 화면에는 추가됐지만 보관하지 못했습니다. 닫기 전에 내용을 보존해 주세요’처럼 상태를 구별해야 합니다. 더 안전한 설계에서는 저장 성공 후에만 기준 상태를 확정하는 방식도 사용할 수 있습니다. 마지막 종합 프로젝트에서는 이 방식으로 연결합니다.

## 9.5 읽기 실패를 빈 목록으로 덮어쓰지 않기

처음 실행해서 저장값이 없는 상황과, 저장값은 있지만 읽을 수 없는 상황은 다릅니다. 둘을 무조건 빈 배열로 바꾼 뒤 곧바로 저장하면 손상된 데이터 위에 빈 목록을 덮어쓸 수 있습니다. 실수로 지운 것이 아니라 ‘안전하게 기본값을 넣었다’고 생각하면서 데이터를 잃는 경우입니다.

처음 실행은 빈 목록으로 시작해도 됩니다. 그러나 잘못된 JSON이나 알 수 없는 버전을 만났다면 원본을 보존하고 읽기 실패를 알려야 합니다. 이 책의 기본 설계는 이런 경우 자동 덮어쓰기를 막는 것입니다. 사용자가 원본을 확인하거나 내보낼 수 있는 길을 남기고, 초기화가 필요하다면 의도를 확인한 뒤 그 앱의 키만 지웁니다.

아래는 읽기 결과를 구별하는 작은 예입니다. 데이터 구조의 상세 검사는 뒤의 종합 프로젝트에서 완성합니다. 현재는 ‘없음’과 ‘실패’를 같은 것으로 처리하지 않는 흐름을 읽어 보세요.

```javascript
function readStoredText() {
  try {
    const text = localStorage.getItem(STORAGE_KEY);
    if (text === null) {
      return { status: "empty", text: null };
    }
    return { status: "found", text: text };
  } catch (error) {
    return { status: "failed", text: null };
  }
}
```

반환 객체의 status는 우리가 정한 결과 이름입니다. 브라우저가 empty나 found의 뜻을 알아서 다음 처리를 해 주는 것이 아닙니다. 호출한 코드가 그 값을 보고 어떻게 행동할지 작성해야 합니다. 이렇게 결과를 명시하면 실패를 기본값으로 숨기는 일을 줄일 수 있습니다.

### 연습 9-5. 안전해 보이지만 위험한 복구

저장된 문자열을 읽다가 오류가 나면 `records = []; localStorage.setItem(STORAGE_KEY, "[]");`를 실행합니다. 어떤 위험이 있고, 우선 어떤 것을 보존해야 할까요?

### 풀이 9-5

아직 복구할 가능성이 있는 원본 문자열을 빈 배열로 덮어쓸 수 있습니다. 게다가 이 책에서 정한 version과 records를 가진 저장 형식도 잃습니다. 우선 원본을 보존하고 오류 상태를 알려야 합니다. 읽기 실패만으로 사용자가 모든 기록을 지우기로 동의했다고 볼 수 없습니다.

## 9.6 삭제와 완료 표시도 같은 흐름을 따른다

새 기록 추가만 저장하고 삭제는 화면에서만 처리하면, 다시 열었을 때 삭제한 기록이 돌아올 수 있습니다. 상태를 바꾸는 모든 동작이 저장과 연결되는지 확인해야 합니다. 여기에서는 id로 특정 기록을 제외한 새 배열을 만드는 예를 보겠습니다.

```javascript console
const records = [
  { id: 1, topic: "HTML" },
  { id: 2, topic: "CSS" },
  { id: 3, topic: "JavaScript" }
];
const removeId = 2;
const nextRecords = [];
for (const record of records) {
  if (record.id !== removeId) {
    nextRecords.push(record);
  }
}
console.log(nextRecords.length);
console.log(nextRecords[1].id);
```

```text
2
3
```

id가2가 아닌 것만 새 배열에 넣습니다. 삭제 뒤 두 번째 위치에는 id3의 기록이 있습니다. 위치 번호와 기록 id가 다르다는 의미가 여기서 드러납니다. 이 짧은 예제는 새 배열만 만들었고, 실제 앱의 상태와 저장소를 아직 바꾸지 않았습니다. 다음 단계에서 저장에 성공했는지 확인하고 기준 상태를 nextRecords로 바꿀 수 있습니다.

완료 표시도 대상 기록의 completed 값을 바꾸는 작업입니다. 여러 함수에서 같은 원본 객체를 아무렇게나 바꾸면 언제 값이 달라졌는지 찾기 어렵습니다. 작은 앱에서도 ‘변경할 다음 상태를 만든다 → 저장 결과를 확인한다 → 기준 상태와 화면을 맞춘다’라는 한 흐름을 정해 두면 설명하기 쉬워집니다.

### 연습 9-6. 두 번째 줄을 지운다는 요구의 함정

화면을 완료된 항목만 보이도록 걸렀습니다. 화면의 두 번째 줄을 눌러 삭제했는데 원본 배열의 두 번째 항목을 지우도록 작성했습니다. 왜 다른 기록이 삭제될 수 있나요?

### 풀이 9-6

필터를 거친 화면의 위치와 원본 배열의 위치가 같다는 보장이 없기 때문입니다. 버튼에 실제 기록의 고유 id를 연결하고 그 id를 기준으로 삭제 대상을 찾는 편이 안전합니다. 화면 순서가 바뀌어도 같은 기록을 가리킬 수 있어야 합니다.

## 9.7 저장과 동기화의 경계

localStorage로 저장하면 같은 브라우저의 같은 출처에서 다시 읽을 수 있는 기반이 생깁니다. 그러나 휴대폰에서 저장한 값이 다른 태블릿에 자동으로 복제되는 것은 아닙니다. 브라우저 프로필이 달라져도 저장소가 다를 수 있고, 사용자가 사이트 데이터를 지우면 기록이 사라질 수 있습니다. 저장소의 존재를 백업이나 기기 간 동기화 보장으로 해석하지 않습니다.[1][2][3]

파일을 직접 여는 `file:` 환경의 저장 동작은 일반적인 HTTP·HTTPS 출처와 다를 수 있습니다. 실제 저장 기능을 확인할 때는 동일한 웹 출처에서 테스트하는 것이 좋습니다. 격리된 교재 미리보기에서는 보안상 저장소 접근이 제한될 수도 있습니다. 그런 환경에서 실패했다고 실제 표준 브라우저 저장 기능이 항상 작동하지 않는다고 결론 내리지 않아야 합니다.

이 저장소에 API 비밀키나 로그인 비밀번호 같은 민감한 정보를 넣어 안전해졌다고 생각해서도 안 됩니다. 같은 출처의 스크립트가 접근할 수 있는 클라이언트 저장소라는 경계를 이해해야 합니다. 이 기록장은 개인 학습용 주제와 시간만 다룹니다. 실제 고객 정보나 업무상 민감한 자료를 넣는 운영 서비스로 확대하려면 추가 보안·백업·권한 설계가 필요합니다.

### 연습 9-7. 휴대폰 기록이 태블릿에 없다

두 기기에서 같은 주소를 열었는데 기록이 서로 다릅니다. localStorage만 사용하는 현재 구조에서 이것을 곧바로 버그라고 할 수 있을까요? 공유를 원한다면 어떤 역할이 추가되어야 할까요?

### 풀이 9-7

현재 구조에서는 기기와 브라우저의 저장소가 분리되어 있으므로 자동 공유를 기대할 수 없습니다. 공유하려면 공통 서버 저장, 사용자 식별과 권한, 요청과 응답, 충돌 처리 같은 역할을 설계해야 합니다. 버튼 문구를 ‘동기화’로 바꾸는 것만으로는 생기지 않습니다.

다음 장에서는 인터넷의 데이터를 받아 화면에 사용하는 방법을 배웁니다. 서버를 직접 만드는 단계는 아니지만, 요청을 보낸 직후와 결과를 받은 뒤가 다른 시점이라는 사실을 이해하면 로딩이 끝나지 않는 앱의 원인을 더 잘 나눌 수 있습니다.
