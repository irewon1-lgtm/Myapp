# 12장. 종합 프로젝트 — AI 초안을 이해하고 내 웹앱으로 완성하기

마지막 장에서는 ‘나의 학습 기록장’을 하나의 작은 프로그램으로 연결합니다. 목표는 완성 코드를 보고 감탄하거나 모두 외우는 것이 아닙니다. 어느 파일이 화면을 만들고, 어느 함수가 입력을 검사하며, 어느 줄에서 저장하고, 어떤 결과를 확인해야 하는지 설명하는 것입니다. AI에게 수정 요청을 할 때도 이 구조를 읽을 수 있으면 범위와 검증 조건을 더 정확하게 정할 수 있습니다.

새로운 기술을 한꺼번에 더하지 않겠습니다. HTML, CSS, JavaScript와 브라우저 저장소를 사용합니다. 로그인 서버나 여러 기기 간 동기화는 없습니다. 예제 데이터를 받아 보는 기능은 같은 출처의 topics.json을 사용하므로 유료 API 키가 필요하지 않습니다. 이 범위를 분명히 정한 뒤 그 안의 동작을 끝까지 확인합니다.

## 12.1 먼저 완성의 뜻을 정하기

기록장은 주제와 공부 시간을 받아 기록을 추가합니다. 주제는 앞뒤 공백을 제거한 뒤1~80자로 제한하고, 시간은1~600분의 정수로 받습니다. 기록을 완료로 표시하거나 삭제할 수 있고, 전체·진행 중·완료 목록을 나누어 봅니다. 새로고침해도 같은 출처의 브라우저 저장소에서 기록을 읽습니다.

저장 실패를 성공으로 표시하지 않습니다. 읽을 수 없는 기존 데이터는 자동으로 빈 목록으로 덮어쓰지 않습니다. 저장 자료를 내보낼 수 있고, 초기화는 별도 확인 뒤 이 기록장의 키만 지웁니다. 외부 주제 요청은 성공·빈 결과·실패·시간 제한을 구분합니다. 화면은 좁은 휴대폰에서도 조작할 수 있어야 합니다.

이 요구사항에는 구현 방식과 결과 조건이 섞여 있습니다. 사용자가 확인할 결과는 ‘기록이 남는다’이고, localStorage는 여기서 선택한 구현입니다. 나중에 서버 저장으로 바꾸더라도 사용자에게 약속한 결과를 지킬 다른 구현이 필요합니다. 구현 이름만 외우는 것보다 결과를 어떻게 확인할지 아는 것이 중요합니다.

### 연습 12-1. 지금 만들지 않는 기능 찾기

이 기록장을 완성하면 가족의 태블릿에서 내 휴대폰 기록을 자동으로 볼 수 있을까요? ‘저장’과 ‘공유’의 차이로 설명해 보세요.

### 풀이 12-1

자동 공유를 구현한 것이 아닙니다. 같은 브라우저의 같은 출처에 저장하고 다시 읽는 구조입니다. 여러 기기에서 같은 기록을 보려면 공통 서버, 사용자 식별과 권한, 동기화 및 충돌 처리 같은 역할이 추가되어야 합니다. UI에 공유라는 단어를 붙이는 것만으로 생기지 않습니다.

## 12.2 세 파일과 데이터 파일을 준비하기

다음 전체 코드는 index.html, style.css, app.js의 세 파일로 나누어 저장합니다. 10장에서 만든 topics.json도 같은 폴더에 둡니다. HTML 코드만 복사하고 연결한 CSS나 JavaScript 파일을 빠뜨리면 모양과 동작이 완성되지 않습니다. 아래의 파일 표시는 각 코드가 들어갈 정확한 위치를 뜻합니다.

```text
study-log/
  index.html
  style.css
  app.js
  topics.json
```

실제 저장과 요청 검증은 이 폴더를 HTTP 또는 HTTPS의 같은 출처로 제공하여 수행합니다. 파일을 직접 여는 방식이나 보안상 격리된 교재 미리보기에서는 저장·요청·다운로드 기능이 제한될 수 있습니다. HTML이 보이는 것과 같은 조건에서 전체 기능이 검증된 것은 다릅니다. 코딩 환경을 AI에게 맡길 때에도 ‘네 파일을 같은 출처로 제공하고, 저장 복원과 JSON 요청을 실제 브라우저에서 확인해 달라’고 요구할 수 있습니다.

이미 배운 구조가 대부분입니다. `aria-labelledby`는 구역의 이름을 문서 안의 제목 id로 연결합니다. `tabindex="-1"`는 목록 제목으로 코드가 초점을 옮길 수 있도록 하되 일반적인 Tab 이동 순서에 새 정지점을 추가하지 않는 용도로 사용했습니다. 기록을 삭제한 뒤 사용자가 어디에 있는지 잃지 않도록 목록 제목에 초점을 둘 예정입니다.

목록을 거르는 select에는 all, active, completed라는 값이 있습니다. 화면의 ‘전체’, ‘진행 중’, ‘완료’는 사용자가 읽는 문구이고, JavaScript는 option의 value를 읽어 어떤 조건을 사용할지 정합니다. 문구만 바꾸면 값도 자동으로 바뀌는 것은 아닙니다.

### 연습 12-2. 버튼을 더 크게 해 달라는 요청

버튼이 너무 작다는 요청을 받았습니다. HTML의 button을 h2로 바꿔 글자를 키우는 방식과 CSS에서 버튼의 글자·안쪽 여백·최소 높이를 조절하는 방식 중 어떤 것이 목적에 맞나요?

### 풀이 12-2

버튼의 의미와 동작을 유지하면서 CSS를 조절하는 방식이 맞습니다. h2로 바꾸면 제목 요소가 되어 기본 버튼의 의미와 조작성이 사라집니다. 수정 뒤에는 긴 버튼 문구와 작은 화면에서도 눌리는지 확인해야 합니다. 크기 하나만 바꾸고 문구가 잘리지 않는지 놓치지 않습니다.

## 12.5 app.js — 작은 함수들이 맡는 일

다음은 app.js 전체입니다. 중간을 생략하지 않았습니다. 길어 보이지만 입력 검사, 저장, 화면 생성, 상태 변경, 주제 요청으로 나누어 읽을 수 있습니다. 위에서 아래로 한 번에 외우지 말고 설명과 번갈아 읽어 보세요. 처음 보는 함수가 어디서 호출되는지 찾으면 목적이 더 분명해집니다.

```javascript file=app.js
"use strict";
const STORAGE_KEY = "study-log-v1";
const MAX_MINUTES = 600;
const MAX_RECORDS = 2000;
const form = document.querySelector("#record-form");
const topicInput = document.querySelector("#topic");
const minutesInput = document.querySelector("#minutes");
const addButton = document.querySelector("#add-record");
const message = document.querySelector("#message");
const list = document.querySelector("#records");
const filter = document.querySelector("#filter");
const summary = document.querySelector("#summary");
const empty = document.querySelector("#empty");
let records = [];
let writable = true;
let loadingTopics = false;
minutesInput.max = String(MAX_MINUTES);

function announce(text) {
  message.textContent = text;
}

function parseInput(topicText, minutesText) {
  const topic = topicText.trim();
  const raw = minutesText.trim();
  const minutes = Number(raw);
  if (topic === "" || topic.length > 80) {
    return { ok: false, error: "内容を確認".replace("内容を確認", "内容") };
  }
  if (raw === "" || !Number.isInteger(minutes)
      || minutes < 1 || minutes > MAX_MINUTES) {
    return { ok: false, error: "시간은 1~" + MAX_MINUTES + "분의 정수로 적어 주세요." };
  }
  return { ok: true, topic: topic, minutes: minutes };
}

function validData(data) {
  if (data === null || typeof data !== "object" || Array.isArray(data)) return false;
  if (data.version !== 1 || !Array.isArray(data.records)) return false;
  if (data.records.length > MAX_RECORDS) return false;
  const ids = new Set();
  for (const record of data.records) {
    if (record === null || typeof record !== "object" || Array.isArray(record)) return false;
    if (!Number.isSafeInteger(record.id) || record.id < 1 || ids.has(record.id)) return false;
    if (typeof record.topic !== "string" || record.topic.trim() === "" || record.topic.length > 80) return false;
    if (!Number.isInteger(record.minutes) || record.minutes < 1 || record.minutes > MAX_MINUTES) return false;
    if (typeof record.completed !== "boolean") return false;
    ids.add(record.id);
  }
  return true;
}

function loadRecords() {
  try {
    const text = localStorage.getItem(STORAGE_KEY);
    if (text === null) {
      records = [];
      return;
    }
    const data = JSON.parse(text);
    if (!validData(data)) throw new Error("지원하지 않는 기록 형식");
    records = data.records;
  } catch (error) {
    writable = false;
    announce("기존 저장 자료를 읽지 못했습니다. 원본은 덮어쓰지 않았습니다. 내보내기로 보존한 뒤 확인해 주세요.");
  }
}

function commitRecords(nextRecords, successText) {
  if (!writable) {
    announce("기존 자료 확인이 필요하여 변경을 잠갔습니다.");
    return false;
  }
  const data = { version: 1, records: nextRecords };
  if (!validData(data)) {
    announce("기록 형식이나 개수 제한을 확인해 주세요.");
    return false;
  }
  try {
    localStorage.setItem(STORAGE_KEY, JSON.stringify(data));
  } catch (error) {
    announce("저장하지 못했습니다. 기존 기록과 입력값은 유지했습니다.");
    return false;
  }
  records = nextRecords;
  renderRecords();
  announce(successText);
  return true;
}

function nextRecordId() {
  let maximum = 0;
  for (const record of records) {
    if (record.id > maximum) maximum = record.id;
  }
  return maximum + 1;
}

function visibleRecord(record) {
  if (filter.value === "active") return !record.completed;
  if (filter.value === "completed") return record.completed;
  return true;
}

function renderRecords() {
  list.replaceChildren();
  let total = 0;
  let visibleCount = 0;
  for (const record of records) {
    total = total + record.minutes;
    if (!visibleRecord(record)) continue;
    visibleCount = visibleCount + 1;
    const item = document.createElement("li");
    item.className = "record";
    const text = document.createElement("p");
    const stateText = record.completed ? "완료" : "진행 중";
    text.textContent = record.topic + " · " + record.minutes + "분 · " + stateText;
    const actions = document.createElement("div");
    actions.className = "actions";
    const toggle = document.createElement("button");
    toggle.type = "button";
    toggle.textContent = record.completed ? "완료 취소" : "완료 표시";
    toggle.setAttribute("aria-pressed", String(record.completed));
    toggle.addEventListener("click", function () {
      toggleRecord(record.id);
    });
    const remove = document.createElement("button");
    remove.type = "button";
    remove.textContent = "삭제";
    remove.setAttribute("aria-label", record.topic + " 기록 삭제");
    remove.addEventListener("click", function () {
      deleteRecord(record.id);
    });
    actions.append(toggle, remove);
    item.append(text, actions);
    list.append(item);
  }
  summary.textContent = "전체 " + records.length + "개 · 총 " + total + "분 · 현재 표시 " + visibleCount + "개";
  empty.textContent = visibleCount === 0 ? "이 조건에 해당하는 기록이 없습니다." : "";
  addButton.disabled = !writable;
}

function handleSubmit(event) {
  event.preventDefault();
  const input = parseInput(topicInput.value, minutesInput.value);
  if (!input.ok) {
    announce(input.error);
    return;
  }
  const next = records.slice();
  next.push({ id: nextRecordId(), topic: input.topic, minutes: input.minutes, completed: false });
  if (commitRecords(next, "기록을 이 브라우저에 저장했습니다.")) {
    form.reset();
    topicInput.focus();
  }
}

function toggleRecord(id) {
  const next = [];
  for (const record of records) {
    next.push({
      id: record.id,
      topic: record.topic,
      minutes: record.minutes,
      completed: record.id === id ? !record.completed : record.completed
    });
  }
  if (commitRecords(next, "완료 상태를 저장했습니다.")) {
    document.querySelector("#list-title").focus();
  }
}

function deleteRecord(id) {
  const next = [];
  for (const record of records) {
    if (record.id !== id) next.push(record);
  }
  if (commitRecords(next, "기록을 삭제하고 저장했습니다.")) {
    document.querySelector("#list-title").focus();
  }
}

function exportRecords() {
  let text;
  try {
    text = localStorage.getItem(STORAGE_KEY);
  } catch (error) {
    announce("저장소에 접근하지 못해 내보낼 수 없습니다.");
    return;
  }
  if (text === null) {
    announce("내보낼 저장 자료가 없습니다.");
    return;
  }
  const blob = new Blob([text], { type: "text/plain;charset=utf-8" });
  const url = URL.createObjectURL(blob);
  const link = document.createElement("a");
  link.href = url;
  link.download = "study-log-backup.txt";

function validTopics(data) {
  if (!Array.isArray(data) || data.length > 100) return false;
  for (const item of data) {
    if (item === null || typeof item !== "object") return false;
    if (typeof item.id !== "string" || typeof item.title !== "string") return false;
    if (item.id.trim() === "" || item.title.trim() === "" || item.title.length > 120) return false;
  }
  return true;
}
```

## 12.6 긴 코드를 입력·상태·표시로 나누어 읽기

첫 부분은 고정 기준과 화면 요소를 준비합니다. MAX_MINUTES는 허용 시간의 상한이고, HTML 입력의 max도 이 값으로 맞춥니다. 입력창 제한과 JavaScript 검사가 서로 다른 상한을 쓰지 않도록 연결한 것입니다. MAX_RECORDS는 이 작은 앱에서 무제한으로 데이터를 쌓지 않도록 정한 제한입니다.2,000개가 모든 브라우저의 저장 용량을 보장하는 숫자는 아닙니다. 저장 실패는 여전히 따로 처리합니다.

parseInput은 입력 문자열을 정리하고 검사합니다. 결과 객체의 ok가 참이면 정리한 주제와 시간을 사용하고, 거짓이면 이유를 보여 줍니다. 이 함수 자체는 문서를 바꾸거나 저장하지 않습니다. 그래서 작은 값만 넣어 규칙을 따로 검사할 수 있습니다. ‘문제를 작게 나누기’가 실제 앱에서 어떤 모습인지 보여 주는 부분입니다.

validData는 저장 자료의 버전과 항목 구조를 확인합니다. `Set`은 중복 여부를 다룰 때 사용할 수 있는 값의 집합입니다. 여기서는 이미 본 id를 넣어 두고, 같은 id가 다시 나오면 거절합니다. `Number.isSafeInteger`는 JavaScript가 정수로 안전하게 다룰 수 있는 범위를 포함해 검사합니다. id는 계산 결과가 충돌하지 않도록 제한이 필요합니다.

loadRecords는 저장값을 읽기만 하고, 읽기에 실패했다고 새 빈 데이터를 쓰지 않습니다. commitRecords는 다음 상태를 받지만 저장에 성공하기 전에는 기준 records를 바꾸지 않습니다. 따라서 저장이 실패하면 입력창을 비우지 않고 기존 상태도 유지할 수 있습니다. 화면에 잠깐 성공처럼 보여 주었다가 새로고침 뒤 사라지는 혼란을 줄이는 설계입니다.

renderRecords는 현재 records를 사용해 목록과 합계를 만듭니다. 필터가 일부 항목을 숨겨도 전체 합계는 전체 records 기준입니다. 문구에 ‘전체’와 ‘현재 표시’를 따로 적은 이유입니다. 어떤 합계를 보여 주는지 정의하지 않으면 필터를 바꿨을 때 사용자가 숫자를 잘못 해석할 수 있습니다.

### 연습 12-3. 저장하기 전에 입력을 지운 경우

handleSubmit에서 commitRecords 호출보다 먼저 form.reset을 실행하도록 바꿨습니다. 저장에 실패하면 사용자에게 어떤 문제가 생길 수 있나요?

### 풀이 12-3

저장하지 못했는데 입력한 내용까지 비워질 수 있습니다. 현재 코드는 저장 성공을 확인한 뒤에만 폼을 초기화합니다. 실패한 작업을 다시 시도할 수 있도록 입력을 보존하는 것입니다. 단순히 코드 줄 수가 줄었다는 이유로 실행 순서를 바꾸면 사용자의 복구 가능성이 달라질 수 있습니다.

## 12.7 배열 복사와 개별 항목 변경의 연결

새 기록을 추가할 때 `records.slice()`로 배열의 얕은 복사본을 만들었습니다. 배열 자체에 항목을 추가하는 작업을 먼저 그 복사본에서 수행하고, 저장 성공 후 기준을 교체합니다. 기존 객체들의 내부까지 깊게 복사하는 기능은 아닙니다. 이 추가 작업에서는 기존 객체의 내부를 바꾸지 않기 때문에 이 방식으로 목적을 충족합니다.

완료 표시에서는 객체의 completed를 바꿔야 합니다. 그래서 새 객체를 만들어 next에 넣습니다. 원래 객체를 먼저 바꿔 버리면 저장 실패 뒤에도 메모리의 값이 달라질 수 있기 때문입니다. 같은 ‘복사’라도 바꿀 대상이 배열인지 내부 객체인지에 따라 필요한 방식이 달라집니다.

각 버튼에 연결한 함수는 그 반복의 record.id를 사용합니다. 화면에서 몇 번째 버튼인지만 사용하는 것이 아니라 실제 기록의 id로 대상 함수를 호출합니다. 필터가 바뀌어도 같은 기록을 가리킬 수 있습니다. 이처럼 앞 장에서 배운 상태와 식별자의 구별이 완성 코드 안에 들어 있습니다.

### 연습 12-4. 잘못된 완료 처리 고치기

완료 함수를 짧게 만들려고 원본 record.completed를 바로 반대로 바꾼 뒤 저장했습니다. 저장에 실패하면 어떤 불일치가 생길 수 있고, 현재 코드의 새 객체 방식은 무엇을 보존하나요?

### 풀이 12-4

원본을 먼저 바꾸면 메모리의 상태는 변경됐지만 저장소는 이전 상태일 수 있습니다. 현재 코드는 다음 상태의 새 객체를 만들어 저장 성공 뒤에만 기준을 바꾸므로 기존 상태를 보존합니다. 얕은 배열 복사만 해 놓고 내부 객체를 바로 변경하는 것까지 안전하다고 생각하면 안 됩니다.

## 12.8 다운로드와 초기화를 정확하게 설명하기

내보내기는 저장소에 있는 원래 문자열을 파일로 내려받도록 요청합니다. 읽기 실패가 난 데이터도 가능한 범위에서 원문을 보존하려는 목적입니다. Blob은 메모리에 있는 내용을 파일처럼 다룰 수 있게 묶는 값이고, 임시 URL은 그 내용을 다운로드 링크에 연결하기 위해 만듭니다. 사용 후 URL을 해제합니다.

‘다운로드 요청’이라는 안내를 사용한 이유는 브라우저나 앱 환경에 따라 실제 파일 저장이 제한될 수 있기 때문입니다. 코드가 링크 클릭을 호출한 사실만으로 사용자의 파일함에 저장됐다고 확정하지 않습니다. 정상 브라우저에서 파일을 열어 원본과 같은지 확인하는 검사가 필요합니다.

초기화는 확인창에서 계속하겠다는 응답을 받은 뒤 이 앱의 STORAGE_KEY만 삭제합니다. `localStorage.clear()`로 같은 출처의 다른 자료까지 무조건 지우지 않습니다. 사용자의 기록을 지우는 기능은 작은 예제에서도 범위를 분명하게 정해야 합니다. 내보낸 파일을 자동으로 다시 불러오는 가져오기 기능은 이번 완성본의 범위에 포함하지 않았습니다. 파일 보존과 자동 복원 기능을 혼동하지 않습니다.

### 연습 12-5. 초기화를 취소했는데 목록이 사라진 경우

확인창을 띄우기 전에 records를 빈 배열로 바꾸고 화면을 다시 그렸습니다. 사용자가 취소를 누르면 어떤 문제가 있나요? 어느 판단을 먼저 해야 하나요?

### 풀이 12-5

사용자가 취소했는데도 현재 화면 상태를 잃을 수 있습니다. 먼저 확인 결과를 보고, 취소라면 어떤 상태도 바꾸지 않고 돌아가야 합니다. 실제 저장소 삭제가 성공한 뒤 기준 상태와 화면을 바꿉니다. 확인창이 있다는 사실보다 확인 이전에 무엇을 변경했는지가 중요합니다.

## 12.9 일부러 조건을 바꾸어 검사하기

완성본은 정상 입력만 검사해서는 안 됩니다. 시간0과601, 소수, 빈칸, 공백 주제, 긴 주제를 넣어 봅니다. 두 기록을 추가하고 완료 표시와 필터, 삭제를 해 본 뒤 새로고침합니다. 저장값이 잘못된 상황에서는 원문이 보존되고 새 추가가 잠기는지 확인합니다. 요청 실패와 시간 초과 뒤에는 재시도 버튼이 다시 활성화되는지 확인합니다.

학습 주제 API는 사용자 기록과 별개입니다. 주제 요청이 실패했다고 기록 배열을 비우지 않습니다. 이미 표시한 정상 주제 목록도 실패 전에 무조건 지우지 않으므로 이전 자료가 남을 수 있습니다. 이 경우 안내문으로 새 요청에 실패했다는 사실을 알립니다. 이전 데이터를 보여 주는 선택은 그 데이터가 얼마나 오래되어도 되는지에 따라 달라질 수 있습니다. 이 예제는 민감한 실시간 자료가 아니라 학습 주제 예시를 다룹니다.

### 연습 12-6. 요구사항을 한 가지 바꾸기

허용 학습 시간을1~900분으로 바꾸라는 요청을 받았습니다. 화면의 숫자600만900으로 바꾸면 충분할까요? 어떤 연결과 검사를 함께 확인해야 하나요?

### 풀이 12-6

MAX_MINUTES를900으로 바꾸고 입력창 max가 그 값으로 설정되는지 확인합니다. parseInput과 validData도 같은 상수를 사용하므로 저장 형식 검사와 입력 검사 기준이 함께 바뀝니다.1과900이 통과하고0과901이 실패하는지, 소수가 거절되는지 검사합니다. 이미 저장한 기록의 읽기와 새 기록 추가가 정상인지도 확인합니다. 코드 안의 숫자를 여러 곳 따로 바꾸는 것보다 기준을 한곳에서 연결하면 누락을 줄일 수 있습니다.

## 12.10 AI에게 맡길 부분과 내가 확인할 부분

긴 파일의 초안이나 반복되는 버튼 생성은 AI가 작성하도록 맡길 수 있습니다. 그러나 어떤 기록을 저장할지, 실패할 때 기존 값을 지킬지, 삭제 범위가 어디까지인지 같은 조건은 사용자의 목적과 연결됩니다. AI가 그럴듯한 화면을 만들었다고 그 조건을 모두 만족했다고 생각하면 안 됩니다.

AI 지원과 학습을 다룬 연구에서는 새 라이브러리를 사용하는 과제를 완료하는 것과 그 내용을 이해하는 것을 구별해 평가했습니다. 개발자52명을 다룬 단기 실험의 결과를 모든 초보자와 모든 웹앱에 그대로 일반화할 수는 없습니다. 다만 ‘결과물이 나왔다’는 사실과 ‘내가 수정할 수 있을 만큼 이해했다’는 사실을 따로 확인해야 한다는 설계 관점을 참고할 수 있습니다.[5]

이 책에서 확인할 질문은 구체적입니다. 버튼이 어떤 함수로 연결되는가, 문자열이 숫자로 바뀌는 줄은 어디인가, 저장 실패 후에도 입력이 남는 이유는 무엇인가, 필터된 화면에서 삭제할 대상을 어떻게 구별하는가를 설명해 보세요. 모든 기호를 암기하지 않아도 이 연결을 찾을 수 있다면 AI가 만든 앱을 더 정확히 수정하고 검증할 수 있습니다.

### 연습 12-7. 수정 요청을 구체화하기

‘앱이 별로니 싹 고쳐’라는 요청 대신, 완료 기록을 먼저 보여 주도록 바꾸고 싶습니다. 원본 데이터와 저장, 기존 기능을 보존하면서 AI에게 어떤 범위의 작업과 검사를 요구할지 짧게 작성해 보세요.

### 풀이 12-7

예를 들어 ‘표시 순서에서 완료 기록을 먼저 보여 주되 기록 id와 저장 내용은 바꾸지 마세요. 같은 완료 상태끼리는 기존 순서를 유지하세요. 필터와 삭제·완료 취소가 올바른 id를 사용하고, 새로고침 뒤에도 기록이 보존되는지 확인하세요’라고 요청할 수 있습니다. 핵심은 바꿀 표현과 보존할 데이터를 분리한 것입니다. 순서 기능을 추가한다는 이유로 전체 저장 형식을 다시 만들 필요가 있는지 먼저 판단할 수 있습니다.

## 12.11 이 트랙의 끝에서

웹을 이해한다는 것은 태그 수를 외우는 일이 아닙니다. HTML은 내용의 의미를 만들고, CSS는 사용할 공간에 맞게 보여 주며, JavaScript는 사용자 행동과 데이터를 연결합니다. 요청에는 기다림과 실패가 있고, 저장에는 범위와 손실 가능성이 있습니다. 테스트는 그 연결이 기대대로 작동하는지 확인하는 방법입니다.

처음에는 버튼 하나가 여러 파일과 함수에 연결된다는 사실이 번거롭게 느껴질 수 있습니다. 그러나 역할을 나누었기 때문에 제목은 제목이 있는 곳에서, 크기는 스타일에서, 시간 규칙은 검사 함수에서 바꿀 수 있습니다. 이제 AI에게 단순히 ‘다시 만들어’라고 말하기 전에 어느 부분의 어떤 조건을 바꿔야 하는지 찾아볼 수 있습니다. 그것이 이 트랙에서 목표로 삼은 웹앱 기초입니다.

## 이 장의 참고자료와 확인 범위

다음 5종을 참고했습니다. 최종 기록장의 전체 코드와 요구사항, 실패 정책, 연습·해설은 새로 작성했습니다. 특정 유료 책의 프로젝트를 그대로 복제하지 않았습니다.

1. [Learning Web Design, 6th Edition — 공식 목차](https://learningwebdesign.com/toc.html), Jennifer Niederst Robbins, 2025. 공개 목차와 [공식 연습자료 안내](https://learningwebdesign.com/6e/materials/index.html)를 확인해 설명과 실습이 연결되는 전체 범위를 참고했습니다. 유료 본문 전체나 다운로드 자료 전부를 통독했다고 표현하지 않습니다.
2. [CS50x — Homepage 과제](https://cs50.harvard.edu/x/psets/8/homepage/), Harvard University. 여러 웹 기술을 연결한 결과물을 요구하고 검사하는 공개 과제 본문을 확인했습니다. 그 과제의 조건을 그대로 이번 기록장의 요구사항으로 복제하지 않았습니다.
3. [MDN — Curriculum](https://developer.mozilla.org/en-US/curriculum/), MDN Web Docs. 핵심 웹 기술과 접근성을 연결하는 공개 교육 범위를 참고했습니다. 이 장의 구현 세부는 앞 장에 명시한 같은 MDN의 DOM·Storage·Fetch 공식 문서와 함께 대조했습니다.
4. [W3C WAI — Easy Checks](https://www.w3.org/WAI/test-evaluate/easy-checks/), W3C Web Accessibility Initiative. 읽기·이동·입력·조작을 확인하는 첫 점검의 공개 자료를 참고했습니다. 이 예제의 검사 통과를 완전한 접근성 인증이라고 표현하지 않습니다.
5. [How AI assistance impacts the formation of coding skills — 저자 연구 보고](https://www.anthropic.com/research/AI-assistance-coding-skills), Anthropic, 2026. 새 Python 라이브러리를 배우는 개발자52명의 실험을 설명한 공개 저자 보고를 확인했습니다. 단기·특정 과제 연구이며 모든 웹 초보자에게 같은 효과가 난다는 일반적 인과 결론으로 사용하지 않았습니다.
