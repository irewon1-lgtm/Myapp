# 8장. 엉킨 코드를 읽기 좋게 고치기

코드가 맞는 결과를 내더라도 고치기 쉬운 것은 아니다. 이름이 `a`, `b`, `x`뿐이거나, 한 함수가 계산과 화면 표시와 저장을 모두 맡으면 작은 요구 변경도 부담스럽다. 이런 코드를 읽기 쉽게 정리하고 싶을 때 **리팩터링**이라는 말을 쓴다.

리팩터링은 외부에서 관찰하는 동작을 유지하면서 내부 구조를 개선하는 작업이다. 결과가 틀린 코드를 맞게 고치는 버그 수정이나, 무료 배송 기준을 바꾸는 기능 변경과는 구별한다. 실제 작업에서 함께 일어날 수는 있지만, 한 번의 변경에 섞으면 무엇 때문에 결과가 달라졌는지 알아보기 어렵다.

7장에서 만든 테스트가 여기서 기준이 된다. 구조를 바꾸기 전에 현재 동작을 확인하고, 작은 수정 뒤에 같은 입력으로 다시 검사한다. “훨씬 깔끔해 보인다”는 감상만으로 안전한 변경이라고 판단하지 않는다.

## 8.1 무엇을 그대로 유지할지 먼저 정하기

다음 함수는 상품 가격 목록과 쿠폰 사용 여부를 받아 결제 금액을 계산한다. 상품 합계가 5000원 이상이고 쿠폰을 사용하면 500원을 할인한다. 이번 장에서는 배송비가 없고 입력 가격은 음수가 아닌 정수라고 가정한다.

```python
def calc(a, b):
    x = 0
    for z in a:
        x = x + z
    if b:
        if x >= 5000:
            x = x - 500
    return x


print(calc([2000, 3500], True))
print(calc([2000, 3500], False))
print(calc([2000], True))
```
```text
5000
5500
2000
```

이 코드는 약속한 범위에서는 계산할 수 있다. 그러나 함수 이름과 변수 이름만 읽어서는 `a`가 가격 목록인지 수량 목록인지, `b`가 쿠폰인지 회원 상태인지 알기 어렵다. 몸체를 끝까지 해석해야 이름의 뜻을 추측할 수 있다.

수정 전에 지킬 동작을 적자. 가격 목록을 변경하지 않는다. 쿠폰이 없으면 합계를 그대로 반환한다. 쿠폰이 있어도 합계가 5000원 미만이면 할인하지 않는다. 정확히 5000원인 주문은 할인한다. 빈 목록은 0원이다. 이 규칙과 대표 입력의 결과가 리팩터링의 비교 기준이다.

### 연습 8-1. 리팩터링인가, 기능 변경인가?

다음 작업을 구별해 보자. ① `x`를 `subtotal`로 바꾼다. ② 할인액을 500원에서 1000원으로 바꾼다. ③ 합계 계산을 별도 함수로 옮긴다. ④ 원래 없던 음수 가격 거절 기능을 추가한다.

### 풀이 8-1

①과 ③은 관찰 가능한 동작이 같도록 올바르게 수행했다면 리팩터링이다. ②는 요금 결과가 바뀌므로 기능 변경이다. ④도 기존에 받아들이던 입력에서 새 예외가 날 수 있으므로 단순 내부 정리가 아니다. 유익한 변경인지 여부와 리팩터링인지 여부는 별개의 질문이다.

## 8.2 이름은 현재 값의 역할을 말해야 한다

먼저 내부 이름을 읽기 쉽게 바꾸자. 동작을 바꾸지 않는 가장 작은 단계다. 함수 외부에서 호출하는 이름 `calc`는 우선 그대로 두고, 매개변수와 내부 이름을 정리한다. 단, 다른 코드가 `calc(a=..., b=...)`처럼 키워드 인수로 호출한다면 매개변수 이름 변경도 외부 호출에 영향을 줄 수 있다. 여기서는 제시된 위치 인수 호출만 사용한다고 명시한다.

```python
def calc(prices, use_coupon):
    subtotal = 0
    for price in prices:
        subtotal = subtotal + price
    if use_coupon:
        if subtotal >= 5000:
            subtotal = subtotal - 500
    return subtotal


assert calc([2000, 3500], True) == 5000
assert calc([2000, 3500], False) == 5500
assert calc([2000], True) == 2000
assert calc([], True) == 0
print("이름 변경 후 검사 통과")
```
```text
이름 변경 후 검사 통과
```

`prices`는 여러 가격, `price`는 현재 가격, `use_coupon`은 쿠폰 사용 여부, `subtotal`은 합계라는 역할을 드러낸다. 하지만 마지막에는 이 이름에 할인 후 금액이 다시 들어간다. 그러면 `subtotal`이라는 이름이 처음과 끝에서 조금 다른 의미를 갖게 된다. 한 이름을 여러 뜻으로 재사용하면 읽는 사람이 시점을 계속 기억해야 한다.

할인 전과 할인 후 값이 모두 중요하다면 `subtotal`과 `payable`처럼 이름을 나누는 편이 좋다. 변수 수가 하나 늘더라도 의미가 분명해진다면 읽기 쉬워질 수 있다. 변수는 적을수록 무조건 좋은 것이 아니라, 서로 다른 값을 구별하는 데 필요하면 쓰는 것이다.

### 풀이 8-2

이 맥락에서는 `ordered_count`가 주문한 개수임을 가장 구체적으로 드러낸다. `quantity`도 수량이라는 뜻은 전달하지만 재고인지 주문 수량인지 추가 맥락이 필요하다. 다만 모든 이름을 아주 길게 만드는 것이 목적은 아니다. 가까운 문맥에서 충분히 분명하면 짧아도 된다. 코드가 실제로 하는 일과 이름의 의미가 맞고, 혼동할 두 값을 구별할 수 있어야 한다.

## 8.3 계산의 일부를 함수로 추출하기

상품 합계를 구하는 부분은 쿠폰 정책과 분리할 수 있다. 관련 문장들을 새 함수로 옮기고, 원래 위치에서 그 함수를 호출하는 작업을 **함수 추출**이라고 한다.

```python
def sum_prices(prices):
    subtotal = 0
    for price in prices:
        subtotal = subtotal + price
    return subtotal


def calc(prices, use_coupon):
    subtotal = sum_prices(prices)
    payable = subtotal
    if use_coupon:
        if subtotal >= 5000:
            payable = subtotal - 500
    return payable


assert sum_prices([2000, 3500]) == 5500
assert calc([2000, 3500], True) == 5000
assert calc([5000], True) == 4500
assert calc([4999], True) == 4999
assert calc([], True) == 0
print("함수 추출 후 검사 통과")
```
```text
함수 추출 후 검사 통과
```

새 함수는 가격 목록을 입력받고 합계 숫자를 돌려준다. 쿠폰 여부는 알지 못한다. 원래 함수는 합계가 어떻게 계산되는지 세부 반복문을 읽지 않고도 `sum_prices`라는 역할을 이용한다. 이번 변경에서 합계에 `return`을 빼먹거나 호출 결과를 받지 않으면 즉시 테스트가 실패할 수 있다.

함수 추출을 할 때는 **새 함수에 무엇을 전달해야 하는지, 새 함수에서 무엇을 반환해야 하는지**가 경계다. 바깥의 임시 변수를 함수 안에서 우연히 읽도록 만들면 분리한 것처럼 보여도 의존성이 숨는다. 필요한 값을 인수로 명확하게 전달하고 결과를 반환하는 구조가 처음 읽는 사람에게 더 분명하다.

### 연습 8-3. 함수를 너무 잘게 나누면

`subtotal = subtotal + price` 한 줄만 함수로 만든 뒤 매 반복마다 호출하게 바꾸면 반드시 더 좋아지는가? 합계 계산 전체를 함수로 묶는 것과 비교해 보자.

### 풀이 8-3

반드시 그렇지는 않다. 단순 덧셈 한 줄에 별도 이름을 붙여도 새로운 업무 의미가 드러나지 않으면 파일을 오가는 부담만 늘 수 있다. 합계 계산 전체는 “가격 목록에서 합계 숫자를 만든다”는 독립 역할이 있으므로 이름으로 읽기 좋다. 분리 단위는 줄 수 공식으로 정하기보다 하나의 설명 가능한 역할인지로 판단한다.

## 8.4 중첩을 줄이되 뜻을 바꾸지 않기

현재 코드는 쿠폰 사용 여부 안에서 다시 금액 조건을 검사한다. 두 조건이 모두 참일 때만 할인하므로 `and`로 연결해 한 조건으로 쓸 수 있다.

```python
def sum_prices(prices):
    subtotal = 0
    for price in prices:
        subtotal = subtotal + price
    return subtotal


def calc(prices, use_coupon):
    subtotal = sum_prices(prices)
    if use_coupon and subtotal >= 5000:
        return subtotal - 500
    return subtotal


print(calc([5000], True))
print(calc([5000], False))
print(calc([4999], True))
```
```text
4500
5000
4999
```

`and`는 두 조건이 함께 성립해야 한다는 의미다. 파이썬은 왼쪽 조건이 거짓이면 오른쪽을 평가하지 않고 결과를 정할 수 있다. 이 예제의 오른쪽은 단순 비교라 특별한 부수효과가 없고, 원래 중첩 조건과 같은 할인 조건을 표현한다.

그러나 복잡한 함수 호출이나 상태 변경이 조건식에 섞여 있으면 평가 순서까지 달라지지 않는지 확인해야 한다. 겉모양이 짧아졌다고 곧바로 같은 코드라고 판단할 수는 없다. 리팩터링은 문장 수를 줄이는 게임이 아니라 **의미를 유지하면서 판단 부담을 줄이는 작업**이다.

### 연습 8-4. `and`와 `or`를 바꾸면

할인 조건을 `use_coupon or subtotal >= 5000`으로 바꾸면 어떤 주문에서 원래와 다른 결과가 나오는가? 반례 두 개를 들어 보자.

### 풀이 8-4

쿠폰이 있지만 합계가 2000원인 주문도 `or`에서는 할인된다. 쿠폰이 없어도 합계가 6000원이면 할인된다. 원래는 두 조건이 모두 참이어야 했지만 `or`는 하나만 참이어도 통과하기 때문이다. 이런 변경은 중첩을 정리한 리팩터링이 아니라 할인 정책을 바꾼 것이다. 반례를 손으로 만드는 능력이 구조 변경을 검증하는 데 도움이 된다.

## 8.5 숫자에 이름을 붙이면 변경 이유가 드러난다

코드의 `5000`과 `500`은 서로 다른 규칙이다. 하나는 할인 기준 금액이고 다른 하나는 할인액이다. 숫자만 여러 곳에 반복되면 어느 숫자를 바꿔야 하는지 헷갈릴 수 있다. 의미가 있는 정책 값에 이름을 붙이면 역할이 드러난다.

```python
COUPON_MINIMUM = 5000
COUPON_DISCOUNT = 500


def sum_prices(prices):
    subtotal = 0
    for price in prices:
        subtotal = subtotal + price
    return subtotal


def calc(prices, use_coupon):
    subtotal = sum_prices(prices)
    if use_coupon and subtotal >= COUPON_MINIMUM:
        return subtotal - COUPON_DISCOUNT
    return subtotal


print(calc([2000, 3500], True))
```
```text
5000
```

대문자 이름은 파이썬에서 값 변경이 기술적으로 금지되었다는 뜻이 아니다. 프로그램에서 상수처럼 취급하려는 값이라는 관례다. 그렇다고 모든 `0`과 `1`에도 긴 이름을 붙여야 하는 것은 아니다. `total = 0`의 0은 합계의 출발값으로 이미 의미가 분명하다. 여러 곳의 정책 판단에 연결되는 숫자처럼 **변경 이유와 의미가 독립적인 값**이 우선 대상이다.

### 연습 8-5. 같은 숫자, 다른 이유

배송비 2000원과 상품 한 개 가격 2000원이 우연히 같다고 하자. 둘을 `COMMON_AMOUNT = 2000` 하나로 묶으면 어떤 문제가 생길 수 있는가?

### 풀이 8-5

배송비만 2500원으로 바꾸려 했는데 상품 가격까지 함께 바뀔 수 있다. 숫자가 같다는 이유만으로 같은 정책은 아니다. 중복 제거는 겉으로 같은 글자를 모으는 작업이 아니라 **같은 이유로 함께 바뀌어야 하는 지식**을 모으는 작업이다. 서로 다른 이유로 정해지는 값은 분리해 두어야 한다.

## 8.6 계산과 표시를 분리하기

계산 함수가 화면용 문장을 바로 출력하면 앱이 커질 때 재사용하기 어렵다. 같은 금액을 영수증 화면, 요약 화면, 저장 자료에서 다르게 표현해야 할 수 있기 때문이다. 계산은 숫자를 반환하고 표시 함수가 문장을 만들도록 역할을 나누자.

```python
def calculate_payable(prices, use_coupon):
    subtotal = 0
    for price in prices:
        subtotal = subtotal + price
    if use_coupon and subtotal >= 5000:
        return subtotal - 500
    return subtotal


def payment_message(amount):
    return "결제 예정 금액: " + str(amount) + "원"


amount = calculate_payable([2000, 3500], True)
message = payment_message(amount)
print(message)
```
```text
결제 예정 금액: 5000원
```

계산 함수에는 한국어 표시 문장이 없고 표시 함수에는 할인 기준이 없다. 그러면 문구를 “총액”으로 바꾸는 작업과 할인액을 바꾸는 작업이 서로 다른 위치에서 일어난다. 이름을 길게 바꾸는 것보다 이런 책임 경계가 실제 수정의 부담을 더 크게 줄일 수 있다.

이 예제에서는 새 함수 이름을 제시했지만 실제 운영 앱에서 기존 공개 함수 이름을 바꿀 때는 호출하는 파일을 모두 확인해야 한다. 외부 코드가 이전 이름을 사용한다면 호환용 함수를 잠시 남기거나 호출부를 함께 바꾸는 절차가 필요하다. 이름 변경이 내부에만 머무는지 외부 연결을 끊는지도 확인해야 한다.

### 연습 8-6. 어떤 함수가 바뀌어야 하는가?

결제 문구를 영어로 보여 달라는 요구와 쿠폰 기준을 7000원으로 바꾸라는 요구가 각각 들어왔다. 방금 구조에서는 어느 함수를 바꿔야 하는가? 두 요구를 같은 커밋에서 처리할 필요가 있는가?

### 풀이 8-6

표시 언어는 `payment_message`, 쿠폰 기준은 `calculate_payable`의 정책 부분을 바꾼다. 서로 독립적인 변경이라면 각각 검사하고 기록하는 편이 변경 이유를 추적하기 쉽다. 배포 계획 때문에 묶을 수는 있지만, 코드 수정과 검증에서는 두 이유를 구별해야 한다. 모든 것을 한꺼번에 바꾼 뒤 어느 부분 때문에 문제가 생겼는지 찾는 상황을 피하는 것이 목적이다.

## 8.7 정리 전후를 같은 사례로 비교하기

마지막으로 정리 전 함수와 정리 후 함수를 같은 입력에 넣어 결과가 같은지 비교하자. 이 비교는 기존 동작 보존에 도움이 된다. 다만 기존 함수에도 오류가 있었다면 같은 오류를 유지한 두 함수가 일치할 수 있으므로, 요구사항에서 직접 정한 기대값 검사도 함께 있어야 한다.

```python
def before(prices, coupon):
    x = 0
    for p in prices:
        x = x + p
    if coupon:
        if x >= 5000:
            x = x - 500
    return x


def after(prices, use_coupon):
    subtotal = sum(prices)
    if use_coupon and subtotal >= 5000:
        return subtotal - 500
    return subtotal


cases = [
    ([], False),
    ([], True),
    ([4999], True),
    ([5000], True),
    ([5001], False),
    ([2000, 3500], True),
]
for prices, coupon in cases:
    original = prices.copy()
    assert before(prices, coupon) == after(prices, coupon)
    assert prices == original

assert after([5000], True) == 4500
print("전후 비교 6사례와 경계 기대값 검사 통과")
```
```text
전후 비교 6사례와 경계 기대값 검사 통과
```

`sum(prices)`는 숫자들의 합계를 구하는 내장 함수다. 우리가 반복으로 익힌 합계 패턴을 제공한다. 입력을 음수가 아닌 정수 목록으로 정했기 때문에 이 예제에서는 같은 계산을 표현한다. 자료형이 다른 복잡한 객체까지 아무 조건 없이 같은 대체라고 일반화하지는 않는다.

`cases`의 각 원소는 `(가격 목록, 쿠폰 여부)`처럼 두 값을 묶은 튜플이다. `for prices, coupon in cases:`는 이번 원소의 두 값을 두 이름으로 나누어 받는다. 이 문법이 아직 낯설면 사례마다 직접 두 함수를 호출해도 원리는 같다. 테스트를 짧게 만들려다가 검사 내용을 이해할 수 없게 만드는 것은 목적에 맞지 않는다.

### 연습 8-7. 전후 비교만으로 놓치는 것

정리 전후 함수가 모두 정확히 5000원인 주문에 할인을 하지 않는 같은 오류를 가졌다면, 두 결과를 비교하는 테스트는 통과하는가? 이를 잡는 검사를 적어 보자.

### 풀이 8-7

두 오답이 같으므로 전후 비교는 통과할 수 있다. 요구사항에서 직접 정한 `assert after([5000], True) == 4500`을 추가하면 오류가 드러난다. 동작 보존 검사와 요구사항 검사는 서로 목적이 다르다. 리팩터링이 기존 동작을 유지했는지와 기존 동작 자체가 올바른지는 따로 확인해야 한다.

### 연습 8-8. 안전한 작업 순서

읽기 어려운 주문 함수에 오류도 있고 신규 할인 기능도 추가해야 한다. 한 번에 전부 다시 쓰는 대신 작업을 어떤 순서로 나누겠는가?

### 풀이 8-8

먼저 현재 오류를 재현하는 사례와 기대값을 확보한다. 오류와 직접 관련된 부분을 수정하고 검사한다. 그다음 동작을 유지하는 작은 구조 정리를 수행하며 같은 검사를 반복한다. 마지막으로 새 할인 요구사항을 분명히 적고 그에 맞는 테스트와 구현을 추가한다. 상황에 따라 작은 구조 정리가 먼저 필요할 수 있지만, 각 변경이 어떤 목적을 갖는지는 계속 구별한다.

리팩터링의 결과는 장식된 코드가 아니라 다음 사람이 변경 이유를 찾기 쉬운 코드여야 한다. 다음 장에서는 처음 보는 작은 작업 관리 프로그램을 받아, 요구사항 파악부터 수정·검증까지 지금까지 배운 모든 단계를 한 흐름으로 수행한다.
