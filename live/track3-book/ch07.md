# 7장. 테스트로 코드가 맞는지 검증하기

배송비 계산을 고칠 때마다 9999원, 10000원, 10001원을 직접 넣어 확인한다고 하자. 처음 몇 번은 할 만하지만 다른 기능을 추가할수록 확인할 사례도 늘어난다. 이전에 검사했던 입력을 잊으면 같은 실수가 다시 들어와도 모르고 넘어갈 수 있다. 사람이 기억하던 기대 결과를 코드에 적어 두면 컴퓨터가 반복해서 비교할 수 있다. 이것이 자동 테스트의 출발점이다.

테스트는 프로그램 전체가 완벽하다는 증명이 아니다. **정해 둔 조건에서 실제 결과가 기대와 일치하는지 확인하는 절차**다. 테스트가 성공해도 빠뜨린 입력이나 잘못 정한 기대값이 있을 수 있다. 따라서 “몇 개 통과했는가”만큼 “어떤 규칙을 어떤 사례로 검사했는가”가 중요하다.

이번 장에서는 문구점의 배송비 함수로 테스트를 처음부터 만든다. 테스트 도구를 설치하기 전에 일반 파이썬 코드와 `assert`만으로 원리를 이해하고, 나중에 검사들을 의미 있는 묶음으로 나눈다.

## 7.1 기대값과 실제값을 독립적으로 준비하기

검사할 규칙은 이렇다. 상품 합계는 음수가 아닌 정수이고 10000원 이상이면 배송비 0원, 미만이면 배송비 2000원이다. 빈 장바구니인지는 이 함수가 아니라 주문 전체 함수에서 처리한다고 하자. 따라서 합계 숫자 `0`을 이 함수에 직접 전달하면 배송비는 `2000`이다.

```python
def shipping_fee(subtotal):
    if subtotal >= 10000:
        return 0
    return 2000


expected = 0
actual = shipping_fee(10000)
print("기대:", expected)
print("실제:", actual)
print("일치:", actual == expected)
```
```text
기대: 0
실제: 0
일치: True
```

`expected`는 규칙을 읽고 사람이 미리 정한 값이다. `actual`은 검사할 함수를 실행해서 얻은 값이다. 두 값이 같은지 비교했다. 만약 기대값을 `expected = shipping_fee(10000)`이라고 만들면 같은 함수를 두 번 실행해 서로 비교할 뿐이어서 그 함수의 계산 오류를 발견하기 어렵다.

테스트도 코드이므로 테스트 자체에 실수가 있을 수 있다. 입력과 기대값을 작은 표로 먼저 적으면 검토하기 쉽다. 코드에서 값이 나왔다고 정답인 것이 아니라, 사용자가 정한 규칙과 독립적인 계산이 기대값의 근거가 되어야 한다.

### 연습 7-1. 잘못된 기대값의 근거

`expected = buggy_function(5)`와 `actual = buggy_function(5)`를 만든 뒤 둘이 같은지 비교하는 테스트가 왜 함수의 오류를 찾기 어려운지 설명해 보자.

### 풀이 7-1

같은 잘못된 계산을 두 번 실행하면 같은 오답이 나올 수 있다. 두 결과가 일치한다는 사실은 요구사항과 일치한다는 뜻이 아니다. 기대값은 요구사항을 손으로 적용하거나 검증된 별도의 근거로 정해야 한다. 동일한 잘못을 반복하는 두 계산은 서로를 검증하는 독립적인 기준이 되지 못한다.

## 7.2 `assert`로 어긋난 결과를 멈추게 하기

일치 여부를 매번 눈으로 찾는 대신 `assert`를 사용할 수 있다. `assert 조건`은 조건이 참이면 다음으로 진행하고, 거짓이면 `AssertionError`를 발생시킨다. 개발 중의 기대를 검사하는 문장이다.

```python
def shipping_fee(subtotal):
    if subtotal >= 10000:
        return 0
    return 2000


assert shipping_fee(9999) == 2000
assert shipping_fee(10000) == 0
assert shipping_fee(10001) == 0
print("배송 경계 검사 통과")
```
```text
배송 경계 검사 통과
```

세 조건이 모두 참이므로 마지막 출력에 도달한다. 가운데 구현이 틀렸다면 그 지점에서 멈추어 기대가 깨졌음을 알려 준다. 단순히 `True`를 여러 줄 출력하는 것보다 실패가 분명하게 드러난다.

`assert`는 사용자 입력 검증을 대신하는 안전장치로 사용하지 않는다. 파이썬의 최적화 실행 옵션에 따라 어설션 검사가 제거될 수 있기 때문이다. 가격이 음수면 허용하지 않는다는 실제 프로그램 규칙은 명시적인 조건문과 예외로 구현하고, 그 동작을 테스트에서 `assert`로 검사한다. **검사 대상의 기능과 그 기능을 검증하는 코드는 역할이 다르다.**

### 연습 7-2. 실패하는 검사를 고치지 않기

배송비 함수의 비교 연산자를 `>`로 잘못 바꾸었다. 10000원을 검사하는 줄에서 실패한다. 이를 통과시키려고 기대값을 2000으로 바꾸면 올바른 수정인가?

### 풀이 7-2

아니다. 요구사항이 여전히 “10000원 이상 무료”라면 기대값 0원이 맞고 구현이 틀렸다. 실패하는 테스트를 없애거나 오답으로 기대값을 바꾸면 경고등을 끈 것뿐이다. 반대로 사람이 정말 “10000원 초과 무료”로 정책을 바꾼 경우에는 요구사항과 구현과 테스트를 함께 바꿔야 한다. 먼저 어떤 약속이 바뀌었는지 구별하자.

## 7.3 정상값만 여러 개 넣는 것으로 충분하지 않다

9999, 10000, 10001을 선택한 이유는 무료 배송 규칙이 바뀌는 경계를 확인하려는 것이다. 20000, 30000, 50000만 검사하면 무료 배송 분기만 지나가므로 유료 배송 쪽 오류를 놓칠 수 있다. 입력 숫자가 많아도 같은 종류만 모으면 새로운 실패를 발견하는 힘은 제한적이다.

입력을 고를 때는 정상적인 일반 사례, 규칙이 바뀌는 경계, 빈 자료, 허용되지 않는 자료를 나누어 생각한다. 자료 목록을 반환하는 함수라면 순서와 중복, 원본 변경 여부도 검사 대상이 될 수 있다. 모든 함수에 똑같은 항목을 기계적으로 붙이는 것이 아니라 그 함수의 약속이 무엇인지에 맞춘다.

| 검사 질문 | 배송비 또는 목록 처리의 예 |
| --- | --- |
| 일반 입력에서 맞는가? | 합계 5000원의 배송비는 2000원 |
| 경계에서 맞는가? | 9999·10000·10001원 |
| 비어 있으면 무엇인가? | 빈 장바구니의 최종 금액은 0원 |
| 잘못된 입력을 구별하는가? | 음수 합계는 예외로 거절 |
| 부수효과가 없는가? | 정렬 결과를 만들어도 원본 순서는 그대로 |

함수 내부를 보지 않고 입력과 기대 결과를 정하는 검사를 **블랙박스 관점**이라고 한다. 반대로 내부 조건문과 반복 경로를 보며 각 경로가 실행되도록 고르는 것은 **화이트박스 또는 글래스박스 관점**이다. 서로 경쟁하는 두 방식이 아니라 보완하는 관점이다. 요구사항에서 빠진 경로를 구현만 보고 찾지 못할 수 있고, 구현의 특이한 분기는 외부 사례만으로 놓칠 수 있다.

### 연습 7-3. 합계 함수의 검사 사례

숫자 리스트를 받아 합계를 반환하며 빈 리스트는 0을 반환하는 함수가 있다. `[1, 2]`만 검사하는 대신 성격이 다른 사례 네 가지와 기대값을 적어 보자.

### 풀이 7-3

예를 들어 빈 목록 `[] → 0`, 한 항목 `[7] → 7`, 음수만 있는 `[-2, -5] → -7`, 양수와 음수가 섞인 `[8, -8] → 0`을 고를 수 있다. 빈 입력의 초기값, 한 항목 처리, 부호, 상쇄를 각각 확인한다. 자료형 오류를 어떻게 처리하는지는 함수의 입력 계약을 추가로 정해야 한다.

## 7.4 예상한 예외가 발생하는지도 검사한다

잘못된 입력에서 예외를 발생시키는 것도 정상적인 설계 결과일 수 있다. 함수가 음수 합계를 거절하도록 바꾸어 보자. 여기서는 입력이 정수라는 전제 아래 음수 여부만 검사한다.

```python
def shipping_fee(subtotal):
    if subtotal < 0:
        raise ValueError("상품 합계는 음수일 수 없습니다")
    if subtotal >= 10000:
        return 0
    return 2000


raised = False
try:
    shipping_fee(-1)
except ValueError:
    raised = True

assert raised
print("음수 거절 검사 통과")
```
```text
음수 거절 검사 통과
```

`raise`는 예외를 명시적으로 발생시키는 문장이다. 테스트는 먼저 예외 발생 표시를 `False`로 준비한다. 음수를 전달한 호출이 예상한 `ValueError`를 발생시키면 표시가 `True`로 바뀐다. 마지막 어설션은 그 일이 실제로 일어났는지 확인한다.

예외가 발생했다는 사실만으로 충분하지 않은 상황도 있다. 잘못된 변수 이름 때문에 `NameError`가 났다면 음수 검증이 정상이라고 볼 수 없다. 그래서 위 테스트는 예상한 종류인 `ValueError`만 처리한다. 다른 예외가 나면 테스트도 실패로 드러나게 둔다.

### 연습 7-4. 아무 예외나 통과시키면

방금 테스트의 `except ValueError`를 `except Exception`으로 바꾸면 어떤 오류를 놓칠 수 있는가? 원래 음수 검증 코드가 삭제되고 함수 안에 이름 오타가 생겼다고 가정해 보자.

### 풀이 7-4

이름 오타로 `NameError`가 나도 넓은 예외 처리에 잡혀 `raised = True`가 된다. 그러면 음수 거절 기능이 올바르게 동작했다고 잘못 판단할 수 있다. 실패를 예상하는 테스트에서도 실패의 **종류와 조건**이 요구사항에 맞는지 확인해야 한다. “무언가 터졌다”와 “정해 둔 이유로 거절했다”는 다르다.

## 7.5 반환값뿐 아니라 원본도 검사하기

3장에서 `sorted`는 새 바깥 리스트를 반환하고 `sort`는 원본을 바꾼다고 배웠다. “원본 순서를 보존한다”가 함수의 약속이라면 정렬 결과만 검사해서는 부족하다.

```python
def ordered_prices(prices):
    return sorted(prices)


original = [3000, 1000, 2000]
before = original.copy()
result = ordered_prices(original)

assert result == [1000, 2000, 3000]
assert original == before
assert result is not original
print("결과와 원본 보존 검사 통과")
```
```text
결과와 원본 보존 검사 통과
```

첫 검사는 값과 순서가 맞는지 확인한다. 둘째는 호출 후 원본이 바뀌지 않았는지 확인한다. 셋째는 새 리스트라는 약속까지 확인한다. 이 약속이 필요 없는 함수라면 동일성 검사를 굳이 강요하지 않아도 된다. 테스트는 스타일 취향이 아니라 실제 요구사항을 검사해야 한다.

원본이 중첩된 리스트와 딕셔너리라면 `before = original.copy()`만으로 변경 전 상태를 독립적으로 보관하지 못할 수 있다. 안쪽 객체가 공유되면 원본과 비교 기준이 함께 바뀌어 검사가 통과할 수 있다. 그 경우에는 `deepcopy` 같은 적절한 복사나 변경 전의 독립적인 기대 자료를 사용해야 한다.

### 연습 7-5. 비교 기준도 함께 바뀌었다

`original = [{"qty": 2}]`, `before = original.copy()`를 만든 뒤 함수가 `original[0]["qty"]`를 5로 바꾸었다. `original == before`가 참으로 나오는 이유는 무엇인가?

### 풀이 7-5

바깥 리스트는 둘이지만 안쪽 딕셔너리를 공유하고 있다. `before`도 변경된 수량 5를 보므로 두 목록은 같아 보인다. 원본 보존을 검사하려면 비교 기준이 원본 변경의 영향을 받지 않아야 한다. 테스트 자체에도 3장의 참조 규칙이 적용된다.

## 7.6 테스트를 작은 이름으로 나누기

검사 줄이 많아지면 무엇을 검사하는지 묶음으로 나누는 것이 좋다. 다음 예제는 별도 설치 없이 실행할 수 있는 작은 테스트 파일이다. 각 테스트 함수의 이름은 확인하려는 약속을 설명한다.

```python
def shipping_fee(subtotal):
    if subtotal < 0:
        raise ValueError("상품 합계는 음수일 수 없습니다")
    if subtotal >= 10000:
        return 0
    return 2000


def test_paid_shipping():
    assert shipping_fee(0) == 2000
    assert shipping_fee(5000) == 2000
    assert shipping_fee(9999) == 2000


def test_free_shipping():
    assert shipping_fee(10000) == 0
    assert shipping_fee(10001) == 0


def test_negative_rejected():
    raised = False
    try:
        shipping_fee(-1)
    except ValueError:
        raised = True
    assert raised


test_paid_shipping()
test_free_shipping()
test_negative_rejected()
print("배송비 검사 6사례 통과")
```
```text
배송비 검사 6사례 통과
```

테스트 함수도 일반 함수이므로 정의만 해서는 실행되지 않는다. 마지막 세 호출이 실제 검사를 수행한다. 전문 테스트 도구는 이런 함수들을 찾아 실행하고 실패 위치를 모아 보고하는 일을 도와준다. 예를 들어 `pytest` 같은 도구를 사용할 수 있지만, 이 장의 원리를 이해하는 데 새로운 도구 설치가 필수는 아니다. 앱의 파이썬 실습에서도 위 코드를 그대로 실행할 수 있다.

한 함수의 역할을 독립적으로 검사하는 것을 **단위 테스트**라고 부른다. 배송비 함수와 상품 합계 함수를 따로 검사하는 것이 예다. 둘을 연결한 최종 주문 금액도 올바른지 검사하는 것은 **통합된 동작의 검사**다. 각 부품이 맞아도 잘못된 값을 연결하면 전체가 틀릴 수 있으므로 둘 다 필요하다.

### 연습 7-6. 부품 검사는 통과했는데 전체가 틀리다

상품 합계 함수는 10000원을 정확히 반환하고 배송비 함수도 10000원에 0원을 반환한다. 그런데 최종 주문 함수가 배송비 함수에 상품 합계 대신 상품 종류 수 `2`를 전달한다면 어떤 결과가 생길 수 있는가? 어느 수준의 검사가 이를 잡는가?

### 풀이 7-6

배송비 함수는 자신이 받은 값 `2`를 합계로 보고 유료 배송비 2000원을 반환한다. 각 함수의 단독 검사만으로는 호출한 쪽이 잘못된 값을 전달한 사실을 확인하지 못할 수 있다. 실제 장바구니를 최종 주문 함수에 넣어 10000원이 나오는지 확인하는 연결 검사가 필요하다. 테스트 실패가 발생하면 값이 어느 함수 경계에서 달라졌는지 추적한다.

## 7.7 통과 숫자보다 중요한 검사 범위

“테스트 100개가 통과했다”는 보고를 보았다고 하자. 모두 같은 정상 입력만 조금씩 바꾼 검사라면 빈 목록이나 경계값 오류를 여전히 놓칠 수 있다. 반대로 검사 수가 적더라도 핵심 위험을 서로 다르게 겨냥했다면 더 많은 문제를 드러낼 수 있다. 수량은 범위를 설명할 때 보조 정보이지 정확성을 보장하는 점수가 아니다.

코드의 모든 줄이 한 번씩 실행되었다는 **커버리지**도 유용하지만 완전한 보장은 아니다. 같은 줄에서도 값의 조합이 달라지면 결과가 달라질 수 있다. 예를 들어 조건문의 참·거짓 경로를 모두 실행했어도 기준과 같은 값을 빼먹으면 경계 오류를 놓칠 수 있다. 자동 검사의 통과 결과를 읽을 때는 어떤 입력을 넣었는지 함께 보아야 한다.

좋은 마무리는 “실패를 재현한 사례가 수정 후 통과했으며, 관련 정상·경계·빈 자료·원본 보존 검사를 다시 실행했다. 아직 검사하지 않은 범위는 이렇다”라고 말하는 것이다. 이는 자신 없는 표현이 아니라 결과가 뒷받침하는 범위를 정확하게 설명하는 방식이다.

### 연습 7-7. 새 검사 하나 추가하기

검색 함수가 첫 상품을 잘 찾는 테스트만 있다. 마지막 상품을 못 찾는 오류와 없는 상품을 잘못 반환하는 오류를 드러내려면 어떤 검사를 추가할까?

### 풀이 7-7

상품 두 개 이상인 목록에서 마지막 항목의 이름을 검색하고 해당 딕셔너리가 나오는지 검사한다. 다음으로 목록에 없는 이름을 검색해 `None`이 나오는지 검사한다. 빈 목록에도 `None`을 기대하는 검사를 추가할 수 있다. 첫 항목 성공만으로는 중간의 조기 반환 오류와 검색 실패 처리를 확인할 수 없다.

### 연습 7-8. 수정 이후 남겨 둘 것

어떤 오류를 고쳤고 당장은 잘 작동한다. 원래 오류를 일으킨 입력은 이제 필요 없으니 지워도 될까? 회귀 검사와 연결해 설명해 보자.

### 풀이 7-8

원래 실패 입력을 테스트로 남기면 같은 오류가 다시 들어오는 것을 잡을 수 있다. 기능이 커지거나 AI가 코드를 다시 작성할 때 이전에 고친 경계 처리가 사라질 수 있기 때문이다. 물론 요구사항이 바뀌어 더 이상 유효하지 않은 기대값은 갱신해야 하지만, 단지 지금 통과한다는 이유로 검사를 없애지는 않는다.

이제 테스트는 “개발이 끝난 뒤 한 번 눌러 보는 것”이 아니라 코드를 고치는 동안 계속 사용할 비교 기준이 되었다. 다음 장에서는 이 기준을 곁에 두고, 동작을 바꾸지 않으면서 읽기 어려운 코드를 정리하는 리팩터링을 배운다.
