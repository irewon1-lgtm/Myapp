# 9장. 남이 만든 코드를 해부하고 수정하기

이제 작은 작업 관리 앱의 기능을 맡았다고 하자. 사용자는 “아직 끝내지 않았고 일주일 안에 해야 하는 작업만 보여 달라”고 요청했다. 다른 사람이 작성한 함수가 이미 있지만 결과가 이상하다. 코드 전체를 새로 만들기 전에 어떤 데이터를 받고 어떤 결과를 내야 하는지부터 확인해야 한다.

이번 장은 앞의 여덟 장을 한 프로그램에 연결하는 종합 실습이다. 요구사항을 정하고, 잘못된 코드를 실행 경로로 읽고, 최소 수정으로 원인을 분리하고, 입력 검증과 원본 보존을 추가한 뒤 테스트한다. 실제 달력 서버나 푸시 알림은 다루지 않는다. 날짜를 계산한 결과인 “오늘로부터 며칠 뒤인가”라는 정수만 사용해 선택 로직에 집중한다.

## 9.1 자연어 요청을 검사 가능한 약속으로 만들기

“일주일 안”이라는 말부터 분명히 정하자. 이번 기능은 오늘을 `0`, 내일을 `1`로 표현하며 `0`부터 `7`까지 모두 포함한다. `-1`은 어제 예정이었던 기한 지난 작업이다. 기한 지난 작업은 다른 화면에서 다룬다고 정했으므로 이 목록에서는 제외한다. 제외한다는 것은 원본 기록을 삭제한다는 뜻이 아니다.

각 작업은 `id`, `title`, `done`, `days`라는 네 필드를 가진 딕셔너리다. `id`는 서로 다른 양의 정수 작업 번호, `title`은 비어 있지 않은 문자열 제목, `done`은 완료 여부를 나타내는 `True` 또는 `False`, `days`는 오늘로부터 남은 날 수를 나타내는 정수다. 예를 들어 `{"id": 12, "title": "자료 정리", "done": False, "days": 2}`는 이틀 뒤 예정이고 아직 끝내지 않은 작업이다.

결과는 조건에 맞는 작업의 새 목록이다. 예정일이 가까운 순서로 정렬하며 같은 날이면 작업 번호가 작은 순서로 정렬한다. 원본 목록과 원본 작업 딕셔너리를 변경하지 않는다. 결과에는 위 네 필드만 담는다. 입력에 그 밖의 필드가 있더라도 원본은 그대로 보존하고 이 결과 목록에는 옮기지 않는다. 잘못된 자료는 조용히 정상 작업처럼 고치지 않고 예외로 알린다.

| 사례 | 이 목록에 포함하는가? |
| --- | --- |
| 오늘 예정이고 미완료 | 포함 |
| 7일 뒤 예정이고 미완료 | 포함 |
| 8일 뒤 예정이고 미완료 | 제외 |
| 어제 예정이고 미완료 | 제외하되 원본에는 보존 |
| 2일 뒤 예정이지만 완료 | 제외 |
| 수량처럼 보이는 문자열 `"2"`가 days에 있음 | 이 함수의 입력 계약 위반으로 거절 |

여기서 문자열 날짜를 거절하는 것은 모든 앱에서 문자열을 쓰면 안 된다는 뜻이 아니다. 서버에서 문자열로 받아 변환하는 경계를 별도로 둘 수 있다. 이번 함수는 변환이 끝난 정수를 받는다는 약속을 택했으므로 내부에서 추측하지 않는 것이다.

## 9.2 잘못된 함수에서 실행 경로를 찾기

기존 함수가 다음과 같다고 하자. 의도적인 오류를 포함한 코드다. 이름이 그럴듯해도 요구사항을 만족하는지는 별도로 확인해야 한다.

```python
def wrong_upcoming(tasks):
    result = []
    for task in tasks:
        if task["days"] < 7 and task["done"]:
            result.append(task)
        return result


tasks = [
    {"id": 30, "title": "보고", "done": True, "days": 2},
    {"id": 20, "title": "통화", "done": False, "days": 7},
    {"id": 10, "title": "정리", "done": False, "days": 0},
]
print(wrong_upcoming(tasks))
```
```text
[{'id': 30, 'title': '보고', 'done': True, 'days': 2}]
```

첫 원소 30번을 보자. 남은 날 수 `2`는 `7`보다 작고 완료 값은 `True`이므로 조건이 참이다. 이 작업을 결과에 넣는다. 다음 줄의 `return`은 반복문 본문 안에 있어 첫 반복에서 함수 전체를 끝낸다. 따라서 뒤의 20번과 10번은 검사하지도 않는다.

오류를 나누면 세 가지다. 미완료가 아니라 완료 작업을 골랐다. 7일을 포함해야 하는데 `< 7`로 제외했다. 첫 반복에서 반환해 나머지 작업을 건너뛰었다. 여기에 기한 지난 음수를 제외하는 하한 조건도 없다. 이처럼 잘못된 결과 하나에 원인이 여러 개일 수 있으므로, 하나를 고친 뒤 다른 사례로 남은 문제를 확인해야 한다.

### 연습 9-2. 첫 원소만 바꾸면 숨는 오류

입력의 첫 원소가 미완료 작업이라면 위 함수는 어떤 값을 반환할까? 그 결과만 보고 “완료된 작업을 잘 제외한다”고 판단해도 될까?

### 풀이 9-2

현재 조건은 `task["done"]`이 참이어야 통과한다. 첫 원소가 미완료면 추가하지 않고 반복 안의 반환문에서 빈 목록을 돌려준다. 빈 목록이 나왔다고 완료 필터가 올바르다는 뜻은 아니다. 이번에는 조건이 맞지 않은 채 조기 반환했을 뿐이다. 서로 다른 입력에서 실제로 어떤 경로를 거쳤는지 확인해야 한다.

## 9.3 먼저 선택 규칙만 바로잡기

정렬과 검증을 동시에 추가하기 전에 선택 조건과 반환 위치부터 고치자. `not task["done"]`은 완료 여부가 거짓일 때 참이다. `0 <= task["days"] <= 7`은 하한과 상한을 모두 포함하는 비교다. `0 <= days and days <= 7`과 같은 의미로 읽을 수 있다.

```python
def select_upcoming(tasks):
    result = []
    for task in tasks:
        if not task["done"] and 0 <= task["days"] <= 7:
            result.append(task)
    return result


tasks = [
    {"id": 30, "title": "보고", "done": True, "days": 2},
    {"id": 20, "title": "통화", "done": False, "days": 7},
    {"id": 10, "title": "정리", "done": False, "days": 0},
]
selected = select_upcoming(tasks)
for task in selected:
    print(task["id"])
```
```text
20
10
```

이제 20번과 10번을 모두 골랐다. 아직 정렬하지 않았으므로 입력에서 나타난 순서다. 이 단계의 검사는 포함 여부를 보는 것이지 최종 순서까지 완성되었다고 주장하는 것이 아니다. 큰 변경을 나누면 현재 어떤 요구사항까지 충족했는지 분명해진다.

### 연습 9-3. 경계 사례 추가하기

남은 날 수가 `-1`, `0`, `7`, `8`인 미완료 작업을 각각 하나씩 넣었을 때 어떤 두 값을 가진 작업이 선택되어야 하는가? 하한을 빼면 어느 사례에서 실패하는가?

### 풀이 9-3

`0`과 `7`만 선택되어야 한다. `days <= 7`만 쓰면 `-1`도 통과한다. 사람은 “일주일 안”에 지난 작업을 포함할지 서로 다르게 해석할 수 있으므로, 먼저 정한 이번 기능의 규칙을 기준으로 검사한다. 코드의 조건은 그 합의된 범위를 정확히 나타내야 한다.

## 9.4 원본 보존과 정렬을 추가하기

현재 선택 함수는 새 바깥 목록을 만들지만 안쪽 작업 딕셔너리는 원본과 공유한다. 결과에서 제목을 수정해도 원본에 영향을 주지 않게 하려면 결과용 작업을 새로 구성해야 한다. 이번 출력의 네 필드는 정수·문자열·불리언이므로 각각의 값을 담은 새 딕셔너리면 충분하다.

```python
def task_order(task):
    return (task["days"], task["id"])


def upcoming_tasks(tasks):
    result = []
    for task in tasks:
        if not task["done"] and 0 <= task["days"] <= 7:
            copied = {
                "id": task["id"],
                "title": task["title"],
                "done": task["done"],
                "days": task["days"],
            }
            result.append(copied)
    return sorted(result, key=task_order)


tasks = [
    {"id": 20, "title": "통화", "done": False, "days": 7},
    {"id": 12, "title": "점검", "done": False, "days": 0},
    {"id": 10, "title": "정리", "done": False, "days": 0},
]
result = upcoming_tasks(tasks)
for task in result:
    print(task["id"], task["title"])
result[0]["title"] = "화면에서 수정한 제목"
print("원본 제목:", tasks[2]["title"])
```
```text
10 정리
12 점검
20 통화
원본 제목: 정리
```

정렬 기준 함수는 `(days, id)`라는 두 값 묶음을 반환한다. 이런 튜플은 앞의 값을 먼저 비교하고 그 값이 같으면 뒤의 값을 비교한다. 그래서 오늘 작업 두 개는 id 10, 12 순서가 되고, 7일 뒤 작업은 그 다음에 온다.

여기서 사용한 `sorted`는 `result`의 정렬된 새 목록을 만든다. 이미 `result` 자체가 원본과 별개이므로 제자리 정렬을 사용해도 원본 목록 순서를 바꾸지는 않는다. 다만 반환값을 받는 코드를 명확하게 읽도록 앞 장에서 익힌 `sorted`를 사용했다. 도구 선택과 원본 보존의 근거를 함께 설명할 수 있어야 한다.

### 연습 9-4. 새 목록이라는 주장 검증하기

결과의 첫 작업 제목을 바꿔 본 뒤 원본의 같은 작업 제목을 확인하는 검사는 무엇을 확인하는가? 원본 목록의 순서만 비교하는 검사와 차이를 설명해 보자.

### 풀이 9-4

목록 순서 비교는 바깥 리스트가 변경되지 않았는지 확인한다. 결과 딕셔너리의 제목을 바꾼 뒤 원본 제목을 확인하는 검사는 안쪽 작업 딕셔너리도 별개인지 확인한다. 바깥 목록만 새로 만들고 작업 객체를 공유하면 첫 검사는 통과해도 둘째는 실패할 수 있다.

## 9.5 잘못된 입력은 조용히 추측하지 않는다

입력 검증을 추가할 차례다. `done`에 문자열 `"False"`가 들어왔다고 하자. 사람이 보기에는 거짓처럼 보이지만 비어 있지 않은 문자열은 조건식에서 참으로 취급된다. 그러므로 완료 여부에 실제 불리언만 허용한다는 계약을 확인해야 한다.

정수 필드에도 주의할 점이 있다. 파이썬에서 불리언은 정수의 하위형이어서 `isinstance(True, int)`가 참이다. 여기서는 작업 번호나 날짜 간격에 `True`가 들어오는 것을 허용하지 않으므로 `type(value) is int`로 정확히 정수형인지 확인한다. 이 방식은 모든 프로그램에서 무조건 더 좋은 검사가 아니라, 이번 입력 계약의 요구에 맞춘 선택이다.

검증 순서도 의미가 있다. 먼저 전체 입력이 리스트인지, 각 항목이 딕셔너리인지, 필수 키가 있는지 확인해야 이후의 값 조회가 가능하다. 그다음 값의 자료형과 범위를 확인한다. 중복 작업 번호는 목록 전체에서 비교해야 하므로 별도의 확인 목록을 둔다. 완료되어 화면에 나오지 않을 작업도 원본 자료 계약은 지켜야 하므로 **선택하기 전에 모든 항목을 검증**한다.

### 연습 9-5. 잘못된 값을 어디서 거절하는가?

완료된 작업 하나에서 `days`가 문자열인데 어차피 결과에 포함하지 않는다는 이유로 검증하지 않고 건너뛰어도 되는가? 이번 함수가 “모든 입력 작업의 형식을 검사한다”고 약속했다는 점을 기준으로 답해 보자.

### 풀이 9-5

그 약속 아래에서는 거절해야 한다. 선택될 항목만 검증하면 같은 잘못된 자료가 완료 여부에 따라 통과하기도 하고 실패하기도 한다. 자료를 미리 검사한 뒤 선택하는 단계로 나누면 계약이 분명하다. 다른 정책을 택할 수는 있지만, 조용히 섞어 쓰지 말고 명시적으로 정해야 한다.

## 9.6 최종 프로그램 전체

아래 코드는 검증·선택·복사·정렬을 모두 포함한 독립 실행 예제다. 앞의 부분 코드를 합칠 필요 없이 이 블록 전체를 실행할 수 있다. `validate_task`는 한 작업을 검사하고, `upcoming_tasks`는 전체 목록 검증과 중복 번호 확인 뒤 결과를 만든다. 오류가 발생한 입력의 일부 결과를 정상처럼 반환하지 않는다.

```python
def validate_task(task):
    if not isinstance(task, dict):
        raise TypeError("각 작업은 딕셔너리여야 합니다")

    required = ["id", "title", "done", "days"]
    for field in required:
        if field not in task:
            raise ValueError("필수 항목 누락: " + field)

    if type(task["id"]) is not int:
        raise TypeError("작업 번호는 정수여야 합니다")
    if task["id"] <= 0:
        raise ValueError("작업 번호는 양수여야 합니다")
    if not isinstance(task["title"], str):
        raise TypeError("제목은 문자열이어야 합니다")
    if task["title"].strip() == "":
        raise ValueError("제목은 비어 있을 수 없습니다")
    if type(task["done"]) is not bool:
        raise TypeError("완료 여부는 True 또는 False여야 합니다")
    if type(task["days"]) is not int:
        raise TypeError("남은 날 수는 정수여야 합니다")


def task_order(task):
    return (task["days"], task["id"])


def upcoming_tasks(tasks):
    """입력을 검증하고, 0~7일의 미완료 작업을 새 자료로 정렬해 반환한다."""
    if not isinstance(tasks, list):
        raise TypeError("작업 전체는 리스트여야 합니다")

    seen_ids = []
    for task in tasks:
        validate_task(task)
        if task["id"] in seen_ids:
            raise ValueError("중복 작업 번호")
        seen_ids.append(task["id"])

    result = []
    for task in tasks:
        if not task["done"] and 0 <= task["days"] <= 7:
            result.append({
                "id": task["id"],
                "title": task["title"],
                "done": task["done"],
                "days": task["days"],
            })
    return sorted(result, key=task_order)


tasks = [
    {"id": 30, "title": "보고", "done": True, "days": 2},
    {"id": 20, "title": "통화", "done": False, "days": 7},
    {"id": 10, "title": "정리", "done": False, "days": 0},
    {"id": 40, "title": "지난 일", "done": False, "days": -1},
    {"id": 50, "title": "다음 주", "done": False, "days": 8},
]

for task in upcoming_tasks(tasks):
    print(task["id"], task["title"], task["days"])
```
```text
10 정리 0
20 통화 7
```

코드가 길어졌다고 한 번에 외워야 할 내용이 늘어난 것은 아니다. 각 구간은 앞에서 다룬 짧은 패턴이다. 필수 키 목록을 순회하고, 잘못된 값이면 예외를 발생시키고, 이미 본 번호 목록을 확인하고, 조건에 맞는 작업을 모은 뒤 정렬한다. 모르는 줄이 있다면 그 줄이 입력을 검사하는 부분인지 결과를 만드는 부분인지부터 찾아 읽으면 된다.

중복 번호 검사는 이해하기 쉬운 리스트 검색을 사용했다. 작업 수가 매우 커지면 확인용 집합을 사용하는 쪽이 효율적일 수 있다. 하지만 이 장의 목표는 대규모 서버 최적화가 아니라 데이터 계약과 수정 근거를 읽는 것이다. 실제 대규모 앱에 적용할 때는 입력 크기에 맞는 성능 검사도 별도로 해야 한다.

### 연습 9-6. 두 반복문의 역할

`upcoming_tasks` 안에 반복문이 두 개 있는 이유를 설명해 보자. 첫 반복에서 결과를 바로 추가하면서 검증까지 하면 어떤 상황을 주의해야 할까?

### 풀이 9-6

첫 반복은 모든 입력이 계약에 맞는지 확인하고, 둘째는 검증된 입력에서 결과를 만든다. 분리하면 완료 작업을 포함한 전체 검증이라는 정책이 읽기 쉽다. 한 반복으로 구현할 수도 있지만 중간에 잘못된 자료가 나왔을 때 일부 결과를 반환하거나 외부에 먼저 저장하지 않도록 주의해야 한다. 반복 수만 줄이는 것보다 실패 시 동작을 명확하게 유지하는 것이 우선이다.

## 9.7 같은 프로그램을 검사하는 전체 테스트

앞의 함수가 실제 약속을 지키는지 테스트해 보자. 아래 블록은 위 최종 예제의 함수 정의를 포함하지 않으므로 단독 실행용이 아니다. 앱에서는 이 절의 전체 실습 버튼으로 함수 정의와 아래 검사들을 함께 실행한다. 코드 파일에서 공부한다면 앞의 세 함수 정의 뒤에 붙이면 된다. 독립 실행용 완성 파일도 교재 부록에 함께 제공한다.

```python capstone-tests
from copy import deepcopy


def ids(tasks):
    result = []
    for task in tasks:
        result.append(task["id"])
    return result


def must_raise(exception_type, value):
    raised = False
    try:
        upcoming_tasks(value)
    except exception_type:
        raised = True
    assert raised


sample = [
    {"id": 30, "title": "완료", "done": True, "days": 2},
    {"id": 20, "title": "7일", "done": False, "days": 7},
    {"id": 12, "title": "오늘B", "done": False, "days": 0},
    {"id": 10, "title": "오늘A", "done": False, "days": 0},
    {"id": 40, "title": "지난 일", "done": False, "days": -1},
    {"id": 50, "title": "8일", "done": False, "days": 8},
]
before = deepcopy(sample)
result = upcoming_tasks(sample)
assert ids(result) == [10, 12, 20]
assert sample == before
assert result is not sample
result[0]["title"] = "변경한 제목"
assert sample == before
assert upcoming_tasks([]) == []
assert upcoming_tasks([sample[0]]) == []

valid = {"id": 1, "title": "작업", "done": False, "days": 1}
for field in ["id", "title", "done", "days"]:
    broken = valid.copy()
    del broken[field]
    must_raise(ValueError, [broken])

bad_cases = [
    ("id", True, TypeError),
    ("id", 0, ValueError),
    ("title", 123, TypeError),
    ("title", "   ", ValueError),
    ("done", "False", TypeError),
    ("done", 0, TypeError),
    ("days", "2", TypeError),
    ("days", True, TypeError),
]
for field, value, error in bad_cases:
    broken = valid.copy()
    broken[field] = value
    must_raise(error, [broken])

must_raise(TypeError, {})
must_raise(TypeError, ["작업"])
must_raise(ValueError, [valid, valid.copy()])

hidden_bad = valid.copy()
hidden_bad["done"] = True
hidden_bad["days"] = "2"
must_raise(TypeError, [hidden_bad])

with_extra = valid.copy()
with_extra["private_note"] = ["내부용"]
extra_before = deepcopy(with_extra)
extra_result = upcoming_tasks([with_extra])
assert set(extra_result[0]) == {"id", "title", "done", "days"}
assert with_extra == extra_before
print("선택·정렬·원본 보존·잘못된 입력 검사 통과")
```
```text
선택·정렬·원본 보존·잘못된 입력 검사 통과
```

처음에는 코드가 길어 보여도 검사 묶음을 나누어 읽자. 첫 묶음은 결과 순서, 원본 보존, 빈 목록, 완료 작업만 있는 목록을 검사한다. 둘째는 필수 키 누락을 하나씩 만든다. 셋째는 값의 자료형과 범위 오류를 만든다. 마지막은 전체 입력 형식, 중복 번호, 결과에 나오지 않는 작업의 검증, 추가 필드가 결과에서 제외되는지를 확인한다.

`del broken[field]`는 테스트용 복사본에서 키를 지우는 문장이다. 정상 예시를 조금씩 바꾸어 원하는 실패 조건을 만든다. `must_raise`는 우리가 만든 테스트 보조 함수이며, 기대한 예외가 발생했는지 확인한다. 기대한 종류와 다른 예외가 나오면 통과시키지 않는다.

이 검사들이 통과해도 인터넷 연결, 저장 서버, 실제 달력 시간대, 화면 푸시 알림을 확인한 것은 아니다. 함수의 계산과 자료 계약을 검사한 것이다. 앱 전체를 만든다면 UI 버튼부터 저장과 재조회까지 이어지는 검사가 추가로 필요하다. 검증 결과는 검사한 대상 범위와 함께 읽어야 한다.

### 연습 9-7. 요구사항 변경을 테스트부터 반영하기

사용자가 일주일이 아니라 3일 이내 작업만 보여 달라고 했다. 가장 먼저 바꿀 기대 사례는 무엇인가? 구현에서는 어느 숫자를 바꾸어야 하는가? 기한 지난 작업을 제외하는 하한 조건도 지워야 할까?

### 풀이 9-7

`days`가 3인 작업은 포함, 4인 작업은 제외라는 경계 기대값을 먼저 적는다. 선택 조건의 상한 `7`을 `3`으로 바꾼다. 오늘부터라는 시작 조건은 바뀌지 않았으므로 하한 `0`은 유지한다. 기존에 7일 작업을 포함하던 테스트는 새 정책에 맞게 기대값을 갱신하고, 완료·원본 보존·입력 검증 같은 바뀌지 않은 계약은 계속 검사한다.

### 연습 9-8. 기능을 직접 확장하기

완료 여부와 날짜 범위는 유지하되 제목에 특정 단어가 들어간 작업만 고르고 싶다. 대소문자 변환이나 한글 정규화는 이번 범위에서 제외하고, 입력 단어가 제목 문자열에 그대로 포함되는지만 확인한다. 현재 선택 조건에 어떤 비교를 추가할 수 있을까? 빈 검색어는 어떤 결과가 되는지 먼저 정해 보자.

### 풀이 9-8

함수에 `keyword`를 입력으로 추가하고 조건에 `keyword in task["title"]`를 연결할 수 있다. 파이썬 문자열에서 `in`은 부분 문자열 포함 여부를 검사한다. 빈 문자열은 모든 문자열에 포함되므로, 빈 검색어를 전체 보기로 정하면 이 동작을 그대로 사용할 수 있다. 빈 검색어를 금지하려면 입력 검증에서 명시적으로 거절해야 한다. 여기서도 문법보다 정책을 먼저 정한다.

## 9.8 수정 결과를 전달하는 법

누군가에게 “다 고쳤습니다”라고만 보고하면 무엇이 달라졌고 무엇이 확인되었는지 알기 어렵다. 이번 프로그램이라면 다음처럼 설명할 수 있다. 완료 조건과 날짜 경계, 반복문 안의 조기 반환을 수정했다. 모든 입력을 검증하고 결과용 딕셔너리를 새로 만들어 원본을 보존한다. 정렬은 날짜와 작업 번호 순서다. 제공한 테스트로 정상 선택, 경계, 빈 목록, 원본 보존, 잘못된 입력 거절을 확인했다. 실제 서버 저장과 기기 알림은 이 함수 검사 범위가 아니다.

이 문단에는 멋진 형용사보다 확인 가능한 사실이 들어 있다. AI에게 작업을 맡길 때도 같은 기준을 사용할 수 있다. 실제로 바뀐 파일, 기대 동작, 실행한 검사, 확인하지 못한 범위를 요구하면 말뿐인 완료와 실행 근거가 있는 완료를 구별하는 데 도움이 된다.

이번 트랙의 목적은 모든 코드를 빈 화면에서 암기해 쓰는 것이 아니었다. 이름과 연산을 구별하고, 실행 경로를 따라가고, 요구사항을 분해하고, 원본 변경을 추적하고, 함수의 입출력을 읽고, 패턴을 골라 적용하고, 오류를 재현하고, 검사하며 수정하는 능력을 만들었다. 처음 보는 프로그램도 이 질문들로 나누면 한꺼번에 모든 줄을 이해해야 하는 막막한 덩어리가 아니라 확인할 수 있는 작은 약속들의 연결이 된다.
